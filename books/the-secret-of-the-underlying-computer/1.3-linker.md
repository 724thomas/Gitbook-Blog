# 1.3 Linker

### 1. 링커는 이렇게 일한다

#### 1) 개념 정의

링커(linker)는 컴파일러가 만들어낸 여러 개의 오브젝트 파일과 라이브러리를 하나의 실행 파일로 합쳐주는 도구이다.

#### 2) 원리 설명

프로그램을 작성할 때 우리는 보통 코드를 여러 개의 소스 파일로 나누어 둔다. \
컴파일러는 이 소스 파일들을 각각 독립적으로 처리해 오브젝트 파일(`.o`)로 변환하는데, 이때 각 파일은 자기 안에 정의되지 않은 함수나 변수가 어디에 있는지 알지 못한 채 "빈자리"를 남겨둔 상태이다. \
링커는 이렇게 흩어진 조각들을 모아서 하나의 완성된 실행 파일을 만드는 역할을 한다. \
이 과정에서 링커는 크게 두 가지 문제를 해결해야 하는데,&#x20;

* 하나는 어떤 파일에서 사용된 이름(심벌)이 실제로 어느 파일에 정의되어 있는지를 찾아 연결하는 **심벌 해석(symbol resolution)**\*\*이고,&#x20;
* 다른 하나는 합쳐진 코드와 데이터가 메모리상 최종적으로 어디에 놓일지를 정해서 그에 맞춰 주소를 채워 넣는 **재배치(relocation)**&#xC774;다.&#x20;

즉 링커는 "조각 모으기 + 이름 연결 + 주소 확정"을 담당하는 빌드 파이프라인의 마지막 단계이다.

#### 3) 세부 메커니즘

링커의 입력으로 들어오는 오브젝트 파일은 단순한 기계어 덩어리가 아니라 여러 개의 **섹션(section)**&#xC73C;로 나뉘어 있다. \
대표적으로&#x20;

* 실행 가능한 명령어가 들어 있는 **코드(text) 섹션**,&#x20;
* 전역 변수 등이 들어 있는 데이터 섹션,&#x20;
* 이 파일이 어떤 이름을 정의했고 어떤 이름을 외부에서 가져다 쓰는지 기록한 **심벌 테이블**,&#x20;
* 그리고 "여기는 나중에 진짜 주소로 바꿔야 한다"를 표시해 둔 **재배치 정보**가 들어 있다.&#x20;

출력인 실행 파일도 비슷한 섹션 구조를 갖지만, 차이는 더 이상 빈자리가 남아 있지 않고 모든 주소가 채워져 바로 실행할 수 있는 상태라는 점이다. 링커는 이 변환을 위해 크게 세 단계를 거친다.

1. **섹션 모으기**: 입력으로 들어온 모든 오브젝트 파일의 같은 종류 섹션끼리 묶는다. 여러 `.o`의 코드(text) 섹션은 한 덩어리의 코드 섹션으로, 데이터 섹션은 한 덩어리의 데이터 섹션으로 합친다.
2. **심벌 해석**: 각 오브젝트가 "외부에서 가져다 쓴다"고 표시해 둔 이름들을, 다른 오브젝트나 라이브러리의 심벌 테이블에서 찾아 짝지어 준다. 짝을 찾지 못하면 흔히 보는 `undefined reference` 오류가 발생한다.
3. &#x20;**재배치**: 섹션들을 합치고 짝을 다 지었으니, 합쳐진 코드와 데이터가 메모리상 어느 위치에 놓일지가 정해진다. 링커는 그 위치 정보를 사용해 비워 두었던 자리를 실제 주소로 채워 넣는다.

이 세 단계가 끝나면 비로소 실행 가능한 하나의 파일이 완성된다.



<details>

<summary>"컴파일러가 이 소스 파일을 컴파일하는 시점에는 함수가 어느 메모리 주소에 위치할지 정확히 알 수 없습니다" 에서 "메모리 주소"는 엄밀히 말하면 틀린 얘기.</summary>

"컴파일러가 소스 파일을 컴파일하는 시점에는, 외부 함수나 전역 변수가 **최종 실행 파일 안에서 어느 위치에 배치될지** 알 수 없다. 따라서 컴파일러는 해당 참조 위치를 비워 두고 재배치 정보를 남긴다. 이후 링커가 여러 오브젝트 파일과 라이브러리를 합치면서 각 심벌의 최종 프로그램 기준 위치 또는 링커 기준 가상 주소를 계산하고, 참조해야 할 부분을 그 값이나 상대 offset으로 채워 넣는다. 실제 실행 시점의 주소는 로더가 프로그램을 메모리에 올릴 때 최종적으로 결정된다." 가 맞다

예를 들어 `a.c`에서 `b.c`에 정의된 함수를 호출한다고 해보자.

```
a.cCPU 설명 함수 호출
b.cCPU 설명 함수 정의
```

`a.c`를 컴파일할 때 컴파일러는 “CPU 설명 함수라는 이름의 함수를 호출해야 한다”는 사실은 알 수 있다. 하지만 `b.c`의 코드가 최종 실행 파일에서 `a.c` 뒤에 붙을지, 앞에 붙을지, 중간에 다른 코드가 들어갈지는 알 수 없다.

따라서 컴파일러는 그 자리에 정확한 주소를 바로 넣지 않고, 오브젝트 파일에 이런 표시를 남긴다.

<pre><code><strong>"여기서는 CPU 설명 함수를 참조해야 한다.정확한 위치는 나중에 링커가 채워라."
</strong></code></pre>

이후 링커가 여러 오브젝트 파일을 하나로 합치면서 최종 배치를 결정한다.

```
a.o 크기 = 1000
b.o 안의 함수 위치 = 100

b.o가 a.o 뒤에 붙는다면,함수의 최종 프로그램 내부 위치 = 1000 + 100 = 1100
```

이때 링커가 계산하는 `1100`은 실행 중의 최종 메모리 주소라기보다는, **최종 실행 파일 내부에서 확정된 위치** 또는 **링커가 가정한 가상 주소 기준 위치**에 가깝다.

그리고 실제 프로그램이 실행될 때는 OS의 로더가 실행 파일을 메모리에 올린다. 이때 ASLR 등의 이유로 프로그램이 매번 다른 위치에서 시작할 수 있다.

```
링커 기준 함수 위치 = 1100
이번 실행에서 프로그램 시작 위치 = 5000
실행 중 함수 위치 = 5000 + 1100 = 6100
```

따라서 실행 시점의 실제 가상 메모리 주소는 로더가 프로그램을 메모리에 올릴 때 결정된다. 링커가 미리 “실제 메모리 주소”를 정확히 알고 채워 넣는 것은 아니다.

</details>



#### 4) 예시

두 개의 소스 파일이 있다고 하자. `main.c`는 `add()`를 호출만 하고, `add.c`는 그 `add()`를 정의한다.

```c
// main.c
int add(int a, int b);   // 선언만 있음

int main(void) {
    return add(1, 2);
}
```

```c
// add.c
int add(int a, int b) {
    return a + b;
}
```

빌드 과정을 명령어로 따라가 보면 다음과 같다.

```bash
gcc -c main.c      # main.o 생성 (add 심벌은 "외부 참조"로 표시됨)
gcc -c add.c       # add.o  생성 (add 심벌이 "정의됨"으로 표시됨)
gcc main.o add.o -o a.out   # 링커가 두 .o를 합쳐 실행 파일 a.out 생성
```

각 단계의 산출물을 보면, `main.o`에는 `main` 함수의 코드가 들어 있지만 `add` 호출 지점은 "이 자리는 나중에 채워야 함"이라는 재배치 표시와 함께 비어 있다. \
`add.o`에는 `add` 함수의 코드와 함께 심벌 테이블에 `add`가 정의되어 있음이 적혀 있다. \
링커는 두 파일을 받아&#x20;

1. 코드/데이터 섹션끼리 모으고,&#x20;
2. `main.o`가 찾던 `add`가 `add.o`에 있다는 사실을 확인해 짝지어 주고,&#x20;
3. 합쳐진 결과에서 `add` 함수가 놓일 최종 주소를 결정해 `main.o`의 호출 지점에 그 주소를 채워 넣는다.&#x20;

그 결과로 만들어진 `a.out`은 더 이상 빈자리가 없는, 바로 실행 가능한 하나의 파일이다.

### 2. 심벌 해석: 수요와 공급

#### 1) 개념 정의

심벌 해석(symbol resolution)은 여러 오브젝트 파일에 흩어진 심벌의 참조(수요)와 정의(공급)를 짝지어, 같은 이름의 심벌이 메모리상의 동일한 실체를 가리키도록 묶어주는 과정이다.

#### 2) 원리 설명

각 `.o` 파일은 컴파일러가 만들어 놓은 **심벌 테이블**을 들고 있다. \
이 테이블에는&#x20;

* "내가 정의한 심벌(공급)"
* "내가 외부에 요청하는 심벌(수요)"

이 함께 적혀 있다.&#x20;

컴파일러는 하나의 소스 파일만 보기 때문에 다른 파일에 있는 함수나 전역 변수의 실제 위치를 알 수 없고, 그저 "이런 이름을 어디선가 가져다 써야 한다"라고 표시만 남겨 둔다. \
링커는 모든 오브젝트 파일의 심벌 테이블을 모아 놓고, 수요 쪽 항목 하나하나에 대해 어느 파일이 그것을 공급하는지 찾아 짝을 맞춘다. \
이 짝짓기가 끝나야 비로소 각 참조가 "어떤 정의를 가리키는지"가 확정된다. \
만약 짝을 찾지 못하면 **undefined reference**(정의되지 않은 참조) 오류가, 같은 이름의 공급자가 둘 이상이면 **multiple definition**(중복 정의) 오류가 발생하여 링크가 실패한다.

#### 3) 세부 메커니즘

심벌 테이블의 각 엔트리는 대략 다음과 같은 속성을 가진다.

* **이름(name)**: 함수·변수의 식별자
* **정의 여부**: 이 파일이 정의(공급)한 심벌인지, 외부에 요청(수요)하는 심벌인지
* **강·약 구분**: 정의된 심벌은 **강 심벌(strong symbol)**&#xACFC; **약 심벌(weak symbol)**&#xB85C; 나뉜다. 함수와 초기값이 있는 전역 변수는 강 심벌, 초기화되지 않은 전역 변수는 약 심벌로 취급된다고 보면된다.

링커는 모든 오브젝트의 심벌 테이블을 차례로 훑으며 "전역 매칭 표"를 만든다. \
한 심벌 이름에 대해 여러 정의가 들어오면 다음과 같은 단순 규칙으로 정리한다.

* 강 심벌끼리 충돌 → 오류
* 강 + 약 → 강 심벌 채택
* 약 + 약 → 하나를 선택 (어느 쪽이 선택되는지 세부 규칙은 환경에 따라 다르므로 _확인 필요_)

이렇게 만들어진 매칭 표가 곧 "어떤 참조가 어떤 정의로 연결되는가"의 정답표가 된다.

#### 4) 예시

**예시 1: 정상적으로 짝이 맞는 경우**

```c
// main.c
extern int counter;   // 수요: counter의 정의는 다른 파일에 있다
void add(void);       // 수요: add의 정의는 다른 파일에 있다

int main(void) {
    add();
    return counter;
}
```

```c
// add.c
int counter = 0;              // 공급: counter 정의
void add(void) { counter++; } // 공급: add 정의
```

링커가 두 오브젝트 파일을 보고 작성하는 매칭 표를 단순화하면 다음과 같다.

| 심벌        | main.o | add.o | 해석 결과         |
| --------- | ------ | ----- | ------------- |
| `main`    | 정의(강)  | -     | main.o의 정의 사용 |
| `counter` | 참조     | 정의(강) | add.o의 정의 사용  |
| `add`     | 참조     | 정의(강) | add.o의 정의 사용  |

수요와 공급이 모두 정확히 맞아떨어졌으므로 링크가 성공한다.

**예시 2: 공급이 없는 경우 (undefined reference)**

위 코드에서 `add.c`를 빼고 `main.o`만으로 링크를 시도하면, `counter`와 `add`에 대한 수요는 있지만 그것을 공급하는 오브젝트 파일이 없다. 링커는 매칭 표를 완성하지 못하고 다음과 같은 형태의 오류를 낸다.

```
main.o: in function `main':
main.c:(.text+0x...): undefined reference to `add'
main.c:(.text+0x...): undefined reference to `counter'
```

즉, "수요는 있는데 공급자가 없다"는 외침이 곧 `undefined reference` 메시지인 셈이다.



심벌 해석은 "어느 참조가 어느 정의를 가리키는지"만 결정할 뿐, 그 정의가 최종 실행 파일의 **어떤 주소**에 놓이는지는 아직 모른다. \
실제 주소를 채워 넣어 참조를 완성하는 작업은 다음 단계인 **재배치(relocation)**&#xC758; 몫이며, 재배치는 심벌 해석이 끝나 매칭 표가 완성된 뒤에야 비로소 시작된다.

### 3. 정적 라이브러리, 동적 라이브러리, 실행 파일

#### 1) 개념 정의

컴파일·링크 과정의 산출물 세 가지로,&#x20;

* 정적 라이브러리는 여러 오브젝트 파일(.o)을 묶은 아카이브,&#x20;
* 동적 라이브러리는 실행 중에 메모리에 적재되어 연결되는 공유 코드 파일,&#x20;
* 실행 파일은 운영체제가 직접 실행할 수 있는 최종 산출물이다.

#### 2) 원리 설명

컴파일러가 소스를 .o로 만든 다음, 링커는 이들을 어떻게 묶느냐에 따라 세 가지 결과물을 만들어낸다.&#x20;

* 정적 라이브러리(`.a` / `.lib`)는 단순히 여러 .o를 한 봉투에 담아둔 아카이브이며, 링크 시점에 필요한 부분이 실행 파일 안으로 **복사되어 박힌다**.&#x20;
* 동적 라이브러리(`.so` / `.dll` / `.dylib`)는 실행 파일에 코드를 박지 않고, "이 라이브러리의 어떤 심벌이 필요하다"라는 **메타정보만** 남겨둔 채 별도 파일로 존재한다.&#x20;
* 실행 파일은 OS의 로더가 읽어들여 프로세스로 띄울 수 있는 형태이며, 정적 라이브러리로부터 받은 코드는 이미 안에 들어 있고 동적 라이브러리는 이름·경로만 적혀 있다.&#x20;

즉 "코드를 언제 합치느냐"와 "코드가 실행 파일 안에 있느냐 밖에 있느냐"가 세 산출물을 가르는 핵심이다.

#### 3) 세부 메커니즘

두 축으로 정리하면 쉽다.

* **합쳐지는 시점**
  * 정적 라이브러리: **컴파일 타임(링크 단계)** 에 합쳐짐. 링커가 `.a` 안에서 필요한 `.o`만 골라 실행 파일에 포함시킴.
  * 동적 라이브러리: **로드 타임 또는 실행 타임** 에 합쳐짐. 프로그램이 실행될 때 OS의 동적 로더가 `.so`/`.dll`을 메모리에 올리고 심벌 주소를 채워 넣음.
* **코드가 어디에 있는가**
  * 정적: 라이브러리 코드의 사본이 실행 파일 내부에 들어 있음 → 실행 파일이 커지지만 자기 완결적.
  * 동적: 실행 파일에는 "libfoo.so의 bar 함수를 부른다"는 참조만 있고, 진짜 코드는 디스크의 별도 파일에 있음 → 실행 파일은 작지만 그 `.so`가 있어야 동작.

실행 파일 자체도 결국 정적 링크의 결과로 만들어지는 "OS가 실행할 수 있는 형식"(예: ELF, PE)이며, 동적 라이브러리에 대한 참조 목록을 헤더에 함께 담고 있다.

#### 4) 예시

같은 `add` 함수를 정적·동적 라이브러리로 빌드해보면 차이가 분명히 드러난다. \
정적 라이브러리는 보통 `-fPIC` 없이, 동적 라이브러리는 `-fPIC`로 빌드한다.

```bash
# 1) 정적 라이브러리
gcc -c add.c -o add_static.o
ar rcs libadd.a add_static.o

# 2) 동적 라이브러리
gcc -c -fPIC add.c -o add_pic.o
gcc -shared add_pic.o -o libadd.so

# 3) 각각 링크해서 실행 파일 만들기
gcc main.c -L. -ladd -static -o app_static   # 코드가 실행 파일에 박힘
gcc main.c -L. -ladd          -o app_dynamic # 참조만 박힘
```

이렇게 만들면 `app_static`은 add 함수 코드가 안에 박혀 있어 파일 크기가 크고, `app_dynamic`은 훨씬 작은 대신 실행 시 `libadd.so`가 필요하다. 의존하는 동적 라이브러리는 다음처럼 확인할 수 있다.

```bash
ldd app_dynamic
# 출력 예:
#   libadd.so => ./libadd.so (0x00007f...)
#   libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
```

`app_static`에 대해 같은 명령을 돌리면 "not a dynamic executable"이라고 나오거나 의존 라이브러리가 거의 없는 식으로 차이가 보인다.



세 산출물의 구분은 곧 "정적 링크 vs 동적 링크" 선택의 결과물이며, 동적 라이브러리를 고르는 순간 **장단점 트레이드오프**가 자동으로 따라온다.

### 4. 동적 라이브러리의 장단점

#### 1) 개념 정의

동적 라이브러리는 실행 시점에 연결되는 방식 덕분에 자원 절약·유지보수 용이성이라는 장점을 얻는 대신, 실행 시점 의존성과 버전 호환 문제라는 비용을 함께 짊어지는 링크 방식이다.

#### 2) 원리 설명

정적 링크와 비교하면 장단점이 명확해진다. \
장점 쪽에서는,&#x20;

* 같은 `.so` 하나를 수많은 프로그램이 공유할 수 있어서 **디스크와 메모리를 절약**할 수 있고,&#x20;
* 버그를 고칠 때 라이브러리 파일만 교체하면 그것을 사용하는 모든 프로그램이 자동으로 패치 효과를 받는다.&#x20;
* 또한 실행 중에 필요한 모듈을 골라 끼워 넣는 **플러그인 아키텍처**도 동적 링크가 있어야 가능하다.&#x20;

단점 쪽에서는,&#x20;

* 실행 시 라이브러리를 찾아 로드하고 심벌을 해석하는 **런타임 비용**이 들고,&#x20;
* 라이브러리 버전이 바뀌었을 때 함수 시그니처가 어긋나면 프로그램이 깨질 수 있다.&#x20;
* 라이브러리 파일이 사라지거나 경로가 어긋나면 실행 자체가 안 되며, 악의적인 `.so`로 바꿔치기당하는 보안 위험도 존재한다.

#### 3) 세부 메커니즘

"메모리 절약이 왜 가능한가"가 핵심이다. \
OS는 같은 `.so`의 **코드(text) 섹션을 담은 페이지**를 메모리에 한 번만 올려두고, 그것을 사용하는 모든 프로세스의 가상 주소 공간에 **매핑**해준다. \
즉 100개의 프로그램이 libc를 쓰더라도 libc의 코드 자체는 물리 메모리에 한 벌만 존재한다. \
데이터 영역은 프로세스마다 달라야 하므로 분리되지만, 가장 덩치가 큰 코드는 공유되므로 시스템 전체의 메모리 사용량이 크게 줄어든다.

반대로 단점 쪽 메커니즘은, 실행 파일이 동적 라이브러리의 "이름과 필요한 심벌 목록"만 가지고 있기 때문에, 실제 라이브러리의 함수 시그니처가 바뀌거나 같은 이름의 다른 버전이 로드되면 잘못된 코드를 호출해 충돌할 수 있다는 점에서 비롯된다. \
과거 윈도우에서 흔하던 "DLL 지옥(DLL Hell)"이 대표적인 사례다.

#### 4) 예시

**메모리 공유 시나리오**: 리눅스에서 ls, cat, bash, python 등 거의 모든 실행 파일이 `libc.so.6`에 의존한다. `ldd`로 확인해보면 다음과 같이 같은 libc를 가리킨다.

```bash
ldd /bin/ls   | grep libc
# libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)

ldd /bin/cat  | grep libc
# libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
```

수십\~수백 개의 프로세스가 동시에 떠 있어도 libc의 코드는 물리 메모리에 사실상 한 벌만 존재한다. \
만약 모두 정적 링크였다면 같은 코드의 사본이 모든 실행 파일·모든 프로세스마다 따로 존재했을 것이다.

**재컴파일 없는 패치 시나리오**: `libssl.so`에 보안 취약점이 발견되어 새 버전이 배포되었다고 하자. \
정적 링크 환경이라면 이 라이브러리를 사용한 모든 프로그램을 다시 빌드·배포해야 한다. \
동적 링크 환경이라면 시스템의 `libssl.so` 파일 하나만 교체하면 끝이고, 그 다음 실행되는 모든 프로그램이 자동으로 새 버전을 사용하게 된다. \
반대로 이 `.so`가 손상되거나 삭제되면 의존하는 모든 프로그램이 한꺼번에 실행 불가가 되는 위험도 같이 따라온다.



이 트레이드오프는 "동적 라이브러리는 코드가 실행 파일 밖에 있다"는 구조에서 직접 비롯된 결과이며, 운영체제의 **로더와 가상 메모리**가 있어야 비로소 의미를 갖는다.

> **TMI**
>
> * 동적 링킹 함수 호출은 첫 호출 시점에 주소를 해석하는 "lazy binding" 방식이 기본인데, 이 덕분에 프로그램 시작은 빠르지만 첫 호출이 미세하게 느려진다. 보안 강화(RELRO, BIND\_NOW)를 적용하면 시작 시점에 모든 심벌을 해석해 lazy binding을 끄는데, Chrome 같은 보안 민감 프로젝트는 이쪽을 선호한다.
> * Windows의 악명 높은 "DLL Hell"은 1990년대 후반 \~ 2000년대 초 여러 앱이 같은 DLL의 다른 버전을 시스템 폴더에 덮어쓰면서 다른 앱을 망가뜨린 사태를 가리킨다. Microsoft가 이를 해결하려 .NET의 GAC(Global Assembly Cache)와 side-by-side assembly(WinSxS) 메커니즘을 도입했다.

### 5. 재배치: 심벌의 실행 시 주소 결정하기

#### 1) 개념 정의

재배치(relocation)란 컴파일 시점에는 알 수 없었던 심벌의 최종 주소를, 링커가 심벌 해석 결과를 바탕으로 계산해 오브젝트 파일에 비어 있던 "주소 자리"에 채워 넣는 과정이다.

#### 2) 원리 설명

컴파일러가 하나의 `.c` 파일을 `.o`로 만들 때, 그 파일이 참조하는 외부 함수나 전역 변수가 최종 실행 파일의 어느 위치에 배치될지 알 방법이 없다. \
다른 `.o` 파일들이 어떻게 합쳐질지, 코드(text) 섹션이 어디서부터 시작할지는 모두 링커가 정하는 일이기 때문이다. \
그래서 컴파일러는 외부 심벌을 사용하는 명령어의 주소 피연산자 자리를 일단 0으로 비워 두고, "이 위치(offset)는 심벌 X의 주소로 나중에 채워야 함"이라는 메모를 함께 남긴다. \
이 메모들을 모아 둔 것이 **재배치 테이블(relocation table)**&#xC774;다. \
링커는 심벌 해석을 끝낸 뒤 각 심벌이 실행 파일에서 차지할 최종 주소를 알게 되므로, 재배치 테이블의 항목들을 하나씩 처리하면서 비어 있던 주소 자리를 그 최종 주소로 덮어쓴다. \
이 단계가 끝나야 비로소 모든 `call`, `jmp`, 전역 변수 접근 명령어가 "올바른 곳"을 가리키게 된다.

#### 3) 세부 메커니즘

오브젝트 파일은 단순히 기계어의 나열이 아니라, "기계어 + 그 기계어 안에서 아직 결정되지 않은 자리의 목록"이라는 두 층의 정보를 함께 담고 있다. \
예를 들어 `call add`라는 한 줄의 어셈블리는 컴파일 직후 `call 0x00000000`처럼 명령어 opcode와 0으로 채워진 4바이트 피연산자로 변환되어 코드(text) 섹션에 박힌다. \
동시에 재배치 테이블에는 "코드 섹션 안의 오프셋 N번지에 있는 4바이트는 심벌 `add`의 주소로 패치하라"라는 항목이 추가된다. \
링커는 모든 `.o`를 모은 다음, 각 섹션이 실행 파일의 어느 가상 주소에서 시작하는지를 정한다(예: 코드 섹션은 `0x401000`부터). \
그러면 `add`라는 심벌이 최종적으로 `0x4011a0`에 위치한다는 사실이 정해지고, 링커는 재배치 테이블의 안내에 따라 그 4바이트 자리를 `0x4011a0`(또는 PC 상대 변위)으로 채워 넣는다. \
비어 있던 구멍이 모두 메워지면 실행 파일이 완성된다. (동적 라이브러리의 경우 일부 재배치는 실행 시점으로 미뤄진다.)

#### 4) 예시

`main.c`가 다른 파일에 정의된 `add`를 호출한다고 하자.

```c
// main.c
int add(int, int);
int main(void) { return add(1, 2); }
```

`gcc -c main.c`로 만들어진 `main.o`를 `objdump -d main.o`로 들여다보면 `call` 명령어의 주소 피연산자가 비어 있는 모습을 볼 수 있다.

```
0000000000000000 <main>:
   ...
   e:   e8 00 00 00 00          call   13 <main+0x13>   ; 피연산자가 00 00 00 00
   ...
```

그리고 `objdump -r main.o`로 재배치 테이블을 보면, 그 자리에 어떤 심벌이 들어가야 하는지가 적혀 있다.

```
RELOCATION RECORDS FOR [.text]:
OFFSET            TYPE              VALUE
000000000000000f  ...               add
```

링커가 `main.o`와 `add.o`를 합쳐 실행 파일을 만들면서 `add`의 최종 주소를 예컨대 `0x4011a0`으로 정했다면, 재배치 테이블의 안내에 따라 오프셋 `0xf`의 4바이트가 `add`의 위치를 가리키도록 패치된다. \
최종 실행 파일을 `objdump -d`로 보면 비어 있던 자리가 채워진 것을 확인할 수 있다.

```
0000000000401120 <main>:
   ...
   40112e:   e8 6d 00 00 00      call   4011a0 <add>
   ...
```



링커가 "최종 가상 주소"라는 구체적인 숫자를 박아 넣을 수 있는 이유는, 각 프로세스가 독립된 가상 주소 공간을 가진다는 전제가 있기 때문이다. \
또한 재배치는 심벌 해석이 끝나야만 가능하다 — 어떤 정의를 가리킬지 먼저 정해져야 그 주소를 채워 넣을 수 있다.

### 6. 가상 메모리와 프로그램 메모리 구조

#### 1) 개념 정의

가상 메모리는 운영체제와 하드웨어(MMU)가 협력해 각 프로세스에게 "나만 쓰는 독립된 주소 공간"이라는 환상을 제공하는 추상화이며, 그 공간은 보통 코드(text)·데이터·힙·스택 같은 영역으로 정형화되어 배치된다.

#### 2) 원리 설명

실제 컴퓨터에는 물리 메모리가 한 덩어리만 있고 그것을 모든 프로세스가 나눠 써야 한다. \
만약 프로그램이 직접 물리 주소를 다뤄야 한다면, 두 프로그램이 같은 주소를 쓰려 할 때 충돌이 나고, 링커는 어떤 주소가 비어 있을지를 매번 예측해야 할 것이다. \
이를 막기 위해 OS는 각 프로세스에게 "이 프로세스는 0번지부터 메모리 끝까지를 혼자 다 쓰는 것처럼" 보이게 만든다.&#x20;

프로세스가 사용하는 주소는 **가상 주소**이고, CPU의 MMU가 이를 실제 물리 주소로 변환해 준다. \
덕분에 서로 다른 프로세스가 같은 가상 주소 `0x401000`을 사용해도, 실제로는 물리 메모리의 서로 다른 위치에 매핑되므로 충돌하지 않는다. \
그리고 한 프로세스의 가상 주소 공간 안에서는 코드·전역 데이터·힙·스택이 미리 약속된 영역에 자리 잡는 표준 레이아웃이 존재한다.

#### 3) 세부 메커니즘

한 프로세스의 가상 주소 공간을 낮은 주소부터 높은 주소로 죽 그려 보면 대략 다음과 같이 나뉜다.

* **코드(text) 섹션**: 실행할 기계어 명령. 보통 읽기 전용.
* **데이터 영역**: 초기값이 있는 전역/정적 변수(`.data` 섹션)와 초기값이 0(또는 미지정)인 변수(`.bss` 섹션).
* **힙(heap)**: `malloc` 등으로 동적으로 할당되며, 낮은 주소에서 높은 주소 쪽으로 자라난다.
* **스택(stack)**: 함수 호출의 지역 변수와 호출 프레임이 쌓이는 곳으로, 높은 주소에서 낮은 주소 쪽으로 자라난다.

핵심은, 모든 프로세스가 이 동일한 레이아웃을 자기 가상 주소 공간 안에서 똑같이 사용한다는 점이다. \
그래서 링커는 "코드(text) 섹션은 항상 어디서부터 시작한다"처럼 고정된 가상 주소를 가정하고 재배치를 수행할 수 있다. \
두 프로그램이 같은 가상 주소를 쓰더라도 OS와 MMU가 각자를 다른 물리 페이지로 연결해 주므로 서로 간섭이 일어나지 않는다.

#### 4) 예시

같은 `hello.out`을 두 번 실행해 두 개의 프로세스가 떴다고 하자. \
두 프로세스의 `main` 함수는 둘 다 가상 주소 `0x401000`(예시)에 위치한다 — 같은 실행 파일에서 나왔으니. \
그러나 OS가 만든 두 프로세스의 매핑은 독립적이어서, 한 프로세스의 `0x401000`은 물리 메모리의 한 페이지에, 다른 프로세스의 `0x401000`은 또 다른 페이지에 연결된다. \
같은 숫자 주소지만 실제로는 다른 메모리를 가리키는 셈이다.

리눅스에서 한 프로세스의 가상 주소 레이아웃을 직접 들여다볼 수도 있다.

```
$ cat /proc/<pid>/maps
00400000-00401000 r-xp ... /home/user/hello.out   # 코드(text)
00601000-00602000 rw-p ... /home/user/hello.out   # 데이터(data/bss)
01234000-01256000 rw-p ... [heap]                 # 힙 (낮은 → 높은 주소로 자람)
7ffdxxxxx000-7ffdyyyyy000 rw-p ... [stack]        # 스택 (높은 주소)
```

(주소·구간 폭은 시스템마다 다르므로 정확한 수치는 _확인 필요_. 다만 "코드/데이터/힙은 낮은 쪽, 스택은 높은 쪽"이라는 큰 그림은 일반적이다.)



재배치가 가능했던 이유가 각 프로그램이 독립된 가상 주소 공간을 가지기 때문에, 링커는 모든 실행 파일에 대해 안심하고 같은 시작 주소(예: 코드 섹션은 `0x401000`)를 가정하고 심벌의 최종 주소를 박아 넣을 수 있다.&#x20;

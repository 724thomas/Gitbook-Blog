# 2.4. Coroutine

### 1. 일반 함수

#### 1) 개념 정의

일반 함수(서브루틴)는 호출되면 처음부터 실행을 시작하고 `return`으로 끝나면 자신이 쓰던 상태가 완전히 사라지는, 한 입구·한 출구의 코드 단위다.

#### 2) 원리 설명

함수를 호출하면 컴퓨터는 그 함수가 사용할 메모리 공간인 "스택 프레임(stack frame)"을 하나 만든다. \
이 프레임에는 함수의 지역 변수, 매개변수, 그리고 함수가 끝난 뒤 돌아갈 위치(반환 주소)가 담긴다. \
함수가 `return`을 만나면 이 프레임은 스택에서 통째로 제거되고, 제어 흐름은 함수를 불렀던 바로 다음 줄로 돌아간다.&#x20;

즉 함수는 호출될 때마다 항상 첫 줄부터 시작하고, 끝나면 자신이 쓰던 모든 상태(지역 변수 값 등)를 버린다. \
이런 구조 때문에 일반 함수는 "한 번 들어가서 끝까지 실행하고 한 번 나온다"는 단순하고 예측 가능한 흐름을 가진다.

#### 3) 세부 메커니즘

스택 프레임들이 차곡차곡 쌓이는 이유는 함수 호출이 중첩되기 때문이다. \
A가 B를 부르고 B가 C를 부르면, 스택에는 A·B·C의 프레임이 순서대로 쌓이고, C가 끝나면 C 프레임만 사라지면서 B로 돌아가고, 다시 B가 끝나면 A로 돌아간다. \
이렇게 "마지막에 쌓인 것이 가장 먼저 제거되는(LIFO)" 방식이라 함수 호출 스택이라 부른다.&#x20;

핵심은 프레임이 사라지는 순간 그 안의 지역 변수 값도 함께 사라진다는 점인데, 그래서 같은 함수를 다시 불러도 이전에 어디까지 실행했는지, 변수가 어떤 값이었는지 전혀 기억하지 못한다.&#x20;

#### 4) 예시

```c
int add(int a, int b) {
    int sum = a + b;     // 지역 변수 sum은 이 프레임 안에만 존재
    return sum;          // 여기서 프레임이 사라짐
}

int main() {
    int x = add(2, 3);   // add 호출 → 새 프레임 생성, 실행 후 5 반환
    int y = add(10, 20); // 다시 호출 → 또 새 프레임, 처음부터 실행
    return 0;
}
```

첫 번째 `add(2, 3)`이 끝나면 `sum`(값 5)은 사라진다. 두 번째 `add(10, 20)`은 이전 호출을 전혀 기억하지 못한 채 다시 첫 줄부터 실행되어 `sum`이 30이 된다. 즉 매 호출은 깨끗한 백지 상태에서 시작한다.



이 "한 입구·한 출구, 끝나면 상태 소멸" 구조가 한계로 작용하는 지점을, "일반 함수에서 코루틴으로"가 멈춤과 재개라는 발상으로 극복한다.

> 💡 **TMI**
>
> * 우리가 당연하게 여기는 "함수 호출 시 반환 주소를 스택에 쌓고, 반환하면 그 자리로 돌아온다"는 호출 규약(calling convention)은 CPU·OS마다 다르다. 예컨대 x86-64의 System V ABI와 Windows x64 ABI는 인자를 전달하는 레지스터 순서가 서로 달라, 같은 C 코드라도 컴파일된 어셈블리의 호출 부분이 플랫폼마다 다르게 생긴다.
> * 일반 함수가 "한 번 들어가면 끝까지 실행하고 한 번 반환한다"는 성질을 깨는 고전적 도구가 C의 `setjmp`/`longjmp`다. 스택을 거슬러 올라가 이전 지점으로 점프할 수 있어 "제한적인 비지역 흐름 제어"로서 코루틴·예외 처리의 사촌 격으로 자주 비교된다.
> * 함수 호출이 빠른 이유 중 하나는 비용 대부분이 스택 프레임을 한 번 만들고 없애는 데 그치기 때문이다. 그래서 많은 컴파일러는 작은 함수를 호출 지점에 그대로 펼치는 인라이닝(inlining)으로 이 비용마저 0으로 만들려 한다.

### 2. 일반 함수에서 코루틴으로

#### 1) 개념 정의

코루틴은 일반 함수와 달리 실행 도중에 멈췄다가, 그 멈춘 지점과 그때의 상태를 그대로 기억했다가 나중에 그 자리에서 다시 이어 실행할 수 있는 함수다.

#### 2) 원리 설명

일반 함수의 출구는 오직 `return` 하나뿐이지만, 코루틴은 여기에 "멈춤(흔히 yield 또는 suspend로 부른다)"이라는 두 번째 종류의 출구를 추가한다. \
`return`이 프레임을 완전히 없애고 떠나는 것이라면, 멈춤은 프레임을 버리지 않고 "지금까지의 상태를 그대로 보존한 채 잠시 빠져나오는 것"이다. \
그래서 같은 코루틴을 다시 호출(재개)하면, 처음부터가 아니라 멈췄던 바로 그 줄의 다음부터 이어서 실행되며, 멈출 때의 지역 변수 값들도 그대로 살아 있다. \
핵심 발상의 전환은 "함수는 끝까지 실행하고 끝나면 사라진다"라는 전제를 버리고 "함수가 중간에 멈췄다가 그 자리에서 살아날 수 있다"로 바꾼 것이다. \
이렇게 하면 하나의 함수가 여러 번에 걸쳐 나눠서 실행될 수 있다.

#### 3) 세부 메커니즘

이것이 가능하려면 일반 함수처럼 멈추는 순간 상태를 버려서는 안 되므로, 멈출 때 그 시점의 지역 변수·실행 위치 같은 상태를 어딘가에 따로 저장해 두어야 한다. \
그래야 나중에 재개할 때 저장해 둔 상태를 복원해서 "어디까지 했고 변수가 무엇이었는지"를 알고 이어갈 수 있다.&#x20;

즉 일반 함수가 "들어감 → 끝까지 실행 → 나가며 상태 소멸"의 한 사이클이라면, 코루틴은 "들어감 → 실행하다 멈춤(상태 보존) → 다시 들어감(상태 복원) → 이어 실행"을 여러 번 반복할 수 있다. \
입구가 매번 첫 줄로 고정된 일반 함수와 달리, 코루틴은 "지난번에 멈춘 그 지점"이 다음번의 입구가 된다는 점이 결정적 차이다.

#### 4) 예시

파이썬에서 코루틴의 가장 쉬운 형태는 제너레이터(generator)다. `counter()`를 호출하면 함수 본문이 곧바로 실행되지 않고 제너레이터 객체만 반환되며, `next(c)`를 부를 때마다 `yield` 지점까지 실행되고 멈춘다.

```python
def counter():
    n = 0
    while True:
        yield n      # 여기서 멈추고 n을 내보냄, 상태(n)는 보존됨
        n = n + 1    # 다음에 재개되면 바로 이 줄부터 이어 실행

c = counter()        # 아직 본문은 실행되지 않음 (제너레이터 객체만 생성)
print(next(c))       # 출력: 0  (yield에서 멈춤, n=0인 상태로 대기)
print(next(c))       # 출력: 1  (멈췄던 다음 줄부터 재개, n이 1로 증가)
print(next(c))       # 출력: 2  (또 그 자리에서 이어짐)
```

일반 함수였다면 `counter()`를 부를 때마다 `n`이 다시 0이 되겠지만, 코루틴은 `n` 값을 기억한 채 멈췄던 자리에서 이어가므로 0, 1, 2가 차례로 나온다. \
이것이 "멈춤과 재개, 상태 보존"의 직접적인 결과다.



"일반 함수"의 한계(끝나면 상태가 사라지고 항상 처음부터 시작)를 정확히 뒤집은 것이 이 키워드로, 두 키워드는 "return만 있는 함수"에서 "멈춤도 가능한 함수"로의 발상 전환이라는 하나의 흐름을 이룬다.

> 💡 **TMI**
>
> * 일반 함수에서 코루틴으로 가는 핵심 변화는 "어디까지 실행했는지(상태)를 호출이 끝난 뒤에도 보존한다"는 점이다. 그래서 코루틴을 "재개 가능한(resumable) 함수"라 부르며, 이 관점은 이론적으로 연속체 전달 방식(CPS, Continuation-Passing Style)으로 일반화된다.
> * 파이썬은 이 전환을 문법적으로 아주 작게 만들었다. 함수 본문에 `return` 대신 `yield`가 한 번이라도 등장하면, 그 함수는 호출 시 곧바로 실행되지 않고 제너레이터(코루틴의 한 형태) 객체를 돌려주는 함수로 통째로 바뀐다.
> * 멈춤을 도입하면 함수는 "한 번 들어가 한 번 나오는" 단순 모델을 넘어선다. 이 능력을 가장 깊이 일반화한 도구가 함수형 언어의 일급 연속체(first-class continuation)인데, 이것으로 코루틴·제너레이터·예외·백트래킹을 모두 만들 수 있다.

### 3. 직관적인 코루틴 설명

#### 1) 개념 정의

코루틴은 실행 도중 원하는 지점에서 스스로 멈췄다가, 나중에 그 멈춘 자리부터 상태를 그대로 보존한 채 다시 이어서 실행할 수 있는 함수다.

#### 2) 원리 설명

보통의 함수는 한 번 호출되면 처음부터 끝까지 쭉 실행되고, `return`을 만나면 모든 지역 변수와 실행 위치를 잃어버린 채 완전히 종료된다. \
다음에 다시 부르면 또 처음부터 시작할 뿐, "어디까지 했었는지"를 기억하지 못한다. \
코루틴은 여기에 "잠깐 멈춤(yield/suspend)"이라는 능력을 더한 함수다. \
멈추는 순간 지금까지의 지역 변수 값과 "코드의 몇 번째 줄에서 멈췄는지"를 그대로 간직해 두고, 호출한 쪽으로 잠시 제어를 돌려준다. \
그러다 다시 호출되면 처음이 아니라 바로 그 멈춘 지점의 다음 줄부터, 보존해 둔 변수 값을 그대로 가지고 이어서 실행한다.

#### 3) 세부 메커니즘

핵심은 "누가 멈춤과 재개를 결정하는가"이다. \
코루틴에서는 함수 안에 프로그래머가 직접 적어 둔 `yield` 지점에서만 멈춘다.&#x20;

즉 멈출 위치가 코드에 미리 박혀 있고, 프로그래머가 통제한다(협조적 방식). \
이것은 스레드처럼 운영체제가 임의의 순간에 강제로 끼어들어 다른 작업으로 바꿔치기하는 방식(선점적 방식)과 다르다.&#x20;

또 하나의 포인트는 "상태를 어디에 저장하느냐"인데, 멈출 때의 지역 변수와 진행 위치(어느 줄까지 실행했는지를 가리키는 표시, 일종의 책갈피)를 따로 보관해 두기 때문에, 재개할 때 그 책갈피를 펴서 곧바로 이어 읽을 수 있다.

#### 4) 예시

파이썬 제너레이터의 `yield`로 멈춤과 재개를 직접 확인할 수 있다.

```python
def counter():
    print("시작")
    yield 1          # 여기서 멈춤 (1을 돌려주고 정지)
    print("다시 이어서 실행")
    yield 2          # 다시 멈춤 (2를 돌려주고 정지)
    print("마지막 구간")
    yield 3

c = counter()        # 아직 본문은 실행되지 않음 (코루틴 객체만 생성)
print(next(c))       # 시작 → 1
print(next(c))       # 다시 이어서 실행 → 2
print(next(c))       # 마지막 구간 → 3
```

실행 결과:

```
시작
1
다시 이어서 실행
2
마지막 구간
3
```

중요한 점은 `next(c)`를 부를 때마다 함수가 처음부터 다시 돌지 않는다는 것이다. \
첫 호출은 `yield 1`에서 멈추고, 두 번째 호출은 바로 그다음 줄(`print("다시 이어서 실행")`)부터 이어진다. \
"시작"이 한 번만 출력되는 것이 그 증거다. \
비유하자면, 책을 읽다가 책갈피를 끼워 두고 덮었다가 나중에 그 자리부터 다시 읽는 것과 같다 — 처음 페이지로 돌아가지 않는다.



이 "직관적인 코루틴 설명"은 협조적 전환(프로그래머가 `yield` 지점에서 직접 제어)과 스레드의 선점적 전환을 대비하는 출발점이 되며, 멈춘 상태를 보존한다는 개념은 키워드 6 "코루틴은 어떻게 구현될까?"(상태 저장·복원)로 자연스럽게 이어진다.

> 💡 **TMI**
>
> * 코루틴의 "서로 양보한다"는 직관을 OS 역사에 대응시키면 협조적 멀티태스킹(cooperative multitasking)이 된다. 초기 Windows(3.x)와 고전 Mac OS는 OS가 강제로 작업을 빼앗는 선점형이 아니라, 각 프로그램이 자발적으로 제어권을 넘겨줘야 다음 프로그램이 도는 방식이었다 — 한 프로그램이 양보를 안 하면 시스템 전체가 멈췄다.
> * 코루틴 간 전환은 스레드 전환보다 훨씬 싸다. 스레드는 보통 OS 커널을 거치며 컨텍스트 스위치가 일어나지만, 많은 코루틴 구현은 사용자 공간(user space)에서 레지스터 몇 개와 스택 포인터만 바꿔치기하므로 커널 진입 비용 자체가 없다.
> * "양보(yield)"라는 직관 덕분에 코루틴은 생산자-소비자 문제의 단골 예제가 된다. 유닉스 파이프(`a | b`)에서 a가 만들고 b가 소비하며 번갈아 진행되는 모습은 코루틴 동작을 OS 레벨에서 보여주는 비유로 자주 인용된다.

### 4. 함수는 그저 코루틴의 특별한 예에 불과하다

#### 1) 개념 정의

일반 함수는 "한 번 호출되면 중간에 멈추는 일 없이 끝까지 실행되고 단 한 번 `return`하는" 코루틴, 즉 코루틴이라는 더 넓은 개념의 특수한 한 가지 경우다.

#### 2) 원리 설명

보통 우리는 함수를 가장 기본적인 단위로 보고, 코루틴은 그 위에 "멈췄다 재개하는" 능력을 덧붙인 확장판이라고 생각한다.&#x20;

그런데 관점을 뒤집어 보면 순서가 거꾸로다. \
코루틴은 실행 도중 여러 번 멈췄다가(yield) 다시 이어서 실행할 수 있는 일반적인 개념이고, 멈출 수 있는 횟수에 아무런 제약이 없다. \
여기서 "멈추는 횟수를 0번으로 고정"하면, 즉 한 번 들어가서 한 번 나오기만 하는 경우로 한정하면 그것이 바로 우리가 아는 일반 함수가 된다.&#x20;

따라서 함수가 더 기본이고 코루틴이 확장인 것이 아니라, 개념적으로는 코루틴이 더 일반적이고 함수가 그 특수 사례인 셈이다.

#### 3) 세부 메커니즘

이 둘의 차이는 "입구와 출구가 몇 개인가"로 정리할 수 있다. \
일반 함수는 입구가 하나(호출 지점)이고 출구도 하나(`return`)다. \
한 번 들어가면 끝까지 달려서 한 번 나오고, 그걸로 함수의 일생이 끝난다.&#x20;

반면 코루틴은 입구가 여러 개이고 출구도 여러 개다. \
`yield`로 멈춘 자리가 다음번 재개 시의 입구가 되고, 멈출 때마다 그 지점이 출구가 되기 때문이다. \
또한 함수는 끝나면 그동안 쓰던 지역 변수 등의 상태가 모두 사라지지만, 코루틴은 멈춰도 그 상태를 보존했다가 재개할 때 그대로 이어 쓴다.

| 구분          | 일반 함수          | 코루틴            |
| ----------- | -------------- | -------------- |
| 중간에 멈출 수 있나 | 아니오 (yield 0번) | 예 (yield 여러 번) |
| 재개 위치       | 해당 없음 (멈추지 않음) | 멈췄던 그 지점부터     |
| 상태 보존       | 끝나면 사라짐        | 멈춰도 보존됨        |
| 입구 / 출구 개수  | 하나 / 하나        | 여러 개 / 여러 개    |

#### 4) 예시

yield가 0번인 함수와 yield가 여러 번인 코루틴을 나란히 두면 차이가 한눈에 보인다.

```python
# (1) 일반 함수: 입구 하나, 출구 하나, 중간에 멈추지 않음
def normal():
    print("시작")
    print("끝")
    return 1

normal()
# 출력:
# 시작
# 끝
# → 호출되면 끝까지 달려 한 번에 return
```

```python
# (2) 코루틴: 중간에 yield로 멈췄다 재개 (입구 여러 개, 출구 여러 개)
def coroutine():
    print("시작")
    yield 1        # 여기서 멈춤 (출구 1 / 다음 입구 1)
    print("재개 후 계속")
    yield 2        # 다시 멈춤 (출구 2 / 다음 입구 2)
    print("끝")

c = coroutine()
next(c)   # 출력: 시작        (첫 실행 → 첫 yield에서 멈춤)
next(c)   # 출력: 재개 후 계속 (멈췄던 지점부터 이어서 → 두 번째 yield에서 멈춤)
next(c)   # 출력: 끝          (다시 이어서 마지막까지)
```

(2)에서 `yield`를 하나도 쓰지 않으면 (1)과 똑같이 "한 번 들어가 한 번 나오는" 함수가 된다. 즉 함수는 코루틴에서 멈춤(yield)을 0으로 줄인 특수한 형태임을 코드로 확인할 수 있다.



이 통찰은 절 전체에서 설명한 "코루틴은 멈췄다 재개할 수 있고(여러 입구·여러 출구) 상태를 보존한다"는 핵심 성질을, 가장 익숙한 일반 함수와 대비시켜 다시 정리해 주는 마무리 관점이다. \
앞서 다룬 yield(멈춤)·재개·상태 보존 개념이 "함수는 그 능력을 쓰지 않는 특수 케이스"라는 한 문장으로 수렴된다.

> 💡 **TMI**
>
> * 이 명제를 가장 깊이 밀어붙인 것이 함수형 언어의 일급 연속체(first-class continuation)다. Scheme의 `call/cc`는 "지금 이 순간 이후에 해야 할 나머지 계산 전체"를 하나의 값처럼 붙잡아 저장하고 나중에 다시 부를 수 있게 해주며, 이를 이용하면 코루틴·제너레이터·예외·백트래킹까지 모두 만들 수 있다.
> * 구현 관점에서 코루틴은 흔히 stackful(독립된 스택을 통째로 가짐)과 stackless(독립 스택 없이 상태기계로 변환됨) 두 종류로 나뉜다. "함수가 코루틴의 특수 경우"라는 시각은 stackless 진영에서 특히 자연스러운데, 일반 함수든 코루틴이든 결국 컴파일러가 동일한 상태기계 틀로 다루기 때문이다.
> * C++20의 코루틴은 이 철학을 문법에 반영했다. 함수 안에 `co_await`, `co_yield`, `co_return` 중 하나라도 쓰이면 그 함수는 자동으로 코루틴이 되며, 컴파일러가 지역 변수와 실행 위치를 담는 코루틴 프레임을 생성한다 — 일반 함수와 코루틴이 같은 "함수" 문법을 공유하는 셈이다.

### 5. 코루틴의 역사

#### 1) 개념 정의

코루틴은 최근에 새로 만들어진 기술이 아니라, 우리가 흔히 쓰는 함수(서브루틴)만큼이나 오래전부터 제안되어 있던 프로그래밍 개념이다.

#### 2) 원리 설명

컴퓨터 초창기부터 "함수"라는 개념과 더불어 "코루틴"이라는 개념도 함께 제안되어 있었다. \
하지만 함수는 호출하면 처음부터 끝까지 실행되고 끝나면 사라지는 단순하고 직관적인 모델이라 널리 쓰인 반면, 코루틴은 중간에 멈췄다가 다시 이어서 실행되는 특성 때문에 상대적으로 주목을 덜 받았다. \
오랜 기간 코루틴은 일부 특수한 용도 외에는 거의 잊힌 개념처럼 남아 있었다. \
그러다 인터넷이 발전하면서 한 서버가 수많은 연결을 동시에 가볍게 처리해야 하는 "고동시성" 수요가 폭발적으로 커졌다. \
이런 수요를 효율적으로 감당하기 위한 수단으로 코루틴이 다시 조명받게 되었고, 현대 언어들이 이를 적극적으로 받아들이면서 부활했다.

#### 3) 세부 메커니즘

코루틴이 다시 떠오른 핵심 이유는 "비용" 문제에 있다. \
동시에 많은 작업을 처리하려고 스레드를 무수히 많이 만들면, 스레드마다 운영체제가 관리해야 할 자원과 스레드 간 전환(context switch) 비용이 커서 금방 한계에 부딪힌다.&#x20;

반면 코루틴은 이런 전환을 OS 개입 없이 사용자 코드 수준에서 가볍게 처리할 수 있어, 하나의 스레드 위에서도 수많은 작업을 번갈아 진행할 수 있다.&#x20;

즉 코루틴의 부활은 "새 발명"이라기보다, 오래된 아이디어가 시대적 수요(많은 연결을 적은 자원으로 처리)와 맞아떨어져 재발견된 것에 가깝다.



"코루틴이 멈췄다가 다시 이어서 실행된다"는 이 역사적 특징이 바로 다음 키워드 "코루틴은 어떻게 구현될까?"에서 다루는 핵심 질문, 즉 "멈춘 지점의 상태를 어떻게 저장하고 복원하는가"로 이어진다.

> 💡 **TMI**
>
> * 'coroutine(코루틴)'이라는 용어는 멜빈 콘웨이(Melvin Conway)가 1958년경 만들고 1963년 발표한 어셈블러 관련 논문에서 처음 활자화한 것으로 널리 알려져 있다(자료마다 표현이 조금씩 다름). 콘웨이는 "시스템 구조는 그것을 설계한 조직의 의사소통 구조를 닮는다"는 콘웨이의 법칙(Conway's Law)으로도 유명하다.
> * 코루틴은 도널드 커누스(Donald Knuth)의 명저 《The Art of Computer Programming》에서 비교적 이른 시기에 비중 있게 다뤄진 개념이기도 하다. 즉 코루틴은 최근 async/await 유행으로 등장한 신기술이 아니라 컴퓨터 과학 초창기부터 있던 오래된 아이디어다.
> * 코루틴을 언어 차원에서 일찍 지원한 대표 주자가 시뮬레이션용 언어 Simula 계열이다. "동시에 진행되는 여러 개체"를 자연스럽게 모델링해야 하는 시뮬레이션 분야가 코루틴 같은 협조적 다중 흐름을 일찍부터 필요로 했기 때문이다.

### 6. 코루틴은 어떻게 구현될까?

#### 1) 개념 정의

코루틴 구현의 핵심은 실행을 멈춘 그 순간의 상태(다음에 실행할 위치, 지역 변수 등)를 함수처럼 그냥 버리지 않고, 따로 저장해 두었다가 재개할 때 그대로 복원하는 것이다.

#### 2) 원리 설명

일반 함수는 호출되면 자신의 지역 변수와 실행 위치 같은 정보를 스택에 올려 두고 일하다가, `return`으로 끝나는 순간 그 정보를 모두 버린다. \
함수는 "한 번 실행하면 끝"이기 때문에 상태를 보관할 필요가 없다. \
그런데 코루틴은 중간에 멈췄다가 나중에 그 지점부터 다시 이어서 실행해야 하므로, 멈추는 순간의 상태를 버리면 안 되고 어딘가에 보관해 두어야 한다. \
그리고 재개될 때는 보관해 둔 그 상태를 그대로 되살려서, 마치 한 번도 멈춘 적이 없었던 것처럼 이어가야 한다. \
결국 코루틴 구현이란 "멈춤과 재개 사이에 실행 상태를 어떻게 저장하고 복원하느냐"의 문제로 귀결된다.

#### 3) 세부 메커니즘

이 상태를 보관하는 방식은 크게 두 가지로 나눠 생각할 수 있다.

* **(1) 코루틴이 자기만의 스택을 통째로 따로 갖는 방식** — 일반 함수가 공용 스택을 쓰는 것과 달리, 코루틴마다 별도의 스택 공간을 마련해 두고 멈출 때는 그 스택을 그대로 남겨 두었다가 재개할 때 다시 그 스택으로 돌아가 이어간다. 어떤 호출 깊이(예: 함수가 또 다른 함수를 부른 안쪽)에서 멈춰도 전체 상태가 자연스럽게 보존되는 장점이 있다.
* **(2) 멈출 때 꼭 필요한 값만 별도 객체에 저장하는 방식** — 스택을 통째로 갖는 대신, 멈추는 시점에 살려 둬야 할 값들(다음 실행 위치, 보존할 지역 변수 등)만 추려서 하나의 객체에 저장해 둔다. 보관할 정보가 더 적어 가볍지만, 보존 범위가 상대적으로 제한적이다.

#### 4) 예시

* **"상태를 객체에 저장하는 방식"의 직관적 그림**: 코루틴이 멈출 때, 작은 메모지에 "다음에 실행할 줄 번호 = 3번째 줄, x = 10, y = 20"이라고 적어 한쪽에 보관해 둔다고 생각하면 된다. 재개될 때는 그 메모지를 다시 꺼내 그 상태로 되돌린 뒤 이어서 실행한다.

```
[멈출 때]   실행 위치: line 3 |  x=10, y=20   → 별도 객체에 저장
[재개될 때] 저장된 값을 꺼내 복원 → line 3부터, x=10, y=20 상태로 계속
```

* **"자기만의 스택을 갖는 방식"의 직관적 그림**: 코루틴 A에게 전용 스택 공간을 따로 준다. A가 일하다 멈추면 A의 스택은 그대로 남겨 두고 다른 작업으로 넘어갔다가, A를 다시 재개할 때 그 스택으로 돌아오면 멈췄던 상태가 고스란히 남아 있어 바로 이어갈 수 있다.



이 "상태를 저장하고 복원한다"는 구현 아이디어는 "코루틴의 역사"에서 본 코루틴의 본질적 특성(멈췄다 이어서 실행)을 실제로 가능하게 만드는 기술적 답이며, 이것이 고동시성 시대에 코루틴을 가볍고 효율적인 동시성 수단으로 만들어 주는 바탕이 된다.

> 💡 **TMI**
>
> * 가장 핵심은 "스택과 레지스터 상태를 어디에 보관하느냐"다. stackful 코루틴은 코루틴마다 별도의 스택 영역을 할당해 양보 시점의 전체 호출 정보를 그대로 보존하고, stackless 코루틴은 컴파일러가 함수를 상태기계로 변환해 필요한 지역 변수만 힙의 작은 구조체에 담는다.
> * 파이썬·C#·러스트의 `async`/`await`나 파이썬의 `yield from`은 겉보기엔 평범한 코드지만, 컴파일러가 내부적으로 "현재 단계 번호 + 보존할 변수들"을 가진 상태기계로 바꿔준다. 그래서 await 지점마다 함수가 멈췄다 재개될 수 있고, 별도의 OS 스레드가 전혀 필요 없다.
> * 산업 현장 사례로 Go의 고루틴(goroutine)이 유명하다. 수십만 개를 띄워도 가벼운데, 런타임의 GMP 스케줄러(G=고루틴, M=OS 스레드, P=논리 프로세서)가 소수의 OS 스레드 위에 다수의 고루틴을 사용자 공간에서 다중화(M:N 스케줄링)하기 때문이다.

### 📚 이 절 핵심 정리표

# Process Resourced shared between Threads

> 한 프로세스의 여러 스레드는 **코드·데이터·힙 영역과 DLL·파일을 공유**하고, **스택·PC·레지스터는 전용**으로 갖는다. 단 스택조차도 같은 주소 공간 안에 있어 주소(포인터)를 넘기면 다른 스레드가 접근할 수 있다. 공유는 편리하지만 **데이터 경쟁**을 부르고, 굳이 공유할 필요 없는 데이터는 **TLS**로 스레드 전용화한다.

***

### 1. 스레드 전용 리소스

#### 1) 개념 정의

스레드 전용 리소스란 같은 프로세스 안에 있더라도 각 스레드가 자기만 따로 갖고 있어야 하는, 즉 스레드마다 독립적으로 존재하는 실행 상태(스택·프로그램 카운터 PC·레지스터 집합)를 말한다.

#### 2) 원리 설명

여러 스레드가 한 프로세스의 메모리(코드, 데이터 등)를 공유하더라도, 각 스레드는 서로 다른 코드 위치에서 서로 다른 일을 동시에 진행하고 있다. 따라서 "지금 어느 함수의 어느 줄을 실행 중인지", "함수 호출이 어디까지 쌓여 있는지", "계산 중인 값이 무엇인지" 같은 정보는 스레드마다 달라야 한다. 만약 이런 상태를 모든 스레드가 공유한다면 한 스레드의 진행 상황이 다른 스레드를 덮어써 버려 정상적인 실행이 불가능하다. 그래서 스택, 프로그램 카운터(PC), 레지스터 집합처럼 "실행의 현재 위치와 진행 상태"를 담는 것들은 각 스레드가 전용으로 가진다.

#### 3) 세부 메커니즘

스레드 전용 리소스의 핵심은 "함수를 실행하려면 그 함수만의 작업 공간이 필요하다"는 점이다.

* **스택**: 함수가 호출될 때마다 지역 변수, 매개변수, 돌아갈 주소 등이 스택에 쌓인다. 두 스레드가 동시에 함수를 호출하면 각자의 호출 기록이 섞이면 안 되므로, 스레드마다 별도의 스택이 필요하다.
* **프로그램 카운터(PC)**: 다음에 실행할 명령어의 주소를 가리킨다. 스레드마다 실행 위치가 다르므로 PC도 각자 따로 가진다.
* **레지스터 집합**: CPU가 계산 중에 임시로 값을 담아두는 곳이다. 그런데 물리 레지스터는 CPU 코어에 한 세트뿐이므로, 여기서 "전용"이란 스레드가 잠시 멈췄다가(전환) 다시 실행될 때 **각 스레드의 레지스터 값을 따로 저장·복원**해 마치 전용인 것처럼 동작시킨다는 뜻이다.

이 세 가지는 모두 "이 스레드가 지금 어디까지, 어떤 상태로 일하고 있는가"를 나타내며, 공유되면 실행 자체가 깨지기 때문에 전용으로 둔다.

#### 4) 예시

**예시 1 — 두 스레드가 같은 함수를 동시에 실행:**

```c
void count() {
    int i = 0;          // 지역 변수 i 는 스택에 저장됨
    for (i = 0; i < 3; i++) {
        // ... 작업 ...
    }
}
```

스레드 A와 스레드 B가 동시에 `count()`를 실행해도, A의 `i`와 B의 `i`는 서로 다른 스택에 있으므로 충돌하지 않는다. A가 `i = 2`일 때 B는 `i = 0`일 수 있고, 둘은 서로의 값을 망가뜨리지 않는다.

**예시 2 — 스택이 따로인 모습(개념 그림):**

```
프로세스 메모리
├── 코드 영역      (공유)
├── 데이터 영역    (공유)
├── 스레드 A 스택  ← A 전용 (i=2, 돌아갈 주소 ...)
└── 스레드 B 스택  ← B 전용 (i=0, 돌아갈 주소 ...)

스레드 A: PC → count()의 3번째 줄,  레지스터 = A의 계산 값
스레드 B: PC → count()의 1번째 줄,  레지스터 = B의 계산 값
```

같은 함수를 가리키지만 PC, 스택, 레지스터가 모두 따로이므로 두 스레드는 독립적으로 진행된다.

#### 5) 다른 키워드와의 연결

이 키워드는 "스레드가 무엇을 **전용**으로 갖는가"를 다루며, 바로 다음 키워드인 "코드 영역(공유)"과 정확히 짝을 이룬다. 코드는 모두가 공유하지만, 그 코드를 실행하는 데 필요한 상태(스택·PC·레지스터)는 전용이기 때문에 여러 스레드가 같은 함수를 동시에 따로따로 실행할 수 있다.

> 💡 **TMI**
>
> * 스레드를 전환할 때 OS가 한 스레드의 레지스터·PC 값을 저장하고 다른 스레드의 값을 복원하는 과정을 "컨텍스트 스위칭(context switching)"이라 부른다. 바로 이 "저장·복원해야 할 상태"가 스레드 전용 리소스의 본질이며, 공유 리소스는 옮길 필요가 없어 전환 비용에 포함되지 않는다.
> * 함수가 자신의 상태를 호출자별 스택에만 두고 전역 상태를 건드리지 않으면 여러 스레드가 동시에 호출해도 안전한데, 이를 "재진입성(reentrancy)"이라 한다. 스택·레지스터가 스레드마다 따로 있다는 사실이 재진입 가능 함수가 곧 스레드 안전해지는 토대가 된다.

***

### 2. 코드 영역 — 모든 함수를 스레드에 배치하여 실행할 수 있다

#### 1) 개념 정의

코드 영역은 프로그램의 명령어(함수들의 기계어)가 저장된, 읽기 전용으로 모든 스레드가 공유하는 메모리 영역이며, 그래서 프로세스 안의 어떤 함수든 어떤 스레드가 가져다 실행할 수 있다.

#### 2) 원리 설명

프로그램이 메모리에 올라오면 함수들의 코드는 코드 영역에 한 벌만 저장된다. 이 영역은 실행 중에 내용이 바뀌지 않는 읽기 전용이므로, 여러 스레드가 동시에 읽어도 서로를 방해하지 않는다. 함수는 결국 "코드 영역에 있는 명령어 묶음"일 뿐이고, 스레드는 그 명령어를 따라 실행하는 주체다. 따라서 특정 함수가 특정 스레드에 묶여 있는 것이 아니라, 프로세스 안의 모든 스레드가 모든 함수를 자유롭게 호출해 실행할 수 있다.

#### 3) 세부 메커니즘

"코드는 공유, 실행 상태는 전용"이라는 분업이 이것을 가능하게 한다. 함수를 실행한다는 것은 (1) 코드 영역에 있는 그 함수의 명령어를 읽고, (2) 그 명령어가 다루는 지역 변수·중간 계산 값을 스레드 자신의 스택·레지스터에 두는 것이다. 코드는 바뀌지 않으니 여러 스레드가 같은 명령어를 동시에 읽어도 안전하고, 변하는 부분(지역 변수 등)은 각자의 전용 공간에 따로 보관되니 섞이지 않는다. 그래서 같은 함수라도 스레드마다 다른 진행 상태로 동시에 실행될 수 있으며, 어떤 함수를 어느 스레드에 맡길지는 프로그램 작성자가 자유롭게 정할 수 있다.

#### 4) 예시

**예시 1 — 한 함수를 여러 스레드에 배치:**

```c
void task() {
    // 코드 영역에 한 벌만 저장된 함수
    printf("실행 중\n");
}

// 스레드 1, 2, 3 모두 같은 task 를 실행 대상으로 지정
create_thread(task);
create_thread(task);
create_thread(task);
```

세 스레드는 코드 영역에 있는 동일한 `task` 명령어를 공유해 읽지만, 각자 전용 스택·PC로 독립 실행된다. 출력은 (순서는 보장되지 않은 채) "실행 중"이 세 번 나타난다.

**예시 2 — 서로 다른 함수를 각 스레드에 배치:**

```c
void download() { /* 파일 받기 */ }
void render()   { /* 화면 그리기 */ }

create_thread(download);   // 스레드 A 는 download 실행
create_thread(render);     // 스레드 B 는 render 실행
```

두 함수 모두 같은 코드 영역에 있고, 어떤 함수든 원하는 스레드에 배치할 수 있다. A와 B는 동시에 서로 다른 함수를 진행한다.

#### 5) 다른 키워드와의 연결

이 키워드는 앞의 "스레드 전용 리소스"와 정확히 대칭을 이룬다. 코드(읽기 전용)는 공유되기 때문에 모든 스레드가 모든 함수를 실행할 수 있고, 실행에 필요한 상태(스택·PC·레지스터)는 전용이기 때문에 충돌하지 않는다. 코드 외에 또 무엇이 공유될까? → 다음은 **데이터 영역**이다.

> 💡 **TM**
>
> * 코드 영역이 "읽기 전용"인 것은 관례가 아니라 하드웨어로 강제된다. OS는 메모리를 페이지 단위로 나눠 각 페이지에 읽기/쓰기/실행 권한 비트를 매기는데, 코드 페이지는 보통 읽기+실행만 켜고 쓰기를 꺼서 실수나 공격으로 코드를 덮어쓰는 것을 막는다.
> * 같은 프로그램을 여러 번 실행해도 코드 영역은 물리 메모리에 보통 한 벌만 올라가 각 프로세스가 공유한다. 코드는 변하지 않으므로 복사할 이유가 없어 메모리를 크게 절약한다.
> * "쓰기 가능한 코드"는 보안 세계에서 곧 취약점으로 통한다. W^X(Write XOR Execute) 정책은 "어떤 메모리 페이지도 쓰기와 실행을 동시에 가질 수 없다"는 원칙으로, 공격자가 데이터를 코드처럼 실행하는 것을 차단하기 위해 현대 OS에 널리 적용돼 있다.

***

### 3. 데이터 영역 — 모든 스레드가 데이터 영역의 변수에 접근할 수 있다

#### 1) 개념 정의

데이터 영역은 전역 변수와 정적(static) 변수가 저장되는 메모리 구역으로, 한 프로세스에 속한 모든 스레드가 동일한 변수에 함께 접근할 수 있는 공간이다.

#### 2) 원리 설명

스레드는 같은 프로세스의 주소 공간을 공유하기 때문에, 그 안에 자리 잡은 데이터 영역도 자연스럽게 공유된다. 전역 변수는 프로그램이 실행되는 동안 항상 같은 위치에 존재하므로, 어느 스레드에서 보든 "그 변수"는 하나뿐인 같은 메모리다. 그래서 한 스레드가 전역 변수의 값을 바꾸면 다른 스레드도 즉시 바뀐 값을 보게 된다. 이 성질 덕분에 데이터 영역은 스레드끼리 정보를 주고받는 통로(통신 수단)가 된다. 하지만 같은 변수를 여러 스레드가 동시에 읽고 쓰면 값이 꼬일 수 있는데, 이것이 바로 **데이터 경쟁(data race)** 의 원인이 된다.

#### 3) 세부 메커니즘

스레드가 데이터 영역을 공유한다는 것을 한 단계 더 들여다보면, 각 스레드가 따로 갖는 것과 함께 쓰는 것이 무엇인지로 구분된다. 스레드마다 별도로 갖는 것은 자신의 스택(지역 변수가 사는 곳)이며, 데이터 영역의 전역/정적 변수는 스택 바깥에 있으므로 어느 스레드의 소유물도 아니고 모두의 공용이 된다. 따라서 전역 변수의 "이름"은 컴파일된 뒤 결국 같은 메모리 주소로 변환되고, 모든 스레드가 그 동일한 주소를 가리키게 된다. 바로 이 "같은 주소를 동시에 만질 수 있다"는 점 때문에, 한 스레드가 값을 다 쓰기 전에 다른 스레드가 끼어들면 중간 상태가 섞여 의도치 않은 결과가 나온다.

#### 4) 예시

```c
#include <stdio.h>
#include <pthread.h>

int counter = 0;  // 전역 변수 → 데이터 영역, 모든 스레드가 공유

void* worker(void* arg) {
    for (int i = 0; i < 100000; i++) {
        counter++;  // 같은 전역 변수를 동시에 수정
    }
    return NULL;
}

int main() {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    printf("counter = %d\n", counter);
    return 0;
}
```

* 두 스레드가 각각 100,000번씩 더하므로 기대값은 `counter = 200000`이다.
* 그러나 실제로 실행하면 `counter = 137254`처럼 200000보다 작은 값이 자주 나온다(정확한 숫자는 실행마다 달라짐 — 데이터 경쟁 때문).
* 이유: `counter++`는 "읽기 → 1 더하기 → 쓰기"의 세 단계로 나뉘어 실행되는데, 한 스레드가 이 세 단계를 끝내기 전에 다른 스레드가 끼어들어 **같은 옛 값을 읽으면** 한 번의 증가가 통째로 사라진다.

#### 5) 다른 키워드와의 연결

데이터 영역과 마찬가지로 힙 영역도 모든 스레드가 공유하지만, 데이터 영역은 변수 "이름"으로 바로 접근할 수 있는 반면 힙 영역은 포인터(주소)를 통해서만 접근할 수 있다는 점에서 갈린다. → 다음은 **힙 영역**이다.

> 💡 **TMI**
>
> * 데이터 영역은 사실 두 칸으로 나뉜다. 초깃값이 있는 전역/정적 변수는 `.data`에, 초깃값이 0인(또는 없는) 변수는 `.bss`에 들어가는데, `.bss`는 실행 파일에 실제 값을 저장하지 않고 "이만큼 0으로 채우라"는 크기 정보만 담아 파일 크기를 줄인다.
> * `counter++` 한 줄은 기계어로는 보통 "메모리에서 읽고(read) → 1 더하고(modify) → 다시 쓰는(write)" 세 단계로 쪼개진다. 두 스레드가 이 사이에 끼어들면 한쪽의 증가가 통째로 사라지는데, 데이터 경쟁이 위험한 이유가 바로 이 "한 줄처럼 보이지만 쪼개지는" 성질 때문이다.
> * 데이터 경쟁(data race)에는 학술적으로 엄밀한 정의가 있다. 동기화 없이 둘 이상의 스레드가 같은 위치에 접근하고 그중 하나 이상이 쓰기일 때 발생하며, C++·자바 같은 언어 표준은 이를 "happens-before" 관계로 정의해 둘 사이에 순서 보장이 없으면 동작이 정의되지 않는다고 규정한다.

***

### 4. 힙 영역 — 포인터가 핵심이다

#### 1) 개념 정의

힙 영역은 `malloc`이나 `new`로 실행 중에 직접 할당하는 메모리 구역으로, 모든 스레드가 공유하지만 변수 이름이 아니라 포인터(주소)를 통해서만 접근할 수 있는 공간이다.

#### 2) 원리 설명

힙에 할당된 메모리에는 전역 변수처럼 미리 정해진 "이름"이 없다. 대신 할당할 때 그 메모리의 시작 주소가 반환되고, 이 주소를 담은 포인터가 메모리를 가리키는 유일한 손잡이가 된다. 힙 영역 자체는 프로세스 주소 공간 안에 있으므로 모든 스레드가 공유하지만, 어떤 스레드가 그 메모리를 쓰려면 반드시 해당 포인터(주소)를 알고 있어야 한다. 즉 한 스레드가 할당한 힙 메모리를 다른 스레드가 사용하려면 그 포인터 값을 전달받아야 한다. 그래서 힙 영역의 공유는 "포인터를 어떻게 넘겨주느냐"의 문제로 귀결된다.

#### 3) 세부 메커니즘

포인터가 핵심이라는 말을 더 파고들면, 포인터 자체가 어디에 저장되느냐와 그것이 가리키는 메모리가 어디에 있느냐를 구분해야 한다. `malloc`이 돌려준 주소를 지역 변수 포인터에 담으면 그 포인터 변수는 해당 스레드의 스택에만 존재하므로 다른 스레드는 그 포인터를 볼 수 없다. 하지만 포인터가 가리키는 대상(힙 메모리)은 공용 공간에 있으므로, 그 주소 값만 다른 스레드에게 알려주면(예: 스레드 생성 시 인자로 전달하거나 전역 변수에 저장) 다른 스레드도 같은 힙 메모리에 도달할 수 있다. 결국 "메모리는 공유되어 있지만 그 위치를 아는 것은 포인터뿐"이라는 구조가 되고, 같은 포인터를 가진 여러 스레드가 같은 힙 메모리를 동시에 만지면 데이터 영역과 똑같은 경쟁 문제가 발생한다.

#### 4) 예시

```c
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>

void* worker(void* arg) {
    int* shared = (int*)arg;  // main이 넘겨준 힙 메모리 주소를 전달받음
    *shared += 1;             // 같은 힙 메모리에 접근해 값 변경
    printf("스레드에서 본 값: %d\n", *shared);
    return NULL;
}

int main() {
    int* p = (int*)malloc(sizeof(int));  // 힙에 메모리 할당, 주소를 p에 저장
    *p = 100;

    pthread_t t;
    pthread_create(&t, NULL, worker, p);  // 포인터(주소)를 인자로 전달
    pthread_join(t, NULL);

    printf("main에서 본 값: %d\n", *p);  // 스레드가 바꾼 결과가 그대로 보임
    free(p);
    return 0;
}
```

실행 결과:

```
스레드에서 본 값: 101
main에서 본 값: 101
```

* `main`이 할당한 힙 메모리의 주소 `p`를 스레드에 넘겨주었기 때문에, 스레드가 바꾼 값을 `main`도 그대로 보게 된다.
* 만약 포인터를 넘겨주지 않았다면, 그 힙 메모리가 공유 공간에 있더라도 스레드는 그것을 찾아갈 방법이 없다.

#### 5) 다른 키워드와의 연결

힙 영역은 데이터 영역과 함께 "스레드가 공유하는 프로세스 리소스"를 이루지만, 데이터 영역이 이름으로 즉시 접근되는 것과 달리 힙 영역은 포인터 전달이라는 한 단계를 거쳐야 한다. 그런데 "주소만 넘기면 접근 가능"이라는 성질은 사실 다음 키워드인 **스택 영역**에도 똑같이 적용된다.

> 💡 **TMI**
>
> * 힙에서 받은 메모리를 해제(free)한 뒤에도 그 주소를 가리키던 포인터는 여전히 옛 주소를 들고 있는데, 이를 "댕글링 포인터(dangling pointer)"라 부른다. 이미 반납된 메모리를 가리키는 이 포인터를 다시 쓰면 use-after-free라는 대표적 보안 취약점이 된다.
> * `malloc` 한 번 호출하는 것은 보기보다 무거운 일이라, 할당자(allocator)는 내부적으로 크기별 빈 블록 목록(free list)이나 영역(arena)을 관리하며 메모리를 잘게 쪼개고 합친다. 멀티스레드 환경에서는 이 할당자 내부 자료구조 자체가 공유 자원이라, 잘못 설계하면 모든 스레드가 할당 때마다 한 줄로 줄 서는 병목이 된다.

***

### 5. 스택 영역 — 공유 공간 내 전용 데이터

#### 1) 개념 정의

스택 영역은 각 스레드가 지역 변수와 함수 호출 흐름을 저장하기 위해 개별적으로 갖는 메모리 공간이지만, 물리적으로는 하나의 프로세스 주소 공간을 나눠 쓰는 것일 뿐이라 다른 스레드가 그 주소를 알면 접근할 수 있는 데이터다.

#### 2) 원리 설명

한 프로세스 안에서 여러 스레드가 동시에 실행되면, 각 스레드는 자기만의 함수 호출과 지역 변수를 추적해야 하므로 스레드마다 별도의 스택을 갖는다. 이렇게 스택이 분리되어 있기 때문에 각 스레드의 지역 변수는 서로 간섭하지 않고 "전용 데이터"처럼 동작한다. 그러나 이 스택들은 모두 같은 프로세스의 하나의 주소 공간 안에 자리 잡고 있다. 즉 "전용"이라는 것은 보통은 서로의 스택을 건드릴 일이 없다는 관례일 뿐, 물리적으로 막혀 있는 것은 아니다. 그래서 한 스레드가 자기 지역 변수의 주소(포인터)를 다른 스레드에게 넘겨주면, 받은 스레드는 그 주소를 통해 남의 스택 영역에 들어 있는 값에 접근할 수 있다.

#### 3) 세부 메커니즘

핵심은 "스택이 분리되어 있다"는 것과 "주소 공간이 하나다"라는 두 사실이 동시에 성립한다는 점이다. 프로세스의 주소 공간은 하나의 연속된 주소 체계이고, 스레드별 스택은 그 안의 서로 다른 구간을 차지한다. 따라서 어떤 변수의 주소는 그 변수가 어느 스레드의 스택에 있든 상관없이 **같은 프로세스 안에서는** 동일하게 유효한 좌표가 된다. 한 스레드가 이 좌표를 다른 스레드에 알려주면, 받은 쪽은 "내 스택이냐 남의 스택이냐"를 따지지 않고 그저 그 좌표의 메모리를 읽거나 쓴다. 다만 지역 변수는 함수가 끝나면 사라지므로, 이미 반환된 함수의 지역 변수 주소를 넘기면 그 주소는 더 이상 유효한 데이터를 가리키지 않게 된다.

#### 4) 예시

```c
#include <stdio.h>
#include <pthread.h>

int *shared_ptr = NULL;   // 전역(모든 스레드 공유)

void *thread_A(void *arg) {
    int local = 100;          // 스레드 A의 스택에 있는 지역 변수
    shared_ptr = &local;      // 자기 지역 변수의 주소를 넘김
    // ... 동기화로 thread_B가 읽을 때까지 대기한다고 가정
    return NULL;
}

void *thread_B(void *arg) {
    // shared_ptr이 채워진 뒤
    printf("%d\n", *shared_ptr);  // 스레드 A의 스택 변수에 접근 -> 100 출력
    return NULL;
}
```

스레드 B는 자기 스택이 아닌 스레드 A의 스택에 있는 `local` 값을 포인터를 통해 읽어 `100`을 출력한다. 이는 두 스택이 같은 주소 공간 안에 있어서 가능한 일이다.

#### 5) 다른 키워드와의 연결

"동적 링크 라이브러리와 파일"이 처음부터 명시적으로 모든 스레드에 공유되도록 설계된 리소스인 것과 달리, 스택은 원래 전용으로 의도되었지만 같은 주소 공간이라는 사실 때문에 결과적으로 공유될 수 있다는 점에서 대비된다.

> 💡 **TMI**
>
> * 리눅스에서 한 스레드의 스택 기본 크기는 흔히 수 MB(많은 시스템에서 8MB) 정도로 잡힌다. 스택은 미리 통째로 다 쓰는 게 아니라 필요할 때 페이지 단위로 늘어나므로, 큰 기본값을 잡아도 실제로 깊이 재귀하기 전까지는 물리 메모리를 거의 차지하지 않는다.
> * 스레드 스택이 모두 같은 프로세스 주소 공간 안에 있다는 사실은 양날의 검이다. 한 스레드가 자기 지역 변수의 주소를 다른 스레드에 넘겨 접근하게 할 수도 있지만, 동시에 한 스레드의 스택 오버플로가 옆 스레드의 영역을 침범하는 사고도 일어날 수 있다.
> * 함수가 자신의 지역 변수 주소를 반환하는 것은 흔한 버그인데, 함수가 끝나면 그 스택 프레임은 사라지므로 반환된 주소 역시 댕글링 포인터가 된다. 컴파일러가 `-Wreturn-local-addr` 같은 경고로 잡아주는 것도 이 때문이다.

### 6. 동적 링크 라이브러리와 파일

#### 1) 개념 정의

동적 링크 라이브러리(DLL/.so)와 열린 파일(파일 디스크립터)은 프로세스 단위로 로드·관리되는 리소스이므로, 그 프로세스 안의 모든 스레드가 함께 사용하는 공유 리소스다.

#### 2) 원리 설명

동적 링크 라이브러리는 프로그램이 실행 중에 불러와 사용하는 코드 묶음으로, 한 프로세스에 한 번 로드되면 그 프로세스의 주소 공간 안에 자리 잡는다. 스레드는 프로세스 안에서 실행되는 흐름이므로, 프로세스 주소 공간에 올라온 라이브러리 코드는 어느 스레드에서든 호출할 수 있다. 마찬가지로 파일을 열면 운영체제는 그 프로세스에 파일을 다루기 위한 식별자(파일 디스크립터)를 부여하는데, 이 식별자는 프로세스에 속한다. 따라서 한 스레드가 연 파일을 다른 스레드가 같은 식별자로 읽거나 쓸 수 있다. 결국 라이브러리든 파일이든 "프로세스가 가진 것"이기 때문에 그 안의 스레드들이 자연스럽게 공유하게 된다.

#### 3) 세부 메커니즘

공유가 성립하는 이유는 이들 리소스가 스레드가 아니라 프로세스에 귀속되기 때문이다. 라이브러리의 경우, 로드된 코드는 한 벌만 주소 공간에 존재하고 스레드들은 같은 코드를 각자 호출할 뿐이다. 파일의 경우, 파일 디스크립터는 보통 작은 정수 번호이고 이 번호는 프로세스 안에서만 의미를 가진다. 그래서 같은 번호를 쓰면 같은 열린 파일을 가리킨다. 다만 공유되기 때문에 주의할 점도 생긴다. 여러 스레드가 **같은 파일 디스크립터로** 동시에 쓰면, 그 디스크립터가 가리키는 열린 파일의 오프셋(다음에 쓸 위치)을 공유하기 때문에 출력 순서가 섞이거나 덮어쓰일 수 있다.

#### 4) 예시

```c
#include <stdio.h>
#include <fcntl.h>
#include <unistd.h>
#include <pthread.h>

int fd;   // 프로세스가 연 파일의 디스크립터 (모든 스레드 공유)

void *writer(void *arg) {
    const char *msg = (const char *)arg;
    write(fd, msg, 5);   // 같은 fd로 같은 파일에 씀
    return NULL;
}

int main() {
    fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
    pthread_t t1, t2;
    pthread_create(&t1, NULL, writer, "AAAAA");
    pthread_create(&t2, NULL, writer, "BBBBB");
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    close(fd);
    return 0;
}
```

두 스레드가 동일한 `fd`로 같은 파일에 쓰기 때문에 결과 파일 `out.txt`에는 두 스레드가 쓴 내용이 모두 들어간다. 즉 한 스레드가 `main`에서 연 파일을 두 스레드가 그대로 공유해 사용한다. (동기화가 없으므로 쓰는 순서나 섞임은 보장되지 않는다.)

#### 5) 다른 키워드와의 연결

앞의 "스택 영역"이 본래 전용이지만 같은 주소 공간 때문에 우연히 공유될 수 있는 데이터인 반면, 동적 링크 라이브러리와 파일은 처음부터 프로세스에 귀속되어 모든 스레드가 공유하도록 되어 있는 리소스라는 점에서 이 절의 "공유되는 프로세스 리소스"라는 주제를 직접적으로 보여준다. 그렇다면 반대로, 공유를 피하고 싶을 때는? → 마지막 키워드 **TLS**.

> 💡 **TMI**
>
> * 같은 "공유 라이브러리"를 윈도우는 `.dll`(Dynamic-Link Library), 리눅스·유닉스는 `.so`(Shared Object), macOS는 `.dylib`라 부른다. 이름은 달라도 "여러 프로그램이 코드 한 벌을 공유한다"는 발상은 같아서, 코드 영역과 마찬가지로 물리 메모리에 한 번만 올려 공유할 수 있다.
> * 파일 디스크립터는 사실 작은 정수일 뿐이고, 이 정수는 커널이 관리하는 "열린 파일 테이블(open file table)"의 항목을 가리키는 색인 역할을 한다. 그래서 프로세스의 모든 스레드가 같은 fd 정수를 쓰면 결국 같은 커널 테이블 항목, 같은 파일 오프셋을 공유하게 된다.
> * 모든 프로세스는 시작할 때 이미 세 개의 fd를 받는데, 0은 표준 입력(stdin), 1은 표준 출력(stdout), 2는 표준 에러(stderr)로 약속돼 있다. 셸의 `2>&1` 표현이 "2번을 1번으로 보내라"는 뜻인 것도 이 번호 약속에서 나온다.

### 7. 스레드 전용 저장소 (TLS, Thread Local Storage)

#### 1) 개념 정의

TLS(스레드 전용 저장소)는 전역 변수처럼 어디서든 접근할 수 있지만, 스레드마다 각자의 독립적인 복사본을 갖게 해 주는 변수 저장 메커니즘이다.

#### 2) 원리 설명

데이터 영역의 일반 전역 변수는 프로세스 안의 모든 스레드가 똑같은 하나의 메모리를 공유하기 때문에, 여러 스레드가 동시에 읽고 쓰면 데이터 경쟁이 발생한다. TLS는 이 문제를 "굳이 공유할 필요가 없는 데이터라면 아예 공유하지 말자"는 방식으로 해결한다. 변수를 TLS로 선언하면, 같은 이름으로 접근하더라도 실제로는 각 스레드가 자기만의 복사본을 따로 갖게 된다. 그래서 스레드 A가 그 변수를 바꿔도 스레드 B의 값에는 전혀 영향을 주지 않는다. 결과적으로 전역 변수의 편리함(어디서든 접근 가능)은 누리면서, 공유로 인한 경쟁 문제는 피할 수 있다.

#### 3) 세부 메커니즘

핵심은 "같은 변수 이름이 스레드마다 다른 메모리 주소로 연결된다"는 점이다. 일반 전역 변수는 하나의 고정된 주소를 가지지만, TLS 변수는 스레드마다 별도의 복사본이 만들어지므로 스레드가 새로 생길 때 각자의 몫이 따로 마련되고, 스레드가 끝나면 그 몫도 함께 사라진다. 따라서 같은 코드 `x = 1`을 실행해도 어느 스레드가 실행하느냐에 따라 값이 기록되는 위치가 달라진다. 이렇게 변수의 "수명과 범위"가 프로세스 전체가 아니라 각 스레드에 묶이기 때문에, 락(lock) 같은 별도의 동기화 장치 없이도 안전하게 쓸 수 있다.

#### 4) 예시

**예시 1 — `__thread` / `thread_local` 키워드:**

```c
#include <stdio.h>
#include <pthread.h>

__thread int counter = 0;   // TLS 변수: 스레드마다 별도 복사본

void* worker(void* arg) {
    counter = counter + 100;          // 자기 스레드의 counter만 변경
    printf("스레드 counter = %d\n", counter);
    return NULL;
}

int main() {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker, NULL);
    pthread_create(&t2, NULL, worker, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    return 0;
}
```

`counter`가 일반 전역 변수였다면 두 스레드가 같은 값을 더해 결과가 200까지 올라가거나 경쟁으로 값이 꼬일 수 있다. 하지만 `__thread`로 선언했기 때문에 각 스레드는 0에서 시작하는 자기만의 `counter`를 갖고, 둘 다 다음과 같이 출력한다.

```
스레드 counter = 100
스레드 counter = 100
```

C++에서는 같은 의미로 `thread_local int counter = 0;`라고 쓴다.

**예시 2 — `errno`:** `errno`는 시스템 호출이 실패했을 때 오류 원인을 담아 두는 변수다. 만약 이것이 모든 스레드가 공유하는 전역 변수라면, 스레드 A가 오류 코드를 확인하기 직전에 스레드 B가 다른 오류로 `errno`를 덮어써 버릴 수 있다. 그래서 `errno`는 멀티스레드 환경에서 **스레드별로 독립적인 값을 갖도록** 정의되어, 각 스레드가 자기 작업에서 난 오류만 보게 된다.

#### 5) 다른 키워드와의 연결

이 절에서 다룬 데이터 영역의 전역 변수가 스레드 간 공유되어 데이터 경쟁을 일으키는 문제에 대한 결론적 해법이 TLS다. "공유하면 경쟁이 생기니, 굳이 공유할 필요 없는 데이터는 스레드 전용으로 두자"는 이 절(2.2) 전체의 마무리 역할을 한다.

> 💡 **TMI**
>
> * 언어와 플랫폼마다 TLS를 선언하는 문법이 제각각이다. C11은 `_Thread_local`, GCC는 `__thread`, MSVC는 `__declspec(thread)`, 그리고 C++11부터는 표준 키워드 `thread_local`로 통합됐다.
> * 컴파일러 키워드가 없던 시절에는 POSIX의 `pthread_key_create`로 키를 만들고 `pthread_setspecific`/`pthread_getspecific`로 스레드별 값을 넣고 꺼내는 API 방식으로 TLS를 구현했다. 키워드 방식보다 번거롭지만, 스레드 종료 시 정리 함수(destructor)를 등록할 수 있다는 장점이 있어 지금도 라이브러리 내부에서 쓰인다.

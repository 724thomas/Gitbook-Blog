# 2.1. OS, Process, Thread

## 2.1 운영체제, 프로세스, 스레드의 근본 이해하기

***

### 1. CPU의 동작 원리

#### 1) 개념 정의

CPU는 메모리에 저장된 명령어를 하나씩 가져와 해석하고 실행하는 작업을 끊임없이 반복하는 부품이다.

#### 2) 원리 설명

CPU가 하는 일은 본질적으로 매우 단순하다. "다음에 실행할 명령어를 가져온다(fetch) → 그 명령어가 무엇을 하라는 뜻인지 해석한다(decode) → 실제로 그 작업을 수행한다(execute)"는 세 단계를 전원이 꺼질 때까지 끝없이 반복할 뿐이다. 우리가 작성한 고수준 언어 코드도 결국 컴파일을 거쳐 이러한 단순한 명령어들의 나열이 되고, CPU는 그 줄을 위에서 아래로 한 줄씩 처리한다. 즉 복잡해 보이는 프로그램의 동작도 사실은 "단순한 명령어를 빠르게 반복 실행"하는 결과물이다.

#### 3) 세부 메커니즘

이 반복을 가능하게 하려면 CPU 내부에 작은 저장 공간들이 필요하다. "지금 어느 주소의 명령어를 실행할 차례인가"를 기억하는 자리(보통 PC, 프로그램 카운터라 부른다)가 있어서, 명령어를 하나 가져올 때마다 그 값이 다음 명령어의 주소를 가리키도록 갱신된다. 가져온 명령어 자체를 잠시 담아두는 자리도 있고, 더하기·빼기 같은 실제 계산을 담당하는 연산 장치가 따로 있다. 그래서 한 번의 사이클은 "PC가 가리키는 주소에서 명령어를 읽어오기 → 그 명령어를 해석해 어떤 종류인지 판별 → 연산 장치에 시켜 결과를 만들고 필요하면 메모리나 레지스터에 저장 → PC를 다음 주소로 옮기기"의 흐름을 갖는다.

#### 4) 예시

메모리에 다음과 같은 두 줄짜리 명령이 놓여 있다고 하자.

```asm
ADD R1, R2, R3   ; R2와 R3을 더해 R1에 저장
STORE R1, [100]  ; R1의 값을 메모리 100번지에 저장
```

처음에 PC가 첫 줄의 주소를 가리키고 있으면 CPU는 그 줄을 가져와 "더하기 명령이구나"라고 해석한 뒤, 연산 장치에 R2와 R3을 보내 합을 R1에 넣는다. 그다음 PC가 두 번째 줄의 주소를 가리키게 되고, 같은 방식으로 STORE 명령을 해석해 R1의 값을 메모리 100번지로 옮긴다. 이런 단순 동작이 1초에 수십억 번씩 일어나는 것이 우리가 보는 "프로그램 실행"이다.

#### 5) 다른 키워드와의 연결

CPU는 이렇게 명령을 한 줄씩 충실히 실행할 뿐이라서, 여러 프로그램을 동시에 돌리거나 자원을 관리하는 일은 스스로 하지 못한다. 이 한계가 바로 다음 키워드인 "CPU에서 운영체제로"에서 OS가 등장하는 이유가 된다.

> 💡 **TMI**
>
> * 흔히 "CPU 성능 = 클럭 속도"로 생각하지만 실제로는 `성능 ≈ 클럭 × IPC(Instructions Per Cycle)`에 가깝다. 2000년대 초 인텔 펜티엄 4가 클럭 경쟁(4GHz)에 매달리다 발열로 실패한 뒤, 업계는 IPC와 멀티코어로 방향을 틀었다.
> * 폰 노이만 구조(명령어·데이터 같은 메모리)와 하버드 구조(분리)는 교과서적으로 대립되지만, 현대 CPU 대부분은 외부적으로는 폰 노이만이면서 내부 L1 캐시는 명령어/데이터를 분리한 "수정된 하버드 구조"를 채택한다. 즉 둘 중 하나가 이긴 것이 아니라 절충형이 표준이 됐다.

### 2. CPU에서 운영체제로

#### 1) 개념 정의

운영체제(OS)는 명령어를 단순 반복할 뿐인 CPU 위에서 여러 프로그램을 동시에 돌리고 하드웨어 자원을 효율적으로 나눠 쓰기 위해 등장한 관리자 역할의 소프트웨어다.

#### 2) 원리 설명

CPU 자체는 "지금 가리키는 명령어를 실행"하는 것만 알기 때문에, 한 프로그램이 시작되면 그 프로그램이 끝날 때까지 CPU를 독차지하게 된다. 그러나 우리는 동시에 음악을 들으면서 문서를 작성하고 브라우저로 검색도 하길 원한다. 또한 메모리, 디스크, 키보드, 화면 같은 하드웨어가 여러 프로그램에서 동시에 필요해지는 상황도 끊임없이 생긴다. 이 충돌을 정리하고, CPU 시간을 적절히 나눠 주고, 하드웨어의 복잡한 세부 사항을 프로그램 대신 처리해 주는 누군가가 필요하다. 그 역할을 맡는 소프트웨어가 운영체제다.

#### 3) 세부 메커니즘

OS는 크게 세 가지 일을 한다. 첫째, **자원 관리**: 메모리를 어떤 프로그램에 얼마나 줄지, 디스크 접근 순서를 어떻게 정할지 등을 결정한다. 둘째, **스케줄링**: CPU를 한 프로그램이 영원히 차지하지 못하도록 짧은 시간 단위로 끊어 가며 여러 프로그램에 번갈아 할당해, 사용자 입장에서는 "동시에 돌아가는 것처럼" 보이게 만든다. 셋째, **하드웨어 추상화**: 프로그램이 디스크 모델이나 그래픽 카드 종류를 직접 알 필요 없이 "파일을 읽어라", "화면에 출력하라" 같은 일관된 요청만 하도록 인터페이스를 제공한다. 일반 프로그램이 이런 OS의 기능을 빌리고 싶을 때 사용하는 통로가 바로 **시스템 콜(system call)** 이다.

#### 4) 예시

C 언어에서 파일을 한 줄 읽는 코드를 보자.

```c
FILE *f = fopen("hello.txt", "r");
fgets(buf, 100, f);
```

이 코드는 디스크의 회전 속도, 섹터 위치, 디스크 컨트롤러의 동작 같은 것을 전혀 신경 쓰지 않는다. 프로그램은 그저 "파일을 열고 한 줄 읽어 줘"라고 요청할 뿐이고, 실제로 디스크에서 데이터를 가져오는 복잡한 일은 OS가 시스템 콜을 통해 대신 처리한 뒤 결과만 돌려준다. 또 다른 예로, 음악 플레이어와 문서 편집기를 동시에 열어 둬도 끊김 없이 둘 다 동작하는 것은 OS가 CPU 시간을 짧게 쪼개 번갈아 두 프로그램에 나눠 주기 때문이다.

#### 5) 다른 키워드와의 연결

OS가 여러 프로그램을 동시에 돌리기 위해 도입한 "실행 중인 프로그램"이라는 단위가 곧 다음 키워드인 **프로세스**다.

> 💡 **TMI**
>
> * 시스템 콜은 일반 함수 호출보다 훨씬 비싸다. 2018년 Meltdown/Spectre 패치(KPTI) 이후 리눅스에서 시스템 콜 비용이 상황에 따라 수배까지 증가한 사례가 보고됐고, 이 때문에 `io_uring`처럼 시스템 콜 횟수 자체를 줄이는 비동기 I/O 인터페이스가 도입됐다.

### 3. 프로세스의 등장과 한계

#### 1) 개념 정의

프로세스란 운영체제가 실행 중인 프로그램에 메모리 공간과 자원을 할당해 독립적으로 돌아가게 만든 "실행의 단위"이다.

#### 2) 원리 설명

여러 프로그램을 동시에 돌리려면 운영체제는 각 프로그램에게 "내가 CPU와 메모리를 혼자 쓰고 있다"라고 착각하게 만들어 줘야 한다. 그래서 운영체제는 프로그램이 실행될 때마다 그것을 프로세스라는 단위로 감싸고, 각각에게 독립된 메모리 공간과 실행 상태를 부여한다. 이렇게 격리해 두면 한 프로그램이 망가져도 다른 프로그램에 영향을 주지 않고, CPU는 프로세스들을 빠르게 번갈아 실행해서 동시에 돌아가는 것처럼 보이게 한다. 즉 프로세스는 "프로그램을 안전하게 동시에 돌리기 위한 격리 상자"인 셈이다.

#### 3) 세부 메커니즘

하나의 프로세스가 차지하는 메모리 공간은 보통 네 영역으로 나뉜다. 기계어 명령이 들어 있는 code 영역, 전역·정적 변수를 담는 data 영역, 실행 중에 동적으로 할당받는 heap 영역, 함수 호출 프레임과 지역 변수를 쌓아 두는 stack 영역이다. 운영체제는 이 메모리 배치와 실행 상태(어디까지 실행했는지, 레지스터 값은 무엇인지 등)를 각 프로세스마다 따로 기록해 두고, CPU가 다른 프로세스로 넘어갈 때 이 정보를 통째로 갈아 끼운다. 그런데 이 "갈아 끼우기"는 가상 메모리 매핑(주소 공간) 전환까지 동반하기 때문에 비용이 크다 — 특히 매핑이 바뀌면 주소 변환용 캐시(보통 TLB라 부른다)의 내용이 무효화되어, 한동안은 메모리 접근이 느려지는 부수 효과까지 생긴다. 또 격리가 너무 철저한 나머지 프로세스끼리는 서로의 메모리를 직접 들여다볼 수 없어, 데이터를 주고받으려면 운영체제가 제공하는 별도의 통신 수단을 거쳐야 한다. 결국 프로세스의 두 가지 한계는 (1) 생성과 전환 비용이 크다는 점, (2) 프로세스 간 데이터 공유·통신이 번거롭다는 점이다.

#### 4) 예시

한 프로세스의 메모리 공간을 그림으로 그리면 대략 아래와 같다.

```
높은 주소
┌──────────────┐
│    stack     │  ← 함수 호출, 지역 변수 (위에서 아래로 자람)
│      ↓       │
│              │
│      ↑       │
│    heap      │  ← malloc/new 같은 동적 할당 (아래에서 위로 자람)
├──────────────┤
│    data      │  ← 전역 변수, 정적 변수
├──────────────┤
│    code      │  ← 실행할 기계어 명령
└──────────────┘
낮은 주소
```

같은 프로그램을 두 번 실행해 프로세스 A와 B가 생겼다고 하자. A에서 전역 변수 `count = 10`이 되어도, B의 `count`는 여전히 0이다. 두 프로세스의 data 영역이 물리적으로 따로 떨어져 있기 때문이다. A와 B가 같은 데이터를 함께 다루고 싶다면 운영체제가 제공하는 통신 수단(파이프, 공유 메모리 등)을 명시적으로 사용해야 하며, 변수 하나 공유하듯이 쉽게 쓸 수는 없다.

#### 5) 다른 키워드와의 연결

앞의 "CPU에서 운영체제로"에서 OS가 여러 프로그램을 관리하게 된 흐름이 곧 프로세스의 등장으로 이어지고, 여기서 드러난 두 가지 한계(무거움·공유의 불편함)가 다음 키워드인 "스레드의 등장" 동기로 직접 연결된다.

> 💡 **TMI**
>
> * 유닉스의 `fork()` + `exec()` 분리 패턴은 다른 OS(특히 윈도우의 `CreateProcess`)에서는 거의 채택하지 않은 독특한 설계다. 메모리를 통째로 복제하는 비용 때문에 Copy-On-Write가 도입됐고, 이마저 부담이 커서 리눅스에는 `vfork`, `posix_spawn` 등 경량 대안이 추가됐다.
> * 컨텍스트 스위칭은 CPU 레지스터만 바꾸는 것이 아니라 TLB(주소 변환 캐시) 무효화, 캐시 미스 폭증 같은 "보이지 않는 비용"을 동반한다. 학술 논문들에서 측정한 직간접 비용을 합하면 마이크로초 단위에 달하며, 캐시 워밍업까지 포함하면 수십 마이크로초까지도 보고된다.
> * 리눅스에서 `ps` 명령으로 보이는 PID의 기본 최대값은 32768(`/proc/sys/kernel/pid_max`)이지만, 64비트 시스템에서는 약 400만(2²²)까지 늘릴 수 있다. 컨테이너 시대에 들어 한 호스트에 수만 개 프로세스가 도는 일이 흔해지면서 이 값을 늘리는 튜닝이 일상화됐다.

### 4. 스레드의 등장

#### 1) 개념 정의

스레드란 하나의 프로세스 안에서 함께 돌아가는 더 가벼운 실행 흐름의 단위로, 같은 프로세스의 메모리를 공유하면서 각자 따로 코드를 실행한다.

#### 2) 원리 설명

프로세스가 무겁고 데이터 공유도 번거롭다면, 하나의 프로세스 안에 여러 개의 "실행 흐름"을 두면 어떨까 하는 발상에서 스레드가 등장했다. 스레드들은 같은 프로세스 안에 살기 때문에 code, data, heap 같은 메모리 영역을 그대로 공유하고, 자기 자신이 실행을 이어가는 데 꼭 필요한 부분만 따로 가진다. 그래서 만들고 없애고 전환하는 비용이 프로세스보다 훨씬 작고, 같은 메모리를 들여다보기 때문에 데이터를 주고받기도 쉽다. 결국 스레드는 "프로세스가 주던 동시 실행의 이점은 살리면서, 무겁고 공유가 불편하다는 단점을 덜어낸" 단위라고 볼 수 있다.

#### 3) 세부 메커니즘

한 프로세스 안의 스레드들은 code 영역, data 영역, heap 영역을 함께 쓴다. 그래서 한 스레드가 heap에 만들어 둔 데이터를 다른 스레드가 그대로 읽고 쓸 수 있다. 반면 함수 호출 정보와 지역 변수는 각 스레드마다 따로 가져야 하므로, 스레드는 자신만의 stack을 별도로 가진다. 실행 위치를 가리키는 정보(어느 명령을 실행 중인지, 레지스터 값은 무엇인지)도 스레드마다 따로 있어야 각자의 흐름을 독립적으로 이어갈 수 있다. 이렇게 "공유할 건 공유하고, 꼭 따로 있어야 하는 것만 따로 두는" 구조 덕분에 스레드는 가볍다. 같은 프로세스 안의 스레드끼리 전환할 때는 주소 공간이 그대로 유지되므로 TLB를 비울 필요가 없어 프로세스 전환보다 비용이 작다(다만 레지스터·스택 포인터는 여전히 교체되며, 스레드가 다른 데이터를 만지면 L1/L2 같은 일반 캐시는 자연스럽게 갈리긴 한다).

#### 4) 예시

프로세스와 스레드의 관계를 그림으로 그리면 다음과 같다.

```
     프로세스
┌─────────────────────────────────────────┐
│  code  │  data  │      heap            │  ← 모든 스레드가 공유
├─────────────────────────────────────────┤
│  ┌──────────┐  ┌──────────┐  ┌────────┐│
│  │ 스레드 1 │  │ 스레드 2 │  │ 스레드3││
│  │  stack   │  │  stack   │  │ stack  ││  ← 스레드마다 따로
│  │ 실행위치 │  │ 실행위치 │  │실행위치││
│  └──────────┘  └──────────┘  └────────┘│
└─────────────────────────────────────────┘
```

비유하자면, 프로세스가 "각자 집(메모리 공간)을 따로 가진 가족들"이라면, 스레드는 "한 집 안에서 같이 사는 식구들"이다. 식구들은 같은 거실(heap)과 같은 책장(data)을 함께 쓰니까 물건을 주고받기 쉽고, 다만 각자 자기 방(stack)에서 자기 일(실행 흐름)을 한다. 예를 들어 음악 플레이어 프로그램이 한 스레드로는 소리를 출력하고 다른 스레드로는 사용자 입력(다음 곡, 멈춤 같은 버튼)을 동시에 처리하면, 두 흐름이 같은 재생 목록(공유 메모리)을 그대로 보면서 협력할 수 있다.

#### 5) 다른 키워드와의 연결

앞 키워드 "프로세스의 등장과 한계"에서 드러난 무거움과 공유 불편 문제를 해소하는 답이 바로 스레드이며, 이 "공유한다"는 특성이 다음 키워드 "다중 스레드와 메모리 구조"에서 어떤 영역이 공유되고 어떤 영역이 분리되는지를 더 구체적으로 다루는 흐름으로 이어진다.

### 5. 다중 스레드와 메모리 구조

#### 1) 개념 정의

한 프로세스 안에서 여러 스레드가 동작할 때, 각 스레드는 자기만의 실행 흐름을 위한 영역을 따로 가지면서 동시에 프로세스가 가진 메모리 자원의 대부분을 함께 사용하는 구조를 말한다.

#### 2) 원리 설명

프로세스는 운영체제로부터 코드 영역, 데이터 영역, 힙, 스택 등으로 구성된 메모리 공간을 할당받는다. 스레드는 이 프로세스 내부에서 만들어지는 실행 단위이므로, 프로세스가 이미 가지고 있는 메모리 공간을 그대로 활용한다. 다만 각 스레드는 함수 호출 흐름과 지역 변수를 따로 관리해야 하므로 자기만의 스택을 별도로 가진다. 결과적으로 "스택은 스레드마다 독립, 그 외(코드·데이터·힙)는 공유"라는 구조가 만들어진다. 이 구조 덕분에 스레드 간 데이터 교환이 쉬워지지만, 동시에 같은 데이터를 여러 스레드가 건드릴 수 있다는 문제가 생긴다.

#### 3) 세부 메커니즘

* **스택이 분리되는 이유**: 함수가 호출될 때 매개변수, 지역 변수, 반환 주소가 스택에 쌓인다. 스레드마다 호출하는 함수와 시점이 다르므로, 스택을 공유하면 서로의 호출 프레임이 뒤섞여 버린다. 그래서 각 스레드는 자기 스택을 가져야 한다.
* **힙이 공유되는 이유**: 힙은 프로그램이 실행 중에 동적으로 할당하는 데이터가 놓이는 영역이다. 프로세스 단위로 하나만 존재하므로, 한 스레드가 `malloc`/`new`로 만든 객체의 주소를 다른 스레드에게 넘겨주면 그대로 접근할 수 있다.
* **공유로 인한 문제**: 두 스레드가 같은 변수에 동시에 접근(특히 한쪽 이상이 쓰기)하면, 한쪽의 결과가 덮어써지거나 중간 상태가 보이는 등 의도하지 않은 값이 만들어질 수 있다 — 이를 **데이터 경쟁(data race)** 이라 부른다. 그래서 공유 데이터를 다룰 때는 한 번에 한 스레드만 접근하도록 막아주는 동기화 장치가 필요하다.
* **코드·데이터 영역의 공유**: 코드 영역은 읽기 전용이라 공유해도 충돌이 없고, 전역·정적 변수가 놓인 데이터 영역은 힙처럼 공유 대상이라 마찬가지로 주의가 필요하다.

#### 4) 예시

프로세스 하나에 스레드 두 개가 있는 경우의 메모리 구조를 단순화하면 다음과 같다.

```
┌─────────────────────────────────────────┐
│            프로세스 메모리 공간          │
│                                         │
│  ┌────────────────────────────────────┐ │
│  │  코드 영역 (공유, 읽기 전용)        │ │
│  ├────────────────────────────────────┤ │
│  │  데이터 영역 (전역/정적 변수, 공유) │ │
│  ├────────────────────────────────────┤ │
│  │  힙 (동적 할당, 공유)               │ │
│  │   ← 모든 스레드가 같이 사용          │ │
│  ├──────────────────┬─────────────────┤ │
│  │  스레드 1 스택   │  스레드 2 스택   │ │
│  │  (지역변수,      │  (지역변수,      │ │
│  │   호출프레임)    │   호출프레임)    │ │
│  └──────────────────┴─────────────────┘ │
└─────────────────────────────────────────┘
```

힙 공유로 인한 문제의 단순 예:

```
// 전역(공유) 변수
counter = 0

thread A:                 thread B:
  counter = counter + 1     counter = counter + 1

// 두 스레드가 동시에 실행하면
// 결과는 2가 아닌 1이 될 수도 있다.
// → 동기화 필요
```

#### 5) 다른 키워드와의 연결

"스레드의 등장"에서 스레드가 프로세스보다 가볍다고 한 이유가 바로 이 메모리 공유 구조에 있다. 또한 여기서 드러난 "공유로 인한 동시 접근 문제(데이터 경쟁)"는 다음 키워드인 "스레드 활용 예"에서 생산자-소비자처럼 스레드 간 데이터를 주고받는 시나리오로 자연스럽게 이어진다.

> 💡 **TMI**
>
> * "False sharing(거짓 공유)"은 서로 다른 스레드가 논리적으로는 다른 변수를 만지는데 같은 캐시 라인(보통 64바이트)에 있다는 이유로 성능이 수십 배 떨어지는 현상이다. JDK에는 이를 막기 위한 `@Contended` 어노테이션이, C++에는 `alignas(std::hardware_destructive_interference_size)`가 존재한다.
> * Lock-free 자료구조는 단순히 락을 안 쓰는 게 아니라 "어떤 스레드 하나는 반드시 진행한다"는 진행 보장(progress guarantee)이 형식적으로 정의된 것이다. 더 엄격한 wait-free는 "모든 스레드가 유한 단계 내에 끝남"을 보장하는데, 구현 난도가 매우 높아 실무에서는 lock-free 큐(Michael-Scott queue) 정도가 현실적인 선이다.

### 6. 스레드 활용 예 (생산자-소비자)

#### 1) 개념 정의

여러 스레드를 사용해서 "데이터를 만들어내는 쪽(생산자)"과 "데이터를 처리하는 쪽(소비자)"의 작업 속도 차이를 중간 버퍼로 흡수하며 동시에 진행시키는, 멀티스레드의 대표적인 활용 패턴이다.

#### 2) 원리 설명

현실의 많은 프로그램은 "데이터를 받아오는 일"과 "데이터를 처리하는 일"의 속도가 다르다. 한쪽이 다른 쪽을 기다리며 멈춰 있으면 전체 성능이 느린 쪽에 묶여 버린다. 이때 두 작업을 각각 별도의 스레드로 분리하고, 중간에 공유 버퍼(큐)를 두면, 생산자는 만들어진 데이터를 버퍼에 넣고 곧바로 다음 일을 하러 가고, 소비자는 버퍼에서 꺼내 자기 속도로 처리한다. 같은 프로세스 안의 스레드들은 힙을 공유하므로 이런 공유 버퍼를 자연스럽게 둘 수 있다. 결과적으로 두 작업이 동시에 진행되며 전체 처리량이 올라간다.

#### 3) 세부 메커니즘

* **버퍼가 필요한 이유**: 생산자와 소비자의 속도가 항상 일치하지는 않는다. 생산자가 잠깐 빠를 수도, 소비자가 잠깐 빠를 수도 있다. 버퍼는 이 순간적인 차이를 흡수해 양쪽이 직접 동기화되지 않고도 진행되게 해준다.
* **버퍼가 비었을 때 / 가득 찼을 때**: 소비자는 버퍼가 비어 있으면 꺼낼 게 없으므로 잠시 대기해야 한다. 반대로 버퍼 용량이 정해져 있다면, 가득 찼을 때 생산자도 잠시 대기해야 한다. 이 "기다림"과 "다시 깨우기"가 스레드 간 협력의 핵심이다.
* **공유 버퍼와 동기화**: 버퍼는 힙 위의 공유 자료구조이므로, 생산자와 소비자가 동시에 넣고 빼면 자료구조가 깨질 수 있다. 그래서 한 번에 한 스레드만 버퍼를 건드리도록 보호하는 장치가 필요하다.
* **확장 형태**: 생산자 여러 개, 소비자 여러 개 형태로 확장할 수 있다. 웹 서버에서 요청을 받아 큐에 넣는 스레드(생산자)와 큐에서 꺼내 요청을 처리하는 작업 스레드(소비자)의 구조가 그 예다.

#### 4) 예시

가장 단순한 생산자-소비자 의사 코드.

```
shared queue Q     // 공유 버퍼 (힙에 위치)

Producer thread:
    loop:
        item = produce()        // 데이터를 만든다
        lock(Q)
            while Q.isFull():
                wait()           // 가득 차면 대기
            Q.push(item)
            notify_consumer()    // 소비자에게 알림
        unlock(Q)

Consumer thread:
    loop:
        lock(Q)
            while Q.isEmpty():
                wait()           // 비어 있으면 대기
            item = Q.pop()
            notify_producer()    // 생산자에게 알림
        unlock(Q)
        consume(item)            // 데이터를 처리한다
```

실제 활용의 단순한 그림:

```
[센서/네트워크 입력] → (생산자 스레드) → ┐
                                          │
                                      [공유 큐]
                                          │
[화면 표시/저장]    ← (소비자 스레드) ← ┘
```

웹 서버 비유: 들어오는 HTTP 요청을 받는 스레드가 요청을 큐에 쌓고, 여러 작업 스레드가 큐에서 꺼내 응답을 만들어 보낸다. 한 요청 처리가 느려도 다음 요청 수신은 막히지 않는다.

#### 5) 다른 키워드와의 연결

바로 앞 키워드 "다중 스레드와 메모리 구조"에서 본 "힙은 공유"라는 성질이 있어서 공유 버퍼라는 발상이 가능하다. 또 이 패턴에서 "여러 소비자 스레드가 큐에서 작업을 꺼내 처리한다"는 구조는 다음 키워드인 "스레드 풀의 동작 방식"의 기본 골격이 된다.

> 💡 **TMI**
>
> * 산업에서 대규모 생산자-소비자는 보통 인메모리 큐가 아닌 메시지 브로커로 풀린다. Kafka는 디스크에 로그를 추가하는 방식으로 초당 수백만 메시지 처리량을 노리는 반면, RabbitMQ는 AMQP 기반의 유연한 라우팅이 강점인 식으로 설계 철학이 다르다.

### 7. 스레드 풀의 동작 방식

#### 1) 개념 정의

스레드 풀(thread pool)은 미리 생성해 둔 워커 스레드들과 작업 큐를 결합해, 들어오는 작업을 재사용 가능한 스레드들에게 분배해 실행하는 구조다.

#### 2) 원리 설명

스레드를 매번 생성하고 파괴하는 일은 비용이 든다. 스레드를 만들 때마다 운영체제에 자원(스택 메모리, 스케줄링에 필요한 정보 등)을 요청·반납해야 하므로, 짧은 작업마다 새 스레드를 만들면 본 작업보다 생성·소멸 오버헤드가 더 커질 수 있다. 그래서 일정 수의 스레드를 미리 만들어 두고, 작업이 들어올 때마다 이 스레드들을 반복해서 활용하는 것이 합리적이다. 스레드 풀은 "스레드를 작업에 묶지 말고, 작업을 스레드에 던져 넣는다"라는 발상의 전환이다. 그 결과 작업 제출과 실행이 분리되며, 스레드 생성 비용은 풀이 시작될 때 한 번만 발생한다.

#### 3) 세부 메커니즘

풀의 핵심 구조는 **하나의 작업 큐 + N개의 워커 스레드**다. 외부에서 작업을 큐에 넣고(생산자), 워커 스레드들은 큐에서 작업을 꺼내 실행한다(소비자) — 전형적인 생산자-소비자 패턴이다. 큐가 비어 있으면 워커 스레드는 새 작업이 들어올 때까지 **대기(블록)** 상태로 들어가고, 작업이 들어오면 깨어나 그 작업을 실행한다. 작업이 끝나면 스레드는 종료되지 않고 다시 큐로 돌아가 다음 작업을 기다린다. 반대로 작업이 너무 빠르게 쌓여 큐가 가득 차면 풀의 정책에 따라 처리되는데, 일반적으로는 제출을 막거나(블로킹), 작업을 거절하거나, 호출자가 직접 실행하게 하는 방식이 있다.

#### 4) 예시

워커 + 큐 의사 코드.

```python
queue = BlockingQueue()        # 스레드 안전한 작업 큐

def worker():
    while True:
        task = queue.take()    # 큐가 비면 여기서 블록
        if task is STOP_SIGNAL:
            break
        task.run()             # 끝나도 스레드는 살아 있음

# 풀 시작 시 워커 N개를 미리 생성
for _ in range(N):
    Thread(target=worker).start()

# 외부에서 작업 제출
queue.put(some_task)
queue.put(another_task)
```

흐름: `submit(task)` → 큐에 enqueue → 대기 중이던 워커 하나가 깨어나 `take()` → `task.run()` 실행 → 워커는 다시 `take()`로 돌아가 다음 작업 대기. 워커 수는 고정이지만 실행되는 작업 수는 무제한에 가깝다.

#### 5) 다른 키워드와의 연결

"스레드의 등장"이 해결한 동시성을 실용적으로 활용하기 위한 패턴이 "스레드 활용 예"와 이 "스레드 풀"이며, 다음 키워드인 "스레드 풀의 스레드 수"는 여기서의 N을 어떻게 정할 것인가에 대한 답이다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * 자바의 `ThreadPoolExecutor` 생성자는 corePoolSize, maximumPoolSize, keepAliveTime, timeUnit, workQueue, threadFactory, rejectedExecutionHandler까지 무려 7개의 파라미터를 받는다. `Executors.newFixedThreadPool` 같은 헬퍼는 이걸 감싼 것일 뿐이며, 큐가 무한 `LinkedBlockingQueue`라 OOM을 유발할 수 있어 실무에서는 직접 생성자를 쓰는 것이 권장된다.
> * 자바 스레드 풀의 거절 정책(`RejectedExecutionHandler`)에는 네 가지 기본 구현이 있다: AbortPolicy(예외), CallerRunsPolicy(호출 스레드에서 직접 실행), DiscardPolicy(조용히 버림), DiscardOldestPolicy(가장 오래된 작업을 버리고 다시 시도). 이 중 CallerRunsPolicy는 자연스럽게 백프레셔 역할을 해서 실무에서 의외로 자주 선택된다.

### 8. 스레드 풀의 스레드 수

#### 1) 개념 정의

스레드 풀의 스레드 수는 풀이 유지하는 워커 스레드의 개수로, 시스템 자원 한계와 작업의 성격(CPU 바운드/IO 바운드)을 함께 고려해 정해야 하는 값이다.

#### 2) 원리 설명

스레드가 너무 적으면 CPU 코어가 일감을 못 받아 놀게 된다 — 코어가 8개인데 워커가 2개면 6개의 코어는 쉬고 있는 셈이다. 반대로 스레드가 너무 많으면 컨텍스트 스위칭 비용과 스레드별 스택 메모리가 늘어나, 실제 작업 시간보다 전환 오버헤드가 더 커지는 지점이 온다. 즉 적정 스레드 수에는 **최적점**이 존재한다. 그리고 그 최적점은 작업이 CPU를 계속 쓰는 종류인지, 대부분의 시간을 외부 응답을 기다리는 데 쓰는지에 따라 크게 달라진다.

#### 3) 세부 메커니즘

* **CPU 바운드 작업**: 압축, 암호화, 수치 계산처럼 CPU를 거의 쉬지 않고 쓰는 작업. 코어 수보다 스레드를 많이 만들어도 코어는 하나뿐이므로 동시에 더 처리되지 않고 오히려 스위칭만 늘어난다. 출발점은 대체로 **CPU 코어 수와 비슷한 값**(코어 수, 혹은 코어 수 + 1). +1은 어떤 스레드가 일시적으로 페이지 폴트 등으로 멈췄을 때 코어를 놀리지 않기 위한 여유분이라는 휴리스틱에서 비롯됐다.
* **IO 바운드 작업**: 디스크 읽기, 네트워크 호출, DB 응답 대기처럼 대부분의 시간을 **블록 상태**로 보내는 작업. 한 스레드가 기다리는 동안 다른 스레드가 CPU를 쓰게 해야 하므로, 코어 수보다 훨씬 많은 스레드가 필요하다.
*   **출발 공식**:

    ```
    스레드 수 ≈ CPU 코어 수 × (1 + 대기시간 / 계산시간)
    ```

    * 대기시간/계산시간 비율이 클수록(IO 바운드일수록) 스레드 수가 커진다.
    * 순수 CPU 바운드라면 대기시간 ≈ 0이므로 결과는 코어 수와 같아진다.
    * 단, 이 식은 모든 스레드가 동일한 비율로 일·대기를 한다는 **이상적인 가정** 위에서 나온 추정이다. 실제로는 측정해 보고 조정해야 한다.

#### 4) 예시

코어 8개 머신에서, 한 요청이 평균적으로 90ms를 외부 API 응답 대기에, 10ms를 자기 계산에 쓰는 IO 바운드 작업이라고 하자.

```
스레드 수 = 8 × (1 + 90/10)
        = 8 × 10
        = 80
```

같은 머신에서 동영상 인코딩 같은 CPU 바운드 작업이라면 대기시간이 거의 0이므로:

```
스레드 수 ≈ 8 또는 9 (코어 수 ± 1)
```

같은 하드웨어라도 작업 성격에 따라 권장 스레드 수가 10배까지 차이날 수 있다는 점이 핵심이다. 단, 위 80이라는 숫자는 이론값이고, 실제 운영에서는 DB 커넥션 수·메모리·외부 API 동시 호출 제한 같은 다른 자원이 먼저 병목이 되는 경우가 많아 그대로 적용해서는 안 된다.

#### 5) 다른 키워드와의 연결

앞 키워드 "스레드 풀의 동작 방식"의 N을 결정하는 기준이며, 더 앞으로 거슬러 올라가면 "다중 스레드와 메모리 구조"(스레드마다 스택을 차지하므로 무한정 늘릴 수 없음)와 "CPU의 동작 원리"(코어 수, 컨텍스트 스위칭 비용)가 그 한계의 근거를 제공한다.

> 💡 **TMI**
>
> * 흔히 인용되는 "스레드 수 = CPU 코어 수 × (1 + 대기시간/계산시간)" 공식은 Brian Goetz 등이 쓴 _Java Concurrency in Practice_(2006) 8장에서 제시된 가이드라인이다. 이론적 근거는 큐잉 이론의 **리틀의 법칙(L = λW)** 에서 끌어올 수 있다.
> * 하이퍼스레딩 환경에서 `Runtime.getRuntime().availableProcessors()`는 물리 코어가 아닌 논리 코어를 반환한다. CPU 바운드 워크로드에서는 하이퍼스레딩의 이득이 보통 20\~30% 수준이라, 논리 코어 수만큼 스레드를 띄우면 오히려 컨텍스트 스위칭으로 손해 보는 경우도 많다.
> * 톰캣의 기본 `maxThreads`는 오랫동안 200이었고, 스프링 부트도 이 값을 그대로 물려받았다. 반면 Netty 기반 비동기 서버는 이벤트 루프 스레드를 `코어 수 × 2`개 정도만 띄우는 식으로 철학이 정반대인데, "스레드를 늘려 동시성을 늘린다"가 항상 정답은 아님을 보여주는 대비 사례다.

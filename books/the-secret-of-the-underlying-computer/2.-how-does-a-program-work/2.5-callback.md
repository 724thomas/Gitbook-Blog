# 2.5 Callback

### 1. 모든 것은 다음 요구에서 시작된다

#### 1) 개념 정의

어떤 작업의 처리 절차는 거의 통째로 똑같은데 그 안에서 **딱 한 군데의 동작만 상황마다 달라지는** 패턴이 있고, "그 한 군데를 상황별 동작으로 채우고 싶다"는 요구가 콜백이 태어나는 출발점이다.

#### 2) 원리 설명

절차를 들여다보면 두 부분으로 나뉜다&#x20;

* 매번 똑같이 되풀이되는 **고정 골격**과,&#x20;
* 그 골격 안의 딱 한 자리인 **가변 부분("빈칸")**&#xC774;다.&#x20;

정렬이라면 "나누고·비교하고·자리 바꾸고·합치는" 큰 흐름은 고정이고, "둘 중 누가 앞이냐"는 판단만 상황마다 다르다(오름차순·내림차순·이름순). \
다운로드라면 "연결하고·읽고·확인하는" 흐름은 고정이고 "다 받은 뒤 무엇을 하느냐"만 다르다.&#x20;

그래서 우리가 원하는 건 분명하다 — **골격은 한 벌만 두고, 그 빈칸에 끼울 상황별 동작만 그때그때 바꿔 넣고 싶다.**

#### 3) 세부 메커니즘

빈칸을 채우는 방법으로 가장 먼저 떠오르는 `if/switch`는 한계가 있다. \
새 기준이 생길 때마다 고정 골격 안을 열어 가지를 쳐야 하므로 "골격은 손대지 않는다"는 요구를 정면으로 배신하고, 골격 제작자가 미래의 모든 경우를 미리 알아야 한다는 무리한 전제가 깔린다.&#x20;

그래서 발상을 뒤집는다 — 빈칸에 들어갈 동작을 **골격을 쓰는 쪽이 정해서 건네주면** 된다. \
다운로드 예에서는 한 걸음 더 나아간 요구가 보인다. \
후속 동작은 "지금"이 아니라 "다 받은 그 시점에" 실행되어야 한다.&#x20;

정리하면 요구는 둘로 모인다&#x20;

1. 동작 자체를 미리 넘기고 싶다,&#x20;
2. 그 동작이 알맞은 시점에 실행되기를 바란다.&#x20;

이 두 요구가 "동작을 값처럼 넘긴다"는 발상에 도달하게 만든다.

#### 4) 예시

구현 코드가 아니라 **요구가 생기는 상황**을 의사코드로 본다. 골격은 그대로고 빈칸만 달라진다.

```
절차 sort(목록):
    반복:
        두 원소 a, b 를 고른다              # 고정
        if  ⟨a 가 b 보다 앞이어야 하는가?⟩:  # ← 빈칸 (상황마다 다름)
            자리를 바꾼다                    # 고정
```

```
상황 A: ⟨빈칸⟩ = "a의 숫자가 b보다 작은가"       → 오름차순
상황 B: ⟨빈칸⟩ = "a의 숫자가 b보다 큰가"         → 내림차순
상황 C: ⟨빈칸⟩ = "a의 이름이 가나다순으로 앞인가" → 이름순
```

```
절차 download(주소):
    연결한다                  # 고정
    바이트를 끝까지 읽는다       # 고정
    ⟨다 받은 뒤에 할 일⟩        # ← 빈칸 (그리고 "다 받은 그 시점"에 실행되어야)
```

골격은 한 글자도 안 바뀌고 빈칸만 교체된다 — 이것이 "골격 한 벌, 빈칸은 교체"라는 요구가 현실에서 생기는 모습이다.



이 요구를 형식적으로 정의한 것이 **콜백 함수의 정의(6번)**&#xC774;고, "동작을 값처럼 넘긴다"를 C에서 실현하는 도구가 **함수 포인터(7번)**&#xB2E4;.

> 💡 **TMI**
>
> * "동작(함수)을 값처럼 인자로 받는 함수"를 학술적으로 \*\*고차 함수(higher-order function)\*\*라 부른다.
> * 빈칸만 비우고 골격은 고정해 재사용하는 발상은 객체지향의 **템플릿 메서드(Template Method)·전략(Strategy) 패턴**과 닿아 있다. 본문은 그런 명칭이 붙기 _이&#xC804;_&#xC758; 날것의 요구만 다뤘다.
> * 정렬에서 비교 기준만 갈아 끼우는 요구가, C 표준 `qsort()`가 비교 함수를 인자로 받도록 설계된 바로 그 이유다.

***

폴링과 비교하면 이 요구를 콜백으로 푸는 이점이 분명해진다.

### 2. 콜백이 필요한 이유

#### 1) 개념 정의

끝났는지 직접 반복 확인하며 기다리는 대신 "끝나면 알아서 불러 달라"고 맡겨 두어 낭비 없이 효율적으로 동작하고, 일을 처리하는 쪽과 그 뒤에 할 일을 정하는 쪽을 떼어 놓아 관심사를 분리하기 위해 콜백이 필요하다.

#### 2) 원리 설명

콜백 없이 결과를 기다리는 전형적 방법은 **폴링(polling)**, 즉 "다 됐니? 아직?"을 일정 간격으로 계속 묻는 것이다. \
폴링은 만들기 쉽지만 결과가 아직 없을 때조차 자원을 써 가며 헛되이 확인을 반복하고, 확인과 확인 사이 간격 때문에 실제 완료 시점과 알아채는 시점 사이에 지연이 생긴다. \
콜백은 이를 뒤집어, 일이 끝나는 그 순간 미리 맡겨 둔 함수가 한 번 호출된다. \
헛된 반복이 사라지고, 끝나자마자 즉시 반응하며, 처리할 일이 늘어도 비용이 폴링처럼 불어나지 않는다.

#### 3) 세부 메커니즘

또 하나의 이점은 **결합도(coupling) 낮추기**다. \
작업을 수행하는 모듈(예: 파일을 다 읽어 주는 함수)은 "다 읽은 다음에 무엇을 할지"를 스스로 알 필요가 없다. \
그 "다음에 할 일"을 콜백으로 바깥에서 받아 두었다가 끝나면 불러 주기만 하면 된다. \
그래서 작업 모듈은 후속 동작을 모른 채로도 동작하는 **재사용 가능한** 코드가 되고, 부르는 쪽은 콜백만 바꿔 끼워 같은 모듈로 다른 뒷처리를 시킬 수 있다. \
"일을 처리하는 관심사"와 "그 뒤에 무엇을 할지의 관심사"가 깔끔히 나뉜다.

#### 4) 예시

```c
/* 폴링: 다 됐는지 계속 물어본다 (그동안 다른 일을 못 한다) */
start_download();
while (!is_download_done()) {
    /* 결과가 없어도 루프를 돌며 CPU를 쓴다 (헛된 확인) */
}
process(get_result());
```

```c
/* 콜백: "끝나면 이 함수를 불러 줘"라고 맡기고 손을 뗀다 */
void on_done(Result r) { process(r); }   /* 끝난 순간 호출됨 */

start_download(on_done);   /* 맡겨 두고 다른 일을 계속한다 */
```

콜백판은 `start_download`에 후속 동작을 넘긴 뒤 곧장 다른 일을 이어 가고, 다운로드가 끝나는 순간 `on_done`이 정확히 한 번 호출된다. \
`start_download`는 `on_done`의 내용을 모르므로 콜백만 `save_to_disk`/`show_on_screen`으로 바꾸면 같은 모듈을 여러 용도로 재사용한다.



"끝나면 불러 줘"라고 맡기는 이 방식은 **비동기 콜백(3번)**&#xC73C;로 이어지고, 누가 언제 콜백을 불러 주는지는 **이벤트 루프**가, 콜백으로 넘기는 함수 자체를 C에서 어떻게 전달하는지는 **함수 포인터**가 다룬다.

> 💡 **TMI**
>
> * 콜백이 "내가 너를 부르지 않을게, 끝나면 내가 부를게"로 제어를 뒤집는 원칙을 \*\*할리우드 원칙(Hollywood Principle)\*\*이라 부른다.
> * 이 "관심사 분리"를 키운 것이 **옵저버(Observer) 패턴**과 이벤트 시스템이다.
> * 단일 스레드·논블로킹 환경(JS 등)에서는 폴링이 사실상 안티패턴으로 취급되며, 이후 Promise/async-await가 콜백을 보완한다.

***

이제 콜백이 "지금"이 아니라 "한참 뒤"에 불리는 경우로 들어간다.

### 3. 비동기 콜백

#### 1) 개념 정의

어떤 함수에게 "이 일을 맡길 테니 끝나면 이 함수를 대신 불러 줘"라고 **미리 건네 두는** 콜백으로, 콜백을 건네는 줄과 실제로 실행되는 줄 사이에 시간 간격이 생긴다.

#### 2) 원리 설명

한 문장으로 줄이면 \*\*"맡기기(등록) → 즉시 반환 → 작업 완료가 방아쇠 → 나중 호출"\*\*이다.&#x20;

1. `오래걸리는작업(콜백)`으로 콜백을 넘기면 "나중에 실행될 코드"로 등록만 된다.&#x20;
2. 맡긴 함수는 작업이 끝나길 기다리지 않고 **곧장 반환**해 다음 줄이 바로 이어진다(블로킹되지 않음).&#x20;
3. 맡긴 작업(디스크 읽기·네트워크 응답·타이머)이 끝나는 그 사건이 신호가 되어,&#x20;
4. 등록해 둔 콜백이 비로소 실행된다. 실행 시점은 내가 아니라 작업이 끝나는 시점이 정한다.&#x20;

이렇게 **등록 시점과 호출 시점이 분리**되는 것이 비동기 콜백의 출발점이다.

#### 3) 세부 메커니즘

핵심은 **호출 스택의 단절**이다. \
함수가 호출되면 그 함수의 지역 변수·매개변수를 담은 한 칸(스택 프레임)이 호출 스택에 쌓이고, 반환하면 치워진다. \
비동기에서는 맡긴 함수가 **콜백을 실행하지 않은 채 곧바로 반환**하므로 그 프레임이 콜백과 무관하게 치워지고, 내 동기 코드가 다 끝나면 그 호출 흐름은 사라진다. \
콜백은 이때 실행되지 않고 "나중에 불러야 할 함수"로 보관될 뿐이다. \
작업이 끝나 방아쇠가 당겨지면, 보관돼 있던 콜백이 **원래 맡겼던 함수의 프레임 위가 아니라, (이벤트 루프가 도는) 완전히 새로운 호출 스택 위에 새 프레임으로 처음부터 얹혀** 실행된다.&#x20;

그래서 결론이 하나 따라온다 — 맡긴 함수는 결과가 준비되기 전에 이미 반환했으므로 그 **반환값(return)으로는 결과를 돌려줄 수 없고**, 결과는 **콜백의 인자로 받아야** 한다.

#### 4) 예시

```c
void 결과처리(int 데이터) {          // 나중에 불릴 콜백
    printf("결과 도착: %d\n", 데이터);
}
int main(void) {
    printf("1. 작업을 맡긴다\n");
    오래걸리는작업(결과처리);          // 콜백 등록하고 '즉시' 반환 (결과를 여기서 못 받음)
    printf("2. 맡기자마자 다음 줄로 넘어옴\n");
    return 0;
    // ... 작업이 끝나면, 그때 시스템이 결과처리(데이터)를 새로 호출 ...
}
// 출력: 1. 작업을 맡긴다 / 2. 맡기자마자 다음 줄로 넘어옴 / 결과 도착: 42
```

적힌 순서와 불리는 순서가 어긋나는 것이 "등록 시점과 호출 시점이 분리됐다"는 증거다. 만약 `int 값가져오기(){ int 결과; 오래걸리는작업(...); return 결과; }`처럼 **return으로 받으려 하면** `return` 줄에 도달한 시점엔 결과가 아직 안 채워져 쓸모없는 값을 돌려준다 — 그래서 콜백 인자 방식을 써야 한다.

> 💡 **TMI**
>
> * **JS Promise / async-await**: 콜백 중첩(콜백 지옥)을 푸는 상위 추상화. "결과를 나중에 받는다"는 본질은 같다.
> * **이벤트 루프와 콜백 큐**: 비워진 호출 스택 위에 콜백을 다시 얹는 일을 누가 어떤 순서로 하는지의 런타임 구조(5번).
> * **epoll / kqueue, reactor 패턴**: 다수의 비동기 완료를 효율적으로 감시해 어떤 콜백을 부를지 정하는 OS 수준 통보 메커니즘·설계 패턴.
> * **signal 핸들러**: 커널에 등록해 두고 신호 도착 시 비동기로 불리는 OS 차원의 "등록 후 나중 호출" 사례.

***

이렇게 순서가 어긋나는 비동기는 프로그래밍 사고방식 자체를 바꾼다.

### 4. 비동기 콜백은 새로운 프로그래밍 사고방식으로 이어진다

#### 1) 개념 정의

"내가 함수를 부른다"에서 **"시스템이 내 함수를 부른다"**&#xB85C; 호출의 방향이 뒤집히면서(제어 흐름의 역전), 코드를 짜고 머릿속으로 생각하는 방식 자체가 바뀐다.

#### 2) 원리 설명

동기적 사고에서 프로그램은 **하나의 긴 이야기**다 — 1번 하고, 끝나면 2번, 끝나면 3번. 흐름의 주인은 내 코드이고, 위에서 아래로 내가 정한 순서대로 흐른다.&#x20;

비동기는 그 주도권을 시스템에 넘긴다. \
나는 오래 걸리는 일을 맡기고 "끝났을 때 실행될 조각(콜백)"만 등록해 둔다. \
그러면 내 코드는 멈추지 않고 다음으로 넘어가고, 나중에 일이 끝나는 시점에 시스템이 그 조각을 대신 실행해 준다.

&#x20;즉 나는 "전체 순서를 짜는 사람"에서 **"어떤 일이 일어나면 무엇을 할지 정해 두는 사람"**&#xC73C;로, 명령에서 반응으로 관점이 바뀐다.

#### 3) 세부 메커니즘

구체적으로 세 가지가 바뀐다.&#x20;

1. **코드의 모양** — 1→2→3이 줄지어 있던 한 덩어리가, "일을 시작하는 부분"과 "끝난 뒤 처리하는 부분(콜백)"으로 물리적으로 갈라진다. 그래서 "위에서 아래로 읽으면 실행 순서"라는 직관이 깨지고, 실행 순서는 사건이 일어나는 순서를 따라가야 보인다.&#x20;
2. **결과가 도착하는 위치** — 반환값으로 그 자리에 오지 않고, 나중에 시스템이 콜백을 부를 때 **콜백의 인자**로 전달된다.&#x20;
3. **상태 보존** — 일을 맡기고 함수가 먼저 끝나면 그 지역 변수도 사라지므로, 콜백이 나중에 쓸 값을 콜백이 닿는 곳에 미리 챙겨 두는 새 습관이 필요해진다(동기에선 고민할 필요조차 없던 문제다).

#### 4) 예시

같은 일("파일을 읽어 글자 수 출력")을 두 사고방식으로:

```
// 동기적 사고 — 위→아래, 결과를 바로 받아 사용 (한 덩어리)
function 작업():
    data = 파일읽기("a.txt")   // 다 읽을 때까지 기다림
    개수 = 글자수세기(data)
    출력(개수)
```

```
// 비동기적 사고 — 맡기고, 후속은 콜백 조각으로 (사건-반응)
function 작업():
    파일읽기_시작("a.txt", 다읽었을때)   // 부탁만 하고 즉시 끝
function 다읽었을때(data):              // 결과 data가 '여기'로 도착
    개수 = 글자수세기(data)
    출력(개수)
```

동기 버전은 "내가 1,2,3을 차례로 시킨다"는 이야기이고, 비동기 버전은 "읽기가 끝났다는 _사&#xAC74;_&#xC774; 생기면 `다읽었을때`로 답한다"는 사건-반응 구조다. \
`작업()`은 이미 끝났는데 `다읽었을때()`는 나중에 시스템이 불러 준다 — 호출 순서와 코드 배치 순서가 어긋나고, 결과는 반환값이 아니라 콜백 인자로 온다.



비동기 콜백의 동작 메커니즘 자체는 **3번**, 콜백을 실제로 불러 주는 장치는 **5번 이벤트 루프**가 맡는다. \
이 절은 그 메커니즘이 프로그래머의 머릿속과 코드 구조를 어떻게 바꾸는가를 다뤘다. \
코드가 조각으로 잘게 쪼개지는 구조를 끝까지 밀어붙이면 **9번 콜백 지옥**이 된다.

> 💡 **TMI**
>
> * 제어의 역전의 정식 용어는 **IoC(Inversion of Control)**, 흔히 _헐리우드 원칙_("Don't call us, we'll call you")으로 요약된다. 스프링 등의 의존성 주입(DI)도 같은 IoC의 다른 적용이나 C 입문 범위 밖이다.
> * 이벤트 기반 시스템엔 "콜백은 오래 멈춰(block) 있으면 안 된다"는 규칙이 있다(한 콜백이 멈추면 다음 사건을 아무도 처리 못 함).
> * 콜백으로 갈라진 코드를 다시 "위→아래 이야기"처럼 보이게 되돌려 주는 문법이 **Promise / async-await**다.

***

그렇다면 "시스템이 내 콜백을 불러 준다"의 그 시스템은 어떻게 생겼을까?

### 5. 이벤트 루프 ⊕

#### 1) 개념 정의

완료된 작업 등의 "이벤트"를 큐에 모아 두고, 루프가 그 큐에서 하나씩 꺼내 등록된 콜백을 호출하는 끝없이 도는 반복문으로, 비동기 콜백을 **실제로 호출하는 주체**다.

#### 2) 원리 설명

이벤트 루프가 푸는 문제는 "스레드 하나로 어떻게 여러 작업을 동시에 하는 것처럼 처리하는가"이다. 핵심은 **기다리지 않는다**는 것 — 시간이 걸리는 작업은 OS나 별도 스레드 등에 맡겨 두고 메인 스레드는 멈춰 서서 기다리지 않고 다음 코드로 넘어간다. 맡긴 작업이 끝나면 그 완료 이벤트가 큐에 쌓이고, 메인 스레드는 한가해지면 큐를 들여다보고 쌓인 이벤트의 콜백들을 하나씩 호출한다. 여기서 "동시처럼"은 실제 병렬 실행이 아니라 대기 시간을 다른 작업으로 채워 동시에 진행되는 것처럼 보이게 하는 것이다(**동시성 ≠ 병렬성**).

#### 3) 세부 메커니즘

구성은 둘이다 — **큐**(끝난 작업의 "콜백 불러도 됨" 신호가 먼저 들어온 순서로 쌓이는 곳)와 **루프**(큐에서 하나 꺼내 콜백을 호출하고 다시 큐를 보는 반복문). 가장 중요한 성질은 **한 번에 하나씩**이다. 루프는 콜백 하나를 호출하면 그것이 **완전히 끝날 때까지** 다음으로 넘어가지 않으므로, 어느 순간에도 콜백은 딱 하나만 실행된다(두 콜백이 같은 데이터를 동시에 건드려 꼬일 일이 없어 예측 가능). 대신 조심할 점이 있다 — 한 콜백이 오래 걸리는 일을 붙잡으면 **그동안 루프 전체가 멈춰** 큐에 쌓인 다른 콜백이 아무도 불리지 못한다. 그래서 콜백은 짧게 끝내야 하고, 시간이 걸리는 일은 다시 비동기로 떠넘겨야 한다("블로킹 콜백을 피하라").

#### 4) 예시

```c
while (true) {                 // 프로그램이 사는 동안 끝없이 반복
    event = queue.waitNext();  // 큐에 완료 이벤트가 들어올 때까지 기다렸다 하나 꺼냄
    event.callback(event.result);  // 그 콜백을 호출 — 이게 끝나야 다음으로
}
```

`readFileAsync("a.txt", 읽기콜백)`과 `setTimer(100, 시간콜백)`을 등록해 두면, 두 작업이 끝나는 대로 큐에 쌓이고 루프가 꺼낸 순서대로 호출한다. 콜백이 불리는 순서는 **코드에 쓴 순서가 아니라 작업이 끝난 순서**이며, 한 콜백이 끝나야 다음 콜백이 시작된다(겹치지 않음).

#### 5) 다른 키워드와의 연결

3번 "비동기 콜백"이 "나중에 불러 달라"고 **등록**하는 쪽이라면, 이 절은 그 콜백을 \*\*언제·어떻게 실제로 부르는가(큐+루프)\*\*를 다룬다. 한 번에 하나만 도는 성질 때문에 콜백이 콜백을 부르며 깊이 중첩되면 9번 콜백 지옥으로 이어진다.

> 💡 **TMI**
>
> * **마이크로태스크 vs 매크로(태스크) 큐**: 실제 JS 엔진은 큐가 하나가 아니라 우선순위가 다른 여러 개다(`Promise.then`이 `setTimeout`보다 먼저).
> * **Node.js의 libuv와 phase(단계)**: timers→pending→poll→check→close 등 정해진 단계를 순서대로 돌며, I/O는 내부적으로 스레드 풀·커널이 처리한다.
> * **브라우저 렌더링 큐**: 콜백 처리 사이사이에 화면 렌더링(`requestAnimationFrame`)이 끼어든다.
> * **epoll / kqueue / IOCP**: "여러 작업 중 무엇이 끝났는지"를 OS가 효율적으로 감시해 큐에 신호를 넣는 저수준 메커니즘(리눅스/macOS/윈도우). 이 구조를 일반화한 설계 패턴이 **Reactor 패턴**.

***

지금까지 "언제 불리는가"를 봤으니, 이제 콜백이 무엇인지 형식적으로 정의한다. → 다음은 콜백 함수의 정의.

### 6. 콜백 함수의 정의 ✎

#### 1) 개념 정의

콜백 함수는 내가 직접 호출하지 않고, 다른 코드(주로 라이브러리)에 **인자로 넘겨주어 그쪽이 적절한 시점에 거꾸로(call back) 호출하게** 만드는 함수다.

#### 2) 원리 설명

보통 코드의 호출 방향은 한쪽이다 — 내 코드가 라이브러리를 부른다(**내 코드 → 라이브러리**). \
호출하는 쪽도 나, 흐름을 쥔 쪽도 나다. \
콜백은 이 방향을 뒤집는다. \
내 함수를 라이브러리에 건네주면 호출하는 주체가 라이브러리가 되고 호출당하는 쪽이 내 함수가 된다(**라이브러리 → 내 코드**). \
"내가 부른다"가 "내가 불린다"로 바뀌는 이 **제어 흐름의 역전**이 콜백의 본질이다 — 내가 라이브러리에 매달려 호출하는 것이 아니라, 라이브러리가 필요한 순간 나를 호출한다.

#### 3) 세부 메커니즘

이 역전이 쓸모 있는 까닭은 **메커니즘과 정책을 분리**하기 때문이다. \
메커니즘("어떤 일을 처리하는 큰 틀·절차, 언제 콜백을 부를지")은 라이브러리가 갖고, 정책("그 틀 안에서 구체적으로 무엇을 할지")은 내가 넘긴 콜백이 갖는다.&#x20;

정렬을 예로 들면, "원소들을 비교·교환하며 정렬해 나가는 절차"는 라이브러리(메커니즘)의 몫이고, "두 원소 중 무엇을 앞에 둘지"라는 비교 기준(정책)은 내가 콜백으로 끼워 넣는다.&#x20;

그래서 라이브러리는 자기 코드를 한 줄도 고치지 않고도 내가 넣어 준 콜백만 바꾸면 전혀 다른 정책으로 동작한다.\
메커니즘 제작자와 정책 제작자가 서로를 몰라도 콜백이라는 약속된 접점 하나로 두 코드가 맞물린다.

#### 4) 예시

```c
#include <stdio.h>
void normal(void) { printf("normal: 내가 직접 부른 함수\n"); }

/* 콜백을 받는 라이브러리 함수: done 자리에 내 함수를 받아 내부에서 거꾸로 호출 */
void process(void (*done)(void)) {
    printf("process: 작업 시작 (메커니즘은 라이브러리가 가짐)\n");
    printf("process: 작업 끝, 이제 너의 콜백을 부른다\n");
    done();   /* ← 여기서 제어가 라이브러리에서 내 코드로 넘어간다 (call back) */
}
void on_done(void) { printf("on_done: 라이브러리가 거꾸로 부른 내 콜백\n"); }

int main(void) {
    normal();            /* 일반 호출: main → normal */
    process(on_done);    /* 콜백 등록: on_done을 넘기기만 함 (직접 부르지 않음) */
    return 0;
}
/* 출력:
   normal: 내가 직접 부른 함수
   process: 작업 시작 (메커니즘은 라이브러리가 가짐)
   process: 작업 끝, 이제 너의 콜백을 부른다
   on_done: 라이브러리가 거꾸로 부른 내 콜백   */
```

마지막 줄이 핵심 증거다. \
`main`은 `on_done`을 **한 번도 직접 호출하지 않았는데** 실행됐다 — 제어가 `main → process → on_done`으로 흘렀다. \
`on_done`이라는 함수 자체는 평범하다. \
&#xNAN;**"내가 부르느냐, 남에게 맡겨 거꾸로 불리게 하느냐"**&#xC758; 차이가 콜백 여부를 가른다.



> 💡 **TMI**
>
> * 제어 흐름의 역전을 디자인 담론에서 부르는 정식 약어가 \*\*IoC(Inversion of Control)\*\*다(1988년 Johnson·Foote의 논문에서 정식화로 알려짐). 단 오늘날 스프링 맥락의 "IoC"는 흐름 제어 역전보다 \*\*의존성 주입(DI)\*\*을 가리키는 경우가 많아, 같은 약어가 문맥마다 가리키는 범위가 다르다.
> * 콜백은 학술적으로 **일급 함수(first-class function)·고차 함수** 개념 위에 선다. C엔 진짜 일급 함수가 없어 함수 포인터로 흉내 내지만, 파이썬·JS는 함수 자체를 변수에 담아 넘긴다.
> * 같은 "Don't call us, we'll call you" 원리를 공유하는 패턴이 \*\*옵저버(Observer)·템플릿 메서드(Template Method)\*\*다.

***

그 "함수를 값처럼 넘긴다"를 C에서 가능하게 하는 도구를 본다.

### 7. 함수 포인터 +

#### 1) 개념 정의

함수의 시작 주소를 담는 변수다. \
평소 포인터가 데이터가 놓인 주소를 가리켰다면, 함수 포인터는 **실행될 코드가 놓인 주소**를 가리킨다 — 콜백을 C에서 구현하는 문법적 수단이다.

#### 2) 원리 설명

컴파일된 함수의 기계어는 메모리에 자리 잡고, **함수 이름은 그 코드가 시작되는 주소**를 나타낸다. \
`add(3, 4)`처럼 이름 뒤에 괄호를 붙이면 "그 주소로 점프해 실행"하는 **호출**이지만, 괄호 없이 `add`라고만 쓰면 그것은 **시작 주소 그 자체**다(배열 이름이 첫 원소 주소로 취급되는 것과 같은 이치).&#x20;

그래서 그 주소를 변수에 담아 두었다가 꺼내 호출할 수 있고, 호출하는 코드는 그대로 둔 채 포인터에 담긴 함수만 갈아 끼우면 동작이 달라진다 — 이 "교체 가능성"이 콜백의 토대다.



#### 3) 예시

```c
#include <stdio.h>
int add(int a, int b) { return a + b; }
int sub(int a, int b) { return a - b; }

int main(void) {
    int (*op)(int, int);   // 함수 포인터 선언
    op = add;  printf("%d\n", op(2, 3));    // 5
    op = sub;  printf("%d\n", op(2, 3));    // -1  (호출 코드 그대로, 함수만 교체)
    return 0;
}
```

```c
#include <stdio.h>
#include <stdlib.h>
int compare(const void *a, const void *b) {   // qsort가 콜백으로 호출
    return (*(int *)a - *(int *)b);            // 음수/0/양수로 순서를 알려줌
}
int main(void) {
    int arr[] = {10, 5, 4, 6, 9};
    int n = sizeof(arr) / sizeof(arr[0]);
    qsort(arr, n, sizeof(int), compare);       // compare(이름=주소)를 넘김
    for (int i = 0; i < n; i++) printf("%d ", arr[i]);  // 4 5 6 9 10
    return 0;
}
```

`qsort`의 네 번째 인자 자리가 함수 포인터다. `compare`를 괄호 없이 이름만 넘겼다는 점이 핵심 — 내가 부르는 게 아니라 `qsort` 안에서 대신 불리도록 주소만 건넨다. \
`*(int*)b - *(int*)a`로 빼는 순서만 바꾸면 같은 코드가 내림차순이 된다.



함수 포인터는 콜백 함수의 정의의 "나중에 호출될 함수"를 C 문법으로 실현하는 도구이며, 넘긴 함수가 즉시 불리는지 나중에 불리는지에 따라 두 가지 콜백 유형으로 갈린다.

> 💡 **TMI**
>
> * **호출 규약(calling convention)·ABI**: `cdecl`/`stdcall` 등 인자를 스택/레지스터에 싣는 규칙. 함수 포인터 타입에 호출 규약이 섞이면 호환되지 않을 수 있으나 입문 범위 밖이다.
> * **C++ 멤버 함수 포인터**: `int (ClassName::*p)()` 형태로 객체(`this`)와 묶여야 호출된다.
> * **클로저·람다 캡처**: 다른 언어의 클로저는 "함수 + 주변 변수 환경"을 함께 담지만, C 함수 포인터는 순수 코드 주소만 담아 환경을 캡처하지 못한다(그래서 보통 `void *` 인자로 문맥 데이터를 따로 넘긴다).

***

같은 콜백도 불리는 시점이 갈린다.

### 8. 두 가지 콜백 유형 ✎

#### 1) 개념 정의

콜백이 불리는 시점을 기준으로 **동기 콜백**(바깥 함수가 리턴하기 전에 콜백 호출)과 **비동기 콜백**(먼저 리턴하고 나중에 콜백 호출)으로 나뉜다. \
가르는 단 하나의 질문은 "콜백이 바깥 함수 **리턴 전이냐 후냐**".

#### 2) 원리 설명

먼저 짚을 점 — **콜백 함수 그 자체만 보고는 동기/비동기를 알 수 없다.** \
콜백은 "남에게 건네주는 함수"일 뿐이고, 언제 불러 줄지는 전적으로 그것을 건네받은 **바깥 함수**가 정한다.&#x20;

그래서 똑같이 생긴 콜백도 어떤 바깥 함수에 넘기느냐에 따라 동기로도, 비동기로도 동작한다. \
기준은 바깥 함수의 **리턴 시점**과 콜백의 **호출 시점**의 선후 하나뿐이다 — 동기는 바깥 함수가 콜백이 끝날 때까지 **기다리고**(흔히 블로킹처럼 쓰임), 비동기는 **기다리지 않고** 곧장 리턴한다(흔히 논블로킹처럼 쓰임). \
단, "동기/비동기"와 "블로킹/논블로킹"이 엄밀히 항상 같지는 않다(→ TMI).

#### 3) 세부 메커니즘

같은 잣대로 나란히 놓으면 차이가 또렷하다.

| 구분              | 동기 콜백             | 비동기 콜백            |
| --------------- | ----------------- | ----------------- |
| 콜백이 불리는 시점      | 바깥 함수 **리턴 전**    | 바깥 함수 **리턴 후**    |
| 바깥 함수의 태도       | 콜백 끝날 때까지 **기다림** | 기다리지 않고 **바로 리턴** |
| 다음 줄 도달 시 콜백 상태 | **이미 다 끝남**       | **아직 안 불림**       |
| 콜백이 도는 위치       | 바깥 함수 흐름 위에서 곧바로  | 바깥 함수가 끝난 뒤 따로    |

표의 마지막 줄("콜백이 도는 위치")은 여기서는 한 줄로만 짚는다 — 비동기 쪽에서 호출 흐름이 어떻게 끊겼다가 콜백이 새로 얹히는지의 안쪽 동작은 \*\*3번(비동기 콜백)\*\*이 다룬다. \
8번의 역할은 어디까지나 "무엇을 기준으로 두 유형을 가르는가"와 "둘이 어떻게 대조되는가"이다.

#### 4) 예시

```c
/* 동기 콜백: qsort는 정렬을 다 끝낸 뒤에야 리턴하며, 그 전에 cmp를 여러 번 부른다 */
int cmp(const void *a, const void *b) { return (*(int*)a) - (*(int*)b); }
int main() {
    int arr[] = {3, 1, 2};
    qsort(arr, 3, sizeof(int), cmp);   // 이 줄이 끝나면 정렬이 이미 완료됨
    printf("%d %d %d\n", arr[0], arr[1], arr[2]);  // 1 2 3
}
```

```
// 비동기 콜백: 요청만 하고 리턴, 콜백은 나중에
요청_보내기(데이터, 콜백);   // "끝나면 콜백 불러줘" 부탁만 하고 즉시 리턴
다음_줄_실행();              // 콜백은 아직 안 불렸는데 이 줄이 먼저 실행됨
// ... 한참 뒤, 맡긴 일이 끝나면 그때서야 콜백(결과)이 불린다
```

**동기는 "리턴한 다음 줄에서 콜백 결과가 이미 준비됨", 비동기는 "리턴한 다음 줄에서 콜백이 아직 안 불림"** — 갈림길은 오직 콜백이 바깥 함수 리턴 전에 불렸느냐 후에 불렸느냐, 그 하나다.



비동기 쪽이 "어떻게 바깥 함수가 먼저 끝난 뒤 콜백이 따로 불리는가"의 안쪽 동작은 **3번**이 이어받는다. \
두 유형 모두 "함수를 인자로 넘긴다"는 같은 도구(**함수 포인터,** ) 위에 선다.

> 💡 **TMI**
>
> * **동기/비동기와 블로킹/논블로킹은 사실 다른 축이다.** 동기/비동기는 "결과를 누가 기다리는가(직접 챙기나 통지받나)", 블로킹/논블로킹은 "제어권이 곧장 돌아오는가"의 문제다. 그래서 동기-논블로킹, 비동기-블로킹 같은 조합도 이론적으로 존재한다(본문은 입문 수준에서 둘을 짝지어 다뤘다).
> * **JS의 Promise/async·await**는 비동기 콜백을 더 읽기 좋게 감싼 상위 문법이다.
> * `setTimeout(fn, 0)`처럼 "0초 뒤"를 줘도 콜백은 지금 줄에서 곧바로 불리지 않고 현재 코드가 끝난 뒤 불린다("리턴 후" 기준을 보여주나, 정확한 순서엔 이벤트 루프·태스크 큐가 필요).

***

비동기 콜백을 여러 개 엮으면 마지막 문제에 부딪힌다.

### 9. 비동기 콜백의 문제: 콜백 지옥

#### 1) 개념 정의

비동기 작업을 정해진 순서대로 실행시키려고 콜백 안에 또 다른 콜백을 계속 집어넣다 보니, 코드가 오른쪽으로 끝없이 깊어져 읽기도 고치기도 어려워지는 상태다. \
들여쓰기가 삼각형처럼 벌어져 멸망의 피라미드(pyramid of doom)라고도 불린다.

#### 2) 원리 설명

비동기 작업은 "지금 시작은 했지만 결과는 나중에 나온다". 작업이 하나면 평화롭지만, 현실의 요구는 보통 "A를 읽어 **그 결과로** B를 요청하고, **B가 오면** 그걸로 C를 처리하라"처럼 뒤 작업이 앞 작업 결과에 의존한다(순서가 있다).

&#x20;그런데 비동기에서는 다음 줄에 써도 순서가 보장되지 않는다(A를 시작하자마자 코드는 다음 줄로 넘어가 A의 결과가 오기도 전에 B를 요청). \
그래서 순서를 강제하려면 "B를 A의 콜백 **안에서** 시작"해야 하고, **콜백만 사용할 경우** 이것이 사실상 유일한 방법이라 작업이 늘수록 콜백이 콜백 안에, 그 안에 또 콜백이 들어가는 중첩이 불가피하게 쌓인다.

#### 3) 세부 메커니즘

**"다음 줄"이라는 개념이 사라진다.** \
동기 코드는 "이 줄 다음엔 아래 줄"이라는 약속에 의지해 위→아래로 읽는다. \
비동기 콜백으로 순서를 엮으면 "다음에 할 일"이 아래 줄이 아니라 **현재 줄의 안쪽(콜백 내부)**&#xC73C;로 들어가, 실행이 바깥→안쪽으로 파고드는 모양이 된다. \
글은 위에서 아래로 읽는데 논리는 안으로 파고드니 둘을 맞춰 읽기가 피곤하다.&#x20;

또 **상태 추적이 어렵다** — 바깥 콜백 값을 안쪽 콜백에서 또 써야 해 값들을 계속 더 안쪽으로 끌고 들어가야 한다. \
**에러 처리가 단계마다 반복된다** — 각 콜백이 자기 단계 실패를 자기 자리에서 점검해야 해 비슷한 검사 코드가 거듭 등장하고 빠뜨리기 쉽다. \
**유지보수도 어렵다** — 중간에 작업을 끼우거나 순서를 바꾸려면 깊게 중첩된 구조를 헤집어야 한다.

#### 4) 예시

```
작업A_시작(입력, 결과A => {
    에러검사(결과A);
    작업B_시작(결과A, 결과B => {
        에러검사(결과B);
        작업C_시작(결과B, 결과C => {
            에러검사(결과C);
            최종처리(결과C);
        });
    });
});
// 닫는 괄호들이 계단처럼 우르르 닫힌다 — 멸망의 피라미드
```

같은 일이 (가상의) 동기 코드였다면 평평하게 흐른다:

```
결과A = 작업A(입력);
결과B = 작업B(결과A);
결과C = 작업C(결과B);
최종처리(결과C);
```

두 코드는 **똑같은 순서의 똑같은 일**을 하지만, 한쪽은 안으로 파고드는 피라미드, 다른 한쪽은 한눈에 읽히는 목록이다. 이 차이가 곧 가독성·에러 처리·디버깅의 차이로 이어진다.



콜백 지옥은 **비동기 콜백**을 여러 개 엮을 때 생기는 부작용이며, **새로운 사고방식(4번)**&#xC5D0;서 말한 "위→아래로 읽히는 자연스러운 흐름"이 비동기에서 깨진다는 사실을 드러낸다. \
이후 이 피라미드를 다시 펴기 위한 도구(Promise 등)가 등장하지만, 출발점은 "왜 콜백이 지옥이 되는가"를 이해하는 데 있다.

> 💡 **TMI**
>
> * **Promise / then·catch, async-await**: 콜백 지옥을 평평하게 펴는 대표적 개선 도구(구체 문법은 책 범위 밖).
> * **CPS(Continuation-Passing Style)**: "다음에 할 일을 함수로 넘긴다"는 콜백 방식을 가리키는 학술 용어.
> * **오류 우선 콜백(error-first callback)**: 콜백 첫 인자로 에러를 넘기는 Node.js 관례 — 단계마다 에러 검사가 반복되는 이유와 관련.

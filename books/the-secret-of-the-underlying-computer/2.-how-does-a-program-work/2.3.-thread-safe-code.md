# 2.3. Thread Safe Code

### 1. 자유와 제약

#### 1) 개념 정의

스레드는 스케줄러에 의해 언제든 자유롭게 실행·중단·전환될 수 있기 때문에, 그 자유를 안전하게 길들이기 위해 코드에 동기화라는 제약을 걸어야 한다는 도입 개념이다.

#### 2) 원리 설명

운영체제의 스케줄러는 여러 스레드를 번갈아 실행시키며, 어느 스레드가 언제 멈추고 언제 이어서 실행될지는 프로그래머가 정할 수 없다.&#x20;

즉 스레드는 우리 코드의 어느 지점에서든 갑자기 멈췄다가 한참 뒤에 다시 시작될 "자유"를 가진다. \
이 자유는 단일 스레드라면 문제가 없지만, 여러 스레드가 같은 데이터를 만질 때는 실행 순서가 뒤엉켜 잘못된 결과를 낳는다.&#x20;

그래서 우리는 "여기서는 한 번에 한 스레드만 들어와라" 같은 제약을 코드에 직접 명시해야 한다. \
이 제약이 바로 동기화이며, 자유를 적절히 제약하는 것이 멀티스레드 프로그래밍의 핵심이다.

#### 3) 세부 메커니즘

스레드 전환은 한 줄의 코드 사이뿐 아니라, 우리가 한 줄로 본 코드의 "중간"에서도 일어날 수 있다는 점이 자유의 본질이다.&#x20;

예를 들어 `count = count + 1`은 소스 코드상으로는 한 줄이지만, 실제로는&#x20;

1. 값을 읽고
2. 1을 더하고
3. 다시 저장하는&#x20;

여러 단계로 쪼개져 실행된다. \
스케줄러는 이 단계들 사이 어디에서든 스레드를 멈출 수 있고, 바로 그 틈에 다른 스레드가 끼어들면 결과가 어긋난다.&#x20;

따라서 제약을 건다는 것은 "쪼개지면 안 되는 동작들을 하나로 묶어, 그 사이에 다른 스레드가 끼어들지 못하게 만드는 것"을 의미한다.

#### 4) 예시

```c
// 두 스레드가 동시에 이 코드를 실행한다고 가정 (초기 count = 0)
count = count + 1;   // 각 스레드가 한 번씩 실행

// 기대 결과: count == 2
// 실제로 일어날 수 있는 일:
//   스레드A: count(0)를 읽음
//   스레드B: count(0)를 읽음   <- 여기서 끼어듦
//   스레드A: 0+1=1 저장
//   스레드B: 0+1=1 저장
// 결과: count == 1  (1이 사라짐!)
```

위처럼 "자유롭게" 끼어드는 전환 때문에, 제약(동기화) 없이는 더하기 한 번이 통째로 누락될 수 있다. \
이렇게 스레드의 접근 순서에 따라 결과가 달라지는 상황을 풀어 말하면 "두 스레드가 서로의 작업을 덮어쓰는 문제"다.



이 자유 때문에 생기는 문제를 제약으로 막아 "추가 동기화 없이도 동시에 호출 가능한 코드"를 만드는 것이 **스레드 안전**의 목표다.

> 💡 **TMI**
>
> * 프로그래밍에서 "자유"와 "제약"의 긴장은 더 큰 격언으로도 나타난다. "공유 가능한 가변 상태(shared mutable state)"가 동시성 버그의 근원이라는 말이 그것인데, 함수형 프로그래밍은 아예 가변 상태를 없애는 방향으로 이 문제를 회피한다.
> * 동시성 버그는 재현이 잘 안 돼서 "하이젠버그(Heisenbug)"라 불리기도 한다. 관찰하려고 디버거를 붙이면 타이밍이 바뀌어 증상이 사라지기 때문이다.
> * "결과가 접근 순서에 따라 달라지는 상황"을 엄밀히는 **경쟁 상태(race condition)**, 그중 동기화 없이 같은 메모리를 동시에 읽고 쓰는 것을 데이터 경쟁(data race)이라 한다. 둘은 포함 관계가 아니라 서로 다른 개념(교집합·차집합 모두 존재)이라 학술적으로 구분된다.

***

이렇게 "자유가 부르는 문제"를 봤으니, 그렇다면 "안전하다"는 것의 정확한 기준은 무엇일까?

### 2. 스레드 안전이란 무엇일까?

#### 1) 개념 정의

스레드 안전 코드란, 호출하는 쪽에서 별도의 동기화 조치를 추가하지 않아도 여러 스레드가 동시에 호출했을 때 항상 올바르게 동작하는 코드다.

#### 2) 원리 설명

"안전하다"의 기준은 결과가 우연히 맞는 것이 아니라, 스레드들이 어떤 순서로 끼어들어 실행되더라도 매번 올바른 결과가 보장되는 것이다. \
핵심은 "호출자가 아무것도 신경 쓰지 않아도 된다"는 점이다. \
어떤 코드가 스레드 안전하면, 사용자는 그냥 여러 스레드에서 마음 놓고 호출하면 되고, 안전하지 않으면 사용자가 직접 잠금 등으로 보호해야 한다.&#x20;

즉 스레드 안전은 "동기화 책임이 코드 내부에 들어 있느냐, 아니면 호출자에게 떠넘겨지느냐"의 문제다.

#### 3) 세부 메커니즘

스레드 안전 여부는 함수가 어떤 종류의 리소스를 건드리는지에 따라 갈린다. \
함수가 자기 스레드만의 데이터(지역 변수 등)만 다룬다면, 다른 스레드와 부딪힐 일이 없으니 그 자체로 안전하다. \
반대로 여러 스레드가 공유하는 데이터를 읽고 쓰면서 아무 보호도 하지 않으면 안전하지 않다.&#x20;

따라서 "스레드 안전하게 만든다"는 것은 추상적인 선언이 아니라, 그 함수가 만지는 공유 데이터를 찾아내 그 접근 부분만 제약으로 보호한다는 구체적 작업을 뜻한다.

#### 4) 예시

```c
// (1) 스레드 안전한 함수 — 지역 변수만 사용
int add(int a, int b) {
    int result = a + b;   // result는 이 호출만의 지역 변수
    return result;
}
// 몇 개의 스레드가 동시에 add()를 불러도 서로 간섭 없음 -> 항상 정확

// (2) 스레드 안전하지 않은 함수 — 전역 변수 공유
int total = 0;
void accumulate(int x) {
    total = total + x;    // 모든 스레드가 같은 total을 동시에 수정 -> 결과 어긋날 수 있음
}
// 호출자가 직접 잠금으로 보호하지 않으면 결과가 틀어질 수 있음 -> 안전하지 않음
```



스레드 안전 여부를 가르는 결정적 기준이 바로 **스레드 전용 리소스와 공유 리소스**의 구분이며, 문제는 공유 리소스에서만 생긴다.

> 💡 **TMI**
>
> * 흔히 "재진입 가능(reentrant)"과 "스레드 안전(thread-safe)"을 같은 말로 착각하지만 둘은 동치가 아니다. 정적 지역 변수에 락을 걸면 스레드 안전이지만 재진입 불가능할 수 있고, 반대로 시그널 핸들러에서 안전하게 재진입되는 함수가 멀티스레드에서는 안전하지 않을 수도 있다.
> * "스레드 안전" 위에는 더 엄격한 개념인 리니어라이저빌리티(linearizability)가 있다. 동시에 일어난 연산들이 마치 어떤 순간에 하나씩 차례로 실행된 것처럼 보여야 한다는 정합성 기준으로, 단순히 "깨지지 않음"보다 강한 보장이다.
> * 자바 표준 라이브러리는 같은 자료구조를 안전 버전과 비안전 버전으로 나눠 제공한다. `Vector`/`Hashtable`은 스레드 안전하지만 느리고, `ArrayList`/`HashMap`은 안전하지 않은 대신 빨라서, 개발자가 상황에 맞게 고르도록 설계되어 있다.

***

그렇다면 "공유 리소스"란 정확히 무엇이고, 무엇이 전용일까?

### 3. 스레드 전용 리소스와 공유 리소스

#### 1) 개념 정의

* 각 스레드가 독립적으로 가지는 전용 리소스(스택·지역 변수·레지스터)
* 여러 스레드가 함께 접근하는 공유 리소스(전역 변수·힙·정적 변수·파일)

를 구분하는 분류로, 스레드 안전 문제는 오직 공유 리소스에서 발생한다.

#### 2) 원리 설명

스레드 전용 리소스는 각 스레드마다 별도로 하나씩 존재하므로, 한 스레드가 자기 것을 아무리 바꿔도 다른 스레드의 것에는 영향이 없다. \
대표적으로 함수 안에서 선언한 지역 변수는 호출하는 스레드마다 자기 스택에 따로 만들어지기 때문에 충돌이 없다. \
반면 공유 리소스는 모든 스레드가 같은 하나의 대상을 바라보므로, 여러 스레드가 동시에 읽고 쓰면 값이 엉킨다.&#x20;

따라서 어떤 코드가 위험한지 판단하려면, 그 코드가 전용 리소스만 만지는지 아니면 공유 리소스를 건드리는지를 먼저 가려내면 된다. \
결국 동기화 제약은 공유 리소스에 접근하는 부분에만 걸면 충분하다.

#### 3) 세부 메커니즘

전용과 공유를 가르는 실질적 기준은 "그 데이터가 메모리상 어디에 놓이느냐"다. \
스택에 놓이는 지역 변수나 함수 인자, 그리고 CPU 레지스터 값은 스레드를 전환할 때 각자 보관·복원되므로 스레드별로 독립적이다. \
반대로 전역 변수와 정적 변수, 그리고 `malloc` 등으로 힙에 할당한 메모리는 프로세스 안의 모든 스레드가 같은 주소를 공유하므로 한 덩어리를 함께 만진다. \
파일 같은 외부 자원도 여러 스레드가 같은 대상을 열어 쓰면 공유 리소스가 된다. \
그래서 함수가 스레드 안전한지 보려면 "지역 변수로만 끝나는가, 아니면 전역·정적·힙·파일에 손을 대는가"를 확인하는 것이 출발점이다.

#### 4) 예시

```c
int g_count = 0;          // 전역 변수 -> 공유 리소스

void worker(void) {
    int local = 0;        // 지역 변수 -> 스레드 전용 (스레드마다 따로 존재)
    local = local + 1;    // 각자 자기 local만 건드림 -> 안전

    g_count = g_count + 1; // 모두가 같은 g_count를 건드림 -> 위험 (보호 필요)
}

// 스레드 3개가 worker()를 실행하면:
//   local  : 각 스레드에서 항상 1 (서로 독립, 문제 없음)
//   g_count: 보호가 없으면 3이 아니라 1이나 2가 될 수 있음
```

지역 변수 `local`은 전용이라 언제나 예상대로 동작하지만, 전역 변수 `g_count`는 공유라서 보호 없이는 값이 어긋난다.



이 분류는 **스레드 안전**을 판단하는 구체적 잣대를 제공하고, **자유와 제약**에서 말한 동기화 제약을 "정확히 어디(=공유 리소스)에 걸어야 하는가"라는 답으로 이어준다.

> 💡 **TMI**
>
> * 프로세스 안의 스레드들은 코드·전역 변수·힙을 공유하지만 스택은 각자 따로 가진다. 그래서 함수 안의 지역 변수가 자동으로 스레드 전용이 되는데, 이 "스택 분리"가 멀티스레드 안전성의 가장 기본적인 출발점이다.
> * 메모리 공유 모델과 정반대 철학을 가진 언어도 있다. Erlang과 Go의 "메시지 패싱" 사상이 대표적으로, Go에는 "메모리를 공유해서 통신하지 말고, 통신해서 메모리를 공유하라(Do not communicate by sharing memory; share memory by communicating)"라는 유명한 격언이 있다.

***

문제가 공유에서만 생긴다면, 가장 쉬운 안전 코드는 "아예 공유하지 않는 것"이다.

### 4. 스레드 전용 리소스만 사용하기

#### 1) 개념 정의

함수 안에서 공유 자원을 전혀 건드리지 않고 오직 스레드마다 따로 존재하는 리소스(지역 변수 등)만 사용하면, 그 함수는 별도의 잠금 없이도 자동으로 스레드 안전해진다는 원칙이다.

#### 2) 원리 설명

멀티스레드에서 문제가 생기는 근본 원인은 여러 스레드가 같은 데이터를 동시에 읽고 쓰면서 서로의 작업을 망가뜨리기 때문이다. \
그렇다면 애초에 "여러 스레드가 같이 쓰는 데이터"를 만들지 않으면 충돌할 일 자체가 사라진다. \
함수 안에서 선언한 지역 변수는 각 스레드가 자기 스택(stack)에 따로 보관하기 때문에, 같은 함수를 100개의 스레드가 동시에 실행해도 각자의 지역 변수는 서로 완전히 분리되어 있다.&#x20;

즉 A 스레드의 지역 변수와 B 스레드의 지역 변수는 이름만 같을 뿐 메모리상 전혀 다른 공간에 존재한다. \
따라서 이런 함수는 잠금(lock)도 필요 없고, 신경 써서 동기화할 것도 없이 그 자체로 안전하다.

#### 3) 세부 메커니즘

왜 지역 변수가 스레드마다 따로 존재할까? \
그 핵심은 "스택은 스레드마다 하나씩 따로 주어진다"는 데 있다. \
프로그램에서 스레드를 만들면 운영체제는 그 스레드 전용으로 스택 공간을 새로 할당한다. \
함수가 호출될 때 지역 변수는 그 함수를 호출한 스레드의 스택 위에 만들어지므로, 같은 함수라도 호출한 스레드가 다르면 변수가 놓이는 메모리 위치가 다르다. \
반대로 전역 변수나 `static` 변수, 힙(heap)에 할당해 여러 스레드가 함께 가리키는 데이터는 모든 스레드가 공유하는 영역에 있으므로 이 안전성이 깨진다.&#x20;

정리하면, "어디에 저장되는가(스레드별 스택이냐, 공유 영역이냐)"가 안전 여부를 가른다.

#### 4) 예시

아래 함수는 지역 변수만 사용하므로 여러 스레드가 동시에 호출해도 안전하다.

```c
int square_sum(int a, int b) {
    int x = a * a;   // 지역 변수: 스레드마다 따로 존재
    int y = b * b;   // 지역 변수: 스레드마다 따로 존재
    int sum = x + y; // 지역 변수
    return sum;
}
```

스레드 1이 `square_sum(2, 3)`을, 스레드 2가 `square_sum(4, 5)`를 동시에 호출해도, 각자의 `x`, `y`, `sum`은 자기 스택에 따로 있으므로 서로 간섭하지 않는다. 결과는 항상 스레드 1은 `13`, 스레드 2는 `41`로 정확하게 나온다.

반대로 아래는 전역 변수를 사용하므로 안전하지 않다(대비용).

```c
int g_sum;  // 전역 변수: 모든 스레드가 공유 → 위험

int square_sum_bad(int a, int b) {
    g_sum = a * a;
    g_sum = g_sum + b * b;
    return g_sum;
}
```

이 경우 두 스레드가 동시에 `g_sum`을 쓰면 서로의 중간 계산값을 덮어써서, 한 스레드가 엉뚱한 결과를 받을 수 있다.



이 키워드는 "스레드 전용 리소스와 함수 매개변수"로 이어진다. \
매개변수도 일종의 전용 리소스가 될 수 있지만, 전달 방식에 따라 이 안전성이 유지될 수도 깨질 수도 있기 때문이다.

> 💡 **TMI**
>
> * "아무것도 공유하지 않기(shared-nothing)"는 멀티스레드뿐 아니라 대규모 분산 시스템의 확장성 설계 원칙이기도 하다. 각 노드가 상태를 공유하지 않으면 락 경합 없이 거의 무한대로 수평 확장할 수 있어서, 많은 웹 서버가 요청별로 독립 처리하는 무상태(stateless) 구조를 택한다.
> * 지역 변수만 쓰면 안전하다는 원칙에도 함정이 있다. 지역 변수의 "주소"를 다른 스레드에 넘겨버리면, 전용 리소스가 순식간에 공유 리소스로 바뀌어 안전성이 깨진다. (바로 다음 키워드의 핵심)

***

방금 언급한 "주소를 넘기면 깨진다"는 단서가, 매개변수를 다룰 때 정확히 문제가 된다.

### 5. 스레드 전용 리소스와 함수 매개변수

#### 1) 개념 정의

함수의 매개변수도 값으로 전달되면 복사본이라 스레드 전용이 되지만, 포인터나 참조로 전달되면 그것이 가리키는 대상이 공유 자원일 수 있으므로 매개변수 자체가 아니라 "가리키는 대상까지" 봐야 안전 여부를 판단할 수 있다는 원칙이다.

#### 2) 원리 설명

함수 매개변수는 기본적으로 지역 변수와 같은 성질을 가진다. \
값으로 전달(pass by value)하면 호출하는 쪽의 값을 복사해서 함수 안에 새로 만들기 때문에, 그 복사본은 해당 스레드의 스택에 있는 전용 리소스가 된다.&#x20;

따라서 값 전달 매개변수만 다루는 함수는 앞의 "전용 리소스만 사용하기"와 마찬가지로 안전하다. \
그런데 포인터(또는 참조)로 전달하면 함수가 받는 것은 "데이터 자체"가 아니라 "데이터가 있는 주소"다. \
이 주소가 여러 스레드가 함께 가리키는 공유 데이터를 향하고 있다면, 매개변수(주소 값)는 전용이어도 그 주소가 가리키는 실제 데이터는 공유 자원이므로 충돌이 발생할 수 있다.

#### 3) 세부 메커니즘

여기서 핵심은 "전용인 것은 어디까지인가"를 구분하는 것이다. \
포인터로 전달할 때, 포인터 변수 그 자체(주소를 담은 작은 값)는 복사되어 각 스레드의 스택에 따로 존재한다.&#x20;

즉 "주소를 담은 상자"는 전용이다. \
하지만 그 상자가 가리키는 곳, 즉 실제 데이터가 놓인 메모리는 복사되지 않는다. \
여러 스레드에 같은 주소를 넘기면 모두가 같은 한 덩어리의 데이터를 가리키게 되고, 그 데이터를 동시에 쓰면 충돌한다.&#x20;

그래서 매개변수의 안전성을 따질 때는 "매개변수 변수가 전용이냐"가 아니라 "매개변수가 최종적으로 도달하는 데이터가 공유되느냐"를 봐야 한다. \
값 전달은 데이터까지 통째로 복사하지만, 포인터 전달은 주소만 복사하고 데이터는 공유한다는 차이가 모든 것을 가른다.

#### 4) 예시

값 전달 — 안전:

```c
int add_one(int x) {  // x는 복사본 → 스레드 전용
    x = x + 1;
    return x;
}
```

스레드 여러 개가 동시에 호출해도 각자의 `x`는 자기 스택의 복사본이므로 서로 영향을 주지 않는다.

포인터 전달 — 같은 대상을 가리키면 위험:

```c
void add_one_ptr(int *p) {  // p(주소)는 전용이지만,
    *p = *p + 1;            // *p(가리키는 데이터)는 공유될 수 있음
}

int shared = 0;
// 스레드 1: add_one_ptr(&shared);
// 스레드 2: add_one_ptr(&shared);
```

두 스레드가 같은 `&shared`를 넘기면, 둘 다 같은 `shared`를 읽고 1을 더해 다시 쓴다. \
동시에 실행되면 둘 다 `0`을 읽고 둘 다 `1`을 쓰는 식으로 겹쳐서, 두 번 더했는데도 결과가 `2`가 아니라 `1`이 되는 일이 생길 수 있다.&#x20;

반면 각 스레드가 서로 다른 자기만의 변수 주소를 넘긴다면(예: 각자의 지역 변수 주소), 가리키는 대상이 전용이므로 안전하다.



이 키워드는 "스레드 전용 리소스만 사용하기"를 매개변수 상황으로 확장한 것이다. \
"전용 리소스만 쓰면 안전하다"는 규칙은 여전히 유효하되, 포인터/참조가 끼면 "겉보기엔 전용 같아도 가리키는 대상이 공유면 위험하다"는 단서를 붙여야 함을 보여준다.

> 💡 **TMI**
>
> * C에서 함수 매개변수가 스레드 전용인 이유는 인자가 호출하는 스레드의 스택에 복사되기 때문이다. 다만 이것은 "값 복사"일 때의 이야기이고, 포인터를 넘기면 가리키는 대상은 여전히 공유될 수 있어서 "값을 넘겼는가, 주소를 넘겼는가"가 안전성의 갈림길이 된다.
> * 매개변수가 스택에 올라가는지는 호출 규약(calling convention)에 따라 다르다. x86-64 System V ABI에서는 앞쪽 정수 인자 6개를 아예 레지스터(rdi, rsi 등)로 전달해 스택조차 거치지 않는데, 그래도 각 스레드의 레지스터는 분리돼 있으므로 전용성은 유지된다.

***

지금까지는 "공유를 피하는" 쪽이었다. 그런데 꼭 공유해야 하는 데이터, 즉 전역 변수는 어떻게 될까?

### 6. 전역 변수 사용

#### 1) 개념 정의

전역 변수는 모든 스레드가 함께 접근할 수 있는 대표적인 공유 리소스이므로, 여러 스레드가 보호 없이 그냥 읽고 쓰면 스레드 안전을 보장할 수 없다.

#### 2) 원리 설명

한 프로세스 안의 스레드들은 같은 메모리 공간을 공유하는데, 전역 변수는 바로 그 공유 메모리에 놓이기 때문에 모든 스레드가 동일한 변수를 동시에 건드릴 수 있다.&#x20;

문제는 우리가 코드에서 한 줄처럼 보이는 연산이 실제로는 여러 단계로 쪼개져 실행된다는 점이다. \
예를 들어 `counter++`는&#x20;

1. 메모리에서 값을 읽기
2. 1을 더하기
3. 다시 메모리에 쓰기"

라는 세 단계로 나뉜다. \
한 스레드가 이 세 단계를 끝내기 전에 다른 스레드가 중간에 끼어들면, 두 스레드가 같은 옛날 값을 읽고 각자 1을 더해 같은 값을 써버리는 일이 생긴다. \
그 결과 두 번 증가시켰는데 실제로는 한 번만 증가한 것처럼, 결과가 어긋나는 상황이 발생한다.

#### 3) 세부 메커니즘

왜 한 줄짜리 `counter++`가 위험한지를 한 단계 더 들여다보면, CPU는 메모리의 값을 직접 더하는 대신 보통 값을 자기 작업 공간으로 가져와 계산한 뒤 되돌려 놓는 방식으로 동작하기 때문이다.&#x20;

즉 "읽기"와 "쓰기"가 분리되어 있어서, 그 사이에 시간 간격이 생긴다. \
스레드는 운영체제에 의해 아무 때나 실행이 잠시 멈췄다가 다른 스레드로 전환될 수 있는데, 하필 이 읽기와 쓰기 사이에서 전환이 일어나면 두 스레드가 같은 값을 본 상태로 각자 계산하게 된다.&#x20;

그래서 이런 변수를 꼭 써야 한다면, 그 여러 단계가 "통째로 한 덩어리처럼" 끝나도록 보호해야 한다. \
가장 흔한 방법은 락(잠금)으로 다른 스레드의 진입을 막는 것이다.

#### 4) 예시

데이터 경쟁이 일어나는 코드:

```c
int counter = 0;  // 전역 변수 (공유 리소스)

void* worker(void* arg) {
    for (int i = 0; i < 100000; i++) {
        counter++;   // 읽기 -> 증가 -> 쓰기 (3단계)
    }
    return NULL;
}
```

스레드 2개가 각각 100000번씩 더하면 기대값은 200000이다. 하지만 보호가 없으면 중간에 끼어듦이 생겨 실제 결과는 매번 다르게 나오고 200000보다 작은 값(예: 137852, 158033 등)이 나온다.

락으로 보호한 안전한 버전:

```c
int counter = 0;
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void* worker(void* arg) {
    for (int i = 0; i < 100000; i++) {
        pthread_mutex_lock(&lock);
        counter++;                  // 한 덩어리로 보호됨
        pthread_mutex_unlock(&lock);
    }
    return NULL;
}
```

이렇게 하면 항상 정확히 200000이 나온다.



전역 변수는 "공유하기 때문에 위험한" 경우를 보여주며, 스레드 전용 저장소는 "아예 공유하지 않게 만들어 위험을 없애는" 정반대 접근법으로 이어진다.

> 💡 **TMI**
>
> * C 표준 라이브러리의 `errno`는 원래 평범한 전역 변수였다. 멀티스레드 시대가 오면서 한 스레드의 오류 코드를 다른 스레드가 덮어쓰는 문제가 생겼고, 그래서 오늘날 `errno`는 매크로를 통해 "스레드마다 별도의 errno"를 가리키도록 바뀌었다.
> * `counter++`가 끼어듦에 노출되는 현상을 엄밀히는 \*\*데이터 경쟁(data race)\*\*이라 한다. 이를 막는 두 축이 ①락으로 한 번에 한 스레드만 들이는 것과 ②읽기·증가·쓰기를 쪼갤 수 없는 하나로 묶는 \*\*원자적 연산(atomic operation)\*\*이다.
> * 같은 보호라도 비용이 다르다. 원자적 연산은 보통 락보다 가볍지만, x86에서는 명령어 앞에 `lock` 접두사를 붙여 버스/캐시 차원에서 원자성을 보장하므로 평범한 덧셈보다는 느리다.

***

전역 변수의 위험을 "보호"로 막는 대신, "애초에 공유하지 않게" 만드는 영리한 방법이 있다.&#x20;



### 7. 스레드 전용 저장소

#### 1) 개념 정의

스레드 전용 저장소(Thread Local Storage, TLS)는 전역 변수처럼 편하게 쓰면서도 각 스레드마다 독립된 복사본을 갖게 하여, 공유가 일어나지 않으므로(그 복사본의 주소를 다른 스레드에 넘기지 않는 한) 자동으로 스레드 안전이 되는 기법이다.

#### 2) 원리 설명

앞에서 전역 변수가 위험한 이유는 여러 스레드가 "같은 하나의" 변수를 공유하기 때문이었다. \
TLS는 발상을 뒤집어, 같은 이름의 변수를 선언하더라도 스레드마다 각자 자기만의 별도 인스턴스를 갖게 만든다.&#x20;

따라서 한 스레드가 그 변수를 바꿔도 다른 스레드의 값에는 전혀 영향을 주지 않는다. \
공유 자체가 없으니 데이터 경쟁이 생길 여지가 없고, 락이나 원자적 연산 같은 보호 장치 없이도 안전하다. \
사용하는 입장에서는 평범한 전역 변수처럼 이름만으로 접근하면 되므로 코드가 단순하다는 장점도 있다.

#### 3) 세부 메커니즘

보통의 전역 변수는 메모리에 단 하나의 자리만 잡지만, TLS로 선언한 변수는 스레드가 만들어질 때마다 그 스레드 전용으로 별도의 자리가 마련된다.&#x20;

그래서 코드에서는 변수 이름 하나만 쓰지만, 실행 중에는 "지금 실행 중인 스레드"에 맞는 복사본이 자동으로 선택되어 사용된다. \
다만 주의할 점이 둘 있다. \
첫째, 모든 스레드가 정말로 같은 값을 공유해야 하는 데이터에는 적합하지 않다(스레드마다 따로이므로). \
둘째, 5절에서 보았듯 TLS 변수의 "주소"를 다른 스레드에 건네면 그 순간 다시 공유가 되어 안전성이 깨진다.

#### 4) 예시

```c
_Thread_local int tls_counter = 0;   // 스레드마다 독립 복사본

void* worker(void* arg) {
    for (int i = 0; i < 100000; i++) {
        tls_counter++;   // 각 스레드가 자기 복사본만 건드림
    }
    // 이 스레드의 tls_counter는 정확히 100000
    return NULL;
}
```

스레드 2개가 돌아도 서로 다른 복사본을 쓰기 때문에, 각 스레드의 `tls_counter`는 락 없이도 정확히 100000이 된다. (전역 공유였다면 데이터 경쟁이 났을 상황)

대표적인 실제 예로 C 표준 라이브러리의 `errno`가 있다. 여러 스레드가 동시에 시스템 호출을 하더라도 각 스레드가 자기 `errno`를 따로 갖기 때문에, 한 스레드의 오류 코드가 다른 스레드의 오류 코드를 덮어쓰지 않는다.



"전역 변수 사용"이 공유로 인한 위험을 락/원자적 연산으로 막는 방법이었다면, TLS는 공유 자체를 없애 같은 문제를 보호 장치 없이 해결하는 보완적 선택지로 이어진다.

> 💡 **TMI**
>
> * TLS는 마법이 아니라 CPU 레지스터에 기대어 구현된다. x86-64 리눅스에서는 FS 세그먼트 레지스터가, 윈도우에서는 GS 레지스터가 각 스레드의 전용 데이터 블록을 가리키도록 설정돼 있어서, 같은 변수 이름이 스레드마다 다른 메모리를 가리킨다.
> * TLS 변수를 선언하는 키워드는 언어·컴파일러마다 다르다. GCC 확장은 `__thread`, C11 표준은 `_Thread_local`, C++11은 `thread_local`, MSVC는 `__declspec(thread)`를 쓰는데, 모두 같은 목적의 서로 다른 방언인 셈이다.
> * 키워드 기반 TLS 이전에는 POSIX의 `pthread_key_create`/`pthread_getspecific` 같은 런타임 API로 스레드 전용 저장소를 만들었다. 컴파일러가 직접 지원하는 `__thread` 방식이 훨씬 빠르지만, 동적으로 키를 만들고 소멸자를 등록하는 유연함은 API 방식이 더 크다.

***

변수뿐 아니라 함수가 "결과를 돌려주는 방식"에도 같은 공유 함정이 숨어 있다.

### 8. 함수 반환값

#### 1) 개념 정의

함수가 결과를 어디에 담아 돌려주느냐에 따라 스레드 안전 여부가 갈리는데, 정적/전역 버퍼에 담아 그 포인터를 반환하면 안전하지 않고, 호출자가 건넨 버퍼에 채워주면 안전하다.

#### 2) 원리 설명

어떤 함수는 결과 문자열 같은 데이터를 만들어 돌려줘야 하는데, 그 데이터를 함수 내부에 마련해 둔 정적(static) 버퍼나 전역 버퍼에 써넣고 그 주소(포인터)만 반환하는 방식이 있다. \
이 버퍼는 함수 호출이 끝나도 사라지지 않고 모든 스레드가 같은 하나를 공유하기 때문에, 두 스레드가 거의 동시에 그 함수를 호출하면 한쪽이 쓴 결과를 다른 쪽이 덮어써 버린다.&#x20;

그래서 호출자는 자기가 받은 줄 알았던 결과가 엉뚱한 값으로 바뀌는 일을 겪는다. \
반대로, 결과를 둘 자리(버퍼)를 호출자가 직접 마련해서 함수에 넘겨주고 함수는 거기에만 결과를 채우면, 스레드마다 각자의 버퍼를 쓰므로 서로 간섭하지 않는다. \
이 때문에 표준 라이브러리는 같은 기능을 두 버전으로 제공하기도 한다.

#### 3) 세부 메커니즘

핵심은 "결과를 담는 공간의 소유권이 누구에게 있느냐"다. \
정적/전역 버퍼 방식은 그 공간이 함수에 단 하나뿐이라 사실상 모든 스레드가 공유하는 자원이 되고, 그래서 동시에 접근하면 충돌이 난다. \
이를 해결한 안전 버전은 함수 이름 뒤에 `_r`을 붙이는 관례를 쓰는데(예: `strtok_r`, `gmtime_r`), 이들은 결과를 담을 버퍼를 매개변수로 추가로 받아 그 안에만 쓴다. 즉 공유되던 자원을 호출자 쪽의 지역 변수로 옮겨 각 스레드가 독립된 공간을 갖게 만든 것이 안전성의 비결이다.

#### 4) 예시

안전하지 않은 옛 `strtok` (내부 정적 상태를 공유):

```c
char str1[] = "a,b,c";
char str2[] = "x,y,z";

// 스레드 A
char *t = strtok(str1, ",");   // 내부 정적 포인터가 str1을 가리킴
// (여기서 스레드 B가 끼어들면)

// 스레드 B
char *u = strtok(str2, ",");   // 내부 정적 포인터가 str2로 덮어써짐

// 스레드 A가 다시 strtok(NULL, ",") 호출 -> str1이 아니라 str2를 이어서 처리
// => 결과가 뒤섞임
```

안전한 `strtok_r` (상태를 호출자 변수에 보관):

```c
char str1[] = "a,b,c";
char *saveptr1;                       // 스레드 A 전용 지역 변수
char *t = strtok_r(str1, ",", &saveptr1);
while (t != NULL) {
    // t -> "a", "b", "c" 순서대로
    t = strtok_r(NULL, ",", &saveptr1);
}
// 스레드 B는 자신만의 saveptr2를 쓰므로 서로 간섭 없음
```

`gmtime`(정적 `struct tm` 반환) 대 `gmtime_r`(호출자가 준 `struct tm`에 채움)도 같은 구조다.



이 `_r` 버전들은 키워드 9 "스레드 안전이 아닌 코드 호출하기"에서 제시하는 해결책(안전한 대체 함수로 교체)의 구체적 도구이며, 키워드 10의&#x20;

①공유 자원 안 쓰기·

②전용화 원칙이 함수 인터페이스 수준에서 적용된 사례다.

> 💡 **TMI**
>
> * 함수가 내부 정적 버퍼의 주소를 반환하면 멀티스레드에서 위험해진다. 과거 `ctime`이나 `inet_ntoa` 같은 함수가 바로 이 패턴 때문에 안전하지 않았다.
> * 함수 이름 끝의 `_r`은 "reentrant(재진입 가능)"의 약자이며, POSIX가 스레드 안전 버전을 만들며 정착시킨 명명 관례다(`localtime_r`, `rand_r`, `gmtime_r` 등). 다만 엄밀히는 "재진입 가능"과 "스레드 안전"은 서로 다른 개념이라, `_r`을 곧 thread-safe와 동의어로 외우면 미세한 오개념이 생길 수 있다.
> * 이 문제의 해법이 언어마다 갈린다. C는 "호출자가 버퍼를 넘겨라(`_r` 버전)"는 방식을 택했고, 가비지 컬렉션이 있는 언어들은 매번 새 객체를 힙에 할당해 반환함으로써 같은 문제를 자동으로 회피한다.

***

내 코드가 직접 공유 자원을 안 써도, 내가 부르는 함수가 위험하면 어떻게 될까?

### 9. 스레드 안전이 아닌 코드 호출하기

#### 1) 개념 정의

내가 만든 함수가 그 자체로는 멀쩡해 보여도, 내부에서 스레드 안전하지 않은 함수를 호출하면 내 함수도 똑같이 안전하지 않게 된다.

#### 2) 원리 설명

스레드 안전성은 함수가 사용하는 모든 부품으로 전파된다. \
내 함수 코드에 공유 변수가 하나도 없더라도, 내부에서 호출하는 하위 함수가 정적/전역 버퍼 같은 공유 자원을 건드린다면 그 위험은 그대로 내 함수의 위험이 된다. \
마치 안전한 재료만 쓴 줄 알았는데 그중 하나가 오염돼 있으면 요리 전체가 오염되는 것과 같다.&#x20;

그래서 함수 하나를 "안전하다"고 판단하려면 그 함수가 부르는 함수들까지 따라가 확인해야 한다. \
해결책은 크게 두 가지다.

#### 3) 세부 메커니즘

두 해결책의 차이를 이해하는 것이 핵심이다.&#x20;

1. 첫째, 안전한 대체 버전으로 바꾸기: 호출하던 불안전 함수에 `_r` 같은 안전 버전이 있으면 그것으로 교체한다(예: `strtok` → `strtok_r`). 이 방법은 애초에 공유 자원을 없애므로 가장 깔끔하다.&#x20;
2. 둘째, 락으로 감싸기: 마땅한 대체 버전이 없으면, 그 불안전 함수를 호출하는 구간 전체를 뮤텍스로 잠가서 한 번에 한 스레드만 들어가게 만든다. \
   이 방법은 어떤 함수든 적용할 수 있지만, 잠그는 동안 다른 스레드가 기다려야 하므로 동시 처리 성능이 떨어진다는 비용이 따른다.

#### 4) 예시

불안전 함수를 그대로 호출해 내 함수도 불안전해진 경우:

```c
// gmtime은 내부 정적 struct tm을 반환(공유) -> 불안전
char *my_now(void) {
    time_t t = time(NULL);
    struct tm *p = gmtime(&t);   // 공유 버퍼를 가리키는 포인터
    static char buf[64];         // 게다가 여기도 정적 버퍼 -> 이중으로 불안전
    strftime(buf, sizeof buf, "%Y-%m-%d", p);
    return buf;
}
```

해결책 1 — 안전한 `_r` 버전으로 교체:

```c
void my_now_r(char *out, size_t n) {  // 결과 버퍼는 호출자가 제공
    time_t t = time(NULL);
    struct tm tmbuf;                  // 지역 변수
    gmtime_r(&t, &tmbuf);             // 호출자 버퍼에 채움 -> 안전
    strftime(out, n, "%Y-%m-%d", &tmbuf);
}
```

해결책 2 — 대체 버전이 없을 때 락으로 감싸기:

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void my_now_locked(char *out, size_t n) {
    time_t t = time(NULL);
    pthread_mutex_lock(&lock);
    struct tm *p = gmtime(&t);        // 불안전 함수지만
    strftime(out, n, "%Y-%m-%d", p);  // 락 안에서만 사용
    pthread_mutex_unlock(&lock);      // 한 번에 한 스레드만 진입
}
```



이 키워드는 키워드 8의 `_r` 버전을 "해결책 1"로 직접 활용하며, 동시에 "호출하는 하위 함수도 안전한지 확인하라"를 구체화한 것이다. 락으로 감싸는 해결책 2는 동기화 원칙의 적용이다.

> 💡 **TMI**
>
> * 안전하지 않은 함수를 락으로 감싸는 방식은 흔하지만 대가가 크다. 락 경합이 심하면 스레드들이 서로 기다리며 줄을 서고, 컨텍스트 스위칭 비용까지 더해져 코어를 늘려도 성능이 오히려 떨어지는 역설이 생긴다.
> * 안전하지 않은 라이브러리를 통째로 락으로 감싸는 것을 "거대 락(giant lock)" 패턴이라 부른다. 파이썬과 루비의 "전역 인터프리터 락(GIL)"이 대표적인데, 구현은 단순하지만 진정한 병렬 실행을 막는 병목이 되어 오랫동안 논쟁거리였다.

***

지금까지의 모든 기법을 한곳에 모아, "그래서 어떻게 만드느냐"로 마무리한다.

### 10. 스레드 안전 코드는 어떻게 구현할까?

#### 1) 개념 정의

스레드 안전 코드를 만드는 길은 결국 "공유 자원을 쓰지 않거나, 어쩔 수 없이 공유한다면 반드시 보호하는 것"으로 요약되며, 이를 위한 다섯 가지 실천 방법이 있다.

#### 2) 원리 설명

스레드 문제의 뿌리는 여러 스레드가 같은 자원을 동시에 읽고 쓰는 데 있으므로, 안전성을 확보하는 전략은 그 뿌리를 차단하는 순서로 정리된다.&#x20;

1. 가장 좋은 것은 애초에 공유할 자원을 만들지 않는 것이고(①지역 변수만 쓰기),&#x20;
2. 그래도 데이터를 유지해야 하면 스레드마다 따로 갖게 하거나(②스레드 전용 저장소),&#x20;
3. 아무도 바꾸지 못하게 읽기 전용으로 굳히는 방법(③불변)이 있다.&#x20;
4. 이 모든 회피가 불가능해 진짜로 공유해야 한다면 그때 비로소 자물쇠(④뮤텍스/원자적 연산)로 보호한다.&#x20;
5. 마지막으로, 내 코드가 부르는 하위 함수까지 안전한지 확인해야 전체가 안전해진다(⑤).&#x20;

즉 "공유를 피하라, 피할 수 없으면 보호하라"가 일관된 원칙이다.

#### 3) 세부 메커니즘

다섯 방법은 비용과 우선순위가 다르다는 점이 핵심이다. \
①\~③은 공유 자체를 없애므로 락이 필요 없고 성능 손실도 거의 없다 — 그래서 먼저 시도해야 한다. \
특히 ②스레드 전용 저장소는 전역처럼 보이지만 스레드마다 별도 복사본을 갖게 하는 방식이라 공유의 외형을 유지하면서 충돌을 없앤다. \
③불변(읽기 전용)은 아무도 쓰지 않으면 동시에 읽기만 하는 것은 안전하다는 사실을 이용한다. \
반면 ④동기화는 만능이지만, 잠금 구간에서 스레드들이 줄 서서 기다리므로 동시성을 깎아먹는다 — 그래서 마지막 수단이다. \
⑤는 앞의 네 가지를 내 코드에만 적용해서는 부족하고, 호출 사슬 전체로 확장해야 한다는 점을 일깨운다(키워드 9의 내용).

#### 4) 예시

①공유 자원 안 쓰기(지역 변수만):

```c
int add(int a, int b) {
    int sum = a + b;   // 스레드마다 스택에 독립 생성 -> 항상 안전
    return sum;
}
```

④어쩔 수 없이 공유하면 뮤텍스로 보호:

```c
long counter = 0;                              // 공유 전역
pthread_mutex_t m = PTHREAD_MUTEX_INITIALIZER;

void inc(void) {
    pthread_mutex_lock(&m);
    counter++;            // 한 번에 한 스레드만 수정
    pthread_mutex_unlock(&m);
}
// 락이 없으면 두 스레드가 동시에 counter++ 하다가
// 증가분이 사라져 최종값이 기대보다 작아질 수 있음
```



이 키워드는 챕터의 종합 정리로서, 키워드 8(반환값을 호출자 버퍼에 채우는 `_r` 설계)은 ①②의 실현, 키워드 9(불안전 함수 호출 처리)는 ④와 ⑤의 적용 사례에 해당한다.

> 💡 **TMI**
>
> * 락 없이 안전성을 얻는 "락-프리(lock-free)" 기법의 핵심에는 CAS(compare-and-swap)라는 원자적 연산이 있다. CPU가 "값이 예상과 같으면 바꾼다"를 한 번에 처리해 주는데, x86에서는 명령어 앞에 `lock` 접두사를 붙여 이 원자성을 보장한다.
> * 락-프리에는 "ABA 문제"라는 유명한 함정이 있다. 값이 A에서 B로 갔다가 다시 A로 돌아오면 CAS는 "아무 일도 없었다"고 착각하는데, 이를 막으려고 버전 카운터를 덧붙이는 등의 우회책이 동원된다.
> * 리눅스의 뮤텍스는 사실 대부분의 경우 시스템 콜조차 하지 않는다. `futex`(fast userspace mutex) 덕분에 경합이 없을 때는 사용자 공간에서 원자적 연산만으로 락을 처리하고, 정말 기다려야 할 때만 커널에 진입하는데, 이 설계가 락의 평균 비용을 크게 낮췄다.

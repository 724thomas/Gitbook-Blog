# 2.8. server with high concurrency and performance

### 1. C10K 문제

#### 1) 개념 정의

한 대의 서버가 동시에 1만 개(Concurrent 10,000)의 클라이언트 연결을 처리하려 할 때, 연결 하나에 프로세스나 스레드를 하나씩 붙이는 전통적 방식이 자원 한계에 부딪혀 무너지는 현상이다.

#### 2) 원리 설명

초창기 서버는 새 연결이 들어올 때마다 그 연결을 전담할 프로세스나 스레드를 하나씩 만들어 붙이는 단순한 방식을 썼다. 이 방식은 연결 수가 수십\~수백 개일 때는 직관적이고 잘 동작하지만, 연결 수가 1만 개로 늘어나면 만들어야 할 실행 단위도 1만 개가 된다. 문제의 핵심은 연결 하나하나가 **동시에 살아 있는(concurrent)** 연결이라는 점이다. 즉 1만 개가 순서대로 들어왔다 나가는 게 아니라 동시에 자원을 점유한 채 머무르므로, 연결 수에 비례해 메모리·CPU·커널 자원이 같이 불어난다. 그 결과 어느 지점을 넘어서면 서버는 실제 요청을 처리하는 일보다 1만 개의 실행 단위를 관리하는 일(메모리 유지, 스케줄링)에 더 많은 자원을 쓰게 되어, 성능이 완만히 떨어지는 게 아니라 급격히 붕괴한다.

#### 3) 세부 메커니즘

연결당 비용은 크게 세 갈래에서 발생한다.

* **스레드 스택 메모리**: 스레드(또는 프로세스)는 저마다 독립된 스택 공간을 잡는다. 이 크기는 보통 수 MB 수준이고(예: 스레드 1개당 약 1MB), 1만 개가 동시에 살아 있으면 스택만으로도 GB 단위의 메모리가 묶인다.
* **문맥 교환(context switch) 오버헤드**: CPU 코어 하나는 한 번에 하나의 실행 단위만 돌릴 수 있어, 운영체제 스케줄러가 1만 개를 코어 수에 나눠 번갈아 가며 전환해야 한다. 스레드 수가 늘수록 CPU가 실제 작업이 아니라 "전환 자체"에 점점 더 많은 시간을 쏟게 되고, 결국 요청 처리보다 전환에 더 많은 시간을 쓰는 지점에 도달한다.
* **커널 자원 한계**: 연결마다 파일 디스크립터(소켓)를 하나씩 차지한다. 운영체제는 프로세스가 열 수 있는 파일 디스크립터 수에 상한을 두고(흔히 기본값이 1,024 수준), 시스템 전체가 열 수 있는 수에도 별도 상한을 두는데, 이 한계에 먼저 걸리면 CPU·메모리가 남아 있어도 새 연결이 거부된다.

#### 4) 예시

**예시 1 — 메모리 산술**: 스레드 1개가 약 1MB의 스택을 쓴다고 보면, 1만 개의 동시 연결은

```
10,000개 × 1MB = 약 10,000MB ≈ 10GB
```

즉 실제 요청 데이터를 담기도 전에, 단지 1만 개의 실행 단위를 "유지"하는 데만 약 10GB의 메모리가 기본으로 필요하다. 연결당 스택이 더 큰 환경이라면 이 숫자는 곧바로 수십 GB로 늘어난다.

**예시 2 — 파일 디스크립터 벽**: 연결당 소켓 하나를 쓰므로 1만 연결에는 최소 1만 개의 파일 디스크립터가 필요하다. 그런데 프로세스당 디스크립터 상한이 1,024로 설정돼 있으면, 1,025번째 연결부터는 CPU·메모리 여유와 무관하게 운영체제 단계에서 거부된다. (구체 기본값은 운영체제·버전마다 다르므로 환경별 확인 필요)

#### 5) 다른 키워드와의 연결

C10K 문제는 "왜 연결마다 프로세스/스레드를 붙이는 순진한 방식으로는 안 되는가"라는 **동기**를 제시하는 출발점이다. 이 한계를 넘기 위해 등장한 구체적 처리 방식들 — 다중 프로세스/스레드, 이벤트 순환과 입출력 다중화, 비동기·콜백, 코루틴 등 — 은 모두 이 문제를 풀기 위한 서로 다른 답이며, 각각의 동작 원리는 해당 소주제에서 다룬다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **댄 케겔의 웹페이지(1999)** — 'C10K'라는 용어는 학술 논문이 아니라 1999년 댄 케겔(Dan Kegel)이 올린 개인 웹페이지 제목에서 나왔다. 그는 "이제 웹 서버가 1만 클라이언트쯤은 동시에 처리해야 하지 않겠나"라며 당시 운영체제별 해법을 정리했고, 이 문서를 10년 가까이 갱신하며 '살아 있는 문서'로 유지했다. 핵심 주장은 1990년대 말 하드웨어는 이미 1만 접속을 감당할 수 있고, 발목을 잡는 것은 소프트웨어 구조라는 것이었다.
> * **C10K를 풀려고 태어난 Nginx** — Nginx는 처음부터 C10K 문제를 풀겠다는 목표로 태어난 서버다. 러시아 포털 람블러(Rambler)에서 일하던 이고르 시소예프가 2002년 개발을 시작해 2004년 공개했고, 훗날 아파치를 제치고 웹 서버 점유율 1위에 오르기도 했다.
> * **왓츠앱의 200만, 그리고 C10M** — 왓츠앱은 2011년 FreeBSD와 Erlang 조합으로 단일 서버 100만 동시 접속을 달성한 뒤, 이듬해 초 ["1 million is so 2011"](https://blog.whatsapp.com/1-million-is-so-2011)이라는 블로그 글로 서버 1대당 200만 접속 달성을 발표했다. 2013년에는 보안 연구자 로버트 그레이엄이 한 단계 위의 'C10M(1천만 동시 접속)' 문제를 제창하며 바통을 이어받았다.

### 2. 다중 프로세스

#### 1) 개념 정의

들어오는 연결을 각각 독립된 주소 공간을 가진 별개의 프로세스에 맡겨 동시에 여러 클라이언트를 처리하는 방식이다.

#### 2) 원리 설명

서버는 부모 프로세스 하나가 연결 요청을 받아들이는(`accept`) 역할을 맡고, 새 연결이 들어올 때마다 그 연결을 처리할 자식 프로세스를 만들어 떠넘긴다. 이렇게 하면 자식 프로세스 안에서는 한 번에 하나의 연결만 신경 쓰면 되므로, 데이터를 기다리는 동안 그냥 멈춰 서 있는(블로킹) 단순한 코드를 위에서 아래로 순차적으로 작성할 수 있다. 한 연결의 일은 한 프로세스가 전담하므로, 어떤 연결을 처리하던 프로세스가 잘못되어 죽더라도 다른 연결을 처리하는 프로세스에는 영향이 가지 않는다. 즉 이 모델의 핵심 매력은 "한 연결 = 한 프로세스"라는 단순한 대응 관계가 주는 프로그래밍의 직관성과 격리에서 오는 안정성이다. 대신 프로세스는 무거운 단위라서, 연결 수가 늘어나면 메모리 사용량과 프로세스 생성 비용이 그만큼 함께 늘어나는 대가를 치른다.

#### 3) 세부 메커니즘

* **fork와 부모-자식 프로세스**: 유닉스 계열에서 자식 프로세스는 `fork()` 시스템 호출로 생성된다. `fork()`는 현재 프로세스를 복제해, 호출한 쪽(부모)과 복제된 쪽(자식)이 같은 지점에서 갈라져 나란히 실행된다. 코드에서는 `fork()`의 반환값으로 둘을 구분한다 — 반환값이 0이면 자식, 0보다 크면 부모다.
* **독립된 주소 공간**: 두 프로세스는 각각 별도의 가상 메모리 공간을 가진다. 같은 변수가 같은 주소처럼 보여도, 한쪽에서 그 메모리를 바꿔도 다른 쪽에는 반영되지 않는다. 메모리를 공유하지 않기 때문에 요청들이 자연스럽게 서로 격리된다.
* **파일 디스크립터의 복사**: 자식은 부모가 가지고 있던 파일 디스크립터(소켓 포함)의 복사본을 물려받는다. 그래서 부모가 `accept`로 얻은 연결 소켓을 자식이 그대로 이어받아 통신할 수 있다. 다만 같은 연결을 부모·자식이 둘 다 쥐고 있으면 안 되므로, 자식은 듣기용(listen) 소켓을 닫고, 부모는 방금 넘긴 연결 소켓을 닫아 역할을 분리한다.
* **프로세스 간 통신(IPC)의 비용**: 주소 공간이 분리되어 있다는 것은, 프로세스끼리 데이터를 주고받으려면 별도의 통신 수단(파이프, 소켓 등)을 거쳐야 한다는 뜻이다. 이런 IPC는 같은 메모리를 그냥 읽는 것보다 비용이 들고, 프로세스를 새로 만드는 일 자체도 무겁다.
* **좀비 정리**: 자식이 일을 마치고 종료하면 부모가 `wait()`/`waitpid()`로 그 종료 상태를 거둬가야 한다. 그렇지 않으면 종료됐지만 정리되지 않은 "좀비" 프로세스가 남는다.

#### 4) 예시

**(1) 연결마다 fork하는 서버 (process-per-connection)** — 부모가 연결을 받을 때마다 자식을 만들어 떠넘기는 가장 기본적인 형태다.

```c
listen(server_sock, ...);              // 듣기 소켓 준비

while (1) {
    conn = accept(server_sock, ...);   // 부모: 새 연결 대기
    pid = fork();                      // 연결마다 프로세스 복제

    if (pid == 0) {                    // ── 자식 프로세스 ──
        close(server_sock);            //   듣기 소켓은 자식에 불필요
        // conn으로 recv/send 반복 (예: 에코)
        close(conn);
        exit(0);                       //   연결 끝나면 종료
    } else {                           // ── 부모 프로세스 ──
        close(conn);                   //   넘긴 연결 소켓은 부모가 닫음
        // 곧바로 다음 accept로 돌아가 다른 클라이언트 대기
    }
}
```

작동 결과: 클라이언트 3개가 동시에 붙으면 그 연결을 담당하는 자식 프로세스가 3개 생기고, 각 프로세스는 자기 클라이언트의 데이터만 읽고 쓸 수 있다. 한 자식이 처리 중 비정상 종료해도 나머지 두 연결은 멀쩡히 유지된다.

**(2) 미리 만들어 두는 prefork 모델** — 연결이 올 때마다 프로세스를 만드는 비용을 줄이기 위해, 시작 시점에 자식 프로세스 여러 개를 미리 만들어 풀로 대기시키는 방식이다. 요청이 오면 이미 떠 있는 유휴 프로세스가 곧바로 처리하므로, 클라이언트가 새 프로세스 생성이 끝나기를 기다릴 필요가 없다.

#### 5) 다른 키워드와의 연결

다중 프로세스 모델은 한 연결당 무거운 프로세스를 띄우는 탓에 동시 연결 수가 메모리에 가로막히는데, 이 한계를 정면으로 제기하는 것이 같은 절의 **C10K 문제**다. 또한 "더 가벼운 실행 단위로 같은 일을 하되 메모리를 공유한다면?"이라는 대안이 바로 짝을 이루는 **다중 스레드**로 이어진다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **PostgreSQL은 여전히 접속당 프로세스** — PostgreSQL은 지금도 클라이언트 접속 1개당 백엔드 프로세스 1개를 띄우는 전통적인 다중 프로세스 모델을 유지하고 있다. 그래서 대규모 서비스에서는 접속 수를 줄여 주는 PgBouncer 같은 커넥션 풀러를 앞단에 두는 것이 사실상 표준 구성이 됐다.
> * **Redis의 fork 스냅숏** — '단일 스레드'로 유명한 Redis도 RDB 스냅숏을 만들 때는 fork()로 자식 프로세스를 생성한다. 운영체제의 copy-on-write 덕분에 수 GB 데이터도 그 순간에는 거의 비용 없이 복제되지만, 스냅숏 도중 쓰기가 폭주하면 메모리 사용량이 최대 2배 가까이 불어날 수 있어 운영자들이 주의하는 포인트다.
> * **크롬의 탭 = 프로세스** — 구글은 2008년 크롬 출시 때 만화가 스콧 매클라우드가 그린 만화책으로 '탭마다 프로세스를 분리한' 설계를 홍보했다. 탭 하나가 죽어도 브라우저 전체는 살아남는다는 논리인데, 이는 서버의 다중 프로세스 모델이 주는 격리(isolation) 장점과 정확히 같은 원리다.

### 3. 다중 스레드

#### 1) 개념 정의

하나의 프로세스 안에서 여러 개의 실행 흐름(스레드)을 만들어, 클라이언트 연결마다 또는 작업마다 스레드를 배정해 동시에 처리하는 서버 구현 방식이다.

#### 2) 원리 설명

다중 프로세스 방식과 달리, 스레드들은 같은 프로세스 안에서 코드·데이터·힙 영역과 운영체제 자원을 공유하고 각자 자신의 호출 스택과 레지스터만 따로 갖는다. 공유하는 자원이 많기 때문에 새 스레드를 만들거나 스레드 사이를 전환하는 비용이 프로세스보다 훨씬 가볍다. 문맥 교환 시 프로세스 간 전환은 가상 메모리 공간(주소 공간) 자체를 바꿔야 하지만, 같은 프로세스 안의 스레드 간 전환은 메모리 공간을 그대로 두고 스택과 레지스터만 교체하면 되므로 더 빠르다. 그래서 서버는 연결이 들어올 때마다 가벼운 스레드를 하나 붙여 여러 요청을 병행해서 처리할 수 있다. 다만 여러 스레드가 같은 메모리를 공유하기 때문에, 동시에 같은 데이터를 건드릴 때 생기는 충돌을 막기 위한 별도의 장치가 필요해진다.

#### 3) 세부 메커니즘

* **자원 공유 방식**: 한 프로세스 안의 스레드들은 데이터 영역과 힙 영역을 공유한다. 즉 같은 전역 변수와 같은 동적 할당 메모리에 모든 스레드가 접근할 수 있어, 스레드 사이의 데이터 교환이 매우 효율적이다.
* **스레드별 스택**: 공유하는 영역과 별개로, 각 스레드는 함수 호출 정보와 지역 변수를 담는 자신만의 호출 스택과 레지스터 상태(프로그램 카운터 포함)를 따로 갖는다. 이 스택이 스레드마다 독립적이어야 각 실행 흐름이 자기 함수 호출을 따로 진행할 수 있다.
* **락/동기화가 필요한 이유**: 힙·데이터를 공유한다는 바로 그 장점이 문제의 원인이 된다. 여러 스레드가 같은 공유 데이터를 동시에 읽고 쓰면 경쟁 상태(race condition)가 발생해 결과를 예측할 수 없게 된다. 예컨대 한 스레드가 잔고를 확인한 뒤 출금하기 직전에 다른 스레드가 끼어들면 잔고가 음수가 되는 식이다. 이를 막으려면 한 스레드가 작업 중인 동안 다른 스레드가 간섭하지 못하게 막는 동기화(뮤텍스·세마포어 같은 잠금)가 필요하다.
* **스레드 풀로 생성 비용 줄이기**: 스레드 생성·종료 비용도 무시할 수 없다. 그래서 요청마다 새로 만들고 없애기를 반복하는 대신, 미리 일정 개수의 스레드를 만들어 풀(pool)에 담아 두고 요청이 오면 놀고 있는 스레드를 꺼내 배정한 뒤 작업이 끝나면 풀로 돌려보내 재사용한다. 이렇게 하면 생성·종료 비용이 사라지고, 동시에 만들 수 있는 스레드의 최대치를 제한해 과부하로 서버가 무너지는 것을 막을 수 있다.

#### 4) 예시

**예시 1 — 연결마다 스레드 생성(thread-per-connection) 의사코드**

```
while (true) {
    client = accept(server_socket)        // 새 연결 수락(대기)
    create_thread(handle_client, client)  // 연결마다 스레드 하나 생성
}

function handle_client(client) {
    request = read(client)    // 이 스레드 안에서 요청 읽고
    response = process(request)
    write(client, response)   // 응답 보내는 동안 다른 스레드는 자기 일을 함
    close(client)
}
```

연결 100개가 동시에 들어오면 스레드 100개가 만들어져 병렬로 요청을 처리한다. 단일 스레드였다면 느린 요청 하나가 뒤따르는 요청들을 모두 막아 버리지만, 스레드를 나누면 그 막힘이 사라진다.

**예시 2 — 스레드 풀에서 작업을 꺼내 처리**

```
pool = create_thread_pool(size = 200)   // 미리 200개 생성(예: 일부 서버 기본값)

while (true) {
    client = accept(server_socket)
    pool.submit(handle_client, client)  // 새로 만들지 않고 풀에 작업만 제출
}
// 풀 안의 유휴 스레드가 작업을 꺼내 처리하고, 끝나면 풀로 복귀해 재사용
// 200개가 모두 사용 중이면 새 요청은 대기열에 쌓이거나 거절됨
```

작동 결과: 스레드를 매번 새로 만들지 않으므로 응답이 빨라지고, 최대 스레드 수가 고정되어 요청이 폭주해도 기존 작업을 안정적으로 마칠 수 있다.

**한계**: 스레드가 가볍다고 해도 연결 1만 개 규모에서는 부담이 된다. 스레드마다 독립된 스택 메모리가 필요하고(흔한 기본값이 스레드당 수 MB 수준), 스레드 수가 많아질수록 CPU가 실제 일을 하기보다 스레드 사이를 전환(문맥 교환)하는 데 시간을 점점 더 많이 쓰게 된다. 결국 동시에 진짜로 처리할 수 있는 작업 수는 CPU 코어 수에 묶여 있다.

#### 5) 다른 키워드와의 연결

이 한계, 곧 연결 1만 개에서 스택 메모리와 문맥 교환 부담으로 무너지는 상황이 바로 **C10K 문제**가 가리키는 지점이다. 또한 다중 스레드는 주소 공간을 격리하는 **다중 프로세스**와 짝을 이루며(공유 대 격리), 스레드를 미리 만들어 두는 풀 개념은 이후 **이벤트 순환과 다중 스레드**에서 이벤트 루프와 결합되는 형태로 다시 등장한다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **10만 스레드: 15분 → 2초** — 리눅스 스레드 구현이 LinuxThreads에서 NPTL로 교체되던 2003년경, IA-32 머신에서 스레드 10만 개를 생성하는 벤치마크에 NPTL은 약 2초, 구형 구현은 약 15분이 걸렸다. 울리히 드레퍼와 잉고 몰나르가 만든 NPTL이 커널 2.6에 들어가면서 '스레드를 대량으로 써도 되는' 시대가 비로소 열린 셈이다.
> * **"스레드는 악이다"** — SQLite 공식 FAQ에는 "Threads are evil. Avoid them.(스레드는 악이다. 피하라)"라는 문장이 실제로 적혀 있다. 멀티스레드 버그의 악명 높은 디버깅 난이도에 데인 시스템 프로그래머들의 정서를 압축한 유명한 문구다.
> * **그린 스레드의 25년 만의 귀환** — 초기 자바(JDK 1.1)는 커널 스레드가 아니라 JVM이 직접 스케줄링하는 '그린 스레드'를 썼는데, 이 이름은 자바를 탄생시킨 썬의 '그린 프로젝트' 팀에서 따온 것이다. 이후 성능 문제로 네이티브 스레드로 전환했다가, 2023년 Java 21의 가상 스레드(Project Loom)로 약 25년 만에 다시 유저 레벨 스레드로 회귀했다.

### 4. 이벤트 순환과 이벤트 구동

#### 1) 개념 정의

\*\*이벤트 구동(event-driven)\*\*은 "무슨 일이 생기면 그에 반응한다"는 프로그래밍 발상이고, \*\*이벤트 순환(event loop)\*\*은 그 반응을 끊임없이 돌려 주는 무한 루프 형태의 엔진이다.

#### 2) 원리 설명

서버가 할 일은 결국 "누가 접속했다", "데이터가 도착했다" 같은 \*사건(이벤트)\*이 생겼을 때 그에 맞는 처리를 해 주는 것이다. 이벤트 구동 방식은 코드를 위에서 아래로 쭉 실행해 버리는 대신, "어떤 이벤트가 오면 어떤 처리를 한다"는 대응 관계만 미리 등록해 두고 기다린다. 이 기다림과 반응을 실제로 굴려 주는 것이 이벤트 루프인데, 평소에는 입력이나 신호를 계속 기다리고 있다가 사건이 발생하면 그에 해당하는 처리로 넘긴다. 핵심은 \*바쁜 폴링(busy polling)\*처럼 "아직 일 생겼나?"를 쉴 새 없이 되묻지도 않고, _연결마다 스레드 하&#xB098;_&#xB97C; 붙여 각 스레드가 자기 일이 오기만 멍하니 막혀(block) 있지도 않으면서, 단 하나의 루프가 "사건이 생길 때만 깨어나" 일을 처리한다는 데 있다.

#### 3) 세부 메커니즘

이벤트 루프의 한 바퀴(사이클)는 아주 단순한 두 동작의 반복이다. **(1) 이벤트를 하나 꺼낸다(get) → (2) 그 이벤트에 맞는 처리로 보낸다(dispatch/handle).** 처리가 끝나면 다시 루프의 처음으로 돌아가 다음 이벤트를 꺼낸다. 여기서 "꺼내기"는 보통 _이벤트가 하나라도 생길 때까지 막혀 있는(blocking)_ 동작이다. 그래서 할 일이 없을 때는 CPU를 태우지 않고 잠들어 있다가, 사건이 생기는 순간에만 깨어난다. 단일 스레드 하나만으로도 여러 일을 동시에 다루는 것처럼 보이는 이유가 바로 이 구조에 있다. 스레드를 여러 개 돌려 진짜로 _병&#xB82C;_&#xB85C; 처리하는 게 아니라, 한 스레드가 "들어온 사건들을 빠르게 번갈아 가며" 차례차례 처리하기 때문이다. 한 번에 하나의 이벤트만 끝까지 처리하고 다음으로 넘어가므로, 여러 스레드가 같은 데이터를 동시에 건드려 생기는 충돌 같은 문제도 자연스럽게 줄어든다.

#### 4) 예시

가장 기본이 되는 이벤트 루프의 골격은 다음과 같은 의사코드로 표현된다.

```c
while (true) {                 // 무한 루프: 서버가 사는 동안 계속 돈다
    event = getEvent();        // (1) 이벤트를 하나 꺼낸다 (없으면 생길 때까지 대기)
    handle(event);             // (2) 그 이벤트에 맞는 처리로 보낸다
}
```

한 바퀴가 도는 모습을 따라가 보면 이렇다.

* 루프가 `getEvent()`에서 **잠들어 대기**한다. 아직 아무 사건도 없으므로 CPU는 거의 놀고 있다.
* 클라이언트 A가 데이터를 보내 "A에 읽을 데이터 도착"이라는 이벤트가 생긴다. `getEvent()`가 **깨어나** 이 이벤트를 돌려준다.
* `handle(event)`가 A의 데이터를 읽어 처리한다. 처리가 끝나면 루프의 처음으로 **되돌아간다**.
* 다시 `getEvent()`에서 대기. 이번엔 거의 동시에 B의 접속과 C의 데이터가 쌓여 있다면, 루프는 이들을 한 바퀴에 하나씩 **번갈아** 꺼내 처리한다.

결과적으로, 스레드는 하나뿐이지만 A·B·C의 요청이 서로 막히지 않고 차례로 빠르게 처리되어, 마치 여러 일이 함께 굴러가는 것처럼 보인다. 조금 더 현실에 가까운 형태에서는, 꺼낸 이벤트의 _종&#xB958;_&#xC5D0; 따라 서로 다른 처리(핸들러)로 나누어 보내기도 한다.

```c
while (true) {
    event = getEvent();
    switch (event.type) {
        case NEW_CONNECTION: acceptConnection(event); break;  // 새 접속 처리
        case DATA_ARRIVED:   readAndProcess(event);   break;  // 데이터 도착 처리
        case CONNECTION_CLOSED: cleanup(event);       break;  // 연결 종료 처리
    }
}
```

#### 5) 다른 키워드와의 연결

이 단순한 "꺼내서 보내기" 루프를 구성요소로 정식화하고 역할을 분담시킨 설계가 바로 **반응자 패턴**이며, 루프가 처리하는 이벤트들이 _어디서 어떻게 한꺼번에 감지되는&#xC9C0;_&#xB294; **입출력 다중화**가, 루프가 그 이벤트로 _실제 I/O를 어떻게 수행하는&#xC9C0;_&#xB294; **이벤트 순환과 입출력**이 이어받아 다룬다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **진행률 표시줄에서 태어난 Node.js** — Node.js를 만든 라이언 달이 꼽은 출발점은 파일 업로드 '진행률 표시줄'이었다. 진행률을 보여 주려면 수많은 연결을 오래 물고 있어야 하는데 당시 아파치식 모델로는 무리라고 느껴 이벤트 구동 서버를 만들었고, 2009년 JSConf EU에서 Node.js를 시연하자 청중이 기립박수를 보낸 일화가 유명하다.
> * **원조는 서버가 아니라 GUI** — 이벤트 루프의 원조는 서버가 아니라 GUI다. 1984년 매킨토시와 1985년 윈도우 1.0의 모든 프로그램은 이벤트(메시지) 루프를 돌며 마우스·키보드 입력을 처리했고, 오늘날 안드로이드의 Looper와 iOS의 RunLoop도 같은 구조다. 서버의 이벤트 루프는 이 40년 된 패턴을 소켓에 적용한 것이다.
> * **Redis의 자체 루프 'ae'** — Redis를 만든 안티레즈(살바토레 산필리포)는 libevent 같은 기성 라이브러리 대신 의존성을 줄이기 위해 수백 줄 규모의 자체 이벤트 루프 'ae'를 직접 작성해 넣었다. 이 단일 이벤트 루프 하나로 초당 10만 건 이상의 명령을 처리한다.

### 5. 입출력 다중화

#### 1) 개념 정의

한 스레드(또는 프로세스)가 수많은 소켓(파일 디스크립터)을 **단 한 번의 호출로 동시에 감시**하다가, 그중 입출력이 준비된 것만 골라 통지받는 메커니즘이다.

#### 2) 원리 설명

이벤트 루프가 돌려면 "처리할 이벤트"가 공급되어야 하는데, 서버에서 그 **이벤트 소스(event source)는 바로 클라이언트와 연결된 소켓들**이다. 어떤 소켓에 새 데이터가 도착하거나 쓰기가 가능해지는 순간이 곧 하나의 이벤트다. 문제는 이런 소켓이 수천 개일 수 있다는 점이다. 소켓 하나하나에 대해 "지금 읽을 게 있나?"를 차례로 물어보는 블로킹 방식은, 한 소켓에서 막히면 나머지를 못 보고 멈춰버린다. 그래서 발상을 뒤집어, \*\*여러 이벤트 소스를 한 묶음으로 커널에 맡기고 "이 중에서 준비된 게 생기면 알려달라"\*\*고 요청하는 것이 입출력 다중화다. 덕분에 한 스레드가 다수의 소켓을 효율적으로 감시할 수 있다.

#### 3) 세부 메커니즘

다중화 호출은 입력과 출력이 분명하게 나뉜다.

* **입력**: 감시하고 싶은 디스크립터들의 집합과, 각 디스크립터에서 무엇을 기다리는지(읽기 가능/쓰기 가능 등) 알려준다. 예컨대 `select` 계열에서는 읽기·쓰기·예외용 디스크립터 집합을 각각 등록한다.
* **호출**: 한 번의 호출로 그 집합 전체를 커널에 넘기고, 준비된 디스크립터가 하나라도 생길 때까지(또는 타임아웃까지) 대기한다.
* **출력**: 준비된 디스크립터가 무엇인지, 몇 개인지를 돌려준다. 호출한 쪽은 그 결과를 보고 "어떤 소켓이 지금 처리 가능한가"만 추려낸다.

핵심은 \*\*"여러 fd를 한 번에 등록 → 준비된 것만 반환"\*\*이라는 한 단계다. 이렇게 골라낸 소켓에 대해 실제로 read/write를 수행하는 일은 이 단계의 몫이 아니다. 다중화 호출을 제공하는 대표적인 시스템 호출로 `select`, `poll`, 그리고 더 많은 연결에 확장성 있는 `epoll`(리눅스) 등이 있다. 다만 `select`는 한 번에 감시할 수 있는 디스크립터 수에 상한(흔히 1,024)이 있어, 수천\~수만 연결 규모에서는 그런 상한이 없는 `epoll` 계열을 쓴다.

#### 4) 예시

한 스레드가 1,000개의 연결 소켓을 감시한다고 하자. 이들을 전부 하나의 감시 호출에 넘기고, 그중 3개만 데이터가 도착해 읽기 준비가 된 상황을 그려보면 다음과 같다.

```python
import selectors

sel = selectors.DefaultSelector()

# (1) 등록: 감시할 1,000개 소켓을 "읽기 가능 이벤트" 대상으로 한꺼번에 등록
for sock in connected_sockets:          # 길이 1000
    sel.register(sock, selectors.EVENT_READ)

# (2) 감시: 단 한 번의 호출로 1,000개를 동시에 감시하며 대기
ready = sel.select()                    # 준비된 것이 생길 때까지 블록

# (3) 통지: 준비된 소켓만 반환됨 — 예를 들어 3개
print(len(ready))                       # 결과: 3

for key, mask in ready:
    # key.fileobj 가 "지금 읽을 데이터가 있는" 소켓
    # 실제 recv/처리는 다음 단계(이벤트 루프의 입출력)로 넘어감
    handle_ready_socket(key.fileobj)
```

작동 결과: 호출 한 번으로 1,000개를 감시했지만 반환된 것은 준비된 3개뿐이다. 스레드는 나머지 997개를 일일이 들여다보지 않고, 통지받은 3개만 처리 대상으로 넘긴다.

#### 5) 다른 키워드와의 연결

입출력 다중화는 **이벤트 순환과 이벤트 구동**에 "지금 처리할 이벤트가 어떤 소켓에서 왔는지"를 공급하는 입구 역할을 한다. 여기서 골라낸 "준비된 소켓"을 받아 실제로 논블로킹 read/write를 수행하는 단계는 **이벤트 순환과 입출력**에서 다룬다(즉, 이 소주제는 "누가 준비됐는지 감시·통지"까지, 실제 읽고 쓰는 처리는 그쪽으로 넘어간다).

> 💡 **TMI** (책 범위 밖 보강)
>
> * **다중화 API 40년 계보** — select는 1983년 4.2BSD, poll은 1986년 System V, kqueue는 2000년 FreeBSD, epoll은 2002\~2003년 리눅스, io\_uring은 2019년 리눅스 5.1에서 등장했다. 즉 select는 윈도우 1.0보다 나이가 많고, epoll과는 약 20년 차이가 난다.
> * **select의 1,024개 상한** — select가 감시할 수 있는 fd 개수는 컴파일 타임 상수 FD\_SETSIZE로 고정돼 있는데, 리눅스는 1024개, 윈도우 윈속은 기본 64개에 불과하다. 다시 말해 select만으로는 C10K는커녕 'C1K'도 빠듯하다.
> * **epoll보다 먼저 나온 kqueue** — FreeBSD의 kqueue(조너선 레몬 작)는 epoll보다 2년이나 먼저 나왔고, 소켓뿐 아니라 파일 변경·시그널·타이머·프로세스 종료까지 하나의 인터페이스로 감시할 수 있어 더 범용적이라는 평가를 받는다. macOS가 BSD 계열이라 지금도 맥에서는 kqueue가 쓰인다.

### 6. 이벤트 순환과 다중 스레드

#### 1) 개념 정의

이벤트 루프는 본질적으로 단일 스레드라 한 코어만 쓰는데, **CPU를 오래 쓰는 무거운 연산**을 여러 코어로 분산하기 위해 이벤트 루프와 다중 스레드를 결합하는 전략이다.

#### 2) 원리 설명

이벤트 루프는 하나의 스레드가 "다음 이벤트를 꺼내 처리하고, 끝나면 또 다음 이벤트를 꺼내는" 식으로 돌기 때문에, 그 스레드는 한 번에 한 가지 일만 처리한다. 문제는 이 한 스레드가 코어 하나만 쓴다는 점이다. 즉 코어가 8개여도 이벤트 루프 한 개로는 사실상 한 코어만 일하고 나머지 7개는 논다. 또 다른 문제는 이벤트 루프 안에서 CPU를 오래 점유하는 무거운 계산(이미지 변환·암호 연산·대량 정렬 등)을 직접 처리하면, 그 계산이 끝날 때까지 루프가 막혀(blocked) 대기 중인 모든 다른 연결이 함께 멈춰 버린다는 것이다. 이때 루프를 막는 주범은 _I/O 대&#xAE30;_&#xAC00; 아니라 _CPU 점&#xC720;_&#xC774;며, 따라서 해법도 (느린 I/O를 논블로킹으로 처리하는 '이벤트 순환과 입출력'과 달리) "그 무거운 일을 다른 코어로 분산"하는 것이다. 구체적으로는 두 가지 전략이 있다: (1) 오래 걸리는 작업을 워커 스레드 풀에 위임하고 결과만 이벤트로 돌려받기, (2) 코어 수만큼 이벤트 루프를 여러 개 띄워 연결을 나눠 받기.

#### 3) 세부 메커니즘

핵심은 "이벤트 루프 스레드는 디스패치(분배)만 하고, 시간이 오래 걸리는 일은 직접 하지 않는다"는 원칙이다.

* **전략 1 — 워커 스레드 풀에 위임**: 이벤트 루프가 무거운 작업을 만나면 직접 계산하지 않고, 미리 만들어 둔 워커 스레드 풀에 작업을 던진다. 워커 스레드가 다른 코어에서 그 작업을 처리하는 동안 이벤트 루프는 막히지 않고 계속 다음 이벤트를 처리한다. 워커가 작업을 끝내면 그 "완료"를 다시 하나의 이벤트로 만들어 이벤트 루프에 통지하고, 루프가 결과를 받아 후속 처리(예: 응답 전송)를 이어간다.
* **전략 2 — 코어당 이벤트 루프 여러 개**: 이벤트 루프 자체를 코어 수만큼 띄우고(예: 8코어면 이벤트 루프 8개, 각각 별도 스레드), 들어오는 연결을 이 루프들에 나눠 배정한다. 각 루프는 자기 몫의 연결만 책임지므로, 여러 루프가 동시에 서로 다른 코어에서 돌며 전체 처리량이 코어 수에 따라 늘어난다.

두 전략은 배타적이지 않고 함께 쓰기도 한다(여러 이벤트 루프 + 그 뒤에 공용 워커 풀).

#### 4) 예시

**예시 1 — 루프 안에서 직접 무거운 계산을 할 때 (나쁜 경우)**

```
이벤트 루프(1개 스레드) ──▶ 연결 A의 요청에서 5초짜리 CPU 계산을 직접 수행
                              (이 5초 동안 루프는 막힘)
연결 B, C, ... 1만 개  ──▶ 모두 큐에서 대기. 계산이 끝나는 5초 뒤에야 처리됨
```

한 연결의 무거운 작업 때문에 나머지 1만 개 연결이 전부 멈춘다. 처리량(초당 요청 수)이 급락하고, 다른 클라이언트들은 응답을 받지 못한 채 기다린다.

**예시 2 — 같은 작업을 워커 스레드 풀에 위임할 때 (좋은 경우)**

```
이벤트 루프 ──▶ 연결 A의 5초 계산을 워커 스레드 풀에 던짐 (즉시 반환)
            ──▶ 곧바로 연결 B, C, ... 의 이벤트를 계속 처리 (루프는 안 막힘)
워커 스레드(다른 코어) ──▶ 5초 계산 수행
                       ──▶ 끝나면 "완료" 이벤트로 루프에 통지
이벤트 루프 ──▶ 통지를 받아 연결 A에 결과 응답
```

루프가 막히지 않으므로 다른 1만 개 연결은 계속 정상 처리되고, 무거운 계산은 별도 코어에서 병렬로 끝난다.

의사 코드로 본 위임 흐름:

```python
def on_request(conn):
    if 무거운_작업(conn):
        thread_pool.submit(heavy_work, conn, callback=on_done)  # 루프는 막히지 않음
    else:
        handle_directly(conn)

def on_done(conn, result):   # 워커가 끝나면 이벤트로 다시 들어옴
    conn.send(result)
```

#### 5) 다른 키워드와의 연결

단일 이벤트 루프가 도는 기본 골격(이벤트를 꺼내 처리하는 순환 자체)은 **이벤트 순환과 이벤트 구동**이 다루며, 이 소주제는 그 한 스레드 루프를 멀티코어로 확장하는 방법만 다룬다. 워커 스레드 풀이 쓰는 공유 메모리·락 같은 일반적인 다중 스레드 개념은 **다중 스레드**가, '느린 I/O로 인한 블로킹을 논블로킹으로 회피'하는 별개 문제는 **이벤트 순환과 입출력**이 맡는다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **"Node.js는 단일 스레드"의 절반만 진실** — 이벤트 루프는 하나지만, 내부의 libuv는 기본 4개짜리 워커 스레드 풀을 따로 두고 파일 I/O나 DNS 조회 같은 작업을 처리하며, 환경 변수 UV\_THREADPOOL\_SIZE로 풀 크기를 늘릴 수 있다.
> * **Redis 6.0의 절충** — 단일 스레드를 오래 고수하던 Redis도 6.0(2020년)부터 I/O 스레드를 도입했다. 단, 명령 '실행'은 여전히 한 스레드가 전담해 원자성을 지키고, 추가 스레드들은 소켓 읽기/쓰기와 프로토콜 파싱만 분담하는 절충 설계다.
> * **코어당 루프 하나는 표준 레시피** — Nginx는 워커 프로세스 수를 CPU 코어 수에 맞추고 각 워커가 독립적인 이벤트 루프를 돌리며, Memcached 역시 기본 4개의 워커 스레드가 각자 libevent 루프를 돌리는 구조다.

### 7. 반응자 패턴

#### 1) 개념 정의

여러 이벤트 소스를 동시에 감시하다가 이벤트가 발생하면 미리 등록해 둔 전용 핸들러(콜백)에게 그 이벤트를 넘겨(디스패치) 처리하게 하는, **이름 붙은 이벤트 처리 설계 패턴**이다.

#### 2) 원리 설명

반응자 패턴은 "누가 일을 시키느냐"의 방향을 뒤집는 데 핵심이 있다(**제어의 역전**). 일반적인 코드는 처리 로직이 먼저 "데이터 왔니?"라고 자원에 직접 물어보지만, 반응자 패턴에서는 처리 로직(핸들러)이 자신이 관심 있는 이벤트를 시스템에 **미리 등록(register)** 만 해 두고 가만히 기다린다. 그 사이 패턴의 중심 부품인 디스패처(Reactor 본체)가 이벤트 디멀티플렉서를 통해 모든 자원을 한꺼번에 감시하다가, 어떤 자원이 준비되면 그 자원에 연결된 핸들러를 **대신 호출**해 준다. 즉 "네가 부르지 마라, 준비되면 우리가 부르겠다"는 식의 역전된 제어 흐름으로 동작한다. 루프가 이벤트를 꺼내 도는 기본 골격 자체는 **이벤트 순환과 이벤트 구동**이 다루고, 여기서는 그 골격 위에 _누가 어떤 책임을 지는&#xAC00;_&#xB97C; 구조로 못박는 데 집중한다.

#### 3) 세부 메커니즘

패턴은 다음 네 가지 구성요소의 역할 분담으로 이루어진다.

* **핸들(Handle) / 이벤트 소스**: 운영체제가 관리하는 자원(소켓, 파일 등)을 가리키는 식별자다. "어느 자원에서 무슨 일이 일어났는가"를 구분하는 이름표 역할을 한다.
* **이벤트 디멀티플렉서**: 여러 핸들을 한꺼번에 감시하며, 그중 하나라도 처리 가능한 상태가 될 때까지 대기한다. (여기서는 추상 구성요소로만 다룬다 — 여러 fd를 감시해 준비된 것을 골라내는 _구체 메커니&#xC998;_&#xC740; **입출력 다중화**가 맡는다.)
* **디스패처(Dispatcher = Reactor 본체)**: 패턴의 중심. ① 핸들러의 **등록/해제**를 관리하고(어떤 핸들에 어떤 핸들러를 붙일지 기억), ② 디멀티플렉서로부터 "이 핸들이 준비됐다"는 통지를 받으면 ③ 그 핸들에 등록된 핸들러를 찾아 호출(디스패치)한다.
* **이벤트 핸들러(Event Handler)**: 특정 이벤트가 왔을 때 실제 일을 하는 부분. 보통 `handle_event()` 같은 정해진 메서드를 구현해 두고, 디스패처가 이 메서드를 불러 준다.

흐름은 **등록 → 감시 → 통지 → 분배 → 처리**의 순서다. 시작 전에 핸들러들을 핸들과 짝지어 디스패처에 등록해 두고, 디스패처가 디멀티플렉서로 자원들을 감시하다가, 준비된 핸들을 통지받으면 그 핸들의 짝 핸들러를 호출한다.

#### 4) 예시

**예시 1 — 카페 운영 비유**. 반응자 패턴을 손님이 끊임없이 드나드는 카페에 빗대면 각 구성요소가 직관적으로 매핑된다.

* **손님이 무언가 요청하는 사건(주문하러 옴, 음료 찾으러 옴)** = 이벤트
* **각 손님 / 손님 번호표** = 핸들(이벤트 소스): "어느 손님에게 무슨 일이 났는지" 식별
* **누가 지금 카운터 앞에 와 있는지 살피는 일** = 이벤트 디멀티플렉서: 여러 손님 중 "지금 응대 가능한 손님"을 골라냄
* **카운터의 총괄 점원** = 디스패처(Reactor 본체): 어떤 요청을 어느 담당에게 넘길지 미리 정해 두고(등록), 준비된 손님이 보이면 알맞은 담당을 부른다
* **주문 종류별 담당(에스프레소 담당, 디저트 담당)** = 이벤트 핸들러: 자기 담당 요청이 들어올 때만 호출되어 처리

운영 흐름은 이렇다. 개점 전, 총괄 점원은 "주문 들어오면 음료 담당, 픽업 오면 픽업 담당"이라는 식으로 담당을 등록해 둔다(등록). 영업이 시작되면 점원은 카운터에 누가 와 있는지 살피며 기다리고(감시), 손님이 와 카운터가 "이 손님 준비됨"을 알리면(통지) 점원이 요청 종류를 보고 알맞은 담당을 호출한다(분배). 담당은 자기 일을 처리하고 다시 대기로 돌아가며(처리), 점원은 곧바로 다음 손님을 같은 방식으로 응대한다.

**예시 2 — 의사코드** (패턴의 배선 구조를 보이는 용도)

```
# 1) 등록 단계: 핸들과 핸들러를 디스패처에 짝지어 등록
dispatcher.register(손님A_핸들, 주문담당_핸들러)
dispatcher.register(픽업창구_핸들, 픽업담당_핸들러)

# 2) 디스패처가 디멀티플렉서로 감시 → 준비된 것만 분배
while 영업중:
    준비된_핸들들 = demultiplexer.wait(등록된_모든_핸들)   # 감시 + 통지
    for 핸들 in 준비된_핸들들:
        핸들러 = dispatcher.lookup(핸들)                    # 짝 찾기
        핸들러.handle_event(핸들)                            # 분배 → 처리
```

#### 5) 다른 키워드와의 연결

반응자 패턴은 **이벤트 순환과 이벤트 구동**에서 설명하는 이벤트 루프 골격을 **하나의 정형화된 설계 구조(역할 분담을 가진 패턴)로 구체화**한 형태이며, 디멀티플렉서가 여러 자원을 감시하는 구체 동작은 **입출력 다중화**에 기대고 있다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **이름을 붙인 사람, 더글러스 슈미트** — 반응자 패턴을 이름 붙여 문서화한 사람은 더글러스 슈미트로, 자신이 만든 C++ 네트워크 프레임워크 ACE에서 얻은 경험을 1995년 패턴 문헌으로 정리했다. ACE는 보잉의 항공전자 시스템, 에릭슨·모토로라의 통신 장비 등에 채택되며 이 패턴의 실전성을 증명했다.

### 8. 이벤트 순환과 입출력

#### 1) 개념 정의

감시 단계에서 "준비됐다"고 통지받은 소켓(fd)에 대해 이벤트 루프가 **논블로킹 방식으로 read/write를 짧게 수행한 뒤 곧바로 루프로 복귀**함으로써, 한 연결의 입출력이 단일 스레드 루프 전체를 멈추지 않게 하는 처리 방식이다.

#### 2) 원리 설명

이벤트 루프는 보통 단일 스레드에서 "한 번에 하나의 작업만" 순차로 처리한다. 그렇기 때문에 루프가 어느 한 연결의 입출력에서 멈춰 버리면, 그 동안 다른 모든 연결은 자기 차례를 받지 못한 채 함께 대기하게 된다. 즉 단일 스레드 루프에서는 입출력 한 번의 지연이 곧 전체 서버의 지연으로 번진다. 이를 막기 위해 이벤트 루프는 **블로킹 입출력을 직접 호출하지 않고 논블로킹 입출력만 사용한다**. 논블로킹 read는 읽을 데이터가 있으면 즉시 읽어 반환하고, 없으면 기다리지 않고 곧장 돌아오기 때문에 루프는 어느 한 연결에 붙들리지 않고 계속 다음 일을 처리할 수 있다. 결과적으로 각 연결의 입출력은 "짧게 처리하고 즉시 루프로 복귀"하는 형태로만 일어난다.

#### 3) 세부 메커니즘

핵심은 블로킹 read와 논블로킹 read의 동작 차이에 있다.

* **블로킹 read**: 데이터가 도착할 때까지 호출이 반환되지 않고 멈춘다. 데이터를 보내지 않는 느린 연결 하나만 있어도 그 자리에서 루프가 정지한다.
* **논블로킹 read**: 데이터가 있으면 그만큼 즉시 읽어 반환하고, 커널에 읽을 데이터가 없으면 멈추지 않고 즉시 "아직 없음"(EAGAIN / EWOULDBLOCK)을 반환한다. 루프는 이 신호를 보고 그 연결은 일단 두고 다음 일로 넘어간다.

여기서 중요한 점은, 이벤트 루프는 아무 fd나 무작정 읽는 것이 아니라 **감시 단계에서 "읽을 준비가 됐다"고 통지받은 fd만 읽는다**는 것이다. 준비됐다고 통지된 fd는 대개 곧바로 읽히므로, 논블로킹 read가 빈손으로 돌아오는 경우는 흔치 않고, 설령 그렇더라도 멈추지 않고 즉시 빠져나오므로 루프는 막히지 않는다. write도 같은 원리로, 보낼 공간이 있으면 쓸 수 있는 만큼만 쓰고 즉시 반환한다. 또한 이런 입출력은 루프가 한 번 도는 시간(처리량)에 직접 영향을 준다. 입출력을 짧게 끝내고 즉시 복귀할수록 루프는 더 빠르게 더 많은 연결을 돌 수 있다.

#### 4) 예시

같은 서버에 1만 개의 연결이 붙어 있다고 하자.

**(가) 블로킹 read를 쓰는 경우 — 잘못된 흐름**

```
loop:
    fd = 준비된 연결
    data = read(fd)        # 이 연결이 데이터를 안 보내면 여기서 멈춤
    handle(data)
```

연결 #1이 느려서 데이터를 보내지 않으면, `read(#1)`이 반환되지 않고 멈춘다. 그 사이 나머지 9999개 연결은 데이터가 와 있어도 처리되지 못하고 전부 대기한다. 단일 스레드 루프가 한 곳에 붙들려 서버 전체가 멈춘 셈이다.

**(나) 논블로킹 read를 쓰는 경우 — 올바른 흐름**

```
loop:
    for fd in 준비됐다고_통지받은_연결들:
        data = read_nonblocking(fd)
        if data == EAGAIN:      # 아직 데이터 없음 → 멈추지 않고
            continue            #   다음 연결로 넘어감
        handle(data)
    # 한 바퀴 끝 → 다시 루프 상단으로 복귀
```

각 read는 읽을 게 있으면 즉시 읽고, 없으면 즉시 빠져나온다. 따라서 느린 연결 #1이 있어도 루프는 거기서 멈추지 않고 준비된 나머지 연결을 차례로 처리한 뒤 곧바로 루프로 돌아온다.

#### 5) 다른 키워드와의 연결

이 소주제는 **입출력 다중화**가 "여러 fd 중 준비된 것"을 가려 통지해 주는 단계 바로 다음에 이어진다. 다중화가 "무엇을 읽을지"를 알려 주면, 이벤트 순환과 입출력은 그 통지를 받아 "실제로 어떻게 막히지 않게 읽고 쓸지"를 담당한다. 또한 논블로킹 read가 곧바로 처리할 수 없는 긴 작업은 **비동기와 콜백 함수**로 넘겨 나중에 결과를 받아 이어가게 된다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **epoll은 일반 파일을 못 본다** — epoll은 일반 디스크 파일을 감시하지 못한다(등록하면 EPERM 에러가 난다). select/poll은 일반 파일을 '항상 준비됨'으로 취급해 사실상 무의미하기 때문에, Node.js(libuv)는 네트워크는 이벤트 루프로, 파일 I/O는 별도 스레드 풀로 처리하는 이원 구조를 택했다.
> * **매뉴얼이 인정한 '거짓 준비'** — 리눅스 select(2) 매뉴얼의 BUGS 절에는 "준비됐다고 보고한 뒤에도 read가 블로킹될 수 있다"는 경고가 실려 있다(예: 도착한 패킷이 체크섬 불량으로 폐기된 경우). 그래서 다중화를 쓰더라도 소켓은 반드시 논블로킹으로 설정하는 것이 정석이다.
> * **천둥 무리(thundering herd)** — 여러 이벤트 루프가 같은 리스닝 소켓을 감시하면 연결 1개에 루프 전원이 깨어나는 '천둥 무리' 문제가 생긴다. Nginx는 오랫동안 accept\_mutex 옵션으로 이를 우회했고, 리눅스 커널은 2016년의 4.5 버전에 와서야 EPOLLEXCLUSIVE 플래그를 추가해 커널 차원에서 해결했다.

### 9. 비동기와 콜백 함수

#### 1) 개념 정의

결과를 기다리지 않고 즉시 반환하는 비동기 호출에서 "작업이 끝났을 때 이어서 할 일"을 함수(콜백)로 미리 넘겨 두고, 작업 완료 시점에 그 콜백이 불려 나머지 처리를 이어가는 방식이다.

#### 2) 원리 설명

동기 호출은 결과가 나올 때까지 호출부가 멈춰 기다리지만, 비동기 호출은 작업을 시작시키고 결과를 기다리지 않은 채 바로 다음 줄로 넘어간다. 문제는, 결과가 아직 없는데 호출이 반환되어 버리면 "그 결과로 해야 할 후속 처리"를 호출 시점에 곧바로 쓸 수 없다는 점이다. 이를 해결하기 위해 결과가 도착한 뒤 실행할 로직을 하나의 함수에 담아 비동기 호출에 인자로 함께 넘긴다. 비동기 작업이 완료되면 시스템이 그때 이 함수를 대신 호출(call back)해 결과를 전달하므로, 후속 처리가 올바른 시점에 이어진다. 즉 "지금 당장 결과를 받는 것"이 아니라 "나중에 결과가 생기면 호출해 달라고 약속한 함수를 등록"하는 구조다. 이렇게 하면 호출부는 기다리며 멈춰 있지 않으면서도 작업 순서를 보장받을 수 있다.

#### 3) 세부 메커니즘

핵심은 두 단계로 나뉜다. 먼저 **등록 단계**에서 콜백 함수를 비동기 호출의 인자로 전달한다 — 이때 비동기 호출 자체는 작업을 걸어 두기만 하고 즉시 반환하므로, 콜백은 아직 실행되지 않고 "완료되면 부를 함수"로만 보관된다. 다음으로 **완료 단계**에서 작업이 실제로 끝나는 시점에 보관해 둔 콜백이 호출되고, 그 인자로 결과(데이터나 오류)가 넘어온다. 문제는 후속 처리가 또 다른 비동기 작업을 필요로 할 때다. 두 번째 작업의 결과를 쓰려면 다시 그 안에 콜백을 넘겨야 하고, 세 번째 작업도 마찬가지가 된다. 그 결과 "A가 끝나면 B, B가 끝나면 C"라는 본래 순차적인 로직이 콜백 안의 콜백, 그 안의 또 콜백 형태로 중첩되며, 들여쓰기가 깊어지고 흐름을 따라 읽기 어려운 구조가 만들어진다. 이것이 흔히 \*\*콜백 지옥(callback hell)\*\*이라 불리는 가독성 문제다.

#### 4) 예시

**(1) 비동기 파일 읽기에 콜백 넘기기** — 파일 읽기는 시간이 걸리는 작업이므로 결과를 기다리지 않고, "읽기가 끝나면 실행할 함수"를 인자로 넘긴다.

```javascript
// readFile은 즉시 반환되고, 읽기가 끝난 뒤 넘긴 콜백이 호출된다
fs.readFile('./file.txt', (err, data) => {
  // 이 안은 "파일 읽기 완료" 시점에 실행된다
  if (err) { console.log('읽기 실패'); return; }
  console.log(data.toString());
});

console.log('읽기 요청을 보냈습니다'); // 위 콜백보다 먼저 출력된다
```

흐름: `readFile` 호출 → 즉시 반환 → `'읽기 요청을 보냈습니다'` 출력 → (시간이 지나 읽기 완료) → 콜백 호출 → 파일 내용 출력.

**(2) 콜백이 중첩된 콜백 지옥** — "하나 → 둘 → 셋"을 순서대로 처리하려는데 각 단계가 비동기라서, 다음 단계를 앞 단계의 콜백 안에 계속 집어넣게 된다.

```javascript
function fn() {
  setTimeout(() => {
    console.log('하나');
    setTimeout(() => {
      console.log('둘');
      setTimeout(() => {
        console.log('셋');
      }, 0);
    }, 0);
  }, 0);
}
```

결과는 `하나 → 둘 → 셋` 순으로 출력되지만, 단계가 늘어날수록 들여쓰기가 한 단계씩 깊어진다. 본래는 단순한 "순서대로 세 번"인 로직이 중첩 구조로 표현되어, 읽기도 수정하기도 어려워지고 중간 단계의 오류 처리도 까다로워진다.

#### 5) 다른 키워드와의 연결

콜백이 실제로 "완료 시점"에 불리도록 작업 완료를 감지하고 대기 중인 콜백을 깨우는 일은 **이벤트 순환과 이벤트 구동**이 담당한다. 그리고 여기서 드러난 콜백 지옥 문제(순차 로직이 중첩으로 쪼개지는 현상)는, 비동기를 동기 코드처럼 평탄하게 쓰게 해 주는 **코루틴**에서 해결한다.

> 💡 **TMI** (책 범위 밖 보강)
>

### 10. 코루틴

#### 1) 개념 정의

실행 도중 특정 지점에서 스스로 멈췄다가(일시중단, suspend) 나중에 바로 그 멈춘 자리부터 상태를 유지한 채 다시 이어서 실행(재개, resume)될 수 있는, 일반 함수를 일반화한 실행 단위다.

#### 2) 원리 설명

일반 함수(서브루틴)는 한 번 호출(call)되면 끝(return)까지 쭉 실행되고, 진입점도 하나 탈출점도 하나다. 코루틴은 여기에 두 가지 동작을 더한다. 실행 중 특정 지점에서 제어권을 자발적으로 양보하며 멈추고(suspend), 나중에 그 지점부터 다시 시작(resume)하는 것이다. 즉 함수가 `call → 실행 → return`이 아니라 `call → 실행 → suspend → resume → 멈춘 지점부터 계속`의 흐름을 가진다. 멈출 때 코루틴은 자신이 어디까지 실행했는지를 기억해 두기 때문에, 재개될 때 처음부터가 아니라 정확히 멈춘 다음 지점부터 이어서 실행할 수 있다. 이렇게 "기다려야 하는 지점에서 멈췄다가 결과가 준비되면 그 자리에서 이어가는" 동작 덕분에, 흐름을 콜백으로 쪼개지 않고도 위에서 아래로 순서대로 읽히는 코드로 비동기 작업을 표현할 수 있다.

#### 3) 세부 메커니즘

핵심은 "멈출 때 무엇을 기억하느냐"에 있다. 코루틴이 일시중단되는 순간, 그때까지의 지역 변수 값과 "지금 실행이 어디까지 왔는지(실행 위치)" 같은 실행 상태가 보존된다. 그리고 재개될 때 이 상태가 복원되어, 마치 한 번도 멈추지 않았던 것처럼 바로 그 지점부터 계속 실행된다. 이것이 일반 함수와 결정적으로 다른 점이다. 일반 함수도 다른 함수를 호출하면 잠시 "빠져나갔다" 돌아오지만, 그것은 호출한 함수가 끝나고 제자리로 복귀하는 것일 뿐 함수 자신의 실행이 중간에 멈췄다 이어지는 것은 아니다. 반면 코루틴은 자기 함수 본문의 한가운데에서 멈추고, 그 중간 상태를 그대로 들고 있다가, 나중에 그 한가운데로 다시 들어와 이어 달린다. 또한 이때 멈추는 것은 스레드가 아니라 코루틴 자신의 실행이라는 점이 중요하다. 코루틴이 멈춰 있는 동안 그 스레드는 막히지 않고 다른 일을 할 수 있다.

#### 4) 예시

같은 로직("사용자 → 게시글 → 댓글을 차례로 가져와 화면을 갱신")을 두 방식으로 비교하면 차이가 분명하다.

콜백으로 흐름을 쪼갠 비동기 코드 — 각 단계의 결과를 다음 콜백 안에서 받느라 코드가 안쪽으로 계속 중첩된다.

```kotlin
api.fetchUser(userId) { user ->
    api.fetchPosts(userId) { posts ->
        api.fetchComments(posts[0].id) { comments ->
            updateUI(user, posts, comments)
        }
    }
}
```

코루틴으로 작성한 같은 로직 — 각 호출 지점에서 결과가 준비될 때까지 코루틴이 일시중단되었다가 재개되므로, 흐름을 쪼개지 않고 위에서 아래로 순서대로 읽힌다.

```kotlin
suspend fun loadContent(userId: String) {
    val user = fetchUser(userId)            // 결과가 올 때까지 멈췄다가 재개
    val posts = fetchPosts(userId)          // 그 다음 줄로 이어서
    val comments = fetchComments(posts[0].id)
    updateUI(user, posts, comments)
}
```

작동 흐름: `fetchUser`를 호출하면 코루틴은 결과가 아직 없는 동안 그 자리에서 일시중단되고(그동안 스레드는 다른 일을 할 수 있음), `user` 값이 준비되면 바로 그 다음 줄부터 재개된다. 결과적으로 동작은 비동기지만 코드 모양은 동기처럼 한 줄씩 순차적으로 읽힌다. 예외 처리도 콜백 체인을 거치지 않고 동기 코드처럼 `try/catch`로 감쌀 수 있어 흐름 파악이 쉽다.

#### 5) 다른 키워드와의 연결

이 소주제는 앞의 **비동기와 콜백 함수**가 정의한 콜백 지옥(중첩으로 흐름이 쪼개지는 문제)에 대한 해법으로 이어진다. 코루틴은 그 쪼개진 흐름을 동기 모양의 순차 코드로 되돌린다. 또한 코루틴이 스레드가 아닌 사용자 영역의 가벼운 실행 단위라는 점은 뒤의 **CPU·스레드·코루틴**에서 다루는 스케줄링 계층과 비용 관점으로 연결된다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **1958년, 콘웨이의 발명** — '코루틴'이라는 용어는 1958년 멜빈 콘웨이가 만들었고, 1963년 그의 논문에서 COBOL 컴파일러를 코루틴들의 조합으로 설계한 사례와 함께 공개됐다. "조직의 구조가 시스템 구조를 결정한다"는 콘웨이의 법칙의 바로 그 콘웨이다.
> * **"서브루틴은 코루틴의 특수한 경우"** — 도널드 크누스는 TAOCP에서 "서브루틴은 코루틴의 특수한 경우"라고 썼다. 코루틴은 Simula 67이나 Modula-2 같은 1960\~70년대 언어에 이미 들어 있다가 주류에서 한동안 사라졌고, C++20(2020년)과 Java 21(2023년) 등으로 되살아났으니 '최신 기능'이 아니라 60년 만에 재발견된 고대 기능에 가깝다.
> * **위챗을 떠받치는 libco** — 텐센트가 공개한 코루틴 라이브러리 [libco](https://github.com/Tencent/libco)는 2013년부터 위챗(WeChat) 백엔드의 수만 대 서버에서 돌고 있다고 공식 소개에 적혀 있다. 기존 동기식 코드를 거의 고치지 않고 시스템 콜을 가로채(훅킹) 코루틴으로 바꿔 주는 접근으로 유명하다.

### 11. CPU·스레드·코루틴

#### 1) 개념 정의

CPU(코어)가 스레드를 실행하고, 그 스레드 하나 위에서 다시 여러 개의 코루틴이 번갈아 실행되는 **3단 적재 관계**다. 즉 실행의 토대는 CPU 코어, 그 위에 운영체제가 굴리는 스레드, 다시 그 위에 사용자 프로그램이 굴리는 코루틴이 얹힌 계층 구조다.

#### 2) 원리 설명

물리적으로 코드를 실행하는 주체는 CPU 코어이며, 코어 하나는 한 순간에 스레드 하나만 돌릴 수 있다. 운영체제는 이 코어 위에서 여러 스레드를 빠르게 바꿔치기해 동시에 여러 일이 진행되는 것처럼 보이게 한다. 그런데 스레드를 바꿀지 말지를 결정하고 실제로 바꾸는 주체는 \*\*운영체제(커널)\*\*여서, 스레드 전환에는 항상 커널이 개입한다. 반면 코루틴은 한 스레드 안에서 서로 실행 권한을 주고받으며 번갈아 도는데, 이 전환을 결정·수행하는 주체는 커널이 아니라 **사용자 프로그램(런타임)** 자신이다. 따라서 스레드 전환은 커널이 끼어들어 비싸고, 코루틴 전환은 커널을 거치지 않아 훨씬 싸다. 바로 이 "누가 스케줄링하는가"의 차이가 두 전환의 비용 차이를 만든다.

#### 3) 세부 메커니즘

* **스레드 전환(커널 개입, 비쌈)**: 운영체제가 끼어들어, 지금 돌던 스레드의 레지스터·스택 포인터·프로그램 카운터 등 실행 상태를 저장하고, 다음 스레드의 상태를 복원한다. 이 과정에서 사용자 모드와 커널 모드 사이를 오가는 **모드 전환**이 일어나고, 다음에 어떤 스레드를 돌릴지 고르는 스케줄러 작업까지 더해져 비용이 든다.
* **코루틴 전환(커널 개입 없음, 가벼움)**: 같은 스레드 안에서 일어나므로 커널을 부르지 않는다. 런타임이 사용자 공간에서 "어디까지 실행했는지(재개 지점)와 필요한 최소 상태"만 바꿔치기하면 끝난다. 모드 전환도, 운영체제 스케줄러 호출도 없어 함수 호출에 견줄 만큼 가볍다.
* 핵심 대비: **스레드 전환의 비용은 대부분 "커널을 거친다"는 데서 오고, 코루틴은 그 단계를 통째로 건너뛴다.**

#### 4) 예시

**(1) 한 스레드 위에 수많은 코루틴을 얹는 그림**

```
   CPU 코어
      │  (운영체제가 스케줄링 — 전환 시 커널 개입)
   스레드 1개
      │  (런타임이 스케줄링 — 전환 시 커널 개입 없음)
   ┌───┬───┬───┬─── … ───┐
  코루A 코루B 코루C  …   코루N   (수천 개)
```

스레드는 단 1개지만, 그 위에서 코루틴 A→B→C…를 사용자 공간에서 차례로 바꿔가며 실행한다. 코루틴 하나가 일을 멈춰야 할 때(예: 입출력 대기) 스레드를 통째로 멈추는 대신 실행 권한만 다음 코루틴에게 넘기므로, 스레드 1개가 수천 개의 동시 작업을 떠받칠 수 있다.

**(2) 비용 대비** — 같은 동시성을 스레드로만 달성하려면 스레드 수만큼 운영체제 자원과 비싼 전환이 필요하지만, 한 스레드 위에 코루틴을 잔뜩 얹으면 전환이 사용자 공간에서 가볍게 일어난다. 그래서 **한 스레드 위에 수많은 코루틴을 값싸게 얹어, 스레드를 무작정 늘리지 않고도 대규모 동시성을 달성**할 수 있다.

#### 5) 다른 키워드와의 연결

이 "한 스레드 위 다수 코루틴" 구조에서 코루틴이 _어떻게_ 멈췄다 이어지며 순차적 코드 모양을 유지하는지(suspend/resume의 동작 원리)는 **코루틴**이 다룬다. 여기서는 그 동작이 "왜 값싼지"(스케줄링 주체·전환 비용)만 짚는다. 코루틴이 입출력 대기 시점에 스레드를 막지 않고 실행 권한을 넘긴다는 점은 **이벤트 순환**·**비동기와 콜백 함수**가 다루는 "막지 않고 일하는" 흐름과 같은 문제의식으로 이어진다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **커널이 버린 M:N, 유저 공간의 부활** — 커널 수준의 M:N 스레딩은 한때 대세였다가 버려진 기술이다. M:N의 대표 주자였던 솔라리스는 복잡성 때문에 솔라리스 9(2002년)에서 1:1 모델로 회귀했고, 리눅스에서도 IBM의 M:N 구현(NGPT)이 1:1 방식의 NPTL에 패배했다. 그렇게 커널 세계가 포기한 M:N을 Go의 고루틴, Erlang, Java 가상 스레드가 유저 공간에서 부활시킨 것이다.
> * **2KB vs 8MB** — 고루틴의 초기 스택은 2KB(Go 1.4에서 8KB에서 2KB로 축소)로, 리눅스 스레드의 기본 스택 8MB의 약 1/4000 수준이다. 덕분에 스레드로는 메모리 부담 때문에 수만 개도 버거운 자리에서 고루틴은 수백만 개를 띄울 수 있다.
> * **Go도 처음엔 코어 1개** — 동시성 언어로 태어난 Go조차 1.5 버전(2015년) 전까지는 GOMAXPROCS 기본값이 1이어서, 설정을 바꾸지 않으면 고루틴이 아무리 많아도 CPU 코어 1개만 사용했다. 런타임 스케줄러가 충분히 성숙한 뒤에야 기본값이 '머신의 코어 수'로 바뀌었다.

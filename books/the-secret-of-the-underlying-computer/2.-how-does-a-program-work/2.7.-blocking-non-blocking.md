# 2.7. Blocking, Non-blocking

### 블로킹과 논블로킹

#### 개념 정의

블로킹(blocking)과 논블로킹(non-blocking)은 어떤 함수를 호출했을 때 **호출한 스레드가 멈추는가**를 가리키는 용어로, 피호출 함수가 결과가 준비될 때까지 반환하지 않고 호출한 스레드가 그동안 아무 일도 실행하지 못한 채 멈춰 기다리면 블로킹 호출, 작업 완료 여부와 상관없이 호출이 즉시 반환되어 스레드가 멈추지 않고 계속 실행되면 논블로킹 호출이다.

#### 원리 설명

함수 호출에는 "피호출 함수가 반환한 다음에야 호출한 쪽의 다음 줄이 실행된다"는 기본 규칙이 있다. 그래서 피호출 함수가 **언제 반환해 주느냐**가 곧 호출한 스레드의 운명을 결정한다. 블로킹 호출에서 피호출 함수는 요청받은 결과를 준비한 뒤에야 반환하므로, 결과가 늦어지면 그 시간 내내 호출한 스레드는 호출 지점에 묶여 다음 줄을 단 한 줄도 실행하지 못한다 — 대신 반환되었다는 사실 자체가 "결과가 준비되었다"는 보장이 된다. 반면 논블로킹 호출에서 피호출 함수는 작업이 끝났든 아니든 곧바로 반환하므로, 호출한 스레드는 멈추는 일 없이 다음 코드를 계속 실행한다 — 대신 반환되었다는 사실이 더 이상 작업 완료를 뜻하지 않는다. 결국 두 용어를 가르는 기준은 함수가 무슨 일을 하느냐가 아니라, **그 호출이 호출한 스레드를 멈춰 세우는가** 하나다.

#### 세부 메커니즘

* **블로킹 호출은 '호출'과 '완료'를 한 묶음으로 판다**: 블로킹 호출에서는 호출 → (결과 준비) → 반환이 하나로 묶여 있어, 호출 시점과 작업 완료 시점 사이의 거리가 그대로 스레드가 멈춰 있는 시간이 된다. 논블로킹 호출은 이 묶음을 풀어 **호출(반환) 시점과 작업 완료 시점을 분리**한다. 호출은 지금 끝나고, 작업의 완료는 그와 별개의 시점에 일어난다.
* **즉시 반환이 보장하는 것과 보장하지 않는 것**: 즉시 반환이 보장하는 것은 단 하나, 호출한 스레드가 멈추지 않고 곧바로 다음 줄을 실행한다는 것이다. 보장하지 않는 것은 두 가지다. 첫째, 결과가 손에 있다는 것 — 결과가 아직 준비되지 않았다면 피호출 함수는 "아직 안 됐다"는 표시를 들고서라도 일단 반환한다. 둘째, 작업이 빨리 끝난다는 것 — 작업 자체의 소요 시간은 그대로이고, 달라지는 것은 그동안 스레드가 멈추느냐 여부뿐이다. 따라서 논블로킹 호출의 반환값을 곧바로 결과로 믿어서는 안 된다.
* **블로킹의 단위는 스레드다**: "프로그램이 블로킹된다"는 말은 부정확하다. 멈추는 것은 그 호출을 실행한 스레드 하나이며, 같은 프로그램 안의 다른 스레드들은 영향을 받지 않고 계속 실행된다. 블로킹/논블로킹을 따질 때는 항상 "어느 스레드가 멈추는가"를 기준으로 보면 된다.
* **같은 기능을 블로킹/논블로킹 두 버전으로 만들 수 있다**: 블로킹 여부는 함수가 하는 일(기능)이 아니라 호출 방식의 속성이므로, 같은 일을 하는 함수가 양쪽 버전으로 모두 존재할 수 있다. 대표적으로 소켓의 데이터 수신 함수는 소켓을 어느 모드로 설정했느냐에 따라, 같은 함수가 블로킹으로도 논블로킹으로도 동작한다(아래 예시 2).

#### 예시

**예시 1 — 같은 작업, 두 호출 방식의 타임라인**

결과를 준비하는 데 2초가 걸리는 데이터 읽기 함수를 가정한다.

```c
/* 블로킹 버전 */
int data = read_data();   // t = 0초에 호출 → 반환될 때까지 이 줄에 멈춤
use(data);                // t = 2초가 되어서야 실행됨 (단, data는 확실히 손에 있다)
other_work();             // 역시 t = 2초 이후로 밀림
```

```c
/* 논블로킹 버전 */
int ret = read_data_nb(); // t = 0초에 호출 → 즉시 반환 (ret는 "아직 준비 안 됨"일 수 있음)
other_work();             // 스레드가 멈추지 않으므로 t ≈ 0초에 바로 실행됨
```

작동 결과: 블로킹 버전에서는 `other_work()`가 2초 뒤에야 시작되지만, `use(data)`가 실행되는 순간 결과는 반드시 준비되어 있다. 논블로킹 버전에서는 `other_work()`가 즉시 시작되지만, `ret`에 원하던 데이터가 들어 있다는 보장은 없다. 그리고 논블로킹이라고 해서 데이터가 2초보다 빨리 준비되는 것도 아니다 — 달라지는 것은 작업 속도가 아니라 호출한 스레드가 멈추느냐 여부다. 스레드의 실행 흐름을 선으로 그리면 다음과 같다.

```
[블로킹]   스레드 실행: ──호출┤ (멈춤: 다음 줄 실행 불가) ├──반환─이후 코드──
[논블로킹] 스레드 실행: ──호출──즉시 반환──이후 코드 계속────────────────
```

**예시 2 — 같은 함수의 두 가지 모드**

소켓 수신 함수 `recv()`는 함수 이름도 인자도 하는 일도 같지만, 소켓의 모드 설정 하나로 블로킹/논블로킹 어느 쪽으로든 동작한다.

```c
/* (a) 블로킹 모드 (소켓의 기본값) */
int n = recv(sock, buf, 1024, 0);
// 줄 데이터가 없으면 반환되지 않는다. 상대가 아무것도 보내지 않는
// 한 이 줄에 멈춰 있다가, 데이터가 도착한 뒤에야 반환되어 다음 줄로
// 넘어간다(연결이 끊기는 등의 예외 상황은 논외로 한다).

/* (b) 논블로킹 모드로 설정을 바꾼 뒤 */
set_nonblocking(sock);   // 운영 체제가 제공하는 모드 전환 설정
int n = recv(sock, buf, 1024, 0);
// 줄 데이터가 없어도 무조건 즉시 반환된다. 이때 n에는 데이터 크기
// 대신 "지금은 기다려야 하는 상황"이라는 표시가 담기고, 스레드는
// 멈추지 않고 다음 줄을 실행한다.
```

작동 결과: (a)는 데이터가 도착해야만 반환되고, (b)는 어떤 경우에도 곧바로 반환된다. 같은 기능의 함수가 두 얼굴을 가질 수 있다는 것은, 블로킹/논블로킹이 함수의 종류가 아니라 **호출 방식의 속성**임을 보여 준다.

#### 다른 키워드와의 연결

여기서 "멈춘다"라고만 표현한 스레드가 운영 체제에 의해 실제로 대기(블로킹) 상태로 처리되는 과정과 그런 기다림이 주로 어디서(입출력) 생기는지는 "블로킹의 핵심 문제: 입출력"이, 즉시 반환받은 뒤 결과를 어떻게 받아 오는지는 "논블로킹과 비동기 입출력"이 이어받는다. 이 축이 동기/비동기 축과 어떻게 짝지어지는지는 "동기와 블로킹"·"비동기와 논블로킹"에서, 전체의 직관적 그림은 "피자 주문에 비유하기"에서 완성된다.

### 블로킹의 핵심 문제: 입출력

#### 개념 정의

프로그램에서 스레드가 대기(블로킹) 상태로 멈추게 되는 가장 대표적이고 핵심적인 원인은 입출력(I/O), 즉 CPU보다 압도적으로 느린 디스크·네트워크 같은 외부 장치와 데이터를 주고받으며 그 결과를 기다려야 하는 작업이다.

#### 원리 설명

CPU는 나노초(ns) 단위로 움직이는 장치이지만 입출력 장치는 차원이 다르게 느려서, 메모리에서 데이터를 읽는 데 약 100ns가 걸리는 동안 하드디스크가 데이터 위치를 찾는 데는 약 10ms로 그 10만 배, 대륙 간 네트워크 왕복에는 약 150ms로 100만 배가 넘는 시간이 걸린다. 이 거대한 격차 때문에, 입출력을 요청한 스레드가 결과가 나올 때까지 CPU를 붙든 채 제자리에서 기다리는 것은 엄청난 낭비다. 그래서 운영 체제는 블로킹 입출력 호출(예: 네트워크 데이터 수신)을 받았는데 당장 줄 데이터가 없으면, 호출한 스레드를 실행 상태에서 대기(블로킹) 상태로 바꿔 CPU에서 내려놓고 스케줄링 대상에서 제외해 버린다. 비워진 CPU는 실행 준비가 된 다른 스레드에게 넘어가므로, 기다림의 비용은 시스템 전체가 아니라 그 스레드 혼자 치른다. 기다리던 데이터가 도착하면 운영 체제가 스레드를 다시 준비 상태로 깨우고, 스케줄러가 CPU를 할당하면 멈췄던 지점부터 실행이 재개된다. 반면 기다릴 외부 장치가 없는 순수 계산 호출에서는 이런 전환이 일어날 이유가 없으므로(이 대비는 "동기와 블로킹" 참고) 블로킹이라는 말이 나오는 곳에는 거의 항상 입출력이 끼어 있다 — 용어 자체의 정의는 앞 소주제 "블로킹과 논블로킹"을 따른다.

#### 세부 메커니즘

블로킹 수신 함수 `recv()` 호출 한 번의 생애 주기를 단계별로 따라가면, "스레드를 내려놓고 깨운다"가 실제로 어떤 일인지 드러난다.

1. **시스템 호출** — `recv()`는 결국 운영 체제에게 보내는 요청이다. 호출과 함께 사용자 모드에서 커널 모드로 진입해 "이 소켓에 도착한 데이터를 달라"고 요청한다.
2. **커널의 수신 버퍼 확인** — 운영 체제는 소켓마다 커널 안에 수신 버퍼를 두고 있다. 거기에 데이터가 이미 와 있으면 사용자 쪽 버퍼로 복사해 즉시 반환하며, 이 경우 블로킹은 일어나지 않는다. 수신 버퍼가 비어 있을 때만 다음 단계로 간다.
3. **대기 상태 전환과 대기 큐 등록** — 커널은 스레드가 멈춘 지점의 실행 문맥(레지스터 값 등)을 저장하고, 스레드 상태를 실행에서 대기(블로킹) 상태로 바꾼 뒤, 실행 가능한 스레드 목록에서 빼서 그 소켓을 기다리는 명단인 대기 큐(wait queue)에 등록한다. 대기 큐의 스레드는 스케줄링 대상이 아니므로 **CPU 시간을 전혀 소비하지 않는다**.
4. **CPU 양도** — 스케줄러가 준비 큐에서 다른 스레드를 골라 CPU에 올린다(컨텍스트 스위칭). 입출력이 진행되는 동안 CPU는 다른 스레드의 일을 한다.
5. **인터럽트로 깨움과 재개** — 네트워크 카드에 데이터가 도착하면 하드웨어가 인터럽트로 커널에 알린다. 커널은 데이터를 소켓의 수신 버퍼에 넣고, 대기 큐에 있던 스레드를 꺼내 준비 큐로 옮긴다(wakeup). 스케줄러가 다시 CPU를 할당하면 스레드는 `recv()` 호출 직후 지점부터 실행을 이어 가며, 버퍼의 데이터를 받아 들고 사용자 코드로 돌아온다.

같은 소켓이라도 블로킹되는 지점은 "기다려야 하는 순간"마다 다르다. `recv()`는 수신 버퍼가 **비어 있을 때** 블로킹되고, 반대로 `send()`는 송신 버퍼가 **가득 차서** 더 넣을 공간이 없을 때 블로킹된다(예: 상대가 데이터를 가져가지 않아 버퍼가 차오른 경우). 즉 블로킹의 본질은 함수 이름이 아니라 "장치나 상대방이 준비될 때까지 기다려야 하는가"이다.

#### 예시

**예시 1 — CPU와 입출력 장치의 속도 격차**

어림 기준 수치로, 하드웨어 세대에 따라 달라질 수 있지만 격차의 규모를 보여 주기에 충분하다.

| 작업         | 소요 시간 | 메모리 참조(100ns) 대비 |
| ---------- | ----- | ---------------- |
| 메모리 참조     | 100ns | 1배               |
| HDD 디스크 시크 | 10ms  | 100,000배         |
| 대륙 간 패킷 왕복 | 150ms | 1,500,000배       |

모든 시간을 10억 배로 늘려 사람의 시간으로 바꿔 보면, 메모리 참조(100ns)가 1분 40초일 때 디스크 시크(10ms)는 약 116일, 대륙 간 왕복(150ms)은 약 4년 9개월이 된다. CPU 입장에서 입출력을 "그 자리에서" 기다린다는 것은 이 정도 체감의 기다림이다.

**예시 2 — `recv()` 호출 한 줄의 타임라인**

```c
char buf[1024];
int n = recv(sock, buf, sizeof(buf), 0);  // 블로킹 수신 호출
printf("%d바이트 수신\n", n);             // 데이터가 도착한 뒤에야 실행된다
```

대륙 간 서버와 통신해 응답 도착까지 150ms가 걸린다고 가정하면 다음과 같이 진행된다.

* t = 0ms: 스레드 A가 `recv()` 호출 → 시스템 호출로 커널 진입. 수신 버퍼가 비어 있으므로 A는 대기(블로킹) 상태로 전환되어 대기 큐에 등록되고, CPU는 스레드 B에게 넘어간다.
* t = 0 \~ 150ms: A의 CPU 사용량은 0. 3GHz CPU라면 이 사이 약 4억 5천만 클록이 지나간다 — A가 제자리에서 기다렸다면 통째로 버려졌을 시간 동안, CPU는 B의 일을 처리한다.
* t = 150ms: 응답 패킷 도착 → 인터럽트로 커널에 알림 → 커널이 수신 버퍼에 데이터를 채우고 A를 준비 큐로 옮긴다(wakeup).
* t = 150ms + α: A가 CPU를 다시 할당받아 `recv()`에서 복귀한다.

작동 결과: 상대가 1,024바이트를 보냈다면 `1024바이트 수신`이 출력된다. 단, 이 줄이 찍히는 시각은 호출 시점이 아니라 데이터 도착으로 스레드가 깨어난 약 150ms 뒤다.

#### 다른 키워드와의 연결

"블로킹과 논블로킹"이 용어의 관점을 잡아 주었다면, 이 소주제는 그 블로킹이 현실에서 **어디서, 왜** 생기는지(압도적으로 느린 입출력)와 그 순간 스레드에게 실제로 일어나는 일을 보여 준다. 이 입출력 대기를 스레드를 멈추지 않고 다루는 길은 "논블로킹과 비동기 입출력"이, 여기서 본 '기다림'을 동기 개념과 구분해 정리하는 일은 "동기와 블로킹"이 이어받는다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **지연 시간 표의 원전**: 본문 같은 지연 시간 표의 원전은 구글 제프 딘(Jeff Dean)의 강연 자료(더 거슬러 가면 피터 노빅의 에세이)이고, 이를 Akka 창시자 요나스 보네르(Jonas Bonér)가 2012년 ["Latency Numbers Every Programmer Should Know"](https://gist.github.com/jboner/2841832)라는 GitHub gist로 정리하면서 폭발적으로 퍼졌다. GitHub에서 가장 유명한 gist 중 하나로, 연도별 변화를 보여주는 [인터랙티브 버전](https://colin-scott.github.io/personal_website/research/interactive_latency.html)도 있다.
> * **표에서 뺀 수치들**: 본문 표에 넣지 않은 수치 몇 개를 더 보면 격차가 입체적으로 보인다. L1 캐시 참조는 0.5ns로 메인 메모리 참조(100ns)의 1/200이고, "빠르다"는 SSD조차 4KB 랜덤 읽기에 150µs로 메모리보다 1,500배 느리며, 같은 데이터센터 안에서 한 번 왕복(0.5ms)하는 동안 CPU는 메모리를 5,000번 참조할 수 있다.
> * **CPU의 시간 감각**: 브렌던 그레그(Brendan Gregg)는 《Systems Performance》에서 이 수치들을 인간 시간으로 환산했다. CPU 1사이클(0.4ns)을 1초라고 치면 메모리 접근은 약 4분, SSD I/O는 1.5~~4일, 회전식 디스크 I/O는 1~~9개월, 샌프란시스코-뉴욕 네트워크 왕복은 5년이다. 블로킹된 스레드가 "잠깐 기다리는" 동안 CPU 입장에서는 계절이 바뀌고 있는 셈이다.

### 논블로킹과 비동기 입출력

#### 개념 정의

논블로킹 입출력은 데이터 준비 여부와 무관하게 '지금 줄 수 있는 만큼'만(전혀 없으면 "아직 준비 안 됨" 표시를) 들고 즉시 반환되는 입출력 방식이고, 비동기 입출력은 요청을 받은 운영 체제가 실제 입출력을 뒤에서 대신 진행하다가 완료되는 시점에 결과를 호출자에게 건네주는 입출력 방식이다.

#### 원리 설명

논블로킹 입출력 호출은 기다리는 대신 '지금 줄 수 있는 것'을 그대로 들고 곧바로 돌아온다. 준비된 데이터가 있으면 그만큼만이라도 담아 주고, 전혀 없으면 빈손이라는 사실 자체를 특별한 표시로 알려 준다(블로킹/논블로킹이라는 용어 자체의 정의는 "블로킹과 논블로킹" 참고). 따라서 호출이 반환되었다는 것이 곧 일이 끝났다는 뜻이 아니므로, 호출자에게는 결과를 끝까지 받아낼 별도의 방법이 필요하다. 첫 번째 방법은 호출자가 틈틈이 같은 호출을 반복하며 준비 여부를 직접 확인하는 폴링(polling)이고, 두 번째 방법은 요청을 운영 체제에 맡겨 두면 실제 입출력은 운영 체제가 뒤에서 진행하고 완료되는 순간 결과를 통지와 함께 건네받는 방식이다. 이 가운데 뒤쪽, 즉 요청만 맡기고 완료 통지로 결과까지 받는 형태가 비동기 입출력이며, 두 방식 모두 호출 스레드를 대기(블로킹) 상태로 만들지 않는다는 점은 같지만 "준비됐는지 확인하는 일"을 누가 하느냐가 다르다.

#### 세부 메커니즘

* **즉시 반환이 실제로 돌려주는 것**: 논블로킹 읽기 호출의 반환값은 두 갈래다. 줄 데이터가 있으면 그 순간 줄 수 있는 바이트 수를 돌려주는데, 요청한 양보다 적을 수 있고 이는 오류가 아니다 — 지금 도착해 있는 양이 그만큼뿐이라는 뜻이다. 줄 데이터가 전혀 없으면 -1과 함께 "지금 진행했다면 블로킹됐을 작업"임을 뜻하는 특별한 오류 코드를 남긴다. 이 코드는 실패 통보가 아니라 "나중에 다시 시도하라"는 신호이므로, 호출자는 연결 끊김 같은 진짜 오류와 구분해 재시도 대상으로 다뤄야 한다.
* **폴링 경로 — 확인 비용과 지연 사이의 트레이드오프**: 폴링에서 확인 한 번은 곧 시스템 호출 한 번이고, 데이터가 아직이면 그 호출은 통째로 헛수고다. 쉼 없이 확인하면 도착을 거의 즉시 알아채는 대신 CPU 한 코어가 '확인'만 반복하며 헛돈다(바쁜 대기). 확인 사이에 간격을 두면 CPU는 아끼지만, 간격 도중에 도착한 데이터를 다음 확인 때까지 알아채지 못하는 지연이 생긴다. 간격을 어디에 잡든 'CPU 낭비'와 '늦게 알아채는 지연' 중 하나는 떠안는 구조이며, 결과를 받아낼 책임이 끝까지 호출자에게 남는다.
* **통지 경로 — 운영 체제가 대신 진행하고 결과를 건네주는 구조**: 호출자는 요청 시점에 결과를 담을 버퍼와 "끝나면 이 함수를 불러 달라"는 콜백을 함께 등록하고 즉시 반환받는다. 이후 데이터 도착을 지켜보고 버퍼를 채우는 일까지 운영 체제가 뒤에서 수행하며, 완료되는 시점에 콜백 호출 같은 통지로 "버퍼에 n바이트 채워 놓았다"는 결과를 호출자에게 건네준다. 호출자 코드에서 확인 작업 자체가 사라지므로 헛도는 시스템 호출이 0이 되고, 준비 여부 확인과 결과 전달의 책임이 호출자에서 운영 체제 쪽으로 넘어간다.

#### 예시

같은 "소켓에서 데이터 읽기"를 두 메커니즘으로 처리해 보면 차이가 드러난다. 데이터는 1초 뒤에 도착한다고 하자.

```c
/* 방법 1 — 폴링: 호출자가 직접 다시 물어본다 (논블로킹 read) */
while (1) {
    n = read(sock, buf, 4096);  /* 데이터가 없어도 즉시 반환 */
    if (n > 0) break;           /* 도착해 있는 만큼만 받음 — 4096보다 적을 수 있다 */
    /* n == -1이고 '아직 준비 안 됨' 표시라면 실패가 아니라 "나중에 다시" */
    do_something_else();        /* 다음 확인 때까지 다른 일 */
}
```

작동 결과: 루프가 약 1ms에 한 번 확인한다면 1초 동안 약 1,000번의 `read` 호출 중 999번은 "아직"이라는 답만 받고 버려진다 — 확인 한 번이 곧 시스템 호출 한 번이므로 이 비용은 전부 호출자 몫이다. 반대로 확인 간격을 100ms로 늘리면 헛확인은 10번 정도로 줄지만, 데이터가 도착해도 최악의 경우 100ms 가까이 지나서야 알아챈다.

```c
/* 방법 2 — 완료 통지: 운영 체제가 뒤에서 진행하고 끝나면 알려 준다 */
void on_done(int n) {
    /* 운영 체제가 buf에 n바이트를 채워 놓은 뒤, 완료 시점에 호출해 준다 */
}

async_read(sock, buf, 4096, on_done);  /* 버퍼와 콜백만 등록하고 즉시 반환 */
do_something_else();                   /* 확인 루프가 아예 없다 */
```

(`async_read`는 개념을 보여 주기 위한 가상의 함수다.)

작동 결과: 1초 뒤 데이터가 도착하면 운영 체제가 `buf`를 채우고 `on_done`을 호출해 결과를 건네준다. 같은 1초 동안 방법 1의 확인용 호출이 1,000번이라면 방법 2는 0번이다 — 결과를 받아내는 일이 호출자의 일감에서 운영 체제의 일감으로 옮겨 갔기 때문이다.

```
[폴링]  호출자: read?→아직  read?→아직  …(999번 헛수고)…  read?→데이터!
[통지]  호출자: async_read 등록 ────(다른 일만 함)────→ on_done(n) 실행
        운영 체제:        (뒤에서 도착 감시·버퍼 채움)──완료, 통지─┘
```

#### 다른 키워드와의 연결

"블로킹의 핵심 문제: 입출력"이 보여 준 입출력 대기를, 이 소주제는 기다리지 않는 호출과 완료 통지라는 입출력 메커니즘으로 풀어냈다. 여기서 갈라진 폴링·통지 두 갈래를 동기/비동기 개념 축 위에 올려 "논블로킹과 비동기는 같은 말인가"를 따지는 일은 다음 소주제 "비동기와 논블로킹"이 맡는다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **"아직 안 됨"의 정체**: 논블로킹 호출이 "아직 안 됨"을 알리는 수단은 거창한 게 아니라 오류 코드다. 리눅스/POSIX에서는 EAGAIN("다시 시도하라")과 EWOULDBLOCK("진행했다면 블로킹됐을 것")이라는 이름으로, 리눅스에서는 두 이름이 같은 값(11)의 별칭이지만 POSIX는 다른 값도 허용해 이식성 있는 코드는 둘 다 검사한다. 실패가 아니라 "나중에 다시 와라"라는 정상적인 신호로 취급된다는 점이 포인트다.
> * **콜백 말고 시그널**: 완료 통지 수단도 콜백만 있는 게 아니다. 1993년 POSIX.1b 실시간 확장으로 표준화된 POSIX AIO(`aio_read` 등)는 완료를 시그널(SIGEV\_SIGNAL)로 받을지, 새 스레드에서 함수를 실행(SIGEV\_THREAD)하게 할지 고를 수 있다. 의외의 사실 하나 — 리눅스 glibc의 POSIX AIO는 커널 비동기가 아니라 유저 공간 스레드 풀이 블로킹 read/write를 대신 해주는 구현이다([man 7 aio](https://man7.org/linux/man-pages/man7/aio.7.html)에 명시).
> * **진짜 비동기까지의 길**: 리눅스 커널 네이티브 AIO(`io_submit`)는 사실상 O\_DIRECT 파일에서만 제대로 비동기로 동작하고 조건이 어긋나면 몰래 블로킹되는 "반쪽 비동기"로 악명이 높았다([Cloudflare 기술 블로그](https://blog.cloudflare.com/io_submit-the-epoll-alternative-youve-never-heard-about/)도 이를 다뤘다). 2019년에야 블록 계층 메인테이너 옌스 악스보(Jens Axboe)가 리눅스 5.1에 io\_uring을 넣으면서, 제출 큐와 완료 큐를 커널과 공유하는 진짜 비동기 I/O가 리눅스에 생겼다.

### 피자 주문에 비유하기

#### 개념 정의

"피자 주문에 비유하기"는 동기/비동기·블로킹/논블로킹이라는 두 쌍의 추상적인 용어를, 주문한 피자가 구워지는 동안 주문자가 보이는 서로 다른 행동 — 카운터 앞에서 그냥 기다리기, 딴 일을 하며 틈틈이 확인하러 가기, 배달로 받기 — 이라는 일상 장면에 대응시켜 직관적으로 익히게 하는 책 2.7절의 비유 장치다.

#### 원리 설명

동기/비동기와 블로킹/논블로킹은 눈에 보이지 않는 프로그램 세계의 일이라, 말로만 들으면 좀처럼 구분이 서지 않는다. 이 비유는 그 용어들을 "주문한 피자를 기다리는 사람"이라는 눈에 보이는 장면으로 바꿔 놓는데, 비유가 성립하는 바탕은 두 세계의 구조가 같다는 데 있다 — 피자는 주문하자마자 나오지 않고 구워지는 시간이 필요하며, 이는 요청을 해 놓고 결과가 준비되기까지 시간이 걸리는 함수 호출과 같은 모양이다. 그래서 같은 가게에서 같은 피자를 주문한다는 조건은 그대로 두고 **주문자의 행동만** 바꾼 장면들을 나란히 놓으면, 추상 용어의 차이가 "카운터 앞에 서 있느냐, 자리에서 게임을 하느냐, 집에서 영화를 보느냐"라는 행동의 차이로 번역되어 눈에 보이게 된다. 독자는 이미 이 장면들을 모두 살아 봤기 때문에 — 매장에서 음식을 기다려 봤고, 진동벨이 없는 가게에서 카운터를 들락거려 봤고, 배달 음식이 올 동안 딴 일을 해 봤기 때문에 — 새 용어를 통째로 외우는 대신 익숙한 경험 위에 라벨만 얹으면 된다. 이때 장면의 각 요소가 프로그램의 어떤 요소를 대신하는지 일러 주는 대응표, 곧 매핑 사전이 비유의 세계와 실제 프로그램 사이를 잇는 다리가 된다.

#### 세부 메커니즘

각 장면을 시간 순서대로 따라가 보자. 장면마다 핵심은 주문자의 행동, 시간이 어떻게 쓰이는가, 그리고 기다림의 질감이다.

**장면 A — 카운터 앞에서 그냥 기다리기 (동기+블로킹)**

1. 18:00, 카운터에서 주문을 넣는다. "30분쯤 걸립니다."
2. 주문자는 카운터 앞을 떠나지 않는다. 도우가 펴지고 오븐에 들어가는 주방 풍경을 그저 바라본다. 따로 하는 일은 없다.
3. 30분 내내 이 사람의 시간은 "피자 기다리기" 하나로만 채워진다.
4. 18:30, 피자가 나오자마자 점원이 그 자리에서 손에 건넨다. 받아 든 순간 기다림이 끝난다 — 카운터를 떠나는 순간, 피자는 반드시 손에 있다.

기다림의 질감: 발이 묶인 기다림. 완성됐는지 물어볼 필요조차 없지만(눈앞에서 나오므로), 그 대가로 자기 시간 전부를 내준다.

**장면 B — 자리에서 딴 일을 하며 틈틈이 확인하러 가기 (동기+논블로킹)**

1. 18:00, 주문을 넣고 곧바로 자리로 돌아온다.
2. 휴대폰 게임을 하거나 일행과 수다를 떤다. 다만 이 가게는 완성돼도 불러 주지 않는 곳이라, 피자가 나왔는지 알아내는 일은 끝까지 주문자의 몫이다.
3. 18:10쯤, 하던 게임을 멈추고 카운터까지 걸어가 묻는다. "다 됐나요?" — "아직이요." 헛걸음을 하고 자리로 돌아온다.
4. 18:20쯤, 두 번째 확인. 또 "아직이요".
5. 18:30, 세 번째 확인에서 "나왔습니다"를 듣고 피자를 받아 돌아온다.

기다림의 질감: 몸은 자유롭지만 신경 한 가닥이 계속 피자에 매여 있는 기다림. 자기 일과 "확인하러 가는 발걸음"이 번갈아 끼어들고, 헛걸음이 쌓인다.

**장면 C — 배달을 시켜 놓고 내 일 보기 (비동기+논블로킹)**

1. 18:00, 집에서 배달 주문을 넣고 주소를 남긴다.
2. 주문 직후 피자를 머릿속에서 지운다. 빨래를 개고, 영화를 튼다. 가게에 전화를 걸 일도, 현관을 내다볼 일도 없다.
3. 그사이 가게 쪽에서는 피자를 굽고, 포장하고, 배달원이 출발한다 — 전부 주문자가 모르는 사이에 진행된다.
4. 초인종이 울린다. 그 소리가 곧 "완성됐고, 문 앞까지 와 있다"는 소식이다.
5. 문을 열면 피자가 손으로 들어온다. 완성을 알리는 일도, 피자를 가져다주는 일도 모두 가게 쪽이 해 주었다.

기다림의 질감: "기다림"이라는 활동 자체가 없다. 피자가 오기까지의 시간이 온전히 자기 일로 채워진다.

**매핑 사전 — 장면 요소를 프로그램 요소로 잇기**

| 피자 장면의 요소             | 프로그램의 요소                |
| --------------------- | ----------------------- |
| 나(주문자)                | 함수를 호출한 스레드(호출자)        |
| 피자 가게(주방)             | 요청을 처리해 주는 피호출자         |
| 피자 주문                 | 함수 호출(요청을 맡기는 일)        |
| 피자                    | 호출 결과                   |
| 피자가 구워지는 30분          | 결과가 준비되기까지 걸리는 시간       |
| 카운터 앞에 서 있기           | 결과가 나올 때까지 멈춰 있는 호출자    |
| 자리에서 하는 게임, 집에서 보는 영화 | 그사이 호출자가 실행하는 자신의 다른 코드 |
| 카운터에 가서 "다 됐나요?" 묻기   | 준비됐는지 물어보는 확인 호출        |
| 초인종                   | 완료 통지                   |
| 문 앞까지 오는 배달           | 결과 전달(결과가 호출자를 찾아옴)     |
| 문을 열고 피자 받기           | 전달된 결과를 받아 쓰기 시작하는 순간   |

이 사전만 옆에 두면, 장면 속 어떤 문장이든 프로그램 문장으로 바꿔 읽을 수 있다 — 그 번역 작업 자체는 이 절의 다음 소주제들이 맡는다.

#### 예시

**예시 — 같은 가게, 같은 피자, 세 주문자의 타임라인** (피자는 18:30에 완성되고, 배달에는 10분이 더 걸린다고 하자)

| 시각    | A. 카운터 대기형           | B. 틈틈이 확인형               | C. 배달 주문형             |
| ----- | -------------------- | ------------------------ | --------------------- |
| 18:00 | 주문 후 카운터 앞에 그대로 서 있음 | 주문 후 자리로 돌아가 게임 시작       | 배달 주문 후 빨래 개기 시작      |
| 18:10 | 계속 서 있음 — 한 일 없음     | 첫 확인 — "아직이요" → 자리 복귀    | 빨래 끝, 영화 시작(피자 생각 없음) |
| 18:20 | 계속 서 있음 — 한 일 없음     | 두 번째 확인 — "아직이요" → 자리 복귀 | 영화 시청 중               |
| 18:30 | 갓 나온 피자를 그 자리에서 받음   | 세 번째 확인 — "나왔습니다" → 받아 옴 | (배달 출발) 계속 영화 시청      |
| 18:40 | —                    | —                        | 초인종 → 문 열고 피자 받음      |
| 라벨    | 동기+블로킹               | 동기+논블로킹                  | 비동기+논블로킹              |

같은 30\~40분을 정산해 보면 세 줄의 차이가 또렷해진다.

* **A**: 기다림 30분, 딴 일 0분. 확인하러 간 횟수 0회(내내 그 자리에 있었으므로), 받은 알림 0회.
* **B**: 딴 일 약 27분 + 확인 걸음 3회(그중 2회는 헛걸음). 받은 알림 0회 — 나왔다는 사실도 결국 자기 발로 가서 알아냈다.
* **C**: 내 일 40분. 확인 0회, 알림(초인종) 1회 — 완성 소식과 피자가 함께 문 앞에 도착했다.

세 주문자의 차이는 피자가 구워져 나온 시각이 아니다 — 피자는 셋 모두 18:30에 완성됐다. 차이는 그때까지의 시간이 **무엇으로 채워졌는가**, 그리고 완성된 피자가 **어떤 경로로 손에 들어왔는가**다.

#### 다른 키워드와의 연결

장면에 붙인 라벨의 용어 정의 자체는 "블로킹과 논블로킹"(블로킹/논블로킹 축)과 2.6절(동기/비동기 축)이 책임지고, 라벨 짝들이 서로 어떤 관계인지 따지는 개념 논증은 "동기와 블로킹"과 "비동기와 논블로킹"이 맡는다. 피자가 구워지는 동안 프로그램 세계에서 실제로 벌어지는 일은 "블로킹의 핵심 문제: 입출력"이, 카운터 확인과 초인종에 해당하는 실제 입출력 방법은 "논블로킹과 비동기 입출력"이 보여 준다.

### 동기와 블로킹

#### 개념 정의

동기는 "결과를 받기 전에는 다음 줄로 진행하지 않는다"는 **호출 순서·제어 흐름**의 속성이고 블로킹은 "기다리는 동안 호출한 스레드가 일시 중지된다"는 **스레드 상태**의 속성이므로, 블로킹 호출은 언제나 동기이지만 동기 호출이 모두 블로킹인 것은 아니다 — 두 개념은 동의어가 아니라 **"블로킹 호출 ⊂ 동기 호출"이라는 비대칭 포함 관계**다.

#### 원리 설명

"동기"와 "블로킹"은 흔히 같은 뜻처럼 섞여 쓰이지만, 사실 서로 다른 질문에 답하는 단어다. 동기는 "호출한 쪽이 결과를 받기 전에는 다음 줄로 진행하지 않는가?"라는 코드 진행 순서에 관한 질문이고(정의는 2.6절 참고), 블로킹은 "그 기다리는 시간 동안 호출한 스레드가 일시 중지되는가?"라는 스레드 상태에 관한 질문이다(정의는 "블로킹과 논블로킹" 참고). 포함 관계의 한쪽 방향은 이렇게 성립한다. 블로킹 호출에서는 호출한 스레드가 멈춰 있어 다음 줄로 진행할 방법 자체가 없으므로, "결과를 받은 뒤에야 진행한다"는 동기의 조건을 저절로 충족한다 — 블로킹이면 반드시 동기다. 그러나 반대 방향은 성립하지 않는다. 동기라는 말은 "함수가 반환하기 전에는 다음 줄로 못 간다"까지만 보장할 뿐, 그 시간을 스레드가 잠들어 보내는지 일하며 보내는지는 아무것도 말해 주지 않기 때문이다. 그래서 스레드가 한순간도 멈추지 않는 동기 호출이 얼마든지 존재할 수 있고, 그 대표가 순수 계산 함수다.

#### 세부 메커니즘

겉에서 보면 두 호출은 구분되지 않는다 — 어느 쪽이든 "호출하면 반환될 때까지 다음 줄로 못 간다"는 모양이 똑같기 때문이다. 차이는 그 시간 동안의 \*\*"기다림의 정체"\*\*에 있다.

* **동기이지만 블로킹이 아닌 호출(순수 계산)이 진행되는 동안**: 호출자가 "결과를 기다리는" 것처럼 보이는 시간의 정체는 사실 기다림이 아니라 **그 스레드 자신의 노동**이다. 결과를 만들어 내는 주체가 바로 호출한 스레드이므로 멈출 이유가 없고, 스레드는 내내 실행 상태를 유지하며 **CPU를 점유한 채 일한다**. 운영 체제가 개입해 재울 일이 전혀 없다.
* **블로킹 호출이 진행되는 동안**: 기다림의 정체가 스레드 바깥의 사건(장치나 상대방의 준비)이라서 스레드가 아무리 명령어를 돌려도 결과를 앞당길 수 없으므로, 스레드는 그 시간을 **CPU를 반납하고 대기(블로킹) 상태로 잠들어** 보낸다. 잠든 스레드는 메모리만 차지할 뿐 CPU 사이클을 전혀 소비하지 않는다. 운영 체제가 어떤 과정을 거쳐 스레드를 재우고 다시 깨우는지는 "블로킹의 핵심 문제: 입출력"에서 다룬다.

요컨대 판별 기준은 한 줄이다. 호출이 진행되는 동안 그 스레드의 CPU 사용량이 0이면 블로킹이고, CPU를 계속 쓰고 있다면 — 동기일지언정 — 블로킹이 아니다.

#### 예시

"동기 = 블로킹"이라는 등식이 참이려면 **모든** 동기 호출이 블로킹이어야 한다. 아래 (a)는 그 등식을 무너뜨리는 단 하나의 반례, 즉 "동기이지만 블로킹이 아닌 호출"의 존재 증명이다.

```c
// (a) 동기이지만 블로킹이 아닌 호출: 순수 계산 — 등식의 반례
long long sum(int n) {
    long long total = 0;
    for (int i = 1; i <= n; i++)
        total += i;
    return total;
}

long long result = sum(100000000);  // 반환 전에는 다음 줄로 못 감 → 동기
printf("%lld\n", result);           // 호출 동안 스레드는 1억 번의 덧셈을 직접
                                    // 수행하며 CPU를 점유 → 블로킹 아님

// (b) 동기이면서 블로킹인 호출: 아직 도착하지 않은 데이터의 입출력
char buf[1024];
int n = read(fd, buf, sizeof(buf));  // 반환 전에는 다음 줄로 못 감 → 동기
printf("%d bytes\n", n);             // 호출 동안 스레드는 대기(블로킹) 상태로
                                     // 잠들어 CPU 사용량 0 → 블로킹
```

작동 결과: 두 경우 모두 `printf`는 호출이 반환된 뒤에야 실행된다 — 둘 다 동기다. 그러나 (a)가 실행되는 동안 시스템 모니터를 보면 이 스레드가 도는 CPU 코어는 100% 가까이 바쁘게 일하고, (b)가 실행되는 동안 이 스레드의 CPU 사용량은 0이다. (a)의 존재로 "동기 호출이 전부 블로킹은 아니다"가 증명되고, 반대로 결과를 기다리며 멈춘 블로킹 호출이 동기가 아닐 길은 없으므로, 포함 관계는 블로킹 쪽이 동기 안에 들어가는 한 방향으로만 성립한다.

#### 다른 키워드와의 연결

블로킹/논블로킹이라는 용어 자체의 정의는 "블로킹과 논블로킹"이 잡아 주고, (b) 같은 입출력 호출에서 스레드가 실제로 어떤 과정을 거쳐 잠들고 깨어나는지는 "블로킹의 핵심 문제: 입출력"이 이어받는다. 여기서 쓴 것과 같은 방식의 비대칭 논증을 반대쪽 짝(논블로킹과 비동기)에 적용하는 일은 "비동기와 논블로킹"이 맡는다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **기다림보다 비싼 점유**: 동기 블로킹의 진짜 비용은 "기다림" 자체보다 기다리는 동안 점유한 자원이다. 리눅스 스레드의 기본 스택 예약은 보통 8MB(가상 메모리 기준), JVM은 스레드당 기본 1MB라서 연결 1만 개를 스레드 1만 개로 받으면 스택 예약만 기가바이트 단위가 되고, 여기에 마이크로초 단위의 컨텍스트 스위칭 비용이 곱해진다. C10K 시대에 thread-per-connection이 무너진 산수가 이것이다.
> * **블로킹을 싸게 만들기**: 업계는 동기 블로킹 스타일을 버리는 대신 "싸게 만드는" 길도 택했다. Go의 고루틴은 초기 스택 2KB로 시작해 필요할 때만 키우고, Java 21(2023)의 가상 스레드(Project Loom)는 블로킹 호출 시점에 OS 스레드를 양보하게 만든다. 코드는 여전히 동기 블로킹처럼 읽히지만 런타임 내부는 논블로킹으로 돌아가는, 일종의 절충안이다.
> * **async/await의 역설**: async/await 문법의 계보를 보면 동기식 코드의 힘을 역으로 알 수 있다. F# 비동기 워크플로(2007)에서 시작해 C# 5.0(2012), Python 3.5(2015), JavaScript ES2017, Rust 1.39(2019)까지 10여 년 만에 주류 언어 전부가 채택했는데, 이 문법의 존재 이유 자체가 "비동기 코드를 동기처럼 읽히게 만들기"다. 그만큼 위에서 아래로 읽히는 동기식 사고가 인간에게 자연스럽다는 방증이다.

### 비동기와 논블로킹

#### 개념 정의

논블로킹은 "호출이 작업 완료를 기다리지 않고 즉시 반환되는가"라는 **호출 반환 방식**의 속성이고, 비동기는 "완료를 알아내고 결과를 챙기는 책임이 호출자에게 있는가, 시스템 쪽으로 넘어갔는가"라는 **결과 전달 방식**의 속성이므로 — 두 용어는 서로 다른 질문에 대한 답이며, 논블로킹 호출이라고 해서 반드시 비동기인 것은 아니다.

#### 원리 설명

두 용어는 실전에서 거의 항상 "비동기 + 논블로킹"이라는 짝으로 함께 등장하기 때문에 같은 뜻처럼 오해되기 쉽지만, 각각이 답하는 질문 자체가 다르다. 논블로킹은 호출의 들고 나는 방식만 말한다 — 작업이 끝나지 않았어도 호출 자체는 곧바로 반환된다는 것(블로킹이라면 호출한 스레드가 대기(블로킹) 상태로 멈춘다 — 용어 정의는 "블로킹과 논블로킹" 참고). 그런데 "즉시 반환된다"는 사실은 완료된 결과가 어떤 경로로 호출자 손에 들어오는지에 대해 아무것도 정해 주지 않는다. 완료를 알아내는 일과 결과를 거두는 일이 여전히 호출자의 몫으로 남아 있다면 결과를 얻는 방식은 동기적이고, 그 책임이 시스템 쪽으로 넘어가 완료가 결과와 함께 호출자에게 전달될 때 비로소 비동기라고 부를 수 있다. 즉 논블로킹은 비동기가 서기 위한 바탕이 되어 주는 일은 많지만, 논블로킹이라는 사실만으로 비동기가 되지는 않는다. 거꾸로 비동기 호출은 호출자가 완료 전에 이미 반환받아 제 일을 하고 있어야 '완료 통지'가 성립하므로 반드시 논블로킹이다. 그래서 둘의 관계는 한쪽 방향으로만 기우는 비대칭이다 — "블로킹이면 반드시 동기"("동기와 블로킹")를 반대쪽에서 본 것과 같은 관계다.

#### 세부 메커니즘

* **두 질문이 분리되는 이유 — 바라보는 구간이 다르다**: 첫째 질문(즉시 반환되는가)은 호출 직후라는 **한 시점**의 속성이고, 둘째 질문(책임이 누구에게 있는가)은 반환 이후 완료에 이르는 **구간 전체**의 속성이다. 한 시점의 사실이 그 뒤 구간 전체의 규칙까지 결정할 수는 없으므로, 두 질문은 논리적으로 독립이며 답도 따로 정해진다.
* **논블로킹이 만들어 내는 틈**: 완료까지 반환하지 않는 호출에서는 반환 시점 = 완료 시점 = 결과 수령 시점이 한 점에 포개져 있어 둘째 질문이 따로 보이지 않는다. 논블로킹은 반환 시점을 완료 시점보다 앞으로 떼어 내는데, 그 순간 "반환과 완료 사이의 빈 구간"이 생기고, 이 구간을 누가 지켜보다 마무리하느냐는 둘째 질문이 비로소 독립된 질문으로 드러난다. 두 용어가 헷갈리는 근본 이유는, 블로킹 세계에서는 애초에 구분할 필요가 없던 질문이기 때문이다.
* **비대칭이 생기는 이유**: 논블로킹은 그 빈 구간을 만들 뿐 채워 주지는 않는다. 구간을 호출자가 스스로 메우면(끝났는지 알아내는 것도, 결과를 가져오는 것도 호출자) 논블로킹이면서 결과 획득은 동기적이고, 시스템이 메워 주면(완료가 결과를 싣고 호출자를 찾아옴) 그때가 논블로킹 + 비동기다. 그래서 "논블로킹 → 비동기"는 성립하지 않으며, 논블로킹은 비동기의 충분조건이 아니다.
* **판정 기준 한 줄**: 비동기 여부는 호출 직후의 모습이 아니라 **완료 순간의 모습**으로 판정한다. 완료를 향해 호출자가 움직이면(알아내러 가면) 동기, 완료가 호출자를 향해 움직이면(전달되어 오면) 비동기다.

이 구분을 표로 고정하면 다음과 같다.

| 질문                                | 가르는 축    | 무엇에 대한 속성인가                | 답                    |
| --------------------------------- | -------- | -------------------------- | -------------------- |
| ① 호출이 작업 완료 전에 즉시 반환되는가?          | 블로킹/논블로킹 | 호출 반환 방식 — 호출 직후 한 시점의 일   | 예 → 논블로킹 / 아니오 → 블로킹 |
| ② 완료를 알아내고 결과를 챙기는 책임이 호출자에게 있는가? | 동기/비동기   | 결과 전달 방식 — 반환 후 완료까지 구간의 일 | 예 → 동기 / 아니오 → 비동기   |

#### 예시

**예시 1 — 네 가지 호출 시나리오 판정 연습**

다음 네 장면을 위 표의 두 질문에 차례로 답해 좌표에 놓아 보자.

* (가) 데이터가 준비될 때까지 반환하지 않는 읽기 호출을 하고 그대로 기다린다.
* (나) 즉시 반환되는 호출을 해 두고, 끝났는지를 호출자가 이따금 직접 알아보고 결과도 직접 가져온다.
* (다) 즉시 반환되는 호출에 "끝나면 결과를 전해 달라"고 맡겨 두고, 호출자는 이 작업을 더 신경 쓰지 않는다.
* (라) 입출력 없이 값을 계산해 반환값으로 돌려주는 함수를 호출한다.

| 시나리오             | ① 즉시 반환되는가?                                        | ② 완료·결과 책임이 호출자에게 있는가?    | 판정(좌표)                    |
| ---------------- | -------------------------------------------------- | ------------------------- | ------------------------- |
| (가) 블로킹 읽기       | 아니오 — 완료까지 반환되지 않음                                 | 예 — 반환받는 것이 곧 결과 수령       | 블로킹 · 동기                  |
| (나) 논블로킹 + 직접 확인 | 예                                                  | 예 — 알아내는 것도 가져오는 것도 호출자 몫 | 논블로킹 · **동기**             |
| (다) 논블로킹 + 완료 통지 | 예                                                  | 아니오 — 완료가 결과와 함께 전달됨      | 논블로킹 · 비동기                |
| (라) 순수 계산        | 아니오 — 단, 기다림이 아니라 스레드가 직접 일하는 시간이므로 블로킹으로 분류하지 않는다 | 예 — 반환값으로 그 자리에서 수령       | 동기 · 블로킹 아님("동기와 블로킹" 참고) |

판정 포인트: (나)와 (다)는 ①의 답이 같고 ②만 다르다 — "논블로킹"이라는 공통점이 비동기 여부를 결정하지 못한다는 비대칭이 표 안에서 그대로 드러난다. 반대로 (가)와 (나)는 ①을 바꿨는데 ②는 그대로다 — 즉시 반환을 도입하는 것만으로는 결과 획득 방식이 동기에서 벗어나지 않는다. (라)처럼 입출력이 없는 호출도 같은 두 질문의 틀로 판정할 수 있다.

**예시 2 — 두 축 좌표평면에 배치하기**

같은 네 장면 중 (가)·(나)·(다)를 두 축의 평면 위에 놓으면, 흔한 오해가 어디서 생기는지 한눈에 보인다.

```
                    ② 결과 전달 방식: 비동기
                              ▲
        [블로킹 · 비동기]     │    [논블로킹 · 비동기]
        성립하지 않는 빈 칸   │    (다) 논블로킹 호출 + 완료 통지
        — 블로킹이면 결과를   │
        기다려 받으므로       │
        반드시 동기           │
        ("동기와 블로킹" 참고)│
  블로킹 ◀────────────────────┼───────────────────▶ 논블로킹
                              │        (① 호출 반환 방식)
                              │
        [블로킹 · 동기]       │    [논블로킹 · 동기]
        (가) 블로킹 읽기      │    (나) 논블로킹 호출 + 직접 확인
                              ▼
                    ② 결과 전달 방식: 동기
```

(가)→(나)는 가로 이동이다 — 호출 반환 방식만 바뀌었고, 결과를 챙기는 책임은 여전히 호출자에게 있다. (나)→(다)는 세로 이동이다 — 호출 모습은 그대로인데 결과 전달 방식이 바뀌었다. "논블로킹이면 비동기"라는 오해는 가로 이동 한 번으로 세로 이동까지 끝났다고 여기는 착각이며, 비동기 칸에 도달하려면 두 이동이 모두 일어나야 한다.

#### 다른 키워드와의 연결

* ①축 용어 자체의 정의와 스레드 관점은 "블로킹과 논블로킹"이 다루고, (가) 같은 블로킹 읽기가 현실에서 왜 생기는지는 "블로킹의 핵심 문제: 입출력"이 다룬다. (나)·(다)의 직접 확인과 완료 통지가 실제 입출력 호출에서 어떤 메커니즘과 코드로 구현되는지는 "논블로킹과 비동기 입출력" 몫이다.
* 같은 식의 짝 맞추기를 반대쪽에서 수행하는 논증("동기라고 해서 블로킹인가?")은 "동기와 블로킹"이 맡고, 두 질문의 분리를 일상 장면으로 굳혀 주는 것은 "피자 주문에 비유하기"다.

> * **기립박수를 받은 발표**: 2009년 11월 베를린 JSConf EU에서 라이언 달(Ryan Dahl)이 청중 150명 앞에서 Node.js를 발표했다. "블로킹 I/O가 기본값인 것 자체가 잘못"이라며 표준 라이브러리 전체를 논블로킹+콜백으로 설계한 런타임이었고, 이 발표는 해당 행사 최초의 기립박수를 받았으며 몇 달 만에 사용자가 수만 명으로 불어났다.
> * **윈도우가 25년 빨랐다**: 완료 통지형 비동기 I/O에서는 윈도우가 리눅스보다 사반세기 빨랐다. IOCP(I/O Completion Port)는 Windows NT 3.5(1994)부터 제공됐지만, 리눅스가 같은 완료 기반 모델(io\_uring)을 갖춘 것은 2019년이다. 그 25년 동안 리눅스 진영은 "완료됨"이 아니라 "준비됨"을 알려주는 epoll + 논블로킹 조합으로 버텼다.
> * **단일 스레드로 초당 10만 건**: Redis는 명령 처리 코어가 단일 스레드 이벤트 루프(논블로킹 다중화)인데도 인스턴스 하나로 초당 10만 건 이상의 요청을 처리한다. 네트워크 I/O 보조 스레드조차 2020년 Redis 6.0에서야 추가됐고 명령 실행은 지금도 단일 스레드다. "동시성 = 스레드 수"가 아님을 보여주는 산업계의 대표 사례다.

# 2.9 data, code, callback, closure, container, vm

### 코드와 데이터

#### 1) 개념 정의

코드(명령)와 데이터(값)는 메모리 안에서 보면 둘 다 똑같은 0과 1의 비트열일 뿐이며, 둘을 가르는 것은 그 비트를 "명령으로 실행할지, 값으로 읽을지"라는 해석의 차이뿐이다.

#### 2) 원리 설명

우리는 보통 "프로그램(코드)"과 "데이터"를 전혀 다른 것으로 느끼지만, 메모리 입장에서는 둘 다 그저 0과 1이 늘어선 비트열이다. \
컴퓨터는 모든 것을 비트로만 다루기 때문에, 메모리에 적힌 비트만 보고서는 그것이 명령인지 데이터인지 스스로 구분하지 못한다. \
실제로 명령어도 결국 숫자로 표현되며, 그래서 데이터와 똑같은 메모리에 나란히 저장될 수 있다.&#x20;

즉 같은 메모리, 같은 비트라는 토대 위에서 코드와 데이터가 공존한다. \
차이는 비트 자체가 아니라 그 비트를 "어떻게 읽느냐"에서 생긴다. \
CPU가 그 비트를 명령으로 가져와 실행하면 코드가 되고, 값으로 가져와 계산에 쓰면 데이터가 된다. 그래서 "코드도 데이터다"라는 말이 성립한다.

#### 3) 세부 메커니즘

같은 비트라도 결국 무엇이 되느냐는 "CPU의 어느 부분이, 어떤 방식으로 그 비트를 읽느냐"가 정한다. \
CPU 안에는 다음에 실행할 명령이 들어 있는 메모리 주소를 담아 두는 전용 레지스터, 즉 명령 포인터(프로그램 카운터, PC)가 있다. \
명령을 가져오는 단계에서 CPU는 이 명령 포인터가 가리키는 주소로 가서, 거기 있는 비트열을 "명령"으로 해석해 실행한다. \
명령 하나를 처리하고 나면 명령 포인터의 주소는 다음 명령 쪽으로 옮겨 가고, CPU는 같은 과정을 반복한다.&#x20;

반면 어떤 계산을 하려고 메모리의 값을 읽어 올 때는, 똑같은 방식으로 주소를 따라가 비트를 가져오지만 이번에는 그것을 "값(데이터)"으로 쓴다.&#x20;

정리하면, 비트가 놓인 곳(코드가 모인 영역인지, 값이 모인 영역인지)과 그 비트를 명령 포인터로 집어 오는지 값으로 집어 오는지에 따라 같은 비트가 명령도, 데이터도 된다. \
핵심은 코드 역시 메모리에 놓이는 순간 주소를 가진 하나의 데이터라는 점이다.

#### 4) 예시

**예시 1 — 같은 1바이트가 값으로도, 명령으로도** 메모리의 어느 한 칸(1바이트)에 비트 `01001000`이 들어 있다고 하자. 이 똑같은 비트열을 무엇으로 읽느냐에 따라 결과가 갈린다.

```
메모리의 1바이트:  01001000   (16진수 0x48)

[값(데이터)으로 읽으면]
  - 정수로 해석   → 72
  - 문자로 해석   → 'H'   (ASCII 72)

[명령(코드)으로 읽으면]
  - 명령 포인터가 이 주소를 가리켜 CPU가 가져가면,
    같은 비트열을 어떤 기계어 "명령"으로 해석해 실행하려 한다.
    (구체적으로 어떤 명령이 되는지는 CPU 종류마다 다름 — 확인 필요)
```

같은 0x48이 한쪽에서는 숫자 72/문자 'H'가 되고, 다른 쪽에서는 실행할 명령이 된다. 비트는 그대로인데 "해석"만 달라진 것이다.

**예시 2 — 메모리 위 코드 영역과 데이터 영역** 프로그램이 메모리에 올라가면, 실행할 명령들이 모인 영역과 값들이 모인 영역이 같은 메모리 주소 공간 안에 함께 자리 잡는다. \
둘 다 주소를 가진 비트열이라는 점은 같고, CPU가 어느 쪽을 명령 포인터로 집어 오느냐가 다를 뿐이다.

```
   주소        메모리 내용         CPU가 읽는 방식
  ---------------------------------------------------
   0x1000   [ 명령 비트열 ]  ← 명령 포인터(PC)가 여기를 가리키면 "명령"으로 실행
   0x1004   [ 명령 비트열 ]
   0x1008   [ 명령 비트열 ]
     ...
   0x4000   [ 값 비트열   ]  ← 계산에 필요할 때 "값(데이터)"으로 읽음
   0x4004   [ 값 비트열   ]
  ---------------------------------------------------
   → 코드도 0x1000 같은 "주소를 가진 데이터"라는 점은 값과 똑같다.
```



코드도 결국 주소를 가진 데이터이므로, 그 주소를 가리켜 코드를 지목할 수도 있고(→ 함수 포인터), 데이터처럼 변수에 담아 다른 곳으로 건네줄 수도 있다(→ 콜백).

> 💡 **TMI**
>
> * "코드도 데이터"라는 발상은 폰 노이만이 1945년 EDVAC 보고서 초안에서 정리한 프로그램 내장 방식의 핵심이다. 그 직전 세대인 ENIAC은 프로그램을 바꾸려면 케이블을 다시 꽂고 3000개에 달하는 스위치를 일일이 맞춰야 해 며칠이 걸렸는데, 1948년 함수 테이블을 일종의 프로그램 ROM으로 쓰는 방식으로 개조되면서 비로소 '저장된 프로그램'을 돌릴 수 있게 됐다.
> * 코드와 데이터를 한 메모리에 함께 두는 폰 노이만 구조와 달리, 명령용 메모리와 데이터용 메모리를 아예 분리한 설계를 하버드 구조라 부른다. 이 이름은 1944년 가동된 하버드 마크 I(하워드 에이킨)에서 유래했는데, 명령을 천공 테이프에, 데이터를 별도 장치에 따로 담아 둘을 동시에 읽을 수 있었다.
> * "코드도 결국 데이터"라는 성질은 보안 공격의 토대가 되기도 한다. 1988년 모리스 웜은 fingerd의 버퍼 오버플로를 악용해 약 6,000대(당시 인터넷의 약 10%)를 감염시켰고, 1996년 11월 Aleph One(엘리아스 레비)이 Phrack에 실은 "Smashing the Stack for Fun and Profit"은 데이터로 밀어 넣은 비트를 코드로 실행시키는 스택 버퍼 오버플로 공격을 처음으로 상세히 해설한 글로 꼽힌다.

### 변수

#### 1) 개념 정의

변수는 메모리의 특정 저장 공간(주소)에 사람이 붙인 이름표로, 그 공간에 든 데이터에 주소 숫자 대신 이름으로 접근하게 해 주는 추상화다.

#### 2) 원리 설명

메모리는 1바이트짜리 칸들이 줄지어 있고 각 칸마다 고유한 번호, 즉 주소가 매겨져 있다. \
데이터는 결국 이 주소 어딘가에 놓이는데, 사람이 `0x7ffe1c3a` 같은 16진수 주소를 직접 외워서 값을 넣고 빼는 것은 비현실적이다. \
그래서 우리는 특정 저장 공간에 `score`, `x` 같은 이름을 붙이고, 그 이름으로 데이터를 읽고 쓴다. \
이때 변수 이름은 "데이터가 사는 곳"을 가리키는 이름표이고, 실제 데이터가 어느 주소에 있는지는 시스템이 대신 관리한다.&#x20;

즉 변수의 본질은 "이름이 붙은 저장 공간"이며, 핵심 동작은 사람이 쓴 이름을 실제 메모리 주소로 바꿔 주는 이름→주소 매핑이다. \
덕분에 프로그래머는 주소가 실제로 어디든 신경 쓰지 않고 의미 있는 이름만으로 데이터를 다룰 수 있다.

#### 3) 세부 메커니즘

이름→주소 매핑이 실제로 자리 잡는 과정은 이렇다. \
컴파일러는 변수를 선언하면 그 이름을 특정 메모리 위치에 묶고(바인딩), 이후 코드에 나오는 변수 이름을 모두 그 위치를 읽고 쓰는 동작으로 번역한다. \
이때 변수의 타입은 두 가지를 결정한다.&#x20;

첫째는 그 공간이 차지하는 바이트 크기로, 예를 들어 흔한 환경에서 `char`는 1바이트, `int`는 보통 4바이트, `double`은 8바이트를 점유한다.&#x20;

둘째는 그 바이트들을 어떻게 해석해 읽을지로, 같은 4바이트라도 타입이 `int`냐 `float`냐에 따라 정수로 읽을지 실수로 읽을지가 달라진다.&#x20;

그래서 변수 하나는 "어느 주소에서 시작하는가 + 몇 바이트인가 + 어떤 방식으로 읽는가"가 한 묶음으로 정해진 저장 공간이다. \
자리 잡는 영역도 종류에 따라 갈린다. \
함수 안에서 선언한 지역 변수는 주로 스택(stack) 영역에 생겼다가 함수가 끝나면 사라지고, 전역 변수는 컴파일 시점에 데이터 영역의 고정된 주소에 자리 잡아 프로그램이 도는 동안 위치가 변하지 않는다.

#### 4) 예시

`int x = 10;` 한 줄을 보면, 이름 `x`가 메모리의 어떤 4바이트 칸 하나에 묶이고 그 안에 정수 `10`이 저장된다. 타입이 `int`이므로 크기는 4바이트, 해석 방식은 "정수"로 고정된다.

```
주소(예시)   메모리 칸                이름표
0x0012FF28  ┌──────────────┐
            │  10 (4바이트)  │  ←──  x
0x0012FF2C  └──────────────┘
```

이 변수가 실제로 어느 주소에 놓였는지는 주소 연산자 `&`로 확인할 수 있다.

```c
int x = 10;
printf("%d\n", x);    // 10      → 이름 x로 "값"에 접근
printf("%p\n", &x);   // 0012FF28 → 이름 x가 가리키는 "저장 공간의 주소"
```

여기서 `x`라고 쓰면 그 칸의 값(10)을, `&x`라고 쓰면 그 칸의 주소(0x0012FF28)를 얻는다. \
같은 이름표가 평소에는 "데이터"를, 필요할 때는 "데이터가 사는 곳의 주소"를 내어 주는 셈이다. \
(출력되는 주소 숫자는 실행 환경마다 달라진다.)



일반 변수는 "값이 곧 데이터"인 이름 붙은 저장 공간인데, 이 개념을 한 단계 비틀어 "값이 곧 다른 변수의 주소"인 저장 공간을 만들면 그것이 포인터다.&#x20;

즉 포인터는 "주소를 값으로 담는 특수한 변수"이며, 자세한 동작은 다음 소주제 \[포인터]에서 다룬다.

> 💡 **TMI**
>
> * "변수는 이름 붙은 메모리 주소"라는 설명에는 함정이 있다. 컴파일러의 레지스터 할당 최적화로 자주 쓰이는 변수는 아예 CPU 레지스터에만 머물며 메모리 주소를 단 한 번도 갖지 않을 수 있고, 이 때문에 디버거로 그 변수를 들여다보면 "optimized out"으로 표시되어 값을 못 보는 일이 흔하다.
> * 메모리 정렬(alignment) 때문에 구조체의 실제 크기는 멤버 크기의 단순 합보다 커지곤 한다. 예컨대 `char`(1바이트)와 `int`(4바이트)를 한 구조체에 담으면 컴파일러가 빈 패딩 바이트를 끼워 넣어 `sizeof`가 5가 아니라 8로 나오는데, 멤버 선언 순서만 바꿔도 패딩이 줄어 크기가 달라지는 것이 그 증거다.

### 포인터

#### 1) 개념 정의

포인터는 값이 다른 데이터의 _메모리 주&#xC18C;_&#xC778; 변수다.

#### 2) 원리 설명

일반 변수가 정수나 문자 같은 데이터 자체를 담는다면, 포인터는 "데이터가 들어 있는 자리의 번지"를 담는다.&#x20;

즉 포인터도 변수의 일종이지만, 그 값이 다른 변수가 사는 곳의 주소라는 점이 다르다. \
메모리는 바이트마다 고유한 번호(주소)가 매겨진 거대한 사물함과 같고, 포인터는 그중 한 칸의 번호를 적어 둔 쪽지에 비유할 수 있다. \
그래서 포인터 하나만 들고 있으면, 그 주소가 가리키는 자리로 찾아가 거기에 있는 실제 데이터를 읽거나 바꿀 수 있다. \
주소를 따라가 그 자리의 데이터에 접근하는 동작을 역참조(dereference)라고 부른다. \
이렇게 포인터는 값을 복사해서 들고 다니는 대신, 원본이 있는 곳을 직접 가리켜 조작하게 해 준다.

#### 3) 세부 메커니즘

한 단계 더 들어가면, 포인터를 다루는 두 연산자와 두 종류의 포인터를 구분해야 한다.

데이터 포인터에서는 두 연산자가 짝을 이룬다. \
주소 연산자 `&`는 변수 앞에 붙어 그 변수가 자리 잡은 주소를 꺼내 주고, 역참조 연산자 `*`는 포인터 앞에 붙어 그 주소가 가리키는 자리의 값에 닿게 해 준다. \
선언은 `int *p;` 형태이며, 여기서 `int *`는 "int가 들어 있는 자리를 가리키는 포인터"라는 뜻이다. \
`p = &x;`로 주소를 담고, `*p`로 그 자리의 값을 읽거나 `*p = 20;`처럼 그 자리에 값을 새로 쓸 수 있다.

함수 포인터는 가리키는 대상이 데이터가 아니라 _코&#xB4DC;_&#xB2E4;. \
함수도 컴파일되면 메모리에 올라가 시작 주소를 가지므로(코드 역시 메모리에 놓인 데이터라는 점이 근거다), 그 주소를 변수에 담을 수 있다.&#x20;

핵심은 함수 이름 자체가 곧 그 함수의 주소라는 것이다. \
그래서 `&` 없이 함수 이름만 적으면 주소가 대입되고(`fp = func;`), 괄호를 붙이면 호출이 된다(`func()`). \
선언은 `반환형 (*이름)(매개변수)` 꼴인데, 예를 들어 반환값과 매개변수가 없는 함수를 가리키는 포인터는 `void (*fp)() = func;`처럼 선언하면서 동시에 주소를 담을 수 있다. \
이때 이름을 감싸는 괄호 `(*fp)`는 반드시 필요하다. 호출은 `fp()`로도, 역참조를 명시한 `(*fp)()`로도 가능하며 결과는 같다. \
단, 함수 포인터와 대상 함수는 반환형·매개변수의 종류와 개수가 맞아야 한다.

#### 4) 예시

예① 데이터 포인터 — `&`로 주소를 담고 `*`로 그 자리의 값을 바꾼다.

```c
#include <stdio.h>

int main(void) {
    int x = 10;
    int *p = &x;   // p에 x의 주소를 담는다
    *p = 20;       // p가 가리키는 자리(=x)에 20을 쓴다
    printf("%d\n", x);  // 20
    return 0;
}
```

`p`를 통해 값을 썼을 뿐인데 `x`가 10에서 20으로 바뀐다. 포인터가 원본이 있는 곳을 직접 가리켜 조작했기 때문이다. 메모리를 그림으로 보면 다음과 같다(주소는 예시값이다).

| 변수  | 주소      | 저장된 값               |
| --- | ------- | ------------------- |
| `x` | `0x100` | `10` → `20`         |
| `p` | `0x200` | `0x100` (= `x`의 주소) |

`p`의 값은 `0x100`이고, `*p`는 그 주소가 가리키는 자리의 값을 의미하므로 `x`와 같다.

예② 함수 포인터 — 함수의 주소를 변수에 담아 그 변수로 호출한다.

```c
#include <stdio.h>

int sum(int a, int b) {
    return a + b;
}

int main(void) {
    int (*fp)(int, int) = sum;     // 함수 이름 = 주소 (& 불필요)
    printf("%d\n", fp(10, 13));    // fp() 호출 → 23
    printf("%d\n", (*fp)(10, 13)); // (*fp)() 호출 → 23 (결과 동일)
    return 0;
}
```

`fp`에는 `sum`의 시작 주소가 담기고, `fp(10, 13)`은 그 주소로 찾아가 함수를 실행해 `23`을 돌려준다. `fp()`와 `(*fp)()`는 표기만 다를 뿐 같은 호출이다.



함수 포인터는 "어떤 함수를 실행할지"를 값처럼 변수에 담아 넘길 수 있게 하므로, 콜백 함수와 클로저가 성립하는 토대가 된다.&#x20;

> 💡 **TMI**
>
> * 포인터의 크기는 가리키는 대상이 `char`든 거대한 구조체든 상관없이 일정하다. 포인터가 담는 것은 데이터가 아니라 '주소'이기 때문이며, 그래서 64비트 시스템에서는 어떤 타입을 가리키든 포인터 하나가 보통 8바이트를 차지한다.
> * 흔히 널 포인터를 "주소 0"이라고 외우지만, C 표준은 널 포인터의 실제 비트 패턴이 전부 0이라고 보장하지 않는다. 표준은 "정수 상수 0을 포인터에 대입하면 널 포인터가 된다"는 의미만 규정할 뿐, 그 내부 표현은 플랫폼이 정하도록 열어 두었다(다만 현실의 거의 모든 주류 환경은 0으로 구현한다).

### 콜백 함수

#### 1) 개념 정의

콜백 함수는 내가 직접 호출하지 않고, 어떤 일이 끝났을 때(또는 특정 시점이 되면) 상대가 대신 불러 주도록 미리 인자로 건네 두는 함수다.

#### 2) 원리 설명

보통의 함수 호출은 "내가 함수를 부른다"는 한 방향이다. \
콜백은 이 방향을 뒤집는다. \
내가 라이브러리에게 함수를 하나 넘겨주면서 "이걸 가지고 있다가 적절한 때가 되면 네가 불러 줘"라고 부탁하면, 부르는 주체가 나에서 라이브러리로 바뀐다 — 이렇게 부르는 주도권이 나에서 상대에게 넘어가는 것이 콜백의 핵심이다. \
라이브러리나 프레임워크가 전체 흐름(메인 루프, 정렬 알고리즘, 이벤트 처리)을 쥐고 있고, 나는 그 흐름의 빈칸에 끼워 넣을 동작만 함수로 제공하는 셈이다. \
그래서 같은 라이브러리 코드를 한 줄도 고치지 않고, 넘기는 콜백만 바꿔서 동작을 갈아끼울 수 있다.

#### 3) 세부 메커니즘

콜백이 도는 흐름은 보통 세 단계다. \
**등록**(콜백을 함수 포인터로 넘김) → **보관**(상대가 그 함수를 내부 변수에 들고 있음) → **호출**(정해진 사건이나 작업 완료 시점에 상대가 그 함수를 실행).&#x20;

여기서 "언제 불리느냐"에 따라 두 갈래로 나뉜다.&#x20;

**동기 콜백**은 넘긴 즉시, 같은 실행 흐름 안에서 불린다. 예를 들어 정렬 함수는 원소들의 순서를 정해야 할 때마다 그 자리에서 비교 콜백을 부르고, 콜백이 끝나야 정렬이 다음으로 넘어간다(콜백이 끝날 때까지 기다림).&#x20;

**비동기 콜백**은 일단 등록만 해 두고 흐름은 그냥 진행되다가, 한참 뒤 어떤 일(파일 다 읽음, 버튼 클릭, 타이머 만료)이 벌어진 그 시점에 불린다.

#### 4) 예시

가장 직관적인 C 예시는 표준 라이브러리 `qsort`에 비교 함수를 콜백으로 넘기는 경우다. \
`qsort`는 정렬 알고리즘을 이미 다 갖고 있지만, "두 값 중 뭐가 앞이냐"는 판단은 모른다. \
그 판단을 내가 함수로 만들어 넘기면, `qsort`가 정렬 도중 비교가 필요할 때마다 내 함수를 대신 불러 준다.

```c
#include <stdio.h>
#include <stdlib.h>

/* qsort가 "비교가 필요할 때" 대신 불러 줄 콜백 */
int comp(const void *a, const void *b) {
    return (*(int *)a - *(int *)b);   /* 오름차순 */
}

int main(void) {
    int arr[] = {5, 2, 3, 1, 4};
    int n = sizeof(arr) / sizeof(arr[0]);

    /* comp를 qsort에 "넘겨서 등록" — 내가 comp를 직접 부르지 않는다 */
    qsort(arr, n, sizeof(arr[0]), comp);

    for (int i = 0; i < n; i++)
        printf("%d ", arr[i]);
    return 0;
}
/* 출력: 1 2 3 4 5 */
```

여기서 핵심은 내 코드 어디에도 `comp(...)`라고 직접 부르는 곳이 없다는 점이다. \
`comp`를 `qsort`에 넘겨만 두면, 부르는 일은 `qsort`가 맡는다. 비교 기준을 내림차순으로 바꾸고 싶으면 `qsort`가 아니라 콜백만 고치면 된다.

"작업이 끝나면 불러 줘" 식의 등록 흐름은 의사코드로 보면 더 분명하다.

```
on_done(결과):                 # 나중에 불릴 콜백
    print("작업 끝남:", 결과)

작업_시작(데이터, on_done)      # 콜백을 "넘겨서 등록"만 함
# ... 흐름은 멈추지 않고 계속 진행 ...
# (작업이 끝나는 그 순간) 상대가 on_done(결과)를 대신 호출
```

내가 `on_done`을 부르는 코드는 없고, 작업이 끝난 시점에 상대가 불러 준다 — 이것이 콜백의 전형적인 모습이다.



콜백은 "함수를 값처럼 넘긴다"는 토대 위에 선다. \
C에서 그 전달 수단이 **함수 포인터**이며(넘기는 문법 자체는 포인터 소주제에서 다룬다), 콜백은 그 포인터를 "나중에 불릴 함수를 건네는 용도"로 쓰는 패턴이다. \
또한 콜백이 불릴 때 자기가 등록되던 당시의 상태(맥락)를 기억해야 하는 경우가 생기는데, 그때 **클로저**로 이어진다&#x20;

즉 콜백은 "넘겨서 나중에 불리는 함수"이고, 거기에 상태를 함께 묶어야 할 때 클로저가 쓰인다.

> 💡 **TMI**
>
> * 콜백이 구현하는 "내가 부르지 말고, 준비되면 네가 불러라"라는 흐름의 역전을 형식 용어로 '제어의 역전(Inversion of Control)'이라 하고, 흔히 "Don't call us, we'll call you"라는 헐리우드 격언에 빗댄다. 다만 이 격언의 출처는 분명치 않은 통속적 비유이고, 학술 용어로서의 'Inversion of Control'은 존슨과 푸트의 1988년 논문 "Designing Reusable Classes"에서 정리된 것으로 거슬러 올라간다.
> * 비동기 콜백을 중첩하면 코드가 오른쪽으로 끝없이 들여쓰기되는 '콜백 지옥(pyramid of doom)'에 빠진다. 자바스크립트는 이를 풀려고 2015년(ES2015)에 Promise를, 그 2년 뒤 2017년(ES2017)에 async/await를 도입했는데, async/await는 사실상 Promise 위에 입힌 문법 설탕이라 내부적으로는 여전히 콜백 기반으로 돌아간다.
> * "콜백을 같은 흐름에서 바로 부르면 동기, 나중에 사건이 나면 부르면 비동기"라는 구분은 사람을 헷갈리게 한다. 표준 C 라이브러리의 `qsort`에 넘기는 비교 함수는 콜백이지만 정렬 도중 그 자리에서 즉시 불리는 완전한 동기 콜백이라, '콜백 = 비동기'라는 통념이 항상 맞지는 않음을 보여 준다.

### 클로저

#### 1) 개념 정의

클로저(closure)는 **함수 그 자체**와, **그 함수가 정의될 때 주변 맥락에서 포획(capture)한 변수 환경(상태)** 을 하나로 묶은 것이다. \
한마디로 "함수 + 포획한 환경"의 묶음이다.

#### 2) 원리 설명

보통의 함수는 호출될 때 받은 인자와 자기 안에서 만든 지역 변수만으로 동작한다.&#x20;

그런데 어떤 함수는 **자기 바깥(자신이 정의된 맥락)에 있던 변수**를 나중에 호출될 때까지 기억해야 할 때가 있다. \
예를 들어 "기준값 10보다 큰지 검사하는 함수"를 만들고 싶은데, 이 `10`이 함수 바깥에서 정해진 값이라면, 함수는 그 값을 어딘가에 붙들고 있어야 한다.

저수준 관점에서 보면 함수 포인터는 결국 **코드의 주소 하나**일 뿐이다. \
주소는 같은 함수면 늘 같은 값이라 그 자체로는 "어떤 상태에서 만들어졌는가"를 담지 못한다.&#x20;

즉 함수 포인터만으로는 "함수가 기억해야 할 상태"를 함께 들고 다닐 수 없다. \
클로저는 바로 이 한계를 메운다. \
**함수(코드)에 그 함수가 포획한 상태(데이터)를 짝지어** 함께 들고 다니게 함으로써, 정의된 맥락을 벗어난 시점·장소에서 호출되어도 그때 포획해 둔 값에 접근할 수 있게 한다.

#### 3) 세부 메커니즘

한 단계 더 들어가 보면, 클로저는 **(코드 주소 + 포획한 데이터)의 한 쌍**으로 표현된다. \
함수가 가리키는 코드 위치와, 그 함수가 바깥에서 붙든 변수들의 값(또는 그 변수에 대한 참조)을 함께 보관하는 묶음인 것이다. \
이 포획된 데이터는 함수와 함께 어딘가에 보관되어, **그 클로저가 살아 있고 호출 가능한 동안 계속 유지**된다. \
그래서 클로저를 호출하면 코드는 "지금 이 자리의 변수"가 아니라 "포획해 둔 그 변수"를 보고 동작한다.

C/C++처럼 클로저가 언어 기본 문법이 아닌 환경에서, 이 한 쌍을 손으로 만들어 표현하는 가장 흔한 방식이 **함수 포인터와 그 함수가 쓸 상태(데이터)를 함께 묶어 넘기는 것**이다. \
보통 "코드 = 함수 포인터", "포획한 데이터 = 컨텍스트(사용자 데이터)"로 짝지어 다닌다. \
이 둘을 하나의 구조체로 묶으면, 바로 (코드 주소 + 캡처된 데이터)라는 클로저의 표현을 직접 손으로 구현한 셈이 된다.

#### 4) 예시

"코드와 상태가 함께 다닌다"가 보이도록, C 스타일 의사코드로 (함수 포인터 + 포획 데이터) 한 쌍을 구조체로 묶어 본다.

```c
// (코드 주소 + 포획한 데이터)의 한 쌍 = 손으로 만든 클로저
struct closure {
    int (*code)(void *ctx, int x);  // 코드: 함수 포인터
    void *ctx;                      // 포획한 상태: 컨텍스트(사용자 데이터)
};

// "기준값보다 큰가?"를 검사하는 함수.
// 기준값은 인자가 아니라 포획한 ctx에서 꺼내 쓴다.
int greater_than(void *ctx, int x) {
    int threshold = *(int *)ctx;    // ctx를 원래 타입으로 되돌려 포획값 사용
    return x > threshold;
}

int main(void) {
    int threshold = 10;             // 함수 바깥 맥락에 있는 상태

    // 코드와 상태를 한 쌍으로 묶는다 → 이 묶음 자체가 클로저
    struct closure is_big = { greater_than, &threshold };

    // 나중에, 다른 곳에서 호출해도 포획한 threshold(=10)를 기억한다
    is_big.code(is_big.ctx, 7);     // 7 > 10  → 0 (거짓)
    is_big.code(is_big.ctx, 42);    // 42 > 10 → 1 (참)
    return 0;
}
```

여기서 핵심은 문법이 아니라 구조다. \
`greater_than`이라는 코드와 `threshold`라는 포획한 상태가 `struct closure`로 **함께 묶여 다니기** 때문에, 이 묶음을 어디로 넘기든 호출 시점에 `10`이라는 값을 기억해 검사할 수 있다. \
함수 포인터 `greater_than`만 넘겼다면 기준값을 들고 다닐 수 없어, 매번 따로 전달하거나 전역 변수에 의존해야 했을 것이다.



* **콜백과의 관계**: 콜백은 "나중에 불리도록 넘겨두는 함수"라는 패턴이다. \
  그 콜백이 **자신이 만들어진 맥락의 변수를 기억해야 할 때**, 함수만 넘겨서는 부족하고 그 상태까지 함께 묶어 넘겨야 한다 — 이때 콜백은 클로저가 된다(위 예시에서 컨텍스트를 함께 넘기는 형태). \
  즉 "상태가 필요한 콜백 = 클로저".
* **함수 포인터와의 차이**: 함수 포인터는 코드 주소 하나일 뿐이고, 클로저는 거기에 **포획한 상태(데이터)** 가 더해진 것이다. "함수 포인터 + 상태"라고 보면 된다.

### 컨테이너

#### 1) 개념 정의

컨테이너는 호스트 운영체제의 커널을 그대로 공유하면서, 그 위에서 프로세스 단위로 격리된 독립 실행 환경을 만드는 기술이다.

#### 2) 원리 설명

컨테이너의 출발점은 "운영체제를 새로 띄우지 않는다"는 것이다. 별도의 커널을 부팅하는 대신, 컨테이너 안에서 도는 것은 결국 호스트의 리눅스 커널 위에서 실행되는 평범한 프로세스다.&#x20;

다만 이 프로세스에게는 자기만의 세계가 보이도록 시야를 좁혀 준다.&#x20;

즉 프로세스 목록, 네트워크, 파일시스템 같은 자원을 들여다볼 때, 호스트 전체가 아니라 자기 몫만 보이게 커널이 따로 떼어 보여 준다. \
그래서 컨테이너 안의 프로그램은 마치 자기 혼자 쓰는 독립된 컴퓨터에 들어와 있다고 착각하지만, 실제로는 같은 커널을 다른 프로세스들과 나눠 쓰고 있을 뿐이다. \
운영체제를 통째로 새로 띄우는 과정이 없으므로 시작이 빠르고 메모리 부담도 작다.

#### 3) 세부 메커니즘

이 "착각"을 만드는 리눅스 커널의 두 장치는 역할이 뚜렷이 다르다.

* **namespace(네임스페이스) — 무엇을 볼 수 있는가(격리)**: 프로세스가 보는 자원의 범위를 따로 떼어 낸다. 같은 커널 위에 있어도, 한 네임스페이스 안의 프로세스는 자기 네임스페이스에 속한 것만 보고 바깥은 보지 못한다. 대표적으로 프로세스 번호(PID), 네트워크(IP 주소·포트), 마운트된 파일시스템 등을 각각 분리한다.
* **cgroup(control group) — 얼마나 쓸 수 있는가(상한)**: 시야를 나누는 것만으로는 한 컨테이너가 호스트의 CPU와 메모리를 다 먹어 버릴 수 있다. cgroup은 프로세스 묶음이 쓸 수 있는 자원의 상한(CPU 시간, 메모리 양, 디스크 I/O 등)을 정해 제한하고, 사용량을 집계한다.

정리하면 namespace는 "무엇을 보는가"를, cgroup은 "얼마나 쓰는가"를 책임진다. \
이 둘이 합쳐져야 비로소 독립된 상자처럼 동작한다.

#### 4) 예시

한 호스트(하나의 커널) 위에서 컨테이너 두 개를 동시에 띄운 모습을 그려 보면 원리가 분명해진다. \
각 컨테이너는 자기만의 PID 네임스페이스를 가지므로, 그 안에서 처음 뜬 프로세스가 저마다 1번(PID 1)이 된다. \
호스트에서 보면 둘 다 그냥 평범한 프로세스이고 실제 PID는 따로 있지만, 컨테이너 내부에서는 서로의 존재를 모른 채 각자 "내가 1번"이라고 여긴다.

```
        [컨테이너 A]              [컨테이너 B]
   PID 1: app_a               PID 1: app_b
   (자기 네트워크·             (자기 네트워크·
    파일시스템만 보임)          파일시스템만 보임)
   ─────────────┐            ┌─────────────
                │            │
        ┌───────┴────────────┴───────┐
        │   하나의 호스트 리눅스 커널    │   ← 공유
        └────────────────────────────┘
              호스트 하드웨어 (CPU/메모리)
```

같은 커널을 공유하는 여러 격리 상자, 각 상자가 CPU·메모리 상한(cgroup)을 가진 채 도는 그림이 컨테이너의 본질이다.



다음 소주제인 가상 머신은 격리 방식이 한 단계 더 무겁다. \
컨테이너가 커널을 공유한 채 프로세스만 격리하는 데 비해, 가상 머신은 운영체제 자체를 따로 띄워 격리한다. \
또한 이 절은 코드와 데이터에서 출발해 변수·포인터·콜백·클로저로 "프로그램이 무엇으로 이루어지는가"를 본 뒤, 컨테이너와 가상 머신에서 "그 프로그램을 어디서, 어떤 격리 환경에서 실행하느냐"로 시야가 넓어지는 전환점이다.

>
> * 컨테이너를 대중화한 Docker는 2013년 3월 15일 산타클라라에서 열린 PyCon의 라이트닝 토크에서 처음 공개됐다. 만든 이 솔로몬 하익스는 작은 회의실에 30명쯤 올 거라 예상했지만 수백 명이 몰렸고, 당시 Docker는 자체 격리 기술이 아니라 LXC를 기본 실행 환경으로 빌려 쓰고 있었다.

### 가상 머신

#### 1) 개념 정의

가상 머신(VM)은 하이퍼바이저가 물리 하드웨어(CPU·메모리·디스크)를 가상화해, 그 위에 완전한 게스트 OS를 통째로 올려 돌리는 '소프트웨어로 흉내 낸 컴퓨터'다.

#### 2) 원리 설명

물리 컴퓨터는 보통 OS 하나만 올려 쓰지만, 가상 머신은 한 대의 물리 머신에서 서로 다른 OS의 여러 '가짜 컴퓨터'를 동시에 흉내 내는 것이 목표다. \
이를 가능하게 하는 핵심 부품이 하이퍼바이저(가상 머신 모니터, VMM)로, 물리 하드웨어와 게스트 OS 사이에 끼어드는 중간 계층이다. \
하이퍼바이저는 실제 CPU·메모리·디스크를 잘게 나눠 각 가상 머신마다 '가상 CPU·가상 메모리·가상 디스크'를 만들어 배정한다. \
그러면 그 위에 리눅스든 윈도우든 완전한 OS 한 벌(커널까지 포함)이 통째로 올라가 돌아간다.&#x20;

즉 가상 머신 안에서 보면 부팅부터 커널, 그 위 프로그램까지 진짜 컴퓨터를 켰을 때와 똑같은 풀스택이 그대로 존재한다. \
덕분에 물리 서버 1대 안에 성격이 다른 OS와 환경을 통째로 분리해 담을 수 있다.

#### 3) 세부 메커니즘

한 단계 더 들어가면, 게스트 OS는 자신이 진짜 하드웨어 위에서 돌고 있다고 '믿는다'는 점이 핵심이다. \
게스트 OS가 하드웨어를 직접 조작하려고 명령을 내리면, 하이퍼바이저가 그 명령을 가로채(intercept) 실제 물리 자원에 대응(매핑)시켜 대신 처리해 준다. \
이런 가로채기·중재 덕분에 여러 게스트가 같은 물리 하드웨어를 서로 충돌 없이 안전하게 나눠 쓸 수 있다. \
하이퍼바이저는 설치 위치에 따라 두 갈래로 나뉜다.&#x20;

하나는 물리 하드웨어 위에 곧바로 하이퍼바이저를 깔고 그 위에 가상 머신을 올리는 방식(베어메탈형), \
다른 하나는 이미 깔린 호스트 OS 위에 하이퍼바이저를 하나의 프로그램처럼 설치하고 그 위에 가상 머신을 올리는 방식(호스트형)이다.&#x20;

베어메탈형은 OS 계층을 거치지 않아 자원 효율이 좋고, 호스트형은 평소 쓰던 OS 위에 손쉽게 얹는다는 차이가 있다(세부 성능·보안 비교는 확인 필요).

#### 4) 예시

예① 물리 서버 1대에 OS를 통째로 얹은 가상 머신 두 개를 동시에 돌리는 그림. 각 가상 머신은 자기만의 게스트 OS 한 벌을 통째로 갖고, 하이퍼바이저가 그 아래에서 물리 자원을 나눠 준다.

```
            가상 머신 A                  가상 머신 B
        ┌────────────────────┐   ┌────────────────────┐
        │   앱 (웹 서버)       │   │   앱 (DB)           │
        │ 게스트 OS: 리눅스    │   │ 게스트 OS: 윈도우   │  ← OS를 통째로 얹음
        │ 가상 CPU/메모리/디스크│   │ 가상 CPU/메모리/디스크│
        └────────────────────┘   └────────────────────┘
        ────────────────────────────────────────────────
                      하이퍼바이저 (VMM)                   ← 물리 자원을 분배·중재
        ────────────────────────────────────────────────
                  물리 하드웨어 (CPU·메모리·디스크)
```

예② 컨테이너 vs 가상 머신 비교 표 (이 절의 종합 정리). 컨테이너 쪽은 대조를 위한 요약일 뿐이며, 그 내부 원리는 앞 소주제에서 다뤘다.

| 비교 항목   | 컨테이너                     | 가상 머신                     |
| ------- | ------------------------ | ------------------------- |
| 격리 수준   | 프로세스 수준 격리(상대적으로 약함)     | 게스트 OS 단위 완전 격리(상대적으로 강함) |
| OS      | 호스트 커널 공유 → 별도 게스트 OS 없음 | 게스트 OS 한 벌을 통째로 포함        |
| 무게(용량)  | 가벼움(수십 MB\~수백 MB 수준)     | 무거움(수 GB 수준)              |
| 부팅 속도   | OS 부팅 없이 바로 실행(초 단위)     | 게스트 OS를 부팅해야 함(상대적으로 느림)  |
| 자원 오버헤드 | 낮음(거의 네이티브에 가까움)         | 높음(게스트 OS 실행에 자원 추가 소모)   |



컨테이너가 '호스트 커널을 공유하면서 프로세스만 격리'하는 가벼운 방식이라면, \
가상 머신은 '하이퍼바이저로 하드웨어 자체를 가상화하고 게스트 OS를 통째로 올리는' 무겁지만 강하게 격리된 방식이다.&#x20;

둘의 갈림은 결국 "OS를 공유하느냐(컨테이너), 통째로 따로 두느냐(가상 머신)"로 요약된다.&#x20;

> 💡 **TMI**
>
> * 컨테이너의 가벼움과 가상 머신의 강한 격리를 둘 다 얻으려고, 컨테이너를 초경량 VM 안에 가두는 구성이 실무에서 쓰인다. 대표적으로 AWS가 2018년 공개한 Firecracker는 그래픽·USB·BIOS 같은 불필요한 에뮬레이션을 걷어 내 마이크로VM을 약 125밀리초 만에 부팅하고 VM당 메모리 오버헤드가 5MiB 미만이며, AWS Lambda와 Fargate가 이 위에서 함수와 컨테이너를 격리해 돌린다.

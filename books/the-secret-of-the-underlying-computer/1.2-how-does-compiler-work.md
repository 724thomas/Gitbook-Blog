# 1.2 How does Compiler work?

## 1.2 컴파일러는 어떻게 작동하는 것일까?

***

### 1. 컴파일러

> &#x20;1.2.1 컴파일러는 그저 일반적인 프로그램일 뿐, 대단하지 않다

#### 개념 정의

컴파일러는 소스 텍스트를 입력받아 타깃 코드(IR 또는 기계어)를 출력하는, 데이터 변환 파이프라인으로 구성된 평범한 프로그램이다.

#### 원리 설명

컴파일러는 문자열을 다른 표현 형식으로 점진적으로 바꿔 나가는 일련의 함수 합성이다. \
원시 코드는 한 번에 기계어로 번역되지 않고, 각 단계마다 더 다루기 쉬운 자료구조로 변환되어 다음 단계로 넘어간다. \
이렇게 단계를 나누는 이유는&#x20;

* (a) 각 단계의 책임을 단순화하고,&#x20;
* (b) 프론트엔드(언어별)와 백엔드(타깃 머신별)를 분리해 재사용성을 확보하기 위해서다.&#x20;

#### 세부 메커니즘

함수 시그니처로 추상화하면 다음과 같다.

```
Compiler : SourceText -> TargetCode
```

내부를 펼치면 각 단계가 자료구조 변환 함수의 합성이다.

```
lex    : SourceText      -> [Token]
parse  : [Token]         -> AST
sema   : AST             -> AnnotatedAST    (의미 분석/타입 체크)
irgen  : AnnotatedAST    -> IR
opt    : IR              -> IR              (미들엔드 최적화)
codegen: IR              -> TargetCode
```

책임 분담:

* **프론트엔드**: `lex → parse → sema`. 언어 문법에 종속적이며, AST/타입 정보를 만들어 낸다.
* **미들엔드**: IR 수준에서의 언어·머신 중립 최적화 (상수 폴딩, 죽은 코드 제거, 인라이닝 등).
* **백엔드**: 명령어 선택, 레지스터 할당, 명령어 스케줄링, 어셈블리/기계어 출력.

각 단계는 입력 타입과 출력 타입이 다를 뿐 "일반 함수"이다.



이 파이프라인 골격은 1.2.2(어휘 분석)부터 1.2.6(코드 생성)까지의 각 절이 다루는 단계들이며, 1.2.2는 그중 첫 단계인 `lex` 함수를 확대한 것이다.

### 2. 어휘 분석 (Lexical Analysis, Lexing)

> 1.2.2 각각의 토큰 추출하기

#### 개념 정의

어휘 분석은 소스 텍스트라는 평탄한 문자 스트림을, 의미 단위로 묶인 토큰 스트림으로 잘라 분류하는 컴파일러의 첫 단계이다.

#### 원리 설명

파서가 직접 문자(`i`, `n`, `t`, , `a`, …)를 다루게 하면, 모든 규칙이 "공백 건너뛰기 + 글자 모으기"부터 시작해야 하므로 매우 복잡해진다. \
그래서 컴파일러는 의미 있는 최소 단위, 즉 **토큰**(키워드 `int`, 식별자 `a`, 연산자 `=` 등)으로 미리 묶어 파서에게 넘긴다. \
어휘 분석기(lexer/scanner)는 입력을 왼쪽에서 오른쪽으로 한 글자씩 읽으며, 현재까지의 문자열이 어떤 토큰 패턴에 부합하는지를 판별한다. \
이 단계는 결정적이고 지역적이라서 한 번 훑는 것만으로 끝낼 수 있고, 이후 단계인 구문 분석의 입력 알파벳 자체를 바꿔 놓는다.

#### 예시

**(1) 토큰 분해 결과**

```c
int sum = a + b * 10;
```

위 한 줄을 lexer에 통과시키면 다음과 같은 토큰 리스트가 만들어진다.

```
[KEYWORD(int), IDENT(sum), OP(=), IDENT(a), OP(+), IDENT(b), OP(*), NUMBER(10), SEMI]
```

공백은 토큰 경계만 표시한 뒤 버려졌고, `10`은 문자 `'1'`, `'0'`이 아니라 `NUMBER` 토큰 한 덩어리로 묶였다.



어휘 분석의 출력인 토큰 스트림은 그대로 다음 단계인 **구문 분석(parsing)** 의 입력 알파벳이 된다. 즉 lexer는 파서가 "글자" 대신 "단어" 단위로 문법을 다룰 수 있게 추상화 수준을 한 단계 올려 주는 역할을 한다.

### 3. 구문 분석 (Syntax Analysis, Parsing)

> &#x20;1.2.3 토큰이 표현하고자 하는 의미

#### 개념 정의

구문 분석은 어휘 분석이 만든 **토큰 스트림**을 입력받아, 언어의 \*\*문법 규칙(Grammar)\*\*에 따라 토큰들의 계층 관계를 분석하고 이를 **트리 형태(파스 트리 또는 AST)**&#xB85C; 조립하는 컴파일러의 두 번째 단계다.

#### 원리 설명

어휘 분석은 문자열을 "단어 단위(토큰)"로 잘라줄 뿐, 그 단어들이 문법적으로 올바르게 배열되었는지, 그리고 어떤 구조(예: `a + b * 10`에서 `*`가 `+`보다 먼저 묶여야 함)를 이루는지는 알 수 없다. \
구문 분석기(파서)는 미리 정의된 문법 규칙을 길잡이 삼아 토큰을 하나씩 소비하면서, 어떤 토큰들이 어떤 비단말(non-terminal) 규칙으로 묶이는지 판정한다. \
그 결과 연산자 우선순위, 결합 법칙, 중첩 구조 같은 계층 정보가 트리 형태로 명시적으로 드러난다.



**파스 트리(CST) vs AST**

* **파스 트리(Concrete Syntax Tree, CST)**: 문법 규칙을 한 단계도 빠뜨리지 않고 그대로 보존. 모든 비단말(`expr`, `term`, `factor`)이 내부 노드로, 모든 단말 토큰(괄호, 세미콜론, 연산자 기호)이 잎으로 등장. 유도 과정의 기록에 가깝다.
* **AST(Abstract Syntax Tree)**: 의미를 전달하는 데 꼭 필요하지 않은 표면 토큰과 중간 비단말을 걷어내고 연산자/구문 구성요소만 남긴 추상 트리. 노드 종류가 간결하고 이후 단계가 순회·변환하기 좋다.

컴파일러는 파스 트리를 명시적으로 만들지 않고 곧장 AST를 만들거나, 파스 트리를 만든 뒤 즉시 AST로 축약하는 것이 일반적이다.



**오류 복구(Error Recovery)**

컴파일러가 첫 오류에서 멈추지 않고 한 번에 여러 오류를 보고하려면 복구 전략이 필요하다. Aho Dragon Book의 4가지 분류:

* **패닉 모드(panic mode)**: 동기화 토큰(`;`, `}`, 문 시작 키워드)을 만날 때까지 토큰을 스킵하고 그 지점부터 재개. 가장 널리 쓰임.
* **구문 수준 복구(phrase-level recovery)**: 지역적으로 토큰을 삽입·삭제·치환해 일단 진행 가능한 상태로 만듦.
* **오류 생성 규칙(error productions)**: 자주 나오는 오류 패턴을 아예 문법에 별도 규칙으로 추가.
* **전역 보정(global correction)**: 최소 편집 거리로 입력 전체를 보정. 비용이 커서 실무에서 거의 안 씀.

목표는 (1) 가능한 한 많은 진짜 오류를 보고하되 (2) 한 오류 때문에 줄줄이 가짜 오류(cascading errors)가 터지지 않게 막는 것.

#### 예시

**예시 1 — 토큰 스트림 → AST**

입력 토큰: `[IDENT(sum), OP(=), IDENT(a), OP(+), IDENT(b), OP(*), NUMBER(10), SEMI]` \
원래 문장: `sum = a + b * 10;`

```
Assign(=)
  ├── Ident(sum)
  └── BinaryOp(+)
        ├── Ident(a)
        └── BinaryOp(*)
              ├── Ident(b)
              └── Number(10)
```

핵심: `*`가 `+`의 자식(더 깊은 노드)으로 들어가 있다는 사실 자체가 **연산자 우선순위**를 트리 구조에 인코딩한 결과다.

**예시 2 — 파스 트리 vs AST**

`a + b * 10`의 파스 트리(CST, 중간 비단말 모두 보존):

```
expr
├── expr
│   └── term
│       └── factor
│           └── IDENT(a)
├── "+"
└── term
    ├── term
    │   └── factor
    │       └── IDENT(b)
    ├── "*"
    └── factor
        └── NUMBER(10)
```

같은 입력의 AST:

```
BinaryOp(+)
├── Ident(a)
└── BinaryOp(*)
      ├── Ident(b)
      └── Number(10)
```

두 트리는 같은 우선순위를 표현하지만 AST가 훨씬 군더더기 없다.

### 4. 의미 분석 (Semantic Analysis)

> &#x20;1.2.4 생성된 구문 트리에 이상은 없을까?

#### 개념 정의

의미 분석은 구문 분석이 만들어낸 AST가 문법적으로 옳을 뿐 아니라 **언어의 의미 규칙(semantic rules)에 비추어 말이 되는지**를 검증하고, 트리의 각 노드에 타입과 심볼 정보를 덧붙이는 컴파일 단계이다.

#### 원리 설명

구문 분석을 통과한 코드라고 해서 곧바로 실행 가능한 의미를 가진 것은 아니다. \
예컨대 `int a = "hello";`는 토큰 배열이 문법에 부합해 AST가 정상 생성되지만, 정수형 변수에 문자열을 대입하는 것은 언어 의미상 허용되지 않는다. \
즉 **AST는 문법적으로 옳다 ≠ 의미적으로 옳다**는 간극이 존재하며, 이 간극을 메우는 것이 의미 분석이다. \
의미 분석기는 AST를 순회하면서 식별자가 어디서 선언되었는지 찾고, 표현식의 타입을 계산하며, 언어 규칙을 위반한 노드가 있으면 오류로 보고한다. \
통과한 결과는 노드마다 타입·심볼 정보가 부착된 \*\*장식 AST(decorated AST / annotated AST)\*\*로, 이후 중간 코드 생성기의 입력이 된다.

#### 세부 메커니즘

의미 분석이 수행하는 검사는 크게 두 축이다.

1. **이름 해석(name resolution / scope lookup)**: AST의 식별자가 실제로 선언되어 있는지, 그리고 현재 위치의 **스코프** 규칙에 따라 어느 선언에 묶이는지(binding) 결정.
2. **타입 검사(type check)**: 연산자 양쪽 피연산자의 타입 호환성, 함수 호출의 인자 개수·타입, 대입문 양변 타입 일치.

이 외에도 정의되지 않은 변수 사용, 동일 스코프 내 중복 선언, 함수 시그니처 불일치, `private` 멤버 접근 같은 접근 제한 위반 등을 함께 잡는다.

핵심 자료구조는 **심볼 테이블(symbol table)**. \
스코프별로 "식별자 이름 → (타입, 선언 위치, 그 외 속성)"을 매핑하며, 중첩 스코프 표현을 위해 보통 스택 또는 트리 구조. 의미 분석기는 AST를 순회하면서 선언을 만나면 심볼 테이블에 등록하고, 식별자 사용을 만나면 안쪽 스코프부터 바깥쪽으로 거슬러 올라가며(lexical scope lookup) 해당 심볼을 찾는다. \
찾아낸 심볼은 AST 노드에 링크로 부착되고, 표현식 노드에는 계산된 타입이 부착되어 **장식 AST**가 완성된다.

#### 예시

**예시 1 — 타입 불일치 (AST는 합법, 의미는 불법)**

```c
int a = "hello";   // 구문 분석 통과, 의미 분석에서 거부
```

좌변의 타입(`int`)과 우변 리터럴 타입(`const char *`)이 호환되지 않음을 발견하여 **타입 불일치 오류(type mismatch)** 보고.

**예시 2 — 미해결 식별자**

```c
print(x);          // x가 어디서도 선언되지 않았다면
```

심볼 테이블에서 `x`를 검색했을 때 어떤 스코프에도 등록되어 있지 않다면 **미해결 식별자 오류(undefined identifier)** 발생.

**심볼 테이블의 모습 (개념도)**

```c
int a;
float b;
int add(int x, int y) {
    int sum;
    return sum;
}
```

`add` 함수 본문 안에서 `sum`을 사용하면, 의미 분석기는 우선 함수 스코프를 검색해 `sum: int`를 찾고, 발견하지 못했다면 부모 Global scope로 이동해 탐색을 이어간다.



입력은 구문 분석의 AST, 출력은 IR 생성기에 넘길 장식 AST. "토큰 → AST → 장식 AST → IR → 타깃 코드" 흐름에서 의미 분석이 통과시키면 이후 단계는 "코드가 적어도 말이 된다"는 전제로 작업할 수 있다.

### 5. 중간 코드 (Intermediate Representation, IR)

> &#x20;1.2.5 구문 트리를 기반으로 중간 코드 생성하기

#### 개념 정의

중간 코드(IR)는 의미 분석을 통과한 장식 AST와 최종 타깃 기계어 사이에 놓이는, **소스 언어와 특정 하드웨어 양쪽으로부터 독립적인 중간 형태의 표현**으로, 최적화와 코드 생성의 공통 기반이다.

#### 원리 설명

컴파일러가 N개의 프로그래밍 언어를 M개의 타깃 아키텍처로 번역해야 한다고 가정하면, 직접 변환 경로는 N×M 개의 번역기가 필요하다. \
그러나 모든 언어를 공통 IR로 먼저 낮추고, 그 IR을 각 타깃으로 번역하는 구조를 택하면 모듈 수는 **N+M**으로 줄어든다. \
또한 IR은 AST보다 기계어에 가깝지만 여전히 특정 하드웨어에 묶이지 않기 때문에, 이 단계에서 **머신 독립 최적화(machine-independent optimization)**&#xB97C; 수행하기에 적합하다.&#x20;



#### 예시

**예시 — 3-주소 코드로 낮추기**

원본: `sum = a + b * 10;`

```
t1 = b * 10
t2 = a + t1
sum = t2
```

이 표현은 어느 특정 CPU 아키텍처에도 묶여 있지 않으며, 이후 백엔드가 이를 x86, ARM 등 실제 명령어로 변환한다.



입력은 의미 분석의 장식 AST, 출력은 코드 생성기에 넘길 IR(+ 머신 독립 최적화 적용). "AST는 문법적 구조, 장식 AST는 의미적으로 검증된 구조, IR은 기계에 가까운 실행 모델"이라는 추상화의 단계적 하강.

### 6. 코드 생성 (Code Generation, 백엔드)

> 📍 1.2.6 코드 생성

#### 개념 정의

코드 생성은 컴파일러 백엔드의 최종 단계로, 중간 표현(IR)을 입력받아 특정 CPU 아키텍처(ISA, Instruction Set Architecture)의 어셈블리 또는 기계어로 변환하는 과정이다.

#### 원리 설명 (depth 1)

컴파일러 파이프라인의 **마지막 단계**다. \
프론트엔드와 미들엔드가 만들어 놓은 머신 독립적 IR은 아직 "어떤 CPU에서도 직접 실행할 수 없는 추상 표현"이기 때문에, 백엔드가 이를 실제 하드웨어가 이해하는 명령어로 내려야(lowering) 한다. \
이 과정에서 IR의 추상 연산이 타깃 ISA의 구체 명령어로 매핑되고(명령어 선택), IR의 가상 레지스터가 한정된 물리 레지스터에 배치되며(레지스터 할당), 해당 CPU의 마이크로아키텍처 특성을 활용한 머신 의존 최적화가 추가로 적용된다. \
같은 IR이라도 백엔드가 x86-64냐 ARM이냐 RISC-V냐에 따라 출력 어셈블리가 완전히 달라진다.

#### 예시

**예시 — 3-주소 코드 IR → x86-64 어셈블리 (Intel 문법)**

원본 C: `sum = a + b * 10;` (a, b, sum은 지역 변수로 스택에 위치, int = 4바이트)

```
IR (3-주소 코드, 가상 레지스터):
  t1 = b * 10
  t2 = a + t1
  sum = t2

레지스터 할당:
  t1 → EAX
  t2 → EAX  (t1 마지막 사용 후 죽었으므로 EAX 재사용 가능)
```

지역 변수가 RBP보다 낮은 주소에 배치되며 int는 4바이트이므로 4바이트씩 떨어진 슬롯에 놓인다고 가정:

```asm
; Intel 문법 (op dst, src)
  mov    eax, DWORD PTR [rbp-8]    ; EAX = b
  imul   eax, 10                    ; EAX *= 10        (t1 = b * 10)
  add    eax, DWORD PTR [rbp-4]    ; EAX += a         (t2 = a + t1)
  mov    DWORD PTR [rbp-12], eax   ; sum = EAX
```



* **입력**: 의미 분석 → IR 생성 → 머신 독립 최적화를 거친 **IR**.
* **출력**: 어셈블리/오브젝트. 이후 **어셈블러 → 링커**가 최종 실행 파일을 만듦(이후 절들 주제).
* **다중 타깃 지원**: 코드 생성은 ISA에 강하게 묶이므로 한 컴파일러가 여러 CPU를 지원하려면 (a) 타깃마다 백엔드를 따로 구현하거나, (b) **공통 IR을 공유**하고 백엔드만 바꿔 끼우는 구조를 택한다. 후자의 대표 사례가 **LLVM** — Clang·Rust·Swift 등이 모두 LLVM IR을 생성하고, x86/ARM/RISC-V 등 백엔드가 같은 IR을 받아 각자의 어셈블리로 내린다. "프론트엔드 N개 × 백엔드 M개"를 "N + M"의 노력으로 줄여 주는 구조적 이점.

# 1.1. Making Programming Language

## 1.1 여러분이 프로그래밍 언어를 발명한다면?

***

### 1. 기계어

> &#x20;1.1.1 창세기: CPU는 똑똑한 바보

#### 개념 정의

기계어는 CPU가 별도의 번역 없이 곧바로 실행할 수 있는, 0과 1로만 이뤄진 명령의 집합이다.

#### 원리 설명

CPU는 전기 신호로 동작하는 회로 덩어리이고, 켜짐과 꺼짐, 즉 1과 0 두 가지 상태만 구분할 수 있다. \
그래서 CPU에게 "무엇을 하라"고 시키려면 그 명령 또한 1과 0의 묶음으로 표현되어 있어야 한다. \
정해진 길이의 비트 묶음 하나하나가 "두 수를 더하라", "값을 옮겨라" 같은 아주 단순한 동작에 대응한다. \
CPU는 이 비트 묶음을 순서대로 읽어 들이고, 묶음이 가리키는 동작을 그대로 수행할 뿐이다. \
똑똑하개 판단을 하는 것이 아니라, 정해진 패턴이 들어오면 정해진 일을 하는 바보인 셈이다.

#### 세부 메커니즘

CPU마다 어떤 비트 패턴이 어떤 동작을 의미하는지가 미리 정해져 있고, 프로그램은 결국 이 약속에 맞춘 0과 1의 긴 나열이다. \
비트 하나만 잘못 적어도 전혀 다른 명령이 되거나 아예 실행이 어긋나기 때문에, 사람이 직접 기계어로 프로그램을 쓰기는 어렵다.

#### 예시

"어떤 값을 다른 곳으로 옮겨라"라는 한 줄짜리 명령은 실제로 CPU에게는 다음과 같은 비트열로 주어진다.

```
10110000 01100001
```

이 0과 1의 묶음이 CPU 안에서 곧바로 하나의 동작으로 해석되어 실행된다.



기계어를 사람이 직접 쓰는 일이 너무 어렵기 때문에, 같은 명령에 사람이 읽을 수 있는 이름을 붙여 주자는 발상에서 어셈블리어가 등장한다.

### 2. 어셈블리어

> &#x20;1.1.2 어셈블리어 등장

#### 개념 정의

어셈블리어는 기계어의 비트 묶음 하나하나에 사람이 알아볼 수 있는 짧은 이름표를 붙여 표기한 언어다.

#### 원리 설명

CPU 입장에서 필요한 것은 여전히 0과 1이지만, 사람 입장에서는 "이 비트가 도대체 무슨 뜻인가"를 한눈에 알아보는 것이 중요하다. \
그래서&#x20;

* "값을 옮긴다"는 명령에는 `MOV`,&#x20;
* "더한다"는 명령에는 `ADD`&#x20;

같은 짧은 영어 약어를 붙여 두고, 사람은 이 이름표로 프로그램을 쓴다. \
**어셈블리 한 줄은 보통 기계어 명령 한 개에 대응한다**(같은 동작이라도 피연산자(레지스터/값/주소)에 따라 비트 표현이 달라지므로, 이름표와 비트가 정확히 일대일은 아니다 — 단 "명령 단위"는 일대일). \
덕분에 0과 1을 직접 쓰는 것보다 훨씬 읽고 쓰기 쉬워졌지만, 동작의 단위 자체는 여전히 CPU가 한 번에 처리하는 작은 명령 그대로다.

#### 세부 메커니즘

사람이 작성한 어셈블리어 코드는 그대로는 CPU가 이해하지 못하므로, 이름표를 다시 원래의 0과 1로 바꿔 주는 도구가 필요하다. \
이 역할을 하는 프로그램이 **어셈블러**이며, `MOV` 같은 약어를 정해진 비트 묶음으로, 숫자나 이름을 알맞은 비트열로 기계적으로 치환해 준다. \
다시마랳, 어셈블리어는 본질적으로 기계어를 사람이 보기 좋게 적어 둔 또 다른 표기일 뿐이다.

#### 예시

앞서 본 비트열은 어셈블리어로는 다음 한 줄로 적을 수 있다.

```asm
MOV AL, 97
```

사람은 이 한 줄을 보고 "값 97을 AL이라는 자리에 넣어라"라고 바로 읽지만, 어셈블러를 거치면 이 줄은 결국 앞 절에서 본 0과 1의 묶음으로 변환되어 CPU에게 전달된다.



어셈블리어는 기계어 위에 얇게 덧씌운 이름표 층이며, 비트와의 거의-일대일 대응이라는 한계 때문에 더 사람다운 표현을 향한 다음 단계의 언어로 나아가게 된다.

### 3. 추상화

> &#x20;1.1.3 저수준 계층의 세부 사항 대 고수준 계층의 추상화

#### 개념 정의

추상화란 아래 계층의 복잡한 세부 사항을 숨기고, 위 계층에서는 단순한 인터페이스만 보고 사용할 수 있도록 만드는 사고 방식이다.

#### 원리 설명

컴퓨터는 결국 0과 1을 옮기고 더하는 기계지만, 사람이 매번 그 수준에서 생각하면 아무것도 만들 수 없다. \
그래서 우리는&#x20;

* "값을 옮긴다"
* "두 수를 더한다"
* "조건이 맞으면 분기한다"&#x20;

같은 의미 단위로 한 겹을 덮는다. \
그 위에 다시 "변수에 값을 대입한다", "두 수를 더해 변수에 넣는다" 같은 더 친숙한 표현을 덮는다. \
이렇게 한 겹씩 덮어 올라가면, 위층에서 일하는 사람은 아래층이 어떻게 돌아가는지 거의 신경 쓰지 않아도 된다. \
추상화의 핵심은 **"감추는 것"과 "단순한 사용법만 노출하는 것"** 두 가지다.

#### 세부 메커니즘

한 겹의 추상화는 "이 안에서 무슨 일이 벌어지든, 너는 이 입력만 주면 이 결과만 받으면 된다"는 약속이다. \
위층은 그 약속만 믿고 코드를 쓰면 되고, 아래층은 약속만 지키면 내부를 마음대로 바꿔도 된다.&#x20;

다만 추상화에는 **대가**가 있다. \
편하게 한 줄로 쓰는 문장이 실제 기계에서는 여러 단계로 풀려 실행되므로, 편리함을 얻는 대신 아래에서 무슨 일이 벌어지는지 보이지 않게 된다.

#### 예시

같은 "두 수를 더해 변수에 넣는다"는 일을, 기계에 가까운 어셈블리와 사람에 가까운 C로 비교하면 차이가 한눈에 보인다.

```asm
mov eax, a
add eax, b
mov c, eax
```

```c
c = a + b;
```

아래쪽 한 줄이 위쪽 세 줄을 "감춰서" 보여 주고 있는 셈이다.



이렇게 아래 계층을 감추고 사람이 읽기 쉬운 문장으로 코드를 쓸 수 있게 해 주는 도구가 "고급 프로그래밍 언어"다.

***

### 4. 고급 프로그래밍 언어

> &#x20;1.1.4 가득한 규칙: 고급 프로그래밍 언어의 시작

#### 개념 정의

고급 프로그래밍 언어란 기계의 동작 방식이 아니라 사람의 사고 방식에 가깝게 코드를 적을 수 있도록 만든 언어다.\
여기서 "고급(high-level)"은 잘 만들었다는 뜻이 아니라, **기계로부터 멀리 떨어져 있다(추상화 계층이 높다)는 뜻**이다.

#### 원리 설명

어셈블리 수준에서는 "레지스터에 값을 옮기고, 더하고, 메모리에 다시 쓰라"고 일일이 지시해야 한다. \
사람은 보통 그렇게 생각하지 않는다. \
사람은&#x20;

* "만약 \~이면 \~하라", "\~인 동안 반복하라"
* "이 일을 하는 절차를 하나 만들어 두고 필요할 때 부르자"

처럼 생각한다. \
고급 언어는 바로 이런 사고를 그대로 문장으로 옮길 수 있게 해 준다. (`if`, `while`, `function` 같은 구문)

#### 세부 메커니즘

사람의 말은 자유롭고 모호하지만, 컴퓨터는 모호한 문장을 실행할 수 없다. \
그래서 고급 언어는 자유롭게 보이면서도 사실은 빈틈없이 정해진 규칙 위에서 작동해야 한다.&#x20;

* 어떤 단어가 키워드인지,&#x20;
* 괄호와 세미콜론은 어디에 와야 하는지,&#x20;
* 한 문장의 의미가 정확히 무엇인지

모두 미리 약속되어 있어야 한다. \
그래야 같은 코드를 누가 읽어도 같은 뜻으로 정해져 있고, 기계가 달라져도 같은 코드를 (각 기계에 맞게 번역만 해 주면) 그대로 쓸 수 있다.

#### 예시

"0부터 9까지 합을 구하라"는 생각을, 사람은 보통 다음 한 덩어리로 적는다.

```c
int sum = 0;
for (int i = 0; i < 10; i++) {
    sum = sum + i;
}
```

기계 수준에서 이 짧은 반복문은 레지스터를 0으로 만들고, 값을 비교하고, 작으면 더하고, 1을 증가시키고, 다시 비교 지점으로 점프하는 여러 단계로 길게 풀려 실행된다. \
고급 언어는 그 긴 절차를 `for` 한 줄 뒤로 감춰 준다.



결국 고급 프로그래밍 언어는 앞서 말한 "추상화"를 언어의 형태로 굳혀 놓은 것이며, 사람이 이렇게 자유롭게 쓴 문장을 기계가 실제로 실행하게 만들려면 정해진 규칙에 따라 해석해 주는 장치가 필요하다.

### 5. 재귀

> 1.1.5 <인셉션>과 재귀: 코드 본질

#### 개념 정의

재귀란 어떤 대상을 정의할 때 그 정의 안에 자기 자신이 다시 등장하는 구조다.

#### 원리 설명

영화 〈인셉션〉에는 꿈속에서 또 꿈을 꾸고, 그 안에서 또 꿈을 꾸는 장면이 등장한다. \
코드의 세계에도 이와 똑같은 일이 벌어진다. \
"표현식"이라는 것을 정의하려고 보면, 그 안에 다시 "표현식"이 들어 있다.&#x20;

예를 들어 `1 + 2`도 표현식이고, 그 결과에 또 무언가를 더한 `1 + 2 + 3`도 표현식이다. \
즉 표현식은 표현식을 품을 수 있고, 그 안의 표현식도 다시 표현식을 품을 수 있다. \
이렇게 자기 자신을 다시 부르는 구조 덕분에, 우리는 길이가 얼마나 길어지든 모든 식을 한 가지 규칙으로 설명할 수 있다.

#### 세부 메커니즘

핵심은 짧고 단순한 규칙 한 줄로, 끝없이 길어질 수 있는 대상을 유한하게 적어낼 수 있다는 점이다. \
**무한 중첩을 유한한 글로 붙잡는 도구가** 재귀다.



이렇게 재귀적으로 정의된 식의 자기 참조 구조를 그림으로 펼쳐 보이면, 구문 트리가 된다.

***

### 6. 구문 트리

> &#x20;1.1.6 컴퓨터가 재귀를 이해하도록 만들기

#### 개념 정의

구문 트리는 코드 한 줄을 트리 모양으로 그려서, 어떤 부분이 어떻게 묶이고 무엇이 무엇 안에 들어 있는지를 한눈에 드러낸 그림이다.

#### 원리 설명

사람은 `2 + 3 * 4`라는 식을 보면 자연스럽게 `3 * 4`를 먼저 묶어서 계산한다. \
컴퓨터에게 이 "묶음"을 알려주려면, 글자를 일렬로 늘어놓은 것만으로는 부족하다. \
이때 코드를 트리로 다시 그려준다. \
각 노드는 `+`나 `*` 같은 연산자가 되고, 트리의 잎에는 `2`, `3`, `4` 같은 숫자나 변수가 자리 잡는다. \
그러면 누가 누구의 부분인지가 그림만 봐도 분명해진다.

#### 세부 메커니즘

구문 트리의 아름다움은, 우선순위 규칙을 따로 외워두지 않아도 **트리 구조 자체가 그 묶음을 이미 담고 있다**는 점이다. \
곱셈이 덧셈보다 먼저 묶여야 한다면, 곱셈을 더 안쪽 가지로 내려 보내면 된다. \
그러면 트리를 안쪽에서부터 바깥쪽으로 풀어 가는 것만으로 자연스럽게 올바른 순서가 따라 나온다. \
앞서 본 "표현식 안의 표현식"이라는 자기 참조 규칙이 그대로 "부모 노드 밑의 자식 노드"라는 형태로 모습을 드러낸 것뿐이다.&#x20;

**트리를 잎부터 위로 한 단계씩 계산해 올라가면, 각 노드의 연산이 자식들의 결과를 받아 하나의 값이 되고, 마지막에 뿌리에서 식 전체의 값이 나온다.**

#### 예시

`2 + 3 * 4`를 구문 트리로 그리면 다음과 같다.

```
  +
 / \
2   *
   / \
  3   4
```

가장 바깥의 `+` 아래에 왼쪽 가지로 `2`가, 오른쪽 가지로 `*` 묶음이 매달려 있다. \
트리만 봐도 `3 * 4`가 먼저 한 덩어리로 묶여 있고, 그 결과(`12`)가 `2`와 더해져 `14`가 된다는 사실이 보인다.&#x20;



구문 트리는 앞 키워드인 재귀적 표현식 정의가 종이 위에 펼쳐진 모습이며, 컴퓨터가 코드의 의미를 다루기 위해 가장 먼저 만들어 두는 발판이 된다. 컴파일러도 결국 이 트리를 받아 기계어로 옮기는 작업을 한다.

### 7. 컴파일러

> &#x20;1.1.7 우수한 번역가: 컴파일러

#### 개념 정의

컴파일러는 사람이 작성한 고급 언어 소스 코드를 컴퓨터가 직접 실행할 수 있는 기계어로 번역해 주는 프로그램이다.

#### 원리 설명

앞서 살펴봤듯이 CPU는 0과 1로 이루어진 기계어만 이해한다. \
그런데 사람은 `if`, `for`, `return` 같은 단어로 생각하는 것이 훨씬 편하다. \
이 두 세계 사이에는 누군가가 다리를 놓아 주어야 하는데, 그 역할을 맡은 것이 바로 컴파일러다. \
마치 **한국어 소설을 영어 독자에게 전달하기 위해 번역가가 통째로 번역본을 만들어 두는 것**과 같다. \
한 번 잘 번역해 두면, 이후에는 원본을 다시 펼치지 않고도 번역본만으로 빠르게 읽어 나갈 수 있다.

#### 세부 메커니즘

컴파일러의 핵심은 **"실행 전에 미리, 그리고 한꺼번에 번역해 둔다"**&#xB294; 점이다. \
프로그래머가 소스 코드를 작성한 뒤 컴파일러를 한 번 돌리면, 그 결과로 기계어로 된 실행 파일이 만들어진다. \
실행할 때는 이미 번역된 기계어를 CPU가 그대로 실행하므로, 매번 번역하는 과정이 없어 일반적으로 빠르다.&#x20;

#### 예시

예를 들어 다음과 같은 C 코드가 있다.

```c
#include <stdio.h>

int main(void) {
    printf("Hello, world!\n");
    return 0;
}
```

이 파일(`hello.c`)을 컴파일러에 한 번 통과시키면 `hello`라는 실행 파일이 만들어진다. \
그 뒤로는 소스 코드 없이도 이 실행 파일만 두 번이고 세 번이고 곧바로 실행할 수 있다. \
사용자 입장에서는 "한 번 빌드해 두고 계속 실행"



컴파일러가 "미리 한 번에 번역해 두는" 방식이라면, 같은 다리 역할을 다른 방식으로 해내는 도구도 있다

***

### 8. 인터프리터 (해석형 언어)

> 1.1.8 해석형 언어의 탄생

#### 개념 정의

인터프리터는 소스 코드를 미리 통째로 번역해 두는 대신, 프로그램을 실행할 때 한 줄씩 읽어 가며 그 자리에서 해석하고 실행해 주는 프로그램이다.

#### 원리 설명

컴파일러가 "책 한 권을 처음부터 끝까지 번역해서 번역본을 건네주는 번역가"라면, 인터프리터는 **"외국 손님 옆에 붙어 앉아 한 문장 들으면 바로 통역해 주는 통역사"**&#xC5D0; 가깝다. \
미리 번역본을 만들어 두지 않으니 준비 시간이 따로 필요 없고, 코드를 고치자마자 곧바로 결과를 확인할 수 있다. 이런 방식으로 동작하는 언어를 해석형 언어(interpreted language)라고 부른다.

#### 세부 메커니즘

가장 큰 차이는 **"번역과 실행을 분리하느냐, 동시에 하느냐"**&#xC5D0; 있다. \
컴파일러 방식에서는 번역이 한 번에 끝나고 그 결과물(실행 파일)이 별도로 남는 반면, 인터프리터 방식에서는 매번 실행할 때마다 인터프리터가 소스 코드를 읽으며 그때그때 해석해 실행한다. \
실행할 때마다 해석 과정을 거치므로 같은 코드를 미리 번역해 둔 경우보다 일반적으로 느리지만, 코드를 고치자마자 결과를 확인할 수 있다.

#### 예시

대표적인 해석형 언어로 Python이 있다. \
다음 코드를 `hello.py`로 저장하고 `python hello.py`라고 입력하면, 별도의 빌드 단계 없이 곧바로 결과가 출력된다.

```python
print("Hello, world!")
```

심지어 Python은 대화형 모드(REPL)도 제공한다. \
터미널에서 `python`을 실행한 뒤 한 줄을 입력하면 그 자리에서 결과가 나오고, 또 한 줄을 입력하면 또 결과가 나온다.



컴파일러와 인터프리터는 결국 "사람의 언어와 기계의 언어 사이를 잇는다"는 같은 목적을 두 가지 방식으로 풀어낸 것이다.&#x20;

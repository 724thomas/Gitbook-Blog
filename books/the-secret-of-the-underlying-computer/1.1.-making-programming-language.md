# 1.1. Making Programming Language

## 1.1 여러분이 프로그래밍 언어를 발명한다면?

***

### CPU와 0/1 스위치

**개념 정의** — CPU는 내부의 수많은 트랜지스터 스위치가 켜짐(1)과 꺼짐(0) 상태를 조합하여 연산을 수행하는 디지털 논리 회로 장치이다.

#### 원리

컴퓨터의 모든 동작은 결국 전기 신호의 "있다/없다"라는 두 가지 상태로 환원된다. \
이 두 상태를 표현하는 가장 기본적인 부품이 트랜지스터이며, 트랜지스터는 전류를 흐르게 하거나 막는 스위치 역할을 한다. \
여러 트랜지스터를 조합하면 NAND/NOR 게이트를 만들 수 있고, 거기에 인버터를 붙이면 AND, OR, NOT 같은 표준 논리 게이트가 된다. \
논리 게이트를 다시 조합하면 가산기(adder), 래치/플립플롭, 레지스터, 그리고 최종적으로 CPU 전체를 구성할 수 있다. \
결국 CPU가 "계산한다"는 것은 입력된 0/1 비트열에 대해 정해진 회로 경로를 따라 전기 신호가 흐르면서 출력 비트열을 만들어내는 물리적 과정이다.



CPU가 직접 이해할 수 있는 신호는 0과 1뿐이므로, 인간이 CPU에게 명령을 전달하려면 0/1로 이루어진 명령 코드, 즉 **기계어**가 필요하다.

***

### 기계어

**개념 정의** — 기계어(machine language)는 CPU가 회로 차원에서 직접 해독하고 실행할 수 있는 0과 1의 이진 명령어 집합이다.

#### 원리

CPU는 정해진 비트 패턴을 받으면 그에 대응하는 회로가 활성화되도록 설계되어 있다. \
"더해라", "메모리에서 값을 가져와라" 같은 동작은 특정한 비트열로 인코딩되며, 이 비트열이 곧 명령어(instruction)이다. \
하나의 기계어 명령은 보통 "무엇을 할지"를 가리키는 **연산 코드(opcode)** 와 "무엇에 대해 할지"를 가리키는 **피연산자(operand)** 필드로 나뉜다. \
CPU는 매 클럭 사이클마다 메모리에서 비트열을 읽어와(fetch) 회로로 해독한 뒤(decode), 실제 연산 회로를 동작시킨다(execute).&#x20;



기계어는 0/1로만 이루어져 사람이 읽고 쓰기 거의 불가능하므로, 이를 다룰 수 있도록 기호화한 표기인 **어셈블리어**가 등장한다.

***

### 어셈블리어

**개념 정의** — 어셈블리어(assembly language)는 기계어 명령에 사람이 읽기 쉬운 기호(mnemonic)를 거의 1:1로 대응시켜 표현한 저수준 프로그래밍 언어이다.

#### 원리

0과 1의 나열은 사람이 직접 작성·디버깅하기 너무 비효율적이다. \
그래서 `ADD`, `MOV`, `JMP` 같은 의미를 짐작할 수 있는 단어(니모닉)와 레지스터 이름, 상수, 레이블을 사용해 명령을 적는 방식이 만들어졌다. \
**어셈블러(assembler)** 가 이 기호 표현을 다시 0/1 비트열의 기계어로 번역해 CPU가 그대로 실행할 수 있게 한다.\
어셈블리어는 기계어와 거의 1:1 대응이지만, 정확히 1:1은 아니다 — 의사명령어(pseudo-instruction)·매크로·어셈블러 지시어(directive)는 단일 기계어 명령에 대응되지 않으며(예: MIPS의 `li`, RISC-V의 `la`는 여러 명령으로 확장된다), 같은 의미라도 여러 인코딩이 존재하기도 한다.



어셈블리어의 피연산자는 대부분 **메모리와 레지스터**를 직접 가리키므로, 다음에는 데이터가 실제로 어디에 저장되고 어떻게 옮겨지는지를 살핀다.

***

### 메모리와 레지스터

**개념 정의** — 메모리(주기억장치, DRAM)는 프로그램의 명령어와 데이터를 담는 대용량 저장 공간이고, 레지스터는 CPU 내부에 있는 극소수의 초고속 저장 슬롯이다.

#### 원리

CPU는 한 번에 소수의 명령을 실행하며 연산에 필요한 피연산자를 즉시 꺼낼 자리가 필요하다. \
메모리는 용량이 크지만 CPU에 비해 상대적으로 매우 느리므로, 모든 연산을 메모리에서 직접 하면 CPU가 대기 시간으로 낭비된다. \
그래서 자주 쓰는 값은 CPU 코어 안의 레지스터에 올려두고, 연산은 레지스터끼리 수행한 뒤 결과만 메모리에 다시 저장한다. \
어셈블리 명령(`MOV`, `ADD` 등)의 피연산자가 대부분 레지스터 이름인 이유다. \
그리고 레지스터와 주기억장치 사이에는 **L1/L2/L3 캐시 계층**이 존재하며, 현대 프로그램의 실효 성능은 캐시 히트/미스율에 크게 좌우된다.



앞선 **어셈블리어** 명령이 직접 다루는 대상이 레지스터·메모리이며, 이 "값을 어디에 보관하고 언제 옮길지"라는 저수준 관리 부담을 위로 숨기기 위해 다음 단계의 **계층적 추상화**와 **고급 프로그래밍 언어**가 등장한다.

***

### 계층적 추상화

**개념 정의** — 복잡한 시스템을 여러 층으로 나누고, 각 층은 아래층의 세부사항을 감춘 채 정해진 인터페이스만 위층에 제공하는 설계 원리.

#### 원리

인간이 0/1 스위치를 직접 조작해 프로그램을 만드는 것은 사실상 불가능하므로, 아래층의 복잡함을 "쓰기 좋은 형태"로 포장해 올리는 작업이 반복되어 컴퓨터 시스템 전체가 만들어졌다. \
각 층은 자기 아래의 세부 구현을 블랙박스로 두고, "이 인터페이스만 지키면 동작을 보장한다"는 약속만 위로 노출한다. \
위층 개발자는 아래 구현을 몰라도 인터페이스만 알면 쓸 수 있고, 아래층은 인터페이스만 유지하면 내부 구현을 자유롭게 바꿀 수 있다.

#### 예시

`c = a + b` 한 줄이 아래로 펼쳐지는 모습:

```
[고급 언어]    c = a + b;                            // 변수만 보임
     │  (컴파일러)
[어셈블리]     MOV EAX,[a] / ADD EAX,[b] / MOV [c],EAX  // 레지스터·주소
     │  (어셈블러)
[기계어]       10001011 00000101 ...                 // 0/1 비트열
     │
[디지털 회로]  게이트 ON/OFF 신호                    // 전압 변화
```

고급 언어 사용자는 위쪽 한 줄만 보고도 동일한 결과를 얻으며, 아래 4단계의 내부 사정은 알 필요가 없다.&#x20;



앞의 **CPU/기계어/어셈블리어/메모리·레지스터**는 모두 "숨겨질 아래층"에 해당하고, **고급 프로그래밍 언어**는 그 위에 새로 쌓이는 층이며, **컴파일러**와 **인터프리터**는 층 사이를 잇는 번역기다.

***

### 고급 프로그래밍 언어

**개념 정의** — 하드웨어 세부사항(레지스터·주소·명령어 인코딩)을 감추고 인간이 읽고 쓰기 쉬운 문법으로 알고리즘을 표현하게 해주는 언어.

#### 원리

어셈블리어는 명령 하나가 CPU 동작 한 단계와 거의 1:1이라 짧은 알고리즘조차 길고 오류가 잦으며, CPU 종류가 바뀌면 다시 써야 한다. \
이 부담을 줄이기 위해 변수·표현식·제어문·함수 같은 "사람의 사고 단위"를 그대로 적을 수 있는 언어를 만들고, 그것을 자동으로 기계어로 바꿔주는 도구(컴파일러/인터프리터)를 함께 제공한다. \
결과적으로 한 줄의 고급 언어 코드가 기계어 명령으로 펼쳐지고, 같은 소스를 여러 CPU용으로 다시 번역할 수도 있다.&#x20;



#### 예시

같은 작업을 어셈블리와 C로 비교하면 추상화 효과가 분명해진다.

```c
// C: 1부터 10까지의 합
int sum = 0;
for (int i = 1; i <= 10; i++) {
    sum += i;
}
```

이 코드는 어셈블리로 풀면 대략 다음과 같다:

```asm
    MOV  EAX, 0        ; sum = 0
    MOV  ECX, 1        ; i = 1
LOOP:
    CMP  ECX, 10       ; i 와 10 비교
    JG   END           ; i > 10 이면 종료로 점프
    ADD  EAX, ECX      ; sum += i
    INC  ECX           ; i++
    JMP  LOOP          ; 루프 시작으로 점프
END:
    MOV  [sum], EAX    ; 결과를 메모리에 저장
```

결과는 양쪽 모두 `sum = 55`.&#x20;



**계층적 추상화**를 가장 사용자 가까이에서 구현한 결과물이 고급 언어이며, 함수 호출이 가능해지면서 자연스럽게 **재귀**라는 개념이 따라온다. \
이 코드를 CPU가 실제로 실행하려면 **컴파일러** 또는 **인터프리터**, 그 내부의 **파싱/AST**, 그리고 **바이트코드/JIT** 같은 변환 기술이 필요하다.

***

### 재귀

**개념 정의** — 어떤 구조나 함수가 자기 자신을 구성 요소로 다시 포함하는 정의 방식.

#### 원리

프로그래밍 언어의 문법은 "표현식 안에 또 다른 표현식이 들어갈 수 있다"처럼 자기 참조적으로 정의된다. \
`a + b`에서 `a`와 `b` 자체가 다시 표현식이 될 수 있으므로, 단 몇 줄의 문법 규칙으로 무한히 복잡한 식을 표현할 수 있다. \
이러한 재귀적 정의는 유한한 규칙으로 무한한 문장을 생성하는 힘을 제공하며, 동시에 동일한 처리 로직을 반복 적용해 복잡한 구조를 단순하게 다룰 수 있게 한다. \
함수 차원에서도 재귀는 큰 문제를 같은 형태의 작은 문제로 환원해 푸는 전략으로 쓰인다.



#### 예시

```c
// 팩토리얼: n! = n * (n-1)!
int factorial(int n) {
    if (n <= 1) return 1;          // 기저 조건
    return n * factorial(n - 1);   // 재귀 단계
}
// factorial(4) → 4 * factorial(3) → 4 * 3 * factorial(2)
//             → 4 * 3 * 2 * factorial(1) → 4 * 3 * 2 * 1 = 24
```

문법 차원의 예시: `1 + 2 * 3`은 `Expr(1) + Expr(Expr(2) * Expr(3))`처럼 표현식 안에 표현식이 중첩된 구조로 해석된다.



고급 프로그래밍 언어의 문법이 재귀적으로 정의되기에, 이를 처리하는 **컴파일러**도 자연스럽게 재귀적인 자료구조인 **구문 트리(AST)** 를 만들고 재귀적으로 순회한다.

***

### 컴파일러

**개념 정의** — 한 언어로 작성된 소스 코드를 다른 언어(일반적으로 더 저수준의 타깃 언어)로 번역하는 프로그램. \
타깃이 반드시 기계어일 필요는 없으며, 바이트코드 컴파일러나 source-to-source 컴파일러(예: TypeScript→JavaScript)도 컴파일러다.

#### 원리

사람이 읽기 좋은 고급 언어와 CPU가 실행하는 0/1 기계어 사이에는 큰 추상화 격차가 있으므로, 이를 메우는 자동 번역기가 필요하다. \
컴파일러는 소스를 한 번에 기계어로 바꾸는 것이 아니라, 여러 단계를 거치며 점진적으로 의미를 추출하고 더 낮은 수준의 표현으로 변환한다. \
각 단계는 이전 단계의 출력을 입력으로 받아 더 구조화된(또는 더 저수준의) 표현을 만든다.&#x20;



#### 예시

`int x = 1 + 2 * 3;`을 컴파일하면:

```
소스:     int x = 1 + 2 * 3;
토큰:     [int] [x] [=] [1] [+] [2] [*] [3] [;]
AST:      Assign(x, Add(1, Mul(2, 3)))
```



**고급 프로그래밍 언어**와 **기계어** 사이의 다리이며, **인터프리터**(즉시 실행) 및 **바이트코드/JIT**(중간 표현을 런타임에 기계어로 변환)와 대비된다.

***

### 파싱과 구문 트리(AST)

**개념 정의** — 파싱은 토큰 나열을 문법 규칙에 따라 계층적 트리 구조(AST, Abstract Syntax Tree)로 조립하는 과정이며, AST는 그 결과로 만들어진 프로그램의 구조적 표현이다.

#### 원리

토큰 스트림은 일렬로 나열되어 있어 연산자 우선순위·중첩 관계·제어 구조 같은 구조를 그대로 드러내지 않는다. \
파서는 재귀적으로 정의된 문법 규칙을 적용해 토큰들이 어떤 규칙으로 묶이는지 판단하고, 그 결과를 부모-자식 관계의 트리로 만든다. \
AST에서는 내부 노드가 연산자나 구문 구조를, 잎(leaf) 노드가 리터럴이나 식별자를 나타낸다. \
이렇게 구조화된 트리는 이후 단계(의미 분석·최적화·코드 생성)에서 단순한 순회로 처리할 수 있다.

#### 세부 메커니즘

파싱 알고리즘은 크게 두 부류다.

* **하향식(top-down, 예: 재귀 하강 파서)**: 시작 기호에서 출발해 문법 규칙을 재귀적으로 펼치며 토큰과 일치시킨다. 문법의 각 비단말 기호마다 함수를 두고 함수가 서로를 호출하는 구조 자체가 재귀적이다.
* **상향식(bottom-up, 예: LR 파서)**: 토큰부터 시작해 문법 규칙의 우변과 일치하는 부분을 좌변으로 환원(reduce)해 가며 트리를 쌓아 올린다.

AST가 만들어진 뒤 **단순한 산술식**의 평가나 스택 기반 코드 생성에는 **후위 순회(post-order traversal)** 가 자연스럽다(자식을 먼저 방문해 값/코드를 만든 뒤 부모 연산에 사용).

#### 예시

`1 + 2 * 3`의 AST와 후위 순회 결과:

```
   AST:
          (+)
         /   \
       (1)   (*)
             / \
           (2) (3)

후위 순회 → 1, 2, 3, *, +

생성되는 가상 어셈블리(스택 기반):
    PUSH 1
    PUSH 2
    PUSH 3
    MUL        ; 스택: [1, 6]
    ADD        ; 스택: [7]
```

곱셈이 덧셈보다 우선순위가 높다는 문법 정보가 트리의 깊이로 자연스럽게 인코딩되어 있어, 후위 순회만으로 `2*3`이 먼저 계산되는 의미가 보장된다.



**재귀적**으로 정의된 언어 문법이 **재귀적** 자료구조인 AST로 표현되며, **컴파일러**는 이 AST를 (IR을 거쳐) 기계어로 변환한다. **인터프리터**는 AST를 순회하며 직접 실행하고, **바이트코드/JIT**는 AST를 일단 바이트코드로 낮춘 뒤 런타임에 기계어로 다시 번역한다.

### 인터프리터와 해석형 언어

**개념 정의** — 인터프리터는 소스 코드(또는 그로부터 생성된 중간 표현)를 미리 네이티브 기계어 파일로 만들어두지 않고, 실행 시점에 의미를 해석해 동작을 수행하는 프로그램. 이런 방식으로 동작하는 언어를 해석형 언어라고 한다.

#### 원리

컴파일러는 "소스 → 타깃 코드"를 한 번에 만들어 두고 이후에는 그 결과물만 실행하지만, 인터프리터는 소스(또는 AST/바이트코드)를 들고 있다가 실행 시점에 각 구문의 의미를 해석해 그에 대응하는 동작을 수행한다. \
따라서 컴파일된 프로그램은 "빌드 결과물 → CPU 직접 실행"의 경로이지만, 해석형은 "소스 → 인터프리터(자체는 네이티브) → 동작 수행"이라는 한 단계가 더 끼어든다. \
이 추가 단계 덕분에 같은 소스 코드를 다른 OS·CPU에서도 그 환경용 인터프리터만 있으면 그대로 돌릴 수 있어 이식성이 높지만, 일반적으로 순수 네이티브 실행보다는 느리다. \
본질적인 트레이드오프는 **이식성·개발 편의성 ↔ 실행 속도**이다.



#### 예시

```python
x = 2
y = 3
print(x + y)
```

파서가 만든 AST는 `Program[ Assign(x, Num(2)), Assign(y, Num(3)), Call(print, BinaryOp(+, Var(x), Var(y))) ]`이다. 트리워킹 인터프리터는:

* `Assign(x, Num(2))` → 환경에 `x=2` 저장
* `Assign(y, Num(3))` → 환경에 `y=3` 저장
* `Call(print, BinaryOp(+, Var(x), Var(y)))` → `Var(x)` 조회 `2`, `Var(y)` 조회 `3`, `+` 평가 `5`, `print(5)` 호출

결과로 콘솔에 `5`가 출력된다.



인터프리터는 앞 단계의 **파싱과 구문 트리(AST)** 결과물을 직접 입력으로 받아 동작하며, **컴파일러**가 AST를 네이티브 기계어로 한 번에 내려가는 것과 대비된다.

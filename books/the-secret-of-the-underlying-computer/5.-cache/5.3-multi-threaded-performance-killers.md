# 5.3 multi-threaded performance killers

### 1. 캐시 라인

5.3절 세 문제의 토대 — 캐시와 메모리가, 그리고 코어들이 데이터를 주고받는 '단위'.

#### 1) 개념 정의

캐시 라인(cache line)은 CPU 캐시와 메모리가 데이터를 주고받는 최소 단위이자, 멀티코어에서 일관성을 관리하는 최소 단위이기도 한, 고정 크기(대표적으로 64바이트)의 연속된 데이터 덩어리다.

#### 2) 원리 설명

CPU가 메모리에서 딱 1바이트가 필요할 때에도, 실제로는 그 1바이트만 따로 읽어 오지 않고 그것이 속한 라인 전체(≈64바이트)를 한 번에 읽어 온다. \
낱개 바이트를 매번 따로 요청하는 것보다, 일정 크기의 덩어리를 한 번의 전송으로 가져오는 편이 메모리와 캐시를 잇는 버스를 훨씬 효율적으로 쓰기 때문이다(덤으로 바로 옆의 인접 데이터도 함께 캐시에 올라온다).&#x20;

그래서 캐시와 메모리 사이의 모든 주고받음은 바이트가 아니라 '라인'을 기본 단위로 삼는다. \
그리고 코어마다 자기 캐시를 따로 가진 멀티코어 환경에서는, 바로 이 라인이 일관성 관리(coherence)의 단위로도 쓰인다.&#x20;

즉 '어느 코어가 무엇을 고쳤으니 누구의 사본을 무효로 볼지'를 판단하는 기준이 개별 변수나 바이트가 아니라 라인 하나라는 뜻이다.

#### 3) 세부 메커니즘

메모리는 처음부터 라인 크기(예: 64바이트)로 죽 잘려 나뉘어 있다고 생각하면 된다. \
그래서 어떤 주소가 주어지면, 주소의 아래쪽 비트는 '이 라인 안에서 몇 번째 바이트인가(오프셋)'를, 나머지 위쪽 비트는 '메모리의 몇 번째 라인인가, 그리고 그 라인을 캐시에서 구별하는 표식(태그)'을 가리킨다. \
라인이 64바이트라는 것은 이 오프셋에 6비트가 쓰인다는 뜻이기도 하다(2⁶ = 64).

핵심은 쓰기(write)가 일어날 때다. 한 라인 안의 단 1바이트만 고쳐도, 캐시는 그 라인 전체를 '수정됨(dirty)'으로 표시한다 — 나중에 메모리에 되돌려 쓸 때도 바이트가 아니라 라인을 통째로 다룬다. \
멀티코어에서는 여기서 한 걸음 더 나아가, 한 코어가 라인 안을 고치면 다른 코어가 갖고 있던 같은 라인의 사본이 통째로 무효 대상이 된다. 무효화 판정이 바이트 단위가 아니라 라인 단위로 일어나는 것이다.

#### 4) 예시

**예시 1 — 라인 하나에 int 16개**

`int` 하나는 4바이트이므로, 64바이트 라인 하나에는 `int`가 정확히 16개 들어간다.

```c
int arr[16];   // 4바이트 × 16 = 64바이트 = 캐시 라인 하나에 딱 맞음
```

프로그램이 `arr[0]` 하나만 읽어도, CPU는 `arr[0]`이 속한 64바이트 라인을 통째로 캐시에 올린다. 결과적으로 `arr[0]`부터 `arr[15]`까지 정수 16개가 한꺼번에 캐시에 들어온다.

**예시 2 — 정수 하나를 고쳤는데 라인 전체가 무효**

이제 코어 0과 코어 1이 각자 이 라인의 사본을 자기 캐시에 갖고 있다고 하자. 코어 0이 `arr[3]` 하나에 값을 쓰면, 코어 1이 가진 사본은 `arr[3]`뿐 아니라 `arr[0]`\~`arr[15]`를 담은 라인 전체가 무효 상태가 된다. 정수 하나만 건드렸는데 나머지 15개까지 싸잡혀 무효로 처리되는 것 — 이것이 "무효화는 라인 단위로 일어난다"는 말의 구체적인 모습이다.

주소로도 확인할 수 있다. 라인 크기가 64바이트일 때, 어떤 주소가 어느 라인의 몇 번째 바이트인지는 이렇게 갈린다.

```
라인 안 오프셋   = 주소 & 0x3F     // 하위 6비트, 0~63
메모리의 라인 번호 = 주소 >> 6      // 나머지 상위 비트
```

예를 들어 주소 `0x1004`는 오프셋이 `0x1004 & 0x3F = 4`(라인 안 오프셋 4, 즉 라인 시작에서 4바이트 떨어진 위치)이고, `0x1000`부터 `0x103F`까지가 통째로 같은 라인에 속한다. `0x1040`부터는 그다음 라인이다.



이렇게 무효화·공유 판정이 '라인 통째로' 일어난다는 성질이 뒤이어 나올 두 문제의 토대가 된다. 여러 코어가 같은 변수를 두고 쓰기를 반복하면 그 변수가 담긴 라인이 코어 사이를 오가고(→ 캐시 튕김), 서로 완전히 다른 변수라도 우연히 같은 라인에 얹혀 있으면 공유하지도 않은 값 때문에 무효화가 번진다(→ 거짓 공유). 이 두 현상이 왜 성능을 갉아먹는지, 또 어떻게 푸는지는 이어지는 두 소주제에서 다룬다.

### 2. 캐시 튕김 문제

첫 번째 방해자 — 여러 코어가 '같은 변수'를 쓸 때, 그 변수가 담긴 라인이 코어 사이를 오간다.

#### 1) 개념 정의

캐시 튕김(cache bouncing)은 여러 코어에서 도는 스레드가 **하나의 같은 변수**를 반복해서 쓸 때, 그 변수가 들어 있는 캐시 라인의 소유권이 코어들 사이를 쉴 새 없이 오가면서(핑퐁) 오히려 성능이 떨어지는 현상이다.

#### 2) 원리 설명

멀티코어에서는 한 코어가 값을 바꾸면 다른 코어가 갖고 있던 그 값의 사본을 무효화해야 일관성이 유지되고, 이 무효화·전송은 **라인 단위**로 일어난다(→ 캐시 라인).&#x20;

그래서 두 코어가 같은 변수를 번갈아 쓰면, 코어 A가 한 번 쓸 때마다 코어 B가 캐시에 들고 있던 그 라인이 통째로 무효화된다. \
B가 그 변수를 다시 쓰려면 최신 라인을 A 쪽에서 받아와야 하고, 그다음엔 반대로 A의 사본이 무효화된다. 이렇게 라인이 두 코어 사이를 탁구공처럼 오가는 동안 매번 **느린 코어 간 통신과 무효화**가 끼어드는데, 그 비용은 정작 '변수에 1을 더하는' 계산보다 훨씬 크다.&#x20;

그 결과, 일을 여러 코어에 나눠 줬는데도 전체 속도가 도리어 느려진다. \
이것이 캐시 튕김의 대표 증상, 즉 **멀티스레드가 싱글스레드보다 더 느려지는** 상황이다.

#### 3) 세부 메커니즘

한 걸음 더 들어가 순서를 따라가 보자. \
어느 순간 그 라인의 '주인'은 오직 한 코어뿐이다. \
값을 바꾸려면 그 라인을 쓰기 권한으로 독점해야 하기 때문이다.

1. 코어 A가 변수를 쓰면 A가 라인의 주인이 되고, 코어 B가 갖고 있던 사본은 무효 표시가 된다.
2. 이제 B가 같은 변수를 쓰려면, 먼저 A에게 "그 라인의 최신본을 달라"고 요청해 라인을 자기 쪽으로 끌어와 **소유권을 넘겨받은 뒤**에야 쓸 수 있다.
3. 그 순간 A의 사본은 다시 무효가 된다. A가 또 쓰려면 이번엔 B에게서 라인을 되찾아 와야 한다.

즉 두 코어의 쓰기는 동시에 진행되지 못하고 **'한 번에 한 코어씩' 줄 서서 처리된다(직렬화)**. \
라인의 소유권이 A→B→A→B로 왕복하는 이 이동 자체가 병목이라, 코어를 더 붙여도 쓰기는 여전히 순번을 기다리므로 빨라지지 않는다.

#### 4) 예시

이 책이 드는 대표 예시는 **카운터 하나를 10억 번 증가시키기**다.

싱글스레드로 하는 경우:

```c
// 싱글스레드: 카운터 하나를 10억 번 증가
long counter = 0;
for (int i = 0; i < 1000000000; i++) {
    counter++;          // 이 코어의 캐시 안에서만 계속 갱신됨 → 코어 간 통신 0
}
```

두 스레드가 일을 반씩 나눠 하는 경우(증가 연산은 통틀어 10억 번으로 동일):

```c
// 멀티스레드: 두 스레드가 '같은' counter를 각각 5억 번 증가
long counter = 0;       // 두 스레드가 공유하는 하나의 변수

// 스레드 1과 스레드 2가 동시에 실행:
for (int i = 0; i < 500000000; i++) {
    counter++;          // 두 스레드가 같은 변수를 갱신
                        // (동기화는 논외 — 원자연산·락으로 값을 정확히 맞춰도 라인 튕김 때문에 느리다)
}
```

직관적으로는 일을 반으로 나눴으니 두 번째가 더 빨라야 한다. 그러나 실제로는 두 번째가 첫 번째보다 **더 느리다**. 이유는 캐시에 있다. 싱글스레드에서는 `counter`가 한 코어의 캐시 안에 계속 '뜨겁게' 머물러 코어 간 통신이 전혀 없다. 반면 두 스레드 버전에서는 두 코어가 같은 `counter`를 번갈아 쓰므로, 한 스레드가 1을 더할 때마다 상대 코어의 라인이 무효화되고 라인이 코어 사이를 오간다. 매 반복마다 이 핑퐁 비용이 붙는데 그 비용은 '1 더하기'보다 압도적으로 크다. 그래서 계산량을 절반으로 줄였는데도 라인을 주고받느라 전체 시간이 오히려 늘어난다. (한 측정에서는 증가 한 번에 드는 시간이 싱글스레드 약 7ns에서, 두 스레드가 같은 카운터를 함께 증가시키자 약 110ns로 대략 **16배**까지 늘어났다.)

여기서 핵심은 이 느림이 **락이나 원자적 연산의 잘못이 아니라는 점**이다. `counter++`를 안전하게 만드는 것과 무관하게, 값이 정확해도 느림의 원인은 그대로 캐시 라인 튕김에 있다.

**완화책 — 공유 자체를 줄이기.** 캐시 튕김은 '같은 변수를 여러 코어가 쓰는' 데서 오므로, 공유를 없애면 사라진다. 각 스레드가 자기만의 \*\*지역 변수(부분합)\*\*에 따로 세어 두고, 모든 스레드가 끝난 뒤 **맨 마지막에 딱 한 번만** 합친다.

```c
// 완화책: 스레드마다 자기 지역 변수에 누적 → 마지막에 한 번만 합산
// 스레드 1
long local1 = 0;
for (int i = 0; i < 500000000; i++) {
    local1++;           // 이 스레드만 쓰는 지역 변수 → 공유가 없어 튕김도 없음
}
// 스레드 2
long local2 = 0;
for (int i = 0; i < 500000000; i++) {
    local2++;
}

// 두 스레드가 모두 끝난 뒤, 공유 접근은 여기 단 한 번뿐:
long counter = local1 + local2;
```

각 스레드가 자기 지역 변수에만 5억 번 더하는 동안에는 공유가 없으니 라인이 튕기지 않고, 코어 간 통신이 필요한 순간은 마지막에 두 부분합을 한 번 합칠 때뿐이다. 그래서 이번에는 일을 나눈 만큼 실제로 빨라진다.



이 문제는 앞의 '**캐시 라인**'이 세운 성질, 곧 무효화와 전송이 '라인 단위'로 일어난다는 점 위에서 생긴다. 하나의 변수를 두고도 코어들이 그 변수가 든 라인 전체를 통째로 주고받기 때문이다. 한편, 방금의 완화책처럼 카운터를 스레드별 지역 변수로 쪼갰을 때, 그 서로 다른 변수들이 자칫 **같은 캐시 라인에 함께 놓이면** 공유가 없는데도 비슷한 튕김이 되살아날 수 있다. 이 함정이 바로 다음 소주제인 '**거짓 공유**'가 다루는 이야기다.

***

### 3. 거짓 공유 문제

두 번째 방해자 — '서로 다른 변수'인데 같은 라인이라, 공유가 없는데도 튕긴다.&#x20;

#### 1) 개념 정의

거짓 공유(false sharing)는 여러 코어의 스레드가 **논리적으로 완전히 독립된 서로 다른 변수**를 각각 쓰는데도, 그 변수들이 우연히 같은 64바이트 캐시 라인에 놓여 있어서 — 실제로 공유하는 데이터가 하나도 없는데도 — 라인이 코어 사이를 계속 튕기며 성능이 떨어지는 문제다.

#### 2) 원리 설명

캐시 튕김에서 본 그 핑퐁이 여기서도 그대로 일어난다. \
"한 코어가 라인을 쓰면 다른 코어가 가진 같은 라인 사본이 무효화되고, 그 코어는 라인을 다시 읽어와야 한다"는 메커니즘 자체는 이미 배운 것이니 다시 풀지 않는다.&#x20;

**딱 하나만 다르다: 이번엔 두 스레드가 건드리는 것이 서로 아무 관련 없는 별개의 변수다.** \
스레드 1은 변수 `a`만, 스레드 2는 변수 `b`만 쓰고, `a`와 `b`는 코드상 어떤 접점도 없다.&#x20;

그런데 하드웨어는 변수 단위가 아니라 **라인 단위로만** 일관성을 관리하므로, `a`와 `b`가 같은 라인에 얹혀 있으면 스레드 1이 `a`를 쓸 때 스레드 2가 캐시에 들고 있던 그 라인(`b`가 함께 실린)까지 통째로 무효화된다.&#x20;

그래서 두 스레드는 공유하는 것이 하나도 없는데도 서로의 라인을 번갈아 무효화하며 느려진다. \
'거짓(false)'이라 부르는 이유가 바로 이 **어긋남**이다 — 논리적 공유는 0인데, 하드웨어는 "같은 라인"이라는 이유만으로 '공유'로 오판한다.&#x20;

그래서 소스 코드만 봐서는 두 스레드가 완벽히 분리돼 보여 문제가 전혀 눈에 띄지 않는, 은밀한 성능 방해자다.

#### 3) 세부 메커니즘

서로 다른 변수가 우연히 같은 라인에 앉는 상황은 생각보다 흔하다. \
(1) **연속 배치된 배열 원소** — 스레드마다 자기 몫의 카운터를 쓰라고 만든 `count[0]`, `count[1]`, `count[2]`… 8바이트짜리라면 8개가 한 64바이트 라인에 들어차, 스레드 0과 스레드 1이 서로 다른 원소를 써도 같은 라인을 다툰다. \
(2) **인접한 구조체 멤버** — 한 구조체 안의 필드 두 개를 두 스레드가 나눠 쓰는 경우(인접한 두 필드는 대개 같은 라인에 놓인다). \
(3) **나란히 배치된 전역 변수** — 링커가 두 전역 변수를 이웃한 주소에 놓아버린 경우.

이 문제가 코드 리뷰로 안 잡히는 까닭은, 경합의 원인이 소스가 아니라 **컴파일·링크가 정한 메모리 배치**에 있고, 그 배치가 하필 64바이트 라인 경계와 겹쳐야만 드러나기 때문이다. \
변수 이름도, 타입도, 접근 코드도 서로 완전히 갈라져 있으니 화면상으로는 경합이 존재하지 않는다.

해결의 핵심은 **배치를 바꿔 두 변수를 서로 다른 라인에 떼어놓는 것**이다. \
두 변수 사이에 라인 한 개 크기(64바이트)만 한 더미 데이터를 끼워 넣거나, 각 변수를 라인 경계에 맞춰 정렬하면 둘은 다른 라인에 앉는다. \
그러면 스레드 1이 `a`를 써도 스레드 2의 라인(`b`)은 건드려지지 않아 무효화의 사슬이 끊긴다. 메모리를 조금 낭비하는 대신 튕김을 없애 속도를 얻는 맞바꿈이다.

#### 4) 예시

**문제 코드** — 두 스레드가 각자 **다른** 필드만 증가시킨다. 코드만 보면 공유가 전혀 없는데도 느리다.

```c
#define N 100000000L

// a와 b는 8바이트 차이 → 대개 같은 64바이트 라인에 함께 놓인다.
struct Counter {
    long a;   // 스레드 1 전용
    long b;   // 스레드 2 전용
};
struct Counter c;

void *thread1(void *arg) { for (long i = 0; i < N; i++) c.a++; }  // a만 갱신
void *thread2(void *arg) { for (long i = 0; i < N; i++) c.b++; }  // b만 갱신
```

`c.a`와 `c.b`는 논리적으로 무관하지만 같은 라인에 얹혀 있어, 두 스레드가 서로의 라인을 쉴 새 없이 무효화한다 → 거짓 공유로 느려진다.

**해결 코드** — `a`와 `b` 사이에 64바이트 더미를 끼워 `b`를 **다음** 캐시 라인으로 밀어낸다.

```c
struct Counter {
    long a;         // 스레드 1 전용
    int  pad[16];   // 4바이트 × 16 = 64바이트 패딩 (라인 하나만큼 밀어냄)
    long b;         // 스레드 2 전용 → 이제 a와 다른 캐시 라인에 앉는다
};
```

이제 `a`와 `b`는 서로 다른 라인이라 한쪽 쓰기가 다른 쪽 라인을 건드리지 않고, 무효화 핑퐁이 사라진다. \
개선 폭은 상당하다 — 한 측정에서는 패딩 전 약 8.41초가 패딩 후 약 2.98초로 대략 2.8배 빨라졌고, 다른 측정에서는 같은 라인에 두 스레드가 쓸 때가 서로 다른 라인일 때보다 약 3배(376ms 대 119ms) 느렸다.

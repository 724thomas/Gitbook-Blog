# 5.4 Beacon Fires and Memory Barriers

### 1. 명령어의 비순차적 실행: 컴파일러와 OoOE

문제의 출발점 — 왜 내가 적은 순서대로 실행되지 않는가, 그 두 원천.

#### 1) 개념 정의

소스 코드에 적힌 명령어의 순서가 실제 실행되는 순서와 달라지는 현상으로, 그 원천은&#x20;

① 컴파일러가 컴파일 타임에 명령어를 재배치하는 것과&#x20;

② CPU가 실행 타임에 명령어를 순서 없이 실행하는 것(Out-of-Order Execution, OoOE) 두 가지다.

#### 2) 원리 설명

두 재정렬 모두 목적은 하나, "코드를 더 빠르게 돌리기"라는 최적화다. \
컴파일러는 컴파일 타임에 서로 의존성이 없는 명령어들의 순서를 바꿔 더 효율적인 기계어를 만든다. \
CPU는 실행 타임에, 앞선 명령어가 느린 메모리 로드 등으로 멈춰(stall) 있으면 뒤의 독립적인 명령어를 앞당겨 실행해 파이프라인이 노는 시간을 줄인다.&#x20;

두 주체 모두 "단일 스레드에서 관찰되는 결과는 원래 코드와 반드시 같도록" 보장하기 때문에, 프로그램이 혼자 돌 때는 재정렬이 절대 티가 나지 않는다.&#x20;

그런데 이 보장은 어디까지나 "자기 스레드 시점"에 한정된 것이라, 다른 스레드가 보는 순서까지 지켜주지는 않는다.

#### 3) 세부 메커니즘

컴파일러와 CPU가 "순서를 바꿔도 된다"고 판단하는 기준은 사실 동일하다

두 명령어 사이에 **데이터 의존성이 없는가**이다. \
명령 A의 결과를 명령 B가 사용하지 않으면, 재정렬하는 쪽 입장에서 A와 B의 선후 관계는 아무래도 좋다.&#x20;

핵심은, 컴파일러는 소스 코드에서 A가 B보다 위에 적혀 있다는 사실을 "A가 B보다 먼저 일어난다"는 약속(happens-before)으로 해석하지 않는다는 점이다(coffeebeforearch: "source order does NOT imply a happens-before relationship"). \
CPU도 같은 논리로, 멈춘 명령을 건너뛰고 준비된 명령을 먼저 처리한다.&#x20;

문제는 이 "의존성이 없다"는 판단이 오직 자기 스레드 안에서만 참이라는 것이다. \
다른 스레드가 "먼저 쓴 데이터, 나중에 세운 플래그"라는 순서에 의존하고 있어도, 재정렬하는 쪽은 그 스레드 간 약속을 볼 수 없다.&#x20;

그래서 단일 스레드 정확성은 100% 지키면서도, 스레드 간 가정은 조용히 깨진다.

#### 4) 예시

예시 1 — 컴파일러 재정렬 (before/after)

```c
int A, B;
void foo() {
    A = B + 1;
    B = 0;
}
```

최적화 없이 컴파일하면 소스 순서 그대로다.

```asm
mov  eax, DWORD PTR B
add  eax, 1
mov  DWORD PTR A, eax     ; A 저장
mov  DWORD PTR B, 0       ; B 저장
```

`-O2`로 최적화하면 컴파일러가 **B에 대한 저장을 A에 대한 저장보다 앞으로** 옮긴다.

```asm
mov  eax, DWORD PTR B
mov  DWORD PTR B, 0       ; B=0 저장이 먼저!
add  eax, 1
mov  DWORD PTR A, eax     ; A 저장이 나중
```

A와 B는 서로 독립이므로 단일 스레드 결과는 완전히 동일하다(A = 옛 B + 1, B = 0). 하지만 실제 메모리에 쓰이는 순서는 뒤바뀌었다.

같은 재정렬이 왜 멀티 스레드에서 위험한지는 이 코드가 보여준다.

```c
int Value;
int IsPublished = 0;

void sendValue(int x) {
    Value = x;         // 먼저 데이터를 쓰고
    IsPublished = 1;   // 그다음 "준비됐다"고 플래그를 세운다
}
```

만약 컴파일러가 `IsPublished = 1`을 `Value = x`보다 앞으로 옮기면, 다른 스레드가 `IsPublished == 1`을 보고 `Value`를 읽었을 때 **아직 갱신되지 않은 옛 값**을 읽을 수 있다. \
이 스레드 하나만 놓고 보면 여전히 아무 문제가 없다는 점이 함정이다.

예시 2 — CPU의 비순차 실행 (OoOE)

프로그램 순서가 아래와 같다고 하자.

```asm
load  r1, [X]        ; X를 메모리에서 로드 — 캐시 미스로 수백 사이클 대기
add   r2, r3, r4     ; X와 무관한 덧셈
```

`load`가 캐시 미스로 멈춰 있는 동안, CPU는 그 결과를 기다리지 않고 뒤의 독립적인 `add`를 먼저 실행한다.&#x20;

즉 명령어의 실제 실행 순서가 프로그램 순서와 달라진다. 그래도 `r1`은 결국 올바른 X 값을, `r2`는 올바른 합을 갖게 되므로 단일 스레드 결과는 그대로다. \
재정렬은 계측 없이는 눈에 띄지도 않을 만큼 조용히 일어난다.



여기서는 "명령어의 순서"가 바뀌는 두 원천만 다뤘다. 이렇게 재정렬된 쓰기가 다른 코어에 실제로 어떤 순서로 "보이는지"는 캐시·가시성 층이 따로 결정하는 문제이며, 그 이야기는 '캐시도 고려해야 한다'가 이어받는다. 또한 컴파일러 재정렬과 CPU 재정렬은 원천이 다르므로 각각을 막는 수단이 필요한데, 그 수단이 바로 메모리 장벽이다.

### 2. 캐시도 고려해야 한다

재정렬의 또 다른 원천 — 명령어가 아니라 '캐시'가 만드는 쓰기 가시성 지연.

#### 1) 개념 정의

한 코어가 명령어를 순서대로 실행했더라도, 그 쓰기가 스토어 버퍼(store buffer)와 캐시 일관성 전파 지연 때문에 다른 코어에는 늦게(또는 다른 순서로) 보일 수 있다는, 캐시가 만드는 쓰기 가시성(visibility) 문제.

#### 2) 원리 설명

공유 변수에 값을 쓰려면 먼저 그 캐시 라인의 배타적 소유권을 얻어야 하는데, 이는 다른 코어 캐시들과 메시지를 주고받는 일관성 프로토콜을 거치므로 느리다. \
이 대기 동안 코어를 멈추지 않으려고, CPU는 쓰기를 스토어 버퍼라는 큐에 넣어 두고 다음 명령어를 계속 실행한다.&#x20;

그 결과 쓰기 명령은 로컬에서 "끝난" 것처럼 보이지만, 값은 버퍼가 캐시로 빠져나갈 때까지 다른 코어에게는 보이지 않는다 — 즉 쓰기가 늦게 보인다. \
읽는 쪽에서도 무효화(invalidate) 메시지가 곧바로 처리되지 않고 큐에 쌓였다가 나중에 적용되므로, 이미 무효화에 응답(ack)했더라도 잠시 캐시의 옛 값을 계속 읽을 수 있다.&#x20;

이 두 가지가 겹치면 명령어를 전혀 재배치하지 않았는데도 한 코어의 쓰기들이 다른 코어에는 늦게, 그리고 다른 순서로 나타난다. \
fgiesen의 표현대로 "이것은 멀티코어 문제라기보다 멀티캐시 문제"다.

#### 3) 세부 메커니즘

스토어는 사실상 세 단계 작업이다. \
(1) 캐시 라인의 배타 소유권을 요청하고, \
(2) 그 값을 스토어 버퍼에 넣은 뒤, \
(3) 소유권이 도착하면 비로소 캐시에 실제로 기록한다.&#x20;

이 창(window) 동안 값은 쓰는 코어 자신에게만 보이고 다른 코어에는 보이지 않는다. \
여기서 "겉보기 재정렬"이 생기는 핵심은 비대칭이다: 변수 A는 소유권이 없어 스토어 버퍼로 들어가 지연되는데, 변수 B는 이미 캐시에 소유하고 있어 곧바로 기록된다면, 프로그램은 A를 먼저·B를 나중에 썼는데도 다른 코어는 B의 새 값을 A보다 먼저 보게 된다. \
읽는 쪽의 무효화 큐도 대칭적인 원인이다 — 응답만 해 두고 실제 적용은 미뤄지므로, 준비 완료를 알리는 변수는 새 값으로 보이는데 정작 데이터 변수는 옛 값이 그대로 읽힌다.&#x20;

따라서 올바른 동기화를 위해서는 명령어 순서를 맞추는 것만으로 부족하고, 장벽이 스토어 버퍼와 무효화 큐까지 손대 캐시 차원의 가시성을 강제해야 한다는 문제가 남는다.

#### 4) 예시

예시 1 — 메시지 전달(생산자-소비자) 패턴. 초기값은 `data = 0, flag = 0`.

```
코어 0 (쓰기)          코어 1 (읽기)
data = 1;             while (flag == 0) { /* 대기 */ }
flag = 1;            r = data;   // 0을 읽을 수 있다!
```

코어 0가 `data` 라인의 소유권이 없는 상태라면 `data = 1`은 스토어 버퍼로 들어가 지연되고, `flag` 라인은 이미 소유하고 있으면 `flag = 1`이 캐시에 곧바로 반영된다. 코어 1은 `flag == 1`을 보고 루프를 빠져나오지만, `data`의 무효화가 아직 큐에 남아 있어 캐시의 옛 값 `data == 0`을 읽을 수 있다. 명령어 순서는 그대로(코어 0는 `data`를 먼저 썼다)인데도, 코어 1 입장에서는 `flag`가 `data`보다 먼저 보인 셈이다. McKenney의 정리 코드는 바로 이 지점에 메모리 장벽을 넣어 막는다:

```c
void foo(void) { a = 1; smp_mb(); b = 1; }
void bar(void) { while (b == 0) continue; smp_mb(); assert(a == 1); }
```

`smp_mb()`가 없으면 `b == 1`을 확인한 뒤에도 `assert(a == 1)`이 실패(`a == 0`)할 수 있다. (이런 위반이 실제로 나타나는지·정도는 CPU마다 다르다 → "다른 CPU, 다른 천성".)

예시 2 — StoreLoad 패턴(Preshing의 실험). 초기값은 `X = 0, Y = 0`.

```c
// 스레드 1                         // 스레드 2
X = 1;                             Y = 1;
asm volatile("" ::: "memory");     asm volatile("" ::: "memory");
r1 = Y;                            r2 = X;
```

각 스레드는 자기 쓰기(`X = 1` / `Y = 1`)를 스토어 버퍼에 넣은 채, 그 값이 캐시로 빠져나가기 전에 상대 변수를 읽을 수 있다. 그러면 `r1 == 0`이면서 `r2 == 0`인, "둘 다 상대의 새 값을 못 본" 결과가 나온다. 여기서 가운데 줄의 `asm volatile("" ::: "memory")`는 컴파일러 재정렬만 막는 장벽이라 이 현상을 막지 못한다 — 원인이 컴파일러가 아니라 하드웨어(스토어 버퍼)임을 보여 준다. Preshing이 실제로 돌려 보니 이 재정렬은 대략 6600번 반복마다 한 번꼴로 관측됐다.

#### 5) 다른 키워드와의 연결

"명령어의 비순차적 실행"과 짝을 이룬다: 그쪽은 컴파일러·CPU가 명령어 자체를 재배치해 생기는 재정렬이고, 이 소주제는 명령어를 재배치하지 않아도 캐시가 만드는 가시성 지연이라 원인이 다르다(예시 2에서 컴파일러 장벽이 안 통하는 것이 그 증거). 또 여기서 제기한 "장벽이 캐시까지 동기화해야 한다"는 문제를 장벽의 어떤 유형으로 나눠 해결하는지는 "네 가지 메모리 장벽 유형"이 다룬다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **MESI = 일리노이 프로토콜**: 널리 쓰이는 MESI 캐시 일관성 프로토콜엔 '일리노이 프로토콜(Illinois protocol)'이라는 별명이 있다. 1984년 일리노이대 어배너-섐페인의 파파마르코스와 파텔이 발표한 데서 붙은 이름이다.
> * **MESIF와 MOESI**: 실제 CPU들은 MESI를 각자 확장한다. 인텔은 여러 공유 사본 중 하나만 스눕에 답하도록 'F(Forward)'를 더한 MESIF를, AMD는 더러워진 라인을 메모리에 먼저 쓰지 않고도 공유하게 하는 'O(Owned)'를 더한 MOESI를 쓴다.
> * **거짓 공유(false sharing)**: 캐시 일관성이 변수가 아니라 통째로 약 64바이트인 '캐시 라인' 단위로 동작하기 때문에, 서로 다른 스레드가 우연히 같은 라인의 다른 변수를 갱신하기만 해도 라인이 코어 사이를 핑퐁하며 성능이 급락한다. 한 사례에선 MySQL 처리량을 약 50%까지 떨어뜨린 것으로 보고됐고, 해법은 `alignas(64)`나 C++17의 `std::hardware_destructive_interference_size`다.

### 3. 네 가지 메모리 장벽 유형

해법 ① — 재정렬을 막는 도구를 네 종류의 원시 펜스로 나누다.

#### 1) 개념 정의

네 가지 메모리 장벽 유형은 "막을 재정렬의 앞 연산 종류 → 뒤 연산 종류" 조합에 따라 장벽을 **LoadLoad · LoadStore · StoreLoad · StoreStore** 네 원시(primitive) 펜스로 분류한 것이며, 각 장벽은 자기 이름이 가리키는 그 한 방향의 재정렬만 금지한다.

#### 2) 원리 설명

메모리 접근은 읽기(Load)와 쓰기(Store) 두 종류뿐이므로, 장벽을 사이에 둔 "앞 연산 → 뒤 연산"의 순서 쌍도 (LL, LS, SL, SS) 네 가지밖에 없다. 각 장벽은 "장벽 앞의 X 연산은 장벽 뒤의 Y 연산보다 먼저 완료·가시화된다"만 보장하여, 정확히 그 방향의 재정렬 하나만 콕 집어 막는다. 이렇게 잘게 나눠 두면 실제로 필요한 재정렬 금지만 골라 걸 수 있어, 불필요하게 모든 순서를 고정하는 것보다 성능 손실이 작다. 다만 이 네 종류는 개념적 분류이고, 실제 CPU가 네 개의 명령을 그대로 갖는 경우는 드물다 — 하드웨어의 장벽 명령은 보통 이들의 조합으로 제공된다.

#### 3) 세부 메커니즘

각 장벽의 정확한 보장과, 그 재정렬을 만들어 내는 하드웨어 특성(따라서 언제 그 장벽이 필요한지)은 다음과 같다.

| 장벽             | 형태                           | 막는 재정렬 (앞 → 뒤) | 보장 내용                                | 필요한 상황                                                                     |
| -------------- | ---------------------------- | -------------- | ------------------------------------ | -------------------------------------------------------------------------- |
| **LoadLoad**   | `Load1; LoadLoad; Load2`     | Load → Load    | Load1의 데이터가 Load2보다 먼저 로드됨           | 투기적 로드·비순차 실행이 있는 CPU (로드 순서를 늘 지키는 CPU에선 no-op)                           |
| **StoreStore** | `Store1; StoreStore; Store2` | Store → Store  | Store1이 Store2보다 먼저 메모리에 플러시/가시화됨    | 쓰기 버퍼·캐시의 플러시 순서를 보장하지 않는 CPU                                              |
| **LoadStore**  | `Load1; LoadStore; Store2`   | Load → Store   | Load1이 Store2(및 이후 저장)의 플러시보다 먼저 로드됨 | Load→Store 재정렬을 허용하는 약한 순서 CPU에 필요 (x86·SPARC-TSO에선 no-op, ARM·POWER에선 필요) |
| **StoreLoad**  | `Store1; StoreLoad; Load2`   | Store → Load   | Store1이 Load2보다 먼저 메인 메모리에 가시화됨      | 최신 멀티프로세서 대부분에 필요 — 넷 중 가장 비쌈                                              |

핵심은 **StoreLoad가 왜 가장 비싼가**이다. 보통 CPU는 스토어를 쓰기 버퍼(write buffer)에 담아 둔 채(아직 다른 코어에는 보이지 않는 상태로) 뒤의 로드를 먼저 진행시켜 성능을 얻는다. StoreLoad는 이 이점을 포기하고, 앞선 스토어가 **다른 코어에도 보이도록(전역 가시화되도록) 쓰기 버퍼를 완전히 비운 뒤에야** 뒤의 로드를 진행시킨다 — 쿡북의 표현으로는 "쓰기 버퍼에서 로드를 만족시키느라 캐시를 우회하던 메커니즘"을 꺼야 하므로 스톨(stall)이 생겨 비용이 크다. 그 대가로 대부분의 구현에서 StoreLoad는 나머지 세 장벽의 효과까지 포함하는 사실상 "만능(universal) 장벽"으로 동작한다. 한편 LoadStore(Load→Store 재정렬을 막음)는 x86·SPARC-TSO 같은 강한 순서 CPU에서는 no-op이지만, ARM·POWER처럼 Load→Store를 재정렬하는 약한 순서 CPU에서는 실제로 필요하다(각각 dmb·lwsync).

#### 4) 예시

**예시 1 — StoreLoad가 필요한 상호 배제(양쪽 모두 필요).** 두 스레드가 각자 플래그를 쓰고(store) 상대 플래그를 읽는(load) 고전적 패턴이다.

```
// 스레드 1              // 스레드 2
X = 1;      // store     Y = 1;      // store
StoreLoad;               StoreLoad;
r1 = Y;     // load      r2 = X;     // load
```

장벽이 없으면 각 CPU가 자기 store를 쓰기 버퍼에 담아 둔 채 상대 변수를 먼저 읽어(store → load 재정렬), **두 스레드 모두 `r1 == 0 && r2 == 0`** 이라는 결과를 볼 수 있다(둘 다 상대의 쓰기를 못 봄). 두 스레드 모두 store와 load 사이에 StoreLoad를 넣으면 쓰기 버퍼가 비워진 뒤에야 로드가 실행되므로 `r1 == 0 && r2 == 0`은 불가능해진다.

**예시 2 — 발행/구독(StoreStore + LoadLoad가 짝을 이뤄야 함).**

```
// 발행 스레드                 // 구독 스레드
data = 42;    // Store1        while (ready == false) {}  // load ready
StoreStore;                    LoadLoad;
ready = true; // Store2        r = data;                   // load data
```

발행 측 StoreStore는 `data` 쓰기가 `ready` 쓰기보다 먼저 메모리에 플러시되도록 **발행 측 두 저장의 순서**를 보장하고, 구독 측 LoadLoad는 `ready`를 읽은 뒤에야 `data`를 읽도록 **구독 측 두 로드의 순서**를 보장한다(두 로드는 서로 데이터 의존이 없어 약한 순서 CPU에서 재정렬될 수 있다). 한 예시가 StoreStore·LoadLoad **두 유형과 각각의 개별 보장**을 동시에 보여 주는 셈이다 — 발행 측만, 혹은 구독 측만 막아서는 부족하다. 다만 이 둘을 맞물려 "`ready`를 보면 `data`도 보인다"는 스레드 간 _종단 간_ 보장으로 끌어올리는 **짝지음(pairing)** 그 자체는 다음 소주제 '획득-해제 의미론'이 상위 추상으로 다룬다.

#### 5) 다른 키워드와의 연결

* 이 네 원시 펜스를 한쪽 방향으로만 짝지어 조합하면 한 방향만 막는 의미론이 만들어지는데, 그 조합 규칙과 이름은 **"획득-해제 의미론"** 소주제에서 다룬다(여기서는 조합의 재료인 네 원시 펜스까지만).
* StoreLoad가 비싼 배경인 쓰기 버퍼·캐시 가시성 **문제 자체**는 **"캐시도 고려해야 한다"** 에서 제기하며, 이 소주제는 그 위에서 장벽 4종의 정의·조합·용도만 다룬다.
* 실제 코드에서 이 펜스를 손으로 거는 대신 언어가 감싼 형태로 쓰는 방법은 **"C++에서 제공하는 인터페이스"** 로 이어진다.

>
> * **자바에서 온 분류**: 이 네 갈래 분류를 대중화한 것은 뜻밖에도 자바 쪽 문서다. 더그 리(Doug Lea)가 자바 메모리 모델(JSR-133) 구현자를 위해 쓴 'JSR-133 Cookbook for Compiler Writers'가 이 분류를 정리해 퍼뜨렸다.
> * **가장 비싼 것과 가장 싼 것**: 네 유형은 값이 다르다. 같은 쿡북에 따르면 StoreLoad는 "최근의 모든 멀티프로세서가 필요로 하는, 대개 가장 비싼" 장벽인 반면, LoadStore는 따로 필요로 하는 프로세서가 거의 없어 사실상 공짜에 가깝다.

### 4. 획득-해제 의미론

해법 ② — 네 원시 장벽을 한 방향으로 묶어 만든 순서 규칙, 획득과 해제.

#### 1) 개념 정의

획득-해제 의미론은, 읽기에 붙는 **획득(acquire)** 과 쓰기에 붙는 **해제(release)** 가 각각 **한 방향의 재정렬만 막는 단방향(one-way) 순서 규칙**이며, 이 둘을 **짝(pairing)** 지어 한 스레드가 준비한 데이터를 다른 스레드가 안전하게 넘겨받게 하는 규칙이다.

#### 2) 원리 설명

획득은 그 **뒤에 오는** 읽기/쓰기가 획득 연산보다 **앞으로** 재정렬되는 것을 막고, 해제는 그 **앞에 오는** 읽기/쓰기가 해제 연산보다 **뒤로** 재정렬되는 것을 막는다. 둘 다 한쪽 방향만 막는 반투과성(one-way) 장벽이라, 허용된 방향으로는 다른 연산이 새어 통과할 수 있어 양방향을 모두 막는 전면 장벽보다 제약이 약하고 비용이 싸다. 이 성질을 쓰면, 생산자가 데이터를 다 채운 뒤 "준비됐다"는 플래그를 **해제 쓰기**로 발행할 때 앞서 채운 데이터 쓰기가 플래그 발행보다 뒤로 밀리지 않는다. 반대로 소비자가 그 플래그를 **획득 읽기**로 관측하면, 뒤이은 데이터 읽기가 플래그 확인보다 앞당겨지지 않는다. 그 결과 소비자가 플래그를 보는 순간 그 앞의 데이터도 반드시 보이며, 이 "발행 후 관측"이 짝을 이뤄야 비로소 스레드 간 데이터 전달이 성립한다. 획득이 읽기에, 해제가 쓰기에 붙는 이유도 여기서 나온다 — 발행은 다른 스레드가 관측할 **쓰기**여야 하고, 수신은 그 발행을 확인하는 **읽기**여야 하기 때문이다.

#### 3) 세부 메커니즘

핵심은 두 장벽이 **서로 반대 방향**을 막아 그 사이 구간을 가둔다는 점이다. 획득은 "아래에서 위로"(뒤 연산이 앞으로) 넘어오는 것만 막고 앞선 연산이 아래로 새는 것은 허용하며, 해제는 "위에서 아래로"(앞 연산이 뒤로) 넘어가는 것만 막고 뒤 연산이 위로 새는 것은 허용한다. 그래서 획득 하나만으로는 그 앞부분이, 해제 하나만으로는 그 뒷부분이 보호되지 않아 **반드시 짝이 필요**하다. 또 짝이 실제로 성립하려면 획득 읽기가 **바로 그 해제 쓰기가 저장한 값을 읽어야** 한다 — 아무 과거의 해제나 자동으로 연결되는 것이 아니라, 관측한 그 값이 두 스레드를 잇는 연결고리가 된다. 이 두 방향 제약이 맞물리면 "해제 앞의 모든 연산" → "획득 뒤의 모든 연산" 이라는 순서가 스레드를 가로질러 보장된다.

방향을 도식으로 보면:

```
[획득 acquire — 읽기에 부착]
        앞선 연산들          ↓ 아래로 통과 허용(앞선 연산은 뒤로 샐 수 있음)
   ── read-acquire ───────────────────────  ← 획득 장벽
        후속 연산들          ✗ 위로 이동 금지(획득보다 앞으로 못 옴)

[해제 release — 쓰기에 부착]
        앞선 연산들          ✗ 아래로 이동 금지(해제보다 뒤로 못 감)
   ── write-release ──────────────────────  ← 해제 장벽
        후속 연산들          ↑ 위로 통과 허용(후속 연산은 앞으로 샐 수 있음)
```

#### 4) 예시

플래그로 데이터를 넘기는 짝(생산자→소비자). 언어 중립 의사코드로, `store_release`는 해제 쓰기, `load_acquire`는 획득 읽기다.

```
// 공유 상태
data  : 일반 변수        (초기값 0)
ready : 원자 플래그       (초기값 false)

// 생산자 스레드
data = 42                       // (1) 일반 쓰기: 데이터 준비
store_release(ready, true)      // (2) 해제 쓰기로 "발행"
   //  해제 => (1)은 (2)보다 뒤로 못 감. data=42가 ready=true보다 먼저 보인다.

// 소비자 스레드
while (load_acquire(ready) == false) { }   // (3) 획득 읽기로 "수신 대기"
print(data)                                 // (4) 일반 읽기
   //  획득 => (4)는 (3)보다 앞으로 못 옴. ready=true를 본 뒤에야 data를 읽는다.
```

작동 결과: 소비자가 `ready == true`를 관측하면 `data`는 **반드시 42**로 보인다(출력은 항상 42). 짝의 방향이 서로 맞물려 (1)→(2) ··· (3)→(4) 순서가 스레드를 가로질러 유지되기 때문이다.

대조군 — 획득/해제 없이 그냥 일반 변수로 했다면: (1)과 (2)가 재정렬될 수 있어, 소비자가 `ready == true`를 보고도 아직 반영되지 않은 `data == 0`을 읽어 **0을 출력**하는 일이 가능하다. 두 연산에 각각 해제·획득을 붙여 짝지었을 때에만 이 오작동이 사라진다.

#### 5) 다른 키워드와의 연결

획득/해제는 "네 가지 메모리 장벽 유형"에서 나열하는 원시 장벽들을 **조합해 만든 상위 추상**이며(어떤 원시 장벽으로 구성되는지는 그 소주제 소관), 이 의미론을 실제 코드에서 호출하는 구체적 API는 "C++에서 제공하는 인터페이스"에서 다룬다. 또한 락 없이 플래그 하나로 데이터를 넘기는 이 짝 구조는 "잠금 없는 프로그래밍"의 기본 도구가 된다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **이름은 자물쇠에서**: '획득(acquire)'과 '해제(release)'라는 이름은 사실 자물쇠에서 왔다. 락을 거는 동작이 획득을, 푸는 동작이 해제를 필요로 하기 때문이며, 그 사이 메모리 연산들은 한 방향 장벽으로 감싸인 '샌드위치' 안에 갇힌다.
> * **아이테니엄의 ld.acq/st.rel**: 인텔 아이테니엄(IA-64)은 획득/해제를 아예 명령어 집합에 새겼다. 별도 장벽 없이 `ld.acq`(획득 적재)·`st.rel`(해제 저장) 명령 하나로 획득/해제 의미론을 얻을 수 있었는데, 당시로선 드문 설계였다.
> * **ARMv8의 LDAR/STLR**: ARM도 한참 뒤 같은 길을 갔다. 64비트 ARMv8은 `LDAR`(load-acquire)·`STLR`(store-release) 전용 명령을 더했는데, 양방향을 다 막는 `DMB`보다 값싼 한 방향 장벽이라 획득/해제가 일반 장벽보다 저렴하게 구현된다.

### 5. C++에서 제공하는 인터페이스

해법 ③ — 그 의미론을 이식 가능한 코드로 쓰게 해 주는 C++ 표준 인터페이스.

#### 1) 개념 정의

C++11 표준 라이브러리가 원자적 연산과 메모리 재정렬 제어를 이식 가능한 코드로 직접 쓸 수 있게 제공하는 도구 묶음으로, `std::atomic<T>` 템플릿, `std::memory_order` 열거형, `std::atomic_thread_fence` 함수가 그 핵심이다.

#### 2) 원리 설명

C++11 이전에는 재정렬을 막으려면 인라인 어셈블리나 컴파일러 전용 내장함수(`__sync_*`, `_mm_mfence` 등)를 직접 삽입해야 했고, 이는 컴파일러·CPU마다 코드가 달라 이식성이 없었다. C++11부터는 표준이 하드웨어와 컴파일러에 독립적인 인터페이스를 제공한다. 프로그래머는 공유 변수를 `std::atomic<T>`로 선언하고, 그 변수의 load / store / read-modify-write(RMW) 연산마다 `memory_order` 인자를 붙여 "이 연산 주변에서 어떤 재정렬을 금지할지"를 지정한다. 인자를 생략하면 기본값은 가장 강하고 가장 느린 `memory_order_seq_cst`이다. 따라서 프로그래머는 정확성이 요구하는 만큼만 강한 순서를 골라 성능과 안전성을 손수 절충할 수 있다.

#### 3) 세부 메커니즘

`memory_order`에는 여섯 가지 값이 있고, 각 값이 보장하는 것은 아래와 같다.

| memory\_order | 한 줄 보장                                                                                           |
| ------------- | ------------------------------------------------------------------------------------------------ |
| `relaxed`     | 원자성(불가분성)만 보장하고 주변 연산에 순서 제약을 두지 않음. 예: 독립 카운터 `counter.fetch_add(1, std::memory_order_relaxed)` |
| `consume`     | 로드한 값에 **데이터 의존성**이 걸린 연산에 한해 순서를 보장(주로 포인터 추적). 실무에서는 컴파일러 지원이 부실해 대개 `acquire`로 대체됨            |
| `acquire`     | 이 로드 **뒤**의 메모리 연산이 로드 앞으로 재정렬되지 못하게 막음('획득')                                                    |
| `release`     | 이 스토어 **앞**의 메모리 연산이 스토어 뒤로 재정렬되지 못하게 막음('해제')                                                   |
| `acq_rel`     | 읽고-쓰는 RMW 연산 하나에서 로드 부분에는 acquire, 스토어 부분에는 release를 동시에 적용                                      |
| `seq_cst`     | 위 순서에 더해, `seq_cst`로 표시된 **모든** 원자 연산이 하나의 전역 총 순서를 이룸. 원자 연산의 기본값                               |

주로 쓰이는 조합은 로드에 `acquire`, 스토어에 `release`, RMW에 `acq_rel`이다. 다만 이는 관용적 짝일 뿐 배타적 규칙이 아니어서, `seq_cst`는 로드·스토어·RMW 어디에나 쓸 수 있다. 반대로 각 연산이 받을 수 있는 order는 정해져 있다 — 로드는 `relaxed`·`consume`·`acquire`·`seq_cst`만, 스토어는 `relaxed`·`release`·`seq_cst`만 받으며, 맞지 않는 order(예: 로드에 `release`)를 넘기는 것은 정의되지 않은 동작(UB)이다.

`std::atomic_thread_fence`는 특정 원자 변수에 붙지 않는 **독립형 배리어**다. 시그니처는 `void std::atomic_thread_fence(std::memory_order order);` 하나뿐이다. 이 함수를 쓰면 배리어를 원자 변수 접근에서 떼어내 코드의 원하는 지점에 한 번만 배치할 수 있다 — 예컨대 여러 개의 `relaxed` 스토어 앞에 `release` 펜스 하나만 두어 그 스토어 전체에 해제 효과를 주는 식이다. (펜스가 막는 재정렬 조합을 LoadLoad·StoreStore 같은 네 유형으로 분류하는 이야기는 형제 소주제 '네 가지 메모리 장벽 유형'의 몫이며, 여기서는 그것을 부르는 **API**로만 다룬다.)

#### 4) 예시

예시 (1) — `std::atomic` 플래그를 이용한 발행/구독:

```cpp
#include <atomic>
#include <cassert>

std::atomic<bool> ready{false};
int data = 0;                                        // 평범한 비원자 변수

// 생산자 스레드
void producer() {
    data = 42;                                       // (1) 일반 쓰기
    ready.store(true, std::memory_order_release);    // (2) 해제 스토어로 '발행'
}

// 소비자 스레드
void consumer() {
    while (!ready.load(std::memory_order_acquire))   // (3) 획득 로드로 '구독'
        ;                                            // ready가 true가 될 때까지 회전
    assert(data == 42);                              // (4) 항상 성공
}
```

동작 결과: (2)의 `release` 스토어가 (3)의 `acquire` 로드와 "동기화"되면, (2) 이전의 모든 쓰기 — 여기서는 (1)의 `data = 42` — 가 (3) 이후 소비자에게 반드시 보인다. 그래서 (4)의 `assert`는 절대 실패하지 않는다. 만약 `ready`를 그냥 `bool`로 두거나 (3)을 `relaxed`로 읽으면 이 보장이 깨져 소비자가 `data == 0`인 낡은 값을 볼 수 있다.

예시 (2) — `std::atomic_thread_fence`로 배리어를 원자 연산에서 분리(cppreference의 producer-consumer 예):

```cpp
std::atomic<int> arr[3] = {-1, -1, -1};
std::string data[1000];              // 비원자 데이터

// 생산자
void ThreadA(int v0, int v1, int v2) {
    data[v0] = computation(v0);
    data[v1] = computation(v1);
    data[v2] = computation(v2);
    std::atomic_thread_fence(std::memory_order_release);          // 해제 펜스 1개
    std::atomic_store_explicit(&arr[0], v0, std::memory_order_relaxed);
    std::atomic_store_explicit(&arr[1], v1, std::memory_order_relaxed);
    std::atomic_store_explicit(&arr[2], v2, std::memory_order_relaxed);
}

// 소비자
void ThreadB() {
    int v0 = std::atomic_load_explicit(&arr[0], std::memory_order_relaxed);
    int v1 = std::atomic_load_explicit(&arr[1], std::memory_order_relaxed);
    int v2 = std::atomic_load_explicit(&arr[2], std::memory_order_relaxed);
    std::atomic_thread_fence(std::memory_order_acquire);          // 획득 펜스 1개
    if (v0 != -1) { print(data[v0]); }
    if (v1 != -1) { print(data[v1]); }
    if (v2 != -1) { print(data[v2]); }
}
```

동작 결과: 세 개의 store를 모두 `relaxed`로 두었는데도, 그 앞에 `release` 펜스 하나를 두면 세 배열 원소 각각에 `release`를 붙인 것과 같은 효과가 난다. 소비자 쪽도 `acquire` 펜스 하나로 이후의 `data[...]` 접근이 로드보다 앞당겨지지 않게 막는다. 즉 원자 변수마다 강한 order를 붙이는 대신, 배리어를 코드에 딱 한 번 배치하는 방식이다.

#### 5) 다른 키워드와의 연결

`memory_order_acquire`/`release`는 형제 소주제 '획득-해제 의미론'이 정의하는 획득/해제 **개념**을 실제 C++ 코드로 옮기는 수단이며, 한 줄짜리 `memory_order` 인자가 컴파일러 재정렬('명령어의 비순차적 실행')과 캐시 가시성('캐시도 고려해야 한다')을 동시에 통제한다. 다만 이 동일한 인터페이스가 CPU마다 서로 다른 기계어 배리어로 번역되는 부분은 '다른 CPU, 다른 천성'의 영역이다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **"atomic<> Weapons"**: 이 인터페이스를 다룬 가장 유명한 강연은 허브 서터가 2012년 'C++ and Beyond'에서 한 "atomic<> Weapons: The C++ Memory Model and Modern Hardware"다. '무기(Weapons)'라는 제목부터 함부로 다루면 위험한 도구임을 경고한다.
> * **사문화된 consume**: 여섯 개 memory\_order 중 `memory_order_consume`은 사실상 사문화됐다. 유용하게 구현하기가 너무 어려워 주류 컴파일러가 조용히 더 강한 `acquire`로 승격시켜 버리며, 표준 위원회도 사용 자제를 권고했다.
> * **atomic이 늘 락-프리는 아니다**: `std::atomic<T>`가 항상 락 없이 도는 것도 아니다. T가 CPU 원자적 명령으로 감당하기 벅차면 라이브러리가 내부적으로 몰래 뮤텍스로 감싸며, 락-프리가 보장되는 것은 `std::atomic_flag`뿐이라 나머지는 `.is_lock_free()`로 확인해야 한다.

### 6. 다른 CPU, 다른 천성

복병 — 같은 소스도 CPU의 '천성'(강한/약한 순서)에 따라 다르게 재정렬된다.

#### 1) 개념 정의

CPU 아키텍처마다 하드웨어가 기본으로 보장하는 메모리 순서(memory ordering) 모델이 달라서, x86처럼 재정렬을 거의 허용하지 않는 **강한 순서(strong ordering)** 계열과 ARM·POWER처럼 재정렬을 폭넓게 허용하는 **약한 순서(weak ordering)** 계열로 나뉜다.

#### 2) 원리 설명

CPU 설계자는 하드웨어가 프로그래머 몰래 메모리 접근을 어디까지 재정렬해도 되는지를 아키텍처 규약으로 못 박는다. 이때 "동시성 추론의 쉬움"과 "성능·전력 효율"을 맞바꾸는데, x86은 전자를, ARM·POWER는 후자를 택했다. x86은 각 코어가 쓰기 버퍼(store buffer)를 갖지만 모든 코어가 저장들의 전체 순서(Total Store Order, TSO)에 합의하기 때문에, 겉으로 새어 나오는 재정렬이 네 종류 중 단 하나뿐이다. 반면 ARM·POWER는 각 코어가 자기 쓰기를 독립적으로 전파하고 읽기를 뒤로 미룰 수 있어 네 종류가 모두 관찰된다. 그 결과 **똑같은 상위 소스가 컴파일러를 거치면 CPU마다 다른 기계어로 번역되어** — x86에서는 배리어 없이도 맞던 코드가 ARM에서는 명시적 배리어를 넣지 않으면 깨진다. 즉 코드의 정확성이 소스가 아니라 그것이 실행되는 CPU의 "천성"에 달려 있게 된다.

#### 3) 세부 메커니즘

재정렬은 인접한 두 메모리 연산의 네 조합으로 쪼갤 수 있다: LoadLoad(읽기-읽기), LoadStore(읽기-쓰기), StoreLoad(쓰기-읽기), StoreStore(쓰기-쓰기). 이 소주제의 핵심은 **각 아키텍처가 이 중 무엇을 허용하고 무엇을 금지하느냐**다.

| 순서 모델                  | 대표 아키텍처             | 하드웨어가 허용하는 재정렬                                  |
| ---------------------- | ------------------- | ----------------------------------------------- |
| 강한 순서 (strong / TSO)   | x86, x86-64         | StoreLoad 하나만                                   |
| 약한 순서 (weak / relaxed) | ARM, POWER(PowerPC) | LoadLoad·LoadStore·StoreLoad·StoreStore 네 가지 모두 |

주의할 점은 "강한 순서"가 "재정렬 전무"를 뜻하지 않는다는 것이다. x86조차 StoreLoad 하나는 허용한다 — 쓰기 버퍼에 들어간 저장이 아직 메모리에 반영되기 전에, 뒤따르는(다른 주소에 대한) 읽기가 그 저장을 앞질러 실행될 수 있다. 그래서 x86도 순차 일관성(sequential consistency)은 아니다. 약한 순서 아키텍처는 여기서 더 나아가 나머지 세 재정렬까지 열어 두므로, 강한 순서 CPU에서는 하드웨어가 공짜로 막아 주던 순서를 약한 순서 CPU에서는 프로그래머가 배리어로 직접 세워야 한다. 이것이 "x86에서는 배리어가 필요 없던 자리에 ARM에서는 명시적 배리어가 박히는" 번역 차이의 근원이다.

#### 4) 예시

아래는 생산자-소비자(메시지 전달) 패턴이다. 소비자는 `ready`가 1이 될 때까지 기다렸다가 `data`를 읽으므로, 의도대로라면 항상 42가 나와야 한다.

```c
// 공유 변수: int data = 0; int ready = 0;

// 스레드 1 (생산자)          // 스레드 2 (소비자)
data  = 42;                   while (ready == 0) { /* spin */ }
ready = 1;                    print(data);
```

* **x86에서:** 생산자 쪽 두 저장은 StoreStore 재정렬이 금지되어 `data=42`가 `ready=1`보다 먼저 보이고, 소비자 쪽 두 읽기는 LoadLoad 재정렬이 금지되어 `ready==1`을 본 뒤의 `data` 읽기가 옛 값을 집을 수 없다. → **항상 42 출력.** 배리어를 하나도 안 넣어도 맞는다.
* **ARM에서:** StoreStore와 LoadLoad가 모두 허용되므로, `ready=1`이 `data=42`보다 먼저 소비자에게 도달하거나 소비자가 `data`를 먼저 읽어 버릴 수 있다. → `ready==1`을 봤는데도 **`data`가 0으로 출력되는 일이 실제로 발생한다.**

즉 같은 소스가 x86 노트북에서는 수천 번 돌려도 42만 나오다가, ARM 기기에 올리는 순간 이따금 0을 뱉는다 — "한쪽에서 잘 돌던 코드가 다른 쪽에서 깨진다"의 전형이다. 이 패턴을 형식화한 것이 Message Passing(MP) 리트머스 테스트로, 결과 `r1=1, r2=0`(=ready는 새 값인데 data는 옛 값)이 **x86-TSO에서는 불가능·ARM/POWER에서는 가능**하다고 정리된다.

#### 5) 다른 키워드와의 연결

* **네 가지 메모리 장벽 유형:** 이 소주제가 "어떤 CPU가 어떤 재정렬을 허용/금지하는가"를 정해 주면, 그렇게 허용된 재정렬을 실제로 막아 세우는 도구가 그 소주제의 장벽들이다 — 약한 순서 CPU일수록 더 많은 장벽이 필요해진다.
* **C++에서 제공하는 인터페이스:** 위 예시의 "같은 소스, CPU마다 다른 기계어" 문제를 언어 차원에서 감싸, 한 번 작성한 원자 연산을 각 CPU에 맞는 배리어로 자동 번역해 주는 것이 그 인터페이스다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **최약체 DEC 알파**: 역대 가장 약한 메모리 모델은 DEC 알파로, 데이터 의존이 있는 적재끼리도 재정렬할 수 있었다(포인터를 읽고 따라갔는데 낡은 값이 보이는 식). 하도 유별나 리눅스 커널은 알파에서만 실제 명령으로 컴파일되는 전용 장벽 `smp_read_barrier_depends()`를 뒀는데, 결국 `READ_ONCE()`에 흡수되며 폐기됐다.
> * **x86도 재정렬한다**: '강한 순서'로 유명한 x86조차 재정렬을 한다. 제프 프레싱(Jeff Preshing)의 짧은 두 스레드 프로그램은 실제 인텔 제온에서 StoreLoad 재정렬을 평균 약 6,600번에 한 번꼴로 잡아낸다.
> * **IRIW의 관점 불일치**: IRIW('독립적 쓰기에 대한 독립적 읽기') 시나리오에선, 두 스레드가 각각 별개의 플래그를 세울 때 이를 지켜보는 다른 두 스레드가 "어느 쪽이 먼저였는지"를 서로 정반대로 관찰할 수 있다. POWER·구형 ARM에선 허용되지만 x86에선 금지된다.

### 7. 누가 명령어 재정렬에 관심을 가져야 하는가: 잠금 없는 프로그래밍

한 걸음 물러서서 — 이 재정렬 이야기를 대체 누가 신경 써야 하는가.

#### 1) 개념 정의

명령어 재정렬을 손수 신경 써야 하는 사람은 극소수로, 뮤텍스(락)를 쓰는 대다수 개발자는 락 안에 필요한 메모리 장벽이 이미 들어 있어 재정렬을 직접 다룰 필요가 없고, 오직 락을 쓰지 않고 **잠금 없는(lock-free) 코드를 손수 짜는 사람**만 재정렬과 장벽을 직접 챙겨야 한다.

#### 2) 원리 설명

데이터를 스레드끼리 공유할 때 **항상 락을 쓰면**, 재정렬로 인한 데이터 경쟁이 원천적으로 막힌다. 이유는 락을 잠그는 연산에는 "획득", 푸는 연산에는 "해제"의 의미가 라이브러리·컴파일러 수준에서 이미 부여되어 있어서, 임계 구역 안의 읽기·쓰기가 구역 밖으로 새어 나가는 재정렬을 막는 장벽이 자동으로 삽입되기 때문이다. 그래서 락 사용자는 장벽이나 메모리 순서 지정자를 한 글자도 몰라도 올바른 코드를 얻는다("펜스를 손으로 쓰지 말고, 뮤텍스·std::atomic 같은 '임계 구역' 추상이 컴파일러에게 장벽을 대신 쓰게 하라" — Sutter). 반대로 락을 쓰지 않고 원자적 연산만으로 직접 동기화를 짜는 사람은 이 장벽을 스스로 넣어야 하며, 빠뜨리면 코드가 조용히 깨진다. **요컨대 이 절이 길게 다뤄 온 재정렬·장벽 이야기는 '모두를 위한 것'이 아니라, 라이브러리가 대신 장벽을 넣어 줄 수 없는 소수 — 락-프리를 직접 만드는 사람 — 을 위한 안내다.** 이것이 "이 뒤 내용을 계속 읽어야 할 사람은 누구인가"에 대한 답이다.

#### 3) 세부 메커니즘

"장벽이 자동으로 들어간다"를 한 단계 더 들여다보면, `lock()`은 획득 장벽을, `unlock()`은 해제 장벽을 발행한다. 획득/해제가 각각 한 방향만 막는 단방향 장벽이라는 성질 자체는 '획득-해제 의미론'에서 다루고, 이 소주제의 초점은 그 둘이 임계 구역의 **양 끝에 놓였을 때** 벌어지는 일이다. 획득(입구)과 해제(출구)가 마주 보면 임계 구역은 양끝이 막힌 상자가 되어, 안쪽의 갱신이 구역 밖으로 새어 나가지 못한다. 그 결과 구역 안의 갱신은 다음에 같은 락을 잡는 스레드에게 반드시 완성된 상태로 보인다(뮤텍스 구현은 컴파일러·하드웨어 재정렬이 lock/unlock 경계를 넘나들지 못하게 장벽을 포함한다 — offlinemark). 그래서 대부분의 프로그래머는 장벽의 존재 자체를 몰라도 정확한 멀티스레드 코드를 얻는다. 장벽이 락 안에 숨어 있기 때문이다.

#### 4) 예시

**예시 A — 락을 쓰는 다수 (장벽이 자동으로 보장됨).** 진입=획득, 이탈=해제.

```cpp
std::mutex mtx;
int  v = 0;
bool ready = false;

// 생산자 스레드
mtx.lock();      // 획득: 이 지점 아래 연산이 위로 못 올라감
v = 42;
ready = true;
mtx.unlock();    // 해제: 이 지점 위 연산이 아래로 못 내려감

// 소비자 스레드
mtx.lock();
if (ready) use(v);   // ready가 true면 v는 반드시 42
mtx.unlock();
```

개발자는 `memory_order` 같은 것을 전혀 쓰지 않았지만, `lock()`이 획득·`unlock()`이 해제로 번역되어(Sutter) `v = 42`가 `ready = true`보다 먼저 보이는 것이 보장된다. **작동 결과: 항상 정확** — 소비자가 `ready == true`를 봤다면 `v`는 예외 없이 42다.

**예시 B — 같은 로직에서 락만 뺀 순진한 코드 (대조).**

```cpp
int  v = 0;
bool ready = false;
// 생산자: v = 42;  ready = true;
// 소비자: while (!ready) {}  use(v);
```

락이 없으니 획득·해제 장벽도 없다. 컴파일러·CPU가 `v = 42`와 `ready = true`를 자유롭게 재정렬할 수 있어, 소비자가 `ready == true`를 보고도 `v`는 아직 0일 수 있다. **작동 결과: 간헐적으로 깨짐** — 특정 플랫폼·특정 실행에서만 틀리는 재현하기 어려운 버그다. 이걸 락 없이 고치려면 재정렬을 막는 장벽을 손수 넣어야 하고, 바로 그 손수 작업을 해야 하는 사람이 이 소주제가 말하는 대상이다.

#### 5) 다른 키워드와의 연결

* 형제 소주제 '잠금 프로그래밍과 잠금 없는 프로그래밍'이 락과 락-프리의 정의·장단점·선택 기준을 **비교**한다면, 이 소주제는 그 앞에서 "재정렬·장벽 이야기를 계속 읽어야 할 사람이 누구인가"라는 **범위 한정**을 맡는다.
* '네 가지 메모리 장벽 유형'·'획득-해제 의미론'·'C++에서 제공하는 인터페이스'는 그 소수가 손수 다룰 도구를 설명하며, 이 소주제는 그 도구를 **누가 왜** 배워야 하는지에 대한 동기 부여에 해당한다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **헐리히의 합의 수(1991)**: 락-프리의 이론적 토대는 모리스 헐리히(Maurice Herlihy)의 1991년 논문 "Wait-Free Synchronization"이다. 그는 동기화 원시연산을 '합의 수(consensus number)'로 줄 세웠는데, 평범한 읽기/쓰기는 두 스레드조차 합의 못 시켜 1등급인 반면 CAS는 합의 수가 무한(∞)인 '만능'이라, CAS가 락-프리의 주력 도구가 되는 근거가 여기 있다.
> * **이름의 오해**: '락-프리'는 코드에 락이 안 보인다거나 스레드가 절대 안 기다린다는 뜻이 아니다. 락-프리 알고리즘도 경합이 심하면 개별 스레드가 수없이 실패·재시도(스핀)하며, 경합이 적을 땐 오히려 평범한 뮤텍스보다 느릴 수도 있다.
> * **정말 필요한 좁은 곳**: 이 기술이 절실한 곳은 의외로 좁다. 멈추면 소리가 끊기는 실시간 오디오 콜백, OS 커널, 저지연 임베디드 인터럽트 처리 같은 영역이 대표적이고, 보통의 응용 코드에선 그냥 뮤텍스가 정답인 경우가 대부분이다.

### 8. 잠금 프로그래밍과 잠금 없는 프로그래밍

그 소수가 딛고 선 두 세계 — 락 기반과 잠금 없는 프로그래밍의 비교.

#### 1) 개념 정의

잠금(lock) 프로그래밍은 한 번에 하나의 스레드만 임계 영역(critical section)에 들어가도록 상호 배제로 공유 데이터를 보호하고 나머지 스레드는 락이 풀릴 때까지 대기(블로킹)시키는 방식이고, 잠금 없는(lock-free) 프로그래밍은 락 대신 CAS 같은 하드웨어 원자적 연산으로 공유 데이터를 조율하여 "적어도 하나의 스레드는 항상 유한한 단계 안에 전진한다"를 보장하는 논블로킹 방식이다.

#### 2) 원리 설명

락은 임계 영역 접근을 직렬화한다 — 익숙하고 단순하지만, 본질적으로 한 스레드가 락을 쥐면 나머지는 아무 일도 못 하고 멈춘다. 락을 쥔 스레드가 페이지 폴트나 스케줄링 지연으로 늦어지면 그 락이 필요한 어떤 스레드도 전진하지 못하며, 데드락·우선순위 역전·컨텍스트 스위치 오버헤드 같은 대가가 따른다. 특히 카운터 증가처럼 아주 짧은 연산에 락을 쓰는 것은 "유용한 작업 대비 스케줄링 오버헤드 비율"이 지나치게 높은 무거운 방식이다. 잠금 없는 방식은 이 락 자체를 하드웨어의 원자적 읽기-수정-쓰기 연산(대표적으로 CAS)으로 대체한다. 공유 값을 지역 변수로 읽어 새 값을 계산한 뒤 "그동안 값이 바뀌지 않았을 때만" 원자적으로 교체하고, 바뀌었으면 다시 시도한다. 어떤 스레드도 다른 스레드를 기다리며 멈추지 않으므로, 한 스레드가 지연·중단돼도 전체 시스템은 계속 나아간다.

#### 3) 세부 메커니즘

CAS 루프의 본질은 "낙관적 동시성(optimistic concurrency)"이다. 미리 락으로 막는 대신 일단 계산하고 마지막에 충돌 여부만 검사한다. 여기서 lock-free의 진행 보장이 나온다 — 내 CAS가 실패했다는 것은 곧 다른 스레드의 CAS가 성공했다는 뜻이므로, 개별 스레드가 재시도를 반복하더라도 시스템 전체로 보면 매 순간 누군가는 전진한다. 이 지점이 블로킹 방식과의 결정적 차이다. 블로킹에서는 락 홀더가 멈추면 그 락에 걸린 전부가 멈추지만, lock-free에서는 그런 전역 정지가 원리적으로 없다. 대가도 명확하다. 경쟁이 심하면 실패한 CAS의 재시도가 CPU를 낭비하고 특정 스레드가 계속 밀려 기아(starvation)에 빠질 수 있으며, CAS는 "값"만 비교하고 그 사이의 변경 이력은 못 보기 때문에 ABA 문제가 생긴다. 게다가 구현이 플랫폼 의존적이고 타이밍에 민감해, 락 기반 코드보다 추론·디버깅이 훨씬 어렵다.

#### 4) 예시

_예시 1 — CAS로 만든 잠금 없는 카운터_ CAS의 의미(원자적으로: 현재 값이 기대값과 같으면 새 값으로 바꾸고 성공, 다르면 실패)를 의사코드로 쓰면 다음과 같다.

```
bool CAS(addr, expected, desired):
    atomically {
        if (*addr == expected):
            *addr = desired
            return true
        else:
            return false
    }
```

이를 이용해 락 없이 카운터를 1 증가시키는 코드는 다음과 같다(C++).

```cpp
void increment(std::atomic<int>& counter) {
    int old = counter.load(std::memory_order_relaxed);
    while (!counter.compare_exchange_weak(old, old + 1)) {
        // CAS 실패: 다른 스레드가 먼저 바꿈 → old가 자동 갱신되어 재시도
    }
}
```

작동 결과: 두 스레드가 동시에 `old = 5`를 읽어도, 먼저 도착한 쪽만 CAS에 성공해 6으로 만든다. 진 쪽은 `compare_exchange_weak`가 `old`를 현재 값(6)으로 자동 갱신하며 실패를 돌려주므로, 6→7로 재시도해 성공한다. 최종값은 7이다. 어느 순간에도 스레드를 재우거나 깨우지 않으며(논블로킹), 실패한 쪽조차 "다른 쪽이 성공했다"는 사실 위에서 전진하므로 시스템은 멈추지 않는다.

_예시 2 — 두 방식 비교 표_

| 항목     | 락 기반(lock-based)                   | 잠금 없음(lock-free)                              |
| ------ | ---------------------------------- | --------------------------------------------- |
| 블로킹 여부 | 블로킹 — 락 대기 시 스레드 정지                | 논블로킹 — 서로 기다리지 않음                             |
| 진행 보장  | 락 홀더가 지연·중단되면 대기 스레드 전부 정지         | 최소 한 스레드는 유한 단계 내 전진                          |
| 성능·확장성 | 경쟁 시 컨텍스트 스위치·직렬화 오버헤드, 멀티코어 확장 불리 | 멀티코어 고동시성에서 확장 유리·지연 스파이크 감소, 단 경쟁 심하면 재시도 낭비 |
| 구현·디버깅 | 쉽고 익숙, 복잡한 자료구조도 다루기 수월            | 어려움 — 플랫폼 의존, 타이밍 버그, 단순 자료구조에 적합             |
| 대표 위험  | 데드락·우선순위 역전·convoy                 | ABA·기아(starvation)                            |

다만 lock-free가 항상 우월한 것은 아니다 — 익숙함과 복잡한 자료구조 처리에서는 락이 유리하고, lock-free는 특정 자료구조에서만 성숙한 해법이 있다.

#### 5) 다른 키워드와의 연결

잠금 없는 프로그래밍은 메모리 순서를 프로그래머가 직접 책임져야 하는 영역이라, 같은 절의 "획득-해제 의미론"과 "C++에서 제공하는 인터페이스"(std::atomic, memory\_order)가 그대로 이 방식의 구현 도구가 된다. 또 "누가 명령어 재정렬에 관심을 가져야 하는가"가 그 관심의 _주체·동&#xAE30;_&#xB97C; 다룬다면, 이 소주제는 그 주체가 택하는 두 패러다임의 _정의·비교 자&#xCCB4;_&#xC5D0; 초점을 둔다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **진행 보장의 사다리**: '락-프리'보다 촘촘한 사다리가 있다 — 방해-없음(obstruction-free) ⊂ 락-프리(lock-free) ⊂ 대기-없음(wait-free). 가장 약한 obstruction-free는 헐리히·루창코·모이어가 2003년 처음 이름 붙였고, 가장 강한 wait-free는 '모든 스레드가 유한 단계 안에 반드시 끝난다'를 보장한다.
> * **ABA 문제**: 락-프리의 대표적 함정. 값이 A였다가 남몰래 B로 갔다 다시 A로 돌아오면 CAS가 "아무 일 없었다"고 착각하는 것으로, 표준 해법은 값에 버전 카운터를 붙이거나 마게드 마이클(Maged Michael)이 2004년 제안한 '해저드 포인터(hazard pointer)'를 쓰는 것이다.
> * **교과서 큐의 실전 데뷔**: 마이클-스콧(Michael & Scott) 락-프리 큐(1996 PODC)는 이론에만 머물지 않았다. 이 알고리즘은 자바 표준 라이브러리 `java.util.concurrent.ConcurrentLinkedQueue`의 바탕이 됐다.

### 9. 명령어 재정렬에 대한 논쟁

맺음 — 재정렬을 애초에 허용하는 것이 옳은가에 대한 찬반 논쟁.

#### 1) 개념 정의

성능을 위해 CPU와 컴파일러가 메모리 접근 순서를 프로그램에 적힌 대로 지키지 않도록 허용하는 약한 메모리 모델(명령어 재정렬)이, 그만한 성능 이득으로 정당화되는 합리적 설계인가, 아니면 프로그래머에게 과도한 인지 부담과 미묘한 버그를 떠넘기는 잘못된 트레이드오프인가를 두고 벌어지는 찬반 논쟁이다.

#### 2) 원리 설명

재정렬을 허용하면 하드웨어와 컴파일러가 최적화 자유를 얻어 속도·확장성·전력효율을 높일 수 있다. 그러나 그 대가로 "메모리 접근이 프로그램에 적힌 순서대로 보인다"는 직관적 보장이 사라진다. 사라진 이 순서는 누군가가 다시 책임져야 하는데, 하드웨어가 강한 순서를 지켜 떠안을 수도 있고 프로그래머가 명시적 장벽으로 떠안을 수도 있다. 즉 이 논쟁의 뿌리는 "복잡성을 하드웨어에 둘 것인가, 소프트웨어(프로그래머)에 둘 것인가"라는 배분의 문제다. 완화할수록 성능은 오르지만 프로그래밍 난이도도 함께 오르는 구조여서, 정답이 하나로 수렴하지 않고 설계 철학의 대립으로 남는다. 그래서 이것은 "재정렬이 일어나는가"라는 사실 문제가 아니라 "재정렬을 허용하는 것이 바람직한가"라는 가치판단의 문제다.

#### 3) 세부 메커니즘

논쟁은 몇 개의 대립 축으로 정리된다. 찬성(약한 순서 옹호) 측은 스토어 버퍼·비순차 실행 같은 최적화를 자유롭게 쓰게 해 성능을 얻는다는 점을, 반대(강한 순서 옹호) 측은 그 자유가 프로그래머에게 전가하는 정확성 부담을 강조한다.

| 논쟁 축    | 약한 순서 옹호(찬성)                                                | 강한 순서 옹호(반대)                                                            |
| ------- | ----------------------------------------------------------- | ----------------------------------------------------------------------- |
| 성능·효율   | 스토어 버퍼·비순차 실행 등 최적화에 자유를 줘 속도·확장성·전력효율을 높인다                 | 투기적 실행·프리페치가 발전하면서 강한 모델과의 성능 격차가 좁혀져 이득이 줄어든다(Hill)                    |
| 복잡성의 위치 | 복잡성을 라이브러리·커널 등 소수 전문가에게 국한하고, 락 뒤에 있는 대부분의 응용 코드는 영향받지 않는다 | 복잡성을 사실상 모든 프로그래머의 인지 부담으로 떠넘긴다. 직관에 어긋나 "제대로 쓸 수 있는 사람이 극소수"다(Sutter)  |
| 정확성·버그  | 잠금 없는 코드에서 필요한 곳에만 명시적 장벽을 넣어 순서를 되찾으면 된다                   | 재현이 어려운 미묘한 버그를 낳고, 강한 CPU에서 우연히 통과하던 코드가 약한 CPU에서 깨지는 이식성 함정을 만든다      |
| 명세·이식성  | 아키텍처마다 성능 특성에 맞는 자유를 준다                                     | 정의 자체가 "너무 복잡"해진다(ARM/POWER). 그래서 RISC-V 등은 더 다루기 쉬운 모델을 지향한다(Arvind 등) |

이 논쟁에서 가장 첨예한 지점은 "비용의 비대칭성"이다. 재정렬로 인한 오류는 락으로 보호된 평범한 코드에서는 거의 드러나지 않기 때문에, 성능 이득은 널리 퍼지는 반면 위험은 잠금 없는 코드를 다루는 소수에게 집중된다. 반대 진영은 바로 이 점, 즉 "대부분의 코드에는 보이지 않지만 일단 생긴 소수의 버그는 잡아내기가 극도로 어렵다"는 특성이 완화형 모델을 위험하게 만든다고 본다. 반면 찬성 진영은 같은 특성을 근거로, 비용은 국소적이니 나머지 시스템 전체의 성능을 위해 감수할 만하다고 본다. Russ Cox는 완화형 모델의 동작이 "보통의 프로그래머에게 설명할 수 있는 종류가 아니며, 이런 식으로 프로그램을 짜서는 안 된다"고까지 표현한다.

#### 4) 예시

1. **"신뢰성 있게 쓸 수 있는 사람이 100명이나 될까"** — Herb Sutter는 순차 일관성보다 약한 원자적 연산을 직접, 신뢰성 있게 사용할 수 있는 사람이 전 세계에 100명이나 될지 의문이라고 말하며 반대 진영의 인지 부담 논거를 상징적으로 드러냈다. 그는 이어 C++·Java 같은 주류 언어가 "데이터 경쟁이 없는 프로그램에 대한 순차 일관성(SC-for-DRF)"으로 수렴했으며, 따라서 더 약한 모델만 지원하는 하드웨어는 "영구히 불리해져 강해지거나 도태될 것"이라고 주장했다. 이는 소프트웨어 쪽 표준이 강한 순서로 정렬되면서 논쟁이 강한 모델 쪽으로 기울고 있다는 구체적 근거로 인용된다.
2.  **강한 CPU에서 통과하다 약한 CPU에서 깨지는 이식성 함정** — 반대 진영이 즐겨 드는 상황은 아래와 같은 생산자-소비자 패턴이다.

    ```c
    // 스레드 1 (생산자)              // 스레드 2 (소비자)
    data  = 42;                      while (ready == 0) { }
    ready = 1;                       print(data);   // 정말 42가 보장되는가?
    ```

    이 코드가 **강한 순서 CPU(x86)에서는 통과하지만 약한 순서 CPU(ARM·POWER)에서는 이따금 깨진다**는 사실 자체는 '다른 CPU, 다른 천성'이 다룬 그대로다. 논쟁의 핵심은 그 사실을 어떻게 _평가하느&#xB0D0;_&#xB2E4; — 반대 진영은 이를 논거로 삼아 "강한 하드웨어에서 우연히 통과 → 약한 하드웨어로 옮기면 깨짐"이라는 이식성 함정, 그리고 표준이 허용하는 동작이라는 사실이 정작 프로그램이 깨졌을 때는 위안이 되지 못한다는 점을 대표적 위험으로 든다(Cox). 한편 Mark Hill은 투기적 실행·프리페치의 발전으로 순차 일관성과 완화형 모델의 성능 격차가 좁혀지므로, 이런 부담을 감수할 만한 성능 이득이 크지 않다며 단순한 모델을 지지한다. (약한 CPU에서 _왜_ 깨지는지의 아키텍처 차이는 '다른 CPU, 다른 천성'에서, 재정렬의 기본 메커니즘은 '명령어의 비순차적 실행'에서 다룬다.)

#### 5) 다른 키워드와의 연결

이 논쟁은 "명령어의 비순차적 실행"과 짝을 이룬다. 후자가 재정렬이 _어떻게_ 일어나는가(사실·메커니즘)를 다룬다면, 이 소주제는 그것이 _바람직한가_(가치판단)를 다룬다. 또한 "네 가지 메모리 장벽 유형"·"획득-해제 의미론"·"C++에서 제공하는 인터페이스"는 이 논쟁의 타협점(완화하되 필요할 때 프로그래머가 순서를 되찾는 도구)에 해당하며, "잠금 없는 프로그래밍"은 이 논쟁의 비용과 위험이 실무에서 가장 첨예하게 부딪히는 현장이다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **힐의 1998년 선언**: 논쟁의 이정표 격 글이 마크 힐(Mark Hill)이 1998년 IEEE Computer에 실은 "Multiprocessors Should Support Simple Memory Consistency Models"다. 어차피 CPU가 추측 실행을 하는 마당에, 공격적으로 약한 모델은 프로그래머에게 떠넘기는 복잡성에 비해 성능 이득이 충분치 않다고 주장했다.
> * **토르발스의 독설(2014)**: 리눅스 창시자 리누스 토르발스는 강한 순서 진영의 유명한 논객이다. 그는 2014년 커널 메일링 리스트에서 "약한 메모리 순서를 좋아하는 사람들은 틀렸고, 가능하면 번식을 자제하는 편이 낫다"고까지 적었다.
> * **ARMv8의 항복(2018)**: 이 논쟁은 탁상공론에 그치지 않았다. 형식 검증 연구자들과 ARM이 "옛 모델의 복잡성 일부는 그 이득으로 정당화되지 않는다"고 결론 내리면서, 2018년 ARMv8은 더 단순한 '멀티카피 원자성(multicopy-atomic)' 모델로 공식 개정됐다.

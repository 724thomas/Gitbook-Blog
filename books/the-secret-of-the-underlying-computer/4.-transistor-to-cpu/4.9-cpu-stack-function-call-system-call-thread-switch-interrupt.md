# 4.9 CPU, Stack, function call, system call, thread switch, interrupt

### 1. 레지스터

CPU가 멈췄다 이어가는 이야기의 가장 작은 벽돌부터 놓는다 — CPU 안의 빠른 저장소, 레지스터다.

#### 1) 개념 정의

레지스터(register)는 CPU 안에 들어 있는, 매우 빠르지만 크기가 아주 작은 임시 저장 공간으로, 연산에 쓰이는 값을 잠깐 담아 두는 곳이다.

#### 2) 원리 설명

CPU는 계산을 하려면 계산할 값(피연산자)을 어딘가에서 꺼내 와야 한다. 그런데 값이 들어 있는 메모리(RAM)는 CPU 바깥에 있어서 접근이 느리다. 주소를 메모리 쪽으로 보내고, 위치를 찾고, 값을 되돌려 받는 여러 단계를 거치기 때문이다. 만약 CPU가 계산할 때마다 매번 이 느린 메모리를 직접 들락거리면 계산 속도가 메모리 속도에 발목을 잡힌다. 그래서 CPU는 바로 옆(내부)에 아주 빠른 저장 공간을 몇 개 두고, 계산에 쓸 값을 여기에 잠깐 올려놓은 뒤 그 위에서 연산한다. 이 작은 저장 공간이 바로 레지스터다.

#### 3) 세부 메커니즘

* **왜 그렇게 빠른가**: 레지스터는 물리적으로 CPU 내부, 연산 장치(ALU) 바로 옆에 있어 값을 주고받는 거리가 거의 없고, 빠르게 읽히도록 설계된 회로를 쓴다. 그래서 레지스터 읽기는 사실상 즉시 끝나는 반면, 메인 메모리 접근은 그에 비해 훨씬 오래 걸린다. (구체적인 속도 배수는 아래 TMI 참고.)
* **왜 개수가 적은가**: 이렇게 빠른 회로는 비싸고 자리를 많이 차지한다. 그래서 레지스터는 전체 메모리에 비하면 극소량만 둔다. 값을 오래 보관하는 창고가 아니라, 지금 당장 계산에 쓰는 값만 잠깐 올려 두는 작업대에 가깝다.
* **범용 vs 특수(구분만)**: 아무 데이터나 주소나 자유롭게 담아 두루 쓰는 **범용 레지스터**가 있고, 특정 용도만 전담하는 **특수 레지스터**가 따로 있다. 이 소주제에서 다루는 것은 범용 레지스터 쪽이다.

#### 4) 예시

메모리에 있는 값 a, b를 더해서 다시 메모리에 저장한다고 하자. 값은 곧장 메모리에서 더해지는 게 아니라, 일단 레지스터로 "올라온" 뒤 연산되고, 결과가 레지스터에 남았다가 메모리로 "내려간다".

```
LOAD  R1, [a]      ; 메모리의 a 값을 레지스터 R1로 올림 (느린 메모리 접근)
LOAD  R2, [b]      ; 메모리의 b 값을 레지스터 R2로 올림
ADD   R3, R1, R2   ; ALU가 R1과 R2를 더해 결과를 R3에 남김 (빠른 레지스터 위에서 계산)
STORE [c], R3      ; R3의 결과를 메모리 c 자리로 내림
```

핵심은 가운데 `ADD` 한 줄이다. 실제 덧셈은 메모리가 아니라 레지스터(R1, R2 → R3) 위에서 순식간에 일어난다. 값을 미리 레지스터에 올려 두었기 때문에 계산 자체는 느린 메모리를 기다리지 않는다.

#### 5) 다른 키워드와의 연결

지금 설명한 "빠르고 작은 저장 공간"이라는 성질은 모든 레지스터의 공통 바탕이다. 같은 절의 **스택 포인터**, **명령어 주소 레지스터**, **상태 레지스터**는 이 공통 바탕 위에서 각자 한 가지 특별한 역할을 맡도록 특화된 특수 레지스터들이며, 그 각각의 동작은 이어지는 소주제에서 다룬다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **레지스터 vs 메모리, 수백 배의 격차**: 레지스터 접근은 사실상 CPU 클럭 1사이클(거의 0에 수렴)이지만, L1 캐시는 약 4사이클, 메인 메모리는 수백 사이클(대략 100\~300+)이 걸린다. 컴파일러가 자주 쓰는 변수를 어떻게든 레지스터에 붙들어 두려 애쓰는 이유가 이 격차다.
> * **보이는 16개, 숨은 수백 개**: 프로그래머가 보는 레지스터(x86-64 범용 16개)는 '이름표'에 가깝다. 인텔 Skylake 코어는 정수용 180개 + 부동소수점 168개의 물리 레지스터를 숨겨 두고, '레지스터 리네이밍'으로 이름을 갈아끼워 명령을 순서를 뒤바꿔(out-of-order) 병렬 실행한다.
> * **1967년에 나온 아이디어**: 레지스터 리네이밍의 원조 알고리즘은 IBM의 로버트 토마술로가 1967년 System/360 Model 91에 구현했고, 그는 이 공로로 1997년 에커트-모클리상을 받았다. 발표 당시엔 거의 안 쓰이다가 1990년대 비순차 실행이 대세가 되며 되살아났다.

### 2. 스택 포인터

특수 레지스터의 첫 번째 — 스택의 꼭대기를 홀로 책임지는 스택 포인터다.

#### 1) 개념 정의

스택 포인터(Stack Pointer, SP)는 스택의 최상단 위치(주소) 하나만을 담아 두는 특수한 레지스터다. 스택 전체를 들고 다니는 게 아니라, "지금 스택의 꼭대기가 메모리의 몇 번지인가"라는 주소 값 하나만 기억한다.

#### 2) 원리 설명

스택은 데이터가 계속 쌓였다 빠지는 공간이라, 꼭대기의 위치는 고정되어 있지 않고 계속 변한다. 그렇다면 CPU는 "지금 이 순간 꼭대기가 어디인지"를 어딘가에 적어 두어야 하는데, 그 역할을 하는 것이 스택 포인터다. 스택 포인터가 항상 꼭대기 주소를 담고 있으므로, 값을 넣을 때도 뺄 때도 "스택 포인터가 가리키는 곳"을 기준으로 삼는다. 그리고 값을 넣거나 뺄 때마다 스택 포인터의 값 자체가 함께 바뀌어, 늘 최신 꼭대기를 가리킨다. 이것이 "스택 포인터가 꼭대기를 추적한다"는 말의 뜻이다.

#### 3) 세부 메커니즘

* **push (값 넣기)**: ① 스택 포인터를 한 칸만큼 증감시켜 새 꼭대기 주소로 옮긴 뒤 ② 그 새 위치에 값을 저장한다.
* **pop (값 빼기)**: push의 반대 순서다. ① 현재 스택 포인터가 가리키는 위치에서 값을 읽고 ② 스택 포인터를 push 때와 반대 방향으로 한 칸 증감시켜 이전 꼭대기를 가리키게 한다.

여기서 "한 칸"의 크기는 넣고 빼는 값의 크기(예: 4바이트짜리 값이면 4)만큼이다. 자라는 방향은 관례적으로 **대개 스택이 높은 주소에서 낮은 주소 쪽(아래쪽)으로** 자란다. 이 경우 push하면 스택 포인터 값이 작아지고, pop하면 커진다. 반대로 위쪽으로 자라는 방식도 있으며 이때는 증감 방향이 뒤바뀐다. 어느 방향이든 원리는 같다 — push와 pop에서 스택 포인터가 서로 반대로 움직여 꼭대기를 따라간다.

#### 4) 예시

스택이 아래쪽(낮은 주소 방향)으로 자라고, 4바이트짜리 값을 다룬다고 하자. 지금 스택 포인터에 `0x1000`이 들어 있다.

```
[값 하나를 push]
push 이전:  SP = 0x1000
① SP를 4만큼 감소  →  SP = 0x0FFC
② 0x0FFC 번지에 값을 저장
push 이후:  SP = 0x0FFC   (새 꼭대기)

[이어서 그 값을 pop]
pop 이전:  SP = 0x0FFC
① 0x0FFC 번지에서 값을 읽음
② SP를 4만큼 증가  →  SP = 0x1000
pop 이후:  SP = 0x1000   (원래 꼭대기로 복귀)
```

스택 포인터가 push 때와 정확히 반대로 움직여 `0x1000`으로 되돌아왔고, 스택은 넣기 전 상태가 됐다.

#### 5) 다른 키워드와의 연결

스택 포인터는 여러 레지스터 중 하나(**레지스터**)이되 "스택 꼭대기 주소"라는 전용 값을 맡았다. 스택이라는 자료구조가 왜 중첩에 잘 맞는가는 **중첩과 스택**이, 함수 호출 때 스택에 무엇을 어떻게 쌓는가는 **함수 호출과 실행 시간 스택**이 다룬다 — 그 쌓기·빼기 과정에서 실제로 오르내리는 것이 바로 이 스택 포인터다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **세대마다 바뀌는 이름 + 정렬 규칙**: x86에서 스택 포인터 이름은 16비트 SP → 32비트 ESP → 64비트 RSP로 바뀐다. x86-64 System V ABI는 함수 진입 순간 스택이 16바이트 경계에 정렬돼 있어야 한다고 못 박는데, 이게 깨지면 정렬된 메모리를 요구하는 SSE 명령에서 크래시가 날 수 있다.
> * **공짜 영역 '레드존'**: 리눅스 x86-64에는 RSP '아래쪽' 128바이트를 스택을 늘리지 않고도 함수가 마음대로 쓸 수 있는 '레드존'이 있다. 다른 함수를 부르지 않는 잎 함수(leaf function)는 스택 포인터를 안 건드리고 이 영역만으로 지역 변수를 처리해 명령 몇 개를 아낀다(단 윈도우 x64엔 없음).
> * **커널은 레드존을 꺼 버린다**: CPU가 인터럽트 핸들러를 부를 때는 레드존을 존중하지 않고 그 위에 데이터를 덮어써 버린다. 그래서 리눅스 커널은 커널 코드를 컴파일할 때 `-mno-red-zone` 옵션으로 레드존을 아예 끈다.

### 3. 명령어 주소 레지스터

두 번째 특수 레지스터 — 지금 실행 흐름이 어디 있는지를 홀로 가리키는 프로그램 카운터(PC)다.

#### 1) 개념 정의

명령어 주소 레지스터(instruction address register)는 다음에 실행할 명령어가 메모리 어디에 있는지 그 주소를 담는 특수 레지스터다. 가장 널리 쓰이는 이름이 \*\*프로그램 카운터(Program Counter, PC)\*\*이고, 인텔 x86 계열에서는 \*\*명령어 포인터(IP)\*\*라고도 부른다 — 모두 같은 것을 가리키는 이름이다.

#### 2) 원리 설명

CPU는 프로그램을 실행할 때 ① 인출(PC가 가리키는 주소의 명령을 읽음) → ② 실행 → ③ 다시 인출을 반복한다. 여기서 PC는 항상 "다음에 인출할 명령의 주소"를 들고 있어, CPU는 매 순간 PC만 들여다보면 어디를 실행할지 안다. 명령어들이 보통 메모리에 순서대로 놓여 있으므로 PC가 한 칸씩 나아가면 명령들이 차례로 실행된다. 즉 \*\*PC 값이 곧 "실행 흐름의 현재 위치"\*\*이고, 이 값이 어떻게 바뀌느냐가 프로그램의 실행 순서를 결정한다.

#### 3) 세부 메커니즘

* **(1) 순차 실행 — 자동 증가**: 명령을 하나 인출하고 나면 CPU는 PC를 방금 인출한 명령어의 길이만큼 자동으로 증가시킨다. 그러면 PC는 바로 뒤의 다음 명령을 가리킨다(명령이 4바이트면 4씩, 2바이트면 2씩).
* **(2) 흐름 변경 — 새 주소로 덮어쓰기**: 분기(branch)·점프(jump)·호출(call)·복귀(return)를 만나면 PC는 자동 증가 대신 완전히 새로운 주소로 덮어써진다. 조건 분기는 조건이 맞으면 목표 주소로 바뀌고, 아니면 그냥 자동 증가해 다음 명령으로 간다.

정리하면 PC는 "가만두면 자동으로 다음 칸으로 증가하고, 흐름을 바꾸는 명령이 나오면 새 주소로 덮어써지는" 레지스터다. 이 단순한 규칙 하나로 순차 실행과 흐름 변경이 모두 표현된다.

#### 4) 예시

명령어가 4바이트인 CPU를 생각하자.

```
[순차 실행]
PC = 0x100  →  0x100 명령 인출·실행 → PC 자동 증가(+4)
PC = 0x104  →  0x104 명령 인출·실행
PC = 0x108  →  ...

[점프가 PC를 덮어쓰는 경우]  0x104가 JUMP 0x200 이라면
PC = 0x104  →  JUMP 0x200 실행 → 자동 증가(0x108)가 아니라 PC ← 0x200
PC = 0x200  →  흐름이 여기로 건너뜀
```

`JUMP 0x200`을 실행하는 순간 PC는 `0x108`로 증가하지 않고 `0x200`으로 바뀐다. **PC 값을 무엇으로 바꾸느냐가 곧 프로그램이 다음에 어디를 실행할지를 결정한다.**

#### 5) 다른 키워드와의 연결

PC도 **레지스터**의 한 종류이되 "다음 실행 명령 주소"만 담는다. 조건 분기에서 "조건이 맞는지"의 판단 재료는 **상태 레지스터**에 있고, 그 판단에 따라 실제로 흐름을 옮기는 것이 PC다. 호출·복귀 때 PC가 바뀌며, 그 복귀 주소를 스택에 저장·복원하는 절차는 **함수 호출과 실행 시간 스택**이 다룬다. 나아가 인터럽트·스레드 전환·시스템 호출도 공통적으로 "지금 실행 위치(PC)를 저장해 두었다가 나중에 복원"하는 골격을 갖는다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **아키텍처마다 다른 이름 + RIP 상대 주소**: x86은 IP/EIP/RIP, ARM은 그냥 PC(옛 R15)라 부른다. x86-64는 'RIP 상대 주소 지정'을 도입해 현재 명령 위치 기준의 상대 주소로 데이터를 가리킬 수 있게 했고, 덕분에 위치 독립 코드(PIC)가 훨씬 값싸졌다.
> * **ARM에서 PC를 읽으면 +8**: 32비트 ARM에서 PC를 읽으면 '지금 실행 중인 명령의 주소 + 8'이 나온다. 3단 파이프라인(인출-해독-실행)의 유산으로, PC는 실행 중인 명령이 아니라 그보다 두 개 앞서 인출 중인 명령을 가리키기 때문이다(Thumb 모드에선 +4).
> * **PC의 미래를 점치는 분기 예측기**: 현대 CPU는 PC가 분기에서 어디로 튈지 미리 찍는 '분기 예측기'를 두는데, 잘 만든 예측기의 적중률은 95%를 훌쩍 넘는다. 빗나가면 이미 파이프라인에 채워 넣은 명령들을 전부 버리고 다시 채워야 해 수십 사이클을 낭비한다.

***

### 4. 상태 레지스터

세 번째 특수 레지스터 — 방금 한 계산이 어떻게 끝났는지를 요약해 두는 게시판이다.

#### 1) 개념 정의

상태 레지스터(status register)는 산술·논리 연산의 결과 상태를 비트 하나하나(플래그)로 기록해 두는 특수 레지스터다. "결과가 0이었나?", "자리올림이 있었나?", "음수였나?" 같은 물음의 답을 CPU가 스스로 켜고 꺼서 남겨 둔다. 플래그 레지스터, 프로그램 상태 워드(PSW)라고도 한다. (연산 결과 외에 CPU 모드 같은 상태도 일부 담기지만, 여기서는 연산 결과 플래그에 초점을 둔다.)

#### 2) 원리 설명

CPU 안에서 실제로 더하고 빼는 부품은 ALU(산술·논리 연산 장치)다. ALU는 계산 결과 값만 내놓는 게 아니라, 그 계산이 어떻게 끝났는지를 알리는 부수 신호(결과가 0인지, 자리올림이 났는지, 최상위 비트가 1인지 등)도 함께 내보낸다. 이 신호들이 상태 레지스터의 각 플래그 자리에 저장된다. 왜 남겨 둘까? CPU가 스스로 갈림길을 정하게 하기 위해서다. 프로그램은 "두 값이 같으면 여기로, 아니면 저기로"처럼 조건에 따라 길을 나눠야 하는데, CPU는 일단 계산을 한 번 하고 그 결과 상태를 플래그로 받아 둔 뒤, 조건 분기 명령이 그 플래그를 읽어 분기 여부를 정한다.

#### 3) 세부 메커니즘

입문 수준에서 알아 둘 대표 플래그는 넷이다.

| 플래그    | 이름             | 언제 켜지나                                     |
| ------ | -------------- | ------------------------------------------ |
| **ZF** | 제로(Zero)       | 연산 결과가 정확히 0일 때                            |
| **CF** | 캐리(Carry)      | **부호 없는** 계산에서 결과가 비트 폭을 넘어 자리올림/내림이 생겼을 때 |
| **SF** | 부호(Sign)       | 결과의 최상위 비트가 1, 즉 결과가 음수일 때                 |
| **OF** | 오버플로(Overflow) | **부호 있는** 계산에서 결과가 표현 범위를 벗어났을 때           |

캐리(부호 없는 관점)와 오버플로(부호 있는 관점)는 자주 헷갈리므로 구분해 두자. 또한 비교 명령 `CMP A, B`는 내부적으로 `A − B`를 계산하되, 보통의 뺄셈과 달리 **결과 값은 버리고 플래그만 세운다.** 그래서 두 값이 같으면 `A − B = 0`이라 ZF가 켜지고, 크기 비교도 함께 세워진 플래그 조합으로 판별한다.

#### 4) 예시

어떤 값에서 5를 빼 0이 되는지 보고, 같으면 특정 위치로 뛰는 코드를 보자.

```asm
cmp  R1, 5      ; R1 - 5 를 계산(결과는 버림), 플래그만 세운다
je   equal      ; ZF == 1 이면(=결과가 0, 즉 두 값이 같으면) equal 로 점프
; ... 여기는 같지 않을 때 실행 ...
equal:
; ... 같을 때 실행 ...
```

`R1`이 5라면 `5 − 5 = 0`이므로 ZF가 1로 켜진다. 바로 뒤의 `je`(jump if equal)는 결과 값을 다시 계산하지 않고 **오직 상태 레지스터의 ZF만 읽어서**, 1이면 `equal`로 점프하고 0이면 다음 줄로 진행한다. 반복문에서 카운터를 1씩 줄이다 0이 되는 순간 ZF가 켜지고 "0이 아니면 다시 위로" 같은 조건 분기가 반복 종료를 정하는 것도 같은 원리다.

#### 5) 다른 키워드와의 연결

상태 레지스터도 **레지스터**의 한 종류이되 "연산 결과 상태"를 담는다. 플래그가 _갈림길의 조&#xAC74;_&#xC774;라면, 그 판단에 따라 실제로 길을 바꾸는 것은 \*\*명령어 주소 레지스터(PC)\*\*다 — 둘이 짝을 이뤄 제어 흐름이 갈라진다. 상태 레지스터의 현재 값도 CPU의 **상황 정보** 일부라서 스레드 전환·인터럽트 때 함께 저장·복원된다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **패리티 플래그의 어정쩡한 유산**: x86 EFLAGS의 패리티 플래그(PF)는 연산 결과 '하위 8비트'의 1의 개수가 짝수인지만 본다 — 64비트 결과라도 최하위 바이트만 검사한다. 이 동작은 1974년 인텔 8080과의 하위 호환을 위해 물려받은 유산이다.
> * **잘 안 알려진 플래그들**: 캐리·제로·부호 말고도 보조 캐리(AF, 하위 4비트 자리올림 — BCD 보정용), 방향 플래그(DF, 문자열 명령의 진행 방향), 인터럽트 플래그(IF, 인터럽트 수신 허용 여부) 등이 있다.
> * **ARM의 NZCV와 조건부 실행**: ARM에서는 CPSR 최상위 4비트 N(음수)·Z(0)·C(자리올림)·V(오버플로)가 같은 역할을 한다. ARM 특유의 조건부 실행("같을 때만 이 명령 실행")은 이 NZCV 비트를 보고 명령 하나하나를 실행할지 결정한다.

### 5. 상황 정보

앞의 레지스터들을 한데 묶으면 무엇이 될까? 바로 "그 순간의 실행 상태" 전체다.

#### 1) 개념 정의

상황 정보(context, 문맥)란 실행 중인 작업이 멈추는 그 순간의 실행 상태를 통째로 담은 스냅샷으로, 나중에 정확히 그 지점부터 이어가기 위해 저장해 두어야 하는 값들의 묶음이다.

#### 2) 원리 설명

프로그램의 진행 상태는 대단히 거창한 무언가가 아니라, 그 시점의 레지스터 값들이 이룬 조합 하나로 완전히 결정된다. 그래서 이 묶음이 곧 "실행 상태 그 자체"이며, 실행 상태를 하나도 빠짐없이 담고 있기에 이것만 있으면 그 작업을 완전히 되살릴 수 있다. 반대로 하나라도 빠지거나 어긋나면 스냅샷이 불완전해져, 재개된 작업은 엉뚱한 곳으로 가거나 잘못된 값으로 이어진다. "실행 상태 = 값들의 묶음"이라는 이 관점, 그리고 재개 가능성이 이 묶음의 완전함에서 나온다는 점이 이 소주제의 핵심이다.

#### 3) 세부 메커니즘

상황 정보는 앞 소주제들에서 개별적으로 다룬 레지스터들을 한데 모은 것이다. 각 레지스터의 동작은 이미 배웠으므로, 여기서는 "각자가 없으면 왜 스냅샷이 불완전해지는가"만 짚는다.

* **프로그램 카운터(PC)** — 재개 지점 그 자체. 빠지면 "어디서부터 이어갈지"를 알 수 없다.
* **스택 포인터(SP)** — 진행 중이던 호출 프레임의 꼭대기를 가리킨다. 빠지면 진행 중이던 함수 호출 관계를 잃는다.
* **범용 레지스터** — 아직 메모리에 안 쓰인 중간 계산값. 빠지면 계산 중이던 값을 잃어 재개된 계산이 어긋난다.
* **상태 레지스터(플래그)** — 직전 연산으로 세워진 조건 플래그. 빠지면 재개 직후의 조건 분기가 엉뚱한 방향으로 갈 수 있다.

이 넷이 함께 있어야 비로소 "그 순간의 실행 상태"가 빠짐없이 담긴다. 그래서 상황 정보는 이들 중 하나가 아니라 이들 전부의 묶음으로 정의된다.

#### 4) 예시

작업 A가 `sum = a + b`를 막 계산해 그 결과가 범용 레지스터에 들어 있고, PC가 그 다음 줄을 가리키던 참이라고 하자. 이 순간의 스냅샷은 다음 값들의 조합이다.

```
A의 상황 정보(스냅샷) = {
    PC            = 다음에 실행할 줄의 주소
    범용 레지스터  = 계산해 둔 sum
    SP            = 현재 호출 프레임의 꼭대기
    상태 레지스터  = 직전 연산으로 세워진 플래그
}
```

이 조합 하나가 A의 실행 상태를 남김없이 담고 있어, A를 완전히 되살리기에 충분하다. 반대로 이 중 PC가 빠지면 어디서부터 이어갈지 알 수 없고, sum이 든 레지스터가 빠지면 계산 결과를 잃는 식으로, 하나만 빠져도 스냅샷은 불완전해진다.

#### 5) 다른 키워드와의 연결

상황 정보는 **레지스터·스택 포인터·명령어 주소 레지스터·상태 레지스터**를 새로 정의하는 게 아니라 한 묶음으로 모은 것이며, 이들이 여기서는 스냅샷의 "구성 요소"로 다시 등장한다. 이 스냅샷을 실제로 저장·복원하며 실행 대상을 바꾸는 _행&#xC704;_&#xB294; **스레드 전환**이 전담한다(여기서는 스냅샷이 '무엇으로 이루어지는가'만). **인터럽트**·**시스템 호출**에서도 실행 흐름이 갑자기 다른 곳으로 넘어갈 때 원래 흐름의 이 상황 정보를 먼저 저장해 두어야 나중에 되돌아올 수 있다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **PCB의 실체는 리눅스에선 `task_struct`**: OS가 각 작업의 상황 정보를 담는 장부를 교과서는 PCB(Process Control Block)라 부르지만, 리눅스 커널에서 그 실체는 `task_struct`라는 거대한 구조체다. 리눅스는 프로세스든 스레드든 전부 이 `task_struct` 하나로 표현한다(스레드는 자원을 공유하는 특별한 태스크일 뿐).
> * **문맥은 계층적이다**: 문맥은 한 덩어리가 아니라, CPU가 하드웨어적으로 다루는 '하드웨어 문맥'(레지스터·PC·플래그)과 OS가 관리하는 문맥(메모리 매핑·열린 파일·우선순위 등)으로 나뉜다. 그래서 함수 호출 때 저장하는 문맥과 스레드 전환 때 저장하는 문맥은 범위가 완전히 다르다.
> * **호출자 저장 vs 피호출자 저장**: 문맥 저장 책임도 나뉜다. 호출 규약(ABI)은 레지스터를 '호출자 저장(caller-saved)'과 '피호출자 저장(callee-saved)'으로 갈라, 함수 호출 때마다 모든 레지스터를 무조건 저장하지 않고 규약이 정한 것만 저장해 비용을 줄인다.

### 6. 중첩과 스택

무대가 레지스터에서 스택으로 옮겨간다. 그 전에, "왜 하필 스택인가"라는 원리부터 짚는다.

#### 1) 개념 정의

중첩(nested)이란 어떤 일이 진행되는 도중에 또 다른 일이 시작되고, 그 안에서 다시 또 다른 일이 시작되는 식으로 일이 겹겹이 포개지는 구조다. 이 구조엔 단순하지만 강력한 규칙이 있다 — **가장 나중에 시작한 일이 가장 먼저 끝난다.** 스택(stack)은 이 규칙을 그대로 담아내는 자료구조로, **나중에 넣은 것이 먼저 나오는** 후입선출(LIFO, Last In First Out) 성질을 갖는다.

#### 2) 원리 설명

큰 상자를 열었더니 그 안에 중간 상자가 있고, 그 안에 작은 상자가 있다고 하자. 다시 다 닫으려면 순서가 정해져 있다 — **가장 마지막에 연 작은 상자를 가장 먼저 닫아야** 한다. 작은 상자가 열린 채로는 중간 상자를 닫을 수 없기 때문이다.

* 여는 순서: 큰 → 중간 → 작은
* 닫는 순서: 작은 → 중간 → 큰 (정확히 반대)

**시작한 순서의 정반대로 끝난다.** 스택도 똑같다 — 차곡차곡 쌓은 뒤 꺼내면 맨 마지막에 올린 것이 맨 위에 있어 가장 먼저 나온다. 두 규칙이 완벽히 같기에, 중첩 구조를 추적하고 되돌리는 일에 스택이 딱 들어맞는다.

#### 3) 세부 메커니즘

스택엔 두 동작만 있다 — **push**(맨 위에 올림), **pop**(맨 위에서 꺼냄). 그리고 결정적 제약이 하나 있다: **접근할 수 있는 것은 오직 맨 위 항목뿐이다.** 안쪽 항목은 그 위를 다 걷어내기 전엔 건드릴 수 없다. 이 "맨 위만 접근 가능"이 후입선출을 만든다.

이 제약이 왜 중첩의 되돌리기 순서와 정확히 일치하는지 짚어 보자. 중첩에서 "지금 끝낼 수 있는 일"은 언제나 가장 최근에 시작한(가장 안쪽) 일 하나뿐이다. 스택에서 "지금 꺼낼 수 있는 항목"도 언제나 맨 위 하나뿐이다.

| 중첩 구조                      | 스택                   |
| -------------------------- | -------------------- |
| 새 일을 시작한다                  | push (맨 위에 올린다)      |
| 지금 끝낼 수 있는 건 가장 최근에 시작한 일뿐 | 지금 꺼낼 수 있는 건 맨 위 항목뿐 |
| 그 일을 끝낸다                   | pop (맨 위를 꺼낸다)       |

새 일마다 push, 끝날 때마다 pop을 하면, 스택 맨 위엔 항상 "지금 진행 중인 일들 중 가장 안쪽 일"이 놓인다. 스택 구조 자체가 중첩의 순서를 자동으로 지켜 주는 것이다.

#### 4) 예시

**괄호 짝 맞추기.** `( [ { } ] )`처럼 여러 괄호가 겹쳐 있을 때, 여는 괄호는 push, 닫는 괄호는 pop해 방금 꺼낸 것과 짝이 맞는지 본다.

```
읽은 글자   동작            스택 상태(왼쪽 바닥, 오른쪽 맨 위)
  (        push (          (
  [        push [          ( [
  {        push {          ( [ {
  }        pop → {  짝!    ( [
  ]        pop → [  짝!    (
  )        pop → (  짝!    (비어 있음)
```

닫는 `}`를 만났을 때 pop하면 가장 최근에 열린 `{`가 나오는데, 정확히 이것이 지금 닫혀야 할 짝이다. 마지막에 스택이 비면 모든 짝이 맞은 것이다. **겹쳐 쌓은 접시**도 같다 — 1·2·3번을 순서대로 올리면(push) 3·2·1번 순으로 집힌다(pop). 밑에 깔린 1번을 쓰려면 위의 2·3번을 먼저 치워야 한다.

#### 5) 다른 키워드와의 연결

이 소주제는 추상 원리만 다뤘다. 이 원리를 함수 호출이라는 구체적 상황에 적용한 것이 **함수 호출과 실행 시간 스택**이고, 스택의 "맨 위"가 어디인지 실제 CPU가 기억하는 방법이 **스택 포인터**다. 나아가 **시스템 호출**·**인터럽트**·**스레드 전환** 모두 "중간에 끼어든 일을 먼저 끝내고 원래 하던 일로 되돌아간다"는 중첩 구조를 가져 하나같이 스택을 쓴다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **스택의 다른 이름 '켈러'(1957)**: LIFO 스택을 계산 장치 원리로 처음 특허화한 건 1957년 독일 뮌헨 공대의 프리드리히 바우어와 클라우스 자멜존으로, 이들은 이를 '켈러(Keller, 지하 저장고) 원리'라 불렀다. 바우어가 ALGOL 위원회 대표였던 덕에 이 스택이 이후 사실상 모든 언어의 함수 호출 표준이 됐다.
> * **함수 호출 밖의 LIFO**: 중첩을 거꾸로 푸는 LIFO는 곳곳에 있다 — 편집기의 실행 취소(undo), 브라우저의 뒤로 가기, `3+4×2` 같은 수식의 우선순위 계산이 모두 스택으로 돌아간다. 실제로 바우어-자멜존의 원래 목적도 '수식 계산'이었다.
> * **초기 포트란은 재귀를 못 했다**: 함수의 재귀·중첩 호출을 다룰 수 있는 건 스택 덕분인데, 초기 포트란(FORTRAN)은 재귀 호출을 아예 지원하지 못했다. 각 함수의 지역 변수 자리를 정적으로 고정 할당해, 함수가 자기를 다시 부르면 이전 호출 값이 덮어써졌기 때문이다(재귀는 Fortran 90에서 도입).

### 7. 함수 호출과 실행 시간 스택

중첩→스택이라는 원리가 우리가 매일 짜는 코드에서 실제로 돌아가는 현장이 함수 호출이다.

#### 1) 개념 정의

함수를 호출할 때마다 그 호출 하나에 필요한 정보를 한 덩어리로 묶어 스택에 쌓았다가, 함수가 끝나면 걷어내는 방식이 함수 호출과 실행 시간 스택이다. 호출 하나가 쌓는 정보 덩어리를 \*\*스택 프레임(stack frame)\*\*이라 하며, 여기엔 ① 복귀 주소(함수가 끝난 뒤 돌아가 이어 실행할 위치), ② 매개변수, ③ 지역 변수가 들어간다. 프레임들이 쌓이는 스택 전체를 **실행 시간 스택(runtime stack)** 또는 \*\*콜 스택(call stack)\*\*이라 부른다. (이 소주제는 사용자 모드의 보통 함수 호출을 다룬다.)

#### 2) 원리 설명

함수 호출은 전형적인 중첩이다 — 나중에 부른 함수가 먼저 끝나고, 끝나면 부른 자리로 정확히 복귀한다. "중첩은 곧 후입선출(스택)"이라는 원리(→ **중첩과 스택**)를 여기에 그대로 적용하면, **호출하면 프레임을 push하고 반환하면 프레임을 pop**하는 구조가 된다. 원리 자체의 증명은 그 소주제가 다루므로, 여기서는 프레임에 무엇이 담기고 호출·반환 때 무엇이 오가는가라는 함수 고유의 몫에 집중한다. 각 함수는 자기 프레임 안의 매개변수·지역 변수만 다루므로, 서로 다른 호출의 변수들이 섞이지 않고 독립적으로 유지된다.

#### 3) 세부 메커니즘

* **(1) 호출 순간 — 프레임 push**: 새 스택 프레임이 스택 맨 위에 쌓인다. 그 안에 매개변수, 복귀 주소(호출 명령 바로 다음 위치), 지역 변수 자리가 잡힌다. 지금 실행 중인 함수의 프레임은 항상 스택 맨 위에 있다.
* **(2) 실행 중 — 자기 프레임 안에서**: 함수는 자기 프레임 안의 변수만 쓴다. 그래서 같은 함수를 다시 호출해도(중첩·재귀) 새 프레임이 따로 생겨 값이 안 섞인다.
* **(3) 반환 순간 — 복귀 주소로 PC 복원 후 프레임 pop**: 프레임에 저장해 둔 복귀 주소를 꺼내 PC에 되돌린다(그러면 CPU가 함수를 불렀던 자리의 다음부터 이어 실행). 그리고 그 프레임을 스택에서 pop한다.

#### 4) 예시

`main`이 `f`를, `f`가 다시 `g`를 부르는 3중 호출을 보자.

```c
int g(int x) { int r = x + 1; return r; }   // g의 지역 변수 r
int f(int a) { int b = g(a); return b; }    // f가 g를 호출
int main(void){ int y = f(10); return 0; }  // main이 f를 호출
```

호출이 가장 깊이 들어간 순간(g 실행 중), 실행 시간 스택엔 프레임 3개가 쌓여 있다.

```
   ┌─────────────────────────────┐  ← 스택 꼭대기 (지금 실행 중)
   │ g의 프레임  (x=10, r, 복귀→f) │
   ├─────────────────────────────┤
   │ f의 프레임  (a=10, b, 복귀→main)│
   ├─────────────────────────────┤
   │ main의 프레임  (y, 복귀→호출자) │
   └─────────────────────────────┘  ← 스택 바닥

시간 흐름:
  main 시작 → push main            [main]
  main→f 호출 → push f             [main, f]
  f→g 호출 → push g                [main, f, g]
  g 반환 → 복귀주소→PC, pop g       [main, f]   ← g가 가장 먼저 끝남
  f 반환 → 복귀주소→PC, pop f       [main]
  main 반환 → pop main             []
```

핵심은 **가장 나중에 쌓인 `g`가 가장 먼저 걷히고, `g → f → main` 역순으로 프레임이 걷힌다**는 점이다. 각 프레임을 걷을 때 그 프레임의 복귀 주소로 PC를 되돌리므로, 실행 흐름이 매번 정확히 부른 자리로 돌아온다.

#### 5) 다른 키워드와의 연결

이 소주제는 **중첩과 스택** 원리의 응용이다. 프레임을 push·pop할 때 꼭대기를 따라 움직이는 것이 \*\*스택 포인터(SP)\*\*이고, 반환 시 복귀 주소를 되돌리는 대상이 \*\*명령어 주소 레지스터(PC)\*\*다. 프레임에 담기는 복귀 주소·매개변수·지역 변수는 이 호출이 이어서 실행되기 위해 보관하는 **상황 정보**의 사용자 모드 버전이다. 한편 **시스템 호출**·**인터럽트**·**스레드 전환**도 스택을 쓰지만, 사용자 모드 함수 호출 스택과는 별개인 커널 상태 스택을 사용한다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **'Stack Overflow'라는 이름의 유래**: 개발자들이 드나드는 Q\&A 사이트 'Stack Overflow'의 이름이 바로 이 콜 스택이 넘치는 에러에서 왔다. 무한 재귀처럼 함수가 끝없이 중첩돼 한계를 넘으면 스택 오버플로가 나는데, 리눅스의 스레드당 기본 스택은 8MB, 윈도우는 1MB로 그 한계가 정해져 있다.
> * **재귀 깊이의 현실적 상한**: 파이썬은 폭주를 막으려 기본 재귀 한도를 1000회로 걸어 두고(넘으면 `RecursionError`), C는 그런 안전장치 없이 스택이 실제로 넘칠 때까지 파고들다가 세그멘테이션 오류로 죽는다.
> * **스택 카나리아**: 콜 스택은 공격 표적이기도 하다. 스택의 반환 주소를 조작하는 '스택 버퍼 오버플로' 공격을 막으려, 컴파일러는 반환 주소 옆에 임의의 감시값 '스택 카나리아(canary)'를 심어 함수가 돌아가기 직전 훼손 여부를 검사한다(갱도의 카나리아에서 딴 이름).

### 8. 시스템 호출과 커널 상태 스택

이제 실행 흐름이 _더 큰 경&#xACC4;_&#xB97C; 넘는 세 장면이 이어진다. 그 첫째, 프로그램이 스스로 커널의 문을 두드리는 시스템 호출이다.

#### 1) 개념 정의

시스템 호출(system call)은 프로그램이 스스로, 그 자리에서(동기적으로) 운영체제(커널)에게 "이 일 좀 대신 해 주세요"라고 요청하는 행위다. 파일 읽기·메모리 할당·화면 출력처럼 하드웨어나 시스템 자원을 직접 건드려야 하는 일은 프로그램이 마음대로 할 수 없어 커널에 부탁하는데, 그 창구가 시스템 호출이다. 이때 CPU는 **사용자 모드에서 커널 모드로 전환**되고, 커널은 사용자 스택이 아닌 **별도의 커널 상태 스택**을 쓴다.

#### 2) 원리 설명

컴퓨터엔 권한 수준이 둘 있다. **커널 모드**(하드웨어를 직접 제어하는 명령을 쓸 수 있는 힘센 상태, 운영체제가 돎)와 **사용자 모드**(그런 명령을 쓸 수 없는 제한된 상태, 보통 프로그램이 돎)다. 왜 프로그램의 힘을 빼앗아 둘까? 한 대의 컴퓨터를 여러 프로그램이 나눠 쓰기 때문이다. 아무 프로그램이나 디스크·메모리·장치를 직접 주무를 수 있다면 실수 하나가 시스템 전체를 무너뜨릴 수 있다. 그래서 자원의 제어는 오직 커널이 한다. 그 결과 프로그램은 위험한(=특권이 필요한) 일을 스스로 못 하고 커널에 요청하며, 요청하는 순간 CPU는 사용자 모드에서 커널 모드로 잠깐 전환됐다가 일을 마치면 다시 내려온다.

#### 3) 세부 메커니즘

1. 프로그램(사용자 모드)이 시스템 호출을 한다.
2. CPU가 **사용자 모드 → 커널 모드**로 전환된다.
3. 커널이 요청받은 일을 처리한다 — 이때 사용자 스택이 아니라 **별도의 커널 상태 스택**을 쓴다(스택 포인터가 사용자 스택 꼭대기에서 커널 스택 꼭대기로 옮겨 간다). 커널이 내부에서 다른 함수를 부르면 그 지역 변수·복귀 주소도 이 커널 스택에 쌓인다.
4. 일이 끝나면 결과를 들고 **커널 모드 → 사용자 모드**로 복귀한다.
5. 프로그램은 원래 사용자 스택으로 돌아와 하던 일을 계속한다.

**왜 스택을 따로 두는가?** 격리와 보안 때문이다. 사용자 스택은 사용자 코드가 언제든 건드릴 수 있는 메모리라, 잘못됐거나 악의적인 코드가 엉망으로 만들어 놨을 수 있다. 커널이 그런 스택 위에서 중요한 작업을 하면 커널의 동작이 프로그램에 휘둘린다. 또 커널이 스택에 쌓는 값(처리 중 데이터·복귀 주소)은 사용자 프로그램이 들여다보거나 고쳐선 안 되는 정보다. 그래서 커널 상태 스택은 커널 모드에서만 접근할 수 있는 보호된 영역에 둔다.

#### 4) 예시

프로그램이 파일에서 데이터를 읽는 상황을 따라가 보자.

```c
char buf[100];
int n = read(fd, buf, 100);   // 파일에서 100바이트 읽기 요청 (시스템 호출)
// 여기서부터 다시 프로그램의 코드가 이어진다
```

1. 프로그램은 스스로 디스크를 읽을 권한이 없어, `read`로 커널에 "이 파일에서 100바이트 읽어 주세요"라고 **자발적으로** 요청한다.
2. CPU가 사용자 모드 → 커널 모드로 전환되고, 스택이 사용자 스택 → **커널 상태 스택**으로 갈아탄다.
3. 커널이 커널 상태 스택 위에서 실제 읽기를 처리한다.
4. 읽기가 끝나면 결과(읽은 바이트 수·데이터)를 들고 커널 모드 → 사용자 모드로 복귀하고, 스택도 사용자 스택으로 돌아온다.
5. 프로그램은 반환값 `n`을 받아 다음 줄부터 계속한다.

프로그램 입장에선 함수 하나 부른 것 같지만, 그 밑에선 "사용자 모드 → 커널 모드 → 커널 스택에서 처리 → 사용자 모드 복귀"라는 왕복이 한 번 일어난 것이다.

#### 5) 다른 키워드와의 연결

보통의 **함수 호출**은 사용자 모드 안에서 시작하고 끝나지만, 시스템 호출은 모드 경계를 넘는 특별한 호출이다. **인터럽트**와는 반드시 대비해야 한다 — 시스템 호출은 프로그램이 원해서(자발적·동기적)이고, 인터럽트는 외부 사건이 갑자기(비자발적·비동기적) 끼어드는 것이다. **스레드 전환**과는 제목이 비슷하지만, 여기서 다룬 건 _한 프로그램이 커널에 들어갔다 나오는 왕&#xBCF5;_&#xC774;지 스레드 A를 B로 바꿔 끼우는 이야기가 아니다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **스레드 하나에 스택 두 개**: 스레드 하나는 사실 사용자 스택과 커널 스택을 둘 다 갖는다. 사용자 스택이 MB 단위인 데 비해 커널 스택은 아주 빠듯해서, x86-64 리눅스에서 고작 16KB(4KB 페이지 2장)뿐이다.
> * **8KB에서 16KB로(2014)**: 이 커널 스택은 원래 8KB였는데 2014년 x86-64에서 16KB로 늘었다. KVM(가상화)·FUSE처럼 스택을 많이 쓰는 서브시스템이 8KB를 넘겨 커널 스택 오버플로(치명적)를 일으켰기 때문이다. 사용자 스택과 달리 커널 스택은 넘치면 곧장 시스템 붕괴로 이어진다.
> * **CPU가 커널 스택을 자동으로 찾는 법**: 권한이 바뀌는 인터럽트가 발생하면 x86 CPU는 TSS(태스크 상태 세그먼트)의 RSP0 필드에 적힌 그 스레드의 커널 스택 꼭대기 주소를 보고, 그 순간 사용자 스택에서 커널 스택으로 자동으로 갈아탄다.

### 9. 인터럽트와 인터럽트 함수 스택

둘째 장면 — 이번엔 프로그램이 부른 게 아니라, 바깥세상이 갑자기 문을 두드린다.

#### 1) 개념 정의

인터럽트(interrupt)는 키보드·타이머·디스크 같은 외부 장치가 CPU에 갑자기 보내는 신호다. 핵심은 이 신호가 **비동기적이고 비자발적**이라는 점 — 지금 실행 중인 프로그램이 요청한 게 아니라, 외부 장치가 아무 때나 끼어든다. CPU는 이 신호를 받으면 하던 일을 멈추고 그 순간의 상황 정보를 저장한 뒤, 인터럽트 처리 함수(핸들러)로 점프해 처리하고, 끝나면 저장분을 복원해 원래 코드로 돌아온다. 이 저장·복원이 스택 위에서 이뤄진다.

#### 2) 원리 설명

인터럽트의 어려움은 "아무 준비도 안 된 코드가 당한다"는 데 있다. 일반적인 함수 호출은 프로그램이 스스로 "지금 이 함수를 부른다"고 정한 지점에서 일어나 부르는 쪽이 미리 준비한다. 그러나 인터럽트를 당한 코드는 자기가 언제 멈출지 전혀 몰랐고, 명령과 명령 사이 어느 틈에서든 갑자기 멈춰진다(계산 도중일 수도, 값을 반쯤 옮기던 중일 수도). 그래서 스스로 상황을 정리할 겨를이 없다. 이 정리를 CPU(그리고 운영체제)가 대신 해 준다 — 핸들러로 넘어가기 전에 현재 상황 정보를 **강제로 저장**하고, 핸들러가 끝나면 정확히 되돌려 놓아, 원래 코드는 자기가 중간에 멈췄다 왔다는 사실조차 눈치채지 못한다.

#### 3) 세부 메커니즘

1. **발생** — 외부 장치가 신호를 보낸다. CPU는 실행 중이던 명령을 마친 직후, 다음 명령으로 넘어가기 전에 이 신호를 감지한다.
2. **상황 정보 저장(스택에)** — 멈춘 코드의 실행 위치(PC)와 레지스터 등 그 순간의 상황 정보를 스택에 저장한다. 함수 호출과 달리 아무 때나 일어나므로, 이 저장은 CPU/OS가 챙겨서 대신 한다.
3. **핸들러 찾아 점프** — 발생한 인터럽트마다 대응하는 처리 함수가 정해져 있다. CPU는 인터럽트의 번호(벡터)로 해당 핸들러를 찾아 그 위치로 점프한다.
4. **처리** — 핸들러가 그 사건을 처리한다(예: 눌린 키 값을 읽어 둔다).
5. **복원 후 복귀** — 2단계에서 저장해 둔 상황 정보를 다시 꺼내 되돌리고, 멈췄던 바로 그 위치로 돌아가 실행을 이어간다.

여기서 스택의 역할이 둘이다 — 멈춘 코드의 상황 정보를 담아 두는 보관 장소이자, 핸들러 자체가 스택 위에서 실행되는 함수라는 점이다. 다만 이 함수는 프로그램이 부른 게 아니라 **저절로 불려 들어온** 함수다.

#### 4) 예시

**계산 도중 키보드 입력.**

```
[계산 진행 중]  a = b * c + d ...
     │
     ▼  ◀── 키보드 인터럽트 발생! (아무 때나, 예고 없이)
① 지금 실행 위치(PC)와 레지스터 값을 스택에 저장
② 키보드 인터럽트 번호로 핸들러를 찾아 점프
③ 핸들러 실행: 눌린 키 값을 읽어 버퍼에 넣음
④ 스택에서 저장분을 꺼내 PC·레지스터 복원
     │
     ▼
[계산 재개]  a = b * c + d ...  ◀── 멈췄던 그 지점에서 그대로 이어감
```

계산하던 프로그램은 자기가 잠깐 멈췄다 돌아왔다는 사실을 모른다. 스택에 저장해 둔 상황 정보를 그대로 복원했기 때문이다. **디스크 읽기 완료**도 마찬가지다 — 프로그램이 디스크에 요청해 두고 다른 일을 하는 동안, 디스크가 준비를 마치면 "다 됐다"는 인터럽트를 보내고, CPU는 하던 일을 멈추고 저장·처리·복원한다. 언제 끝날지 프로그램이 정한 게 아니므로 이 완료 신호 역시 비동기로 끼어드는 전형적 인터럽트다.

#### 5) 다른 키워드와의 연결

인터럽트가 나면 **상황 정보**를 스택에 저장한다(무엇을 상황 정보라 하는지는 그 소주제 몫). 핸들러도 스택 위에서 도는 함수라는 점은 **함수 호출**과 같지만, 자발적으로 불렀는가 vs 저절로 불려 들어왔는가가 결정적 차이다. **시스템 호출**과는 반드시 대비할 형제다 — 시스템 호출은 자발·동기, 인터럽트는 비자발·비동기. 그리고 타이머 인터럽트가 **스레드 전환**을 촉발할 수 있으나, 두 스레드를 맞바꾸는 절차 자체는 스레드 전환 소주제 몫이고, 여기선 저장→핸들러→복귀 뼈대까지다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **인터럽트 벡터 테이블**: CPU는 인터럽트 번호로 처리 함수 주소를 찾는 '인터럽트 벡터 테이블'을 참조한다. 옛 x86 리얼 모드에선 이 표가 메모리 맨 앞 0번지에 256개 × 4바이트 = 딱 1KB로 놓여 있었고, 보호 모드에선 IDT(인터럽트 서술자 테이블)로 확장됐다.
> * **탑 하프와 보텀 하프**: 핸들러는 짧아야 한다(처리 중 다른 인터럽트가 막히니까). 그래서 리눅스는 처리를 둘로 쪼갠다 — 당장 급한 최소 작업만 하는 '탑 하프'와 나머지 무거운 일을 나중에 처리하는 '보텀 하프'. 초인종이 울리면 일단 문만 열어 주고, 접대는 이따 하는 셈이다.
> * **막을 수 없는 인터럽트, NMI**: 대부분의 인터럽트는 '마스킹'으로 잠시 막을 수 있지만, NMI(Non-Maskable Interrupt)는 소프트웨어가 어떤 방법으로도 무시할 수 없는 최고 우선순위 신호다. 심각한 하드웨어 오류나 커널이 멈췄는지 감시하는 '워치독' 용도로 쓰며, 커널이 인터럽트를 전부 꺼도 NMI만은 뚫고 들어온다.

### 10. 스레드 전환과 커널 상태 스택

마지막 장면 — 5번의 "상황 정보"가 마침내 도구로 쓰인다. 한 스레드를 멈추고 다른 스레드로 갈아타는 순간이다.

#### 1) 개념 정의

스레드 전환(thread switching)은 CPU가 지금 실행하던 스레드를 멈추고 다른 스레드를 실행하도록 바꿔 끼우는 행위다. 지금 스레드의 상황 정보를 저장(save)하고, 다음 스레드가 예전에 저장해 둔 상황 정보를 꺼내 복원(restore)해서 실행 대상을 맞바꾼다. 문맥 교환(context switch)이라고도 부른다.

#### 2) 원리 설명

CPU는 하나뿐이라 두 스레드가 동시에 CPU를 차지할 수 없다. 그래서 지금 멈추는 스레드 A는 나중에 다시 실행될 것이므로, 멈추는 순간의 상태(어디까지 실행했는지, 레지스터에 무슨 값이 있었는지)를 저장해 둬야 이어 달릴 수 있다. 그리고 다음에 실행할 스레드 B가 예전에 저장해 둔 상태를 꺼내 CPU에 복원하면, 복원이 끝나는 순간 명령어 주소 레지스터(PC)가 B의 중단점을 가리키고 레지스터엔 B가 쓰던 값이 채워져, 그 순간부터 CPU는 자연스럽게 B를 이어서 실행한다. 즉 전환은 **"저장 → 복원"이라는 맞바꿈** 한 번으로 요약된다. (저장·복원되는 그 상황 정보가 무엇인지는 **상황 정보** 소주제에서 정의했고, 여기서는 그것을 도구로 써서 실행 대상을 교체하는 절차에 집중한다.)

#### 3) 세부 메커니즘

1. **현재 스레드(A)의 상황 정보를 저장한다** — CPU 안의 값들(PC·SP·범용/상태 레지스터)을 A의 저장 공간, 곧 A의 제어 블록(스레드/프로세스 제어 블록)이자 커널 상태 스택에 옮겨 담는다. 보호받는 커널 영역이라 사용자 스레드가 함부로 건드릴 수 없다.
2. **스케줄러가 다음 스레드를 고른다** — 실행 준비가 된 스레드들 가운데 하나(B)를 운영체제의 스케줄러가 선택한다. (어떤 기준으로 고르는지는 이 소주제의 범위를 넘어선다.)
3. **다음 스레드의 상황 정보를 CPU로 복원한다** — B가 예전에 자기 커널 상태 스택/제어 블록에 남겨 뒀던 상황 정보를 꺼내 CPU 레지스터들에 되돌려 놓는다.
4. **그 스레드가 이어서 실행된다** — PC가 B의 중단점을 가리키므로, CPU는 B를 멈췄던 자리부터 이어서 실행한다.

여기서 반드시 기억할 점은 **스레드마다 자기 커널 상태 스택(과 제어 블록)을 따로 가진다**는 것이다. A의 상태는 A의 커널 스택에, B의 상태는 B의 커널 스택에 park되므로, 여러 스레드가 번갈아 멈추고 이어 달려도 서로의 중단점이 섞이지 않는다.

#### 4) 예시

스레드 A가 실행되던 중 전환 시점이 되었다고 하자(예: 타이머 인터럽트가 "이제 다른 스레드에게 CPU를 넘길 때"라고 알린다).

```
[전환 전]  CPU 안: A의 PC, A의 SP, A의 레지스터들   ← A 실행 중

  1) 저장:  A의 PC · SP · 레지스터  ──►  A의 커널 상태 스택 / 제어 블록
  2) 선택:  스케줄러가 다음 스레드로 B를 고름
  3) 복원:  B의 커널 상태 스택 / 제어 블록  ──►  CPU 안(PC, SP, 레지스터)

[전환 후]  CPU 안: B의 PC, B의 SP, B의 레지스터들   ← B가 멈췄던 자리부터 실행
```

복원이 끝나는 순간 CPU의 PC는 B가 예전에 멈췄던 명령을 가리키므로, B는 마치 한 번도 멈춘 적 없던 것처럼 그 자리부터 이어 실행된다. 나중에 다시 A 차례가 오면, 똑같이 B의 상태를 B의 커널 스택에 저장하고 A의 커널 스택에서 A의 상태를 복원한다.

#### 5) 다른 키워드와의 연결

이 소주제에서 저장·복원되는 대상이 바로 **상황 정보**다 — "상황 정보"가 그 스냅샷이 _무엇인지_(명사)를 정의했다면, 이 소주제는 그것을 실제로 저장·복원해 실행 대상을 바꾸는(동사) 절차다. **시스템 호출**과는 제목이 "커널 상태 스택"으로 똑같이 끝나지만, 시스템 호출은 _하나의 스레&#xB4DC;_&#xAC00; 커널에 들어갔다 나오는 왕복(모드 전환)이고 이 소주제는 _스레드 A↔B 교&#xCCB4;_&#xB2E4;. 그리고 **인터럽트**(특히 타이머 인터럽트)가 전환을 촉발할 수 있으나, 인터럽트가 어떻게 끼어들고 처리되는지 그 절차는 인터럽트 소주제의 몫이다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **문맥 교환은 공짜가 아니다**: 레지스터를 저장·복원하는 '직접 비용'만도 대략 1~~수 마이크로초이지만, 진짜 타격은 '간접 비용'이다 — 새 스레드가 캐시·TLB·분기 예측기를 다시 데우는 동안 성능이 떨어져 총비용이 수십~~수백 마이크로초에 이를 수 있다.
> * **TLB 때문에 특히 비싸다**: 프로세스가 바뀌면 주소 매핑이 달라져 TLB(주소 변환 캐시)를 통째로 비워야 했고, 이후 접근마다 페이지 테이블을 다시 뒤지느라 느려졌다. 그래서 현대 x86은 프로세스마다 꼬리표를 붙이는 PCID 기능으로 이 전면 플러시를 피한다(리눅스 4.14부터 활용).
> * **누구를 다음에 실행할지는 스케줄러가**: 문맥 교환은 커널 스택 위에서 벌어지지만, '누구를 다음에 실행할지'는 별도의 스케줄링 알고리즘이 정한다(리눅스는 오랫동안 CFS, 커널 6.6부터 EEVDF).

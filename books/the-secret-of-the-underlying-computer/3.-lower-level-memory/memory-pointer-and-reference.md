# Memory, pointer and reference

### 1. 메모리의 본질 — 사물함·비트·바이트·객체

#### 1) 개념 정의

메모리는 1바이트(8비트)짜리 칸이 일렬로 늘어선 거대한 사물함이며, 모든 칸에는 0번부터 차례로 매겨진 고유한 주소(보통 16진수 일련번호)가 붙어 있다.

#### 2) 원리 설명

비트(0 또는 1) 하나로는 두 가지 상태밖에 표현하지 못하므로, 컴퓨터는 비트 8개를 한 묶음으로 보고 이를 바이트라 부르며 메모리를 다루는 기본 칸으로 삼는다. \
사물함이 칸으로 구획되어야 "몇 번 칸"이라고 가리킬 수 있듯, 메모리도 바이트 단위로 나뉘어야 위치를 지목할 수 있다.&#x20;

그래서 각 바이트 칸에는 맨 앞 0번부터 1씩 늘어나는 번호가 빠짐없이 붙고, 이 번호가 곧 주소다. \
주소는 한번 정해지면 변하지 않으며, 칸 안에 담긴 0과 1의 내용물만 바뀐다. \
정수·실수처럼 한 칸으로 모자란 값은 번호가 이어지는 여러 칸에 연속으로 걸쳐 저장된다. \
그 값을 가리킬 때는 시작 칸의 주소 하나와 "몇 칸짜리인가"라는 크기 정보만 있으면 전체를 집어낼 수 있다.

#### 3) 세부 메커니즘

* 단위의 사다리: 비트(0/1) → 8비트가 모이면 1바이트(칸 하나) → 바이트 여러 개가 모이면 워드(CPU가 한 번에 다루기 편한 묶음, 흔히 4바이트나 8바이트).
* 주소는 칸마다 하나씩: 워드 단위가 아니라 바이트 칸마다 주소가 붙는다(바이트 주소 지정). 덕분에 문자 한 글자 같은 1바이트 값도 곧장 한 칸을 콕 집어 읽고 쓸 수 있다.
* 주소 표기: 주소는 그냥 정수지만, 자릿수가 길어 사람이 읽기 번거롭기 때문에 보통 16진수로 적는다(예: 0x10은 16번 칸).
* '객체'의 저장: 정수·실수·구조체처럼 여러 바이트를 차지하는 값을 객체라 부른다. 객체는 주소가 1씩 연속으로 이어지는 칸들에 통째로 들어가며, 그 객체의 주소는 관례적으로 "시작(첫) 칸의 주소"로 본다.
* 크기가 곧 칸 수: 어떤 종류의 값인지 알면 칸을 몇 개 쓰는지 정해진다. 흔한 환경에서 문자는 1칸, 정수는 4칸, 8바이트 실수는 8칸을 차지한다(환경에 따라 다를 수 있음).

#### 4) 예시

정수 하나는 흔히 4칸을 차지한다. \
시작 주소가 0x7fffe058이라면, 그 정수는 다음 네 칸에 연속으로 걸쳐 저장되고, 주소는 칸마다 1씩 늘어난다.

```
주소(16진수)     내용물(한 칸 = 1바이트 = 8비트)
-----------     --------------------------------
0x7fffe058      [ 11010010 ]   ← 정수의 시작 칸(이 주소가 곧 객체의 주소)
0x7fffe059      [ 00001010 ]
0x7fffe05a      [ 10110001 ]
0x7fffe05b      [ 01101110 ]   ← 정수의 마지막 칸
0x7fffe05c      [ ........ ]   ← 다음 값이 들어갈 그 다음 칸
```

이처럼 4바이트 정수가 0x7fffe058에서 시작하면, 바로 다음에 놓이는 또 다른 4바이트 정수의 시작 칸은 0x7fffe058 + 4 = 0x7fffe05c가 된다.&#x20;

반면 문자 'A' 한 글자는 1칸이면 충분하므로, 단 한 개의 주소(예: 0x7fffe058)만으로 읽고 쓸 수 있다. \
핵심은 "주소 하나 + 칸이 몇 개냐"만 알면 그 값 전체를 정확히 집어낼 수 있다는 점이다.

(참고: 여러 바이트가 칸에 담기는 '순서'는 환경마다 다를 수 있음.)



이렇게 "메모리의 모든 칸에는 주소가 있다"는 사실이 토대가 되어, 그 주소에 사람이 읽기 쉬운 이름표를 붙이면 변수가 되고, 그 주소 자체를 값으로 담아 들고 다니면 포인터가 된다(자세한 내용은 해당 소주제에서).

### 2. 변수의 의미

#### 1) 개념 정의

변수란 메모리의 한 칸(타입에 따라 연속된 여러 칸)에 사람이 읽을 수 있는 이름을 붙여, 그 이름으로 안에 든 값을 읽고 쓰게 만든 것이다.

#### 2) 원리 설명

앞에서 메모리는 '주소가 매겨진 바이트 칸들'이라고 했는데, 그 주소는 `0xff456e` 같은 16진수라 사람이 외워 쓰기엔 너무 불편하고 실수하기 쉽다. \
그래서 우리는 칸에 `score`, `age` 같은 이름표를 달고, 실제 주소가 몇 번인지는 컴파일러에게 맡긴다.&#x20;

즉 변수는 **이름 ↔ 주소 ↔ 값**이라는 삼각관계로 이해할 수 있다: 이름은 사람이 쓰는 호칭, 주소는 그 이름이 가리키는 메모리 위치, 값은 그 위치에 실제로 담긴 데이터다. \
코드에 `score`라고 쓰면 컴파일러가 이를 그 변수에 배정해 둔 주소로 바꿔 주므로, 우리는 주소를 한 번도 직접 몰라도 값을 다룰 수 있다. \
그리고 이름과 값은 분리되어 있어서, 같은 이름표가 가리키는 칸의 값은 프로그램이 도는 동안 얼마든지 바뀔 수 있다(그래서 '변(變)수').

#### 3) 세부 메커니즘

* **이름은 주소의 별명이다.** 컴파일러는 변수 이름마다 고유한 주소를 정해 기계어에 박아 넣는다. \
  그래서 실행 중에 CPU가 보는 것은 이름이 아니라 주소뿐이고, 이름은 사람을 위한 호칭으로만 존재한다.
* **이름은 "타입이 정한 칸 묶음 전체"를 가리킨다.** 변수가 몇 칸을 쓰는지는 타입이 정하고(메모리 소주제에서 본 크기 그대로), 이름은 그 칸 묶음을 대표 주소(연속된 칸 중 첫 바이트)로 가리킨다. \
  그래서 `score`라는 이름 하나가 "어디서 시작하는, 몇 칸짜리 값인지"를 통째로 지시한다.
* **타입이 비트의 해석 방식도 정한다.** \
  메모리에 들어 있는 것은 결국 0과 1의 묶음일 뿐이라, 같은 비트라도 타입이 다르면 다르게 읽힌다. \
  타입은 "여기서 몇 바이트를, 정수로 볼지 실수로 볼지 문자로 볼지"를 알려 주는 해석 규칙이다.

#### 4) 예시

```c
int score = 90;
```

* `int`라서 컴파일러는 연속된 4개의 바이트 칸을 잡고, 거기에 `score`라는 이름을 붙인다. 그 칸들의 시작 주소가 예컨대 `0x7ffe5367e040`이라면, `score`는 곧 "주소 `0x7ffe5367e040`에서 시작하는 4바이트 정수 칸"을 뜻한다.
* 값 `90`은 그 4바이트 안에 2진수 비트(`...01011010`)로 채워진다. 우리는 `0x7ffe5367e040`을 외울 필요 없이 그냥 `score`라고 부르기만 하면 된다.

```c
int myAge = 43;
printf("%p\n", (void *)&myAge);   // 출력 예: 0x7ffe5367e044
```

* `&myAge`는 "`myAge`라는 이름이 실제로는 어떤 주소인지"를 꺼내 보여 준다. 환경에 따라 주소 값은 매번 다르지만, 이름 하나가 특정 주소 한 곳을 가리킨다는 관계는 변하지 않는다. (`&`로 꺼낸 주소를 값으로 담는 변수가 바로 포인터인데, 그건 별개의 이야기다.)



보통 변수는 이렇게 값을 **직접** 담지만, 그 값이 다른 칸의 '주소'인 특별한 변수가 포인터다 → '포인터 이해하기'. \
또한 변수에 든 값을 함수로 넘길 때 칸을 복사할지 원래 칸을 가리킬지가 갈리는데, 이는 '값 전달·참조 전달'에서 다룬다.

> 💡 **TMI**
>
> * **주소가 아예 없는 변수도 있다**: 변수는 '주소가 붙은 칸'이라고 배우지만, 최적화 컴파일러는 자주 쓰는 변수를 메모리 칸이 아니라 CPU 레지스터 안에만 두기도 한다. 이런 변수는 주소라는 게 존재하지 않아서, C에서 `&`로 주소를 꺼내려는 순간 컴파일이 거부된다. 초창기 C에는 "이 변수는 레지스터에 넣어 달라"고 부탁하는 `register` 키워드까지 있었는데, 요즘 컴파일러는 알아서 더 잘 판단하므로 이 키워드는 사실상 무시한다.
> * **실행 파일에는 변수 이름이 남지 않는다**: 변수 이름은 사람을 위한 호칭일 뿐이라, 컴파일이 끝나면 보통 기계어에서 지워지고 주소만 남는다. 그런데도 디버거가 멈춘 줄에서 `score = 90`처럼 이름과 값을 보여 줄 수 있는 건, 컴파일러가 "이 이름은 이 주소"라는 대조표(DWARF·PDB 같은 디버그 심볼)를 따로 만들어 두기 때문이다. 배포용 빌드에서 `strip`으로 이 심볼을 떼어내면 용량은 줄지만, 크래시가 나도 주소만 찍히고 어떤 변수였는지는 알 수 없게 된다.

### 3. 포인터 이해하기

#### 1) 개념 정의

포인터는 다른 변수가 저장된 메모리 주소를 자신의 값으로 담는 변수다.

#### 2) 원리 설명

모든 변수는 메모리 어딘가에 자리를 잡고 있고, 그 자리에는 고유한 주소가 매겨져 있다. \
보통의 변수가 정수나 문자 같은 "데이터"를 담는다면, 포인터는 그 데이터가 들어 있는 "위치(주소)"를 담는다. \
그래서 포인터는 값을 직접 들고 있는 대신, 값이 있는 곳을 가리키는 이정표 역할을 한다. \
포인터에 주소가 담겨 있으면, 그 주소를 따라가 원래 변수에 간접적으로 접근할 수 있다. \
이때 "어느 변수의 주소를 얻을지"는 주소 연산자 `&`가, "그 주소가 가리키는 값을 어떻게 다룰지"는 역참조 연산자 `*`가 담당한다.

#### 3) 세부 메커니즘

* **선언 `int *p;`** : 자료형 뒤에 별표를 붙여 "p는 int가 들어 있는 곳을 가리키는 포인터"임을 선언한다. \
  여기서의 `*`는 역참조가 아니라 "이 변수는 포인터다"라는 표시일 뿐이다. \
  int 변수를 가리키려면 `int *`, char 변수를 가리키려면 `char *`처럼 가리킬 대상의 자료형을 함께 적는다.
* **주소 얻기 `&`** : 변수 이름 앞에 `&`를 붙이면 그 변수의 주소가 나온다. \
  `p = &a;`는 변수 `a`가 놓인 자리의 주소를 포인터 `p`에 담는다. 이제 `p`는 `a`를 "가리키는" 상태가 된다.
* **값 다루기 `*`** : 포인터 앞에 `*`를 붙이면, 포인터에 담긴 주소로 찾아가 그 자리의 실제 값에 접근한다. \
  `*p`를 읽으면 그 주소에 저장된 값(즉 `a`의 값)을 가져오고, `*p = 20;`처럼 쓰면 그 주소의 값을 직접 바꿔 원래 변수 `a`까지 함께 변한다. \
  즉 `&`는 주소를 꺼내 포인터에 넣는 방향이고, `*`는 그 주소를 따라가 값을 읽거나 쓰는 방향이다.

#### 4) 예시

```c
#include <stdio.h>

int main(void)
{
    int a = 10;        // 일반 변수
    int *p = &a;       // p에 a의 주소를 담는다 (p가 a를 가리킨다)

    printf("a  = %d\n", a);          // a의 값
    printf("&a = %p\n", (void*)&a);  // a의 주소
    printf("p  = %p\n", (void*)p);   // p가 담은 값 = a의 주소
    printf("*p = %d\n", *p);         // p가 가리키는 곳의 값 = a의 값

    *p = 20;           // p가 가리키는 곳(a)에 20을 쓴다
    printf("a  = %d\n", a);          // a가 20으로 바뀐다

    return 0;
}
```

출력 예 (주소값은 실행 환경마다 달라진다):

```
a  = 10
&a = 0x7ffd5c3a4b1c
p  = 0x7ffd5c3a4b1c
*p = 10
a  = 20
```

`&a`와 `p`가 같은 주소를 가리키는 것을 보면 포인터가 변수의 "위치"를 담고 있음을 알 수 있고, `*p = 20;` 한 줄로 `a`가 20으로 바뀌는 것을 보면 역참조가 원래 변수에 직접 작용함을 알 수 있다.



포인터에 담긴 주소를 1 늘리면 어떻게 되는지(`p + 1`)는 "포인터 산술"에서, 주소를 통한 간접 접근이 주는 위력과 위험은 "포인터의 힘과 파괴력"에서 이어서 다룬다.

> 💡 **TMI**
>
> * **포인터 크기는 가리키는 대상과 무관하다**: `char*`든 거대한 구조체를 가리키는 포인터든, 같은 컴퓨터에서는 크기가 똑같다 — 64비트 환경이면 전부 8바이트다. 포인터는 '내용물'이 아니라 '주소(번지수)'만 담는 종이쪽지라, 가리키는 대상이 1바이트짜리든 1메가짜리든 번지수를 적는 칸 크기는 변할 이유가 없기 때문이다.

### 4. 포인터 산술

#### 1) 개념 정의

포인터 산술이란 포인터에 정수를 더하거나 빼서 "가리키는 위치를 원소 단위로 옮기는" 연산으로, 이동 거리는 바이트 수가 아니라 가리키는 타입의 크기(`sizeof(*p)`)를 곱한 만큼이다.

#### 2) 원리 설명

`p + 1`이 주소를 정확히 1바이트만 올리지 않고 타입 크기만큼 점프하는 이유는, 포인터 연산의 단위가 "바이트"가 아니라 "원소"이기 때문이다. \
컴파일러는 `p`가 어떤 타입을 가리키는지 알고 있으므로, `p + n`을 계산할 때 정수 `n`에 그 타입의 크기를 자동으로 곱해서 주소에 더한다.&#x20;

즉 실제 주소 계산은 `주소(p + n) = 주소(p) + sizeof(*p) * n` 형태로 이루어진다. \
덕분에 `int*`든 `double*`든 `p + 1`은 항상 "바로 다음 원소"를 가리키게 되어, 원소 크기가 달라도 똑같은 코드로 배열을 순회할 수 있다. \
이 "원소 단위로 자동 환산" 규칙이 포인터 산술의 핵심이다.

#### 3) 세부 메커니즘

* **타입 크기 곱셈(스케일링):** `int`가 보통 4바이트이면 `int*`에서 `p + 1`은 주소를 4, `p + 2`는 8 올린다. \
  만약 같은 자리에 있는 `char*`라면 `p + 1`은 1만, `double*`(보통 8바이트)라면 8을 올린다. 같은 정수 `1`을 더해도 타입에 따라 실제 이동 바이트가 달라진다.
* **배열-포인터 등가:** 배열 이름은 첫 원소를 가리키는 포인터처럼 동작한다. \
  그래서 `a[i]`는 정의상 `*(a + i)`와 완전히 같은 식이다. \
  즉 `a[i]`는 "`a`에서 `i`칸 이동한 뒤 그 자리를 역참조"하라는 뜻이며, 첨자 표기는 포인터 산술 + 역참조를 짧게 쓴 문법일 뿐이다.
* **포인터 뺄셈:** 같은 배열을 가리키는 두 포인터를 빼면 결과는 바이트 차이가 아니라 "그 사이의 원소 개수"다. \
  예컨대 두 주소가 4바이트 차이여도 `int*`끼리 빼면 결과는 `1`이다(내부적으로 바이트 차이를 타입 크기로 나눈 값).
* **유효 범위:** 의미 있는 포인터 산술은 한 배열의 내부, 그리고 마지막 원소 "한 칸 너머(one-past-the-end)"까지만 허용된다. \
  이 한 칸 너머 위치는 주소를 만들어 비교(예: 반복문 종료 조건)하는 데는 쓸 수 있지만, 실제 원소가 없으므로 그 자리를 역참조해서 값을 읽거나 쓰면 안 된다.

#### 4) 예시

```c
#include <stdio.h>

int main(void) {
    int arr[3] = {10, 20, 30};
    int *p = arr;            // p는 첫 원소 arr[0]을 가리킴

    // 주소는 실행할 때마다 달라지므로 아래 16진수는 '예시값'이다.
    // 변하지 않는 것은 '4씩 차이난다'는 사실이다(int가 4바이트일 때).
    printf("%p\n", (void *)(p));      // 예: 0x1000
    printf("%p\n", (void *)(p + 1));  // 예: 0x1004  (+4)
    printf("%p\n", (void *)(p + 2));  // 예: 0x1008  (+8)

    printf("%d\n", *(p + 1));         // 20  → p에서 한 칸 이동 후 역참조
    printf("%d\n", arr[2]);           // 30
    printf("%d\n", *(arr + 2));       // 30  → arr[2] 와 완전히 동일
    printf("%d\n", (int)((p + 2) - p));  // 2   → 두 포인터 사이의 '원소 개수'

    return 0;
}
```

동작 결과 정리:

* `p`, `p + 1`, `p + 2`의 주소는 (절대값은 실행마다 달라도) 서로 **4씩** 차이난다 — `int` 한 칸이 보통 4바이트이기 때문이다.
* `*(p + 1)`은 `20`. 한 칸 이동 후 그 자리의 값을 읽은 것이다.
* `arr[2]`와 `*(arr + 2)`는 둘 다 `30`으로 **항상 같다** — 첨자 표기가 곧 포인터 산술이기 때문이다.
* `(p + 2) - p`는 `2`. 바이트 차이(8)가 아니라 두 포인터 사이의 원소 개수다.



여기서 다룬 것은 "올바른 산술의 규칙과 동작"이며, 유효 범위를 벗어난 잘못된 포인터 산술이 일으키는 버그·크래시는 같은 절의 "포인터의 힘과 파괴력"에서 이어진다.

> 💡 **TMI**
>
> * **0부터 세는 데는 거장의 논거가 있다**: 배열 첨자가 1이 아니라 0부터 시작하는 게 단순 관습처럼 보여도, 에츠허르 데이크스트라는 1982년 짧은 메모 EWD831 "Why numbering should start at zero"에서 이를 정면으로 옹호했다. 첫 원소를 0번으로 두면 `a[i]`가 곧 "시작점에서 i칸 떨어진 곳(`*(a+i)`)"과 자연스럽게 맞아떨어지고, 구간의 길이가 그냥 '끝 - 시작'으로 깔끔하게 떨어지기 때문이다. 포인터 산술의 "시작 주소 + 이동 칸 수"라는 셈법이, 0부터 세는 관습과 한 몸이라는 이야기다.

### 5. 포인터의 힘과 파괴력 — 능력과 책임

#### 1) 개념 정의

포인터는 메모리를 직접 가리키고 고칠 수 있는 강력한 도구지만, 바로 그 직접성 때문에 잘못 쓰면 프로그램을 망가뜨리는 양날의 검이다.

#### 2) 원리 설명

포인터의 능력과 위험은 같은 뿌리에서 나온다. \
포인터는 "그 자리(메모리 주소)를 직접 가리키는" 도구라서, 데이터를 복사하지 않고 원본을 그대로 만지고, 실행 중에 필요한 만큼 메모리를 잡아 자료구조를 자유롭게 짤 수 있다.&#x20;

그런데 C는 이 직접 접근에 안전장치를 거의 두지 않는다. \
가리키는 주소가 유효한지, 배열의 범위를 벗어났는지 자동으로 검사하지 않으며, 다 쓴 메모리를 알아서 치워 주지도 않는다. \
그래서 "강력한 능력에는 책임이 따른다" — 메모리를 언제 잡고 언제 놓을지, 포인터가 지금 올바른 곳을 가리키는지를 전부 프로그래머가 직접 책임져야 한다. \
위반의 결과도 두 갈래다. \
NULL을 가리키는 포인터를 건드리면 대개 그 자리에서 시끄럽게 멈추지만(즉시 크래시), 그 외의 잘못된 접근은 조용히 엉뚱한 값을 망가뜨리며 한동안 멀쩡해 보이기까지 해서 더 위험하다.

#### 3) 세부 메커니즘

**능력 (왜 강력한가)**

* **직접 접근**: 포인터로 메모리의 그 자리를 가리켜, 큰 데이터를 복사하지 않고 원본을 바로 읽고 고칠 수 있다.
* **동적 자료구조**: 한 칸이 다음 칸을 가리키게 이으면 연결 리스트·트리처럼 크기가 정해지지 않은 유연한 구조를 만들 수 있다.
* **동적 할당**: `malloc`으로 실행 중에 필요한 만큼 메모리(힙)를 잡고, 다 쓰면 `free`로 돌려준다. 컴파일 시점에 크기를 몰라도 된다.

**파괴력 (무엇이 위험한가)**

* **와일드 포인터(wild pointer)**: 초기화하지 않은 포인터. 태어날 때부터 쓰레기 주소를 들고 있어 어디를 가리키는지 알 수 없다.
* **댕글링 포인터(dangling pointer, 허상 포인터)**: 한때는 멀쩡했지만 가리키던 메모리가 이미 `free`된 포인터. 주소는 그대로 들고 있으나 그 자리는 더 이상 내 것이 아니다.
* **해제 후 사용(use-after-free)**: 댕글링 포인터로 그 자리를 다시 읽거나 쓰는 것. 엉뚱한 값이 나오거나 데이터가 조용히 망가진다.
* **NULL 역참조**: 아무것도 안 가리키는(NULL) 포인터를 역참조하는 것. 보통 그 즉시 프로그램이 멈춘다(크래시).
* **메모리 누수(memory leak)**: `free`를 하지 않아, 다 쓴 메모리를 돌려주지도 못하고 다시 쓰지도 못하는 상태. 오래 도는 프로그램에서 누적되면 메모리를 고갈시킨다.
* **범위 밖 접근(out-of-bounds)**: 포인터 산술이 배열 끝을 넘어선 자리를 가리킬 때. C는 범위를 검사하지 않으므로, 옆 데이터를 덮어쓰거나 크래시가 난다.

#### 4) 예시

**(1) 댕글링 포인터 — 해제 후 사용**

```c
int *p = malloc(sizeof(int) * 5);
free(p);     // 메모리를 돌려줬다. 하지만 p는 그 주소를 그대로 들고 있다(댕글링).
*p = 2;      // 이미 내 것이 아닌 자리에 씀 → 엉뚱한 값 / 데이터 손상 (undefined behavior)
```

`free` 직후 `p`는 댕글링 포인터다. 여기에 값을 쓰면 운이 좋으면 아무 일 없어 보이고, 나쁘면 다른 데이터를 조용히 망가뜨린다. 그래서 보통 `free(p);` 다음에 `p = NULL;`을 적어 둔다.

**(2) 메모리 누수 — free 누락**

```c
int *p = malloc(sizeof(int) * 100);
p = malloc(sizeof(int) * 100);   // 새 메모리를 p에 다시 담음.
                                 // 앞서 잡은 100칸은 가리키는 포인터가 사라져 영영 회수 불가 → 누수
```

첫 번째 블록을 가리키던 유일한 손잡이(`p`)를 덮어써 버렸다. 이제 그 메모리는 `free`할 방법조차 없다. 이런 코드가 반복 실행되면 누수가 쌓여 메모리가 고갈된다.

**(3) NULL 역참조 — 즉시 크래시**

```c
int *p = NULL;   // 아무것도 가리키지 않음
*p = 5;          // NULL(주소 0) 역참조 → 프로그램이 그 자리에서 멈춤(크래시)
```

NULL 역참조는 위 두 경우와 달리 대개 즉시, 눈에 띄게 멈춘다. 그래서 메모리를 쓰기 전에 `if (p != NULL)`로 확인하는 습관이 안전장치가 된다.



이런 위험(직접 주소를 잘못 만지는 데서 오는 사고)을 줄이려고 주소를 한 겹 감싸 직접 노출을 막은 것이 '참조'

### 6. 참조 — 메모리 주소 감추기

#### 1) 개념 정의

참조(reference)는 이미 존재하는 어떤 변수에 붙인 또 다른 이름, 즉 별칭(alias)으로, 포인터와 달리 메모리 주소를 겉으로 드러내지 않고 원래 변수처럼 그대로 쓰게 해 준다.

#### 2) 원리 설명

참조를 만들면 컴파일러는 그 참조를 "원본 변수와 같은 실체"로 취급한다.&#x20;

즉 참조는 원본과 같은 자리에 붙은 또 다른 이름이므로, 참조를 읽으면 원본 값이 읽히고 참조에 값을 넣으면 원본이 바뀐다. \
포인터는 "주소를 담은 별도의 상자"라서 그 안의 주소를 꺼내려면 `*`로 역참조해야 하지만, 참조는 주소를 다루는 과정을 언어가 대신 처리해 사용자에게는 보이지 않는다. \
그래서 참조는 내부적으로는 개체의 위치를 다루더라도, 구문적으로는 개체 그 자체처럼 동작한다. \
결과적으로 프로그래머는 주소라는 개념을 의식하지 않고, 원본에 새 이름표 하나를 더 붙였다고 생각하며 코드를 쓰면 된다.

#### 3) 세부 메커니즘

* **선언과 동시에 반드시 초기화**: 참조는 "무엇의 별칭인지"를 만들 때 정해야 한다. 어떤 대상도 가리키지 않는 빈 참조는 만들 수 없다.
* **한 번 묶이면 다시 묶을 수 없음(no reseat)**: 처음 묶인 원본에 평생 고정된다. 이후 `ref = b;`라고 써도 참조가 `b`를 가리키도록 바뀌는 게 아니라, 원본에 `b`의 값을 복사해 넣는 동작이 된다.
* **포인터 산술 불가**: 참조는 주소를 다루는 값이 아니므로 `+1` 같은 산술로 옆 칸으로 옮겨갈 수 없다.
* **`&`나 `*` 없이 그대로 사용**: 값을 읽고 쓸 때 역참조 기호가 필요 없다. 또 참조의 주소를 구하면(`&ref`) 원본의 주소가 나온다 — 주소가 따로 숨어 있는 게 아니라 원본과 그냥 같다.

포인터와의 차이를 정리하면 다음과 같다.

#### 4) 예시

**C++ — 참조는 원본의 또 다른 이름**

```cpp
int a = 10;
int &ref = a;   // ref는 a의 별칭(같은 자리를 가리킴)

ref = 20;       // 사실상 a를 바꾸는 것
// 이제 a == 20, ref == 20

// 주소를 찍어 보면 둘이 같다
// &a 와 &ref 는 동일한 주소
```

`ref`에 20을 넣었을 뿐인데 `a`도 20이 된다. `*`나 `&`를 쓰지 않았고, `&a`와 `&ref`가 같은 주소라는 점에서 둘은 같은 메모리 한 칸의 두 이름임을 알 수 있다.

**파이썬 — 대입은 복사가 아니라 '별칭 붙이기'**

```python
accounts = [1, 2, 3]
backup = accounts          # 복사가 아니라, 같은 리스트에 이름표를 하나 더 붙인다

print(backup is accounts)  # True  ← 둘은 '같은 객체'(별칭)
```

자바·파이썬 같은 고수준 언어에서는 (적어도 객체에 대해) 변수가 값 자체가 아니라 객체를 가리키는 이름표처럼 동작한다. \
`backup = accounts`는 리스트를 복사하는 게 아니라 같은 객체에 이름표 하나를 더 다는 것이라, `backup is accounts`가 참이다 — 앞의 C++ 예에서 `&a`와 `&ref`가 같았던 것과 똑같은 '별칭' 관계다. \
(이렇게 공유된 객체를 함수에 넘기면 어떻게 되는지는 뒤의 '값·참조 전달'에서 다룬다.) \
여기서도 프로그래머는 주소를 직접 만지지 않는다.



참조는 "주소를 감춘 포인터"처럼 볼 수 있어, 앞의 **포인터 이해하기**·**포인터 산술**에서 다룬 주소 다루기의 위험을 줄여 준다. \
참조를 함수 인자로 넘기는 활용은 뒤의 **값·참조 전달**에서 이어 다룬다.

> * **널이라는 '10억 달러짜리 실수'**: 참조가 "아무것도 안 가리킬 수 없게(널 불가)" 설계된 데는 뼈아픈 역사가 있다. 토니 호어는 1965년 ALGOL W를 만들며 '널(null) 참조'를 넣었는데 — "구현이 너무 쉬워서 유혹을 못 참았다"고 했다 — 이 포인터 비슷한 빈 참조가 이후 수십 년간 셀 수 없는 충돌과 보안 결함을 낳았다. 그는 2009년 QCon 런던 강연에서 이를 "나의 10억 달러짜리 실수"라 부르며 공개 사과했고, 널을 아예 허용하지 않는 참조는 바로 이 실수에 대한 설계적 응답으로 볼 수 있다.
> * **참조는 사실 연산자 오버로딩 때문에 태어났다**: C++에 포인터가 이미 있는데도 비야네 스트롭스트룹이 참조를 따로 추가한 가장 큰 이유는, 놀랍게도 `a + b` 같은 연산자를 사용자 정의(연산자 오버로딩)할 때 코드를 자연스럽게 만들기 위해서였다. 만약 참조 없이 포인터만 있었다면 `a + b`를 `&a + &b` 비슷하게 써야 했을 텐데, 이는 도저히 봐 줄 수 없는 문법이었던 것이다. "주소를 감춰 코드를 깔끔하게"라는 참조의 성격이, 사실은 연산자 문법을 살리려다 나온 부산물인 셈이다.

### 7. 값/참조 전달 (call by value vs call by reference)

#### 1) 개념 정의

값 전달은 인자의 '값을 복사해서' 함수에 넘기는 방식이고, 참조 전달은 인자의 '주소(또는 별칭)를 넘겨서' 함수가 원본을 직접 다루게 하는 방식이다.

#### 2) 원리 설명

함수는 호출될 때 매개변수라는 새 변수를 만드는데, 이때 무엇을 그 매개변수에 채워 넣느냐가 두 방식을 가른다. \
값 전달이면 원본의 값을 그대로 복사해 채우므로, 매개변수와 원본은 서로 다른 메모리를 쓰는 별개의 변수가 된다. \
그래서 함수 안에서 매개변수를 아무리 바꿔도 원본은 그대로다. 반면 참조 전달이면 원본이 있는 '주소'를 넘기므로, 함수는 그 주소를 따라가 원본 자체를 건드린다. \
결국 같은 메모리를 두 이름이 가리키는 셈이라, 함수 안의 변경이 함수 밖 원본에도 그대로 남는다. 덤으로, 큰 데이터를 통째로 복사하지 않고 주소만 넘기므로 복사 비용도 아낀다.

#### 3) 세부 메커니즘

* **값 전달**: 호출 시 매개변수가 스택에 새로 잡히고 원본 값의 복사본이 들어간다. 원본과 복사본은 주소가 다르므로 서로 영향이 없다.
* **참조/포인터 전달**: 매개변수에는 값 대신 원본의 주소(또는 원본을 가리키는 별칭)가 들어간다. 함수는 그 주소를 통해 원본 메모리에 접근한다.

언어마다 이 "원본을 넘기는" 방법이 다르다.

* **C**: 언어 차원에서는 값 전달뿐이다. 원본을 바꾸고 싶으면 주소를 직접 값으로 넘기고(즉 포인터를 복사해서 넘기고), 함수는 그 주소를 따라가 원본을 고친다. 그래서 흔히 "포인터로 참조 전달을 흉내낸다"고 말한다.
* **C++**: C의 포인터 방식도 그대로 쓸 수 있고, 추가로 진짜 참조 매개변수를 지원한다. `&`를 붙인 매개변수는 호출한 쪽 변수와 같은 대상을 가리켜서, 함수 안에서 평범하게 대입하듯 써도 원본이 바뀐다.
* **자바·파이썬**: "객체 참조를 값으로 전달"한다. 즉 객체를 가리키는 참조 자체가 복사되어 넘어간다. 두 참조가 같은 객체를 가리키므로 **객체의 내용은 바꿀 수 있다**(예: 리스트에 원소 추가). 하지만 함수 안에서 매개변수에 **다른 객체를 새로 대입(재대입)하면**, 복사된 참조만 다른 곳을 가리킬 뿐 호출한 쪽 변수는 그대로다. 특히 파이썬에서 정수·문자열·튜플 같은 불변 객체는 제자리 수정이 불가능해 결과적으로 값 전달처럼 보인다.

#### 4) 예시

**C — 값 전달 swap (실패)**

```c
#include <stdio.h>

void swap(int x, int y) {  // 복사본을 받음
    int tmp = x;
    x = y;
    y = tmp;
}

int main(void) {
    int a = 1, b = 2;
    swap(a, b);
    printf("a=%d, b=%d\n", a, b);  // a=1, b=2  (안 바뀜)
    return 0;
}
```

함수 안 `x`, `y`는 `a`, `b`의 복사본이라, 둘을 교환해도 원본 `a`, `b`는 그대로다.

**C — 포인터로 참조 전달 swap (성공)**

```c
#include <stdio.h>

void swap(int *x, int *y) {  // 주소를 받음
    int tmp = *x;
    *x = *y;
    *y = tmp;
}

int main(void) {
    int a = 1, b = 2;
    swap(&a, &b);                  // a, b의 주소를 넘김
    printf("a=%d, b=%d\n", a, b);  // a=2, b=1  (바뀜)
    return 0;
}
```

이번엔 `a`, `b`의 주소를 넘겼으므로, 함수가 그 주소를 따라가 원본 값을 직접 교환한다.

**C++ — 진짜 참조로 swap (성공)**

```cpp
void swap(int &x, int &y) {  // x, y가 곧 a, b
    int tmp = x;
    x = y;
    y = tmp;
}
// 호출: swap(a, b);  →  a=2, b=1
```

주소를 직접 넘기거나 풀어볼 필요 없이, 매개변수가 원본 그 자체처럼 동작한다.

**자바·파이썬 — 객체는 내용 수정은 되고, 재대입은 반영 안 됨**

```python
def add_item(lst):
    lst.append(4)   # 같은 리스트를 수정 → 호출자에 반영됨

def rebind(lst):
    lst = ["new"]   # 매개변수만 다른 객체를 가리킴 → 호출자에 반영 안 됨

nums = [1, 2, 3]
add_item(nums)
print(nums)         # [1, 2, 3, 4]

nums = [1, 2, 3]
rebind(nums)
print(nums)         # [1, 2, 3]  (그대로)
```

객체의 내용을 고치는 것과, 매개변수에 새 객체를 대입하는 것은 결과가 다르다.

"원본을 바꾸거나 큰 데이터 복사를 피하고 싶을 때 주소·별칭을 넘긴다"는 것이 핵심 쓰임이다.

> 💡 **TMI**
>
> * **자바·파이썬 방식엔 따로 이름이 있다 — '공유에 의한 호출'**: 자바·파이썬의 인자 전달을 두고 "값 전달이냐 참조 전달이냐"는 논쟁이 끝없이 벌어지는데, 사실 이 방식엔 1974년 바버라 리스코프가 CLU 언어를 설계하며 붙인 '공유에 의한 호출(call by sharing)'이라는 정식 이름이 있다. 객체 자체를 복사하지도, 호출자의 변수를 통째로 넘기지도 않고, '같은 객체를 가리키는 참조'를 복사해 공유한다는 뜻이다. 본문에서 본 "내용 수정은 반영되지만 재대입은 반영 안 됨"이라는 헷갈리는 동작이, 이 이름 하나로 깔끔하게 설명된다.
> * **숫자 1을 2로 바꿔 버린 포트란**: 초창기 포트란은 인자를 참조로 넘겼는데, 이 때문에 전설적인 버그가 있었다. 함수에 상수 `1`을 그대로 넘기고 함수 안에서 그 매개변수를 고치면, 컴파일러가 코드 곳곳의 `1`을 같은 메모리 자리로 묶어 두는 바람에 그 뒤로 프로그램 전체에서 `1`이 `2`로 바뀌어 버리는 식이었다. 참조 전달이 "원본을 직접 건드린다"는 능력을, 상수라는 절대 변하면 안 될 값에까지 적용했을 때 벌어지는 악몽을 보여 주는 사례다.
> * **사라진 제3의 방식, '이름에 의한 호출'**: 값 전달·참조 전달 말고 한때 '이름에 의한 호출(call by name)'이라는 제3의 방식도 있었다. 인자를 미리 계산해 두지 않고 함수 안에서 실제로 쓰이는 순간마다 그 자리에서 다시 계산하는 방식인데, ALGOL 60에 들어 있었다. 더 놀라운 건 이게 의도된 설계가 아니라, 참조 전달을 우아하게 정의하려다 실수로 생겨난 부작용이었고 한참 뒤에야 'Jensen's device'라는 기법을 통해 그 정체가 드러났다는 점이다.

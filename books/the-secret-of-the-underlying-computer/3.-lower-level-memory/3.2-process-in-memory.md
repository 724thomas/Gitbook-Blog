# 3.2 Process in memory

### 1. 가상 메모리 — 눈에 보이는 것이 항상 실제와 같지는 않다

#### 1) 개념 정의

가상 메모리란, 각 프로세스가 실제 물리 메모리의 배치와 무관하게 **자신만의 크고 연속된 주소 공간을 통째로 가진 것처럼 보이게 해 주는 메모리 추상화(착시)** 기법이다.

#### 2) 원리 설명

만약 프로세스가 물리 메모리 주소를 직접 사용한다면 여러 문제가 생긴다. \
두 프로세스가 우연히 같은 물리 주소를 쓰려고 하면 서로의 데이터를 덮어써 충돌이 나고, 한 프로세스가 다른 프로세스(또는 운영체제)의 메모리를 마음대로 들여다보거나 망가뜨릴 수 있어 격리와 보호가 불가능하다. \
또 프로그램은 자신이 실제 메모리의 어느 위치에 적재될지 미리 알 수 없으므로 프로그래밍 자체가 까다로워진다. \
가상 메모리는 프로세스와 물리 메모리 사이에 한 겹의 추상층을 두어 이 문제를 해결한다.&#x20;

즉, 프로세스는 항상 0번지부터 시작하는 깔끔하고 독립적인 "가상 주소"만 사용하고, 이 가상 주소가 실제로 물리 메모리의 어디에 놓이는지는 하드웨어와 운영체제가 뒤에서 매핑(연결)해 준다. \
그 덕분에 각 프로세스는 다른 프로세스의 존재를 신경 쓰지 않고도 마치 메모리 전체를 혼자 쓰는 것처럼 동작할 수 있고, 물리 메모리가 군데군데 비어 조각나 있어도 프로세스에게는 연속된 공간으로 보여 줄 수 있으며(단편화 회피), 프로그램이 실제 RAM보다 커도 당장 쓰는 부분만 물리 메모리에 두는 식으로 실행할 수 있다. \
"눈에 보이는 것이 항상 실제와 같지는 않다"가, 프로세스가 보는 주소는 실제 물리 주소가 아니라 운영체제가 보여 주는 가상의 모습이다.

#### 3) 세부 메커니즘

이 추상화를 한 단계 더 들여다보면, 핵심은 "가상 주소 공간"과 "매핑이라는 간접층" 두 가지다. \
가상 주소 공간은 프로세스마다 하나씩 따로 주어지며, 0번지부터 시작하는 연속된 주소들의 범위로, 그 크기는 물리 메모리(RAM)의 실제 용량이 아니라 CPU가 다룰 수 있는 주소의 폭으로 정해진다.&#x20;

예를 들어 32비트 시스템에서는 2³² = 약 4GB 범위의 가상 주소를 표현할 수 있다. \
그래서 두 프로세스가 똑같이 `0x1000`번지를 사용해도 서로의 데이터를 건드리지 않는다 — 각자의 가상 주소 공간이 독립적이기 때문이다. (같은 가상 주소가 프로세스마다 실제로는 다른 물리 위치로 이어지는데, 그 일이 '어떤 자료구조로, 어떻게' 일어나는지는 형제 소주제 '페이지와 페이지 테이블'이 다룬다.)&#x20;

이 "가상 → 물리"를 이어 주는 매핑이 바로 간접층의 본질이며, 이 한 겹의 연결 덕분에 프로세스 격리, 메모리상의 자유로운 재배치, 메모리 공유 같은 일들이 가능해진다.

#### 4) 예시

같은 프로그램을 두 번 실행해 전역 변수의 주소를 출력해 보면, 서로 다른 두 프로세스가 **똑같은 가상 주소를 보고**한다는 것을 직접 확인할 수 있다.

```c
#include <stdio.h>
int g = 0;
int main(int argc, char** argv) {
    g = (argc > 1) ? 999 : 1;     // 인자 없이 실행=A, 인자 주고 실행=B
    printf("&g=%p  g=%d\n", (void*)&g, g);
    return 0;
}
```

같은 실행 파일을 인자만 다르게 해서 두 번 돌린 실제 출력(주소 값은 환경에 따라 달라짐):

```
--- 프로세스 A ---
&g=00007FF66F389080  g=1
--- 프로세스 B ---
&g=00007FF66F389080  g=999
```

두 프로세스가 보고한 변수 `g`의 가상 주소(`0x7FF66F389080`)는 완전히 같다. \
이것이 바로 "각 프로세스가 자기만의 주소 공간을 가진다"는 착시다. \
만약 이 주소가 진짜 물리 주소였다면, 두 프로세스가 동시에 살아 있을 때 같은 메모리 칸을 두고 충돌해야 한다.&#x20;

그러나 실제로는 각자의 `0x...9080`이 서로 다른 물리 메모리로 매핑되어 충돌 없이 공존한다. (참고: 두 실행에서 주소가 같게 나온 것은 이 시스템 환경에서의 결과로, 주소 값과 그 일치 여부는 환경에 따라 달라질 수 있다.)



가상 메모리는 자연스럽게 "그렇다면 가상 주소를 물리 주소로 잇는 매핑 정보는 어디에, 어떻게 저장되는가?"라는 질문을 낳는다.&#x20;

> 💡 **TMI**
>
> * **"실행마다 주소가 달라지는" 보안 기법 ASLR**: 현대 OS에서 같은 프로그램을 실행할 때마다 변수 주소가 달라지는 것은 ASLR(주소 공간 배치 무작위화) 때문인데, 공격자가 "특정 주소에 코드가 있다"고 가정하는 공격을 막으려는 장치다. 흥미롭게도 ASLR은 OS 회사가 아니라 PaX라는 익명 보안 프로젝트가 2001년 리눅스 커널 패치로 처음 설계했고, OpenBSD가 2003년 기본 적용한 첫 주류 OS, Windows는 2007년 Vista에서야 도입했다.
> * **32비트의 "2GB"는 사실 절반을 OS가 가져간 결과**: 32비트 프로세스가 표현할 수 있는 주소 공간은 4GB지만, 그중 기본 2GB만 애플리케이션 몫이고 나머지 2GB는 커널 몫이다. 메모리를 많이 쓰는 프로그램을 위해 `/3GB` 부팅 옵션과 `LARGE_ADDRESS_AWARE` 플래그로 사용자 영역을 3GB까지 늘릴 수 있었지만, 커널 영역이 1GB로 줄어 드라이버가 오작동하는 부작용 탓에 권장되지는 않았다.

### 2. 페이지와 페이지 테이블 — 가상에서 현실로

#### 1) 개념 정의

페이지(page)는 가상 메모리를 자른 고정 크기 단위이고, 프레임(frame)은 물리 메모리를 같은 크기로 자른 단위이며, 페이지 테이블(page table)은 "어느 가상 페이지가 어느 물리 프레임에 들어 있는지"를 적어 둔 프로세스별 매핑 표다.

#### 2) 원리 설명

가상 메모리와 물리 메모리를 양쪽 모두 동일한 고정 크기(예: 4KB) 조각으로 잘라, **페이지 단위로** 서로 대응시킨다.&#x20;

즉 "프로세스는 페이지의 집합, 메모리는 프레임의 집합"이고, 페이지 하나가 프레임 하나에 통째로 들어간다. \
이때 어떤 가상 페이지가 어떤 물리 프레임에 들어갔는지를 기록하는 자료구조가 페이지 테이블이며, 페이지 번호를 인덱스로 넣으면 대응하는 프레임 번호가 나오도록 되어 있다. \
핵심은 페이지 테이블이 **프로세스마다 따로 하나씩** 존재한다는 점이다 — 그래서 같은 가상 주소라도 프로세스가 다르면 서로 다른 물리 프레임으로 풀린다. \
프로그램이 가상 주소를 낼 때마다 이 표를 거쳐 물리 주소로 바꾸는 변환이 반복적으로 일어난다.

#### 3) 세부 메커니즘

변환의 비밀은 가상 주소를 **두 토막으로 쪼개는 것**에 있다. \
페이지 크기가 2ⁿ바이트면, 가상 주소의 **하위 n비트는 오프셋(offset, 페이지 안에서의 위치)**, 그 위의 **상위 비트는 페이지 번호**가 된다. \
변환은 다음 세 단계로 진행된다.

1. **분할(split)**: 가상 주소를 `[페이지 번호 | 오프셋]`으로 나눈다.
2. **조회(lookup)**: 페이지 번호를 페이지 테이블의 인덱스로 사용해, 대응하는 **프레임 번호**를 읽어 온다.
3. **재조립(reconstruct)**: 읽어 온 프레임 번호 뒤에 **오프셋을 그대로 붙여** 물리 주소를 완성한다.

여기서 결정적인 포인트는 **오프셋이 변환 과정에서 바뀌지 않는다**는 것이다. \
페이지와 프레임의 크기가 같으므로 "페이지 안 5번째 바이트"는 "프레임 안 5번째 바이트"와 같다.&#x20;

따라서 변환은 사실상 "앞 토막(페이지 번호)만 프레임 번호로 갈아 끼우는" 작업이다. 식으로 쓰면 다음과 같다.

```
물리 주소 = (프레임 번호 << 오프셋 비트 수) + 오프셋
         = (프레임 번호 × 페이지 크기) + 오프셋
```

#### 4) 예시

**예시 ① — 작은 주소 공간으로 원리 보기**

* 조건: 페이지 크기 16바이트(2⁴ → 오프셋 4비트), 주소 공간 64바이트(2⁶ → 총 6비트, 페이지 번호 2비트)
* 가상 주소 `21` = 이진수 `010101`
  * 페이지 번호 = 상위 2비트 `01` = **1번 페이지**
  * 오프셋 = 하위 4비트 `0101` = **5**
* 페이지 테이블 조회: 1번 페이지 → **2번 프레임**이라고 하자.
* 물리 주소 = (2 × 16) + 5 = 32 + 5 = **37**

**예시 ② — 비트 분할로 직접 계산**

* 조건: 페이지 크기 16바이트(오프셋 4비트), 주소 공간 64바이트(총 6비트, 페이지 번호 2비트). 페이지 테이블 = `[5, 3, 2, 8]` (인덱스 0\~3 → 프레임 번호)
* 가상 주소 `50` = 이진수 `110010`
  * 오프셋 = 하위 4비트 `0010` = **2**
  * 페이지 번호 = 상위 2비트 `11` = **3번 페이지**
* 페이지 테이블 조회: 인덱스 3 → 값 `8` = **8번 프레임**
* 물리 주소 = (8 × 16) + 2 = 128 + 2 = **130** ( = 이진수 `10000010`)

두 예시 모두 "오프셋은 그대로, 앞 토막만 프레임 번호로 교체"라는 같은 규칙으로 풀린다는 점을 확인할 수 있다.



\*\*'가상 메모리'\*\*가 "프로세스마다 연속된 자기만의 주소 공간이 있는 것처럼 보이게 한다"는 _목적과 착&#xC2DC;_&#xB97C; 다룬다면, 여기서 본 페이지·페이지 테이블·주소 변환은 그 착시를 **실제로 떠받치는 구현 장치**다.&#x20;

즉 가상 메모리가 "무엇을/왜"라면, 페이지 테이블 변환은 그것을 "어떻게" 현실의 물리 주소로 바꿔 주는 톱니바퀴에 해당한다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **변환의 99%는 페이지 테이블까지 안 내려간다**: 매 메모리 접근마다 페이지 테이블을 뒤지면 너무 느리기 때문에, TLB(Translation Lookaside Buffer)라는 하드웨어 캐시가 최근 변환 결과를 들고 있다. 실제 시스템의 TLB 적중률은 보통 95\~99%에 달하는데, 4KB 한 페이지 안에서 프로그램이 한동안 머무는 "지역성(locality)" 덕분이다. 즉 100번 중 1번 정도만 진짜로 페이지 테이블까지 내려간다.
> * **대형 페이지(huge page)는 TLB를 아끼는 트릭**: 기본 4KB 대신 x86에서 2MB나 1GB짜리 페이지를 쓰면, 같은 양의 메모리를 매핑하는 데 필요한 페이지 테이블 항목 수가 확 줄어든다(1GB huge page 한 개 = 4KB 페이지 262,144개분). 그래서 Oracle, PostgreSQL 같은 대형 데이터베이스는 성능을 위해 huge page를 일부러 켜서 운영한다.
> * **발상이 정반대인 역페이지 테이블**: 보통 페이지 테이블은 "가상 페이지마다 한 줄"이라 주소 공간이 클수록 표가 커지는 반면, 역페이지 테이블(inverted page table)은 "물리 프레임마다 한 줄"이라 표 크기가 실제 물리 메모리 양에 묶여 일정하다. 이 방식은 PowerPC, UltraSPARC, Itanium(IA-64) 같은 실제 상용 아키텍처에서 채택됐다.

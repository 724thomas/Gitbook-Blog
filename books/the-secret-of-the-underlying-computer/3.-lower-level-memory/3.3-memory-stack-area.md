# 3.3 Memory: Stack area

### 1. 함수: 프로그래머를 위한 도우미

#### 1) 개념 정의

함수란 여러 단계의 작업을 하나의 이름으로 묶어 둔 코드 덩어리로, 호출하는 쪽은 그 이름만 부르면 될 뿐 내부가 어떻게 돌아가는지는 몰라도 되는 "추상화 도우미"다.

#### 2) 원리 설명

프로그램이 커질수록 사람의 머리로 한꺼번에 다룰 수 있는 양을 넘어선다. \
그래서 우리는 큰 문제를 작은 작업 단위로 쪼개고, 각 단위를 함수라는 상자 안에 넣어 이름을 붙인다. \
이렇게 이름을 붙여 두면, 잠재적으로 매우 복잡한 작업도 단 한 줄의 호출로 처리할 수 있다. \
핵심은 함수가 "복잡함을 숨김으로써 복잡함을 다루게 해 주는" 도구라는 점이며, 컴퓨터 과학에서는 이 개념을 추상화(abstraction)라고 부른다. \
함수를 쓰는 사람은 그 안에 어떤 단계들이 들어 있는지 신경 쓸 필요 없이, "무엇을 해 주는가"만 알면 된다. \
덕분에 한 번 잘 만든 함수는 수많은 다른 상황에서 몇 번이고 다시 불러 쓸 수 있다(코드 재사용).

#### 3) 세부 메커니즘

함수가 도우미가 될 수 있는 비결은 "인터페이스"와 "구현"을 분리하는 데 있다. \
함수는 일종의 검은 상자(black box)여서 바깥에서는 안을 들여다볼 수 없다. \
상자를 쓰기 위해 알아야 할 것은 오직 인터페이스 — 무엇을 넣으면 무엇이 나오는가 — 뿐이고, 그 안의 구현은 몰라도 된다. \
이 분리가 주는 실질적 이득은, 상자를 바깥에서 본 동작이 그대로 유지되는 한 내부 구현은 언제든 바꿔도 된다는 것이다. \
그래서 호출자는 "면적을 구한다"는 결과에만 의존하고, 그 계산이 어떤 공식·어떤 순서로 이뤄지는지에는 의존하지 않는다. \
결국 함수는 큰 문제를 더 작은 하위 문제들로 나누되, 각 조각을 깔끔한 인터페이스 뒤에 가두어 서로의 복잡함이 새어 나오지 않게 만드는 장치다.

#### 4) 예시

운전 비유로 추상화의 감을 먼저 잡아 보자. \
시동을 걸 때 스타터 모터가 플라이휠을 돌리고 크랭크축이 회전하며 피스톤이 움직이는 복잡한 기계 동작이 일어나지만, 운전자는 그 원리를 전혀 몰라도 차를 몰 수 있다. \
함수도 똑같이, 내부의 복잡한 동작을 감춘 채 "쓰기만 하면 되는" 인터페이스를 제공한다.

코드로 보면 다음과 같다. 사각형 넓이를 구하는 함수를 한 번 만들어 두면:

```c
// 구현: 이 안이 어떻게 동작하는지는 호출자가 몰라도 된다
int rectangle_area(int width, int height) {
    return width * height;
}

int main(void) {
    int a = rectangle_area(5, 3);   // 호출자는 "5×3짜리 넓이"라는 결과만 안다
    int b = rectangle_area(10, 2);  // 같은 함수를 다른 상황에서 재사용
    // a == 15, b == 20
}
```

호출하는 쪽(`main`)은 `rectangle_area(5, 3)`이 `15`를 돌려준다는 사실만 알면 충분하며, 안에서 곱셈을 하는지 다른 방법을 쓰는지는 알 필요가 없다. \
만약 나중에 내부 계산 방식을 바꾸더라도, "넓이를 돌려준다"는 바깥 동작만 같으면 `main`은 한 글자도 고치지 않아도 된다. \
동시에 같은 함수를 `(10, 2)`로 다시 불러 코드를 재사용한 것도 확인할 수 있다.



이렇게 호출자가 "내부는 몰라도 된다"며 함수를 도우미로 마음껏 부르려면, 컴퓨터는 그 호출이 끝난 뒤 어디로 돌아가고 누가 무엇을 처리 중인지를 정확히 추적해 줘야 한다. \
바로 이 추적을 담당하는 자료구조가 「스택: 함수 호출 활동 추적」으로 이어지며, 이 절의 나머지 소주제들은 그 추적이 실제로 어떻게 구현되는지를 파고든다.

> 💡 **TMI**
>
> * **함수(서브루틴)의 탄생**: '함수(서브루틴)' 개념은 1951년 무렵 케임브리지의 데이비드 휠러·모리스 윌크스·스탠리 길이 EDSAC에서 고안했다. 휠러가 만든 호출 방식은 그의 이름을 따 '휠러 점프(Wheeler Jump)'로 불렸고, 휠러는 이 업적으로 1951년 세계 최초의 컴퓨터과학 박사학위를 받았다.
> * **호출이 사라지기도 한다**: 컴파일러는 호출·프레임 생성 비용을 없애려 짧은 함수의 본문을 호출 지점에 그대로 펼쳐 넣는 '인라인(inline)' 최적화를 한다. 우리가 작성한 함수가 항상 실제 '호출'로 남는 것은 아니다.

### 2. 스택: 함수 호출 활동 추적

#### 1) 개념 정의

함수 호출은 "가장 마지막에 시작한 함수가 가장 먼저 끝나고 자신을 부른 자리로 정확히 되돌아온다"는 후입선출(LIFO) 성질을 가지므로, 프로그램이 '지금 어떤 함수들이 호출 도중에 있는지'를 추적하는 데에 push/pop만 허용하는 자료구조인 **스택**이 정확히 들어맞는다.

#### 2) 원리 설명

함수 A가 함수 B를 부르면, A는 아직 끝나지 않은 채 멈춰 서서 B가 끝나기를 기다린다. \
만약 B가 다시 C를 부르면, B 역시 멈춰 선 채 C를 기다린다.&#x20;

즉 호출이 중첩(A→B→C)될수록 **가장 나중에 시작된 함수(C)가 가장 먼저 끝나야** 그 아래에서 기다리던 함수(B)가 비로소 이어서 진행할 수 있다 — 이것이 함수 호출이 본질적으로 갖는 후입선출 순서다. \
콜 스택은 이런 "활성 상태로 실행을 마치지 못하고 대기 중인 함수들"의 정보를 저장하는 자료구조이며, 이 활성화가 어떤 깊이로든 중첩될 수 있기 때문에 스택 구조가 필요하다. \
함수를 호출할 때 그 함수의 호출 활동 정보를 스택 맨 위에 쌓고(push), 함수가 끝나면 맨 위에서 걷어내는(pop) 동작이, 위에서 본 "마지막 호출이 먼저 끝난다"는 순서와 한 치의 어긋남 없이 일대일로 맞아떨어진다.&#x20;

그래서 별도의 복잡한 장부 없이, 스택의 맨 위만 보면 '지금 실제로 실행 중인 함수'를 항상 알 수 있다.

#### 3) 세부 메커니즘

스택 맨 위에 올라와 있는 것이 현재 실행 중인 함수이고, 그 아래에 깔린 것들은 모두 "자기가 부른 함수가 끝나기를 기다리며 멈춰 있는" 함수들이다.&#x20;

따라서 스택은 단순한 메모리 더미가 아니라 **호출 관계의 기록**이다 — 아래에서 위로 읽으면 "누가 누구를 불렀는가"의 사슬(호출 경로)이 그대로 드러난다. \
핵심은 스택이 push/pop이라는 두 가지 연산만 허용한다는 제약 자체가 함수 호출의 규칙을 강제한다는 점이다. \
함수는 반드시 가장 최근에 호출된 것부터 끝나므로, 중간에 끼어 있는 함수를 임의로 먼저 끄집어낼 수 없고 오직 맨 위 것만 pop된다. \
push되고 pop되는 이 한 덩어리의 정보를 흔히 \*\*스택 프레임(stack frame)\*\*이라고 부르는데, 여기서 중요한 것은 프레임의 내용이 아니라 "프레임이 호출될 때 쌓이고 끝날 때 정확히 역순으로 걷힌다"는 활동 추적의 질서 그 자체다.

#### 4) 예시

함수 A가 B를, B가 C를 호출하는 상황을 생각해 보자.

```
함수 호출/반환 흐름            스택의 변화 (맨 위 = 최근 호출, 아래로 자람)

A 시작                         [ A ]
A가 B 호출  → push B           [ A | B ]        ← B가 실행 중 (맨 위)
B가 C 호출  → push C           [ A | B | C ]    ← C가 실행 중 (맨 위)
C 끝        → pop  C           [ A | B ]        ← B로 되돌아옴
B 끝        → pop  B           [ A ]            ← A로 되돌아옴
A 끝        → pop  A           [        ]       ← 스택 비어 있음
```

호출 순서는 A → B → C였지만 **종료 순서는 정확히 그 역순인 C → B → A**다. \
C가 끝나는 순간 스택 맨 위에는 다시 B가 드러나고, 프로그램은 B가 멈췄던 바로 그 지점에서 이어서 실행된다. \
가장 마지막에 시작된 C가 가장 먼저 사라지고, 가장 먼저 시작된 A가 가장 늦게 사라지는 것 — 이것이 함수 호출 추적에서 LIFO가 작동하는 구체적 모습이다. (재귀 호출은 같은 함수가 자기 자신을 부르는 경우인데, 호출마다 새로운 프레임이 따로 쌓이므로 위와 똑같은 push/pop 질서가 그대로 적용된다.)



> 💡 **TMI**
>
> * **자료구조 스택 = 콜 스택**: LIFO 자료구조 '스택'과 호출을 추적하는 '콜 스택'은 이름만 같은 게 아니라 동작 원리가 같다. 나아가 JVM 같은 '스택 머신'은 연산까지 스택에 값을 쌓고 꺼내는 방식으로 수행하도록 설계된 가상 기계다.
> * **스택 트레이스의 정체**: 프로그램이 죽었을 때 보는 '스택 트레이스(stack trace)'나 디버거의 `backtrace` 명령은 바로 이 콜 스택을 위에서부터 풀어 읽은 것이다. "어느 함수가 어느 함수를 불렀는지"의 호출 사슬을 사람이 읽을 수 있게 출력한 것이다.
> * **자라는 방향은 규약일 뿐**: 스택이 높은 주소에서 낮은 주소로 자란다는 것은 아키텍처가 정한 규약일 뿐 절대적 법칙이 아니다. 일부 아키텍처는 반대 방향으로 자라도록 설계되어 있다.

### 3. 스택 프레임과 스택 영역(거시적 관점)

#### 1) 개념 정의

스택 프레임은 함수 호출 한 번에 필요한 정보(인자·반환 주소·이전 BP·지역 변수·저장된 레지스터)를 한 덩어리로 묶은 메모리 구획이며, 이런 프레임들이 메모리의 스택 영역에 차곡차곡 쌓인 전체 모습이 곧 실행 중인 프로그램의 호출 상태다.

#### 2) 원리 설명

함수는 서로를 호출하며 중첩되므로, 각 호출이 쓰는 작업 공간도 호출된 순서대로 쌓였다가 끝난 순서의 역순으로 사라져야 한다. \
이 "나중에 들어간 것이 먼저 나오는(LIFO)" 성질이 스택 자료구조와 똑같기 때문에, 호출 정보 묶음을 스택 영역에 쌓는다. \
스택 영역은 메모리에서 큰 주소 쪽에 자리를 잡고 **낮은 주소 방향으로 자라며**, 함수가 호출될 때마다 새 프레임이 더 낮은 주소 쪽에 하나 더 붙는다. \
함수가 반환하면 그 프레임은 통째로 걷히고, 스택은 호출 직전 상태로 돌아간다.&#x20;

따라서 어느 순간 스택 영역을 위에서 아래로 훑으면, 가장 바깥 함수부터 지금 실행 중인 함수까지의 호출 사슬이 그대로 보인다.

#### 3) 세부 메커니즘

"지금 어느 프레임이 활성 상태인가"는 두 포인터가 가리킨다. \
스택 포인터(SP)는 스택 영역의 현재 꼭대기, 즉 가장 최근 프레임의 가장 낮은 주소 쪽 경계를 가리키고, 베이스 포인터(BP)는 그 프레임 안의 고정된 기준점을 가리킨다.&#x20;

그래서 SP와 BP 사이 구간이 곧 "현재 활성 프레임"의 영역이 된다. \
또 각 프레임에는 호출한 쪽의 BP 값(이전 BP)이 보관되어 있어서, 이 값이 한 단계 위(더 큰 주소)의 프레임이 어디 있는지를 가리킨다. \
이렇게 프레임들이 줄줄이 연결되어, 정지된 메모리만 봐도 호출 사슬 전체를 따라갈 수 있다.

#### 4) 예시

다음은 `main` → `f1` → `f2` 순서로 호출된 순간의 스택 영역 그림이다. 주소는 위가 높고 아래가 낮으며, 스택은 아래(낮은 주소) 방향으로 자란다. 모든 인자가 스택에 놓인 고전적 프레임 모델로 그렸다.

```
   높은 주소
  ┌───────────────────────────┐
  │      ... (그 이전)         │
  ├───────────────────────────┤  ┐
  │   main 의 인자             │  │
  │   반환 주소(→ main 호출자) │  │  main 의 프레임
  │   이전 BP(main 호출자의)   │  │  (가장 바깥, 가장 오래됨)
  │   main 의 지역 변수        │  │
  │   저장된 레지스터          │  │
  ├───────────────────────────┤  ┘
  │   f1 의 인자(main이 넘김)  │  ┐
  │   반환 주소(→ main 안)     │  │  f1 의 프레임
  │   이전 BP(main 의 BP)      │  │
  │   f1 의 지역 변수          │  │
  │   저장된 레지스터          │  │
  ├───────────────────────────┤  ┘
  │   f2 의 인자(f1이 넘김)    │  ┐
  │   반환 주소(→ f1 안)       │  │
  │   이전 BP(f1 의 BP)        │  │  f2 의 프레임  ← BP (이 프레임의 기준점)
  │   f2 의 지역 변수          │  │  (현재 실행 중)
  │   저장된 레지스터          │  │  ← SP (스택 꼭대기 = 가장 낮은 주소)
  └───────────────────────────┘  ┘
   낮은 주소  ↓ 스택은 이 방향으로 자란다
```

한 프레임만 떼어 본 표준 배치(높은 주소 → 낮은 주소 순서)는 다음과 같다.

```
  높은 주소
  ┌──────────────────────┐
  │  호출 인자/매개변수   │   ← 호출한 쪽이 넘겨준 값
  │  반환 주소            │   ← 함수가 끝나고 돌아갈 위치
  │  이전 BP 저장값       │   ← 호출한 쪽 프레임으로 이어지는 고리
  │  지역 변수            │
  │  임시 저장된 레지스터 │
  └──────────────────────┘
  낮은 주소
```

위 그림은 모든 인자를 스택에 놓는 고전적 모델이다. \
실제 64비트 환경에서는 처음 몇 개의 인자를 레지스터로 전달하는 경우가 많지만, 큰 그림을 보는 데는 이 단순한 형태로 충분하다.



> 💡 **TMI**
>
> * **Stack Overflow라는 이름**: 재귀가 너무 깊어 프레임이 끝없이 쌓이면 스택 영역의 한계를 넘는 '스택 오버플로(stack overflow)' 크래시가 난다. 유명한 개발자 Q\&A 사이트 'Stack Overflow'의 이름이 바로 이 오류에서 따온 것이다.
> * **꼬리 호출 최적화**: 함수가 마지막에 단순히 다른 함수를 호출하고 그 결과를 그대로 반환하는 '꼬리 호출(tail call)'이라면, 컴파일러는 새 프레임을 쌓는 대신 현재 프레임을 재활용할 수 있다. 덕분에 아주 깊은 재귀도 스택을 늘리지 않고 돌릴 수 있다.
> * **Scheme은 의무, Common Lisp은 선택**: Scheme은 이 꼬리 호출 최적화를 표준이 강제하는 필수 요구사항으로 규정한 최초의 Lisp 계열 언어다. 반면 Common Lisp 표준은 강제하지 않아, 같은 Lisp 계열이라도 보장 수준이 다르다.

### 4. 함수 점프와 반환의 구현

#### 1) 개념 정의

함수 점프와 반환이란, CPU가 호출 시점에 **반환 주소**(호출한 자리 바로 다음 명령의 주소)를 저장해 두고 함수 본문으로 점프했다가, 함수가 끝나면 그 주소로 다시 점프해 원래 자리로 정확히 돌아오는 **제어 흐름** 메커니즘이다.

#### 2) 원리 설명

CPU는 "다음에 실행할 명령의 주소"를 가리키는 **프로그램 카운터(PC)** 를 따라 한 줄씩 코드를 실행한다. \
함수를 호출한다는 것은 이 PC를 함수 본문의 시작 주소로 **점프**시키는 일이다.&#x20;

그런데 함수가 끝났을 때 PC를 어디로 되돌려야 할지 CPU가 미리 기억해 두지 않으면, 호출한 자리로 돌아올 방법이 없다.&#x20;

그래서 호출 명령은 점프하기 직전에 **"호출 다음 명령의 주소"** 를 어딘가에 저장해 두는데, 이것이 반환 주소다. \
반환 시점에는 저장해 둔 반환 주소를 다시 PC에 실어 그곳으로 점프하므로, 실행이 끊긴 지점 바로 다음부터 자연스럽게 이어진다.&#x20;

즉 점프는 PC가 수행하고, 되돌아올 위치는 반환 주소가 기억한다.

#### 3) 세부 메커니즘

반환 주소를 어디에 저장하는가가 핵심이다. \
추상 모델에서 **호출(call)** 은 두 동작을 한 번에 한다. \
먼저 호출 직후 명령의 주소(= 그 시점 PC가 가리키던 다음 명령 주소)를 **스택에 저장**하고, 그다음 PC를 함수 시작 주소로 바꿔 점프한다. \
스택은 낮은 주소 방향으로 자라므로, 반환 주소를 밀어 넣을 때 스택 포인터(SP)는 더 낮은 주소로 이동한다. \
이 반환 주소는 새로 만들어지는 스택 프레임에서 \[호출 인자] 바로 아래, \[이전 BP 저장값]·\[지역 변수]보다 위쪽에 놓인다. **반환(return)** 은 그 역순이다. \
스택에 보관해 둔 반환 주소를 꺼내(pop) PC에 다시 싣고, 그 주소로 점프한다. \
함수가 중첩 호출되어도 각 호출의 반환 주소가 스택에 차례로 쌓였다가 후입선출(LIFO) 순서로 꺼내지므로, 항상 가장 최근에 호출한 자리로 정확히 되돌아온다.

#### 4) 예시

`main`이 `foo`를 호출하는 상황을 주소와 함께 따라가 보자. (주소는 설명용 가상 값이다.)

```
[코드와 주소]
main:
  0x100:  ... (foo 호출 준비)
  0x104:  call foo        ; foo로 점프 + 반환 주소 저장
  0x108:  x = 1           ; <-- 반환 주소: 'call 다음 줄'
  0x10C:  ...

foo:
  0x200:  ... (foo 본문)
  0x210:  return          ; 반환 주소로 점프
```

단계별 진행:

```
1) PC = 0x104, "call foo" 실행
     - 반환 주소 0x108 을 스택에 저장 (SP가 낮은 주소로 이동)
     - PC <- 0x200  (foo 시작으로 점프)

   스택(높은 주소 → 낮은 주소), call 직후 시점:
     [ foo 호출 인자  ]
     [ 반환 주소 0x108 ]   <- 방금 저장됨, SP는 여기 바로 아래
              ↑ SP
   ([이전 BP 저장값]·[지역 변수]는 foo의 프롤로그가 실행된 뒤에야 쌓인다)

2) PC = 0x200 → 0x210, foo 본문 실행 (프롤로그에서 이전 BP·지역 변수 영역을 마련)

3) PC = 0x210, "return" 실행
     - 스택에서 반환 주소 0x108 을 꺼냄(pop) (SP가 높은 주소로 복귀)
     - PC <- 0x108  (저장해 둔 자리로 점프)

4) PC = 0x108, "x = 1" 부터 실행 재개
     → main이 foo를 부르기 전에 멈췄던 '바로 다음 줄'에서 흐름이 이어진다.
```

결과적으로 `foo`로 빠졌던 제어가 `call foo` 다음 줄(`0x108`)로 정확히 돌아와, `main`이 중단 없이 계속 실행된다. \
만약 `foo` 안에서 또 다른 함수 `bar`를 호출한다면, `bar`의 반환 주소가 `0x108` 위에 한 번 더 쌓였다가 먼저 꺼내지므로, `bar` → `foo` → `main` 순으로 정확히 되돌아온다.



* **레지스터의 저장과 복원**: 함수가 망가뜨리면 안 되는 레지스터를 보존하는 일반 문제는 별개지만, "반환 주소를 스택에 보관한다"는 사실 자체는 그 보관 메커니즘과 같은 스택을 공유한다.
* **매개변수 전달과 반환값의 구현**: 여기서 '반환'은 오직 _제어(점프)_ 를 돌려주는 것이고, 함수가 계산한 _값(데이터)_ 을 어떻게 돌려주는지는 그 소주제에서 다룬다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **x86의 call/ret vs ARM의 LR**: x86은 `call` 명령 하나가 반환 주소를 스택에 밀어 넣으며 점프하고, `ret` 명령이 그 주소를 꺼내 돌아간다. 반면 ARM은 반환 주소를 스택이 아니라 별도의 '링크 레지스터(LR)'에 먼저 담아 두는 방식이라, 스택을 거치지 않는 leaf 함수 호출이 더 빠르다.
> * **반환 주소를 노린 최초의 인터넷 웜**: 반환 주소가 스택에 그대로 놓인다는 점은 공격의 표적이 되기도 한다. 1988년 로버트 모리스가 퍼뜨린 최초의 인터넷 웜은 UNIX `fingerd`의 버퍼 오버플로(취약한 `gets()` 사용)로 반환 주소를 덮어써 코드를 실행시켰고, 이 사건은 미국 컴퓨터사기남용법(1986) 위반 최초의 중범죄 유죄 판결로 이어졌다.

### 5. 매개변수 전달과 반환값의 구현

#### 1) 개념 정의

함수 호출 시 호출자가 함수에게 입력값(인자/매개변수)을 건네고, 함수가 계산 결과(반환값)를 호출자에게 되돌려주는 — 즉 호출 경계를 넘나드는 데이터를 주고받는 약속과 그 통로를 가리킨다.

#### 2) 원리 설명

함수는 혼자 동작하지 못하고 보통 외부에서 받은 값을 가지고 일한 뒤 그 결과를 다시 밖으로 내보내야 한다.&#x20;

그런데 호출자와 함수는 서로 다른 코드 영역이라, "값을 어디에 놓아두면 상대가 그곳에서 꺼내 쓴다"는 **사전에 정해진 약속**이 없으면 데이터를 주고받을 수 없다.&#x20;

그래서 인자를 놓는 자리와 반환값을 놓는 자리를 미리 고정해 둔다. \
이 자리로 쓸 수 있는 후보는 두 가지뿐이다 — 빠르지만 개수가 적은 **레지스터**, 그리고 느리지만 넉넉한 **스택**이다. \
호출자는 약속된 자리에 인자를 채워 넣고 함수를 부르며, 함수는 같은 약속에 따라 그 자리에서 인자를 읽고 결과를 약속된 반환 자리에 적어 둔다.

#### 3) 세부 메커니즘

* **인자를 놓는 곳**: 인자가 적을 때는 빠른 접근을 위해 **인자 전달용 레지스터**에 담는다. \
  실제 64비트 환경에서는 처음 몇 개의 인자를 이런 레지스터들로 전달한다. \
  인자가 그보다 많아져 레지스터가 모자라면, 넘치는 나머지 인자들은 호출자가 자신의 스택 프레임 위쪽(높은 주소 쪽의 \[호출 인자/매개변수] 영역)에 쌓아 두어 함수가 그곳에서 읽어 가도록 한다.
* **반환값을 내보내는 곳**: 함수는 계산이 끝나면 결과를 약속된 **반환값 레지스터**에 적어 두고 호출자에게 제어를 넘긴다. \
  호출자는 함수가 돌아온 직후 그 레지스터에서 결과를 꺼낸다. \
  반환값은 보통 이렇게 하나의 정해진 레지스터로 돌려준다.
* **요점**: 인자는 "레지스터 우선, 부족하면 스택"이라는 2단 구조이고, 반환값은 단일 레지스터 통로라는 점이 비대칭이다.

#### 4) 예시

```c
int add(int a, int b) {
    return a + b;
}

int main() {
    int c = add(2, 3);   // 결과: c == 5
}
```

고전적 프레임 모델로 그리면(스택은 아래로 자람), 호출자가 인자 `a`, `b`를 스택의 인자 영역에 놓고 함수를 부른다.

```
 높은 주소
 ┌──────────────────────────┐
 │ 인자: a = 2              │  ← 호출자가 채워 넣은 매개변수
 │ 인자: b = 3              │     ([호출 인자/매개변수] 영역)
 ├──────────────────────────┤
 │ 반환 주소 (위치 정보)     │  ← 자리만 표시 (역할은 「함수 점프와 반환」 소관)
 ├──────────────────────────┤
 │ 이전 BP 저장값           │
 ├──────────────────────────┤  ← BP
 │ (add의 지역/임시 공간)    │
 └──────────────────────────┘  ← SP
 낮은 주소

 add 내부: a + b = 2 + 3 = 5  →  [반환값 레지스터] = 5
 호출자(main): [반환값 레지스터]에서 5를 꺼내 c에 저장  →  c == 5
```

`add`는 두 인자를 읽어 합 `5`를 **반환값 레지스터**에 실어 두고, 호출자는 그 레지스터에서 `5`를 꺼내 `c`에 넣는다. (위 그림은 모든 인자를 스택에 놓는 고전 모델이며, 실제 64비트 환경이라면 `a`, `b`처럼 적은 인자는 인자 전달용 레지스터로 전달된다.)



> 💡 **TMI**
>
> * **누가 스택을 치우나**: 32비트 시절엔 cdecl·stdcall·fastcall 등 여러 규약이 공존했고, 핵심 차이 중 하나가 "스택에 쌓은 인자를 누가 치우는가"(호출자 정리 vs 피호출자 정리)였다. 잘못 섞어 호출하면 스택이 어긋나는 실제 버그의 원인이 되곤 했다.
> * **큰 반환값은 사실 인자다**: 레지스터에 다 담기지 못하는 큰 구조체 반환값은, 호출자가 미리 공간을 마련해 그 주소를 '숨은 포인터 인자'로 넘기고 함수가 그곳에 결과를 쓰는 방식(반환 슬롯)으로 처리된다.

### 6. 지역 변수는 어디에 있을까

#### 1) 개념 정의

지역 변수는 함수가 호출될 때마다 그 호출만의 스택 프레임 안 '지역 변수' 칸에 새로 자리가 잡히는, 그 함수 안에서만 쓰이는 데이터다.

#### 2) 원리 설명

함수가 호출되면 그 호출을 위한 스택 프레임이 하나 만들어지고, 그 함수가 선언한 지역 변수들은 이 프레임 안의 '지역 변수' 칸에 놓인다. \
호출이 일어날 때마다 프레임이 새로 생기므로, 같은 함수를 여러 번 부르면 그때마다 지역 변수의 자리도 새로 잡힌다.&#x20;

그래서 어떤 호출의 지역 변수는 다른 호출의 지역 변수와 물리적으로 다른 주소에 있고, 서로 값이 섞이지 않는다. \
함수 실행이 끝나면 그 프레임이 통째로 회수되면서 안에 있던 지역 변수의 자리도 함께 사라진다. \
이것이 "지역 변수는 함수가 끝나면 없어진다"라는 말의 실제 모습이다.&#x20;

즉 지역 변수의 수명은 그 함수의 한 번의 실행 동안만이다.

#### 3) 세부 메커니즘

프레임 안에서 지역 변수는 절대 주소가 아니라 **BP(베이스 포인터) 기준의 오프셋**으로 접근된다. \
우리 모델의 프레임은 높은 주소에서 낮은 주소 순으로 \[호출 인자] → \[반환 주소] → \[이전 BP 저장값] → \[지역 변수] → \[임시 저장된 레지스터]를 담는데, 지역 변수 칸은 저장된 BP보다 낮은 주소 쪽에 있으므로 "BP에서 일정 칸만큼 떨어진 곳"이라는 식으로 첫 번째, 두 번째 지역 변수를 찾아 읽고 쓴다. \
함수마다 BP는 자기 프레임을 가리키므로, 같은 오프셋이라도 각 호출은 자기 프레임 안의 자리를 가리킨다.&#x20;

한편 모든 지역 변수가 꼭 프레임에 들어가는 것은 아니어서, 자주 쓰는 일부 변수는 속도를 위해 메모리 대신 **레지스터**에 둘 수도 있다(주소를 꼭 메모리에 둬야 할 이유가 없을 때). \
함수가 반환할 때는 SP를 프레임이 시작하던 높은 주소 쪽으로 되돌려 프레임을 회수하는데, 이때 지역 변수가 있던 메모리는 더 이상 그 함수의 것이 아니게 되어 변수의 자리가 사라진다. (값이 즉시 0으로 지워진다기보다, 그 칸이 회수되어 다음 호출이 덮어 쓸 수 있는 상태가 된다.)

#### 4) 예시

같은 이름의 지역 변수가 호출마다 다른 프레임에 따로 잡혀 섞이지 않는 모습을, 자기 자신을 부르는 재귀 함수로 본다.

```c
int fac(int n) {
    int result;          // 지역 변수: 호출마다 새 프레임에 새로 생김
    if (n <= 1)
        result = 1;
    else
        result = n * fac(n - 1);   // 자기 자신을 다시 호출
    return result;
}
// fac(3) 호출
```

`fac(3)`은 `fac(2)`를, `fac(2)`는 `fac(1)`을 부른다. 세 호출이 동시에 살아 있는 순간(가장 깊이 들어갔을 때) 스택에는 세 개의 프레임이 쌓이고, 각 프레임은 자기만의 `n`과 `result`를 가진다. \
이름은 똑같이 `n`, `result`지만 서로 다른 주소의 자리다.

스택 모습 (낮은 주소가 아래, 가장 늦게 생긴 프레임이 맨 아래):

```
높은 주소
┌─────────────────────────┐
│ fac(3)의 프레임          │  n = 3,  result = (아직 계산 중)
├─────────────────────────┤
│ fac(2)의 프레임          │  n = 2,  result = (아직 계산 중)
├─────────────────────────┤
│ fac(1)의 프레임          │  n = 1,  result = 1   ← 먼저 끝남
└─────────────────────────┘
낮은 주소  (스택은 아래로 자란다)
```

반환은 안쪽부터 일어난다. `fac(1)`이 `result=1`을 돌려주고 그 프레임이 사라지면, `fac(2)`는 자기 프레임에 있던 `n=2`를 그대로 써서 `result = 2 * 1 = 2`를 만든다. 이어 `fac(3)`은 자기 `n=3`으로 `result = 3 * 2 = 6`을 만든다.

| 호출     | 그 프레임의 n | 그 프레임의 result | 반환값 |
| ------ | -------- | ------------- | --- |
| fac(1) | 1        | 1             | 1   |
| fac(2) | 2        | 2             | 2   |
| fac(3) | 3        | 6             | 6   |

각 호출의 `n`이 자기 프레임에 따로 보관되었기 때문에, 안쪽 호출이 끝나고 돌아와도 바깥 호출의 `n` 값이 망가지지 않는다. \
만약 지역 변수가 호출마다 새로 잡히지 않고 하나만 공유됐다면 재귀는 값이 뒤엉켜 동작하지 않았을 것이다. 최종 결과는 `fac(3) = 6`.



> 💡 **TMI**
>
> * **"Smashing the Stack"**: 지역 변수 배열에 입력을 넘치게 써서 바로 옆의 반환 주소를 덮어쓰는 공격이 '스택 스매싱(버퍼 오버플로)'이다. 이를 대중화한 글이 1996년 11월 Phrack 매거진에 실린 Aleph One(엘리아스 레비)의 "Smashing the Stack for Fun and Profit"으로, 보안 역사상 가장 영향력 있는 문서로 꼽힌다.
> * **스택에 없는 지역 변수도 있다**: 모든 지역 변수가 메모리(스택)에 자리 잡는 것은 아니다. 자주 쓰이는 지역 변수는 컴파일러가 아예 레지스터에 상주시켜 스택에 한 번도 쓰지 않을 수 있어, "지역 변수는 스택에 있다"는 설명은 최적화 전의 단순화된 그림에 가깝다.

### 7. 레지스터의 저장과 복원

#### 1) 개념 정의

호출을 가로질러(across a call) 깨지면 안 되는 레지스터 값을 함수 진입부에서 스택에 저장(save)해 두었다가 종료부에서 원래 값으로 복원(restore)하는 일이다.

#### 2) 원리 설명

레지스터는 CPU 안의 빠르지만 수가 적은 공유 자원이라, 실행되는 모든 함수가 같은 레지스터들을 돌려쓴다.&#x20;

그래서 호출자가 어떤 레지스터에 값을 담아 계산하던 도중 다른 함수를 부르면, 불려간 함수도 똑같은 레지스터를 자기 계산에 쓰기 때문에 그 안에 있던 호출자의 값이 덮어써질 수 있다. \
만약 아무 조치도 하지 않으면, 호출이 끝나고 돌아온 호출자는 멀쩡하던 값이 깨져 있는 것을 보게 된다. \
이를 막으려면 누군가가 그 레지스터 값을 호출 전에 안전한 곳(스택)에 옮겨 두었다가 호출이 끝난 뒤 되돌려 놓아야 한다. \
원칙적으로 호출이 끝나고 나면 레지스터들은 호출 전과 같은 값을 가지고 있어야 하며, 이 약속을 지키게 해 주는 작업이 바로 레지스터의 저장과 복원이다. \
저장 장소로 스택을 쓰는 이유는, 호출이 중첩되어도 각 호출이 자기 프레임의 칸에 값을 쌓아 두면 서로 섞이지 않기 때문이다.

#### 3) 세부 메커니즘

이 저장·복원은 함수의 진입부(프롤로그)와 종료부(에필로그)에서 짝을 이루어 일어난다. \
프롤로그에서는 이 함수가 앞으로 망가뜨릴 레지스터들의 현재 값을 스택 프레임의 '임시 저장된 레지스터' 칸에 차례로 push 한다. \
그리고 에필로그에서는 정확히 그 역순으로 pop 하여 각 레지스터를 원래 값으로 되돌린 뒤 호출자에게 제어를 돌려준다. \
push 한 순서와 pop 하는 순서가 반대여야 마지막에 넣은 값이 먼저 나와 제 짝을 찾는다. \
이전 BP(베이스 포인터)를 보존하는 일도 이 저장·복원의 한 예다. \
함수는 진입하면서 호출자의 BP를 프레임의 '이전 BP 저장값' 칸에 push 해 두고, 떠나면서 그 값을 다시 pop 한다. \
BP는 자기 프레임의 기준점을 가리키는 레지스터인데 모든 함수가 같은 BP를 쓰므로, 이 칸에 호출자의 BP를 백업해 두지 않으면 호출이 끝나고 돌아온 호출자가 자신의 프레임 기준점을 잃어버리기 때문이다. \
한편 누가 이 저장을 책임지느냐는 한 가지로 정해져 있지 않다. \
값을 가진 호출자가 호출 전에 직접 저장할 수도 있고, 불려간 함수가 "이 레지스터를 쓰겠으니 내가 보존하겠다"며 진입부에서 저장할 수도 있다(구체적 분류 규약은 책 범위 밖).

#### 4) 예시

호출자가 범용 레지스터 R에 값 V를 담아 두고 함수 `g()`를 부른다. \
`g()`도 R을 자기 계산에 써야 하므로, R을 저장→사용→복원하는 절차를 거친다. \
스택은 낮은 주소 방향으로 자라고, 저장된 R은 `g()` 프레임의 '임시 저장된 레지스터' 칸(가장 낮은 주소 쪽, 가장 나중에 push)에 들어간다.

| 단계           | 일어나는 일                     | R의 값  | 스택(임시 저장 칸) |
| ------------ | -------------------------- | ----- | ----------- |
| ① 호출 직전      | 호출자가 R에 V를 둠               | V     | 비어 있음       |
| ② `g()` 프롤로그 | R을 스택에 push (save)         | V     | \[ V ]      |
| ③ `g()` 본문   | `g()`가 R을 자기 값 W로 덮어씀      | W     | \[ V ]      |
| ④ `g()` 에필로그 | 스택에서 pop 하여 R 복원 (restore) | V     | 비어 있음       |
| ⑤ 호출자로 복귀    | 호출자가 R을 다시 읽음              | **V** | 비어 있음       |

결과적으로 호출자는 호출 중간에 `g()`가 R을 마음껏 썼다는 사실을 전혀 모른 채, 호출 전에 두었던 값 V를 그대로 본다. 의사 코드로 보면 다음과 같다.

```
; 호출자 쪽
R ← V              ; R에 값 V를 둠
call g             ; 함수 호출
use R              ; 여기서 R은 다시 V여야 함

; g()의 모습
g:
    push R         ; (프롤로그) R의 현재 값 V를 스택에 저장
    ...
    R ← W          ; g가 R을 자기 계산에 사용 (V가 덮어써짐)
    ...
    pop R          ; (에필로그) 저장해 둔 V를 R에 복원
    return         ; 호출자에게 복귀 → 호출자는 R == V 를 봄
```

위 예는 불려간 `g()`가 R을 저장·복원하는 경우다. 반대로, R을 호출자가 직접 저장하기로 하면 `call g` 앞뒤에서 호출자가 R을 push·pop 하고 `g()`는 R을 자유롭게 쓴다. \
어느 쪽이든 "호출이 끝나면 R은 V"라는 결과는 같으며, 단지 저장하는 주체만 다르다.



「매개변수 전달과 반환값의 구현」과 「함수 점프와 반환의 구현」이 인자·반환 주소를 레지스터/스택에 **옮기는** 일을 다룬다면, 이 소주제는 그런 이동과 무관하게 호출을 가로질러 레지스터 **값이 깨지지 않게 지키는** 일을 다룬다. 또 저장 장소로 쓰는 '임시 저장된 레지스터'·'이전 BP' 칸은 「스택 프레임과 스택 영역」 소주제에서 정리하는 프레임 구조의 일부다.

> 💡 **TMI**
>
> * **caller-saved vs callee-saved**: 호출 규약은 레지스터를 두 부류로 나눈다 — 호출 후 값이 보존되지 않을 수 있어 호출자가 알아서 백업해야 하는 caller-saved(volatile), 함수가 쓰려면 직접 저장·복원해 줘야 하는 callee-saved(non-volatile). 이 약속 덕분에 두 함수가 같은 레지스터를 두고 충돌하지 않는다.

### 8. 큰 그림: 우리는 지금 어디에 있을까

> (이 절은 책의 정리 소주제다. 앞 7개 소주제를 시간 순서로 꿰어 한 번의 함수 호출 전체를 따라가고, 3장 '메모리' 안에서 스택 영역이 어디에 있는지 위치를 짚는다.)

#### 1) 개념 정의

지금까지 따로따로 본 일곱 조각 — 함수라는 추상화, 호출을 추적하는 스택, 프레임의 구조, 점프와 반환, 인자·반환값, 지역 변수, 레지스터 저장/복원 — 은 사실 **한 번의 함수 호출이 시작되어 끝나기까지 일어나는 한 편의 연속 동작**이며, 그 무대가 바로 메모리의 스택 영역이다.

#### 2) 원리 설명

앞 소주제들은 각자 "한 가지 일"만 떼어 설명했지만, 실제로는 함수가 한 번 불릴 때 이들이 정해진 순서로 맞물려 돌아간다.&#x20;

1. 호출하는 쪽은 인자를 약속된 자리에 놓고(매개변수 전달) 반환 주소를 남기며 함수로 점프하고(점프와 반환),&#x20;
2. 불려간 함수는 자기 프레임을 펼쳐 이전 BP와 레지스터를 백업하고 지역 변수 자리를 잡은 뒤(프레임 구조·레지스터 저장·지역 변수) 일을 하고,&#x20;
3. 끝나면 결과를 반환값 자리에 두고(반환값) 백업을 되돌린 다음 반환 주소로 점프해 호출한 자리로 정확히 복귀한다.&#x20;

이 모든 과정이 스택의 push/pop이라는 한 가지 질서(스택) 위에서 이뤄지므로, 호출이 아무리 깊이 중첩되어도 각 호출은 자기 프레임 안에서만 살다가 깔끔히 사라진다. \
결국 "함수를 마음 놓고 호출만 하면 된다"(함수: 도우미)는 편리함은, 그 아래에서 스택이 묵묵히 떠받치고 있기에 성립한다.

#### 3) 세부 메커니즘

`c = add(2, 3)` 한 줄이 실행되는 동안 일어나는 일을 시간 순서로 늘어놓으면 다음과 같다(괄호 안은 그 단계를 담당한 소주제).

```
[호출 직전]  main 이 실행 중, main 의 프레임만 스택에 있음
   ↓
1. main 이 인자 2, 3 을 약속된 자리에 놓음              (매개변수 전달)
2. call 실행: 반환 주소를 스택에 push, PC 를 add 로 점프  (점프와 반환 / 스택 push)
   ↓  ── 여기서 add 의 프레임이 새로 생기기 시작 ──
3. add 프롤로그: 이전 BP 저장, 새 BP 설정,
   망가뜨릴 레지스터 백업, 지역 변수 자리 확보           (레지스터 저장 / 프레임 구조 / 지역 변수)
4. add 본문: 인자 2,3 을 읽어 5 계산, 결과를 반환값 자리에 둠 (지역 변수 / 반환값)
5. add 에필로그: 백업한 레지스터·이전 BP 복원, 지역 변수 자리 회수 (레지스터 복원)
6. return 실행: 반환 주소를 pop 해 PC 에 싣고 점프         (점프와 반환 / 스택 pop)
   ↓  ── add 의 프레임이 통째로 사라짐 ──
7. main 이 반환값 자리에서 5 를 꺼내 c 에 저장            (반환값)
[호출 직후]  스택은 호출 직전과 똑같은 모습으로 돌아옴
```

핵심은 **2\~3에서 부풀었던 스택이 5\~6에서 정확히 같은 만큼 줄어들어**, 호출이 끝나면 스택이 호출 전 상태로 완벽히 복원된다는 점이다. \
이 "쌓고 → 쓰고 → 정확히 되돌린다"의 대칭이 깨지지 않기 때문에 재귀든 깊은 중첩이든 안전하게 동작한다.

#### 4) 예시

같은 호출을 스택의 부피 변화로만 그리면 다음과 같다.

```
스택 크기
  │            ┌────────┐
  │            │ add 의 │   ← 3~4단계: add 프레임이 올라가 있는 동안
  │            │ 프레임 │
  │  ┌─────────┘        └─────────┐
  │  │      main 의 프레임         │   ← 호출 전·후 동일
  └──┴────────────────────────────┴──→ 시간
     호출 전   call   ...   return   호출 후
```

호출 전과 호출 후의 `main` 프레임 높이가 똑같다는 것이 곧 "함수 호출은 흔적을 남기지 않고 끝난다"는 뜻이다. (만약 어딘가에서 push 와 pop 의 짝이 맞지 않으면 이 그림이 호출 후 제자리로 돌아오지 못하고, 그게 바로 호출 규약이 어긋났을 때 프로그램이 무너지는 이유다 — 자세한 규약 이름은 책 범위 밖.)



> 💡 **TMI** (책 범위 밖 보강)
>
> * **이 모든 약속의 이름, ABI**: 지금까지 본 콜 스택·인자 전달·레지스터 저장 규칙을 하나로 묶어 문서화한 것이 바로 ABI(Application Binary Interface)다. 서로 다른 컴파일러로 따로 빌드한 코드가 문제없이 링크되어 호출되는 것은, 모두가 같은 ABI라는 '계약'을 지키기 때문이다.

# 6.1 I/O in CPU

### 1. 전문적으로 처리하기: 입출력 기계 명령어

출발점 — CPU가 장치에 말을 거는 첫 번째 방법, "장치 레지스터"의 정의.

#### 1) 개념 정의

CPU가 메모리 주소 공간과는 **완전히 별개인 전용 입출력 주소 공간(입출력 포트 공간)** 을 따로 두고, 오직 그 공간만 다루는 **전용 기계 명령어**(x86의 `IN`/`OUT`)로 장치와 데이터를 주고받는 방식.

#### 2) 원리 설명

CPU가 장치를 다루려면 장치 쪽에 "말을 걸 수 있는 주소"가 있어야 하는데, 장치는 자기 내부 회로를 통째로 열어 주는 대신 **장치 레지스터**라는 작은 창구 몇 개만 CPU 쪽으로 내놓는다.

> 📎 **장치 레지스터(device register)** — 장치가 CPU에게 노출하는, 보통 **1\~4바이트짜리** 작은 레지스터. CPU가 장치와 주고받는 모든 대화는 이 창구를 통해서만 이루어진다. 역할에 따라 나뉜다.
>
> * **데이터 레지스터**: 장치가 준 입력을 CPU가 읽어 가고, CPU가 보낼 출력을 써 넣는 곳 (읽기 전용/쓰기 전용이 따로 있기도 함)
> * **상태 레지스터**: 장치가 지금 놀고 있는지, 바쁜지, 입력 준비가 됐는지, 오류가 났는지를 비트로 나타내는 곳 — CPU는 여기서 읽기만 함
> * **제어 레지스터**: CPU가 장치에게 명령을 내리거나 설정(패리티 검사 여부, 워드 길이 등)을 바꾸려고 비트를 써 넣는 곳

문제는 이 창구들에 붙일 주소를 어디서 가져오느냐인데, 이 방식의 답은 "메모리 주소는 손대지 않고, 입출력만을 위한 주소 공간을 하나 더 만든다"이다. \
x86에서 이 공간은 2^16 = **64K(65,536)개의 8비트 포트**로 이루어지고, 각 포트에는 0번부터 65535번(0x0000\~0xFFFF)까지 번호가 붙는다.&#x20;

그런데 주소 공간이 둘이 되었으니 명령어도 둘이어야 한다 — 메모리를 읽고 쓰는 평범한 명령어와는 **별개로**, 오직 포트만 읽고 쓰는 전용 명령어 `IN`(포트 → CPU 레지스터)과 `OUT`(CPU 레지스터 → 포트)이 존재한다.&#x20;

"전용으로 처리한다"는 말은 **주소 공간도 전용, 명령어도 전용** 을 가리킨다.

#### 3) 세부 메커니즘

**(1) 데이터 폭은 포트가 아니라 "어떤 레지스터를 적었는가"가 정한다**

`IN`/`OUT`은 바이트(8비트)·워드(16비트)·더블워드(32비트)를 옮길 수 있는데, 어느 폭인지는 포트 주소가 아니라 **명령어에 어떤 레지스터를 적었느냐**로 결정된다.

| 명령어에 적은 레지스터 | 실제로 오가는 폭   |
| ------------ | ----------- |
| `AL`         | 8비트 (1바이트)  |
| `AX`         | 16비트 (2바이트) |
| `EAX`        | 32비트 (4바이트) |

포트 공간 자체는 8비트 포트 64K개지만, **연속한 두 포트를 16비트 포트 하나로**, **연속한 네 포트를 32비트 포트 하나로** 취급한다.&#x20;

그래서 최대 개수는 8비트 포트 64K개, 16비트 포트 32K개, 32비트 포트 16K개가 된다.

**(2) 포트 번호를 적는 방법이 두 가지다**

* **즉시값(immediate)으로 직접**: 포트 번호 1바이트를 명령어 안에 그대로 박아 넣는다. 짧고 빠르지만 **0\~255번 포트만** 가리킬 수 있다.
* **DX 레지스터로 간접**: 포트 번호를 먼저 `DX`에 넣고 명령어는 `DX`를 가리킨다. 이 방법으로는 **0\~65535번 전체**를 가리킬 수 있다.

즉 흔히 쓰는 낮은 번호 포트를 위한 지름길과, 모든 포트를 커버하는 일반 경로를 둘 다 준 셈이다.

**(3) 주소선은 공유하고, 제어선이 "지금은 메모리가 아니라 입출력"이라고 알린다**

주소 공간이 둘이라고 해서 배선이 두 벌인 것은 아니다. \
**주소선과 데이터선은 메모리와 같이 쓰되**, 대신 **제어선 쪽에 "메모리 접근"용과 "입출력 접근"용을 구분하는 별도의 신호선**을 둔다. CPU가 `OUT`을 실행하면 주소선에 포트 번호를 싣고 "입출력 쓰기" 제어선을 켜고, `MOV`로 메모리에 쓸 때는 "메모리 쓰기" 쪽을 켠다.&#x20;

그래서 **메모리 0x20번지와 0x20번 포트가 같은 숫자를 갖고도 전혀 다른 대상**일 수 있다.&#x20;

뒤집어 말하면, 이 구분 신호를 켜 줄 누군가가 필요했기 때문에 애초에 전용 명령어가 있어야 했다. \
기계어 수준에서 `MOV`와 `OUT`이 갈라져 있어야 CPU가 어느 제어선을 켤지 알 수 있다.

#### 4) 예시

**시리얼 포트로 바이트 하나 내보내기**

PC에서 첫 번째 시리얼 포트(COM1)에는 포트 번호 **0x3F8**이 배정되어 있다. 여기로 문자 `'A'`(0x41) 한 바이트를 내보내 보자.

```asm
MOV DX, 0x3F8   ; 포트 번호 0x3F8을 DX에 넣는다
                ; (255보다 크므로 즉시값으로는 못 적는다 → DX 간접 방식)
MOV AL, 0x41    ; 보낼 데이터 1바이트. 0x41 = 문자 'A'
OUT DX, AL      ; AL의 1바이트를 0x3F8번 포트로 내보낸다
```

`OUT` 한 줄이 실행되는 순간 하드웨어에서 벌어지는 일:

1. CPU가 주소선에 `0x3F8`을, 데이터선에 `0x41`을 싣는다.
2. 동시에 **"입출력 쓰기" 제어선**을 켠다. → 메모리 0x3F8번지는 아무 반응도 하지 않는다. 제어선이 "이건 메모리가 아니다"라고 말하고 있기 때문이다.
3. 0x3F8번 포트로 배선된 시리얼 장치만 이 버스 사이클을 자기 것으로 알아듣고, 자기 **데이터 레지스터**에 0x41을 받는다.
4. **결과**: 시리얼 선을 타고 문자 `'A'`가 밖으로 나간다. (장치가 이미 초기화되어 있다는 전제)

반대 방향은 `IN`이다. `IN AL, DX`는 같은 포트에서 1바이트를 읽어 `AL`에 담는다.

여기서 이 방식의 성격이 하나 드러난다. \
**포트 안의 비트 하나만 검사하고 싶어도 곧바로 검사할 수 없다.** \
반드시 `IN`으로 CPU 레지스터에 읽어 들인 뒤 그 레지스터에서 검사해야 한다. 포트를 건드릴 수 있는 명령어가 `IN`/`OUT` 둘뿐이기 때문이다.



* 장치 레지스터에 주소를 붙이는 방법은 이것만이 아니어서, 전용 주소 공간 대신 **메모리 사상 입출력**을 쓰는 방식이 다음 소주제에 나온다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * `IN`/`OUT`은 흔히 특권 명령이라고 하지만 정확히는 조건부다. 프로세서는 먼저 현재 특권 수준이 EFLAGS의 IOPL 이하인지 보고, 아니면 TSS 안의 입출력 허가 비트맵에서 그 포트 비트가 0인지 다시 본다. 입출력 주소 공간이 통째로 64KB(포트 0\~65535)뿐이라 그 비트맵도 최대 8192바이트면 전부 표현되고, 덕분에 일반 사용자 프로그램에게 "이 포트 하나만" 열어 주는 일이 가능하다.
> * 리눅스 `ioperm()`은 커널 2.6.8 이전까지 앞쪽 0x3ff번 포트까지만 지정할 수 있었고, 그 위 포트가 필요하면 `iopl(3)`으로 전체 권한을 통째로 받는 수밖에 없었다. 2.6.8부터 65536개 포트를 모두 지정할 수 있게 바뀌었다.
> * 별도의 입출력 명령어를 가진 아키텍처는 오늘날 소수파다. ARM과 RISC-V에는 `IN`/`OUT`에 해당하는 명령어가 아예 없어 모든 장치가 메모리 사상으로만 접근되고, x86조차 PCIe 설정 공간과 BAR 영역은 메모리 사상 쪽으로 옮겨 갔다.

### 2. 메모리 사상 입출력

전용 명령어를 새로 만드는 대신, 이미 있는 메모리 주소를 빌려 쓴다.

#### 1) 개념 정의

**메모리 사상 입출력(memory-mapped I/O, MMIO)** 은 장치 레지스터를 메모리 주소 공간 안의 특정 주소에 올려놓아서, CPU가 전용 입출력 명령어 없이 평범한 메모리 읽기/쓰기 명령어(load/store, mov)만으로 장치를 다루게 하는 방식이다.

#### 2) 원리 설명

CPU가 메모리에 접근할 때 실제로 하는 일은 "주소 버스에 주소를 싣고 데이터 버스로 값을 주고받는 것"뿐이다. \
그 주소 끝에 진짜 RAM 칩이 붙어 있는지, 그래픽 카드나 디스크 컨트롤러가 붙어 있는지는 CPU가 알지도 못하고 신경 쓰지도 않는다.&#x20;

이 점을 이용해 주소 공간의 일부 구간을 RAM 대신 장치의 레지스터에 배정해 두면, 하나의 메모리 주소가 물리 RAM의 일부를 가리킬 수도, 장치의 레지스터를 가리킬 수도 있게 된다.&#x20;

그 결과 장치를 위한 별도의 명령어가 필요 없어진다\
메모리에 접근할 수 있는 모든 명령어를 그대로 써서 장치를 조작할 수 있고, 프로그래머 입장에서는 장치 레지스터를 읽고 쓰는 코드가 그냥 변수에 대입하는 코드처럼 보인다.&#x20;

대신 그렇게 떼어 준 주소 구간은 더 이상 RAM 용도로 쓸 수 없다.

#### 3) 세부 메커니즘

**(1) RAM으로 갈지 장치로 갈지는 CPU가 아니라 주소를 보는 회로가 정한다.** \
CPU가 주소 버스에 주소를 실으면, 버스에 매달린 각 장치는 주소 버스를 감시하다가 자기에게 배정된 주소로의 접근이면 응답해서 시스템 버스를 자기 하드웨어 레지스터에 연결한다. \
이것이 주소 디코딩이다.&#x20;

그래서 `0xB8000` 같은 주소에 값을 쓰면 그 쓰기는 RAM으로 가지 않고 그래픽 하드웨어로 곧장 간다. \
CPU가 실행한 명령어는 똑같은 store 하나인데, 도착지가 갈라지는 지점은 CPU 바깥의 디코딩 회로인 것이다.

**(2) 그 회로는 공짜가 아니다.** \
장치마다 자기 주소인지 아닌지를 판별하려면 주소 버스 전체를 봐야 한다. \
32비트 주소 버스를 쓰는 기계라면 32개의 주소선 상태를 모두 판정하는 논리 게이트가 필요하고, 그만큼 하드웨어를 붙이는 비용이 올라간다.

**(3) 대가 ① — 주소 공간을 떼어 준다.** \
장치를 수용하려면 CPU가 쓰는 주소 공간 중 일부를 입출력용으로 예약해야 하고, 그 영역은 일반 물리 메모리로 쓸 수 없다. \
즉 RAM을 아무리 많이 꽂아도 그 구간에 해당하는 만큼은 메모리로 보이지 않는다.

**(4) 대가 ② — 이 주소는 캐시하면 안 된다.** \
보통의 메모리 주소는 값이 CPU가 쓴 그대로 유지되지만, 장치 레지스터는 CPU 몰래 하드웨어가 값을 바꿔 놓는다. \
캐시에 들어 있던 옛 값을 읽으면 틀린 값을 읽는 것이고, 반대로 쓴 값이 캐시에만 머물면 장치에는 영영 도달하지 않는다. \
그래서 이 구간은 "캐시하지 않는 영역"으로 표시해 둔다. 컴파일러 쪽에도 같은 종류의 주의가 필요한데, 컴파일러는 우리가 RAM이 아니라 장치에 접근한다는 사실도, 화면에 글자가 뜬다는 부수 효과도 모르기 때문에 그 쓰기가 불필요하다고 판단해 지워 버릴 수 있다.

**(5) 트레이드오프 — 메모리 사상 입출력 vs 입출력 기계 명령어 방식**

|       | 메모리 사상 입출력                           | 입출력 기계 명령어 방식                        |
| ----- | ------------------------------------ | ------------------------------------ |
| 주소 공간 | 메모리와 같은 주소 공간을 나눠 쓴다 → 그만큼 RAM에 못 쓴다 | 입출력 전용 주소 공간을 따로 둔다 → 메모리 공간을 깎지 않는다 |
| 명령어   | 메모리용 명령어·주소 지정 방식·포인터를 그대로 재사용       | 그 전용 공간에 닿는 별도의 명령어가 필요              |
| 하드웨어  | 장치마다 주소 버스 전체를 디코딩해야 함               | 상대적으로 디코딩 부담이 작음                     |

한쪽이 항상 옳은 것은 아니다.두 입출력 사상 방식 중 어느 하나가 보편적으로 우월하지는 않다.

#### 4) 예시

PC의 텍스트 화면은 `0xB8000` 번지부터 시작하는 구간에 사상되어 있다. 이 주소에 대한 읽기와 쓰기는 RAM에 가지 않고 VGA 하드웨어의 텍스트 버퍼로 직접 간다. \
화면은 25행 × 80열이고, 한 칸이 2바이트다 — 아래 바이트는 문자 코드, 위 바이트는 색상 속성(하위 4비트 글자색, 그다음 3비트 배경색, 맨 위 1비트 깜빡임)이다.

```c
/* 화면 맨 왼쪽 위 칸에 검정 배경 + 흰 글씨로 'A'를 찍는다 */
volatile unsigned short *screen = (volatile unsigned short *)0xB8000;

screen[0] = 'A' | (0x0F << 8);   /* 0x0F00 -> 글자색 흰색, 배경 검정, 깜빡임 없음 */
```

작동 결과: 운영체제 없이 직접 실행되는 코드(부팅 직후의 커널 등)에서, **`0xB8000`이라는 숫자가 곧바로 그 물리 주소를 가리키는 상태**로 이 한 줄을 실행하면, 출력 함수를 부르지도 않았는데 화면 왼쪽 맨 위에 흰색 `A`가 나타난다. 겉보기에는 그냥 배열 원소에 값을 대입한 평범한 문장이지만, 그 주소가 RAM이 아니라 그래픽 장치에 배정되어 있기 때문에 대입이 곧 출력이 된다. `screen[1] = 'B' | (0x0F << 8);` 로 바꾸면 그 오른쪽 칸에 `B`가 찍힌다. 참고로 `volatile`을 빼면 컴파일러가 "이 값을 다시 읽는 곳이 없다"고 판단해 대입문 자체를 없애 버릴 수 있고, 그러면 화면에는 아무것도 나타나지 않는다.



이 방식은 앞 소주제의 입출력 기계 명령어 방식과 나란히 놓이는 또 하나의 선택지이며, 실제 기계는 두 방식을 함께 갖추고 있는 경우가 많다. \
여기서 마련된 "주소 하나로 장치 레지스터에 닿는 통로"는 이후 소주제들에서 CPU가 장치의 상태를 확인하거나 데이터를 주고받을 때 쓰이는 기본 수단이 된다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * 2000년대에 "램 4GB를 꽂았는데 3GB 남짓만 보인다"며 사람들이 당황했던 사건의 범인이 바로 이것이다. 펌웨어가 4GB 경계 아래에서부터 아래쪽으로 장치의 MMIO 영역을 깔고, 겹치는 만큼의 실제 램을 주소 공간에서 감춰 버리기 때문이다. 램이 모자란 게 아니라 주소가 모자랐던 것이다.
> * 포인터에 `volatile`만 붙이면 될 것 같지만 부족하다. `volatile`은 컴파일러의 재배치만 막을 뿐, CPU가 접근 순서를 바꾸거나 여러 접근을 하나로 합쳐 버리는 것은 막지 못한다. 그래서 리눅스 커널 문서는 MMIO를 반드시 `readl()`/`writel()` 같은 전용 접근자로 하라고 못 박는다.
> * MMIO의 가장 유명한 실물이 본문에 쓴 VGA 텍스트 화면이다. 운영체제를 직접 만들어 보는 사람들의 "첫 화면 출력" 코드가 예외 없이 이 주소에 포인터로 값을 대입하는 것인 이유이기도 하다 — 출력 함수도, 드라이버도, 심지어 운영체제도 없이 글자를 띄울 수 있는 가장 짧은 길이기 때문이다.

### 3. CPU가 키보드를 읽고 쓰는 것의 본질

#### 1) 개념 정의

"CPU가 키보드를 읽고 쓴다"는 말의 실체는, 키보드 컨트롤러가 내어 놓은 **장치 레지스터**에서 **한 번에 1바이트짜리 숫자를 꺼내 오고(읽기)**, 같은 자리에 **1바이트짜리 숫자를 밀어 넣는 것(쓰기)** — 딱 그것뿐이다.

#### 2) 원리 설명

키를 누르는 순간 먼저 움직이는 쪽은 CPU가 아니다. \
키보드가 눌린 키의 **위치**를 알아내 그에 대응하는 숫자, 곧 **스캔 코드**를 만들어 키보드 컨트롤러로 보내면, 컨트롤러는 그 값을 **데이터 레지스터(출력 버퍼)** 에 놓고 **상태 레지스터**의 "읽을 것이 도착했다" 비트를 1로 세운다.&#x20;

이때 CPU가 하는 일은 그 데이터 레지스터를 한 번 읽어 값 하나를 자기 레지스터로 가져오는 것이 전부이며, 앞의 두 접근 방식 중 어느 쪽으로 손을 뻗든 CPU가 손에 쥐는 결과물은 똑같이 "바이트 하나"다.&#x20;

그래서 CPU는 '키보드'라는 개념 자체를 모른다 — 문자도, 자판 배열도 모르고, 그저 숫자 하나를 받을 뿐이다. 그 숫자에 '문자'라는 의미를 붙이는 일은 훨씬 위 계층의 몫이다 — 스캔 코드는 문자가 아니고, 소프트웨어가 별도의 변환표로 아스키 코드 같은 문자 코드로 옮겨 주어야 비로소 글자가 된다.&#x20;

**쓰기도 정확히 대칭이다**\
CPU가 키보드에 명령을 내리는 것(예: Caps Lock 램프를 켜라)도 특별한 '명령 전송 회로'가 아니라 같은 데이터 레지스터에 바이트 하나를 써 넣는 행위다.

#### 3) 세부 메커니즘

* **같은 주소라도 읽기냐 쓰기냐에 따라 닿는 레지스터가 다르다.** \
  키보드 컨트롤러가 노출하는 주소는 `0x60`과 `0x64` 둘뿐인데, 그 뒤에 놓인 레지스터는 셋이다 — 출력 버퍼, 입력 버퍼, 상태 레지스터. `0x60`을 **읽으면** 출력 버퍼(키보드 → CPU)에 닿고, `0x64`를 **읽으면** 상태 레지스터에 닿는다. \
  반면 **쓰기는** `0x60`이든 `0x64`든 모두 같은 입력 버퍼(CPU → 키보드 쪽)에 닿되, 어느 주소를 썼느냐가 그 바이트를 어떻게 해석할지를 정한다. \
  `0x60`에 쓴 바이트는 키보드 자체를 향한 데이터·명령이고, `0x64`에 쓴 바이트는 **키보드 컨트롤러**를 향한 명령으로 읽힌다. \
  읽기와 쓰기가 같은 문패를 공유하되 서로 반대 방향의 통로인 셈이다.
* **두 비트가 뜻하는 것은 같지만, CPU가 기다려야 하는 값은 서로 반대다.** \
  비트0(출력 버퍼)도 비트1(입력 버퍼)도 `1`은 똑같이 "그 버퍼가 차 있다"는 뜻이다. \
  그런데 CPU가 원하는 상황이 읽기와 쓰기에서 정반대라서 기다리는 값도 뒤집힌다 — 읽으려면 출력 버퍼에 값이 들어와 있어야 하니 **비트0이 1이 되기를** 기다리고, 쓰려면 입력 버퍼가 비어 있어야 하니 **비트1이 0이 되기를** 기다린다. \
  읽기 조건과 쓰기 조건이 각기 다른 비트로 분리되어 있다는 것이, 읽기와 쓰기가 별개의 한 동작임을 그대로 드러낸다.
* **읽기는 단순 조회가 아니라 장치 쪽 상태를 바꾸는 행위다.** \
  CPU가 출력 버퍼에서 바이트를 가져가면 비트0은 스스로 `0`으로 내려간다 — 버퍼가 다시 비었다는 뜻이다. \
  값을 "본" 것만으로 상대편 상태가 달라진다는 점이, 몇 번을 읽어도 같은 값이 나오는 일반적인 저장 공간 읽기와 갈리는 지점이다.
* **CPU가 받아 든 1바이트에 담긴 정보는 딱 두 가지다.** \
  "어느 자리의 키인가"와 "눌렸나, 떼졌나". 스캔 코드 세트 1에서는 누를 때 나오는 값(make code)에 `0x80`을 더한 값이 뗄 때 나오는 값(break code)이다. \
  문자는 이 바이트 어디에도 들어 있지 않다.
* **쓰기가 먹혔는지 확인하는 일조차 결국 "바이트 하나 읽기"로 돌아온다.** \
  키보드에 명령 바이트를 써 넣으면 키보드는 `0xFA`(ACK)라는 응답 바이트를 되돌려 주는데, CPU가 이를 확인하는 방법은 데이터 레지스터에서 바이트를 한 번 읽는 것이다. \
  명령을 보내는 것도, 그 명령이 통했는지 아는 것도, 전부 바이트 하나를 주고받는 일로 환원된다.

#### 4) 예시

**예시 1 — 읽기: A 키를 눌렀다 뗀다**

```asm
; 상태 레지스터의 비트0이 1이 되어, 읽을 값이 도착해 있는 상태라고 하자
in   al, 0x60      ; 데이터 레지스터에서 1바이트를 읽어 al에 담는다

; A 키를 눌렀을 때 -> al = 0x1E   (make code)
; A 키를 뗐을 때   -> al = 0x9E   (break code = 0x1E + 0x80)
```

CPU 입장에서 `al`에 들어온 것은 **30과 158이라는 두 숫자**일 뿐, 'A'라는 글자는 어디에도 없다. 실제로 같은 위치의 키가 QWERTY 자판에서는 `A`, AZERTY 자판에서는 `Q`로 인쇄되어 있다 — 같은 스캔 코드가 자판에 따라 다른 글자가 되는 것이니, 이 바이트는 애초에 문자일 수가 없다. `0x1E`를 'A'로 바꾸는 변환표는 CPU 바깥, 훨씬 위 계층에 있다.

**예시 2 — 쓰기: Caps Lock 램프를 켠다**

```asm
mov  al, 0xED      ; "LED 상태를 바꿔라"라는 키보드 명령 바이트
out  0x60, al      ; 데이터 레지스터에 1바이트를 써 넣는다
in   al, 0x60      ; 키보드가 돌려준 0xFA(ACK)를 읽어 확인한다

mov  al, 0x04      ; 파라미터 1바이트: 비트2=CapsLock, 비트1=NumLock, 비트0=ScrollLock
out  0x60, al      ; 0x04 = 비트2만 1 -> Caps Lock만 켜라
in   al, 0x60      ; 이 바이트에 대해서도 0xFA(ACK)가 돌아온다

; (실제 코드는 out 앞에서 상태 레지스터(0x64)의 비트1이 0인지,
;  in 앞에서 비트0이 1인지를 먼저 확인하고 기다린다. 여기서는 생략했다.)
```

작동 결과: 키보드의 **Caps Lock 램프에 실제로 불이 들어온다.** 그러나 CPU가 한 일은 `0xED`와 `0x04`라는 숫자 두 개를 정해진 자리에 밀어 넣은 것뿐이고, '램프'나 'Caps Lock'이라는 의미는 그 숫자를 받은 키보드 쪽에서 붙인다. (같은 바이트라도 `0x60`이 아니라 `0x64`에 썼다면 키보드가 아니라 키보드 컨트롤러를 향한 명령으로 해석된다.)

#### 5) 다른 키워드와의 연결

* 이 장치 레지스터에 **어떤 방법으로** 손을 뻗는가(전용 입출력 기계 명령어냐, 메모리 사상 입출력이냐)는 앞의 두 소주제가 다루고, 여기서는 그 방법이 무엇이든 CPU가 얻는 결과는 "바이트 하나"라는 데서 멈춘다.
* 상태 레지스터의 비트0이 **언제** 1이 되었는지를 CPU가 알아채는 방법(폴링, 인터럽트)은 이어지는 소주제들의 몫이다. 이 소주제가 확정한 것은 "한 번의 읽기·쓰기가 무엇인가"까지다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * Ctrl+Alt+Del을 만든 사람은 IBM PC 엔지니어 데이비드 브래들리이고, 코드를 짜는 데 5분쯤 걸렸다고 한다. 2001년 IBM PC 20주년 행사 패널에서 빌 게이츠 옆에 앉아 "제가 발명했을진 몰라도 유명하게 만든 건 빌이죠"라고 말해 객석을 뒤집었다. 본인 말로는 "그게 문화적 아이콘이 될 줄은 몰랐다".
> * 지금 쓰는 키보드가 실제로 내보내는 것은 스캔 코드 세트 2이고, 메인보드의 키보드 컨트롤러가 그것을 옛 XT 시절의 세트 1로 번역해서 CPU에게 준다. 원래 IBM PC 키보드는 세트 1을 썼는데 AT 키보드가 세트 2로 바뀌면서 호환을 위해 번역기를 끼워 넣은 것이다. 즉 본문의 `0x1E`는 키보드가 보낸 원본이 아니라 이미 한 번 번역을 거친 값이다.
> * "키 하나 = 코드 하나"가 아니다. 키 하나를 누르고 떼는 동작은 0개에서 6개 사이의 스캔 코드를 만들어 낼 수 있다. 키패드 `/`는 누를 때 `e0 35`, 뗄 때 `e0 b5`를 보내고, PrtSc는 수식 키 없이 누르면 `e0 2a e0 37` 네 바이트가 한꺼번에 나온다.

### 4. 폴링: 계속 검사하기

질문이 "무엇을 읽는가"에서 "**언제** 읽는가"로 옮겨 간다. 그 첫 번째 답 — CPU가 알 때까지 계속 물어본다.

#### 1) 개념 정의

폴링은 CPU가 장치 레지스터의 상태 비트를 자기 쪽에서 반복해 읽어, 원하는 상태(예: '준비됨')가 될 때까지 같은 검사를 되풀이하는 방식이다.

#### 2) 원리 설명

장치는 CPU보다 훨씬 느리게 움직이므로, 명령을 내린 뒤 결과가 준비되기까지 시간이 걸린다.&#x20;

이때 "준비됐는가?"를 CPU가 직접 물어보는 것 말고 알 방법이 없다면, CPU는 상태 레지스터를 읽고 → 비트를 검사하고 → 아직 아니면 다시 읽는 루프를 돈다.&#x20;

여기서 놓치기 쉬운 사실은 이 검사가 공짜가 아니라는 점이다 — 루프 한 바퀴마다 실제 기계 명령어 몇 개가 실행되고 그만큼 사이클이 소모된다. \
그래서 폴링의 총비용은 "한 바퀴 비용 × 도는 횟수"라는 단순한 곱셈으로 정해지고, 도는 횟수는 기다림이 길어질수록 그대로 늘어난다. \
그 횟수를 줄이려고 검사와 검사 사이에 간격을 두면, 이번에는 장치가 준비된 시점과 CPU가 그것을 알아채는 시점이 그 간격만큼 벌어진다.&#x20;

결국 폴링을 설계한다는 것은 **검사 비용과 응답 지연을 양팔에 올린 저울에서 어느 지점에 설 것인지를 정하는 일**이다.

#### 3) 세부 메커니즘

**(1) 루프 한 바퀴의 실체 — 명령어 3\~4개.** \
"검사 1회"는 추상적인 동작이 아니라 실제로 실행되는 명령어 몇 줄이다. 앞 소주제의 상태 레지스터를 검사하는 폴링 루프는 이렇게 생겼다.

```asm
    mov  dx, STATUS_PORT    ; 상태 레지스터의 포트 번호를 준비해 둔다
poll_loop:
    in   al, dx             ; 상태 레지스터를 읽고
    test al, READY_BIT      ; 준비 비트를 검사하고
    jz   poll_loop          ; 아직 서 있지 않으면 되돌아간다
```

되풀이되는 몸통은 `in` / `test` / `jz` **3개**다. 여기에 매 바퀴 포트 번호를 다시 적재해야 하는 구조에서는 한 바퀴가 **4개**가 된다. 어느 쪽이든 한 자릿수 명령어이고, 바로 이 작은 수가 곱셈의 앞쪽 항이 된다.

**(2) 비용은 곱셈으로 정해진다.** \
앞쪽 항이 작아도 뒤쪽 항이 크면 결과는 커진다. 한 바퀴가 4개라면 "장치 레지스터를 50번 폴링하면 명령어 200개를 실행하게 된다"(4 × 50 = 200). \
그리고 그 횟수는 프로그래머가 정하는 값이 아니라 **기다림의 길이가 정하는 값**이다 — 쉼 없이 붙여 도는 루프라면 헛돈 횟수 ≈ (기다린 시간) ÷ (한 바퀴 시간)이 된다. \
이 곱셈의 극단을 보여 주는 것이 프린터다. \
프린터가 다음 바이트를 받기까지 10초가 걸린다면, CPU는 그 10초 동안 프린터의 상태 포트를 검사하는 것 말고는 아무것도 하지 않는 루프를 돈다. \
다른 작업을 실행하는 데 쓸 수 있었던 프로세서 시간이 쓸모없는 활동에 낭비되는 것이다. \
한편 한 바퀴에서 검사하는 대상이 여럿이면 앞쪽 항 자체가 커진다 — 검사할 장치가 너무 많으면 그것들을 모두 폴링하는 데 드는 시간이 정작 장치를 서비스할 수 있는 시간을 초과할 수 있다.

**(3) 간격 T — 이 비용을 조절하는 유일한 손잡이.** \
검사를 빈틈없이 붙여 돌리는 대신 검사와 검사 사이에 간격 T를 두면(실제로는 `delay()`·`sleep()` 같은 지연 함수로 만든다), 단위 시간당 검사 횟수가 1/T에 비례해 줄어들고 검사 비용도 정확히 그만큼 줄어든다. \
이 손잡이의 양 끝은 한 문장에 담긴다 — 폴링은 "프로세서 대역폭을 사실상 전부 차지하는 고속의 타이트한 루프로 할 수도 있고, 일정한 간격을 두고 덜 자주 할 수도 있다". \
문제는 **같은 손잡이가 반대쪽 팔도 함께 움직인다**는 것이다. 검사를 뜸하게 하면 이벤트는 다음 검사 주기에야 보이므로, 장치가 준비된 순간과 그것이 관측되는 순간 사이에 지연이 생긴다. \
폴링에서 **최악 지연은 T로 묶이고**, 평균 지연은 대략 T/2다. 즉 T 하나를 정하면 검사 비용(∝ 1/T)과 응답 지연(∝ T)이 동시에, 서로 반대 방향으로 결정된다. 폴링 설계에서 고를 것은 사실상 이 값 하나뿐이다.

**(4) T의 위아래 끝을 정하는 것.** \
아래쪽 끝은 검사 비용이 정한다 — T를 0에 가깝게 몰면 루프가 프로세서 대역폭을 전부 먹고, 게다가 CPU가 계속 깨어 있어야 하므로 아무 일이 없어도 사이클을 소모하고 불필요한 전력 소비로 이어진다. 위쪽 끝은 **요구되는 응답 속도**가 정한다 — 최적의 폴링 주기는 여러 요인, 그중에서도 원하는 응답 속도에 따라 달라진다. 같은 이야기를 두 장치로 대비하면 이렇다: 데이터가 쉴 새 없이 도착하는 장치라면 마이크로초 단위로 검사해야 놓치지 않지만, 상태가 어쩌다 한 번 바뀌는 장치라면 1초에 한 번 확인해도 충분하다. 요컨대 T의 허용 범위는 장치와 용도가 먼저 정해 주고, 그 범위 안에서 어디에 설지를 고르는 것이 설계자의 몫이다.

**(5) 이 저울로 조절되지 않는 두 가지.** 첫째는 **방향**이다. \
폴링에서 묻는 쪽은 언제나 CPU 한쪽뿐이고, 장치는 상태 레지스터에 표시만 해 둘 뿐 스스로 먼저 알리지 않는다. "언제 아느냐"가 전적으로 CPU의 검사 일정에 달려 있다는 이 성질 때문에 T가 곧 지연이 되는 것이다. 둘째는 **순서**다. 상태를 확인하고 나서 데이터에 접근해야지, 그 반대는 성립하지 않는다. 표준 핸드셰이크가 "바쁨 비트가 내려갈 때까지 반복해서 읽고 → 내려가면 명령 레지스터에 명령을 쓴다"는 순서로 정의되어 있는 이유다. 읽기 쪽도 마찬가지로 준비 비트가 선 것을 본 다음에야 데이터 레지스터를 읽어야 한다. 이 순서는 T를 크게 잡든 작게 잡든 건너뛸 수 없는 **정확성 조건**이지 저울에 올릴 항목이 아니다.

#### 4) 예시

**예시 1 — 폴링은 명령 하나에 두 번 등장한다.**

CPU와 장치가 주고받는 표준 상호작용 프로토콜은 이렇게 생겼다.

```
While (STATUS == BUSY)
    ;                            // 장치가 바쁘지 않을 때까지 대기   <- 폴링 (1)
Write data to DATA register
Write command to COMMAND register
                                 // 장치가 시작되어 명령을 실행한다
While (STATUS == BUSY)
    ;                            // 요청이 끝날 때까지 대기          <- 폴링 (2)
```

똑같은 검사 루프가 **명령을 쓰기 전에 한 번, 쓴 뒤에 한 번** 나온다. 앞의 것은 "지금 명령을 넣어도 되는가"를, 뒤의 것은 "결과가 나왔는가"를 확인한다. 따라서 앞 절에서 센 곱셈은 한 번의 입출력마다 두 벌 발생한다.

읽는 쪽만 떼어 C 스타일로 적으면 (5)에서 말한 순서가 그대로 드러난다.

```c
while ((*STATUS & READY_BIT) == 0)   // ① 준비 비트가 설 때까지 검사만 되풀이
    ;                                //    (헛도는 것은 바로 이 한 줄이다)
value = *DATA;                       // ② 준비된 것을 확인한 뒤에야 데이터를 읽는다
```

두 줄의 순서를 뒤집으면 아직 갱신되지 않은 값을 읽게 되므로, ①의 검사는 생략하거나 뒤로 미룰 수 있는 성질의 것이 아니다.

**예시 2 — 같은 가정으로 계산한 두 갈래 산술.**

아래 두 표는 모두 **CPU 1 GHz(1사이클 ≈ 1 ns), 루프 한 바퀴 = 4사이클 ≈ 4 ns**라는 가정에서 산술로 유도한 어림값이다. (실제 사이클 수는 CPU와 컴파일된 코드에 따라 달라진다.)

_(가) 쉼 없이 붙여 도는 경우 — 기다림의 길이가 헛돈 횟수를 정한다._

| 장치가 준비되기까지 걸린 시간 | 헛돈 루프 횟수  | 헛되이 실행된 명령어 수 |
| ---------------- | --------- | ------------- |
| 100 ns           | 25바퀴      | 100개          |
| 1 µs             | 250바퀴     | 1,000개        |
| 1 ms             | 250,000바퀴 | 100만 개        |
| 10 ms            | 250만 바퀴   | 1,000만 개      |
| 10 s             | 25억 바퀴    | 100억 개        |

_(나) 간격 T를 두는 경우 — 같은 손잡이가 비용과 지연을 반대로 움직인다._

| 검사 간격 T         | 1초당 검사 횟수 | 1초당 검사에 쓰는 사이클 | CPU 시간 중 비율 | 최악 지연 | 평균 지연  |
| --------------- | --------- | -------------- | ----------- | ----- | ------ |
| 쉼 없이 (T ≈ 4 ns) | 2억 5천만 회  | 10억 사이클        | 100%        | 4 ns  | 2 ns   |
| 50 µs           | 20,000회   | 80,000사이클      | 0.008%      | 50 µs | 25 µs  |
| 1 ms            | 1,000회    | 4,000사이클       | 0.0004%     | 1 ms  | 0.5 ms |

첫 행의 "최악 지연 4 ns"는 장치가 그만큼 빨리 답한다는 뜻이 아니라, **루프 한 바퀴가 4 ns라는 위 가정에서 나온 값**이라는 점에 주의하자 — 검사와 검사 사이가 한 바퀴만큼밖에 안 되므로 알아채는 데 걸리는 시간도 한 바퀴가 된다.

표 (나)를 세로로 읽으면 저울이 눈에 보인다. T를 4 ns에서 1 ms로 **25만 배** 벌리면 검사 비용은 100%에서 0.0004%로 **25만분의 1**이 되고, 최악 지연은 4 ns에서 1 ms로 **25만 배** 늘어난다. 두 칸 사이도 같은 비율이다 — T를 1 ms에서 50 µs로 20배 좁히면 검사는 20배 잦아지고 지연은 20배 짧아진다. 실제로도 1 ms마다 폴링하면 평균 대기는 대개 0.5 ms 안팎, 50 마이크로초마다 폴링하면 평균 대기는 25 마이크로초 안팎이 되며, 그 대가는 상태를 검사하는 데 계속 지불하는 CPU 시간이다. 고를 것은 이 줄 위의 한 점이다.

#### 5) 다른 키워드와의 연결

여기서 CPU가 반복해서 읽는 상태·데이터 레지스터에 애초에 어떤 수단으로 접근하는지는 "메모리 사상 입출력"과 "전문적으로 처리하기: 입출력 기계 명령어"가 다룬다. 검사의 방향을 뒤집어 장치 쪽이 먼저 알리게 하는 방식은 "인터럽트 구동식 입출력"이 다룬다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * 같은 원리를 장치가 아니라 잠금장치에 적용하면 스핀락이 된다. 그리고 폴링이 늘 손해인 것도 아니어서, 임계 구역이 몇 마이크로초처럼 짧으면 문맥 전환 비용이 아예 없는 스핀 쪽이 이긴다. "폴링은 원시적, 인터럽트는 발전형"이 아니라 기다리는 시간의 길이가 승패를 가른다.
> * 게이밍 마우스 광고의 "폴링 레이트 1000Hz/8000Hz"는 같은 단어지만 주체가 반대다. USB는 호스트가 모든 전송을 시작하는 폴링 버스라 장치가 호스트를 먼저 깨울 수 없고, 호스트가 정해진 주기로 물어본다. USB 2.0 고속 구간의 최소 주기가 125 µs이므로 8000Hz 마우스는 그 최소 주기를 꽉 채워 쓰는 셈이다.
> * 운영체제 교재 OSTEP은 36장에서 이 주제를 "잦은 폴링 없이 장치 상태를 확인해 CPU 부담을 낮추려면?"이라는 물음으로 세우고 인터럽트를 답으로 준다. 그런데 곧바로 단서를 단다 — 장치가 아주 빨리 끝내는 경우엔 다른 프로세스로 갈아탔다가 인터럽트를 처리하고 되돌아오는 왕복 비용 때문에 인터럽트가 오히려 시스템을 느리게 만든다.

### 5. 배달 음식 주문과 중단 처리

#### 1) 개념 정의

"음식을 시켜 놓고 현관 앞에 서서 기다리는 대신, 하던 집안일을 하다가 초인종이 울리면 그때 나가서 받는다"는 일상의 장면을 빌려 중단(인터럽트) 처리라는 일하는 방식을 설명 비유하여 설명한다.

#### 2) 원리 설명

음식을 시켜 놓고 현관 앞에 서 있으면, 그 40분 동안 내 손은 비어 있다. 앉지도 못하고, 개려던 빨래도 싱크대에 쌓인 그릇도 그대로다. 그렇다고 내가 서 있어서 음식이 1분이라도 빨리 오는 것도 아니다. 그런데 음식이 도착한 걸 알아채려고 꼭 문 앞에 붙어 있어야 하는 것은 아니다 — 배달원은 도착하면 초인종을 누르기로 되어 있고, 그 소리는 안방에서도 들린다. 그러니 나는 방에서 빨래를 개다가 소리가 나면 그때 현관으로 나가면 된다.

#### 3) 세부 메커니즘

이 주제가 실제로 다루는 것은 위 장면이 컴퓨터의 무엇에 대응하는지, 그리고 **어디까지만 대응하는지**다.

**(가) 비유 ↔ 컴퓨터 매핑**

| 비유 속 요소             | 컴퓨터 쪽                          |
| ------------------- | ------------------------------ |
| 나                   | CPU                            |
| 배달원                 | 입출력 장치                         |
| 초인종 소리              | 인터럽트 신호                        |
| 소리가 나기 전까지 개고 있던 빨래 | 실행 중이던 프로그램                    |
| "내가 어디까지 개고 있었더라"   | 실행 상태 (무엇에 어떻게 적어 두는지는 별도 소주제) |
| 현관에 나가 문 열고 음식 받기   | 인터럽트 처리 함수(ISR)                |

표의 오른쪽 칸이 이 비유의 번역문 전부다. 왼쪽 칸의 장면을 넘어서는 이야기는 이 비유가 감당하지 못한다.

**(나) 비유가 맞는 범위 — 네 군데에서 끊긴다**

**① 벨소리가 늘 들리고 늘 응답된다고 가정한다.** \
비유에서 초인종은 "누르면 들리는 것"이다. 누르는 순간과 내가 아는 순간 사이에 틈이 없고, 들렸으면 당연히 나간다. 실제 집은 그렇지 않다 — 헤드폰을 끼고 음악을 들으며 울리는 전화를 흘려 넘기는 상태에서는 그 전화를 알아채는 데 더 오래 걸린다. 부름을 못 듣는 것과 듣고도 지금은 안 받는 것은 그 장면 안에서 이어져 있다. 게다가 벨이 울린 뒤에도, 내가 하던 것을 내려놓고 현관까지 걸어 나올 때까지 문은 열리지 않는다. 부름이 언제 인지되는가는 비유가 0으로 놓고 지나가는 자리다.

**② "하던 일로 돌아온다"가 보장이 아니라 희망이다.** \
비유대로라면 음식을 받고 난 뒤 나는 하던 일로 돌아가기를 **택한다**. 이 "택한다"가 비유가 실제보다 후하게 말하는 지점이다. 전화가 걸려 온 경우로 바꿔 보면 반대쪽이 보인다 — 전화를 받고 나면 하던 일 A로 돌아갈 수도 있지만, 통화 내용 때문에 A를 옆으로 밀어 두고 곧장 B부터 시작하게 될 수도 있다. "문 열고 음식 받고 → 다시 빨래"는 비유가 그리는 가장 순한 경우 하나일 뿐이다.

**③ 비유에는 초인종이 하나뿐이다.** \
그래서 이 비유 안에는 "누가 눌렀나"라는 질문 자체가 없다. 소리가 나면 배달원이다. 앞문에서 누르든 뒷문에서 누르든 똑같은 소리가 나는 초인종이 이 단순화를 잘 보여 준다. 현실의 집에는 벨이 여럿이고, **소리가 났다는 것**과 **누가 불렀는가**는 서로 다른 문제인데 비유에서는 이 둘이 하나로 붙어 있다.

**④ "소리를 듣는 역할"이 누구인지 비유에 아예 비어 있다.** \
비유 속의 나는 빨래도 개고 벨소리도 듣는다. 두 가지를 동시에 하는 것이 너무 당연하게 그려져서, 누가 어떻게 듣고 있는지는 아무도 묻지 않는다. 이건 비유가 틀린 자리가 아니라 **비유가 침묵하는 빈칸**이고, 이 비유 뒤에 한 줄을 반드시 덧붙여야 하는 이유이기도 하다 — 실제 인터럽트 처리는 이 장면이 그리는 것보다 한 겹 더 복잡하다. 그중 가장 큰 빈칸이 "하던 일을 다시 이어가려면 무엇이 남아 있어야 하는가"인데, 비유 속의 나는 그것을 그냥 기억하고 있는 것으로 처리해 버린다.

#### 4) 예시

18:40에 음식을 주문했고, 배달은 40분 걸려 19:20에 도착한다. 도착 시각은 두 안에서 똑같다.

**A안 — 문 앞에서 기다리기**

| 시각             | 내가 한 일                         |
| -------------- | ------------------------------ |
| 18:40          | 주문 완료. 곧장 현관으로 나가 선다           |
| 18:41 \~ 19:20 | 그대로 서 있는다. 빨래 바구니 그대로, 설거지 그대로 |
| 19:20          | 초인종. 바로 앞이므로 곧장 문을 연다          |
| 19:21          | 식탁에 놓고 식사 시작                   |

40분 동안 끝낸 집안일: **0개**

**B안 — 하던 일을 하다가 초인종에 반응**

| 시각             | 내가 한 일                                          |
| -------------- | ----------------------------------------------- |
| 18:40          | 주문 완료. 안방으로 들어간다                                |
| 18:41 \~ 18:55 | 빨래를 갠다 (14분)                                    |
| 18:55 \~ 19:10 | 설거지를 한다 (15분)                                   |
| 19:10 \~ 19:20 | 책상을 정리한다 (10분)                                  |
| 19:20          | 초인종. 정리하던 것을 내려놓고 현관으로 나가 문을 열고 음식을 받는다 (약 40초) |
| 19:21          | 식탁에 놓고 식사 시작                                    |

40분 동안 끝낸 집안일: **빨래 개기, 설거지, 책상 정리 — 3개**

두 안 모두 19:21에 밥을 먹기 시작한다. 배달에 걸리는 40분은 어느 쪽에서도 1분도 줄지 않았다. 달라진 것은 그 40분 사이에 집에서 벌어진 일의 개수뿐이다 — **인터럽트가 없애는 것은 대기 시간이 아니라 대기 시간의 낭비다.**

####

비유가 비워 둔 "누가 소리를 듣는가"는 "CPU는 어떻게 인터럽트 신호를 감지할까?"가, "벨이 울린 뒤 실제로 어떤 순서로 일이 진행되는가"는 "인터럽트 구동식 입출력"이, "어디까지 개고 있었더라"를 실제로 어디에 어떻게 적어 두는가는 "중단된 프로그램의 실행 상태 저장과 복원"이 이어받는다. 한편 문 앞에 서 있는 대신 문을 계속 열어 보는 쪽을 택하면 그건 "폴링: 계속 검사하기"의 이야기가 된다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * 인터럽트를 처음 쓴 기계가 무엇이냐는 아직도 정리되지 않았다. UNIVAC 1103이 자주 꼽히지만 1953년 매뉴얼에는 인터럽트 설명이 없어 1956년의 1103A를 최초로 보는 견해도 있고, 입출력 인터럽트만 놓고 보면 1954년 미국 표준국의 DYSEAC에 최초의 자리를 주는 견해도 있다.
> * 초인종을 잠시 끄는 스위치에도 예외가 있다. x86의 `CLI`는 EFLAGS의 IF 플래그만 지우기 때문에 마스크 가능한 외부 인터럽트만 막히고, NMI와 예외는 그대로 들어온다. 전원이 곧 끊길 것 같은 상황처럼 "무시하면 안 되는 벨"을 위해 일부러 남겨 둔 선이다.
> * 벨을 누른 순간부터 실제로 문 앞에 도착하기까지의 시간에도 정식 이름이 있다 — 인터럽트 지연(interrupt latency)이다. ARM Cortex-M3에서는 대기 없는 메모리 기준 12사이클까지 줄어드는데, 이 12사이클 안에 레지스터 저장과 벡터 인출, 핸들러 첫 명령어 인출이 모두 들어 있다.

### 6. 인터럽트 구동식 입출력

하나의 입출력이 진행되는 동안 주도권이 CPU와 장치 사이를 두 번 오간다.

#### 1) 개념 정의

인터럽트 구동식 입출력은 CPU가 장치 레지스터에 명령을 써 넣어 작업을 지시한 뒤 곧바로 손을 떼고 다른 프로그램을 실행하다가, 장치가 일을 끝내고 인터럽트를 올리면 그때 인터럽트 처리 함수(ISR)로 들어가 뒷마무리를 하는 입출력 방식이다.

#### 2) 원리 설명

장치가 끝날 때까지 CPU를 붙잡아 두지 않는 편이 낫다는 것은 이미 본 결론이다. \
이 방식의 핵심은 **하나의 입출력을 '요청'과 '완료'라는 두 사건으로 쪼개고, 그 사이 구간을 장치에게 통째로 넘기는 것**이다. \
CPU는 장치 레지스터에 무엇을 하라는 명령을 써 넣는 것으로 요청을 거는데, 명령이 명령 레지스터에 들어가는 그 행위 자체가 장치에게 "지금부터 시작하라"는 신호가 된다.&#x20;

그 뒤로 장치는 CPU의 클럭과 무관하게, CPU의 통제도 받지 않고 혼자 움직이며, 그동안 CPU는 이 입출력과 아무 상관 없는 다른 프로그램의 명령어를 실행한다. \
일이 끝나면 이번에는 장치 쪽에서 인터럽트를 올려 CPU를 부르고, CPU는 하던 일을 잠시 멈추고 인터럽트 처리 함수로 들어가 결과를 챙긴 뒤 멈췄던 자리로 돌아간다.&#x20;

결국 하나의 입출력이 진행되는 동안 **주도권은 CPU → 장치 → CPU로 딱 두 번 넘어가며, 그 두 인계 지점이 이 방식의 뼈대 전부**다.

#### 3) 세부 메커니즘

디스크에서 블록 하나를 읽어 오는 요청을 예로 들어, 매 단계의 행위자가 CPU인지 장치인지 표시하며 따라가 보자.

1. **\[CPU] 요청 준비** — 장치 드라이버가 무엇을(디스크의 몇 번 블록을) 어디로(메모리의 어느 주소로) 읽어 올지를 장치 레지스터에 채워 넣는다.
2. **\[CPU] → \[장치] · 첫 번째 인계 지점** — 마지막으로 **명령 레지스터에 "읽어라"라는 명령 값을 쓴다.** 이 쓰기가 이루어지는 순간이 주도권이 넘어가는 지점이다. 별도의 "출발" 신호가 따로 있는 게 아니라, 명령 레지스터에 값이 들어가는 것이 곧 시작 지시다.
3. **\[CPU] 요청 함수가 반환한다** — 데이터를 손에 쥐지 않은 채로 돌아온다. CPU는 이 입출력에서 완전히 빠져나와 다른 프로그램을 실행하러 간다.
4. **\[장치] 장치가 혼자 일한다** — 이 구간의 행위자는 오로지 장치다. 장치는 CPU와 같은 클럭으로 돌지도 않고 CPU의 통제를 받지도 않은 채(비동기) 제 속도로 작업하고, 읽어 낸 데이터는 자기 데이터 레지스터(버퍼)에 담아 둔다.
5. **\[장치] → \[CPU] · 두 번째 인계 지점** — 작업이 끝나면 **장치가 인터럽트를 올린다.** CPU가 이를 알아채고 인터럽트 처리 함수로 넘어간다. 첫 번째 인계가 CPU가 능동적으로 건네준 것이었다면, 이번 인계는 장치가 일방적으로 되돌려 주는 것이다 — 언제 넘어올지 CPU 쪽 코드에는 적혀 있지 않다. (CPU가 이 신호를 어떤 경로로 알아채는지는 뒤의 소주제 몫이다.)
6. **\[CPU] 인터럽트 처리 함수 안** — 장치의 상태 레지스터를 읽어 정상 완료인지 오류인지 확인하고, 장치의 데이터 레지스터(버퍼)에 있는 데이터를 메모리로 옮긴 뒤, 이 요청이 끝났다고 표시한다.
7. **\[CPU] 복귀** — 저장해 두었던 실행 상태를 복원하고, 인터럽트로 끊겼던 자리로 되돌아가 하던 일을 계속한다.

두 인계 지점 사이(3\~5단계)에는 **이 입출력의 주인이 CPU가 아니다.** 이 구간의 길이는 장치가 정하지 CPU가 정하지 않으며, CPU 쪽에는 그 길이를 알 방법도, 기다릴 의무도 없다. 인터럽트 구동식 입출력의 절차를 이렇게 주체별로 갈라 놓고 보면, "CPU가 입출력을 한다"는 말이 사실은 **양 끝의 두 토막에서만 참**이라는 것이 드러난다.

#### 4) 예시

**예시 1 — 시간선: CPU가 이 요청에 실제로 쓰는 시간**

```
  시각:  t0 ──── t1 ──────────────────────────────── t2 ──── t3 ──────▶

  CPU :  [ 요청 걸기 ]   ( 이 요청과 무관한 다른 일 )   [  ISR  ]  원래 일로 복귀
               │                                          ▲
      주도권 CPU → 장치                          주도권 장치 → CPU
               ▼                                          │
  장치:    (대기)     [ 디스크가 혼자 블록을 읽는 중 ]      (대기)
                     └───── 이 구간의 주인은 장치 ─────┘
```

* `t0~t1` — CPU가 장치 레지스터를 채우고 명령 레지스터에 명령을 쓴다. **여기서 주도권이 장치로 넘어간다.**
* `t1~t2` — 장치가 혼자 읽는다. 이 구간에 CPU는 이 요청과 무관하다.
* `t2` — 장치가 인터럽트를 올린다. **여기서 주도권이 CPU로 되돌아온다.**
* `t2~t3` — 인터럽트 처리 함수가 데이터를 메모리로 옮기고 요청을 끝났다고 표시한다.

> **CPU가 이 입출력 요청 때문에 실제로 쓰는 시간은 요청을 거는 순간(`t0~t1`)과 인터럽트 처리 함수(`t2~t3`), 두 조각뿐이다.** 그림에서 가장 긴 `t1~t2` 구간에는 CPU 쪽 비용이 0이다 — 그 구간의 행위자가 장치이기 때문이다.

**두 조각의 비용.** 위 캡션이 말한 "두 조각"은 공짜가 아니다. 인터럽트가 하나 올라올 때마다 CPU는 _하던 일을 멈추고 → 인터럽트 처리 함수로 들어갔다가 → 원래 자리로 돌아오는_ 과정을 매번 처음부터 되풀이한다. \
이 진입·복귀는 옮기는 데이터가 1바이트든 4KB든 상관없이 **인터럽트 1회마다 똑같이 한 번씩 붙는 고정 비용**이다. \
올라온 인터럽트를 어느 처리 함수에 배분할지 가려내고 실제로 처리하는 일 자체가, 옮기는 데이터의 양과 무관하게 그만큼의 시간을 잡아먹는다.

그래서 이 방식이 **언제나** 이기는 것은 아니다. \
되찾는 것은 `t1~t2` 구간이고 치르는 것은 인터럽트 1회당 고정 비용이니, **`t1~t2`가 그 고정 비용보다 충분히 길 때만 남는 장사**다. \
장치가 아주 빨라 기다림이 애초에 짧거나, 인터럽트가 극단적으로 자주 올라와 고정 비용이 계속 쌓이면 이득이 뒤집힌다 — 인터럽트 처리 비용이 만만치 않기 때문에, 기다리는 시간이 애초에 짧다면 차라리 폴링으로 그냥 기다리는 쪽이 더 빠르다. 인터럽트를 쓸지 말지는 결국 이 비교로 결정된다.

**예시 2 — 요청 코드와 완료 코드가 두 함수로 쪼개진다**

앞 절차를 그대로 코드로 옮기면, 하나였던 "디스크에서 읽어 오기"가 소스 코드에서 두 개의 함수가 된다.

```c
/* (1) 요청을 거는 쪽 — 데이터 없이 곧바로 반환한다 */
void disk_read(int block, char *buf) {
    pending_buf = buf;                     /* 완료 시 어디에 담을지 기억해 둔다 */
    write_reg(DISK_ADDR_REG, block);       /* 무엇을 읽을지 */
    write_reg(DISK_CMD_REG,  CMD_READ);    /* <- 이 쓰기 순간, 주도권이 장치로 */
    return;                                /* 데이터는 아직 없다. 그냥 돌아간다 */
}

/* (2) 완료를 처리하는 쪽 — 한참 뒤, 장치가 인터럽트를 올렸을 때 실행된다 */
void disk_isr(void) {
    if (read_reg(DISK_STATUS_REG) & ERR) { /* 오류 처리 */ }
    copy_from_device(DISK_DATA_REG, pending_buf);  /* 데이터를 메모리로 */
    mark_done();                                   /* 요청이 끝났음을 표시 */
}
```

눈여겨볼 것은 `disk_read()`가 반환한 시점과 `disk_isr()`가 도는 시점이 **시간적으로 떨어져 있고**, 그 사이 간격을 프로그램이 아니라 장치가 정한다는 점이다. 하나의 논리적 동작이 이렇게 **요청 코드와 완료 코드 두 조각으로 갈라지는 것**이 인터럽트 구동식 입출력이 프로그램 구조에 남기는 대표적인 흔적이다.

갈라짐의 대가는 코드 안에도 그대로 보인다. 둘로 나뉘었으니 **첫 조각이 알고 있던 것(읽어 온 데이터를 어디에 담을지)을 어딘가에 남겨 둬야 둘째 조각이 그것을 찾을 수 있다** — 위 코드의 `pending_buf`가 바로 그 자리다. 한 함수 안에서 끝나는 일이었다면 그냥 지역 변수였을 것이 요청과 완료 사이를 건너가야 해서 밖으로 나온 것이다.

실제 장치 드라이버도 같은 모양이다. "보내기" 함수는 전송이 끝나기를 기다리지 않고 즉시 반환하고, 전송이 정말 끝났을 때 할 일은 완료 처리 함수 쪽에 따로 적는다. 요청을 거는 자리와 결과를 받는 자리가 소스 코드에서 아예 다른 곳인 것이다.

#### 5) 다른 키워드와의 연결

2단계의 "레지스터에 명령을 쓴다"를 어떤 수단으로 하는지는 "전문적으로 처리하기: 입출력 기계 명령어"와 "메모리 사상 입출력"이, 5단계의 "CPU가 인터럽트를 알아챈다"의 하드웨어 경로는 "CPU는 어떻게 인터럽트 신호를 감지할까?"가, 7단계의 저장·복원 기법은 "중단된 프로그램의 실행 상태 저장과 복원"이, `disk_isr()`가 보통의 함수 호출과 어떻게 다른지는 "인터럽트 처리와 함수 호출의 차이"가 각각 이어받는다. 위 비교에서 반대편에 놓이는 방식, 곧 CPU가 직접 반복 검사하는 쪽의 비용이 어떻게 계산되는지는 "폴링: 계속 검사하기"가 다룬다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * 인터럽트 처리에만 매달리다 정작 본 작업을 못 하는 상태에는 "수신 라이브록(receive livelock)"이라는 이름이 붙어 있고, Mogul과 Ramakrishnan이 1996년 USENIX 연례 학술대회에서 발표한 논문이 그 고전이다. 리눅스의 해법인 NAPI는 방향을 아예 거꾸로 돌려서, 인터럽트가 한 번 오면 그 장치의 인터럽트를 마스크해 버리고 폴링이 끝날 때까지 다시 켜지 않는다. 부하가 높을수록 인터럽트 방식이 폴링 방식으로 되돌아가는 셈이다.
> * 인터럽트 처리 중에는 잠들 수 있는 API를 부를 수 없다. 리눅스에서는 `mutex_lock()`은 물론이고 잠들지 않는 `mutex_trylock()`조차 금지이며, 메모리 할당도 `GFP_KERNEL` 대신 절대 블록하지 않는 `GFP_ATOMIC`을 써야 한다(대신 실패할 확률이 올라간다). 이 제약이 처리 함수를 급한 앞부분과 미뤄도 되는 뒷부분으로 쪼개는 관행을 낳았다.

### 7. CPU는 어떻게 인터럽트 신호를 감지할까?

#### 1) 개념 정의

장치에서 CPU까지 물리적으로 연결된 **인터럽트 요청선(핀)** 에 신호가 올라오면, CPU는 명령어 하나를 완전히 끝낸 **명령어 경계**에서 그 핀을 검사해 인터럽트가 왔음을 알아채고, 함께 전달받은 **인터럽트 번호**로 **인터럽트 벡터 테이블**을 조회해 인터럽트 처리 함수(ISR)의 주소를 얻어 그 주소로 점프한다.

#### 2) 원리 설명

CPU가 인터럽트를 알아채는 통로는 소프트웨어가 아니라 **전선 한 가닥**이다. \
CPU 칩에는 `INTR`(interrupt request)이라는 이름이 붙은 핀이 실제로 나 있고, 이 선의 전압을 바꾸는 것이 곧 "인터럽트를 요청한다"는 뜻이다.&#x20;

그런데 CPU는 이 핀을 매 순간 쳐다보고 있는 것이 아니라, **명령어 하나를 실행하고 난 직후**에 검사한다.&#x20;

즉 인출 → 해석 → 실행이 끝나는 지점마다 "혹시 인터럽트 선이 올라와 있나?"를 한 번씩 확인하는 것이다. \
검사 시점이 명령어 경계라는 것은 곧, 인터럽트를 받아들이는 순간의 CPU가 언제나 "직전 명령어까지는 완전히 끝났고, 다음 명령어는 아직 아무것도 바꾸지 않은" 상태에 있다는 뜻이다 — 명령어를 반쯤 처리한 어중간한 상태가 아니다. 그래서 인터럽트 신호가 명령어 실행 도중에 도착하더라도 **실행 중이던 명령어는 중간에 잘리지 않고 온전히 끝난 뒤**에야 인터럽트가 받아들여진다.

#### 3) 세부 메커니즘

한 단계 더 들어가면, 검사 이후에 "누가 걸었는지"를 알아내는 절차가 따로 있다.

* **컨트롤러가 여러 요청선을 하나로 모은다.** \
  장치는 키보드·타이머·디스크 등 여럿인데 CPU에 난 인터럽트 핀은 사실상 하나뿐이다. 그래서 중간에 **인터럽트 컨트롤러**를 두고, 장치들의 요청선(IRQ0, IRQ1, …)을 컨트롤러가 받아 우선순위를 정한 뒤 CPU의 INTR 핀 하나를 올린다. 컨트롤러는 "CPU의 하나뿐인 INTR 핀을 여러 개로 확장해 주는 장치"인 셈이다.
* **핀만으로는 발신자를 알 수 없으므로 번호를 받아온다.** \
  선이 올라왔다는 사실만으로는 어느 장치인지 알 수 없다. CPU는 인터럽트를 받아들이기로 하면 **응답 신호(INTA)** 를 되돌려 보내고, 컨트롤러는 그 응답에 맞춰 **8비트짜리 인터럽트 번호(벡터 번호)** 를 데이터 버스에 실어 준다. "누가 걸었는가"는 전선이 아니라 이 번호로 전달된다.
* **번호는 테이블의 몇 번째 칸인지를 뜻하는 색인이다.** \
  CPU는 받은 번호를 주소로 바로 쓰지 않는다. 번호에 항목 하나의 크기를 곱하고 테이블 시작 주소를 더해 **인터럽트 벡터 테이블 안의 위치**를 계산한 뒤, 그 칸에 적힌 값을 읽어 처리 함수의 주소를 얻는다. x86의 초기 방식에서는 항목 하나가 4바이트라 "번호 × 4"가 곧 색인이 된다.
* **감지를 잠시 꺼 두는 스위치가 두 군데 있다.** \
  CPU 안에는 **인터럽트 허용 플래그**가 있어서, 이 플래그가 꺼져 있으면 명령어 경계에서 검사를 하더라도 인터럽트를 받아들이지 않는다(x86의 `cli`/`sti`가 이 플래그를 끄고 켠다). 또 컨트롤러 쪽에도 **마스크 레지스터**가 있어, 특정 IRQ 선 하나만 골라서 막아 둘 수도 있다. 한편 절대 무시하면 안 되는 긴급 신호를 위해, 이 스위치로 막을 수 없는 **마스크 불가능 인터럽트(NMI)** 핀이 따로 나 있다.

> 참고: 자료에 따라 검사 시점을 "명령어 실행이 끝난 직후"라고 쓰기도 하고 "다음 명령어가 시작되는 시점"이라고 쓰기도 하는데, 둘 다 같은 **명령어 경계**를 가리키는 표현이다.

#### 4) 예시

**명령어 주기에 끼워 넣은 인터럽트 검사 — 키보드를 눌렀을 때**

CPU가 쉬지 않고 도는 반복문의 맨 끝에 검사 한 줄이 붙어 있다고 생각하면 된다. 아래는 사용자가 키를 하나 눌렀을 때 그 검사에서 벌어지는 일을 실제 숫자로 채운 것이다.

```c
while (1) {
    명령어 = 인출(PC);         // 인출: 메모리에서 명령어를 읽어 온다
    동작   = 해석(명령어);      // 해석
    실행(동작);                // 실행 ── 이 안에서는 끼어들 수 없다.
                              //        키보드가 IRQ1을 올려도 이 명령어는 끝까지 간다
    PC = PC + 명령어_길이;

    /* ────── 여기가 명령어 경계: 인터럽트 검사 지점 ────── */
    if (인터럽트_허용_플래그 == 1 && INTR핀 == 1) {   // 컨트롤러가 IRQ1을 받아 올려 둔 핀
        번호 = 컨트롤러에게_인터럽트_번호를_받는다();   // INTA 응답 → 8비트 번호, 키보드는 9(0x09)
        주소 = 메모리[벡터테이블_시작주소 + 번호 * 4]; // 0 + 9*4 = 36(0x24)번지의 4바이트를 읽는다
        PC   = 주소;   // ★ 키보드 처리 함수의 첫 명령어로 점프
    }                  //   ── 이 소주제는 정확히 여기까지다
}
```

초기 IBM PC 계열이 쓰던 **실제 모드**에서는, IRQ0\~IRQ7이 인터럽트 번호 0x08\~0x0F에 대응하도록 컨트롤러가 설정되어 있어 타이머(IRQ0)는 8번, 키보드(IRQ1)는 9번을 받는다.&#x20;

이때 벡터 테이블은 0번지에서 시작하고 한 칸이 4바이트이므로 테이블 전체 크기는 `256 × 4 = 1024`바이트(0x000\~0x3FF)다. \
한 칸의 4바이트는 단순한 주소 하나가 아니라 **코드 영역을 가리키는 값과 그 안에서의 위치, 두 개가 짝을 이룬 것**이어서, 둘이 합쳐져야 처리 함수의 자리가 완성된다. (테이블의 위치·항목 크기·IRQ에 붙는 번호는 CPU의 동작 모드에 따라 달라진다 — 여기서 드는 숫자는 이 전제 아래의 값이다.)

#### 5) 다른 키워드와의 연결

이 소주제는 "벡터 테이블에서 얻은 주소로 점프한다"는 순간에서 정확히 멈춘다 — 점프하기 직전에 CPU가 **실행 상태**를 어떻게 갈무리하고 나중에 어떻게 되돌리는지는 "중단된 프로그램의 실행 상태 저장과 복원"이 이어받는다. 또 여기서 설명한 감지 메커니즘은 "인터럽트 구동식 입출력"이 그리는 전체 흐름 가운데, 장치가 보낸 신호가 CPU에 도달해 처리 함수로 넘어가는 구간 하나를 확대해 본 것이다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * PC/AT는 인터럽트 컨트롤러를 두 개 물려 썼지만 쓸 수 있는 선은 16개가 아니라 15개다. 슬레이브의 출력이 마스터의 IRQ2를 차지해 버리기 때문이다. 게다가 BIOS 기본 매핑은 연속적이지도 않아서, IRQ0~~7은 인터럽트 번호 0x08~~0x0F인데 IRQ8~~15는 갑자기 0x70~~0x77로 뛴다.
> * 8259 컨트롤러 안에는 상태를 추적하는 레지스터가 셋 있다. IRR은 요청은 왔지만 아직 CPU에 올리지 못한 선, ISR은 CPU가 받아들였지만 아직 처리 완료 신호가 오지 않은 선, IMR은 가려 놓은 선을 표시한다. 그 뒤를 이은 IO-APIC은 24칸짜리 리다이렉션 테이블을 갖는데, 한 칸이 64비트라 설정하려면 32비트 쓰기를 두 번 해야 한다.
> * 요즘 PCIe 장치의 인터럽트에는 전용 신호선이 아예 없다. MSI 방식에서는 장치가 약속된 주소에 메모리 쓰기를 한 번 하는 것이 곧 인터럽트다. 부수 효과가 재미있는데, 그 쓰기가 앞선 데이터 쓰기를 추월할 수 없어서 인터럽트가 도착한 시점이면 데이터는 이미 메모리에 다 들어와 있다. 개수도 핀 방식 함수당 1개에서 MSI 32개, MSI-X 2048개로 늘었다.

### 8. 인터럽트 처리와 함수 호출의 차이

처리 함수로 점프한 뒤 — 이 이동은 우리가 아는 함수 호출과 무엇이, 왜 다른가.

#### 1) 개념 정의

함수 호출은 프로그램이 소스 코드에 **직접 적어 둔 약속된 이동**이고, 인터럽트 처리는 프로그램이 전혀 모르는 사이에 **외부가 강제로 끼워 넣는 이동**이라서, 둘은 "지금 하던 곳을 떠났다가 돌아온다"는 겉모습만 같을 뿐 성립 조건이 근본적으로 다르다.

#### 2) 원리 설명

겉으로 보면 둘은 똑같다. \
지금 위치를 기억해 두고, 다른 코드로 뛰어가서, 일을 끝내고, 원래 자리로 돌아온다.&#x20;

그래서 인터럽트를 "하드웨어가 강제로 건 함수 호출"이라고 부르기도 한다 — 단, 그 호출은 **아무 두 명령어 사이에서든 일어날 수 있다**.&#x20;

바로 여기서 근본적인 차이가 갈린다. \
함수 호출은 호출 지점이 소스 코드에 적혀 있으므로 컴파일러가 **컴파일 타임에 "여기서 떠난다"는 것을 알고**, 그 지점을 기준으로 필요한 준비 코드를 미리 끼워 넣을 수 있다.&#x20;

반면 인터럽트는 언제 들어올지 컴파일 타임에 알 수 없으므로 **"들어오기 직전"에 미리 무언가를 저장해 둘 수가 없다**. 미리 알 수 없다는 것은 곧 미리 준비할 수 없다는 뜻이고, 미리 준비할 수 없다는 것은 곧 **양쪽이 역할을 나눠 갖는 사전 합의가 성립할 수 없다**는 뜻이다. \
그 결과 인터럽트 처리 쪽은 "아무것도 기대할 수 없으니 내가 다 책임진다"는 훨씬 무거운 방식으로 동작하게 된다.

#### 3) 세부 메커니즘

**호출 규약(calling convention)이란 결국 '역할 분담 계약'이다.** \
함수 호출에서는 컴파일러가 부른 쪽과 불린 쪽 코드를 **모두 보면서** 미리 계약을 맺어 둔다. \
어떤 레지스터는 "불린 쪽이 마음대로 써도 되니, 아쉬우면 **부른 쪽이 호출 직전에** 알아서 챙겨 둬라", 다른 어떤 레지스터는 "**불린 쪽이** 쓰더라도 돌아가기 전에 반드시 원래대로 돌려놔라"는 식이다. \
이 계약 덕분에 저장해야 할 양이 최소로 줄어든다 — 부른 쪽은 **불린 쪽이 건드려도 되는 것만** 저장하면 되기 때문이다.

**그런데 인터럽트에서는 이 계약의 전제가 통째로 무너진다.** 첫째, "호출 직전"이라는 시점 자체가 존재하지 않는다. 프로그램은 자기가 언제 멈출지 모르므로 "부른 쪽이 미리 챙겨 두는 몫"을 애초에 수행할 수 없다.

**둘째, — 인터럽트 처리 함수(ISR)는 원래 실행 중이던 프로그램과 아무 관계도 없는 코드다.** \
같은 프로그램 안의 두 함수라면 컴파일러가 양쪽을 함께 보고 계약을 맺을 수 있지만, 키보드가 부르는 인터럽트 처리 함수는 지금 돌아가고 있던 계산 프로그램의 소스 코드를 **본 적조차 없다**. \
계약을 맺을 상대가 없는 것이다. \
그래서 인터럽트 처리 함수는 "어느 레지스터는 안 건드리기로 하자"는 합의에 기댈 수 없고, **모든 레지스터를 '내가 원래대로 돌려놔야 하는 것'으로 취급**해야 한다. 인터럽트 처리 함수는 하드웨어가 자동으로 챙겨 주는 것 외에는 **아무것도 저장돼 있으리라 기대할 수 없다**. 결론은 하나다 — **함수 호출보다 통째로 저장해야 할 것이 훨씬 많아진다.** (그 저장 대상이 정확히 무엇이고 어떤 순서로 저장·복원되는지는 다음 소주제의 몫이다.)

| 비교 축          | 함수 호출                        | 인터럽트 처리                                                              |
| ------------- | ---------------------------- | -------------------------------------------------------------------- |
| 누가 개시하는가      | 프로그램 자신이 명시적으로 (`call`)      | 외부 장치가 **비동기적으로** 신호를 보내 강제로                                         |
| 호출 지점을 미리 아는가 | 소스 코드에 적혀 있어 **컴파일 타임에 알려짐** | **어느 두 명령어 사이에 끼어들지 아무도 모름**                                         |
| 호출 규약이 있는가    | 있음 — 누가 무엇을 저장할지 컴파일러가 미리 합의 | **없음** — 합의를 맺을 상대가 없어 사실상 전부 보존                                     |
| 저장 부담         | 계약에 따라 필요한 최소한만              | 훨씬 많음                                                                |
| 인자와 반환값       | 인자를 넘기고 값을 돌려받음              | **인자도 반환값도 없음** — 전역 메모리로만 주고받음                                      |
| 복귀 명령어        | `ret` — 돌아갈 주소만 되돌림          | `iret` — 인터럽트 **전용** 복귀 명령어, 함께 밀어 넣어 둔 것까지 되돌림                      |
| 특권 수준·스택      | 보통 그대로 유지                    | 하드웨어를 직접 만져야 하므로 더 높은 특권 수준으로 올라가는 것이 보통이고, 스택도 별도로 쓸 수 있음(CPU마다 다름) |
| 잠시 막을 수 있는가   | 막을 수 없음 — 적혀 있으면 반드시 실행됨     | **막을 수 있음** — 인터럽트를 켜고 끄는 전용 기계 명령어가 있음                              |
| 직접 불러도 되는가    | 물론 됨                         | **직접 부르면 안 됨** — 처리기가 부르는 것을 전제로 만들어진 코드                             |

인자·반환값 항목의 이유도 같은 뿌리다. 보통 함수 호출은 레지스터와 스택을 통해 인자를 주고받는다. 인터럽트 처리 함수도 물리적으로는 같은 CPU의 같은 레지스터 위에서 돌지만, 애초에 값을 실어 줄 "부르는 쪽"이 없고, 게다가 자기가 건드린 레지스터는 나가기 전에 전부 원래대로 되돌려 놓아야 한다 — 레지스터에 결과를 남겨 봐야 복원 과정에서 지워진다. 그래서 인자도 반환값도 그 경로로는 오갈 수 없고, 결국 **전역 메모리를 통해서만** 데이터를 주고받게 된다. 부르는 쪽이 아예 없으니 넘겨줄 인자도, 돌려줄 대상도 없는 셈이다.

#### 4) 예시

**똑같은 일을 하는 코드가 '함수'일 때와 '인터럽트 처리 함수'일 때**

```c
/* (가) 보통 함수 — 프로그램이 직접 부른다 */
int add_one(int n) {
    return n + 1;              /* 인자를 받고, 값을 돌려준다 */
}

void main(void) {
    count = add_one(count);    /* <- 이 '호출하는 줄'이 소스에 적혀 있다 */
}
```

```c
/* (나) 같은 일을 하는 인터럽트 처리 함수(ISR) */
volatile int count;            /* 전역 변수로만 주고받는다 */

void keyboard_isr(void) {      /* 인자 없음, 반환값 없음 */
    count = count + 1;
}
```

두 코드가 하는 일은 "count를 1 늘린다"로 똑같다. 그런데 (가)는 `count = add_one(count);`라는 줄을 소스에서 **찾을 수 있다**. (나)는 프로그램 전체를 뒤져도 `keyboard_isr()`를 부르는 줄이 **어디에도 없다**. 그런데도 키를 누르면 실행된다. "부르는 줄이 없는데 실행되는 함수" — 이것이 두 방식의 차이를 가장 직관적으로 보여주는 장면이다. 그리고 바로 그 때문에 (나)는 인자도 반환값도 가질 수 없고, 값은 전역 변수 `count`를 거쳐야만 오간다.

**돌아가는 방식도 다르다.**

```asm
; (가) 함수 호출
    call  add_one     ; 돌아올 주소를 스택에 밀어 넣고 점프
    ...
add_one:
    ...
    ret               ; 밀어 넣어 둔 '돌아갈 주소'만 꺼내서 복귀
```

```asm
; (나) 인터럽트 처리 — 이 진입을 적은 줄이 소스 어디에도 없다
keyboard_isr:
    ...
    iret              ; 인터럽트 전용 복귀 명령어
```

`ret`은 `call`이 밀어 넣은 "돌아갈 주소"를 꺼내는 것이 전부다. 반면 인터럽트가 끼어들 때는 하드웨어가 돌아갈 주소 외에 플래그 같은 것까지 함께 밀어 넣어 두므로, **그것까지 한꺼번에 되돌리는 전용 명령어 `iret`이 따로 필요**하다. 즉 인터럽트 처리 함수는 보통 함수처럼 `ret`으로 끝낼 수 없다. 명령어 이름은 CPU마다 다르지만, "인터럽트에서 돌아오기 위한 전용 복귀 명령어"가 따로 있다는 점은 공통이다. 무엇이 저장되고 복원되는지의 구체적인 목록과 절차는 다음 소주제에서 다룬다.

#### 5) 다른 키워드와의 연결

* "저장할 것이 훨씬 많아진다"는 이 소주제의 결론이 곧바로 \*\*"중단된 프로그램의 실행 상태 저장과 복원"\*\*의 출발점이 된다(무엇을 어떻게 저장·복원하는지는 거기서).
* "부르는 줄이 없는데 어떻게 그 함수로 들어가는가"라는 남은 의문은 \*\*"CPU는 어떻게 인터럽트 신호를 감지할까?"\*\*가 답하고, 이렇게 강제로 불린 함수가 실제 입출력에서 무슨 일을 하는지는 \*\*"인터럽트 구동식 입출력"\*\*이 이어받는다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * System V AMD64 ABI에는 스택 포인터 바로 아래 128바이트를 함수가 마음대로 쓰는 "레드 존"이 있다. 그런데 GCC 문서는 이렇게 못 박는다 — "스택 전환 없이 인터럽트될 수 있는 코드는 반드시 `-mno-red-zone`으로 컴파일해야 한다. 하드웨어 설계상 인터럽트 핸들러가 레드 존을 건드릴 수밖에 없기 때문이다." 커널을 만들면서 이 플래그를 빠뜨리면 인터럽트가 남의 지역 변수를 조용히 덮어쓴다.
> * 이 차이가 워낙 근본적이라 컴파일러가 아예 언어 기능으로 흡수했다. GCC의 `__attribute__((interrupt))`를 붙이면 `RET` 대신 `IRET`으로 돌아가는 진입·복귀 코드가 자동 생성되고, Rust에도 `x86-interrupt`라는 전용 호출 규약이 있다.
> * 손으로 짠 어셈블리 래퍼는 "뭘 망가뜨릴지 모르니 전부" 저장하는 반면, 컴파일러가 지원하는 인터럽트 호출 규약은 그 핸들러가 실제로 건드리는 레지스터만 골라 저장·복원한다. 다만 LLVM은 MMX와 x87 부동소수점 레지스터까지는 보존해 주지 않는다는 알려진 구멍이 있다.

### 9. 중단된 프로그램의 실행 상태 저장과 복원

#### 1) 개념 정의

인터럽트가 걸린 순간, CPU가 진행 중이던 프로그램의 **실행 상태**(다음에 실행할 명령어의 주소, 플래그 레지스터, 계산 중이던 범용 레지스터 값들)를 스택에 밀어 넣어 두었다가 인터럽트 처리 함수(ISR)가 끝나면 그대로 되돌려 놓아, 원래 프로그램이 멈췄던 바로 그 명령어부터 아무 일도 없었다는 듯 이어 달리게 하는 장치다.

#### 2) 원리 설명

인터럽트 처리 함수는 별도의 CPU에서 도는 것이 아니라, 하던 일을 멈춘 프로그램이 쓰고 있던 **바로 그 CPU와 바로 그 레지스터들을 물려받아** 실행된다.&#x20;

그래서 인터럽트 처리 함수가 계산을 하려고 레지스터에 값을 쓰는 순간, 원래 프로그램이 거기 담아 두었던 값은 덮어써져 사라진다. \
인터럽트 처리 함수가 무언가를 건드리기 **전에** 원본을 안전한 곳으로 옮겨 두어야 하는 이유가 이것이고, 그 안전한 곳으로 쓰이는 것이 스택이다.

앞서 본 이유로 인터럽트는 저장해 두어야 할 것이 많은데, 이 소주제에서 중요한 것은 **정확히 무엇을 저장하고 어떤 순서로 되돌리느냐**다. \
지켜야 할 조건은 하나뿐이지만 매우 엄격하다 — 돌아온 프로그램은 **자기가 멈췄었다는 사실조차 눈치채지 못해야 하며**, 재개하는 순간 모든 레지스터가 멈추기 직전과 똑같은 값을 갖고 있어야 한다.&#x20;

하나라도 빠뜨리면 프로그램은 틀린 값으로 계산을 이어 가거나 엉뚱한 주소로 뛰어 그대로 망가진다.

#### 3) 세부 메커니즘

**(1) "실행 상태"는 무엇으로 이루어져 있나**

이 목록이 곧 저장·복원해야 할 대상이다.

* **프로그램 카운터(PC)** — 다음에 실행할 명령어의 주소. x86에서는 EIP(64비트에서는 RIP)에 해당한다. 이것이 없으면 처리를 끝내고도 어디로 돌아가야 할지 알 수 없다. x86에서는 "어느 코드 영역을 실행 중인가"를 가리키는 CS 레지스터가 EIP와 짝을 이루어야 복귀 주소가 완성되므로, 둘은 늘 함께 저장된다.
* **플래그 레지스터** — 직전 연산의 결과가 0이었는지, 자리올림이 났는지, 음수였는지 같은 조건 비트들의 모음. x86에서는 EFLAGS다. `if` 문이나 반복문의 분기는 이 비트들을 보고 방향을 정하므로, 비교 명령과 분기 명령 사이에서 인터럽트가 걸렸을 때 이 값이 틀어지면 프로그램이 아예 다른 갈림길로 간다.
* **범용 레지스터들** — 계산 중이던 중간값, 다루던 배열의 주소, 반복문 카운터 등이 들어 있다.
* **스택 포인터(SP)** — 스택의 현재 꼭대기 위치. 다만 아래 전제(같은 스택을 계속 쓰는 경우)에서는 스택 포인터를 스택에 따로 밀어 넣지 않는다. 밀어 넣은 것을 전부 꺼내고 나면 저절로 원래 위치로 돌아오기 때문이다. (스택을 바꿔 타는 경우라면 이야기가 달라져, 원래 스택의 위치를 어딘가 적어 두어야 한다.)

**(2) 하드웨어가 하는 몫과 소프트웨어가 하는 몫**

저장 작업은 한 주체가 다 하지 않고 **둘로 나뉜다**. 어디까지가 하드웨어 몫인지는 CPU 설계마다 다르며, 여기서는 x86의 32비트 보호 모드에서 **특권 수준이 바뀌지 않는 경우**(이미 커널 코드가 돌고 있을 때 인터럽트가 걸린 경우)를 기준으로 본다. 특권 수준이 바뀌면 스택 자체가 바뀌므로 하드웨어가 쌓는 것이 더 늘어나는데, 이 소주제는 그 경우는 다루지 않는다.

* **하드웨어가 자동으로 하는 부분**: CPU가 인터럽트를 받아들이는 그 순간, 명령어 한 줄 없이 일부가 스택에 쌓인다. x86에서는 EFLAGS, CS, EIP 세 개가 이 순서로 자동으로 밀려 들어간다. 하드웨어가 직접 할 수밖에 없는 이유는 분명하다 — 프로그램 카운터를 인터럽트 처리 함수 쪽 주소로 바꿔치기하려면, 원래 값을 그 전에 어딘가 치워 두어야만 하기 때문이다.
* **인터럽트 처리 함수가 직접 하는 부분**: 나머지는 인터럽트 처리 함수가 시작하자마자 `push` 명령어로 직접 저장한다. x86에서는 범용 레지스터들이 여기에 해당한다. (범용 레지스터 일부까지 하드웨어가 자동으로 쌓아 주는 CPU도 있다. 경계선의 위치는 아키텍처마다 다르지, 어느 한쪽이 전부를 맡는 것이 아니다.)

**(3) 순서: 쌓기 → 처리 → 거울상으로 꺼내기**

1. **하드웨어 자동 저장** — 플래그와 복귀 주소가 스택에 쌓인다.
2. **인터럽트 처리 함수 진입부** — 자기가 쓸 범용 레지스터들을 `push`로 마저 쌓는다.
3. **실제 처리** — 그제서야 본래 할 일을 한다.
4. **거울상으로 꺼내기** — 쌓아 둔 것을 **정확히 역순으로** `pop` 한다. 스택은 나중에 넣은 것이 먼저 나오는 구조이므로, 꺼내는 순서는 쌓은 순서의 거울상이어야 한다. 중요한 것은 "정해진 순서로 넣는 것"이 아니라 \*\*"넣은 순서를 그대로 뒤집어 꺼내는 것"\*\*이다.
5. **복귀 명령어** — 마지막으로 인터럽트 전용 복귀 명령어(x86의 `iret`)를 실행하면, 하드웨어가 자동 저장했던 부분이 한꺼번에 되돌아간다. 플래그가 복원되고 **프로그램 카운터가 원래 값으로 되돌아가는 순간**, 실행은 멈췄던 바로 그 명령어부터 이어진다.

여기서 놓치기 쉬운 점 하나. 거울상 규칙은 범용 레지스터들 사이에서만 성립하는 것이 아니라 **하드웨어 몫과 소프트웨어 몫 사이에서도 성립한다.** 나중에 쌓인 소프트웨어 저장분이 먼저 빠져나가고, 맨 처음 쌓인 하드웨어 저장분이 맨 마지막에 `iret` 한 번으로 빠져나간다. 저장이 "하드웨어 → 소프트웨어" 순이었으니 복원은 "소프트웨어 → 하드웨어" 순인 것이다.

#### 4) 예시

**스택에 무엇이 어떤 순서로 쌓이는가**

x86에서 인터럽트가 걸린 직후 스택이 변해 가는 모습이다. (스택은 위쪽이 높은 주소이고, 밀어 넣을수록 아래로 자란다.)

```
   [1] 인터럽트 직전        [2] 하드웨어 자동 저장 후    [3] ISR 진입부 push 후
   ────────────────         ────────────────────        ──────────────────
   높은 주소 ↑              높은 주소 ↑                  높은 주소 ↑

   (원래 프로그램이          (원래 프로그램이             (원래 프로그램이
    쓰던 스택 내용)           쓰던 스택 내용)              쓰던 스택 내용)
   ──────────── ← ESP        EFLAGS   ┐                   EFLAGS   ┐
                             CS       │ 하드웨어가         CS       │ 하드웨어 몫
                             EIP ←ESP ┘ 자동으로          EIP      ┘
                                                          EAX      ┐
                                                          ECX      │ ISR이 직접
                                                          EDX ←ESP ┘ push
   낮은 주소 ↓              낮은 주소 ↓                  낮은 주소 ↓
```

돌아올 때는 이 그림을 정확히 거꾸로 되감는다. `[3] → [2]`는 인터럽트 처리 함수의 `pop`들이, `[2] → [1]`은 `iret` 한 줄이 담당한다.

**인터럽트 처리 함수 진입부·종료부 코드**

```asm
interrupt_stub:
    ; 여기 도착했을 때 EFLAGS / CS / EIP 는 이미 스택 위에 있다.
    ; (CPU 하드웨어가 알아서 밀어 넣은 것 — 코드로 적을 필요가 없다)

    push eax        ; 여기서부터는 인터럽트 처리 함수가 직접 저장한다
    push ecx
    push edx

    call do_handle_interrupt    ; 실제 처리 작업

    pop  edx        ; push 한 순서의 정확한 역순으로 꺼낸다
    pop  ecx        ; (edx → ecx → eax)
    pop  eax

    iret            ; EIP / CS / EFLAGS 를 한 번에 되돌리고,
                    ; 멈췄던 바로 그 명령어부터 실행을 재개한다
```

구체적인 숫자로 따라가 보자. \
어떤 프로그램이 덧셈을 하다가 EAX에 중간 합 `1000`을 담아 둔 상태에서 인터럽트가 걸렸다고 하자. \
인터럽트 처리 함수가 키보드에서 읽은 키 코드 `0x1C`를 EAX에 써 버려도 상관없다. \
진입부의 `push eax`가 `1000`을 스택에 옮겨 두었기 때문에, 나가기 직전 `pop eax` 한 번으로 EAX는 다시 `1000`이 된다. `iret`이 프로그램 카운터를 되돌리면 원래 프로그램은 멈췄던 다음 명령어에서 여전히 `1000`을 보고 덧셈을 이어 간다. 자기가 잠시 멈췄다는 사실은 끝내 알지 못한다.

#### 5) 다른 키워드와의 연결

이 저장·복원이 확실하다는 보장이 있어야만 CPU가 입출력이 끝나기를 기다리지 않고 다른 일을 하러 가도 안전한데, 그 전체 그림은 "인터럽트 구동식 입출력"이 다룬다. 또 어느 순간 무엇을 근거로 이 저장이 시작되는지는 "CPU는 어떻게 인터럽트 신호를 감지할까?"가, 저장할 것이 왜 이렇게 많아지는지는 "인터럽트 처리와 함수 호출의 차이"가 맡는다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * 하드웨어가 쌓아 주는 프레임의 크기가 상황마다 다르다는 게 초보자를 가장 많이 잡는 함정이다. 일부 예외는 오류 코드를 한 칸 더 얹어 주는데, `IRET` 전에 그것을 걷어내지 않으면 스택이 어긋난 채로 복귀한다. GCC의 interrupt 속성이 오류 코드 인자를 받는 시그니처를 요구하고 `IRET` 직전에 그걸 빼내는 코드를 대신 넣어 주는 이유다.
> * 32비트 x86에는 범용 레지스터 8개를 명령어 하나로 통째로 밀어 넣고 꺼내는 `pusha`/`popa`가 있었다. 그런데 64비트 롱 모드에서는 이 명령어가 삭제되어, 그 오피코드(0x60/0x61)를 만나면 잘못된 명령어 예외(#UD)가 난다. 그래서 64비트 커널의 인터럽트 진입 코드는 `push`를 하나하나 나열한다.
> * ARM Cortex-M은 이 저장을 아예 하드웨어에 맡긴다. 예외가 발생하면 xPSR, PC, LR, R12, R3\~R0 여덟 개(32바이트)를 CPU가 자동으로 스택에 밀어 넣어 주기 때문에 핸들러를 평범한 C 함수로 써도 된다. 게다가 인터럽트가 연달아 걸리면 앞 핸들러의 복원과 뒤 핸들러의 저장을 통째로 건너뛰는 "테일 체이닝"이 작동해, Cortex-M3/M4에서는 핸들러 사이 전환이 일반 진입의 절반 수준인 6사이클까지 줄어든다.

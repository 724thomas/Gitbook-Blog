# 6.4. High Concurrency: Multiple IO

### 1. 파일 서술자

열어 놓은 파일을 가리키는 데 필요한 것은 결국 정수 하나뿐이라는 이야기.

#### 1) 개념 정의

파일 서술자(file descriptor)는 프로세스가 연 파일을 가리키기 위해 운영체제가 돌려주는 **정수 하나**이며, 프로그램은 이 숫자만 들고 있으면 그 파일을 읽고 쓸 수 있다.

#### 2) 원리 설명

유닉스 계열 운영체제는 "모든 것은 파일이다(Everything is File)"라는 추상화를 택했다\
디스크뿐 아니라 네트워크로 들어온 데이터, 터미널, 심지어 프로세스 사이의 통신 도구인 파이프까지 전부 파일로 취급한다. \
프로그래머 입장에서 파일이란 그저 N개의 바이트가 늘어선 것(b1, b2, b3, …, bN)일 뿐이므로, 대상이 무엇이든 "열고 → 읽거나 쓰고 → 닫는다"는 **한 벌의 인터페이스**로 모든 입출력을 처리할 수 있다.&#x20;

그렇다면 열어 놓은 그 파일을 프로그램은 무엇으로 지목할까? \
원글은 주말 식당의 대기 번호표를 든다 — 서빙 직원은 당신이 누구인지, 이름이 무엇인지 전혀 모르지만 **번호 하나만으로 당신을 찾아낼 수 있다**.&#x20;

파일도 똑같아서, 운영체제가 번호 하나를 발급하고 프로그램은 그 번호를 내밀기만 하면 된다. \
파일 서술자는 그저 숫자 하나일 뿐이지만 이 숫자를 통해 우리는 열린 파일을 조작할 수 있고, 그 번호 덕분에 프로세스는 파일에 대해 아무것도 모른 채로 지낼 수 있다 — 파일이 디스크의 어느 위치에 있는지, 메모리가 파일을 어떻게 관리하는지 같은 정보는 운영체제의 몫이고, 운영체제는 프로세스에게 파일 서술자 하나만 주면 충분하다.

#### 3) 세부 메커니즘

"왜 하필 정수 하나로 충분한가"를 한 단계 파고들면, 그 숫자가 임의로 붙인 이름표가 아니라 **목록의 몇 번째 칸이냐를 가리키는 번호**라는 데 답이 있다. \
`open`의 매뉴얼은 반환값을 이렇게 정의한다 — "작고 음수가 아닌 정수로, 그 프로세스의 열린 파일 서술자 테이블의 한 항목을 가리키는 **인덱스**". 여기서 세 가지가 따라 나온다.

1. **인덱스이므로 작은 정수면 된다.** 커널이 프로세스마다 "지금 열어 둔 파일 목록"을 유지하고 있으니, 프로그램이 파일 이름 문자열이나 디스크상의 주소를 들고 다닐 이유가 없다. 목록의 몇 번째 칸인지만 말하면 된다.
2. **그 목록은 프로세스마다 따로 있다.** 따라서 파일 서술자는 그 프로세스 안에서만 통하는 번호다. 다른 프로세스의 3번이 내 3번과 같은 파일이라는 보장은 없다(다를 수 있다).
3. **번호 발급 규칙이 있다.** 성공한 `open` 호출이 돌려주는 번호는 "그 프로세스에서 현재 열려 있지 않은 가장 작은 번호"다. 실패하면 대신 `-1`을 돌려준다.

프로그램은 시작하는 순간 이미 파일 서술자 세 개를 손에 쥐고 출발한다 — 관례상 **0번이 표준 입력, 1번이 표준 출력, 2번이 표준 오류**다.&#x20;

정확히 말하면 셸이 프로그램을 띄울 때마다 이 셋을 새로 여는 것이 아니라, **셸이 이미 열어 두고 있던 것을 자식 프로세스가 그대로 물려받는다.** \
어느 쪽이든 프로그램 입장에서 결과는 같아서, 앞의 "가장 작은 미사용 번호" 규칙과 맞물려 프로그램이 직접 여는 첫 번째 파일은 보통 **3번**을 받게 된다.

**번호를 만드는 창구는 `open` 하나가 아니다.** \
소켓을 만드는 `socket()`은 `open`과 똑같이 **반환값으로** 파일 서술자를 돌려주고, 파이프를 만드는 `pipe()`는 **인자로 받은 배열에 읽기용·쓰기용 파일 서술자 두 개를 채워 준다**(반환값은 성공 여부다). \
창구의 모양은 조금씩 달라도 나오는 물건은 같은 정수이고, `read()`·`write()`·`close()`는 그 출신을 따지지 않고 번호만 받는다. "모든 것은 파일이다"라는 추상화가 함수 시그니처 수준에서 실현된 지점이 바로 여기다.

#### 4) 예시

**예시 1 — 번호 하나만 주고받는 코드**

원글에 실린 형태는 요점만 남긴 축약형이다.

```c
int fd = open(file_name);
read(fd, buff);
```

실제로 컴파일되는 형태로 옮기면 이렇게 된다.

```c
#include <fcntl.h>
#include <unistd.h>

int main(void) {
    int  fd = open("hello.txt", O_RDONLY);   // 커널이 번호표를 발급 → 예: 3
    char buff[64];

    ssize_t n = read(fd, buff, sizeof(buff)); // "3번에서 읽어 줘"
    write(1, buff, n);                        // "1번(표준 출력)에 써 줘"
    close(fd);                                // "3번 다 썼어"
    return 0;
}
```

**작동 결과.** `hello.txt`에 `hello, fd!`가 들어 있다면 화면에 `hello, fd!`가 찍힌다. \
눈여겨볼 점은 이 코드가 파일의 정체를 언급하는 곳이 **맨 첫 줄 하나뿐**이라는 것이다. \
그 뒤로 오가는 것은 `fd`라는 정수 하나이고, 그 파일이 디스크의 몇 번 블록에 있는지, 커널이 읽어 온 내용을 어느 메모리에 담아 두었는지는 코드 어디에도 나타나지 않는다.

**예시 2 — 정수를 손으로 직접 써 보기**

```c
#include <unistd.h>

int main(void) {
    write(1, "hello\n", 6);   // 1번 = 표준 출력
    write(2, "oops\n",  5);   // 2번 = 표준 오류
    return 0;
}
```

**작동 결과.** \
터미널에 `hello`와 `oops` 두 줄이 그대로 출력된다. \
핵심은 **이 프로그램이 `open`을 한 번도 부르지 않았다**는 점이다. 셸에게서 물려받은 0·1·2가 이미 열려 있으므로, 우리가 한 일은 `1`과 `2`라는 **날것의 정수**를 함수에 건네준 것뿐이다. "파일 서술자는 그저 숫자 하나일 뿐"이라는 말이 문자 그대로 눈에 보이는 장면이다.

### 2. 다중 입출력을 어떻게 효율적으로 처리하는 것일까?

문제를 세우는 소주제 — 답을 주지 않고, 순진한 해법 셋이 각각 어디서 값을 치르는지까지만 본다.

#### 1) 개념 정의

서버 하나가 파일 서술자를 수천\~1만 개씩 손에 쥐고 있을 때 **그 전부를 무슨 수로 처리할 것인가**를 묻는 질문이며, 여기서 확인할 것은 답이 아니라 **누구나 먼저 떠올리는 해법 셋이 각각 왜 비싼가**이다.

#### 2) 원리 설명

높은 동시성이라는 말은 곧 서버가 상대하는 클라이언트가 하나가 아니라 수천\~수만이라는 뜻이고, 그만큼의 파일 서술자를 **동시에** 손에 들고 있다는 뜻이다. \
여기서 서버가 처한 곤란의 뿌리는 하나다 — **지금 그중 어느 것이 읽을 수 있는 상태이고 어느 것이 쓸 수 있는 상태인지를 서버는 모른다.**&#x20;

그런데 아직 준비되지 않은 상대에게 입출력을 시도하면 결과는 하나뿐이라, 프로세스가 그 자리에서 막혀 실행이 멈춰 버린다. \
"모른 채로 손을 뻗으면 멈춘다" — 이 두 사실이 맞물리면서 떠올릴 수 있는 해법이 셋으로 갈라진다: \
**A는 그냥 하나씩 순서대로 처리하는 것,** \
**B는 서술자마다 프로세스나 스레드를 하나씩 붙이는 것,** \
**C는 아예 막히지 않게 바꿔 놓고 루프를 돌며 전부 훑는 것이다.**&#x20;

셋 다 실제로 동작은 하는데, **비용이 서로 다른 자리에서 발생할 뿐 셋 모두 감당하기 어려운 값을 부른다**는 것이 이 소주제의 결론이다.

#### 3) 세부 메커니즘

**A — 비용은 CPU가 아니라 "다른 연결들의 대기 시간"으로 나온다.** \
서술자를 앞에서부터 하나씩 읽어 나가면, 데이터가 아직 오지 않은 서술자를 만나는 순간 프로세스 전체가 그 자리에 붙들린다.&#x20;

문제는 붙들려 있는 동안 **나머지 서술자들에게 이미 도착해 있는 데이터도 그대로 방치된다**는 점이다. 여기서 A의 병이 정확히 무엇인지가 드러난다 — 느린 것은 네트워크도 디스크도 아니고, **서버가 일을 처리하는 순서가 데이터가 준비된 순서와 아무 상관 없이 정해져 있다**는 것이다. \
준비된 순서대로 처리했다면 즉시 끝났을 일이, 루프의 앞자리에 놓인 조용한 연결 하나 때문에 뒤로 밀린다. \
그리고 이때 CPU는 바쁜 것이 아니라 **아무 일도 못 하고 정지해 있다** — 비용이 CPU 사용률이 아니라 처리량 0과 지연으로 나타나기 때문에, 자원 사용량만 봐서는 문제가 보이지도 않는다.

**B — 비용은 "연결 수"에 비례해서 세 갈래로 붙는다.** \
막히는 게 문제라면 막혀도 되는 실행 흐름을 연결마다 하나씩 주면 된다. 그런데 이 방식은 값을 세 군데에서 따로 낸다.

* **① 만들고 없애는 값.** \
  연결이 수만 개면 스레드도 수만 개를 만들고 없애야 하고, 연결이 짧고 잦을수록 **본 작업보다 스레드를 만들고 정리하는 일이 더 커진다.** \
  원글이 "대량으로 스레드를 만들고 없애는 것은 시스템 성능에 심각한 영향을 준다"고 못 박는 자리가 여기다.
* **② 붙들고 있는 값.** \
  실행 흐름 하나에는 자기만의 **호출 스택**이 하나씩 딸려 온다. \
  연결이 늘면 스택 개수가 그대로 따라 늘고, 그 스레드가 데이터를 기다리며 멈춰 있는 동안에도 그 자리는 계속 잡혀 있다. \
  스택 하나를 1 MB로 잡으면 연결 1만 개는 **요청을 단 한 바이트도 처리하기 전에 이미 약 10 GB**이고, 256 KB로 줄여 잡아도 2.5 GB다(스택 크기는 시스템·언어마다 크게 다르므로 **자릿수 감각을 위한 어림값**). \
  **다만 이 10 GB를 물리 메모리 10 GB로 읽으면 안 된다** — 스택 크기는 "여기까지 쓸 수 있다"고 **미리 잡아 두는 주소 공간의 크기**이고, 실제 물리 메모리는 그 스레드가 **실제로 건드린 만큼만** 채워진다. \
  대신 스레드 하나마다 커널 쪽에도 자기 몫의 살림살이가 따라붙는데, **이쪽은 예약이 아니라 실제로 쓰는 메모리**이고 스레드 수에 그대로 비례한다. \
  그래서 실제로 데이터를 주고받는 스레드가 100개뿐이어도 나머지 9,900개어치의 자리 예약과 커널 쪽 몫은 그대로 나간다.
* **③ 갈아 끼우는 값.** \
  CPU 개수는 그대로인데 스레드만 수만 개가 되면, 하나의 CPU 위에서 실행 흐름을 갈아 끼우는 일이 계속 벌어진다. 그런데 **갈아 끼우는 그 자체는 어떤 요청도 처리하지 않는 순수 부대비용**이다. \
  교환 한 번을 5 µs로, 초당 1만 번이 일어난다고 잡으면 0.05초 — **CPU 시간의 5%가 요청 처리가 아니라 실행 흐름을 갈아 끼우는 데만** 쓰인다는 뜻이고(역시 어림값), 스레드가 많아질수록 이 비율은 오르기만 한다.

세 갈래를 관통하는 것은 하나다 — **값이 "실제로 데이터가 오간 연결 수"가 아니라 "들고 있는 연결 수"에 붙는다.** 1만 개 중 실제로 바쁜 것이 100개뿐이어도 값은 1만 개어치를 낸다.

**C — 막힘은 사라지지만, 그 자리에 헛수고가 들어온다.** \
서술자를 논블로킹으로 바꿔 두면 아직 데이터가 없는 서술자를 읽어도 멈추지 않고 "지금은 없다"는 답이 즉시 돌아온다. A의 병은 이걸로 사라진다.&#x20;

대신 이제 **서버가 직접 1만 개를 한 바퀴씩 계속 훑어야 한다.** 여기서 6.1에서 이미 세운 계산식이 그대로 따라오는데, **곱셈의 두 항이 통째로 바뀐다는 것이 새로운 지점**이다.

* **앞 항이 커진다.** \
  예전에는 한 바퀴가 상태 비트 하나를 보는 일이었지만, 지금은 **한 바퀴가 곧 서술자 1만 개어치의 확인**이다.
* **한 번의 확인이 비싸진다.** \
  데이터가 도착했는지를 아는 쪽은 서버 프로그램이 아니라 **커널**이다. \
  그래서 서술자 하나를 확인하는 일이 프로그램 안에서 변수를 들여다보는 일이 아니라 **매번 커널에 물어보러 넘어갔다 돌아오는 일**이 된다. 확인 1만 번은 곧 커널 왕복 1만 번이다.
* **비율이 최악이다.** \
  준비된 서술자가 몇 개 없을 때도 훑는 개수는 언제나 1만 개다. **값이 "준비된 개수"가 아니라 "가진 개수"에 비례하기 때문에, 한가할수록 헛수고의 비율이 오히려 높아진다.**
* **간격을 벌려도 저울이 반대로 기울 뿐이다.** \
  검사를 뜸하게 하면 CPU는 아끼지만 이미 도착해 있는 데이터가 다음 바퀴까지 방치되어 응답이 늦어진다. 6.1에서 본 저울이 서술자 1만 개 위에서 그대로 다시 나타난다.

**셋을 나란히 놓으면** \
A는 값을 **지연**으로, \
B는 **메모리와 부대비용**으로, \
C는 **헛도는 CPU**로 낸다.&#x20;

내는 곳은 다르지만 원인은 하나로 모인다 — 셋 모두 **어느 서술자가 준비되었는지 모르는 채로** 움직이고 있고, 그래서 각자 다른 방식으로 헛일을 한다. **그래서 다른 방법이 필요하다.**

#### 4) 예시

**예시 1 — 블로킹 루프에서 실제로 굶는 연결**

```c
int fds[10000];        /* 서버가 들고 있는 연결 1만 개 */
char buf[4096];

while (1) {
    for (int i = 0; i < 10000; i++) {
        int n = read(fds[i], buf, sizeof(buf));  /* ← 데이터가 없으면 여기서 멈춘다 */
        handle(buf, n);
    }
}
```

`fds[0]`은 사용자가 화면만 보고 있는 조용한 연결이고, `fds[7]`은 요청을 방금 보낸 연결이며, 그 사이의 `fds[1]`\~`fds[6]`은 마침 데이터가 준비되어 있어 곧바로 처리된다고 하자.

| 시각            | `fds[0]`                    | `fds[7]`                      | 서버가 실제로 한 일  |
| ------------- | --------------------------- | ----------------------------- | ------------ |
| 0.000초        | `read` 호출 → 데이터 없음 → **정지** | —                             | 없음 (프로세스 멈춤) |
| 0.001초        | 여전히 정지                      | **요청 도착. 커널까지 이미 들어와 있음**     | 없음           |
| 0.002\~2.999초 | 여전히 정지                      | 읽히기를 기다림                      | 없음           |
| 3.000초        | 1바이트 도착 → `read` 반환         | 계속 대기                         | `fds[0]` 처리  |
| 3.000초+       | —                           | 루프가 `fds[1]`\~`fds[6]`을 지나 도달 | `fds[7]` 처리  |

`fds[7]`의 데이터는 **0.001초에 이미 도착해 있었다.** 3초 늦어진 이유는 네트워크가 느려서도, CPU가 모자라서도 아니고 **서버가 `fds[0]` 앞에 서 있었기 때문**이다. 그 3초 동안 CPU 사용률은 사실상 0이었다 — 놀고 있는 CPU와 굶고 있는 연결 9,999개가 동시에 존재한다. 그리고 이건 낙관적으로 잡은 경우다. 앞자리에 조용한 연결이 하나만 더 있어도 서버는 거기서 또 멈춰 서고, **`fds[7]`의 대기 시간은 그만큼 다시 늘어난다** — 굶는 시간은 데이터가 도착한 시점이 아니라 **자기 앞에 몇 개의 조용한 연결이 놓여 있느냐**로 정해진다.

**예시 2 — 논블로킹으로 바꾸고 전수 순회하기**

```c
for (int i = 0; i < 10000; i++)
    set_nonblocking(fds[i]);          /* 이제 read는 멈추지 않는다 */

while (1) {
    for (int i = 0; i < 10000; i++) {
        int n = read(fds[i], buf, sizeof(buf));
        if (n < 0 && errno == EAGAIN)
            continue;                  /* "아직 데이터 없음" → 그냥 넘어간다 */
        handle(buf, n);
    }
}
```

이제 굶는 연결은 없다. 그런데 준비된 연결이 3개뿐인 순간을 보면 **한 바퀴에 `read` 1만 번 중 9,997번이 `EAGAIN`만 받고 돌아온다.** 게다가 `read` 한 번 한 번이 커널까지 넘어갔다 오는 호출이라, 헛친 9,997번도 전부 값을 치른 왕복이다.

**수치로 보기** (한 바퀴가 1 ms에 끝난다고 **가정**했을 때의 어림값):

|                         | 한 바퀴       | 1초 동안       |
| ----------------------- | ---------- | ----------- |
| `read` 호출 횟수            | 10,000회    | 1,000만 회    |
| 그중 헛친 횟수(준비된 fd가 3개일 때) | 9,997회     | 약 999만 7천 회 |
| 헛수고 비율                  | **99.97%** | 99.97%      |

이 표에서 흔들리지 않는 것은 **헛수고 비율 99.97%** 하나뿐이다. 이 값은 "1만 개 중 3개만 준비됨"에서 곧바로 나오므로 한 바퀴가 얼마나 걸리든 그대로다. 반면 **1,000만 회**와 **3,000건**은 "한 바퀴 = 1 ms"라는 가정에 통째로 매달려 있다. 한 바퀴에 `read`를 1만 번 부르므로 1 ms는 커널 왕복 한 번을 100 ns로 잡은 셈인데, 실제 왕복은 이보다 여유 있게 드는 것이 보통이다. 그러니 절대 수치는 "이 정도 자릿수"로만 읽고 **비율 쪽만 결론으로 가져가면 된다**.

CPU 사용률은 100%인데, 실제로 처리한 요청은 초당 3,000건어치다. **A에서는 CPU가 0%인 채로 아무 일도 못 했고, C에서는 CPU가 100%인 채로 거의 아무 일도 못 한다.**

#### 5) 다른 키워드와의 연결

여기서 전제로만 쓴 "파일 서술자가 아주 많다"의 **파일 서술자**가 무엇인지는 바로 앞 소주제가, 검사 비용과 응답 지연이 이루는 저울의 기본형은 6.1의 **폴링**이 이미 다뤘다. 세 해법이 공통으로 걸려 넘어진 지점 — **어느 서술자가 준비되었는지 서버가 알 수 없다** — 을 어디서부터 풀 것인지가 다음 소주제부터 이어진다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **문맥 교환 비용을 단일 숫자로 외우면 절반만 아는 것이다.** lmbench 논문(McVoy·Staelin, USENIX 1996)은 **같은 기계**에서 두 값을 나란히 쟀는데, 프로세스 2개가 캐시를 거의 건드리지 않을 때 **6 µs**, 프로세스 8개가 각자 32KB를 주무를 때 **101 µs**였다 — 17배 차이가 오직 작업 집합 크기에서 나왔다. 그 기계의 2차 캐시가 256KB이고 8×32KB가 정확히 그 크기라는 점이 핵심으로, 스레드를 늘릴 때 진짜 비싼 것은 교환 그 자체가 아니라 **교환이 쓸어버리는 캐시**다.

### 3. 상대방이 아닌 내가 전화하게 만들기

발상만 다루는 소주제 — 지금까지 왜 방향이 거꾸로 서 있었는지까지만 보고, 이름과 절차는 다음으로 넘긴다.

#### 1) 개념 정의

파일 서술자가 준비됐는지를 **아는 쪽은 커널인데 정작 모르는 쪽인 응용 프로그램이 계속 묻고 있었다**는 비대칭을 알아차리고, 묻는 방향을 거꾸로 세워 **아는 쪽이 알리게** 만드는 발상의 전환이다.

#### 2) 원리 설명

원글은 이 발상을 판촉 전화에서 끌어온다. \
하루에 판촉 전화를 여덟 통 열 통 받으면 몸이 축나는데, 원글이 짚는 이 장면의 핵심은 **거는 쪽이 당신에게 살 마음이 있는지 없는지를 모른다**는 것, 그리고 **모르니까 한 번 또 한 번 물어보는 수밖에 없다**는 것이다.&#x20;

그러니 더 나은 방법은 그들이 걸게 두지 말고 번호를 적어 두었다가 **필요할 때 내가 거는 것**이다 — "나한테 전화하지 마, 필요하면 내가 걸게." \
입출력이 정확히 이 모양이었다. \
준비 여부를 아는 쪽은 커널인데, 모르는 쪽인 응용 프로그램이 자기가 쥔 서술자를 하나씩 들고 커널에게 물으러 다니고 있었던 것이다(앞 소주제의 해법 셋이 공통으로 걸려 넘어진 바로 그 지점이다). \
방향을 거꾸로 세우면 응용 프로그램은 원글의 표현대로 "바쁜 **능동**"에서 "한가한 **피동**"으로 바뀐다 — 원글이 그 자리에 덧붙이는 말이 이 발상의 정서를 그대로 담고 있다.&#x20;

"**어차피 어느 장치가 준비됐는지는 커널이 알려 줄 텐데, 게으름을 피울 수 있다면 굳이 그렇게 부지런할 이유가 없다.**"

#### 3) 세부 메커니즘

그런데 왜 하필 응용 프로그램이 모르는 쪽인가. 이걸 파고들면 뒤집기가 실제로 무엇을 없애는 일인지도 같이 드러난다.

**(가) "모른다"는 것은 사고가 아니라 설계다.** \
데이터가 도착하는 사건은 장치에서 커널로 이어지는 쪽에서 시작해 커널 안에서 끝난다(그 경로는 6.1·6.2에서 본 그대로다). \
그동안 응용 프로그램의 주소 공간에서는 아무 일도 일어나지 않는다 — **지금 우리가 다루는 방식, 곧 소켓을 `read`/`write`로 직접 읽고 쓰는 모델에서는** 데이터가 도착해도 프로그램이 가진 변수는 하나도 바뀌지 않으니, 자기 안을 아무리 들여다봐도 알아낼 방법이 없다.&#x20;

그런데 이건 운영체제가 뭔가를 감춰서 생긴 사고가 아니다. \
앞서 파일 서술자 소주제에서 본 대로 **파일 서술자를 쥐어도 프로세스는 그 파일에 대해 아무것도 모르며, 원글은 그런 정보는 운영체제 소관이라 프로세스가 신경 쓸 필요가 없다고 말한다.** \
"신경 쓸 필요가 없다"가 이 추상화가 준 이득이라면, "스스로는 알아낼 방법이 없다"는 같은 동전의 뒷면이다. \
응용 프로그램은 **모르도록 만들어졌고**, 그 대가로 앎에 이르는 통로가 딱 하나 — 커널에게 묻는 것 — 만 남는다. \
모르는 쪽이 아는 쪽에게 계속 물어보는 구조는 그래서 생긴 것이다.

**(나) 그래서 헛된 질문의 비율을 정하는 것은 부지런함이 아니다.** \
아는 쪽에서 아무 단서도 받지 못하니 후보를 좁힐 수가 없고, 좁힐 수 없으니 매번 전부에게 똑같이 묻는 수밖에 없다. \
앞 소주제가 세어 본 대로 1만 개 중 준비된 것이 3개뿐이면 질문의 99.97%가 "아니오"를 받자고 건 질문이 된다. \
여기서 이 소주제가 새로 물을 것은 **왜 하필 그 비율인가**이다.&#x20;

답은 프로그램이 게을러서가 아니고, 더 영리하게 물으면 줄어드는 것도 아니다 — **어느 질문이 헛것인지 미리 골라내려면 바로 그 앎이 있어야 하는데, 그게 없어서 묻고 있는 것이기 때문이다.** \
모르는 쪽이 묻는 구조에서 헛됨의 비율은 묻는 쪽의 노력이 아니라 **무지 그 자체**로 정해진다.

**(다) 뒤집기가 없애는 것은 '아는 비용'이 아니라 '앎이 경계를 넘는 횟수'다.** \
방향을 거꾸로 세워도 커널이 **새로 알아내야 할 것은** 없다. \
준비됐다는 사실은 커널이 따로 **알아낸** 것이 아니라 자기가 그 일의 당사자라서 이미 손에 쥐고 있는 것이고, 뒤집힌 뒤에도 그건 그대로다.&#x20;

그러니 이 뒤집기의 이득은 커널이 사실을 새로 알아내 주는 데서 나오는 것이 아니다 — 달라지는 것은 **이미 있는 그 앎이 경계를 몇 번 건너느냐**다. (지켜보는 일을 넘겨받은 커널이 그 일을 얼마나 싸게 해내느냐는 또 다른 문제.)&#x20;

헛된 질문이 통째로 사라지는 이유도 여기서 나온다 — 질문이 빨라져서가 아니라 **질문이라는 행위 자체가 필요 없어지기 때문**이다. \
아는 쪽은 자기 자신에게 물어볼 필요가 없다. (다만 "알려 준다"를 커널이 내 코드를 대신 불러 준다는 뜻으로 읽으면 안 된다 — 그 알림이 실제로 어떤 형태로 오는지는 다음 소주제가 다룬다.)

#### 4) 예시

**예시 1 — 뒤집기 전, 그리고 뒤집은 뒤의 한마디**

뒤집기 전. 원글은 이 장면을 응용 프로그램이 커널에게 **기어들어가는 목소리로 묻는(`弱弱的问`)** 모습으로 그린다.

```
# 뒤집기 전 — 모르는 쪽이 하나하나 묻는다
묻는다("1번 파일 서술자, 읽고 쓸 수 있나요?")     # 아니오
묻는다("2번은요?")                                # 아니오
묻는다("3번은요?")                                # 아니오
...
묻는다("10000번은요?")                            # 여기까지 와야 한 바퀴가 끝난다
```

쓸 만한 답은 몇 개 안 되는데, **어느 것이 쓸 만할지 미리 알 수 없어서** 1만 개를 다 물었다.

뒤집은 뒤. 원글에서 태도가 뒤집히는 자리는 **패기 있게 알리는(`霸气的告诉`)** 한마디다.

```
# 뒤집은 뒤 — 묻기를 그만두고, 명단을 통째로 넘긴다
넘긴다([1번, 2번, 3번, ..., 10000번])
  # "여기 1만 개가 있으니, 읽고 쓸 수 있는 게 생기면 그때 알려 줘, 내가 처리하게."
```

물음표가 1만 개에서 0개가 됐다. 그리고 마지막 "**내가 처리하게**"가 이 뒤집기가 어디까지인지를 그어 준다 — 뒤집힌 것은 **묻는 방향**이지 일하는 주체가 아니다. 이 두 줄 뒤에 실제로 무슨 일이 벌어지는지는 다음 소주제의 몫이다.

**예시 2 — 원글의 전화 장면과 대응표**

원글이 그리는 장면은 이렇다. 판촉원들이 하루 종일 당신에게 전화를 걸어 댄다. 거는 쪽은 당신이 살 마음이 있는지 없는지를 모르니 한 번 더, 또 한 번 더 걸어 볼 수밖에 없다. 그래서 당신이 말한다 — **"나한테 전화하지 마. 번호는 적어 뒀으니 필요하면 내가 걸게."**

원글이 직접 밝힌 대응 관계에, 이 소주제가 파고든 비대칭을 나란히 놓으면 이렇게 된다.

| 전화 장면            | 입출력         | 아는 쪽 / 모르는 쪽                    |
| ---------------- | ----------- | ------------------------------- |
| 전화를 받던 **당신**    | **커널**      | 살 마음이 있는지 **아는 쪽** = 준비됐는지 아는 쪽 |
| 계속 걸어 대던 **판촉원** | **응용 프로그램** | **모르는 쪽** — 그래서 계속 묻는 쪽         |
| **전화번호**         | **파일 서술자**  | 걸 수는 있지만, 상대의 상태는 담겨 있지 않다      |
| 당신과 전화로 소통하는 것   | **입출력**     |                                 |

그러니 소제목의 "내가"는 **커널의 목소리**다. 뒤집히고 나면 응용 프로그램은 거는 쪽에서 받는 쪽으로 옮겨 앉는다.

**다만 비유와 실제 그림은 한 군데에서 어긋난다.** 원글의 비유에서는 **여러 판촉원이 한 사람에게** 걸지만, 원글이 몇 문장 뒤에 적는 실제 장면은 **하나의 응용 프로그램이 커널에게 "1번 되나요? 2번은요? 3번은요?"를 차례로 묻는** 모습이다. 비유 쪽은 거는 쪽이 여럿이고 받는 쪽이 하나인데, 실제로는 양쪽 다 하나이고 여럿인 것은 **전화번호(파일 서술자)** 다. 비유에서 사람 수로 표현된 다수를 **번호 개수의 다수**로 옮겨 읽으면 비유가 제자리를 찾는다.

#### 5) 다른 키워드와의 연결

이 발상은 "어느 서술자가 준비되었는지 알 수 없다"를 정면으로 겨눈 답의 방향이고, 커널에게 넘기는 명단의 원소 하나하나가 이 절 첫 소주제의 **파일 서술자**다. \
여기까지가 발상이며, **이 발상에는 이름이 필요하다**

### 4. 입출력 다중화

앞 소주제가 제시한 발상에 **이름을 붙이고 정의를 세우는** 자리다.

#### 1) 개념 정의

입출력 다중화(I/O multiplexing)는 여러 개의 파일 서술자를 **한 번의 함수 호출로 커널에 맡겨 놓고 기다렸다가**, 그 함수가 반환될 때 그중 입출력이 가능해진 것이 무엇인지 알아내어 그것들만 처리하는 방식이다.

#### 2) 원리 설명

앞에서 우리는 "내가 서술자를 하나하나 붙잡고 물어보는 방식"으로는 여러 입출력을 감당할 수 없다는 문제를 확인했다. 그 해법에 붙은 이름이 입출력 다중화이며, 원글은 이것을 다음 **세 단계의 과정**으로 정의한다.

1. **파일 서술자 한 뭉치를 확보한다.** \
   네트워크와 관련된 것이든 디스크 파일과 관련된 것이든, 어떤 파일 서술자라도 상관없다.
2. **어떤 함수를 호출해 커널에게 말한다** — \
   "이 함수, 너는 일단 반환하지 마라. 나 대신 이 서술자들을 감시하고 있다가, 이 뭉치 중에 입출력 읽기·쓰기 작업을 할 수 있는 것이 생기면 그때 반환해라."
3. **그 함수가 반환되면**, \
   어떤 파일 서술자가 입출력을 할 수 있는 상태인지 알게 된다.

여기서 결정적인 것은 **블로킹이 사라지지 않았다**는 점이다 — 프로그램은 여전히 자기가 부른 함수 안에서 멈춰 서서 기다리며, 달라진 것은 **기다림의 대상**뿐이다. \
예전에는 서술자 하나에 대해 한 번씩 블로킹했다면, 이제는 **서술자 집합 전체에 대해 단 한 번 블로킹한다.**&#x20;

그래서 실행 흐름 하나(프로세스 하나, 스레드 하나)가 아주 많은 수의 입출력을 동시에 들고 있을 수 있게 된다. \
이런 일을 해 주는 함수로 예를 들어 `select` 같은 것이 있다.

#### 3) 세부 메커니즘

**(1) 세 단계 각각의 입력과 출력**

| 단계         | 프로그램이 넣는 것 (입력)                       | 프로그램이 받는 것 (출력)      | 이때 프로그램은       |
| ---------- | ------------------------------------- | -------------------- | -------------- |
| ① 뭉치 확보    | 지금까지 열어 둔 파일 서술자들                     | 감시 대상 집합 하나          | 실행 중           |
| ② 대기 함수 호출 | 그 집합 + "읽기를 볼지 쓰기를 볼지" + **얼마나 기다릴지** | **아직 없음** — 반환하지 않는다 | **멈춰 있음(블로킹)** |
| ③ 함수 반환    | (없음)                                  | 입출력이 가능해진 서술자들       | 다시 실행          |

②에 "얼마나 기다릴지"를 함께 넘길 수 있다는 점도 짚어 두자. 무기한으로 두면 위 설명 그대로 준비된 것이 생길 때까지 반환하지 않지만, 시간을 정해 두면 **아무것도 준비되지 않은 채로 반환될 수도 있다**. 이 노트의 예시는 전부 무기한 대기를 가정한다 — 뒤에 나올 코드에서 `select(…, NULL)`의 마지막 `NULL`과 `epoll_wait(…, -1)`의 `-1`이 바로 그 "무기한"이다.

②에서 프로그램이 커널에 넘기는 것은 **"감시해 달라는 대상 목록"이지 작업 지시가 아니다.** 커널에게 "읽어 놔라"라고 시키는 것이 아니라 "읽을 수 있게 되면 알려 달라"고 부탁하는 것이다. 그리고 그 알림은 **함수의 반환이라는 형태로만** 온다 — 커널이 내 프로그램의 코드를 대신 실행해 주는 것이 아니다. 프로그램은 자기가 부른 함수 안에서 잠들어 있다가, 그 함수가 값을 돌려주며 깨어난다.

**(2) 반환 후 프로그램이 아는 것과 여전히 모르는 것**

| 반환 뒤 **아는 것**                          | 반환 뒤 **여전히 모르는 것**                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------- |
| 감시를 맡긴 서술자들 중 지금 입출력을 할 수 있는 것이 어느 것인지 | 그 서술자에 **몇 바이트**가 와 있는지                                                               |
| 그래서 어느 것부터 읽기·쓰기를 **시도해 볼지**           | 한 번 읽으면 다 비워지는지, 아직 남는지                                                               |
|                                        | 보고되지 않은 나머지 서술자들이 **지금** 어떤 상태인지 (커널이 살펴본 그 순간에 준비되지 않았다는 것까지만 알 뿐, 그 직후에 준비됐을 수도 있다) |
|                                        | 다음번에는 어느 것이 준비될지                                                                      |

다만 "보고됐다"가 "절대 안 멈춘다"의 보증은 아니다. `select`의 man page는 소켓이 **읽기 가능하다고 보고됐는데도 뒤이은 `read`가 멈추는** 경우가 있다고 적어 두고(도착한 데이터가 검사에서 걸러져 버려지는 경우 등), 그래서 "멈추면 곤란한 소켓은 논블로킹으로 열어 두는 편이 안전하다"고 권한다. 쓰기 쪽도 마찬가지여서, 쓰기 가능하다고 보고된 소켓에 버퍼 여유보다 큰 덩어리를 한 번에 쓰면 그 자리에서 멈출 수 있다. **다중화와 논블로킹을 늘 같이 쓰는 이유가 이것이다.**

즉 대기 함수는 **데이터를 가져다주지 않는다.** \
"언제 읽으면 되는가"라는 타이밍 정보만 준다. \
실제로 읽고 쓰는 일은 ③ 이후에 프로그램이 자기 손으로 한다. 그리고 위 오른쪽 칸이 비어 있기 때문에, 프로그램은 ①\~③을 **한 번 하고 끝내는 것이 아니라 반복해서 돌게 된다** — 이번 반환에서 알아낸 사실은 이번 순간에만 유효하기 때문이다.

**(3) 블로킹의 위치가 옮겨 간다**

```
[다중화 없이]                       [입출력 다중화]

read(fd_3)   ← 여기서 멈춤          감시하며_기다린다({fd_3, fd_7, ...})
   ↑                                        ↑
   이 사이에 fd_7이 준비돼도               어느 하나라도 준비되면 반환
   알 수 없다                              → 준비된 것들을 알려 준다
```

왼쪽에서 블로킹의 단위는 **서술자 하나**다. 그래서 서술자가 N개면 기다리는 지점도 N개가 되고, 실행 흐름 하나로는 그중 한 곳에서만 기다릴 수 있다. 오른쪽에서 블로킹의 단위는 **집합 전체**다. 기다리는 지점이 하나로 합쳐졌으므로 실행 흐름 하나로 충분해진다.

**(4) 그런데 여기서 "다중화되는" 것은 무엇인가**

`multiplexing`은 원래 통신 분야에서 쓰던 말이다. 통신 회선을 충분히 활용하려면 **하나의 채널에 여러 갈래의 신호를 실어 보내고** 싶은데, 그러려면 그 여러 갈래를 한 갈래로 결합해야 한다. \
여러 갈래 신호를 하나의 신호로 합치는 장치를 **multiplexer**라 하고, 받는 쪽에서 그 합쳐진 신호로부터 원래의 여러 갈래를 복원하는 장치를 **demultiplexer**라 한다. 이렇게 하는 목적은 희소한 자원(전선 한 가닥, 회선 하나)을 여럿이 나눠 쓰기 위해서다.

#### 4) 예시

**예시 — 세 단계를 그대로 따라가는 서버**

연결 1만 개를 들고 있는 서버가 있다고 하자.

```python
# ① 파일 서술자 한 뭉치를 확보한다
감시집합 = [fd_3, fd_4, fd_5, ... , fd_10002]   # 서술자 10,000개

while True:
    # ② 어떤 함수를 호출해 커널에게 맡기고 기다린다
    #    "반환하지 말고, 이 중에 읽을 수 있는 게 생기면 그때 반환해라"
    #    ↓ 이 줄에서 프로그램이 멈춘다 (블로킹)
    준비된_것들 = 감시하며_기다린다(감시집합, 읽기)

    # ③ 반환됐다 = 준비된 것이 생겼다는 뜻이다
    #    이제 어느 서술자가 읽기 가능한지 알 수 있다
    for fd in 준비된_것들:          # 이번 반환에서는 3개였다
        데이터 = read(fd)           # 여기서는 멈추지 않는다
        처리(데이터)
    # 다시 while 위로 → ②로 돌아가 또 기다린다
```

**작동 결과를 숫자로 세어 보면**

| 항목                | 값                        |
| ----------------- | ------------------------ |
| 들고 있는 파일 서술자      | 10,000개                  |
| 이번 바퀴에서 블로킹한 횟수   | **1회** (`감시하며_기다린다` 한 줄) |
| 그 1회가 커버한 서술자     | 10,000개 전부               |
| 반환값에 담겨 온 서술자     | 3개                       |
| 실제로 `read`를 부른 횟수 | **3회**                   |
| 나머지 9,997개에 건 호출  | **0회**                   |
| 이 일을 한 실행 흐름      | **1개**                   |

핵심은 마지막 두 줄이다. 준비되지 않은 9,997개에는 **아예 손을 대지 않는다** — **응용 프로그램이 거는 `read` 호출에 관한 한** 헛수고가 0이다. 커널이 뒤에서 그 1만 개를 어떻게 지켜보는지, 그 일에 값이 얼마나 드는지는 이 표에 잡히지 않는다. 그 값이 실제로 얼마인지는 구현마다 다르고, 그건 다음 소주제가 다룬다. 그리고 이 모든 일을 스레드 하나가 한다. 만약 다중화 없이 서술자 하나마다 블로킹 읽기를 걸었다면, `read(fd_3)`에서 멈춰 있는 동안 `fd_7`이 준비되어도 알 방법이 없었을 것이다.

한 가지 더 눈여겨볼 점 — 반환값이 3개였다는 사실은 **이번 바퀴에 대해서만** 참이다. 다음 바퀴에서는 0개일 수도, 500개일 수도 있다. 그래서 이 구조는 반드시 반복문 안에 놓인다.

#### 5) 다른 키워드와의 연결

②단계의 "**어떤 함수**"가 실제로 무엇인지, 즉 리눅스가 제공하는 구체적인 함수들과 그 차이는 바로 다음 소주제 "삼총사: `select`, `poll`, `epoll`"이 다룬다. \
(①단계에서 뭉치로 모으는 그 "파일 서술자"의 정체는 첫 소주제가 이미 설명했다.)

### 5. 삼총사: select, poll, epoll

이름 붙은 방식을 리눅스가 실제 시스템 콜로 구현해 놓은 셋, 그리고 그 셋을 가르는 차이.

#### 1) 개념 정의

`select`, `poll`, `epoll`은 리눅스가 입출력 다중화를 실제로 수행하려고 제공하는 세 개의 시스템 콜이며, 셋은 골라 쓰는 대등한 대안이 아니라 **select → poll → epoll 순서로 앞의 것이 남긴 비효율을 하나씩 걷어낸 개선의 계보**다.

#### 2) 원리 설명

가장 오래된 `select`가 남긴 문제는 네 가지다. \
① 감시할 수 있는 파일 서술자가 `FD_SETSIZE`라는 컴파일 시점 상수(리눅스에서 1024)에 묶여 있고, \
② 넘긴 집합을 커널이 제자리에서 고쳐 돌려주기 때문에 루프를 돌 때마다 집합을 처음부터 다시 채워야 하며, \
③ 감시 집합을 **호출할 때마다** 사용자 공간에서 커널로 넘겨야 하고, \
④ 돌아오는 것이 "몇 개가 준비됐다"는 개수뿐이라 어느 것인지 찾으려면 감시 목록 전체를 다시 훑어야 한다.&#x20;

`poll`은 이 중 **①과 ②를** 고쳤다 — 고정 크기 비트맵 대신 호출자가 길이를 정하는 배열을 써서 상한을 없애고, 요청 칸(`events`)과 결과 칸(`revents`)을 나눠서 매번 다시 채우는 수고를 없앴을 뿐, **③과 ④는 그대로다.**&#x20;

`epoll`이 바꾼 것은 바로 그 구조 자체다. 감시 목록을 호출 인자로 매번 실어 보내는 대신 **커널 쪽에 만들어 두고**(`epoll_create`), 거기에 연결마다 한 번씩 등록해 둔 다음(`epoll_ctl`), 대기할 때는(`epoll_wait`) 목록을 다시 넘기지 않고 **준비된 것만 골라 받는다**.&#x20;

그래서 한 번 대기하는 데 치르는 값이, select와 poll에서는 "감시 중인 전체 개수"에 비례했지만 epoll에서는 "**실제로 활동 중인 개수**"에 비례하게 된다.

#### 3) 세부 메커니즘

|                         | `select`                                                       | `poll`                          | `epoll`                                     |
| ----------------------- | -------------------------------------------------------------- | ------------------------------- | ------------------------------------------- |
| 감시 목록을 담는 그릇            | 고정 크기 비트맵 `fd_set` 3개(읽기·쓰기·예외용)                               | 호출자가 길이를 정하는 `struct pollfd` 배열 | 커널 안에 만들어진 epoll 인스턴스(`epfd`로 가리킴)          |
| 감시 개수 상한                | **있음** — 파일 서술자 _번&#xD638;_&#xAC00; `FD_SETSIZE`(1024)보다 작아야 함 | 없음 — 배열 길이를 호출자가 정함             | 없음                                          |
| 대기할 때마다 목록 전체를 커널에 넘기는가 | **넘긴다** (→ 위 ②·③)                                              | **넘긴다**                         | **넘기지 않는다** — 등록과 대기가 분리돼 있어 `epfd` 하나만 건넨다 |
| 반환값이 알려 주는 것            | 준비된 **개수**뿐                                                    | 준비된 **개수**뿐                     | 준비된 **개수**, 그리고 그 개수만큼 채워져 돌아온 이벤트 배열       |
| 반환 후 전체를 훑어야 하는가        | **훑어야 함** — `FD_ISSET`으로 하나씩 검사                                | **훑어야 함** — `revents`를 하나씩 검사   | **훑지 않음** — 돌려받은 배열이 곧 준비된 것들의 목록           |
| 대기 한 번의 비용이 비례하는 대상     | 감시 중인 **전체 개수**                                                | 감시 중인 **전체 개수**                 | 준비된(활동 중인) **개수**                           |

표를 채우고 나면 한 칸씩 더 파고들 지점이 세 군데 남는다.

**(1) `FD_SETSIZE`가 묶는 것은 '개수'가 아니라 '번호'다.** \
man page는 "select()는 `FD_SETSIZE`(1024)보다 **작은 번호**의 파일 서술자만 감시할 수 있다"라고 적는다.&#x20;

즉 감시 대상이 다섯 개뿐이더라도 그중 하나의 번호가 2000이면 select는 그것을 다루지 못한다. \
실무에서는 번호가 대체로 0부터 차례로 배정되므로 결과적으로 "1024개를 넘길 수 없다"와 같은 말이 되지만 정확히는 **번호에 걸린 상한**이다. \
그리고 이 값은 실행 중에 늘릴 수 있는 설정값이 아니라 `fd_set`이라는 자료형 자체에 박힌 컴파일 시점 상수다.

**(2) select와 poll의 진짜 차이는 '입력과 출력을 같은 칸에 쓰느냐'다.** \
select에서는 커널이 반환할 때 각 집합을 **제자리에서 고쳐** 준비된 것만 남기고 나머지 비트를 지워 버린다. \
그래서 루프를 도는 프로그램은 다음 호출 전에 집합을 처음부터 **다시 채워야** 한다. \
poll은 같은 구조체 안에서 요청을 담는 칸(`events`)과 결과를 받는 칸(`revents`)을 나눠 놓아서 이 재구성이 필요 없다.&#x20;

하지만 이건 "매번 다시 채우는 수고"가 없어진 것일 뿐, **배열을 통째로 커널에 건네는 일과 돌아와서 전부 검사하는 일은 그대로 남는다.** \
poll이 없앤 것은 `FD_SETSIZE`라는 고정 상한과 **매번 집합을 다시 채우는 수고**이지, **매번 전체를 오가는 비용**이 아니다.

**(3) epoll이 줄인 것과 줄이지 않은 것.** \
epoll이 없앤 것은 "**감시할 목록 전체를 대기할 때마다 커널로 실어 보내는 일**"이다. \
결과를 받아 오는 복사 자체가 없어진 것은 아니다 — `epoll_wait`의 man page는 커널이 준비된 이벤트를 **호출자가 넘겨준 버퍼에 채워서** 돌려준다고 적는다.&#x20;

다만 그 버퍼에 담겨 오는 것은 감시 중인 전체가 아니라 준비된 것뿐이라서, 복사되는 양 자체가 활동량만큼으로 줄어든다.&#x20;

#### 4) 예시

**예시 1 — 같은 서버 루프를 select로 짤 때와 epoll로 짤 때**

```c
/* ── select ── 대기할 때마다 처음부터 다시 차린다 ── */
while (1) {
    FD_ZERO(&readfds);                        /* ① 집합을 매번 비우고 */
    int maxfd = -1;
    for (int i = 0; i < n_conn; i++) {        /* ② 감시할 것을 매번 다시 채우고 */
        FD_SET(conn[i], &readfds);
        if (conn[i] > maxfd) maxfd = conn[i]; /*    ← 가장 큰 번호도 매번 다시 구해야 한다 */
    }

    int ready = select(maxfd + 1, &readfds, NULL, NULL, NULL);
    /*                            └ ③ 이 집합이 통째로 커널로 넘어간다
     *  ready 에는 "몇 개가 준비됐다"는 개수만 담겨 온다 */

    for (int i = 0; i < n_conn; i++)          /* ④ 그래서 전체를 다시 훑는다 */
        if (FD_ISSET(conn[i], &readfds))      /*    ← 준비된 것을 여기서 비로소 찾는다 */
            handle(conn[i]);
}
```

```c
/* ── epoll ── 등록은 한 번, 대기는 반복 ── */
int ep = epoll_create(1);                     /* ① 감시 목록을 커널 쪽에 만들어 둔다.
                                               *    인자 1은 감시할 개수가 아니다 —
                                               *    지금은 무시되는 옛 크기 힌트로,
                                               *    0보다 크기만 하면 된다 */

for (int i = 0; i < n_conn; i++) {            /* ② 연결이 생길 때 한 번만 등록한다 */
    struct epoll_event ev = { .events = EPOLLIN, .data.fd = conn[i] };
    epoll_ctl(ep, EPOLL_CTL_ADD, conn[i], &ev);
}

while (1) {
    int ready = epoll_wait(ep, events, MAX_EVENTS, -1);
    /*                     └ ③ 감시 목록을 다시 넘기지 않는다. ep 하나만 건넨다
     *  ready = 준비된 개수이자, events 배열에 채워져 돌아온 원소의 개수 */

    for (int i = 0; i < ready; i++)           /* ④ 준비된 것만 훑는다 */
        handle(events[i].data.fd);
}
```

(두 예시 모두 조각이라 `<sys/select.h>`·`<sys/epoll.h>` 포함과 `fd_set readfds`, `struct epoll_event events[MAX_EVENTS]` 같은 선언은 생략했다. 앞 소주제 예시 2의 `EAGAIN`도 `<errno.h>`가 필요하다.)

**작동 결과.** 두 코드의 차이는 결국 마지막 `for`문의 상한 하나로 요약된다. select 쪽은 `i < n_conn`(감시 중인 전체), epoll 쪽은 `i < ready`(준비된 것)다. 그리고 select 쪽 루프에는 시작 부분에 `FD_ZERO`/`FD_SET`으로 집합을 다시 채우고 **가장 큰 번호까지 다시 구하는** 단계가 있는데, epoll 쪽에서는 그 단계가 `while` 바깥으로 빠져나가 있다 — **등록과 대기가 분리됐다**는 말이 코드에서는 이렇게 보인다.

**예시 2 — 연결 1만 개 중 3개만 활동 중일 때**

연결이 1만 개면 파일 서술자 번호는 대략 3번부터 10,002번까지 뻗는다(연결을 닫지 않아 번호가 재활용되지 않는다고 볼 때). 여기에는 조용한 전제가 하나 깔려 있다 — **프로세스 하나가 열 수 있는 파일 개수의 상한부터 올려 두어야 한다.** 이 상한의 기본값이 1024인 시스템이 흔해서, 그대로 두면 1만 번째 연결은 fd 번호를 받아 보기도 전에 거절당한다. 아래 표는 그 상한을 이미 넉넉히 올려 둔 상태를 전제한다. 그러고 나면 이 번호대가 select 칸의 모든 숫자를 결정한다.

|                      | `select`                                                                    | `poll`            | `epoll`                                   |
| -------------------- | --------------------------------------------------------------------------- | ----------------- | ----------------------------------------- |
| 1만 개를 다 감시할 수 있는가    | **아니다** — 번호가 1024보다 작은 약 1,021개까지만. 나머지 약 8,979개는 이 API로는 감시 대상에 올릴 수조차 없다 | 가능                | 가능                                        |
| 대기 한 번에 커널로 넘기는 것    | 0\~1023 번호대를 덮는 비트맵 3개                                                      | 배열 원소 **10,000개** | **감시 목록은 넘기지 않음** (`ep` 하나와 결과를 받을 빈 버퍼만) |
| 반환 후 프로그램이 훑는 원소     | 약 1,021개                                                                    | **10,000개**       | **3개**                                    |
| 활동 중인 것을 찾기까지의 검사 횟수 | 약 1,021번 (그나마 감시 범위 안에 든 것들에 한해)                                            | 10,000번           | 0번 (이미 3개만 와 있다)                          |

**select 칸의 숫자가 poll보다 작아 보이는 것을 오해하면 안 된다.** 그건 select가 더 효율적이어서가 아니라 **나머지 약 9천 개를 아예 보지 못하기 때문**이다. 1,021개를 훑어서 3개를 찾는 일과 10,000개를 훑어서 3개를 찾는 일은 성격이 같고, 다만 select는 그 일을 전체의 10분의 1에 대해서만 할 수 있을 뿐이다. 그래서 이 표는 사실상 "select는 이 규모의 문제에 나설 수 없고, 나설 수 있는 둘 중에서 poll과 epoll이 갈린다"로 읽어야 한다.

그리고 이 표에서 정말 중요한 것은 각 칸의 숫자가 아니라 **어느 숫자가 자라는가**다. 연결을 10만 개로 늘리고 여전히 3개만 활동 중이라고 해 보자. poll 쪽 숫자는 전부 10만으로 함께 자라지만, epoll 쪽은 대기할 때 넘기는 감시 목록이 **여전히 없고** 반환 후 훑는 원소도 **여전히 3개**다. epoll에서 연결 개수에 비례해 늘어나는 일은 대기 루프가 아니라 연결이 생길 때 한 번씩 하는 `epoll_ctl` 등록뿐이고, 그건 대기할 때마다 반복되지 않는다. "비용이 전체 연결 수가 아니라 활동 중인 연결 수에 비례한다"는 말의 실체가 이것이다.

# 6.2 CPU while disk on I/O process

### 1. 장치 제어기

CPU가 디스크의 기계 동작을 직접 지휘할 수 없는 이유, 그리고 그 복잡함을 감춰 주는 하드웨어.

#### 1) 개념 정의

장치 제어기(device controller)는 CPU와 물리 장치 사이에 놓여 장치의 전기적·기계적 동작을 대신 처리하고, CPU에게는 레지스터 몇 개짜리 단순한 인터페이스만 보여 주는 전자 부품(하드웨어)이다.

#### 2) 원리 설명

CPU가 할 줄 아는 일은 결국 "주소를 지정해서 읽고 쓴다" 하나뿐이다.&#x20;

그런데 디스크에서 데이터 한 조각을 꺼내려면 스핀들 모터를 돌리고, 액추에이터로 헤드를 목표 트랙 위까지 옮기고, 원판이 회전해 목표 섹터가 헤드 밑에 올 때까지 기다린 다음, 자기 신호로 흘러나오는 직렬 비트 열을 받아 오류를 정정해야 한다. \
이런 서보·모터 제어는 CPU 명령어 집합으로 표현할 수 있는 종류의 일이 아니고, 게다가 장치마다 방식이 전부 다르다. 그래서 그 일을 전담하는 전자 부품을 장치 쪽에 붙여 둔 것이 장치 제어기다. \
제어기는 "운영체제와 통신하는 법"과 "입출력 장치와 통신하는 법"을 둘 다 알고 있어서, 아래로는 장치의 지저분한 물리 동작을 직접 지휘하고 위로는 규격화된 레지스터 인터페이스만 노출한다. 그래서 CPU 입장에서는 디스크든 키보드든 프린터든 전부 "정해진 주소의 레지스터를 읽고 쓰는 대상"으로 똑같이 보이게 된다 — 제어기는 장치의 복잡함을 감추는 하드웨어 추상화 계층이다.

#### 3) 세부 메커니즘

제어기가 위로 노출하는 인터페이스는 보통 세 종류의 레지스터로 이루어지고, **각 레지스터마다 CPU가 쓸 수 있는 방향이 정해져 있다**.

| 레지스터        | 방향    | CPU가 하는 일                                      |
| ----------- | ----- | ---------------------------------------------- |
| 상태(status)  | 읽기 전용 | 지금 명령을 받을 수 있는지, 작업 중인지, 끝났는지, 오류가 났는지를 비트로 확인 |
| 명령(command) | 쓰기 전용 | "읽어라", "써라" 같은 명령 코드를 써 넣음                     |
| 데이터(data)   | 읽기/쓰기 | 장치로 보낼 값과 장치에서 받은 값이 드나드는 창구                   |

자료에 따라 두 번째 레지스터를 "제어(control) 레지스터"라고 부르기도 한다. 같은 것을 가리킨다.

**명령 한 번이 레지스터 수준에서 일어나는 순서**는 이렇다. \
① CPU가 상태 레지스터를 읽어 장치가 명령을 받을 수 있는 상태인지 확인한다. \
② 명령에 필요한 인자(어느 블록인지, 몇 개인지)를 각각의 레지스터에 써 넣는다. \
③ **마지막에** 명령 레지스터에 명령 코드를 쓴다. 이 마지막 쓰기 자체가 "인자는 다 준비됐으니 이제 시작하라"는 방아쇠 역할을 한다. \
④ 제어기가 실제 기계 동작을 수행하고, 끝나면 상태 레지스터의 비트를 갱신해(작업 중 비트를 내리고, 문제가 있었으면 오류 비트를 세워) 결과를 알린다.

**로컬 버퍼.** 제어기 안에는 장치에서 들어오고 나가는 데이터를 임시로 담는 작은 메모리가 있고, 장치에서 로컬 버퍼로 읽어 오는 일은 제어기가 담당한다. 이게 필요한 이유는 세 가지다. \
(ㄱ) 원판은 한번 돌기 시작하면 CPU 사정을 봐 주며 멈춰 주지 않으므로, 흘러나오는 비트를 일단 받아 둘 곳이 있어야 한다.\
(ㄴ) 제어기의 본업 중 하나가 직렬 비트 열을 블록 단위 바이트로 바꾸고 오류 정정을 하는 것인데, 이는 512바이트가 다 모여야 할 수 있는 일이다. \
(ㄷ) 장치와 CPU의 데이터 전송률 차이를 흡수해 준다. 즉 로컬 버퍼는 "온전한 한 덩어리가 완성될 때까지 기다리는 대기실"이다.

**CPU가 이 레지스터들을 어떻게 지정하는가.** \
두 방식이 있다. \
메모리 사상 입출력(제어기 레지스터에 메모리 주소를 할당해 일반 메모리처럼 접근)과 포트 사상 입출력(메모리와 분리된 별도의 I/O 주소 공간을 두고 `IN`/`OUT` 같은 전용 명령어로 접근)이다. 두 방식을 섞어 쓰는 경우도 있다. (개념 자체는 앞 절에서 다뤘다.)

**제어기와 드라이버의 역할 분담.** \
장치 제어기가 하드웨어라면 장치 드라이버는 소프트웨어다. 드라이버는 "이 제어기의 몇 번 레지스터에, 무슨 값을, 어떤 순서로 써야 하는가"를 알고 있는 코드다. 제어기가 물리 장치의 복잡함을 감춰 주고, 드라이버가 그 위에서 제어기 모델마다 다른 레지스터 규약을 감춰 준다. 그래서 운영체제 위쪽 코드는 그냥 "읽어라"만 말하면 된다.

#### 4) 예시

**예시 1 — 오래된 IDE 디스크 제어기의 레지스터 지도**

교육용 운영체제 xv6가 IDE 디스크 제어기와 대화할 때 쓰는 포트 주소는 다음과 같다. 이것이 CPU 눈에 보이는 "디스크"의 전부다.

```
0x1f0   데이터 레지스터   ← 데이터가 드나드는 창구
0x1f1   오류 레지스터
0x1f2   섹터 개수         ← 몇 개 읽을지
0x1f3   LBA 하위 8비트   ┐
0x1f4   LBA 중간 8비트   ├ 몇 번째 블록인지
0x1f5   LBA 상위 8비트   ┘
0x1f6   주소 방식(LBA) 지정 + 드라이브 선택 + LBA 최상위 4비트
0x1f7   쓰면 → 명령 레지스터 / 읽으면 → 상태 레지스터
```

여기서 눈여겨볼 점은 **0x1f7 하나가 방향에 따라 두 역할을 한다**는 것이다. 명령 레지스터는 쓰기 전용이고 상태 레지스터는 읽기 전용이라 서로 충돌하지 않으므로, 같은 주소에 겹쳐 둘 수 있다.

0x1f7을 **읽었을 때** 돌아오는 상태 비트와, 0x1f7에 **썼을 때** 쓰는 명령 코드는 이렇다.

```c
/* 상태 레지스터(0x1f7 읽기)의 비트 */
#define IDE_BSY       0x80   /* 비트7: 제어기가 작업 중 */
#define IDE_DRDY      0x40   /* 비트6: 명령을 받을 준비 완료 */
#define IDE_DF        0x20   /* 비트5: 장치 결함 */
#define IDE_ERR       0x01   /* 비트0: 오류 발생 */

/* 명령 레지스터(0x1f7 쓰기)에 넣는 명령 코드 */
#define IDE_CMD_READ  0x20   /* 섹터 읽기 */
#define IDE_CMD_WRITE 0x30   /* 섹터 쓰기 */
```

"디스크의 100번 블록을 1개 읽어라"를 레지스터 수준으로 옮기면 이렇게 된다.

```c
/* ① 먼저 상태 레지스터(0x1f7)를 읽어 BSY가 내려가고 DRDY가 올라왔는지 확인한다 */

/* ② 인자들을 각 레지스터에 써 넣는다 */
outb(0x1f2, 1);                          /* 섹터 1개 */
outb(0x1f3, 100 & 0xff);                 /* LBA = 100, 하위 8비트  */
outb(0x1f4, (100 >>  8) & 0xff);         /*            중간 8비트  */
outb(0x1f5, (100 >> 16) & 0xff);         /*            상위 8비트  */
outb(0x1f6, 0xe0 | (0 << 4) | ((100 >> 24) & 0x0f));
/*           └ "이 주소는 LBA로 해석하라"는 표시
 *                  └ 비트4 = 드라이브 번호 (0 = 첫 번째 디스크)
 *                            └ LBA의 남은 최상위 4비트 */

/* ③ 마지막에 명령 레지스터에 명령 코드 — 이 한 줄이 곧 "시작" 신호 */
outb(0x1f7, IDE_CMD_READ);               /* 0x20 */
```

**작동 결과.** CPU가 하는 일은 위 여섯 줄이 전부다. 그 다음부터 제어기가 하는 일 — 헤드를 100번 블록이 있는 트랙 위로 이동시키고, 원판이 돌아 목표 섹터가 헤드 밑에 올 때까지 기다리고, 자기 신호를 직렬 비트 열로 읽어 512바이트로 모으고, 오류 정정 부호로 검사해 로컬 버퍼를 채우는 일 — 은 CPU가 실행하는 코드에 **단 한 줄도 나타나지 않는다**. 작업이 끝나면 제어기는 상태 레지스터의 BSY 비트(0x80)를 스스로 내린다. CPU는 0x1f7을 읽어 그 비트가 0인 것만 보면 된다. (로컬 버퍼에 담긴 그 512바이트를 메모리까지 실제로 옮기는 방법은 별개의 문제이며, 이 절 뒤쪽에서 다룬다.)

**예시 2 — 주소가 "100번 블록"이라는 숫자 하나로 끝나는 이유**

위 코드에서 CPU가 지정한 것은 그냥 `100`이라는 정수 하나였다. 원래 디스크 주소는 그렇게 단순하지 않았다. 초기 방식인 실린더-헤드-섹터(CHS)는 수직 좌표인 헤드, 반경 좌표인 실린더, 각도 좌표인 섹터로 구성된 3차원 좌표계였고, 소프트웨어가 이 세 좌표를 직접 계산해 넣어야 했다. 그런데 소프트웨어가 원판의 물리적 생김새를 알고 있어야 한다는 것 자체가 문제였다. 그래서 지금은 그 3차원 좌표를 걷어내고, 블록에 0, 1, 2… 로 번호만 매기는 LBA(논리 블록 주소 지정)를 쓴다.

**작동 결과.** 지금 CPU가 0x1f3\~0x1f6에 써 넣는 값은 원판 위의 물리적 위치가 아니라 그냥 일련번호다. 그 번호가 실제로 어느 원판의 어느 트랙 어느 섹터인지 번역하는 일은 제어기 몫이다. "제어기가 기계적 복잡함을 감춘다"는 말이 주소 체계에서 문자 그대로 실현된 사례다.

#### 5) 다른 키워드와의 연결

예시 1에서 명령을 쓴 뒤, 데이터는 아직 제어기의 로컬 버퍼까지만 와 있다. 그 데이터를 메모리까지 누가 어떻게 옮기느냐가 바로 이어지는 "CPU가 직접 데이터를 복사해야 할까?"와 "직접 메모리 접근"이 답하는 질문이다. 또 제어기가 "레지스터라는 좁은 창구"로만 대화한다는 이 구조가, 뒤의 "전 과정 정리"에서 한 번의 디스크 읽기를 처음부터 끝까지 따라갈 때의 출발점이 된다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **제어기는 사실상 작은 컴퓨터다**: OSTEP 교재는 장치 내부를 이렇게 설명한다 — "아주 단순한 장치는 칩 한두 개면 되지만, 더 복잡한 장치는 간단한 CPU와 약간의 범용 메모리, 그리고 장치 전용 칩들을 포함한다." 실제로 최신 RAID 제어기는 수십만 줄짜리 펌웨어로 굴러간다. 우리가 "주변 장치"라고 부르는 물건 안에 이미 작은 컴퓨터가 한 대 들어앉아 있는 셈이다.
> * **로컬 버퍼는 생각보다 크다**: 요즘 HDD는 8\~256MiB, SSD는 최대 4GB의 캐시 메모리를 달고 나오는데, 이 버퍼로 읽기 선행(read-ahead), 인터페이스와 헤드 사이의 속도 정합, 쓰기 가속(플래터에 닿기 전에 "완료"라고 응답), 명령 큐잉을 한다. 디스크 스펙표의 "캐시 256MB"가 바로 이것이다.
> * **옛날 디스크는 컴퓨터에게 대놓고 거짓말을 했다**: 주소 공간을 더 확보하려고 "실제 존재하는 것보다 더 많은 수의 헤드"가 있다고 신고했고, 제어기가 그 가짜 CHS 값을 실제 물리 위치로 몰래 번역해 줬다. 이 곡예가 한계에 부딪히며 504MiB, 8032.5MiB 같은 악명 높은 용량 벽이 생겼고, 결국 1990년대 중반 LBA로 갈아탔다.

***

이렇게 제어기가 데이터를 자기 로컬 버퍼까지는 가져다 놓았다. 그런데 거기서 메모리까지 남은 마지막 한 구간은 누가 걸을까? → 다음은 CPU가 직접 나설 때의 값.

### 2. CPU가 직접 데이터를 복사해야 할까?

로컬 버퍼에서 메모리까지 남은 마지막 한 구간 — 그 구간을 CPU가 걸을 때의 값.

#### 1) 개념 정의

디스크 제어기 안에 도착한 데이터를 메모리까지 옮기는 운반 노동을 CPU 자신이 명령어를 실행해 한 조각씩 처리하는 방식 — 이를 **프로그램 제어 입출력(Programmed I/O, PIO)** 이라 하며, "값비싼 범용 프로세서에게 이 단순 운반을 계속 맡기는 것이 타당한가"를 묻는 문제.

#### 2) 원리 설명

디스크에서 읽어 낸 데이터는 곧바로 메모리에 앉지 않는다. \
먼저 장치 제어기 안에 모이고, 거기서 메모리까지 가는 **마지막 한 구간**이 남는다. \
PIO에서 이 구간을 걸어 주는 주체가 다름 아닌 CPU다. \
전송 하나하나가 프로그램 속 명령어로 개시되며 모든 거래에 CPU가 관여한다는 것이 이 방식의 정의이고, 그래서 CPU는 데이터 조각마다 명령어를 실행하는 **복사 루프를 손수 돈다**.&#x20;

문제는 그 루프가 도는 동안 CPU가 오직 운반만 한다는 것이다 — 입출력 관리에 전념하느라 다른 작업을 동시에 진행할 수 없고, 입출력이 끝날 때까지 다음 일로 넘어가지 못한다. \
장치를 기다리는 방식(폴링이든 인터럽트든)을 아무리 개선해도, **기다림이 끝난 뒤의 복사 노동 자체는 고스란히 CPU에게 남는다.**

#### 3) 세부 메커니즘

복사 루프 한 바퀴를 쪼개 보면, 데이터가 목적지인 메모리로 **직행하지 못한다**는 사실이 드러난다.

1. **읽기** — 제어기의 데이터 레지스터 값을 CPU 레지스터로 가져오는 명령어(x86이라면 `IN` 계열). 즉 값은 일단 **CPU 레지스터에 담긴다.**
2. **쓰기** — 그 CPU 레지스터 값을 목적지 메모리 주소에 저장하는 명령어. 읽기 명령어만으로는 데이터가 메모리에 도달하지 않으니 반드시 한 번 더 실행해야 한다.
3. **루프 유지** — 목적지 포인터 증가, 남은 개수 감소, 조건 분기.

여기서 **한 바퀴에 옮길 수 있는 양이 정해져 있는** 이유가 나온다. 모든 조각이 CPU를 거쳐 가는 구조이므로, 한 번의 왕복으로 나를 수 있는 양은 CPU가 한 번에 다루는 폭(그리고 상대하는 포트의 폭)을 넘을 수 없다 — x86에서 `AL`을 쓰면 1바이트, `AX`면 2바이트, `EAX`면 4바이트다. (x86에는 위 세 단계를 한 명령어로 묶어, 값을 레지스터에 담지 않고 메모리로 곧장 써 넣는 블록 전송 형태도 있다. 그래도 그 명령어를 실행하는 주체는 여전히 CPU이고, 한 번에 한 단위씩 옮긴다는 것도 그대로다 — 루프 유지 명령어가 줄어들 뿐 운반 노동이 CPU에서 떨어져 나가지는 않는다.) 결과적으로 **N바이트를 옮기려면 루프는 N ÷ (레지스터 폭)번 돌아야 하고**, 이 횟수는 전송량에 정비례해 선형으로 늘어난다. 옮길 데이터가 커질수록 CPU가 지불하는 값도 그만큼 정직하게 커진다는 뜻이며, 그래서 PIO는 전송 하나를 준비하고 데이터를 옮기는 데 상당한 CPU 오버헤드를 요구한다고 정리된다.

#### 4) 예시

**예시 1 — 복사 루프의 모습**

```c
// 4KB 한 페이지 분량을, CPU가 손수 메모리로 퍼 나른다
uint32_t *dst = (uint32_t *)buf;

for (int i = 0; i < 4096 / 4; i++) {
    uint32_t word = read_data_register();  // ① 제어기 데이터 레지스터 → CPU 레지스터
    *dst = word;                           // ② CPU 레지스터 → 메모리
    dst++;                                 // ③ 다음 자리로
}
```

그림으로 그리면 데이터는 `제어기 → CPU 레지스터 → 메모리`라는 **ㄷ자 우회로**를 탄다. 최종 목적지는 메모리인데도 모든 조각이 예외 없이 CPU 안을 한 번 통과했다가 다시 나가는 것이다. 이 4KB를 옮기는 동안 CPU가 한 일을 요약하면 "값을 받아서 그대로 옮겨 적었다"뿐, 더하거나 비교하거나 판단한 것은 하나도 없다.

**예시 2 — 숫자로 세어 보기**

4KB(= 4,096바이트) 한 페이지를 32비트(4바이트) 단위로 옮긴다고 하자.

| 항목              | 계산                 | 값                   |
| --------------- | ------------------ | ------------------- |
| 루프 반복 횟수        | 4,096 ÷ 4          | **1,024회**          |
| 한 바퀴당 최소 필수 명령어 | 읽기 1 + 저장 1        | 2개                  |
| 루프 유지까지 포함하면    | + 포인터 증가·카운터 감소·분기 | 대략 4\~5개            |
| 4KB 하나에 드는 명령어  | 1,024 × 약 4\~5     | **약 4,000\~5,000개** |

(한 바퀴의 정확한 명령어 개수는 명령어 집합과 컴파일 결과에 따라 달라진다 — 위 숫자는 규모를 가늠하기 위한 어림값이다. 그리고 이 4\~5개는 서로 값이 같지 않다. 그중 첫 번째인 포트 읽기만은 CPU 안에서 끝나는 계산이 아니라 버스 건너편 장치의 응답을 기다리는 접근이어서, 나머지 서너 개와 비교가 안 되게 오래 걸린다. 실제로 치르는 값은 명령어 개수가 시사하는 것보다 훨씬 크다.)

조금만 키워 보면 규모가 드러난다.

* 4MB짜리 파일 하나 = 4,194,304 ÷ 4 = **1,048,576회**, 백만 번이 넘는 반복
* 1GB = 1,073,741,824 ÷ 4 = **약 2억 6,800만 회**

그리고 이 반복이 도는 내내, CPU는 **다른 프로세스의 계산을 한 줄도 진행시키지 못한다.** 실행 대기 중인 다른 프로그램의 연산, 화면 갱신, 압축이나 암호화 같은 진짜 계산이 전부 뒤로 밀린다. 그 시간에 CPU가 하고 있는 일은 값을 받아 옆으로 옮겨 적는 것뿐인데 말이다.

여기서 자연스럽게 질문이 선다. **산술·논리 연산을 하라고 비싸게 만들어 놓은 범용 프로세서를, 상태 확인과 조각 단위 운반에 계속 묶어 두는 것이 과연 맞는가?** 특히 디스크처럼 한 번에 큰 덩어리를 옮기는 장치에서는, 값비싼 범용 프로세서가 사소한 운반 일에 통째로 붙들려 있는 셈이 된다. 결론은 하나로 모인다 — **이 운반만 대신 맡아 줄 전담 하드웨어가 필요하다.**

#### 5) 다른 키워드와의 연결

앞의 "장치 제어기"가 "데이터가 일단 어디에 도착하는가"를 짚었다면, 이 소주제는 그 뒤를 이어 \*\*"거기서 메모리까지 누가 옮기는가"\*\*를 묻고 그 답이 CPU일 때의 비용을 계산한다. 이 질문의 실제 답 — CPU를 복사 노동에서 빼내 줄 전담 하드웨어 — 은 바로 다음 소주제 "직접 메모리 접근"의 몫이고, "전 과정 정리"에서는 이 복사 단계가 디스크 읽기 전체 흐름의 어느 자리에 놓이는지 확인하게 된다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **퇴출 사유가 문서에 "주의 산만"으로 적혀 있다**: 옛 IDE 문서는 PIO의 문제를 이렇게 적어 놓았다 — "하드디스크 읽기나 쓰기가 필요할 때마다 CPU가 본업에서 주의를 빼앗긴다(distracted)." 성능 수치가 아니라 '산만해짐'이 퇴출 사유로 남은 셈이다. 이름의 유래도 같은 곳을 가리킨다: '프로그램 제어'는 전송 하나하나가 프로그램에 적힌 명령어로 개시된다는 뜻이라, 이름 자체가 이미 고백이었다.
> * **CPU가 감당 못 해서 취소된 규격**: PIO는 ATA 하드디스크 규격의 전송 모드 이름이기도 하다. 모드 0(사이클 600ns, 3.3MB/s)부터 모드 4(120ns, 16.7MB/s)까지가 표준이 됐는데, 22MB/s짜리 모드 5도 제안됐지만 끝내 하드디스크에는 구현되지 못했다. 이유가 인상적이다 — "당시 CPU들이 그 타이밍에 맞춰 하드디스크를 기다리느라 심하게 느려졌을 것"이기 때문이다.
> * **x86의 I/O 주소 공간은 통째로 64KB뿐**: I/O 전용 주소 버스가 16비트라서 접근 가능한 공간이 전부 합쳐 65,536바이트다. 기가바이트 단위로 세는 메모리 주소 공간과 나란히 놓고 보면 참 좁은 쪽문인데, 그래서 메모리와 I/O 장치가 같은 주소 공간을 나눠 쓰는 메모리 사상 입출력이라는 우회로가 따로 있다.

***

CPU가 손수 나르는 것은 가능하지만 값이 너무 비싸다는 결론이 났다. 그렇다면 이 운반을 대신 맡을 하드웨어는 어떻게 생겼을까? → 다음은 두 번째 버스 주인.

### 3. 직접 메모리 접근

메모리의 주인이 CPU 하나여야 할 이유는 없다 — 두 번째 버스 주인이라는 아이디어.

#### 1) 개념 정의

직접 메모리 접근(DMA, Direct Memory Access)은 CPU와 독립적으로 시스템 메모리에 접근할 수 있는 별도의 하드웨어(DMA 컨트롤러)가, CPU를 거치지 않고 장치와 메모리 사이의 데이터 이동을 대신 수행하는 기능이다.

#### 2) 원리 설명

메모리에 접근하는 주인이 반드시 CPU 하나여야 할 이유는 없다 — 주소 버스와 제어선을 몰 수 있는 부품이라면 무엇이든 메모리를 읽고 쓸 수 있다. \
DMA 컨트롤러는 바로 그 목적으로 만들어진 부품으로, 메모리 주소를 생성하고 메모리 읽기 또는 쓰기 사이클을 개시할 수 있다.&#x20;

즉 CPU 말고도 버스의 주인, 곧 **버스 마스터**가 될 수 있는 두 번째 하드웨어다. \
이 두 번째 주인이 생기는 순간 CPU의 역할이 바뀐다 — 앞 소주제에서 CPU가 손수 지고 있던 데이터 나르기를 이 하드웨어가 통째로 넘겨받고, CPU는 '복사하는 자'에서 '지시하는 자'가 된다. \
CPU가 하는 일은 "어디서·어디로, 몇 개, 어느 방향"을 DMA 컨트롤러의 레지스터에 써 넣고 시작 명령을 내리는 것뿐이며, 그 뒤로는 CPU가 먼저 전송을 시작시키고 전송이 진행되는 동안 다른 작업을 수행하다가 작업이 끝나면 DMA 컨트롤러로부터 인터럽트를 받는다.&#x20;

그래서 블록을 아무리 크게 잡아도 CPU에서는 데이터 이동이 완료되었다는 단 한 번의 인터럽트만 발생한다.

#### 3) 세부 메커니즘

**(1) CPU가 써 넣는 값 — DMA 컨트롤러 자신의 레지스터**

DMA 컨트롤러는 CPU가 읽고 쓸 수 있는 여러 개의 하드웨어 레지스터를 갖는다. CPU가 지시를 내린다는 것은 곧 이 레지스터들을 채운다는 뜻이다.

| 레지스터                                    | 담는 값                                                          |
| --------------------------------------- | ------------------------------------------------------------- |
| **주소 레지스터** (address register)          | 메모리 쪽 블록의 시작 주소 — 데이터를 가져올 곳(읽기)이거나 넣을 곳(쓰기)                  |
| **카운트 레지스터** (word/byte count register) | 옮길 워드(또는 바이트)의 **개수**                                         |
| **제어 레지스터** (control register)          | 전송 **방향**(장치→메모리인지 메모리→장치인지), 출발지·목적지, 전송 단위의 크기, 버스를 나눠 쓸 모드 |

그리고 마지막으로 "전송을 시작하라"는 제어 신호 하나. CPU가 이 전송에 대해 하는 일은 여기까지다.

**(2) 버스를 넘겨받는 악수(handshake)**

* 장치가 준비되면 DMA 컨트롤러에 "옮길 것이 있다"는 **전송 요청**을 보낸다.
* DMA 컨트롤러는 CPU에 "버스를 좀 쓰겠다"는 **버스 요청**을 건다.
* CPU는 **버스 승인**으로 답하며 버스를 내준다. 이때 평소 CPU가 만들어 내던 신호들이 하이도 로우도 아닌 **삼상태(tri-state)** 에 놓인다 — CPU가 버스에서 물리적으로 손을 떼는 것이다.
* 이제 DMA 컨트롤러가 버스 마스터다. 버스 승인 입력이 1이면 CPU가 버스들을 내놓은 것이고, DMA 컨트롤러는 메모리와 직접 통신할 수 있다.

**(3) 한 번의 전송 사이클 — '직접(direct)'의 진짜 의미**

DMA 컨트롤러는 주소 버스에 주소를 싣고, 메모리 쪽 신호와 장치 쪽 신호를 한 전송 구간 안에 함께 걸어 준다(장치→메모리라면 "장치에서 읽어라"와 "메모리에 써라"를 걸고, 이를 내려 메모리가 그 바이트를 래치해 저장하게 한다). \
그러면 데이터는 장치와 메모리 칩 사이를 곧장 건너간다 — 이렇게 읽기 신호와 쓰기 신호를 한 전송 구간에 겹쳐 거는 방식에서는, 옮겨지는 데이터가 **DMA 칩 안에 잠시도 머무르지 않는다**. \
컨트롤러가 대는 것은 주소와 제어 신호뿐이다. \
어느 쪽이든 변하지 않는 것은 **데이터가 CPU를 거치지 않는다**는 점.

한 단위가 건너갈 때마다 컨트롤러 내부에서 두 숫자가 반대 방향으로 움직인다: 바이트가 하나 전송될 때마다 DMA 컨트롤러의 **주소 레지스터는 증가하고**, 몇 바이트를 옮겨야 하는지 세는 **카운트 레지스터는 감소한다**. 카운트가 0에 도달하면 그 블록의 전송이 끝났다는 신호가 서고, 바로 그 시점에 CPU에게 완료 인터럽트가 **딱 한 번** 올라간다.

**(4) 버스는 한 번에 한 주인만 — 나눠 쓰는 방식**

여기서 짚어야 할 점이 하나 있다. \
CPU가 '자유롭다'는 것은 **데이터를 나르는 일에서** 자유롭다는 뜻이지, 버스를 100% 쓸 수 있다는 뜻이 아니다. \
버스의 주인은 한 순간에 하나뿐이므로, DMA 컨트롤러가 버스를 쥐고 있는 동안 CPU는 메모리 접근을 잠시 기다려야 한다. 그래서 버스를 어떻게 나눠 쓸지를 정하는 모드가 있다.

| 모드                                  | 버스 점유 방식                                                | CPU 쪽 영향                                           |
| ----------------------------------- | ------------------------------------------------------- | -------------------------------------------------- |
| **버스트(burst) / 블록**                 | 블록 전체를 하나의 연속된 시퀀스로 전송하고, 다 옮긴 뒤에야 버스를 CPU에 돌려준다        | 전송은 가장 빠르지만, 그동안 CPU는 버스를 쓰지 못한다                   |
| **사이클 스틸링(cycle stealing) / 단일 전송** | 한 단위(1바이트/1워드)를 옮기고 버스를 놓았다가, 블록이 다 갈 때까지 다시 요청하기를 반복한다 | CPU가 사이사이 계속 돌아간다. 이름 그대로 CPU에게서 버스 **사이클을 훔치는** 것 |
| **투명(transparent) 모드**              | CPU가 시스템 버스를 사용하지 않는 명령을 실행할 때만 전송한다                    | CPU가 프로그램 실행을 결코 멈추지 않는다는 게 장점이지만, 가장 느리다          |

한 가지 더 — DMA 컨트롤러가 CPU를 건너뛰고 메모리를 직접 고치기 때문에, 5장에서 본 CPU 캐시 안에 그 주소의 사본이 남아 있으면 낡은 값이 되어 버린다. 이것이 DMA가 일으키는 **캐시 일관성 문제**다(해결 기법은 TMI 참조).

#### 4) 예시

**예시 1 — CPU가 '지시'만 하고 빠지는 모습**

디스크에서 4096바이트를 메모리 버퍼로 읽어 오라고 시키는 코드다(레지스터 이름과 배치는 칩마다 다르므로 개념을 보여 주는 유사 코드).

```c
// CPU가 DMA 컨트롤러에게 내리는 '지시'
dma->addr     = 0x00102000;         // 주소 레지스터: 메모리 쪽 블록 시작 주소
dma->count    = 1024;               // 카운트 레지스터: 옮길 워드 개수
                                    //   (4바이트 워드 1024개 = 4096바이트)
dma->control  = DIR_DEVICE_TO_MEM   // 제어 레지스터: 방향 (장치 -> 메모리)
              | MODE_CYCLE_STEAL;   //                버스를 나눠 쓸 모드
dma->control |= START;              // "시작하라"

// --- CPU가 이 전송에 관여하는 일은 여기서 끝난다 ---
schedule_other_task();              // 곧바로 다른 작업으로 넘어간다
```

핵심은 CPU가 넘기는 정보가 **주소 · 개수 · 방향 · 시작** 네 가지뿐이라는 점이다. 이 몇 줄이 실행된 뒤 실제로 일어나는 일을 숫자로 보면 이렇다.

| 항목                   | 값                                                |
| -------------------- | ------------------------------------------------ |
| 옮기는 데이터              | 4바이트 워드 1024개 = 4096바이트                          |
| 버스 위에서 일어나는 전송 사이클   | 워드 하나당 한 번씩, **1024회**                           |
| 그 1024회를 수행하는 주체     | 전부 DMA 컨트롤러                                      |
| 주소 레지스터              | 0x00102000 → 0x00102004 → … (매번 증가)              |
| 카운트 레지스터             | 1024 → 1023 → … → **0** (매번 감소)                  |
| **CPU에 올라오는 인터럽트**   | **딱 1회** (카운트가 0이 되는 마지막 순간)                     |
| 그 사이 CPU가 이 전송에 쓴 시간 | **0** (명령어 실행 기준. 다만 사이클 스틸링이므로 버스 사이클 일부는 양보한다) |

CPU가 이 전송에 관여하는 순간은 처음 레지스터 몇 개를 채울 때와, 마지막에 인터럽트를 한 번 처리할 때 — 이렇게 **두 지점**뿐이다. 블록을 여덟 배로(워드 8192개 = 32768바이트) 늘리면 버스 전송 사이클도 8192회로 여덟 배가 되지만, CPU 쪽 인터럽트는 **여전히 1회**다.

**예시 2 — 버스를 누가 쥐고 있는지 그림으로**

사이클 스틸링 모드에서 시간에 따른 버스의 주인:

```
시간 →
버스 주인:  CPU  CPU [DMA] CPU  CPU  CPU [DMA] CPU  CPU [DMA] CPU ...
                      └1워드              └1워드         └1워드
CPU 상태:   실행  실행  대기  실행  실행  실행  대기  실행  실행  대기  실행
```

DMA 컨트롤러가 버스를 쥐는 것은 한 워드를 옮기는 짧은 순간뿐이고, 그때마다 곧바로 버스를 CPU에 돌려준다. CPU는 계속 명령어를 실행하되 그 사이사이 버스 사이클 몇 개를 '도둑맞을' 뿐이다.

버스트 모드에서는 같은 그림이 이렇게 바뀐다:

```
시간 →
버스 주인:  CPU  CPU [DMA DMA DMA DMA DMA DMA DMA DMA] CPU  CPU ...
                     └────── 블록 전체를 한 번에 ──────┘
CPU 상태:   실행  실행 [───── 버스 사용 불가 ─────]      실행  실행
```

블록 전체가 다 갈 때까지 버스를 놓지 않으므로 전송 자체는 가장 빠르지만, 그동안 CPU는 메모리에 접근하지 못한다. 같은 4096바이트를 옮기더라도 어느 모드를 고르느냐에 따라 CPU가 겪는 방해의 '모양'이 달라진다 — 잘게 여러 번이냐(사이클 스틸링), 한 번에 길게냐(버스트).

#### 5) 다른 키워드와의 연결

장치 제어기가 준비해 놓은 데이터를 실제로 메모리까지 실어 나르는 주체가 바로 이 DMA 컨트롤러이며, "CPU가 직접 데이터를 복사해야 할까?"가 던진 물음에 하드웨어로 답한 것이 여기서 본 **버스 마스터**라는 아이디어다. 이 전송 구간이 디스크 읽기 요청 전체의 시간 흐름 어디에 놓이는지는 "전 과정 정리"가, 그 결과가 코드를 짜는 사람에게 무엇을 뜻하는지는 "프로그래머에게 시사하는 것"이 이어받는다.

***

### 4. 전 과정 정리

부품이 아니라 배턴 — 누가 무엇을 누구에게 넘기고, 그때 CPU는 무엇을 하고 있는가.

#### 1) 개념 정의

한 번의 디스크 읽기는 **프로그램 → 커널의 장치 드라이버 → 장치 제어기 → 디스크 → DMA 컨트롤러 → 완료 인터럽트 → 다시 그 프로그램**으로 배턴이 넘어가는 릴레이이며, CPU는 이 릴레이의 첫 구간과 마지막 구간에만 잠깐 뛰고 그 사이에는 아예 트랙 위에 없다.

#### 2) 원리 설명

앞에서는 부품을 하나씩 뜯어봤다면, 여기서는 그 부품들이 **시간 순서로 배턴을 어떻게 주고받는지**를 본다. \
읽기 요청 하나가 끝나기까지 걸리는 시간의 대부분은 디스크가 물리적으로 데이터를 찾고 그 데이터가 메모리로 옮겨지는 구간인데, 이 구간에서 CPU가 할 일은 하나도 없다. 그래서 운영체제는 요청을 내보낸 직후 그 프로세스를 실행 상태에서 내려 대기 큐에 넣고, CPU에는 다른 프로세스를 올린다.&#x20;

결국 **CPU가 이 긴 과정에 관여하는 것은 극히 짧은 두 순간뿐이다 — 요청을 만들어 제어기에 내보낼 때, 그리고 완료 인터럽트를 받아 처리할 때.** \
그 사이의 시간은 CPU에게 "기다리는 시간"이 아니라 "다른 프로세스를 실행하는 시간"이다.&#x20;

그래서 읽기 요청 하나를 따라가면 서로 다른 두 개의 타임라인이 생긴다. \
**요청한 프로세스는 내내 멈춰 있지만, CPU는 그동안 한순간도 쉬지 않는다.** 이 둘을 분리해서 보는 것이 이 절 전체의 결론이다.

#### 3) 세부 메커니즘

각 단계마다 **누가 하는가 / 무엇을 넘기는가 / 그때 CPU는 / 그때 요청한 프로세스는**을 함께 본다.

| # | 단계                        | 누가 하는가         | 무엇을 넘기는가                                  | 이때 CPU는                             | 이때 요청한 프로세스는                  |
| - | ------------------------- | -------------- | ----------------------------------------- | ----------------------------------- | ----------------------------- |
| 1 | `read()` 호출, 시스템 콜로 커널 진입 | 응용 프로그램 → 커널   | "어느 파일의 어디를, 몇 바이트, 어느 버퍼에"               | 그 프로세스의 코드를 커널 모드로 이어서 실행           | **실행 중**                      |
| 2 | 요청을 디스크가 알아듣는 명령으로 번역해 전달 | 커널의 장치 드라이버    | 읽기 명령을 **장치 제어기에 써 넣음**                   | 여전히 그 프로세스를 위해 일하는 중 ← **CPU 관여 ①** | **실행 중**                      |
| 3 | 요청한 프로세스를 재우고 문맥 교환       | 커널(스케줄러)       | 그 프로세스를 실행 상태에서 **대기 큐**로, CPU는 다른 프로세스에게 | **다른 프로세스를 실행하기 시작**                | **대기(블로킹)** — `read()`에서 멈춤   |
| 4 | 데이터를 물리적으로 찾아 읽음          | 디스크 + 장치 제어기   | 읽은 데이터를 제어기의 로컬 버퍼에 채움                    | **관여 없음.** 다른 프로세스 실행 중             | 계속 대기                         |
| 5 | 데이터를 메모리로 옮김              | **DMA 컨트롤러**   | 로컬 버퍼의 내용 → 메모리                           | **관여 없음.** 다른 프로세스 실행 중             | 계속 대기                         |
| 6 | 전송 완료를 알림                 | DMA 컨트롤러 → CPU | "끝났다"는 **인터럽트 신호**                        | 하던 일을 즉시 멈추고 현재 상태를 저장              | 계속 대기                         |
| 7 | 인터럽트 핸들러 실행               | CPU(커널의 핸들러)   | 어느 요청이 끝났는지 확인 → 그 프로세스를 **대기 큐 → 준비 큐**로 | 짧게 핸들러만 실행 ← **CPU 관여 ②**           | 대기 → **준비**                   |
| 8 | 인터럽트 직전 하던 일로 복귀          | CPU            | (넘기는 것 없음) 저장해 둔 상태를 되살림                  | 아까 실행하던 **다른 프로세스를 계속 실행**          | **준비 상태로 줄만 서 있음** (아직 실행 아님) |
| 9 | 다시 CPU를 얻고 `read()`가 반환   | 스케줄러           | 커널이 받아 둔 데이터를 프로세스가 준 버퍼에 채우고 반환          | 그 프로세스를 실행                          | **실행** — `read()` 다음 줄로 진행    |

#### 4) 예시

**파일에서 4KB를 읽을 때.** 어떤 프로그램이 `read(fd, buf, 4096)`으로 하드디스크에서 4KB를 읽는다고 하자.

```
시간 ─────────────────────────────────────────────────────────────────▶

프로세스 A : 실행 ─[read()]─▶ 대기 · · · · · · · · · · · · · ·▶ 준비 ─▶ 실행
                     │                                          ▲
                     │ (드라이버가 제어기에 명령)                  │ (핸들러가 깨움)
                     ▼                                          │
디스크/DMA :         ─▶ 탐색·회전 (≈10 ms) ─▶ DMA 전송 ─▶ 완료 인터럽트
                                                                │
CPU        : A 실행 ─▶ A용 짧은 작업 ─▶ B 실행 ────────────▶ 핸들러 ─▶ B 실행 …
              └ 관여 ① ┘               └──── 관여 없음 ────┘  └ 관여 ② ┘
```

**시간 규모의 대비 — 왜 이 사이에 CPU를 놀릴 수 없는가**

* 디스크 헤드가 그 4KB가 있는 자리를 찾아가는 **탐색(seek) 한 번이 약 10 ms = 10,000,000 ns**다.
* 같은 CPU에서 **메인 메모리 참조는 약 100 ns, L1 캐시 참조는 약 0.5 ns**다.
* 즉 디스크 탐색 한 번을 그냥 기다린다면, 그 시간에 **메모리 참조를 10만 번, L1 캐시 참조를 2천만 번** 할 수 있었던 시간을 통째로 버리는 셈이다.
* 그래서 3단계(프로세스를 재우고 다른 프로세스로 문맥 교환)는 성능 최적화가 아니라 **필수**다. CPU가 4\~6단계 내내 그 자리에 서 있는 설계는 애초에 성립하지 않는다.
* SSD로 바꿔도 성격은 같다. **4KB 랜덤 읽기가 약 150 μs = 150,000 ns**로, 여전히 메모리 참조 1,500번 분량이다. 규모만 줄었을 뿐 "CPU를 세워 둘 만큼 짧은 시간"은 아니다.

#### 5) 다른 키워드와의 연결

2단계에서 드라이버가 명령을 써 넣는 상대가 **장치 제어기**이고, 4\~5단계에서 데이터를 옮기는 주체가 CPU가 아니라 **DMA 컨트롤러**여야 하는 이유는 "CPU가 직접 데이터를 복사해야 할까?"에서 이미 답이 나와 있다. 그리고 이 사슬을 알고 나면 코드를 쓰는 방식이 달라지는데, 그 이야기는 "프로그래머에게 시사하는 것"의 몫이다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **실제 리눅스의 경로는 훨씬 길다**: 이 절의 흐름도는 상당히 압축된 버전이다. 리눅스의 실제 경로는 read(2) → VFS → 파일 시스템 → 블록 계층 → SCSI 중간 계층 → 드라이버로 내려갔다가, 완료 인터럽트를 받고 그 역순으로 되짚어 올라온다(중간에 페이지 캐시가 끼어들지만, 다이렉트 I/O는 이를 건너뛴다). 이 여정을 코드로 추적한 커널 개발자는 성공하려면 먼저 "복잡한 걸음 부(Ministry of Complicated Walks)에서 몇 년쯤 도제 생활을 해야 한다"고 농담했다.
> * **잠들기 전에 커널은 쪽지를 남긴다**: 다이렉트 I/O 코드를 보면 `dio->waiter = current`로 "지금 이 태스크를 깨워달라"고 적어둔 뒤 `io_schedule()`로 잠들고, 나중에 완료 처리 쪽이 `wake_up_process(dio->waiter)`로 그 쪽지를 읽어 깨운다. 심지어 인터럽트 핸들러조차 그 자리에서 다 끝내지 않고 `raise_softirq_irqoff(BLOCK_SOFTIRQ)`로 뒷일을 미룬다.
> * **지연 시간을 사람 시간으로 환산하면**: 제프 딘의 지연 시간 목록을 10억 배로 늘리면 감이 확 온다 — L1 캐시 참조가 심장박동 한 번(0.5초)일 때, 메인 메모리 참조는 이 닦는 시간, SSD 랜덤 읽기는 주말 하나, 디스크 탐색은 무려 "대학교 한 학기"다. 실제로 7200RPM 디스크는 평균 회전 지연만 4.17ms인데, SSD는 탐색 시간이 0.08\~0.16ms이고 회전 지연이라는 개념 자체가 없다.

***

무슨 일이 일어나는지는 다 봤다. 그렇다면 이 사실이 내가 짜는 코드에는 무엇을 요구할까? → 마지막은 실무 결론.

### 5. 프로그래머에게 시사하는 것

하드웨어 사실에서 코드로 — 그래서 내 프로그램은 어떻게 짜야 하는가.

#### 1) 개념 정의

"데이터 전송 중에는 CPU가 자유롭다"는 하드웨어 사실을, 실제 애플리케이션 코드를 쓸 때의 세 가지 결론 — **대기 중인 스레드는 CPU를 쓰지 않는다 / 입출력 집약형은 코어 수보다 많은 스레드가 이득이다 / 요청은 잘게 여러 번보다 크게 한 번이 낫다** — 로 옮겨 놓은 실무 지침이다.

#### 2) 원리 설명

앞 소주제들이 밝힌 결론은 한 줄로 요약된다

DMA 컨트롤러 덕분에 디스크가 데이터를 옮기는 동안 CPU는 다른 일을 할 수 있다.&#x20;

그런데 이 사실이 프로그래머에게 주는 의미는 "그동안 CPU가 논다"가 아니라 "**그동안 CPU를 다른 스레드에게 줄 수 있다**"이다. 실제로 블로킹 읽기를 호출한 스레드는 "전 과정 정리" 3단계에서 본 대로 CPU를 내놓고 대기 상태로 내려간다.&#x20;

즉 대기 중인 스레드는 CPU 사이클을 태우며 도는 것이 아니다. \
**단, 이것은 운영체제가 그 스레드를 실제로 재워 줄 때만 참이다.** `while (아직_안_끝났나) ;` 처럼 조건이 바뀌기를 스스로 돌면서 확인하는 대기(바쁜 대기)는 기다리는 내내 코어를 하나 통째로 태운다. \
상태 레지스터를 계속 읽어 보는 폴링 방식이 바로 그것이다. \
겉보기에는 똑같이 "기다리는 중"이지만 CPU 입장에서는 정반대다.&#x20;

그래서 "블로킹 입출력은 CPU를 낭비한다"는 흔한 말은 (재워 주는 대기를 두고 한 말이라면) 부정확하다 — **낭비되는 것은 CPU가 아니라 그 스레드**다. \
블로킹 연산은 극도로 유한한 자원인 스레드를 하나 잡아먹는다.&#x20;

여기서 두 가지 실무 결론이 곧장 따라 나온다. \
스레드가 놀고 있을 뿐 CPU는 비어 있으니 **입출력 집약형 작업은 스레드를 코어 수보다 많이 잡을수록 이득**이고, 반대로 CPU를 계속 쓰는 CPU 집약형 작업은 코어 수를 넘겨 봐야 서로 CPU를 다투며 문맥 교환 비용만 늘 뿐이다.

#### 3) 세부 메커니즘

**(가) 대기 자체는 공짜지만, 대기의 시작과 끝은 공짜가 아니다.** 블로킹된 스레드가 대기 큐로 내려갔다가 완료 인터럽트에 의해 준비 큐로 되돌아오는 경로 자체는 앞의 "전 과정 정리"에서 3단계와 7단계로 이미 본 그대로다. 프로그래머가 거기에 덧붙여 알아야 할 것은 그 경로에 **값이 붙는다**는 사실이다. 문맥 교환이 두 번 일어난다(블로킹될 때 한 번, 깨어날 때 한 번). 게다가 그 스레드가 잠들어 있는 동안에도 저장된 상태와 스택은 그대로 남아 있다. 스레드를 하나 만들 때마다 스택으로 쓸 주소 공간이 통째로 예약되는데, 그 크기가 플랫폼에 따라 대략 1MB에서 8MB에 이른다. 실제 물리 메모리는 스택이 실제로 닿은 만큼만 나중에 붙지만, 예약된 주소 공간 자체가 스레드 수의 상한을 만든다. 이것이 "스레드를 무한정 늘리면 된다"가 성립하지 않는 이유이며, 동시에 "애초에 요청 건수 자체를 줄이자"는 세 번째 결론의 동기가 된다.

**(나) 스레드 수 산정이 대기 시간과 계산 시간의 비율에서 유도되는 방식.** 작업 하나가 계산에 C, 대기에 W를 쓴다고 하자. 그 작업을 맡은 스레드는 자기 수명 중 `C / (C + W)` 만큼만 코어를 실제로 점유하고, 나머지 `W / (C + W)` 동안에는 코어를 비워 둔다. 그러니 **코어 하나를 쉬지 않고 채우려면** 그 역수인 `(C + W) / C = 1 + W/C` 개의 스레드가 필요하다. 코어가 여러 개면 여기에 코어 수를 곱한다.

```
적정 스레드 수 = 코어 수 x (1 + 대기 시간 / 계산 시간)
```

이 식이 두 극단을 한꺼번에 설명한다. 대기 시간이 0인 순수 CPU 집약형이면 `1 + 0/C = 1`이 되어 **적정 스레드 수 = 코어 수**로 떨어진다. 대기 시간이 길어질수록 괄호 안이 커져 스레드 수도 함께 커진다. (실무에서는 코어를 100%가 아니라 목표 이용률까지만 채우도록 계수를 하나 더 곱하기도 한다.)

#### 4) 예시

**예시 1 — 코어 4개, 대기 시간이 계산 시간의 9배인 작업**

파일이나 데이터베이스에서 데이터를 읽어 가볍게 가공하는 전형적인 작업을 생각하자. 요청 1건에 10ms가 걸리는데 그중 9ms는 응답을 기다리는 시간이고 실제 계산은 1ms뿐이다(W/C = 9).

| 항목                   | 값                       |
| -------------------- | ----------------------- |
| 코어 수                 | 4                       |
| 계산 시간 C              | 1ms                     |
| 대기 시간 W              | 9ms                     |
| 스레드 1개의 코어 점유율       | 1 / (1 + 9) = **10%**   |
| 코어 1개를 채우는 데 필요한 스레드 | 1 + 9/1 = **10개**       |
| 적정 스레드 수             | 4 x (1 + 9/1) = **40개** |

스레드를 코어 수와 똑같이 4개만 두면 어떻게 될까. 스레드 하나가 코어를 10%만 쓰므로 스레드 4개가 만들어 내는 일감은 **코어 0.4개분**뿐이다. 코어 4개짜리 머신은 결국 **10%만 가동되고 90%는 논다.** 40개까지 늘려야 비로소 한 스레드가 기다리는 9ms 동안 다른 스레드들이 그 자리를 채워 네 코어가 꽉 찬다. **다만 이 계산에는 숨은 전제가 하나 있다 — W가 9ms로 고정되어 있다는 것이다.** W는 상수가 아니라 부하에 따라 달라지는 값이다. 요청 40개를 동시에 던졌을 때 디스크나 데이터베이스가 그것을 정말 나란히 처리해 주면 9ms가 유지되지만, 감당하지 못하고 줄을 세우면 뒤에 선 요청의 W가 함께 늘어난다. 그러면 식이 자기 입력을 스스로 무너뜨린다. 그래서 이 공식은 출발점을 잡아 주는 것이지 최종 답이 아니고, 실제 값은 재 보고 정해야 한다.

반대로 이미지 필터링이나 압축처럼 계산만 하는 CPU 집약형 작업이라면 W가 거의 0이라 식은 `4 x 1 = 4`를 준다. 여기에 40개를 넣으면 처리량이 10배가 되는 게 아니라, 40개가 4개의 코어를 서로 뺏느라 문맥 교환만 늘고 각 스레드의 스택 메모리까지 잡아먹어 **더 느려진다.** 같은 코어 4개, 같은 40개 스레드가 한쪽에서는 정답이고 다른 쪽에서는 오답인 것이다.

**예시 2 — 4KB씩 1000번 읽기 대 4MB 한 번 읽기**

똑같이 4MB를 읽는 두 코드다.

```python
# (A) 잘게 1000번
total = 0
with open("data.bin", "rb", buffering=0) as f:   # 버퍼링 끔
    for _ in range(1000):
        chunk = f.read(4 * 1024)                 # 시스템 콜 1000회
        total += len(chunk)

# (B) 한 번에 크게
with open("data.bin", "rb", buffering=0) as f:
    data = f.read(4 * 1024 * 1024)               # 시스템 콜 1회
```

`buffering=0`을 붙인 이유가 그 자체로 이 예시의 교훈이다 — 파이썬의 기본 `open`은 이미 내부 버퍼를 끼워 주기 때문에, 그냥 두면 (A)의 `read` 1000번이 실제로는 훨씬 적은 수의 시스템 콜로 접힌다. 언어가 이미 뒤에서 이 최적화를 해 주고 있다는 뜻이고, 대비를 눈으로 보려면 그 버퍼를 꺼야 한다.

옮기는 데이터의 총량은 4MB로 동일한데, **요청 건수에 비례하는 고정 비용**은 1000배 차이가 난다.

|                  | (A) 4KB x 1000회 | (B) 4MB x 1회 |
| ---------------- | --------------- | ------------ |
| 읽는 총량            | 4MB             | 4MB          |
| 시스템 콜(커널 진입)     | 1000회           | 1회           |
| 요청 준비 + 완료 인터럽트  | 각 1000회         | 각 몇 회 수준     |
| 그로 인한 스레드 블로킹/재개 | 최대 1000쌍        | 1쌍           |

시스템 콜 한 번은 사용자 공간에서 커널 공간으로 경계를 넘는 일이고, 여기에는 커널 모드 진입과 경우에 따라 문맥 교환이 따라붙는다. 그리고 요청 하나가 끝날 때마다 하드웨어가 완료 인터럽트를 한 번씩 올린다. 이 비용들은 **옮긴 바이트 수가 아니라 요청 횟수에 비례**하므로, 요청 수를 1000분의 1로 줄이면 이 고정 비용도 그만큼 줄어든다. (커널이 아주 큰 요청 하나를 하드웨어에 내릴 때는 몇 개로 나눠 내리기도 해서 인터럽트가 정확히 1회로 떨어지지는 않지만, 1000회와는 자릿수가 다르다.)

버퍼링이 효과를 내는 이유가 정확히 이것이다. 버퍼 없이 한 줄씩 1만 줄을 쓰면 시스템 콜이 1만 번 발생하지만, 버퍼를 쓰면 메모리에 모아 두었다가 버퍼가 찼을 때만 커널로 넘긴다. 다만 버퍼 크기는 파일 시스템 블록·메모리 페이지 크기(흔히 4KB)와 하드웨어·작업 특성에 따라 최적점이 달라진다 — 버퍼 크기는 추측할 것이 아니라 측정할 것이다.

#### 5) 다른 키워드와의 연결

이 소주제는 앞의 "장치 제어기"·"CPU가 직접 데이터를 복사해야 할까?"·"직접 메모리 접근"이 밝혀 놓은 하드웨어 사실을 전제로만 빌려 쓰고, 그로부터 나오는 코드 작성 지침에만 집중한다 — 전송 중 CPU가 왜 자유로운지는 "직접 메모리 접근"이, 그 전 과정이 어떤 순서로 이어지는지는 "전 과정 정리"가 각각 담당한다.

>
> * **스레드 수 공식의 출처는 책 한 권**: 지금도 인용되는 이 공식의 출처는 브라이언 괴츠의 『자바 병렬 프로그래밍(Java Concurrency in Practice)』이다. "스레드 수 = 코어 수 × (1 + 대기 시간 / 서비스 시간)" — 응답 50ms에 실제 처리 5ms인 작업을 2코어에서 돌리면 22개가 나온다. 여기에 리틀의 법칙을 얹으면 "워커 22개 ÷ 평균 0.055초 ≈ 초당 400건"처럼 곧바로 처리량 숫자로 번역된다.
> * **"코어 수 + 1"을 두고 출처끼리 답이 갈린다**: 한쪽은 CPU 집약형 작업에 여전히 코어 수 + 1을 권하며 그 여분 1개가 페이지 폴트 같은 짧은 멈춤을 메워준다고 설명하고(8코어면 9개), 다른 쪽은 그건 CPU 작업과 입출력 작업을 한 풀에 섞어 쓰던 시절의 낡은 지혜라며 풀을 아예 둘 — 코어 수에 고정된 계산용 + 무제한에 가까운 블로킹용 — 로 나누라고 반박한다.
> * **mmap이 빨랐던 진짜 이유는 모드 전환이 아니었다**: 어떤 실험에서 mmap이 read 시스템 콜보다 2\~6배 빨랐는데, 커널의 복사 함수가 AVX 벡터 명령을 일부러 쓰지 않기 때문이었다. AVX를 쓰면 시스템 콜마다 그 레지스터들을 저장·복원해야 해서 오히려 경계를 넘는 비용이 더 커진다. 반면 사용자 공간의 memmove는 AVX를 마음껏 쓴다 — 버퍼링 방식 하나 고르는 문제가 이런 층위까지 내려간다.

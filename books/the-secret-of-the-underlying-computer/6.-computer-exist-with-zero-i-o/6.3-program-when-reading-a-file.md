# 6.3 program when reading a file

### 1. 메모리 관점에서 입출력

입출력이란 결국 외부 장치와 내 메모리 사이에서 바이트를 복사하는 일이고, 그 복사가 도착하는 자리가 버퍼다.

#### 1) 개념 정의

메모리를 기준으로 다시 정의하면, 입출력(I/O)이란 **외부 장치와 프로그램의 메모리 사이에서 데이터를 복사하는 일**이다. \
입력(read)은 장치 → 메모리 방향의 복사이고, 출력(write)은 메모리 → 장치 방향의 복사다.

#### 2) 원리 설명

CPU가 명령어의 피연산자로 직접 지정할 수 있는 것은 자기 레지스터와 메인 메모리에 있는 값뿐이다. \
디스크에 있는 바이트에는 그렇게 지정할 주소가 없으므로, CPU가 그것을 다루기 전에 반드시 먼저 메모리로 옮겨져야 한다.&#x20;

그래서 "파일을 읽는다"는 말은 실제로는 "디스크 위에 있는 바이트를 내 프로세스의 메모리 안 어딘가로 복사한다"는 뜻이 된다.&#x20;

그 복사가 도착할 자리가 바로 **버퍼(buffer)** 다. (`read(fd, buf, count)`에서 `buf`) \
read는 파일 디스크립터 `fd`로부터 최대 `count` 바이트를 "`buf`에서 시작하는 버퍼로" 읽어 들인다. \
출력은 방향만 반대여서, `write(fd, buf, count)`는 같은 모양의 버퍼로부터 최대 `count` 바이트를 `fd`가 가리키는 파일로 내보낸다. (이 복사를 실제로 수행하는 하드웨어는 앞 절에서 본 DMA 컨트롤러다.)

#### 3) 세부 메커니즘

**버퍼는 커널이 주는 것이 아니라 내가 마련해 두는 메모리다.** \
`read`는 데이터를 담을 공간을 새로 만들어 주지 않는다. \
이미 존재하는 내 메모리의 주소를 받아서 거기를 채울 뿐이다.&#x20;

그래서 버퍼는 지역 변수로 선언한 배열(`char buf[100];`)이어도 되고 `malloc`으로 잡은 공간이어도 된다. \
스택이든 힙이든 read 입장에서는 차이가 없다.&#x20;

다만 커널이 검사해 주는 것은 그 주소가 **내 프로세스의 주소 공간 안**이라는 데까지이고, 거기에 정말 `count` 바이트를 받을 자리가 있는지는 검사해 주지 않는다. \
`char buf[100];`을 선언해 놓고 `read(fd, buf, 200)`을 부르면 커널은 아무 불평 없이 200바이트를 써 넣고, 뒤의 100바이트는 버퍼 옆자리를 덮어쓴다. \
`count`를 버퍼 크기 이하로 맞추는 책임은 전적으로 호출자에게 있다.

**도착지가 내 주소 공간 밖이면 복사는 거부된다.** \
`buf`가 접근할 수 없는 주소를 가리키면 read/write는 데이터를 옮기는 대신 오류를 돌려준다. \
입출력이 "장치와 _내_ 메모리 사이의 복사"라는 정의가 규칙으로 못 박혀 있는 지점이다.

**버퍼 크기는 약속이 아니라 수용 한도다.**\
&#x20;`count`는 "이만큼 주세요"가 아니라 "이만큼까지는 받을 수 있습니다"라는 뜻이다.&#x20;

그래서 실제로 복사된 양(반환값 `n`)은 `count`보다 작을 수 있고, 그것은 오류가 아니다. 표준은 이 값이 **결코 요청한 크기보다 클 수는 없다**고 못 박는다.&#x20;

즉 버퍼 크기는 한 번의 복사가 넘지 못하는 상한선이지, 실제로 복사된 양이 아니다. 실제로 몇 바이트가 채워졌는지는 반환값으로만 알 수 있다.

**왜 "이동"이 아니라 "복사"라고 해야 정확한가.** \
복사이기 때문에 원본은 디스크에 그대로 남는다. \
파일을 읽어 버퍼를 채운 뒤 그 버퍼의 내용을 메모리에서 고쳐도 디스크의 파일은 조금도 바뀌지 않는다. \
바뀐 내용을 파일에 반영하려면 `write`로 반대 방향 복사를 **따로 한 번 더** 해야 한다. \
read와 write가 별개의 함수인 이유가 여기에 있다.

#### 4) 예시

**예시 1 — 도착지를 어디에 마련하는가**

```c
/* (a) 스택에 마련하는 방식: 지역 배열이 곧 도착지다 */
char buf[100];
ssize_t n = read(fd, buf, sizeof(buf));   /* 최대 100바이트가 buf로 복사된다 */

/* (b) 힙에 마련하는 방식: malloc으로 잡은 공간이 도착지다 */
char *buf = malloc(buflen);
ssize_t n = read(fd, buf, buflen);        /* 최대 buflen 바이트가 buf로 복사된다 */
```

둘 다 정상 동작한다. read에게 스택이냐 힙이냐는 아무 차이가 없다. 대신 "그 주소에 buflen 바이트를 받을 공간이 있다"는 것은 read가 _확인해 주는 사&#xC2E4;_&#xC774; 아니라 **호출자가 보증하는 약속**이다.

**예시 2 — 버퍼 크기와 실제 복사량**

표준 입력을 표준 출력으로 그대로 옮기는 코드다. 버퍼 크기를 바꿔 가며 실행할 수 있다. 아래 표는 **표준 입력이 일반 파일로 리다이렉트된 경우**(`./a.out < data.txt`, `data.txt`는 1000바이트)를 기준으로 한다.

```c
char *buf = malloc(buflen);          /* 예: buflen = 512 */
ssize_t n;

while ((n = read(0, buf, buflen)) > 0)
    write(1, buf, n);                /* buflen이 아니라 n 만큼만 내보낸다 */
```

1000바이트짜리 입력을 `buflen = 512`로 처리하면 반환값 `n`은 이렇게 나온다.

| 호출 | 요청한 크기(count) | 실제 복사된 양(n)   |
| -- | ------------- | ------------- |
| 1  | 512           | 512           |
| 2  | 512           | 488           |
| 3  | 512           | 0 (더 읽을 것 없음) |

512 + 488 = 1000으로 파일 전체가 옮겨진다. 두 번째 호출에서 512를 요청했지만 488만 복사된 것은 오류가 아니라 정상이다. 같은 파일을 `buflen = 4096`으로 처리하면 표는 1000, 0 두 줄로 줄어든다 — 버퍼가 크면 같은 양을 더 적은 횟수의 복사로 옮긴다.

같은 코드를 파이프나 터미널에 물리면 표가 이대로 나오지 않는다. 특히 마지막 줄의 `0`은 "더 읽을 것이 없다"가 아니라 **입력의 끝**을 뜻하므로, 파이프에서는 쓰는 쪽이 끝을 닫아야, 터미널에서는 사용자가 끝 표시를 입력해야 나온다. 그 전까지 read는 0을 돌려주지 않고 그냥 기다린다.

여기서 결정적인 한 줄은 `write(1, buf, n)`이다. `buflen`이 아니라 `n`을 넘긴다. 버퍼는 512바이트지만 두 번째 호출에서 유효한 내용은 앞의 488바이트뿐이고, 나머지 24바이트는 이전 내용이 남아 있는 쓰레기 값이다. 버퍼의 크기와 그 안에 실제로 들어 있는 데이터의 양은 별개라는 사실이 코드에 그대로 드러난다.



여기서 다룬 것은 **데이터가 어디에서 어디로 가는가**, 즉 복사의 출발지와 도착지라는 공간 문제다. 그 복사가 **언제, 어떤 순서로** 일어나는지 — `read()`를 호출한 뒤 프로그램에 무슨 일이 벌어지는지 — 는 형제 소주제 "read 함수는 어떻게 파일을 읽는 것일까?"가 다룬다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **"두 번 복사"에는 이름이 붙어 있다**: 윈도우 드라이버 모델의 "버퍼링된 I/O(buffered I/O)"에서는 I/O 관리자가 사용자 버퍼와 **같은 크기의** 시스템 버퍼를 커널 쪽에 따로 잡고, 드라이버가 장치 데이터를 거기에 담은 뒤, 문서의 표현 그대로 "원래 스레드가 다시 활성화됐을 때(when the original thread is again active)" 비로소 사용자 버퍼로 옮긴다. 두 번째 복사가 스레드가 깨어난 뒤에야 시작되므로, 그 전까지 사용자 버퍼의 물리 메모리는 다른 프로세스가 가져다 써도 무방하다. 같은 문서는 이 방식을 키보드·마우스·직렬·비디오처럼 작은 전송에 권하고, 여러 페이지를 한꺼번에 옮기는 드라이버에게는 "버퍼링된 I/O를 쓰려 하지 말라"고 못 박는다.
> * **왕복 자체를 없애는 길**: 파일을 그대로 네트워크로 흘려보내기만 하는 서버에서는 read로 사용자 버퍼를 채웠다가 write로 도로 커널에 넘기는 왕복이 순전한 낭비다. 그래서 리눅스에는 `sendfile()`이 있고, 매뉴얼은 "이 복사가 커널 안에서 이루어지기 때문에, 데이터를 사용자 공간으로 오가게 해야 하는 read+write 조합보다 효율적"이라고 설명한다. 이 최적화는 설정 파일 수준까지 올라와 있어서 nginx에는 `sendfile on|off;` 지시어가 따로 있고(기본값은 `off`), 자바 `FileChannel.transferTo`의 공식 문서도 "많은 운영체제가 파일 시스템 캐시에서 대상 채널로 바이트를 실제로 복사하지 않고 곧바로 옮길 수 있다"고 적고 있다.

### 2. read 함수는 어떻게 파일을 읽는 것일까?

`read()` 한 줄이 실행되는 동안, 읽을 데이터가 아직 커널에 준비돼 있지 않다면 그 줄을 부른 스레드는 CPU에서 내려와 입출력 대기열에 매달렸다가 준비 완료 대기열을 거쳐 돌아온다.

#### 1) 개념 정의

`read()`는 "파일 내용을 가져오는 함수"이기 이전에, 요청한 데이터가 아직 커널에 준비되지 않았을 때 **호출한 스레드를 실행 상태에서 끌어내려 입출력 대기열에 매달아 두고, 준비가 끝나면 준비 완료 대기열로 돌려보내는** 함수다.

#### 2) 원리 설명

프로그래머가 보는 `read()`는 한 줄짜리 함수 호출이고, 그 줄에서 프로그램이 잠시 굳었다가 데이터를 손에 쥔 채 다음 줄로 넘어가는 것처럼 보인다.&#x20;

그러나 커널 입장에서 이 한 줄은 "요청을 장치 쪽으로 넘기는 일"과 "호출한 스레드를 실행 후보에서 빼는 일" 두 가지이며, 요청한 데이터가 아직 커널에 준비돼 있지 않으면 커널은 이 스레드를 실행 불가로 표시하고 그 요청에 딸린 대기열에 매달아 둔다. \
일단 매달린 뒤로 이 스레드는 스스로 자기 상태를 확인하지도, 자기를 깨우지도 못한다.&#x20;

앞 절에서 본 "대기 중인 스레드는 CPU를 쓰지 않는다"가 큐의 언어로 다시 표현된 것이 이것이다. \
그동안 스케줄러는 준비 완료 대기열에서 다음 차례의 스레드를 꺼내 CPU에 올린다. \
나중에 완료 통지가 커널에 올라오면 커널이 이 스레드를 그 대기열에서 빼내 준비 완료 대기열로 옮긴다. \
그리고 스케줄러가 이 스레드를 다시 고르는 순간에야 `read()`가 반환값을 들고 돌아오는데, "돌아오지 않는 것처럼 보였던" 시간의 정체가 바로 이 두 번의 큐 이동과 그 사이의 기다림이다.

#### 3) 세부 메커니즘

* **대기열은 사실 연결 리스트다.** 큐마다 머리 역할을 하는 헤더가 있고 그 헤더가 첫 원소와 마지막 원소를 가리키며, 원소들은 다음 원소를 가리키는 포인터로 사슬처럼 이어진다. 우리가 머릿속에 그리는 "줄 서 있는 사람들"은 이 사슬의 비유다.
* **큐에 들어가는 것은 스레드가 아니라 제어 블록이다.** 커널은 스레드마다 상태값, 프로그램 카운터, 레지스터 값, 스케줄링 정보(큐 포인터 포함), 열린 파일 목록 같은 것을 담은 **제어 블록**을 갖고 있고, 큐에 매달리는 것은 이 제어 블록이다. 따라서 "스레드를 큐에서 큐로 옮긴다"는 말은 실행 흐름을 어딘가로 이사시킨다는 뜻이 아니라, **제어 블록을 한 연결 리스트에서 떼어 다른 연결 리스트에 잇는 포인터 조작**이라는 뜻이다.
* **대기열은 하나가 아니라 기다리는 대상별로 쪼개져 있다.** 실행 준비가 끝난 쪽이 서는 준비 완료 대기열이 있고, 그와 별도로 장치마다(디스크 0번, 터미널 0번 …) 자기 입출력 대기열이 따로 있다. 어떤 스레드가 지금 무엇을 기다리는지는 "그 제어 블록이 어느 큐에 매달려 있는가"로 표현된다. (앞 절에서 "대기 큐 → 준비 큐"라고 짧게 부르고 지나갔던 것이 바로 이 두 종류의 큐다.)
* **그래서 "누구를 깨울지"를 뒤져 찾을 필요가 없다.** 스레드는 잠들 때 자기 제어 블록을 아무 데나 두는 게 아니라 **바로 그 장치·그 요청에 딸린 큐**에 걸어 두었다. 완료 통지가 올라오면 커널은 그 큐에 매달린 쪽을 꺼내면 되고, 이것이 "커널이 올바른 스레드를 골라 다시 실행 가능하게 만든다"의 실체다. (원칙은 **그 결과를 기다리던 쪽만** 깨우는 것이다. 여럿이 똑같은 조건 하나를 함께 기다리고 있을 때 하나만 깨울지 전부 깨울지는 커널이 정하며, 여기까지가 표준이 규정하지 않는 영역이다.)
* **상태 전이 = 큐 이동.** 실행 중인 스레드는 어느 큐에도 없이 CPU 위에 있고, 입출력을 기다리는 스레드는 그 장치의 입출력 대기열에, 실행 준비가 된 스레드는 준비 완료 대기열에 있다. 상태값을 바꾸는 일과 큐를 옮기는 일은 같은 동작의 양면이며, 그 이동을 실행하는 주체는 언제나 커널이다(요청을 낼 때 한 번, 완료 통지를 받았을 때 한 번).
* **깨어남은 "실행"이 아니라 "줄 서기"까지다.** 깨우기가 하는 일은 상태를 실행 가능으로 바꾸고 준비 완료 대기열에 넣는 데서 끝난다. 그 뒤 언제 CPU를 받을지는 스케줄러가 결정하므로, 데이터가 다 도착한 뒤에도 `read()`는 곧바로 반환되지 않을 수 있다.

#### 4) 예시

**예시 1 — 코드에서는 보이지 않는 두 번의 큐 이동**

```c
int fd = open("data.txt", O_RDONLY);
char buf[4096];

ssize_t n = read(fd, buf, 4096);  // ← 데이터가 준비돼 있지 않으면 여기서 실행 상태에서 사라진다
printf("%zd bytes\n", n);         // ← 다시 CPU를 받은 뒤에야 실행된다

close(fd);
```

소스 코드에서 `read`와 `printf`는 붙어 있는 두 줄이지만, 그 사이에는 커널 안에서 벌어진 "입출력 대기열로 이동 → (기다림) → 준비 완료 대기열로 이동 → (다시 기다림) → CPU 획득"이 통째로 들어 있다. 그 기다림이 언제 끝나는지 — 커널이 이 스레드를 언제 깨우는지 — 는 **"요청한 4096바이트가 다 찰 때"로 정해져 있지 않다.** 커널은 내어 줄 것이 생긴 시점에 깨우며, 그 시점은 읽는 상대가 무엇이냐에 따라 달라진다. 위 코드처럼 상대가 디스크 위의 일반 파일이면 커널은 파일 끝에 닿기 전까지 요청한 만큼을 다 갖춰 놓고 깨우는 것이 원칙이다. 그러나 파이프·터미널·소켓이면 그렇지 않다 — 파이프는 누가 무엇이든 써 넣은 순간에, 터미널은 보통 한 줄이 입력된 순간에, 소켓은 지금 도착해 있는 만큼을 가지고 깨운다. 프로그래머가 손에 쥐는 것은 반환값 `n` 하나뿐이다. 즉 결과값에는 이 스레드가 어느 큐에 얼마나 매달려 있었는지가 전혀 드러나지 않는다.

**예시 2 — 큐의 스냅숏: 제어 블록이 어디에 매달려 있는가**

스레드 A가 위 코드의 `read()`를 호출했고, 스레드 B·C는 그냥 계산만 하는 스레드라고 하자.

```
[read() 호출 직후]
  준비 완료 대기열    head → [제어블록 C] → tail
  디스크 0번 대기열   head → [제어블록 A] → tail       ← read()를 부른 우리 스레드
  터미널 0번 대기열   head → tail (비어 있음)
  CPU 위             제어블록 B의 스레드가 실행 중

[완료 통지가 커널에 올라온 직후]
  준비 완료 대기열    head → [제어블록 C] → [제어블록 A] → tail   ← A는 줄 맨 끝에 섰을 뿐
  디스크 0번 대기열   head → tail (비어 있음)
  CPU 위             제어블록 B의 스레드가 여전히 실행 중
```

옮겨진 것은 A의 실행 흐름이 아니라 A의 제어 블록을 잇는 포인터 하나뿐이고, 그 결과 A의 상태가 "대기"에서 "준비"로 바뀐다. 같은 장면을 시간 순서로 적으면 이렇게 된다. **칸에 적히는 것은 오직 "어느 상태 / 어느 큐인가"뿐이고 하드웨어는 등장하지 않는다.**

| 시점                    | 스레드 A              | 스레드 B     |
| --------------------- | ------------------ | --------- |
| ① `read()`를 막 호출한 순간  | 실행 중               | 준비 완료 대기열 |
| ② 커널이 요청을 넘기고 A를 재운 뒤 | 디스크 0번 대기열         | 실행 중      |
| ③ 완료 통지가 올라와 A를 깨운 직후 | 준비 완료 대기열          | 실행 중      |
| ④ 스케줄러가 A를 다시 고른 뒤    | 실행 중 (`read()` 반환) | 준비 완료 대기열 |

A는 ③에서 이미 깨어났지만 실제로 `printf` 줄을 실행하는 것은 ④이다. 이 두 칸의 간격이 "깨어났다 ≠ 즉시 실행된다"의 전부다.

한 가지 더 눈여겨볼 것이 있다. ③에서 A는 준비 완료 대기열의 **맨 뒤**에 섰는데, ④에서는 앞에 있던 C를 제치고 A가 CPU를 받았다. 이것은 실수가 아니라 같은 이야기의 다른 면이다 — **준비 완료 대기열에 서 있는 순서가 곧 CPU를 받는 순서는 아니다.** 큐에 매달아 두는 일은 커널이 하지만, 그중 누구를 CPU에 올릴지는 스케줄러가 자기 기준으로 따로 정한다.



"메모리 관점에서 입출력"이 **공간** — 데이터가 어디로 복사되고 `buf`가 어디에 있는가 — 를 맡는다면, 이 소주제는 그 복사가 끝날 때까지 **호출한 스레드가 어느 큐에 있는가(시간)** 를 맡는다. \
한 번의 `read()` 안에서 "버퍼가 채워지는 이야기"와 "스레드가 큐 사이를 오가는 이야기"가 나란히 진행된다고 보면 된다.

# 4.7 Evolution of CPU(2)

### 1. 복잡함을 단순함으로

RISC 이야기를 시작하기 전에, 먼저 "왜 잘 나가던 복잡한 명령어를 버리고 단순함으로 되돌아가자는 발상이 나왔는가"라는 배경부터 짚는다.

#### 1) 개념 정의

하나의 명령어에 온갖 기능을 욱여넣어 걷잡을 수 없이 비대해진 복잡 명령어 집합(CISC)이 정작 실제로는 소수의 단순한 명령어만 대부분 쓰인다는 관찰에 부딪히면서, "복잡함을 덜어내고 단순한 명령어로 돌아가자"는 발상의 전환이 일어난 배경을 가리킨다.

#### 2) 원리 설명

초기 컴퓨터는 메모리가 매우 비싸고 귀했다. 그래서 프로그램이 차지하는 크기를 최대한 줄이는 것이 중요했고, 설계자들은 명령어 하나에 여러 작업(값 불러오기·계산·저장 등)을 묶어 코드를 짧게 만들려 했다. \
또 당시에는 사람이 어셈블리어로 직접 프로그램을 짜는 일이 많아, 사람이 쓰기 편한 강력하고 똑똑한 명령어가 선호되었다. \
세대가 지날수록 "이런 명령어도 있으면 좋겠다"는 요구에 따라 명령어가 계속 추가되었고, 명령어 집합은 점점 방대하고 복잡해졌다.&#x20;

그런데 시간이 흐르며 메모리는 싸지고 컴파일러 기술이 발전해, 굳이 복잡한 명령어를 하드웨어에 넣지 않아도 컴파일러가 알아서 여러 단순 명령어로 처리할 수 있게 되었다.&#x20;

이때 결정적인 관찰이 나온다 — 그 많은 복잡한 명령어들이 실제 프로그램에서는 거의 쓰이지 않고, 대부분의 일은 소수의 단순한 명령어로 이루어지고 있었던 것이다.

#### 3) 세부 메커니즘

왜 복잡함이 짐이 되었는지는 CPU 내부의 "마이크로코드"라는 장치를 보면 한 단계 더 선명해진다. \
복잡한 명령어 하나는 CPU가 곧바로 실행하지 못하고, 내부의 번역표(마이크로코드)를 거쳐 여러 개의 작은 단계로 쪼개진 뒤에야 처리된다.&#x20;

문제는 이 번역표 자체가 칩 안에서 상당한 면적을 잡아먹는다는 점, 그리고 자주 쓰이는 단순한 명령어조차 이 우회 경로 때문에 느려질 수 있다는 점이었다.&#x20;

여기서 핵심 발상이 나온다. "어차피 마이크로코드가 복잡한 명령어를 잘게 쪼개서 실행한다면, 그 쪼개는 일을 컴파일러에게 맡기고 하드웨어는 단순한 명령어만 두면 되지 않을까?" \
이 문제의식이 단순화의 출발점이 되었다.&#x20;

다만 그 단순한 명령어를 실제로 _어떤 규칙으로_ 설계했는지는 "축소 명령어 집합의 철학"에서 다룬다.

#### 4) 예시

* 명령어 집합에는 수백 개의 명령어가 담겨 있어도, 실제 프로그램을 뜯어보면 그중 극히 일부만 반복해서 쓰인다. \
  흔히 "쓰이는 것의 대부분은 전체의 일부에 불과하다"는 8:2(파레토)식 비율로 회자되는데, 나머지 복잡한 명령어들은 만들어 두기는 했지만 거의 쓰이지 않는 장식에 가까웠다.
* 초기의 어떤 프로세서는 전체 트랜지스터의 약 1/3을 복잡한 명령어를 잘게 번역하는 마이크로코드에 쓰고 있었다. \
  다시 말해 칩 자원의 큰 몫이, 정작 자주 쓰이지도 않는 복잡함을 유지하는 데 소모되고 있었던 셈이다.



이 "단순함으로 돌아가자"는 동기가 구체적인 설계 규칙으로 정리된 것이 "축소 명령어 집합의 철학"이고, 그렇게 단순화된 방식을 기존 복잡한 방식과 항목별로 견주어 보는 것이 "복잡 명령어 집합과 축소 명령어 집합의 차이"다.&#x20;

> 💡 **TMI**
>
> * **다항식을 명령어 하나로 — VAX의 POLY**: 복잡 명령어의 극단을 보여주는 예가 DEC VAX의 `POLY` 명령이다. 다항식을 기계어 명령 하나로 통째로 계산해 버리는데, 이런 초복잡 명령들 탓에 VAX 명령어는 길이가 1바이트부터 56바이트까지 제각각이었다. "다항식 계산"까지 CPU 명령으로 넣을 정도였으니 CISC가 얼마나 비대해졌는지 보여주는 상징적 사례로 자주 인용된다.
> * **비대함의 원동력, 마이크로코드(1951)**: CISC를 비대하게 만든 핵심 기술인 마이크로코드(마이크로프로그래밍)는 1951년 영국의 모리스 윌크스가 고안했다. 하드웨어를 직접 뜯어고치지 않고도 복잡한 명령을 계속 추가할 수 있게 해 준 이 기법이 있었기에 명령어 집합은 손쉽게 불어났고, 훗날 RISC는 바로 이 "마이크로코드로 명령을 늘리는" 관행에 대한 반작용으로 등장한다.
> * **'CISC'는 소급해서 붙은 이름**: 사실 'CISC'라는 말은 나중에 붙었다. 1980년경 'RISC(축소 명령어 집합)'라는 용어가 만들어진 뒤에야, 그 반대편의 기존 복잡한 컴퓨터들을 가리키기 위해 'CISC'라는 대조어가 생겨났다. 즉 CISC는 스스로 그렇게 불린 적이 없다가 RISC의 등장으로 소급해서 이름을 얻은 셈이다.

### 2. 축소 명령어 집합의 철학

앞에서 "단순함으로 돌아가자"는 동기를 봤다면, 이제 그 발상이 실제로 _어떤 설계 규&#xCE59;_&#xC73C;로 구체화됐는지를 본다.

#### 1) 개념 정의

명령어를 단순하고 고정된 길이로 통일하고 각 명령어가 한 가지 일만 하도록 설계하여, 하드웨어를 간결하게 유지하고 복잡한 처리는 컴파일러에 맡기려는 CPU 설계 사상이다.

#### 2) 원리 설명

RISC는 CPU가 처리해야 할 명령어의 종류를 자주 쓰이는 단순한 것들로 좁히고, 각 명령어를 되도록 한 사이클 안에 끝나도록 설계한다. \
명령어의 길이를 32비트처럼 일정하게 고정해, CPU가 다음 명령어의 시작 위치를 미리 알고 빠르게 해독할 수 있게 한다. \
연산은 오직 레지스터끼리만 수행하고, 메모리에 접근하는 일은 전용 적재(load)·저장(store) 명령어로만 하도록 역할을 분리한다. \
이렇게 명령어가 단순하고 실행 시간이 일정하기 때문에, 제어 회로도 마이크로코드 없이 하드웨어로 직접 배선(하드와이어드)할 수 있다.&#x20;

대신 문자열 처리나 형 변환처럼 복잡한 작업은 하드웨어가 단일 명령어로 떠맡지 않고, 컴파일러가 여러 개의 단순 명령어로 풀어서 조합하도록 넘긴다.&#x20;

즉 "하드웨어는 단순하게, 똑똑함은 소프트웨어에" 두는 것이 핵심 사상이다.

#### 3) 세부 메커니즘

네 가지 선택은 각각 노리는 이득이 다르다.

* **고정 길이 명령어**: 명령어마다 연산 코드와 피연산자가 늘 같은 자리에 오므로, 해독(decode) 회로가 위치를 계산할 필요 없이 곧바로 읽어낼 수 있다. 목표는 해독 단계의 단순화와 실행 시간의 예측 가능성이다.
* **load-store 아키텍처**: 계산 명령어에서 메모리 접근을 떼어내, 연산은 빠른 레지스터에서만 하고 느린 메모리 왕래는 별도 명령어로 국한한다. 목표는 연산과 메모리 접근을 분리해 각 명령어의 동작을 단일하고 짧게 유지하는 것이다.
* **하드와이어드 제어**: 명령어가 단순하고 종류·길이가 고정되어 있으므로, 제어 신호를 마이크로코드 표에서 찾아보는 대신 회로로 직접 만든다. 목표는 마이크로코드 조회 과정을 제거해 해독·실행 속도를 높이는 것이다.
* **레지스터 우선(다수의 범용 레지스터)**: CPU 안에 범용 레지스터를 넉넉히 두어, 자주 쓰는 값을 메모리에 다시 내려보내지 않고 레지스터에 오래 담아둔다. 목표는 상대적으로 느린 메모리에 대한 의존도를 낮추는 것이다.

또한 명령어 길이가 고정되고 실행이 한 사이클로 일정하다는 점은 명령어 파이프라인에 유리한 전제가 된다

#### 4) 예시

메모리에 있는 값 두 개를 더해 다시 메모리에 저장하는 동작을 생각해 보자. RISC 철학에서는 이 일을 하나의 명령어로 하지 않고, 적재→연산→저장의 세 종류로 쪼갠다.&#x20;

아래는 특정 CPU의 실제 문법이 아닌, 원리를 보여 주는 개념적 스케치이다.

```
load  R1, [A]       ; 메모리 주소 A의 값을 레지스터 R1로 읽어온다
load  R2, [B]       ; 메모리 주소 B의 값을 레지스터 R2로 읽어온다
add   R1, R1, R2    ; 레지스터끼리만 더한다 (메모리 접근 없음)
store [A], R1       ; 결과를 메모리 주소 A에 저장한다
```

여기서 연산 명령어 `add`는 오직 레지스터만 다루고, 메모리를 만지는 일은 `load`와 `store`가 전담한다. \
또한 `add R1, R1, R2`처럼 더할 두 값과 결과를 담을 곳을 각각 따로 지정할 수 있어, 원래 값을 덮어쓰지 않고 `c = a + b` 형태로 계산할 수 있다.



"복잡함을 단순함으로"가 단순화에 이르게 된 배경이라면, 이 소주제는 그 결과로 RISC가 실제로 채택한 설계 원칙을 다룬다. 여기서 확립된 고정 길이·단일 사이클 원칙은 이어지는 "명령어 파이프라인"이 성립하기 위한 밑바탕이 된다.

> 💡 **TMI**
>
> * **RISC를 세상에 선언한 논문(1980)**: RISC 철학을 세상에 알린 문서는 패터슨과 디첼이 1980년에 발표한 "The Case for the Reduced Instruction Set Computer(축소 명령어 집합 컴퓨터를 옹호하며)"다. 제목 그대로 "명령어를 줄인 컴퓨터가 오히려 더 효율적일 수 있다"는 당시로선 도발적인 주장을 담았고, 이 논문이 RISC라는 용어 자체를 대중화시켰다.
> * **첫 RISC는 대학이 아니라 IBM**: RISC 아이디어를 최초로 구현한 것은 존 코크가 이끈 IBM 팀이 1970년대에 만든 'IBM 801'로 꼽힌다. 이 특이한 이름은 팀이 근무하던 연구소 건물 번호(801동)에서 따온 것이다. 코크는 이 공로 등으로 1987년 튜링상을 받았다.
> * **부품 절반으로 더 빠르게 — 버클리 RISC-I**: 버클리 대학원생들이 1년 남짓 만에 설계한 RISC-I 칩은 트랜지스터를 약 4만 4천 개만 쓰고도, 10만 개를 쓴 당대의 복잡한 상용 CISC(VAX)를 여러 벤치마크에서 앞질렀다. 절반도 안 되는 부품으로 더 빠르다는 결과가 "단순함이 곧 성능"이라는 RISC 주장에 힘을 실었다.

### 3. 복잡 명령어 집합과 축소 명령어 집합의 차이

RISC의 철학을 봤으니, 이제 그것을 기존 CISC와 _나란히 놓고_ 무엇이 어떻게 다른지 항목별로 대조한다.

#### 1) 개념 정의

복잡 명령어 집합(CISC)과 축소 명령어 집합(RISC)이 명령어 개수·길이·실행 방식·제어 회로·메모리 접근·레지스터·코드 크기·컴파일러 부담이라는 여러 축에서 서로 어떻게 반대편에 서는지를 항목별로 나란히 대조한 것이다.

#### 2) 원리 설명

두 방식의 근본 트레이드오프는 "복잡함을 어디에 둘 것인가"이다.&#x20;

CISC는 복잡함을 하드웨어(와 마이크로코드) 안에 넣는다. 명령어 하나가 많은 일을 하도록 만들면 프로그램이 짧아지고 컴파일러가 할 일이 줄어들지만, 그 대신 명령어를 해석하고 실행하는 회로가 복잡하고 명령어마다 걸리는 시간이 들쭉날쭉해진다.&#x20;

RISC는 반대로 복잡함을 하드웨어 바깥, 즉 소프트웨어(컴파일러)로 밀어낸다. \
명령어를 단순하고 규칙적으로 만들면 하드웨어가 간단해지고 빨라지지만, 같은 일을 하려면 더 많은 명령어가 필요해 프로그램이 길어지고 컴파일러의 책임이 커진다.&#x20;

즉 한쪽이 얻는 것을 다른 쪽이 내주는 관계이며, 어느 쪽도 공짜 이득은 아니다.

#### 3) 세부 메커니즘 (항목별 대조)

| 비교 축           | CISC (복잡 명령어 집합)  | RISC (축소 명령어 집합)           |
| -------------- | ----------------- | -------------------------- |
| 명령어 개수         | 많고 종류가 다양함        | 적고 자주 쓰는 것 위주로 단순함         |
| 명령어 길이         | 가변 길이             | 고정 길이                      |
| 명령어당 실행 시간     | 명령어마다 다르며 여러 사이클  | 1사이클 실행 지향(일부 예외)          |
| 제어 방식          | 마이크로코드(마이크로프로그램)  | 하드와이어드(고정 배선 회로)           |
| 메모리 접근         | 여러 명령어가 메모리 직접 연산 | load/store만 접근, 연산은 레지스터끼리 |
| 범용 레지스터 수      | 상대적으로 적음          | 상대적으로 많음                   |
| 코드 밀도(프로그램 길이) | 높음(프로그램이 짧음)      | 낮음(명령어가 많아 길어짐)            |
| 컴파일러 부담        | 작음(하드웨어가 흡수)      | 큼(복잡함이 컴파일러로 이동)           |
| 파이프라인 적합성      | 상대적 불리            | 상대적 유리(동작은 소주제 4 참고)       |

핵심 대비는 "명령어 하나에 많은 일을 담아 하드웨어가 알아서 처리(CISC)" 대 "명령어를 잘게 단순하게 쪼개 규칙적으로 처리(RISC)"로 요약된다.

#### 4) 예시

같은 작업(메모리에 있는 두 값을 더해서 다시 메모리에 저장)을 두 방식이 어떻게 처리하는지의 대비다.&#x20;

```
CISC 스타일 — 한 명령이 메모리 접근과 연산을 함께:
ADD [C], [A], [B]      ; A와 B의 값을 더해 C에 저장 (개념 예시)

RISC 스타일 — 메모리 접근과 연산을 분리해 여러 명령으로:
LOAD  R1, [A]
LOAD  R2, [B]
ADD   R3, R1, R2       ; 레지스터끼리만 연산
STORE [C], R3
```

같은 일을 CISC는 개념적으로 한 명령으로, RISC는 load/store를 포함한 여러 명령으로 나눈다. \
이것이 "코드 밀도는 CISC가 높고, 명령어는 RISC가 단순하다"는 대비가 실제로 드러나는 지점이다.



> 💡 **TMI**
>
> * **겉은 CISC, 속은 RISC**: 의외의 반전은, 오늘날의 x86 CPU가 겉은 CISC지만 속은 RISC라는 점이다. 1995년 인텔 펜티엄 프로(P6) 이후로 x86 칩은 복잡한 CISC 명령을 내부에서 잘게 쪼개 'RISC식 마이크로 연산(micro-op)'으로 변환한 뒤 실행한다. 즉 두 진영의 대결은 "CISC 껍데기 안에 RISC 엔진을 넣는" 절충으로 귀결된 셈이다.
> * **철학은 RISC, 시장은 x86이라는 역설**: RISC가 설계 철학 논쟁에서는 사실상 이겼지만, 정작 수십 년간 PC 시장을 지배한 것은 CISC 계열 x86이었다. 반대로 스마트폰 시대에는 RISC 계열(ARM)이 압도했으니, 두 진영은 "어느 쪽이 옳은가"가 아니라 "어느 시장을 잡았는가"로 승부가 갈린 셈이다.
> * **CISC의 남은 무기, 코드 밀도**: CISC에도 RISC가 못 가진 장점이 있는데, 바로 코드 밀도(프로그램이 차지하는 메모리 크기)다. 명령 하나가 많은 일을 하는 CISC는 같은 작업을 더 적은 바이트로 표현한다. 그래서 대표적 RISC인 ARM조차 나중에 16비트 압축 명령 집합 'Thumb'을 추가해 CISC의 장점인 코드 밀도를 일부 흡수했다.

### 4. 명령어 파이프라인

단순하고 규칙적인 명령어가 _왜 실제로 빠른&#xAC00;_&#xB97C; 설명하는 핵심 장치가 파이프라인이다. RISC가 그런 설계를 택한 성능상의 이유가 여기서 드러난다.

#### 1) 개념 정의

명령어 하나를 처리하는 과정을 여러 단계로 쪼갠 뒤, 앞 명령어가 다음 단계로 넘어가는 순간 곧바로 뒤 명령어를 새로 밀어 넣어 여러 명령어의 서로 다른 단계를 '겹쳐서' 동시에 처리하는 기법이다.

#### 2) 원리 설명

명령어 하나를 실행하는 일은 원래 여러 작은 작업(인출·해석·실행 등)의 연속이다. \
파이프라인이 없으면 한 명령어가 이 작업들을 처음부터 끝까지 다 마쳐야 다음 명령어를 시작할 수 있어, 대부분의 부품이 자기 차례가 아닐 때는 놀고 있다. \
파이프라인은 각 단계를 담당하는 부품을 항상 바쁘게 만드는 발상이다.&#x20;

즉 인출 부품이 첫 명령어를 넘겨주고 나면 놀지 않고 곧바로 두 번째 명령어를 인출하기 시작한다. \
이렇게 단계를 겹치면 한 명령어를 끝내는 데 걸리는 시간(지연) 자체가 줄지는 않지만, 파이프라인이 가득 찬 뒤부터는 매 클럭마다 명령어 하나씩이 완료되어 나온다.&#x20;

결국 단위 시간당 완료되는 명령어 수, 즉 처리량(throughput)이 크게 오른다.

#### 3) 세부 메커니즘

명령어 처리를 흔히 다음 단계로 나눈다(단계 수와 이름은 설계마다 다르며, 아래는 대표적인 5단계 예시다).

* **인출(Fetch)**: 메모리에서 명령어를 가져온다.
* **해석(Decode)**: 가져온 명령어가 무슨 일을 시키는지 해독하고 필요한 값을 준비한다.
* **실행(Execute)**: 실제 연산을 수행한다.
* **메모리 접근(Memory)**: 필요하면 메모리에서 값을 읽거나 쓴다.
* **쓰기(Write Back)**: 결과를 레지스터에 저장한다.

각 단계 사이에는 앞 단계의 결과를 잠시 붙잡아 다음 클럭에 뒤 단계로 넘겨주는 저장 장치(래치)가 있다. \
그래서 매 클럭마다 모든 단계가 서로 다른 명령어를 하나씩 물고 한 칸씩 전진한다. \
파이프라인이 완전히 채워지면 다섯 개의 단계가 동시에 다섯 개의 명령어를 각각 다른 단계에서 처리하고, 그 결과 매 클럭 한 명령어씩 쏟아진다.

이때 고정 길이·단일 사이클로 설계된 명령어가 파이프라인을 매끄럽게 한다. \
명령어 길이가 일정하면 다음 명령어가 어디서 시작하는지 인출 단계에서 즉시 알 수 있어 해석이 단순해지고, 모든 명령어가 대체로 비슷한 일을 비슷한 시간에 끝내면 어느 한 단계에서 정체가 생기지 않아 각 칸이 매 클럭 규칙적으로 채워진다. \
파이프라인 속도는 가장 느린 단계에 좌우되므로 단계 길이를 고르게 맞추는 것이 중요하다.

한편 앞 명령어의 결과를 뒤 명령어가 곧바로 필요로 하거나, 분기 때문에 다음에 무엇을 인출할지 흔들리면 파이프라인이 잠시 막혀 빈칸(버블)이 생길 수 있다(해저드). \
이 경우 이상적인 "매 클럭 1명령어"에 조금 못 미치게 된다.

#### 4) 예시

**예시 1 — 3개 명령어를 5단계 파이프라인으로 처리**

명령어 A, B, C가 클럭마다 어느 단계에 있는지 나타낸 표다. (IF=인출, ID=해석, EX=실행, MEM=메모리, WB=쓰기)

| 클럭 | 1  | 2  | 3  | 4   | 5   | 6   | 7  |
| -- | -- | -- | -- | --- | --- | --- | -- |
| A  | IF | ID | EX | MEM | WB  |     |    |
| B  |    | IF | ID | EX  | MEM | WB  |    |
| C  |    |    | IF | ID  | EX  | MEM | WB |

* 클럭 3을 보면 A는 실행(EX), B는 해석(ID), C는 인출(IF) 단계에 동시에 놓여 있다. 세 명령어가 서로 다른 단계에서 나란히 처리되는 것이 파이프라인의 핵심 그림이다.
* 파이프라인이 없다면 명령어 하나가 5클럭을 온전히 쓰므로 3개에 5 × 3 = 15클럭이 든다.
* 파이프라인을 쓰면 첫 명령어가 완료되는 데 5클럭, 그 뒤로는 매 클럭 1개씩 나오므로 총 5 + (3 − 1) = 7클럭이면 끝난다.
* 일반화하면 명령어 n개, 단계 k개일 때 파이프라인은 약 (k + n − 1)클럭이 걸린다. n이 아주 커지면 명령어당 사실상 1클럭에 수렴하여, 이론적으로 단계 수(k)에 가까운 속도 향상을 얻는다.

**예시 2 — 세탁소 비유**

빨래 한 더미를 처리하는 데 세탁 → 건조 → 개기의 세 단계가 필요하다고 하자. \
한 더미를 완전히 끝낸 뒤에야 다음 더미를 시작하면(비파이프라인), 세탁기가 도는 동안 건조기와 접는 사람은 놀고 있다. 대신 첫 더미를 세탁기에서 건조기로 옮기는 즉시 두 번째 더미를 세탁기에 넣으면, 세탁·건조·개기가 서로 다른 더미를 두고 동시에 돌아간다. \
각 단계에 걸리는 시간은 그대로지만, 파이프라인이 가득 차면 한 단계 시간마다 빨래 한 더미가 완성되어 나온다. \
명령어 파이프라인이 처리량을 끌어올리는 원리가 이와 똑같다.



파이프라인이 잘 돌아가려면 명령어가 규칙적이고 단순해야 하는데, 이 요구가 바로 형제 소주제인 "축소 명령어 집합의 철학"(고정 길이·단일 사이클 지향)과 "복잡 명령어 집합과 축소 명령어 집합의 차이"로 이어진다. 파이프라인은 RISC가 왜 그런 설계를 택했는지를 성능 관점에서 설명해 주는 핵심 장치다.

> 💡 **TMI**
>
> * **조립 라인과 똑같은 발상**: 파이프라인은 흔히 자동차 조립 라인에 비유된다. 한 대를 완성하고 다음 차를 시작하는 대신, 여러 대를 각기 다른 공정에 동시에 올려 두어 전체 처리량을 높이는 방식이 CPU가 명령을 겹쳐 처리하는 원리와 똑같기 때문이다. 각 단계의 작업 시간은 그대로여도, '흐르게' 만들면 전체 속도가 몇 배로 뛴다.
> * **RISC보다 오래된 기술(1961)**: 파이프라인은 RISC보다 훨씬 오래됐다. 1961년 출하된 IBM 7030 '스트레치'가 선구적 사례로, 실행과 병행해 명령을 미리 최대 6개까지 앞서 읽고 해독하는 구조였다. 다만 스트레치는 기존 기계의 100\~200배를 목표로 했다가 실제로는 약 30배에 그쳐 IBM에 큰 굴욕을 안긴 프로젝트이기도 하다.
> * **5단계 파이프라인은 게임기 안에도**: 교과서의 전형적인 'RISC 5단계 파이프라인'은 뜻밖에도 게임기 안에 들어 있었다. 닌텐도 64의 CPU(VR4300, MIPS 계열)가 바로 5단계 파이프라인의 RISC 프로세서였다. 파이프라인 이론이 학술 개념이 아니라 1990년대 거실 게임기의 성능을 좌우한 실전 기술이었던 셈이다.

### 5. 천하에 명성을 떨치다

단순함이라는 설계가 뜻밖의 방향에서 세상을 바꾼다. \
그 단순함에서 따라온 저전력이 어떻게 RISC를 천하에 이름 떨치게 했는지 본다.

#### 1) 개념 정의

단순하고 전력을 적게 쓰는 축소 명령어 집합(RISC), 그중에서도 ARM 계열이 배터리로 돌아가는 모바일 기기 시장을 사실상 장악하고, 나아가 노트북·데스크톱·서버로까지 세력을 넓혀 온 성공의 역사를 가리킨다.

#### 2) 원리 설명

RISC는 명령어를 단순하게 유지하는 설계 철학 덕분에 회로가 간결하고, 그 결과 같은 일을 하면서도 전력을 덜 쓰고 발열이 적다. \
흥미로운 점은, RISC의 원래 출발점은 저전력이 아니라 단순함과 파이프라인을 통한 '성능'이었고, 저전력·저발열은 간결한 회로에서 따라온 부수 효과에 가까웠다는 것이다.&#x20;

그런데 이 부수 효과가, 콘센트에 꽂아 쓰는 데스크톱에서는 크게 중요하지 않았지만 한정된 배터리로 하루를 버텨야 하는 스마트폰에서는 곧바로 승부를 가르는 무기가 됐다. \
전력을 적게 먹을수록 배터리를 작게 만들고 기기를 얇고 가볍게 만들 수 있으며, 뜨거워지지 않으니 손에 쥐는 기기에 넣기 좋았기 때문이다. \
고성능 위주로 발전한 CISC(x86)와 달리 ARM은 이 저전력을 전면에 내세웠고, 스마트폰의 등장과 폭발적 성장과 함께 천하에 이름을 떨치게 됐다.

#### 3) 세부 메커니즘

성공은 기술적 우위 하나만으로 이뤄지지 않았고, ARM의 독특한 사업 방식이 확산을 가속했다.

* **저전력이 만든 시장 적합성**: 단순한 명령어 → 간결한 회로 → 낮은 소비 전력·발열이라는 연쇄가 "작은 배터리로 오래 가는 기기"를 가능하게 했고, 이것이 모바일이라는 거대 시장의 요구와 정확히 맞아떨어졌다.
* **IP 라이선싱 방식**: ARM은 칩을 직접 만들어 파는 회사가 아니라, 설계도(IP)를 다른 회사에 빌려주고 로열티를 받는 방식으로 사업을 한다. 애플·삼성·퀄컴 같은 여러 회사가 ARM 설계를 가져다 자기 칩을 만들 수 있으니, 한 회사가 독점 생산하는 구조보다 훨씬 빠르고 넓게 퍼졌다. 이렇게 여러 회사가 같은 명령어 체계를 공유하니 소프트웨어·개발 도구 같은 생태계도 함께 두터워졌고, 이는 다시 더 많은 채택을 부르는 선순환을 만들었다.

#### 4) 예시

* **스마트폰의 ARM 프로세서**: 오늘날 아이폰과 갤럭시를 비롯한 스마트폰의 두뇌(AP)는 대부분이 ARM 설계를 기반으로 한다(자료에 따라 90% 이상으로 집계된다). 즉 모바일 영역에서 RISC 계열은 사실상 표준의 자리를 차지했다.
* **애플 M1의 데스크톱 진출**: 2020년 애플은 자사 맥(Mac) 컴퓨터의 두뇌를 인텔의 x86(CISC) 칩에서 ARM 기반으로 갈아탄 M1 칩을 내놓았다. 저전력이라는 모바일용 강점을 그대로 노트북·데스크톱에 가져와, 냉각 팬 없이도 조용하고 배터리가 오래 가는 맥북에어를 실현했다. 모바일에서 통했던 RISC가 전통적으로 CISC의 영역이던 개인용 컴퓨터까지 넘본 상징적 사건이다.



이 소주제가 말하는 "왜 이겼는가"의 뿌리에는 형제 소주제인 "축소 명령어 집합의 철학"(단순함의 설계 원칙)과 "복잡 명령어 집합과 축소 명령어 집합의 차이"(RISC와 CISC의 기술적 대비)가 있다. 그리고 단순한 명령어가 실제로 성능까지 끌어올리는 원리는 "명령어 파이프라인"과 이어진다.

> 💡 **TMI** (책 범위 밖 보강)
>
> * **ARM의 저전력은 우연한 발견**: ARM의 상징인 초저전력은 원래 의도가 아니라 우연이었다. 초기 ARM1 칩을 시험하던 개발 보드에서 전원선에 전류가 제대로 공급되지 않았는데도 칩이 멀쩡히 돌아갔는데, 알고 보니 회로의 누설 전류만으로 동작하고 있었다(소비전력 약 0.1W). 설계자 소피 윌슨은 훗날 "오늘날 모든 휴대폰에 ARM이 들어가게 된 저전력 특성은 완전한 우연이었다"고 회고했다.
> * **ARM은 애플이 투자한 합작사**: ARM은 한 회사의 작품이 아니라 1990년 말 에이콘·애플·VLSI 세 회사의 합작으로 세워진 회사(Advanced RISC Machines)다. 특히 애플이 300만 달러를 투자했는데, 자사 PDA '뉴턴'에 쓸 저전력 칩이 필요했기 때문이다. 뉴턴은 흥행에 실패했지만, 그때 뿌려진 씨앗이 훗날 아이폰 시대에 거대하게 자라났다.
> * **손톱만 한 칩부터 슈퍼컴퓨터까지**: RISC가 저전력 기기만의 것이라는 편견을 깬 사건이 일본의 슈퍼컴퓨터 '후가쿠'다. ARM 계열 프로세서(후지쓰 A64FX)를 쓴 이 기계는 2020년 6월 TOP500에서 세계 1위에 올랐는데, ARM 아키텍처가 슈퍼컴퓨터 정상을 차지한 것은 이때가 처음이었다. RISC가 손톱만 한 칩부터 지구 최고 성능의 컴퓨터까지 아우른다는 것을 보여 준 순간이다.

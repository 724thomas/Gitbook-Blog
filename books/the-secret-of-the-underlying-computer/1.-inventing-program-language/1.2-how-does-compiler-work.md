# 1.2 How does Compiler work?

## 1.2 컴파일러는 어떻게 작동하는 것일까?

***

### 1. 컴파일러 (개요)

> 1.2.1 컴파일러는 그저 일반적인 프로그램일 뿐, 대단하지 않다

#### 개념 정의

컴파일러는 사람이 쓴 소스 코드를 기계가 실행할 수 있는 코드로 바꿔주는 평범한 프로그램이다.

#### 원리 설명

컴파일러는 입력을 받아 출력을 내놓는 보통의 프로그램과 다르지 않다. \
입력은 우리가 텍스트 편집기로 작성한 소스 코드 한 덩어리이고, 출력은 CPU가 직접 실행할 수 있는 기계어다. \
입력과 출력 사이에 있는 모든 과정은 사람이 직접 손으로 따라갈 수 있는 단순한 절차들의 연속이다.

#### 세부 메커니즘

이 처리 과정은 보통 다음과 같이 나뉜다.

1. **어휘 분석** — 소스 코드를 의미 있는 최소 단위인 토큰으로 자른다.
2. **구문 분석** — 토큰들을 문법에 맞춰 트리 구조로 엮는다.
3. **의미 분석** — 트리가 언어 규칙(타입, 선언 여부 등)에 맞는지 검사한다.
4. **중간 코드 생성** — 기계어보다 단순한 중간 형태로 옮긴다.
5. **코드 생성** — 중간 형태를 실제 기계어로 바꾼다.

컴파일러를 한 덩어리의 거대한 함수가 아니라 여러 단계로 쪼개는 이유는 각 단계마다 다루는 문제의 성격이 다르기 때문이다. \
글자 뭉치를 토막 내는 일과, 토막들을 문법 구조로 엮는 일과, 그 구조를 기계어로 옮기는 일은 모두 별개의 문제다.\
단계를 나누면 한 단계는 자기 일만 처리하고 다음 단계로 결과를 넘기면 되므로, 각 부분이 단순해지고 만들기도 고치기도 쉬워진다.

#### 예시

```c
int a = 1 + 2;
```

이 코드가 컴파일러를 통과하는 모습을 거칠게 따라가 보면 이렇다.&#x20;

* 먼저 어휘 분석이 이 문장을 `int`, `a`, `=`, `1`, `+`, `2`, `;`라는 토큰 목록으로 잘라 낸다.&#x20;
* 구문 분석은 이 토큰들을 "변수 `a`를 선언하면서 `1 + 2`라는 식의 값을 대입한다"라는 트리 모양으로 엮는다.&#x20;
* 의미 분석은 `a`가 중복 선언된 적이 없는지, 대입되는 값의 타입이 맞는지를 확인한다.&#x20;
* 그 뒤 중간 코드 생성과 코드 생성 단계를 거치면, 결국 "메모리의 어떤 자리에 정수 3을 써 넣어라" 같은 의미를 가진 기계어 명령들이 만들어진다.



컴파일러는 결국 "소스 코드를 받아 단계별로 변환을 거듭한 끝에 기계어를 내놓는 함수"이며, 다음 절부터 다룰 어휘 분석은 이 함수의 가장 첫 단계다.

### 2. 어휘 분석 (Lexical Analysis, Lexing)

> &#x20;1.2.2 각각의 토큰 추출하기

#### 개념 정의

어휘 분석은 소스 코드라는 문자열을 의미를 가진 최소 단위인 토큰들로 잘라 내는 과정이다.

#### 원리 설명

컴파일러에 처음 들어오는 소스 코드는 컴파일러 입장에서는 그저 한 줄로 길게 이어진 문자들의 나열일 뿐이다. \
사람은 한눈에 `int`가 키워드이고 `sum`이 변수 이름이라는 것을 알아보지만, 컴파일러에는 그저 `i`, `n`, `t`, 공백, `s`, `u`, `m` 같은 글자가 차례로 늘어서 있을 뿐이다.&#x20;

어휘 분석은 이 글자들을 훑으며&#x20;

* "여기서부터 여기까지는 키워드 하나",&#x20;
* "이 다음은 변수 이름",&#x20;
* "그 뒤는 연산자"

라는 식으로 의미 있는 덩어리로 묶는 일을 한다. 이렇게 묶인 한 덩어리를 **토큰**이라고 부른다.

#### 세부 메커니즘

토큰의 종류는 언어마다 조금씩 다르지만 대략 비슷하다.

* **키워드** — `int`, `return`처럼 언어가 미리 정해 둔 단어
* **식별자** — `sum`, `a` 같이 프로그래머가 붙인 이름
* **리터럴** — `1`, `2`, `3.14`처럼 값 자체
* **연산자** — `+`, `=`, `<` 같이 계산이나 비교
* **구분자** — `;`, `,`, `(`, `)` 같이 문장 구조를 나누는 기호

어휘 분석기는 글자들을 차례로 읽으며 공백과 주석은 건너뛰고, 의미 있는 글자들이 모이면 그것이 어떤 종류의 토큰인지를 판정해 다음 단계로 넘겨준다.

이 단계를 따로 두는 이유는, 다음 단계인 구문 분석이 글자 단위로 일하기에는 다뤄야 할 경우가 너무 많기 때문이다. \
어휘 분석이 미리 문자열을 토큰 단위로 깔끔하게 잘라 주면, 구문 분석은 글자 따위는 잊고 "키워드 다음에 식별자, 그다음에 등호 토큰" 같은 더 추상적인 수준에서 문법을 따져 볼 수 있다.

#### 예시

```c
int sum = a + b;
```

어휘 분석을 거치고 나면 이 문장은 아래와 같은 토큰들의 목록이 된다.

```
[키워드: int] [식별자: sum] [연산자: =] [식별자: a] [연산자: +] [식별자: b] [구분자: ;]
```

원래는 한 줄로 이어진 글자 더미였던 것이, 이제는 "무엇이 어떤 종류의 토큰인지"가 명시된 일곱 개로 정돈되었다.



구문 분석은 바로 이 토큰 목록을 입력으로 받아 문법 구조를 세우게 된다. \
어휘 분석은 첫 번째이자, 컴파일러 전체가 글자 더미를 구조화된 정보로 끌어올리기 위한 출발점이다.

### 3. 구문 분석 (Syntax Analysis, Parsing)

> 1.2.3 토큰이 표현하고자 하는 의미

#### 개념 정의

구문 분석은 일렬로 늘어선 토큰들을 정해진 문법 규칙에 따라 묶어, 그 안에 숨겨진 구조와 의미 관계를 트리 형태로 드러내는 단계다.

#### 원리 설명

어휘 분석을 거치면 우리는 토큰의 줄, 즉 "단어 목록"을 얻는다. \
그런데 단어를 늘어놓는 것만으로는 문장의 의미가 드러나지 않는다. \
어느 단어가 어느 단어와 한 덩어리인지, 무엇이 무엇을 꾸미는지, 어떤 연산이 먼저 일어나야 하는지가 보이지 않는 것이다. \
그래서 컴파일러는 토큰들을 다시 한 번 묶어 트리 모양으로 조립한다. \
이 트리가 바로 1구문 트리이며, 트리의 모양 자체가 곧 "이 코드가 무엇을 말하고 있는가"를 표현한다.

**왜 굳이 트리인가?** \
토큰을 일렬로 두면 `2 + 3 * 4`에서 2와 3을 먼저 더해야 할지, 3과 4를 먼저 곱해야 할지 줄 위에 적혀 있지 않다. \
트리로 묶으면 "안쪽 가지부터 먼저 계산한다"는 한 가지 규칙만으로 우선순위가 자동으로 결정된다.

#### 세부 메커니즘

구문 분석기는 미리 정해 둔 문법 규칙을 손에 들고 토큰을 하나씩 읽어 나간다. \
"변수 선언은 자료형 다음에 이름이 오고, 그 다음에 등호와 식이 따라온다" 같은 규칙에 비추어, 토큰들이 어느 규칙에 맞아떨어지는지 판정하며 묶음을 만들어 간다. \
묶음 안에 또 묶음이 들어가는 식으로 규칙을 거듭 적용하면, 결국 토큰 목록 전체가 하나의 트리로 조립된다. \
규칙에 어긋나는 토큰이 나타나면 그 자리에서 문법 오류로 보고된다.

#### 예시

```c
int sum = a + b * 10;
```

어휘 분석은 이 문장을 다음과 같은 토큰의 줄로 바꿔 놓는다.

```
[int] [sum] [=] [a] [+] [b] [*] [10] [;]
```

이 줄만으로는 `a + b * 10`이 `(a + b) * 10`인지 `a + (b * 10)`인지조차 알 수 없다. \
구문 분석기는 문법 규칙에 따라 토큰들을 묶어, 다음과 같은 트리를 만들어 낸다.

```
        변수 선언
      /    |    \
자료형:   이름:   초기값:
  int     sum       +
                   / \
                  a   *
                     / \
                    b  10
```

트리에서는 더 깊이 있는 묶음이 먼저 계산되므로, "곱셈이 덧셈보다 우선한다"는 연산자 우선순위가 트리의 모양 안에 자연스럽게 새겨진 셈이다. \
토큰을 늘어놓을 때는 보이지 않던 묶음과 우선순위가, 트리로 옮겨 놓는 순간 한눈에 드러난다.



구문 분석은 어휘 분석이 만들어 낸 토큰 스트림을 입력으로 받아, 구문 트리라는 새로운 형태로 변환한다. \
그리고 이 트리는 곧이어 살펴볼 의미 분석 단계의 입력이 되어, "문법은 맞는데 말이 되는가"를 따지는 다음 검사대로 넘어간다.

### 4. 의미 분석 (Semantic Analysis)

> 1.2.4 생성된 구문 트리에 이상은 없을까?

#### 개념 정의

의미 분석은 구문 트리가 문법적으로는 올바르더라도 실제로 말이 되는 코드인지 한 번 더 검사하는 단계다.

#### 원리 설명

앞 단계에서 만들어진 구문 트리는 어디까지나 "괄호가 맞고, 세미콜론이 제자리에 있고, 키워드 순서가 규칙에 맞는다"는 것만 보장한다. \
하지만 문법에 맞게 쓰였다고 해서 그 코드가 의미가 통하는 건 아니다.&#x20;

예를 들어 "나는 어제 내일 학교에 갔다"라는 문장은 단어 배열이 문법적으로는 멀쩡하지만 시제가 충돌해서 말이 안 된다. \
의미 분석은 코드에 대해서도 같은 방식으로 따져 본다. \
트리를 한 번 더 훑으면서 "이 표현이 진짜 말이 되는가?"를 검증하는 것이다.

#### 세부 메커니즘

의미 분석이 주로 잡아내는 것은 두 종류다.

* **존재 여부** — 변수가 쓰이기 전에 제대로 선언되었는지, 사용된 함수가 어디에 정의되어 있는지.
* **타입 일치** — 양쪽의 타입이 서로 어울리는지. 정수 자리에 문자열이 들어왔다거나, 함수 인자 개수가 안 맞는 경우.

검사를 위해 컴파일러는 지금까지 본 이름들을 표에 적어두고, 새 이름이 나올 때마다 그 표를 뒤진다. \
표에 없는 이름이면 미선언 오류, 표에 적힌 타입과 사용 자리의 타입이 안 맞으면 타입 오류.

#### 예시

다음 코드는 괄호와 세미콜론이 모두 제자리에 있어서 구문 트리는 무리 없이 만들어진다.

```c
int a = "hello";   // 정수 변수에 문자열 — 타입 불일치
int b = c + 1;     // c는 어디에도 선언된 적 없음 — 미해결 식별자
```

그러나 첫 줄은 정수 변수에 문자열을 넣으려 하고, 둘째 줄은 선언된 적 없는 `c`를 쓰고 있다. \
의미 분석 단계에서 두 줄 모두 오류로 걸린다.



의미 분석은 구문 분석이 만든 트리를 입력으로 받아, 그 트리가 "문법적으로 옳다"에서 "의미적으로도 옳다"로 검증을 한 단계 끌어올린 뒤 다음 단계로 넘겨준다.

### 5. 중간 코드

> 1.2.5 구문 트리를 기반으로 중간 코드 생성하기

#### 개념 정의

중간 코드는 의미 분석을 통과한 구문 트리를, 기계어보다는 단순하지만 원본 소스보다는 평탄한 형태로 한 번 더 변환한 결과물이다.

#### 원리 설명

컴파일러가 구문 트리에서 바로 기계어로 가지 않고 굳이 중간 단계를 하나 더 두는 이유는 두 가지다.

1. **구문 트리는 가지가 깊게 뻗어 있어 다루기 까다롭다.** \
   한 줄짜리 식이라도 그 안에 또 다른 식이 끼어 있어 한눈에 보기 어렵다.
2. **기계어는 CPU 종류마다 다르다.** \
   만약 구문 트리에서 곧장 어떤 한 CPU의 기계어로 내려가 버리면, 그 결과물은 다른 CPU에서는 쓸 수 없다.

#### 세부 메커니즘

그래서 컴파일러는 트리를 한 줄 한 줄 작은 조각으로 쪼개어 늘어놓는다. \
복잡하게 중첩된 계산을 임시 변수에 차례차례 담아 가는 식으로 풀어 쓰는 것이다. \
이렇게 펼쳐 두면 한 단계에 한 가지 일만 일어나므로 컴파일러가 코드를 분석하거나 다듬기가 훨씬 쉬워진다. \
게다가 이 형태는 아직 특정 CPU의 명령어가 아니므로, 같은 중간 코드를 두고 나중에 어느 기계의 기계어로 내릴지 따로 결정할 수 있다.

#### 예시

```c
sum = a + b * 10;
```

이 식은 곱셈과 덧셈이 한 줄 안에 섞여 있다. \
중간 코드 단계에서는 이것을 다음처럼 한 단계씩 풀어 늘어놓는다.

```
t1 = b * 10
t2 = a + t1
sum = t2
```

각 줄은 단순한 연산 하나만 수행한다. \
이 형태는 아직 어떤 CPU의 명령어도 아니므로 그 자체로는 실행되지 않지만, 그렇기에 오히려 다양한 기계로 옮겨 가기 좋다.



의미 분석을 통과한 구문 트리를 받아, 뒤이어 진짜 기계어를 만드는 단계가 작업하기 좋은 평탄한 형태로 다듬어 넘겨주는 다리 역할을 한다.

### 6. 코드 생성

> 1.2.6 코드 생성

#### 개념 정의

코드 생성은 컴파일러의 마지막 단계로, 중간 코드를 받아 실제 CPU가 실행할 수 있는 어셈블리/기계어로 바꾸는 과정이다.

#### 원리 설명

앞의 단계들에서 컴파일러는&#x20;

* 소스 코드를 분석하고,&#x20;
* 의미를 점검하고,&#x20;
* CPU에 종속되지 않은 중간 코드로 다듬어 왔다.&#x20;

코드 생성 단계가 하는 일은 단순하다. \
이 중간 코드를 한 줄씩 살펴보며 그에 대응하는 CPU 명령으로 옮겨 적는 것이다. \
중간 코드의 변수와 임시값은 CPU의 레지스터나 메모리 자리로 배치되고, 더하기·곱하기 같은 연산은 해당 CPU가 알아들을 수 있는 명령으로 치환된다. \
이렇게 나온 결과물이 우리가 흔히 보는 어셈블리 코드이며, 이를 다시 0과 1의 기계어로 옮기면 비로소 CPU가 직접 실행할 수 있는 형태가 된다.

#### 세부 메커니즘

중요한 점은, **같은 중간 코드라도 어떤 CPU를 목표로 하느냐에 따라 출력되는 어셈블리가 달라진다**는 것이다. \
CPU마다 사용할 수 있는 명령의 종류와 이름, 레지스터 개수가 모두 다르기 때문이다. \
그래서 컴파일러는 지원하려는 CPU의 종류만큼 코드 생성 단계를 따로 갖춰야 한다. \
앞쪽 단계(어휘·구문·의미 분석, 중간 코드 생성)는 CPU와 무관하게 공유할 수 있지만, 마지막 코드 생성 단계는 목표 CPU에 맞춰 새로 작성되어야 한다.

#### 예시

```
t1 = b * 10
t2 = a + t1
sum = t2
```

코드 생성기는 이를 대략 이런 모양의 어셈블리로 옮긴다.

```asm
load  R1, b       ; b를 레지스터 R1로 가져옴
mul   R1, R1, 10  ; R1 = b * 10   (t1)
load  R2, a       ; a를 레지스터 R2로 가져옴
add   R2, R2, R1  ; R2 = a + t1   (t2)
store R2, sum     ; sum에 결과 저장
```

중간 코드 한 줄이 보통 CPU 명령 한두 줄로 풀어진다. \
어떤 CPU를 목표로 하느냐에 따라 명령 이름이나 레지스터 표기는 달라지지만, 흐름은 비슷하다.



코드 생성의 입력은 중간 코드 생성이 만들어낸 중간 코드이고, 출력은 목표 CPU의 어셈블리/기계어다. 컴파일러의 앞단이 "무엇을 계산할지"를 정리해 두면, 뒷단인 코드 생성이 "이 CPU에서 어떻게 계산할지"를 결정한다.
